# ACE 精读：用需求门槛与网页证据评估消费建议

推荐一台符合预算的电脑，不能只在回答里写出一个低价格，还需要找到支持这个价格、型号和配置的网页。ACE 将消费建议拆成具体要求：先检查核心目标是否满足，再检查每条建议是否符合条件，以及需要外部证据的说法是否有来源支持。论文在四类任务上测试十个开启网页搜索的模型，最高平均分为 56.1%；购物领域最高为 45.4%。这些分数是包含门槛和负分的评分标准均值，不是完成购买的成功率。[论文第 2–5 节、表 2](https://arxiv.org/pdf/2512.04921v3#page=3)

## 评测对象是带约束的建议

ACE 给模型一段请求，部分请求还带有用户背景。送礼任务同时描述送礼者与收礼者，饮食任务可能指定份量、已有食材和器具，游戏任务可能要求兼容某个平台。模型通过搜索形成文字回答，不在模拟商城中下单，也不实际烹饪、维修或试玩游戏。

已有的知识或推理测试，无法直接说明一次推荐是否兼顾预算、偏好、兼容性和可用来源。ACE 的改变集中在评分：每题有自己的标准，满足核心要求是获得分数的前提，涉及网页事实的标准还要再次验证。它没有训练一个新模型，也没有提出新的搜索算法。[论文第 1、2、7 节](https://arxiv.org/pdf/2512.04921v3#page=1)

最初的提示较简短，一些专家在评分时期待价格或购买链接，但请求中并未明确写出。作者因此按工作流追加说明，让模型明确交代每个推荐是否满足要求，并在适用时提供来源、购买链接与价格。DIY 原始请求已足够具体，没有追加这一段。评测使用这种明确化后的提示，不能将结果直接外推到没有交代偏好的真实对话。[第 2.3 节、附录 C](https://arxiv.org/pdf/2512.04921v3#page=13)

## 一道送礼题如何变成九条标准

图 2 的公开任务 676 描述加拿大 Halifax 的一位用户，希望为弟弟推荐两款笔记本：单台购买预算为税后 800 加元，需要至少 512 GB 存储，并满足两人常玩的 Total War: WARHAMMER 2 的推荐配置。它要求给出两个备选型号，不是用 800 加元购买两台电脑。[图 2](https://arxiv.org/pdf/2512.04921v3#page=2)

九条标准分别检查：推荐数量、价格、显卡性能、CPU 性能、购买链接、内存、DirectX 支持、操作系统和存储容量。原图将价格标准标为门槛，除数量以外的八项要求网页证据。性能阈值包括 G3D Mark 不低于 5954、CPU Mark 不低于 5238；这些是该题评分标准中的阈值，本文没有据此另行验证实际游戏表现。

这个例子把两类判断分开：回答是否声称推荐的机器低于预算；来源网页是否支持对应型号与价格。只写出“符合预算”不能直接得到证据分。同样，存在一个能打开的网页，也不等于它支持推荐中每项配置。

## 从单条判断到最终得分

### 单条标准有三种结果

令第 $i$ 题第 $j$ 条标准的文本检查结果为 $a_{ij}\in\{0,1\}$，需要网页证据的标记为 $z_{ij}\in\{0,1\}$。当文本检查通过且需要证据时，再得到证据检查结果 $b_{ij}\in\{0,1\}$。按论文第 4 节与图 4，可将该标准的分数写为：

$$
q_{ij}=\begin{cases}
0,&a_{ij}=0,\\
1,&a_{ij}=1,\ z_{ij}=0,\\
1,&a_{ij}=1,\ z_{ij}=1,\ b_{ij}=1,\\
-1,&a_{ij}=1,\ z_{ij}=1,\ b_{ij}=0.
\end{cases}
$$

0 表示回答没有满足这一要求；−1 表示回答看起来满足要求，但相关说法未通过来源核验。后者比遗漏信息受到更重处罚。DIY 和 Food 的标准不走网页证据检查，Gaming 与 Shopping 的部分标准才走这条路径。[第 4 节](https://arxiv.org/pdf/2512.04921v3#page=5)

### 门槛控制整题得分

对含至少一条门槛的任务，设门槛标准集合为 $H_i$，题目共有 $m_i$ 条标准。固定公开代码要求所有门槛标准的最终分数都为 +1，随后保留整题标准分数之和：

$$
h_i=\mathbf1\{q_{ij}=1\text{ 对所有 }j\in H_i\},\qquad
s_i=h_i\frac{\sum_{j=1}^{m_i}q_{ij}}{m_i}.
$$

门槛本身也包含在分子、分母中，不是额外加分。价格门槛如果因来源不足得 −1，整题最终被置为 0；不能再把其余标准的负分当作最终题分。代码先并行评分所有标准，再计算门槛后的总分，因此“先过门槛”是计分逻辑，不代表实现一定先停止后续 API 调用。[评分实现](https://github.com/Mercor-Intelligence/apex-evals/blob/6cbf3f43156bf332329abe76ed4a695fc71ec5b0/ace/harness/autograder.py)

用一个自拟五条标准的例子说明：第一条为门槛，分数依次为 $1,1,1,-1,0$，最终为 $2/5=40\%$；如果第一条改为 0，整题变成 0。另一组 $1,-1,-1,-1,-1$ 在门槛通过时得 −60%。这些仅为算术示例，不是论文中的模型回答。

论文将证据型任务的通用理论范围写为 −100% 至 100%。对于实际至少有一条必须得 +1 的门槛的题目，不能同时让所有标准都为 −1 且通过门槛；具体可达下界还取决于门槛数量及证据标准配置。因此通用范围不表示每一道题都能达到 −100%。

### 多个推荐不能靠堆数量碰中答案

附录 A 描述一种全称要求：若返回三个商品，检查“都符合预算”时，三个都必须满足，并且都具有证据；一个缺乏证据就会使该项得 −1。这防止模型靠大量输出掩盖不符合要求的推荐。[附录 A](https://arxiv.org/pdf/2512.04921v3#page=10)

当前公开代码更具体地解释标准中的量词：`all`、`only`、`each` 要求全部通过，而“至少两个”等表述可以走 `per_product_any` 分支，仅要求达到指定数量。文章中的全称规则对应论文描述及具有全称含义的标准，不能泛化成当前代码对任何文字都强制全部通过。

## 网页证据是怎样取得的

评测框架先启用提供商的网页搜索，再把回答正文中的 URL 与 API 返回的来源信息合并、去重。接着用模型提取推荐或主要说法，把它们映射到相关链接，抓取网页正文，最后核对标准与证据。普通页面使用 Firecrawl，Reddit 有专用抓取逻辑，YouTube 通过 SearchAPI 获取字幕。购物链接还结合 `Shop vs. Product` 区分商家页与商品页。[附录 A、代码说明](https://github.com/Mercor-Intelligence/apex-evals/tree/6cbf3f43156bf332329abe76ed4a695fc71ec5b0/ace)

这里的证据是评测器重新抓取和抽取到的内容，不保证与回答生成时模型读到的内容完全相同。价格变动、地区差异、登录限制、动态页面以及抓取失败，都可能影响核验。论文承认发现少量提取错误，但没有报告一套足够详细的人工对照实验来分解抓取、映射与最终评判的误差率。[第 6.1、6.5 节](https://arxiv.org/pdf/2512.04921v3#page=8)

“未通过证据检查”因此是操作性定义，不能将每个 −1 都直接解释为已经人工确认的虚构事实。反过来，网页支持某个说法也不证明网页本身永远正确。

## 实验设置与统计单位

十个模型的回答于 2025 年 11 月底通过各自 API 收集，均启用搜索与思考。可设置的推理强度采用 High；Gemini 2.5 Flash、2.5 Pro 与 Opus 4.1 的思考预算约为 24K、32K、32K，Sonnet 4.5 与 Opus 4.5 约为 64K。Gemini 2.5 系列温度为 0.7，Gemini 3 Pro 为 1.0。不同提供商的搜索能力和推理设置并非同一个实现，所以这是整套模型服务配置的比较。[第 3 节](https://arxiv.org/pdf/2512.04921v3#page=4)

评判模型为 Gemini 2.5 Pro，温度 0；原文描述启用高思考。每模型每题生成八次，隐藏集共 $400\times8\times10=32,000$ 个回答，标准级判分超过 22 万次。论文报告八次得分的标准差平均为 16.4 个百分点，不是总榜分数的标准误。

设模型 $M$ 对题目 $i$ 第 $r$ 次的得分为 $s_{Mir}$，先计算：

$$
\bar s_{Mi}=\frac18\sum_{r=1}^{8}s_{Mir},\qquad
S_M=\frac1{400}\sum_{i=1}^{400}\bar s_{Mi}.
$$

总分按题目等权，不能将全部标准混在一起，使标准多的 DIY 任务获得更大权重。四领域各 100 题，因此领域均值也等权。

作者在题目层面做 10,000 次 bootstrap：总榜每次重采样 400 题，领域榜每次 100 题，得到 95% 区间。表格使用 bootstrap 均值，与原始均值相差小于 0.1 个百分点。这个过程重采样的是已聚合八次的题目成绩，不是把 32,000 个回答当作彼此独立的题目。[第 5 节、附录 D](https://arxiv.org/pdf/2512.04921v3#page=6)

## 证据失败与细项表现

证据检查只在前面的文本条件满足后触发。不同模型实际触发次数不同：跨八次运行，Opus 4.1 为 2,517 次，o3 Pro 为 4,209 次。GPT-5.1 的证据通过率最高，为 70.8%；Gemini 3 Pro 为 38.0%。这些是被触发检查的条件通过率，不能写成所有回答的事实准确率。[第 5.1 节](https://arxiv.org/pdf/2512.04921v3#page=6)

图 5 比较证据标准通过率与全部标准通过率，Gemini 3 Pro 的差值为 −27.6 个百分点，Opus 4.5 为 +12.0。后者表示在自己进入该检查的样本上相对表现较好，不表示它的总榜更高，也不是随机抽取相同断言后的公平事实性对照。

表 3 进一步显示，格式与数量要求通常容易于精细约束。例如 GPT-5 在 DIY 的逐步说明项为 99%，建议必要时咨询专业人员为 49%；GPT-5.1 在 Gaming 的兼容性为 60%，o3 Pro 为 35%。购物中的价格与链接项目可能出现负均值：Gemini 3 Pro 的价格项为 −28%，链接项为 −54%。由于标准分数包含 −1，这些数值是净分，不能称为负的通过概率。[表 3](https://arxiv.org/pdf/2512.04921v3#page=7)

论文没有给出关闭门槛、取消证据负分或替换抓取器的完整消融。因此它展示了指定评测机制下的差异，没有量化每个机制单独改变了多少模型排名或消费者体验。

## 开发集结果与版本差异

表 4 中公开集成绩都高于隐藏集，增幅约 1.3–4.8 个百分点；GPT-5.1 在公开集为 60.0%，GPT-5 为 59.3%，o3 Pro 为 59.5%。这表明公开集可用于理解方法，但模型次序并不完全相同，不能用开发集成绩代替隐藏榜单。[第 5.3 节、表 4](https://arxiv.org/pdf/2512.04921v3#page=8)

表 4 对 GPT-5.1 的隐藏分数打印为 55.2%，Gemini 3 Pro 为 45.6%，而主表与区间表为 55.1%、45.7%。本文保留主表作为主要结果，公开集列则按表 4 引用，不凭这些小差异推断另一次未披露的模型实验。公开任务数、门槛标记和分数的口径差异，都需要在复现记录里单独保留。

## 公开代码与可执行的复现入口

本次检查 `Mercor-Intelligence/apex-evals` 的提交 `6cbf3f43156bf332329abe76ed4a695fc71ec5b0`，ACE 位于独立子目录 `ace/`。数据仓库快照为 `dc24443aeba0f2a70ddb8d4de735c61ac175964d`。检查覆盖 CSV 装载、提供商调用配置、URL 与推荐抽取、证据映射、标准评分、门槛汇总及结果导出，没有运行模型或收费抓取服务。[固定代码](https://github.com/Mercor-Intelligence/apex-evals/tree/6cbf3f43156bf332329abe76ed4a695fc71ec5b0/ace)、[固定数据](https://huggingface.co/datasets/mercor/ace/tree/dc24443aeba0f2a70ddb8d4de735c61ac175964d)

| 环节 | 代码行为与复现影响 |
| --- | --- |
| 输入提示 | 优先使用 CSV 中 `Specified Prompt`，避免遗漏追加的明确要求 |
| 门槛与证据 | 从 `Hurdle Tag`、`Criterion Grounding Check` 读入，不应仅凭标准名称重新推断 |
| 判分模型 | `gemini-2.5-pro`、温度 0；生成配置没有显式固定论文所写的高思考预算，不能把服务默认值当成已锁定参数 |
| 抽取与映射 | 使用额外的 Gemini 2.5 Flash 调用，并不只需要被评模型的 API 权限 |
| 门槛总分 | 同时输出 `total_score` 和 `total_hurdle_score`；后者才应用门槛，仍需除以 `num_criteria` 得到题分 |
| 无门槛记录 | 当前实现直接把门槛后总分设为 0，导入自建任务时必须检查门槛标记 |
| 结果文件 | 原始回答、抓取内容、标准评分分别保存；存在最终评分 JSON 被用作完成标志 |
| 重试 | 未完成任务重新运行可能重新生成回答，不能默认是对同一个回答重复判分 |
| 统计 | 导出工具输出每次原始总分，不能直接替代八次题均值与题目层面 bootstrap |

评分器的异常处理也影响解释：部分限流错误会向上抛出，让任务重试；其他文本判定错误可能转成失败结果，来源内容缺失会使证据核验失败。抓取、解析或评判失败并不都被统一剔除。因此应把服务错误与模型错误分开审计，保存网页快照和每个阶段的理由，而不只保留最后一个分数。[评分器](https://github.com/Mercor-Intelligence/apex-evals/blob/6cbf3f43156bf332329abe76ed4a695fc71ec5b0/ace/harness/autograder.py)

环境要求 Python 3.11+、`uv` 和用于 URL 抽取的 `xurls`；网页处理使用 Firecrawl、SearchAPI，Supabase 为可选结果存储。依赖文件中多项采用最低版本约束，实际复现应同时固定 `uv.lock`。在已经配置服务与独立环境后，可以按官方入口只跑一道公开题：

```bash
# 在固定版本仓库的 ace/ 目录中
uv sync
uv pip install -e .
source .venv/bin/activate
python3 pipeline/init_from_dataset.py Shopping gemini-2.5-pro
python3 pipeline/test_single_task.py 676 gemini-2.5-pro 1 Shopping
```

这段命令是执行入口，不是本次已经运行的实验。一次任务仍包含搜索、网页抓取、映射和多个标准判分的调用；论文没有给出整套评估的可核实总费用。完整开发集比较需运行编号 1–8，并检查失败和缺失记录；隐藏榜单还需要未公开的 400 题。[README](https://github.com/Mercor-Intelligence/apex-evals/blob/6cbf3f43156bf332329abe76ed4a695fc71ec5b0/ace/README.md)

## 结果的适用范围

ACE 测量的是给定背景与明确要求下，模型服务生成消费建议的能力，以及其中一部分说法的网页证据支持程度。它不测实际购买是否成功、长期满意度、真实维修效果或多轮沟通中发现偏好的能力。首版只覆盖四领域与文字输入输出；搜索和网站持续变化，同一模型在另一日期运行也未必可直接比较。[第 6 节](https://arxiv.org/pdf/2512.04921v3#page=8)

公开开发集有利于调试，隐藏集降低了直接记题的风险，但无法证明不存在污染或面向评测的优化。本文覆盖 14 页正文及附录 A–D、核心评分公式、任务示例、结果与区间表，并核对上述代码和公开数据。性能数值采用作者报告；算术示例与代码观察已分别注明，尚未独立复现模型结果。

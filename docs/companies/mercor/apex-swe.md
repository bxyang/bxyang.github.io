# APEX-SWE：评测系统集成与故障排查能力

原文：[*APEX–SWE*](https://arxiv.org/abs/2601.08806v3)，2026 年 3 月 23 日 v3。

## 1. 摘要翻译

以下按原文顺序翻译；[论文采用 CC BY 4.0 许可](https://arxiv.org/abs/2601.08806v3)。

我们介绍面向软件工程的 AI 生产力指数（AI Productivity Index for Software Engineering，APEX-SWE），这是一项评估前沿 AI 模型能否执行具有经济价值的软件工程工作的基准。现有评测侧重范围较窄、定义明确的任务，而 APEX-SWE 评估两种反映实际软件工程的新任务类型：（1）集成任务，共 100 道，要求跨异构云基础组件、业务应用和基础设施即代码服务构建端到端系统；（2）可观测性任务，共 100 道，要求利用日志、监控面板等遥测信号，以及非结构化背景信息，排查生产故障。

我们为 APEX-SWE 排行榜评测了 11 个前沿模型。Claude Opus 4.6 以 40.5% 的 Pass@1 领先，Claude Opus 4.5 以 38.7% 紧随其后。我们的分析表明，较强的表现主要由认知上的严谨性驱动，即区分假设与已验证事实的能力。这种能力通常与行动前的系统性验证相结合。我们开放了 APEX-SWE 的评测框架，以及包含 50 道题的开发集。

## 2. 研究背景与相关研究

软件工程不仅包括编写代码，还包括连接已有服务、配置基础设施、分析日志和修复运行中的系统。任务说明往往只是起点：工程师需要核实服务接口、理解数据结构，确认系统现在怎样运行，再判断修改是否有效。

论文第 7 节将已有评测分为几条路线。HumanEval、MBPP 等主要检查独立函数生成；SWE-bench 及其扩展将范围扩大到真实仓库中的问题修复，但仍主要围绕单个仓库；其他智能体环境覆盖特定领域或模拟的软件公司任务。作者认为，这些路线尚未充分评测异构服务之间的集成，以及从日志、工单和讨论中诊断故障的过程。

APEX-SWE 因此保留自动测试的结果验证方式，同时改变模型开始工作时能看到的资料和环境。集成任务需要让多个组件共同运行；故障排查任务则不给模型现成的失败单元测试，而要求它从运行信号中定位问题。（原文 §1、§7）

## 3. 核心贡献

**核心要解决的问题。** 测量模型能否在多个服务与不完整的初始描述之间搜集事实、实现修改并验证结果，覆盖仅生成代码或修复单仓库问题难以充分反映的工程工作。

**核心方案。** 基准提供两组各 100 道隐藏任务。集成任务包含数据库、云服务模拟器和业务应用，要求模型实现可运行的工作流，例如读取工单要求、处理数据，再把结果上传到规定位置。故障排查任务提供代码、日志、开发者讨论及工单，要求模型找到根因并修复。

模型通过统一运行框架使用终端、文件和服务接口。集成任务由直接调用服务 API 的测试检查结果；故障排查任务既检查原先失败的测试是否修复，也检查已有功能是否保持正常。每题独立运行三次，以平均通过率报告 Pass@1，并另行开放 50 道开发题和评测代码。（原文 §2–4）

**结论。** 论文中的最高总体 Pass@1 为 40.5%。对轨迹的分析发现，成功案例通常会先查询环境、明确要求，再检查实际输出；失败案例常见未验证就宣布完成、误读接口或忽略日志截断等问题。作者将这种区分假设与事实、持续验证的习惯概括为“认知上的严谨性”。这来自轨迹的定性分析，并不意味着论文通过单独控制该因素证明了因果关系。

两类任务均显示，写出看似合理的代码还不足以可靠交付软件工程工作。结论对应这一版本的任务、模型和运行框架；网站后续排行榜的更新不属于本论文结果。（原文 §3–6）

# APEX-SWE：在多服务集成和故障排查中评测软件 agent

APEX-SWE 把软件 agent 放进运行着数据库、业务应用和日志服务的环境。任务可以是从项目工单中查明要求，把 CSV 上传到指定对象存储路径；也可以是根据日志和开发者讨论定位故障，再修改现有仓库。模型需要取得环境中的事实、完成实现并验证结果。论文在 200 道隐藏任务上评测 11 个模型，每题独立运行三次：Claude Opus 4.6 的平均单次通过率最高，为 40.5%。公开的 50 道开发题是另一套任务，不能用它们的结果直接替代隐藏榜单。（论文 §2、附录 B、表 6）

## 从代码修改扩展到运行中的系统

函数生成题通常把输入输出和目标函数直接交给模型。仓库修复题进一步要求模型理解项目、定位问题并提交补丁。APEX-SWE 保留代码操作，但把部分需求和诊断线索放到了外部服务中：工单说明目标，聊天记录提供讨论，日志记录实际异常，数据库和业务 API 保存最终状态。

论文把任务分为两类：

| 类别 | agent 需要完成的工作 | 正确性依据 |
| --- | --- | --- |
| Integration，集成 | 查询工单，理解服务接口与凭据，编写程序、配置资源，完成跨服务数据流 | pytest 直接查询服务 API，核对结果与交付物 |
| Observability，可观测性故障排查 | 从日志和讨论中识别异常，定位代码原因，修改仓库 | 原先失败的测试转为通过，原先通过的测试保持通过 |

“可观测性”在这里主要指利用日志等外部信号诊断程序运行状态。任务不是笼统地“给项目增加监控”。模型通常面对一个已有故障，需要利用监控环境找到并修复它。论文将这两类工作与单仓库修复、函数调用和业务应用操作基准区分；这说明任务形态不同，并不构成在相同模型和预算下优于所有前作的对照实验。（§1、§7）

## 任务如何制作，以及哪些题公开

### 集成题的来源与验证

集成题由具有至少三年经验的软件工程师制作。每题经过三阶段验证：检查提示是否与提供的源材料一致；检查测试是否评到了要求并避免可钻空子的评分；制作人类参考解，确认其通过全部测试。这个过程验证参考方案在环境中可执行，但论文未给出不同审核员间的一致率或每轮淘汰题数。（§3.1、图 3）

集成任务均配置临时 PostgreSQL 数据库与 Plane 项目管理服务。其他服务在隐藏集中的覆盖情况如下，比例可以重叠：

| 服务 | 任务占比 | 用途 |
| --- | ---: | --- |
| LocalStack | 56% | 在本地模拟 AWS 的 S3、Lambda、DynamoDB、Kinesis 等服务 |
| EspoCRM | 35% | 客户关系管理 |
| MailHog | 33% | 收集和检查 SMTP 测试邮件 |
| Mattermost | 32% | 团队聊天 |
| Medusa | 31% | 电商业务 |
| Zammad | 26% | 工单处理 |

模型还需要处理不同认证方式，例如 Basic Auth、JWT、IAM/STS、API key 和数据库连接字符串。论文要求从环境变量读取凭据，避免硬编码。这里描述的是基准要求；仅凭通过某个任务的功能测试，不能推定模型已经完成全面的安全审计。（§3.1）

### 故障排查题的来源与环境

Observability 题从真实 GitHub issue 与 PR 配对中构建。论文的筛选条件包括：仓库至少 350 stars，补丁至少涉及 100 行代码、三个文件，并检查测试覆盖和测试是否过度依赖特定实现。随后由至少三年经验的工程师转成任务。（§4.1）

环境包括代码工作区、Loki/Promtail 日志系统、Grafana，以及 Plane/Mattermost 工单与讨论服务。日志并非完整录制的真实生产流量：工程师编写 500–1,000 行正常运行日志，混入 10–20 行故障症状，用于重现诊断场景。聊天素材来自公开开发者讨论，例如 GitHub Discussions、Gitter，issue 素材来自仓库。

agent 获得用户问题概述、说明仓库相关函数的 `interface.md` 和 MCP 工具说明。评测材料另包含 `test.patch` 与 `golden.patch`：前者提供评分时应用的测试，后者是验证任务的参考修复。这里“不提供失败测试”指不把隐藏目标测试作为求解输入，并非代码仓库内完全没有测试可运行。公开开发包为了便于研究会同时发布评分与参考材料，使用时需要保持 agent 输入和评测端资料的边界。（§4.1；公开任务结构）

### 隐藏集与开发集的分布不同

| 数据范围 | 集成题 | 故障排查题 | 合计 |
| --- | ---: | ---: | ---: |
| 隐藏榜单 | 100 | 100 | 200 |
| 公开开发集 | 25 | 25 | 50 |

论文中隐藏 Observability 集的语言分布为 Go 30、Python 25、TypeScript 25、Java 10、C++ 10。本次逐个读取公开 25 题的 `test_metadata.json`，实际为 **Go 15、Python 10**，没有另外三种语言。因此，公开集的结果不能验证论文在 Java、TypeScript 或 C++ 上的结论。这个差异也意味着公开集和隐藏集不只需要关注样本量，还要关注具体任务构成。（表 4、附录 B；[固定数据版本](https://huggingface.co/datasets/mercor/APEX-SWE/tree/4d7aeb2b829ca348c224992da803bca6502235f4)）

任务文件带有禁止用于训练的 canary 标记，可帮助识别数据来源；它本身不是“训练中绝无污染”的证明。论文没有报告覆盖所有被测模型的污染审计。公开仓库 issue/PR 也与未公开任务包装是两个层次，需要分别考虑。

## 两道公开题的完整含义

### 上传用户快照：交付物和远端状态都要正确

公开集成题 `1-aws-s3-snapshots` 的工单要求读取现有 `users.csv`，上传到已经存在的 `users-snapshot-bucket`，对象键采用当天的 `snapshots/YYYY-MM-DD/users.csv`。交付文件为 `/app/upload_snapshot.py`，上传后输出确认信息，并验证对象存在。这道题先在 Plane 中提供工单标题，agent 需要查询工单正文才能取得完整细节。

它至少涉及四个连续步骤：取得需求；找到输入文件和服务配置；执行上传；重新查询对象存储，核对路径与内容。只生成一个看起来合理的 boto3 程序，还没有证明文件到了指定位置。

公开 `tests/test_outputs.py` 包含六项测试，检查脚本执行、脚本存在、桶存在、当天对象存在、CSV 必需列和实际数据。评分器通过 S3 API 读取对象，不是根据 agent 的“已完成”说明打分。代码还显示了要求与测试之间的具体边界：

- 工单指定 `upload_snapshot.py`，测试同时接受备用文件 `solution.py`。
- CSV 表头检查要求四个必需字段是实际字段的子集，并不排除额外列。
- 工单给出四分钟完成要求，而测试启动脚本时使用 120 秒的子进程超时。

这些是该公开题当前文件中的实现，不应推广为所有隐藏题的规则。它们也说明复现时需要同时读工单和测试，不能只凭文字要求重写一个评分器。（[该题文件](https://huggingface.co/datasets/mercor/APEX-SWE/tree/4d7aeb2b829ca348c224992da803bca6502235f4/Integration/1-aws-s3-snapshots)）

### 挂载路径回归：从现象定位代码修复范围

公开 Observability 题 `containers-podman-compose-1221-1231-observability` 描述 bind mount 指向了错误宿主机目录，要求通过日志确定路径解析问题并修复相对路径处理。模型面对的是症状说明，而不是直接收到最终补丁。

其评分元数据列出六个 FAIL_TO_PASS 测试，涉及 SELinux volume、相对宿主机路径和 home 目录；还列出 37 个 PASS_TO_PASS 测试，覆盖原本正常的环境变量、资源限制、网络等配置转换。任务目标既包括修好新问题，也包括不破坏已有行为。这里的测试数量来自公开文件统计；未执行容器，不能把静态列表等同于本机已成功跑过的 43 项测试。（[该题文件](https://huggingface.co/datasets/mercor/APEX-SWE/tree/4d7aeb2b829ca348c224992da803bca6502235f4/Observability/containers-podman-compose-1221-1231-observability)）

## agent 循环与评分公式

### 模型如何与环境交互

论文使用持续多步的 ReAct harness：模型接收系统提示和工具定义，调用终端、文件操作和 MCP 服务，再根据工具返回继续行动。终端通过持久 tmux 会话执行 Bash，工作区支持读写；MCP 提供 Loki、Plane、Medusa 等服务接口。模型输出 `<task_complete>` 或达到一小时墙钟时间上限时结束。（§2）

一次 episode 是交互过程中的一轮，不是独立任务，也不等于固定 token 数。整个框架没有训练新的参数，论文主要改变评测环境、任务和验证协议。

### 严格通过与部分测试通过的区别

用 $s_{ir}\in\{0,1\}$ 表示第 $i$ 题第 $r$ 次运行是否通过，$N$ 是题数。按照论文的三次独立运行定义，可以写成：

$$
\operatorname{Pass@1}=\frac{1}{3N}\sum_{i=1}^{N}\sum_{r=1}^{3}s_{ir},
\qquad
\operatorname{Pass@3}=\frac{1}{N}\sum_{i=1}^{N}\mathbf{1}\!\left[\sum_{r=1}^{3}s_{ir}>0\right].
$$

以上公式是对 §2 评分文字的展开，取值为 0–1，表格以百分数报告。Pass@1 是三次运行中的平均单次通过率，不是只看第一次；Pass@3 是三次至少成功一次的题目比例，不表示模型已经能在不知道答案时可靠选择正确结果。

**说明示例：**三道题分别通过 3 次、1 次、0 次，那么 Pass@1 为 $4/9=44.4\%$，Pass@3 为 $2/3=66.7\%$。把三次请求当成一次工作流，成本与单次运行也不同。

对于故障排查题，设 $F_i$ 是 FAIL_TO_PASS 测试集合，$P_i$ 是 PASS_TO_PASS 集合，则严格成功需要：

$$
s_{ir}=\mathbf{1}\!\left[\forall t\in F_i,\ t\text{通过}\right]
\cdot\mathbf{1}\!\left[\forall t\in P_i,\ t\text{通过}\right].
$$

公开 `parser/eval_utils.py` 对应这个全通过逻辑，另外明确规定空的 FAIL_TO_PASS 集合不能验证修复，判为失败。单项成功比例可以用于诊断，但论文榜单不按“六项修好五项”给部分成功分。测试日志仍需由具体语言框架解析、匹配测试 ID；评分可靠性还依赖任务元数据和解析器，不能仅由上述公式保证。

两类隐藏题各 100 道，因此总榜单是两类 Pass@1 的等权平均。使用已四舍五入的一位小数重算时可能有末位差异，以下保留原表总分。

## 模型与预算设置

论文评测 11 个模型，所有模型每题三次独立运行。附录 A 使用 LiteLLM 调用接口，单请求失败时按指数退避重试，最多三次尝试。这类请求重试与三次完整任务运行是不同的计数。（§2、附录 A）

| 模型 | 论文上下文窗口 | 最大输出 | 思考配置 |
| --- | ---: | ---: | --- |
| Claude Opus 4.5 | 200,000 | 64,000 | High |
| Claude Opus 4.6 | 1,000,000 | 128,000 | High |
| Claude Sonnet 4.5 | 200,000 | 64,000 | High |
| Cognition SWE-1.6 Preview | 180,000 | 未列 | High |
| DeepSeek V3.2 | 262,144 | 30,000 | NA |
| Gemini 3 Pro | 1,000,000 | 65,536 | High |
| GPT-5.1 Codex / GPT-5.2 Codex | 272,000 | 128,000 | High |
| Grok 4 | 256,000 | 128,000 | 默认开启 |
| Kimi K2 Instruct / Kimi K2.5 | 262,144 | 32,768 | NA |

数值来自表 5，描述实验设置，不是对当前产品规格的更新。正文概括为 High，但附录对 DeepSeek、Kimi 明确列 NA，不能改写成每个模型都启用了同一种思考模式。窗口和最大输出也不等于每题实际消耗，论文没有给出统一 token 成本或费用表。

若 11 个模型完整执行 200 道隐藏题各三次，共对应 6,600 次任务运行；这是按实验设计计算的次数，不包括工具服务启动、接口失败重试和公开开发集评测。论文没有提供每个模型总账单、完整原始轨迹或主表的置信区间，不能由一小时上限推出实际平均耗时。

Opus 4.6 的总分比 Opus 4.5 高 1.8 个百分点，但集成题低 1.4 点，排障题高 5.0 点。这是总分和分项排名不同的具体来源。Grok 4 的集成与排障单次成绩相差 30.6 点；DeepSeek V3.2 则排障高于集成。不能把某一类任务的排序当成跨场景通用能力排序。

还有一处正文与数字不一致：§4.2 称 Opus 4.6 从 31.7% 到 39.0% 的 7.3 点是最大 Pass@3 增益，但表 3 中 Gemini 3 Pro 从 19.7% 到 31.0%，增益为 11.3 点，GPT-5.1 Codex 和 SWE-1.6 Preview 也分别增加 10.7、10.0 点。按表中数据，Opus 4.6 的绝对 Pass@3 最高，增益并非最大。

### 编程语言与服务数量分析

表 4 的跨模型平均单次通过率为：Python 27.3%、Go 20.4%、C++ 20.0%、TypeScript 12.1%、Java 10.0%。这些语言组题量分别为 25、30、10、25、10，道题涉及的仓库和问题也不同。作者将差异与运行时反馈、类型系统和项目框架联系起来；论文没有把同一问题翻译成不同语言后做受控比较，因此不能把 17.3 点的 Python–Java 差距直接解释为语言本身的因果效果。

§7 另外报告，53 道单服务题的平均 Pass@1 为 39.5%，47 道多服务题为 18.6%，差 20.9 点。论文此前又说所有集成题均带 PostgreSQL 和 Plane，因而这里的“服务数”不宜直接理解为部署容器总数；正文未完整说明哪些基础服务被排除。两组本身也不是只改变服务数量的配对任务，结果说明分组相关性，不是增加一个服务必然造成多少性能下降。

## 轨迹分析：观察到的行为与尚未验证的机制

作者把一种常见成功行为称为 epistemic discipline：区分假设和已经验证的事实。具体而言，集成任务先查询服务配置和接口，提取精确要求，完成后重新读取状态；排障任务逐步筛选日志，从不同信息源核对症状，再修改代码。（§3.3、§4.3）

在所分析的成功集成轨迹中，70.5% 在实现前读环境配置，95.0% 查询外部 API。所分析的成功排障轨迹全部使用了 Loki 之外至少一个 MCP 工具，修改前平均读 11.3 个文件。论文没有给出这些定性分析子样本的完整数量、抽样规则、审阅一致性或逐条标注文件。因此，“100%”的分母是作者分析的成功轨迹，不是所有任务，也不是所有成功运行。

一个排障案例中，Opus 4.5 首次查询得到 15,729 字符日志，随后加 LogQL 过滤缩到 2,354 字符，再缩到 264 字符，从而隔离相关错误。相比之下，论文记录 DeepSeek V3.2 一次取得 16,515 字符、出现截断提示后仍继续修改。这些案例解释了“逐步查询”的实际动作，但不是随机分配模型是否过滤日志的消融实验。

| 排障 | 验证不足 | 28% |
| 排障 | 基础设施相关失败 | 18% |
| 排障 | 执行失败 | 16% |

来源为图 4、图 6 与相邻正文。论文使用 failure signals 等表述，未充分交代一个轨迹能否产生多个信号、分层标签如何汇总，因此这些百分比不应乘以“100 道题”换算成失败题数。

集成案例包括：脚本发出库存邮件但产品数为三而实际为六，七项测试只过五项；直接用错误认证调用 Plane，反复收到 403，最终报告零项完成工单；邮件业务执行了，但主题、正文格式或数量不满足要求。排障案例包括忽略日志截断、只查单一来源、工具参数格式错误反复重试，以及修改后不运行验证。（§3.4、§4.4）

“基础设施相关失败”在这里包含模型错误使用工具引发的失败，不全是服务器宕机。论文还报告 Grok 4 的大量 `str_replace` 首次调用失败、DeepSeek 的 `view_file` 参数错误；这些观察同时受模型和工具接口设计影响。

### 交互轮数不是生产率测量

表 2 报告集成题各模型平均轮数：成功运行平均 44.9 轮，失败运行 59.6 轮；Opus 4.6 全部运行平均 48.6 轮，成功时 38.5 轮；Kimi K2 Instruct 全部运行仅 19.2 轮，但单次通过率为 18.3%。更少轮数既可能来自有效求解，也可能来自较早停止。

论文把验证习惯与成功联系起来，但没有报告移除验证工具、强制模型验证或保持其他因素一致的机制消融。也没有人类与 agent 的配对耗时实验。因此标题中的 Productivity Index 在本文中是任务完成能力指标，不能直接转译为工程师节省的工时或可替代岗位比例。

## Rubric 评分是另一条分析线

除了严格通过率，论文还让 Gemini 3 Pro 独立评判工程师为每题编写的 rubric，配置为温度 0.1、High thinking。judge 阅读最终补丁和执行日志，分别评估：功能行为是否满足要求；对异常、边界条件的健壮性；以及仅用于排障题的代码风格、文档与仓库惯例。（§5）

**Rubric 不参与榜单总分。**它与程序化全通过测量的是不同对象。例如，Kimi K2 Instruct 在集成题的 rubric quality 为 75.0%，但 Pass@1 为 18.3%；功能分 78.0%、健壮性 72.1%。代码可以在多个局部要求上合理，最终服务状态仍不正确。相反，通过有限测试也不意味着所有健壮性要求都已满足。Grok 4 集成 Pass@1 为 36.3%，健壮性评分为 46.4%。（§5.1、图 7）

论文没有给出该 judge 与独立人工评分的一致性实验，也没有完整说明不同题目和 rubric 类别的权重汇总方式。因此，本文保留报告值，不从它推导新的综合指数，不把模型裁判分数当成已验证的代码维护成本。

## 开发集分数为何不能替代榜单

附录 B 比较了两套题的总 Pass@1。以下保留几个能显示排名变化的模型：

| 模型 | 隐藏 200 题 | 公开 50 题 | 公开减隐藏 |
| --- | ---: | ---: | ---: |
| Claude Opus 4.6 | 40.5% | 58.7% | +18.2 点 |
| Claude Opus 4.5 | 38.7% | 57.3% | +18.6 点 |
| Cognition SWE-1.6 Preview | 31.7% | 52.7% | +21.0 点 |
| Kimi K2.5 | 30.3% | 50.0% | +19.7 点 |
| GPT-5.2 Codex | 30.8% | 40.7% | +9.9 点 |
| Gemini 3 Pro | 26.8% | 41.3% | +14.5 点 |

表 6 中前两名和末三名的位置保持一致，但 Kimi K2.5 从第六升至第四，GPT-5.2 Codex 从第五降到第七。论文报告跨模型平均为公开集 40.7%、隐藏集 27.9%，相差 12.8 点。

作者将差异归于较小样本量。较少题目会使估计更不稳定，但论文没有给出重采样或难度匹配实验，不能仅凭题量解释所有模型公开集系统性更高的分数；公开语言分布也与隐藏集不同。准确复现应标明所用集合，不能用“APEX-SWE 分数”掩盖这两个分母。

## 公开代码与复现步骤

本次检查固定在代码提交 [`7cfa580dd59704ff15cf558bda80257c23b6cb04`](https://github.com/Mercor-Intelligence/apex-swe/tree/7cfa580dd59704ff15cf558bda80257c23b6cb04)，数据版本 [`4d7aeb2b829ca348c224992da803bca6502235f4`](https://huggingface.co/datasets/mercor/APEX-SWE/tree/4d7aeb2b829ca348c224992da803bca6502235f4)。这些是本次读取的公开快照，并非论文声明的实验锁定版本。

### 先准备任务，再分别运行两套 harness

仓库分别提供 `integration/` 和 `observability/`，二者不是同一 CLI。基础依赖包括 Python、Docker、模型 API key 和任务镜像/服务。Integration 文档给出 8 GB 最低内存、16 GB 推荐内存；这只是运行建议，不是本文实测的吞吐或资源开销。公开代码为 MIT 许可，任务数据标注 CC BY 4.0，任务中的上游仓库和组件仍需对应其各自许可。

应先下载固定版本的任务目录，将两类题放到对应 harness 可识别的位置，保留代码、数据、镜像和模型配置。数据集是文件树，不能假定一次通用表格加载就能得到完整容器任务。

Integration 的安装脚本实际位于 `integration/install.sh`。根 README 示例从根目录执行 `./install.sh`，与本次目录树不符；应进入该子目录后安装。以下是根据源码整理的单题入口，**尚未执行模型评测**：

```bash
cd integration
./install.sh
source venv/bin/activate
apx run apex-swe-dev-check \
  --tasks 1-aws-s3-snapshots \
  --tasks-dir /absolute/path/to/Integration \
  --models claude-opus-4-6 \
  --n-trials 3 \
  --timeout 3600 \
  --reasoning-effort high
```

`--tasks-dir` 需要替换为下载任务的实际绝对路径。`src/main.py` 的默认超时为 **900 秒**，并非论文的一小时，因而必须显式调整。默认试验数为三次，与论文重复次数一致，但仅使用默认参数不能说明其余实验设置已经匹配。

Observability 的 `run_e2e.py` 默认一小时，但默认只运行一次、reasoning 为 medium、message limit 为 250。对单题三次运行，需要分别使用 `--trial 1`、`2`、`3` 并保留独立输出；并行模式提供 `--trials` 参数。其单次入口形如：

```bash
cd observability
python run_e2e.py \
  --task containers-podman-compose-1221-1231-observability \
  --model claude-opus-4-6 \
  --trial 1 \
  --time-limit 3600 \
  --reasoning high
```

运行前还需按该子目录 README 安装依赖、配置任务及模型凭据。上面不是已经验证通过的全自动安装脚本。当前 harness 支持的模型名单也比论文更多，不能把新增模型结果拼入 v3 主表后仍标为原论文结果。

### 结果核对应保留到测试级别

Integration 应保存每次 agent 日志、测试输出、`passed` 状态和实际服务产物。Observability 应保存最终补丁、测试框架输出、F2P/P2P 逐项匹配结果和超时信息。源码的评分准备流程会应用测试补丁，参考解只在相应验证模式下使用；正式评测 agent 时不能用参考解替换模型补丁。

尤其需要区分三类失败：模型没有完成要求；环境或测试不能正常启动；输出解析无法确认结果。只保存最终一个百分数，会丢失诊断这些差异所需的证据。论文未提供足以独立重建全部隐藏题结果的公开材料，所以目前能进行的是公开开发集复现，而非自行完整复现 200 题榜单。

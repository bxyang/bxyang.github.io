# ResearchRubrics：用细项标准评测深度研究报告

要求研究助手分析社交媒体对社会的影响，答案可以有不同结论，却仍应覆盖多个社会领域、比较正反证据，并为重要判断提供依据。只检查结论是否与参考答案相同，难以评估这样的报告。ResearchRubrics 为 101 个开放式研究问题编写了 2,593 条人工评分标准，让评审者逐项检查回答，再按重要程度汇总。论文中的 Gemini、OpenAI 和 Perplexity 深度研究系统，三元评分均值分别为 67.7%、66.4% 和 56.6%；这些是带正负权重的标准符合分，不是整篇报告完全正确的比例。[论文 §3–4、表 5](https://arxiv.org/pdf/2511.07685v1)

本文研究的是对已经生成的研究报告进行评测，没有提出新的深度研究生成模型，也没有报告用这些标准训练一个新模型的收益。

## 开放问题需要可检查的具体要求

论文中的社交媒体题要求逐领域比较影响。对应标准可以要求覆盖至少五个社会领域，可以奖励提到相关政策，也可以扣除没有证据的笼统心理健康结论。即使两篇报告最后分别认为利大于弊、弊大于利，也可以依据这些共同要求评分。

评分标准不是参考报告的逐句清单。一条标准中的示例用于说明可以接受的证据或论证，并非必须逐项照抄的唯一答案。原评审提示也明确说明示例并不穷尽所有正确回答。[论文图 1、附录 E](https://arxiv.org/pdf/2511.07685v1)

ResearchRubrics 主要评估报告中可见的事实、推理与表达。它不会因为报告很长、搜索很多次或引用很多条，就自动判定研究过程可靠。公开评分器接收 Markdown 报告，没有重新运行代理的搜索过程，也没有浏览引用网页逐一验证来源。

## 101 道任务如何写成

每个问题和每条标准都由人编写，论文明确说没有用 LLM 生成初稿。流程包含三个分开的角色：第一位专家提出问题与标准；第二位专家审阅，与第一位反复修改；第三位独立终审并调整。问题灵感来自用户论坛、问答网站和头脑风暴，再改写为完整研究任务。[论文 §3.1、图 2](https://arxiv.org/pdf/2511.07685v1)

这里“专家”的定义是具有较强 STEM 背景、擅长任务设计与评估，并选择自己熟悉的领域，不表示每道题都由该领域持证专业人士制作。三人是每条任务的角色配置，不是整项研究只有三位参与者。论文报告累计超过 2,800 小时人工工作，但没有细分创作、审核、标注各阶段工时，也未给出报酬、初稿总量、淘汰率和全部贡献者人数。

全部任务都是单轮问题，每题有 20–43 条标准，平均约 25.67 条。单轮描述的是用户交付问题的方式，不表示代理内部只检索或推理一步。数据是评测集合，没有论文定义的训练、开发拆分。

## 标准的类别、正负号与必选性

论文设计六个质量维度：显式要求、隐式要求、信息综合、引用与证据、表达质量、指令遵循。显式要求检查用户直接提出的内容；隐式要求检查一份充分回答应交代但用户未逐字要求的背景；信息综合则检查能否将不同材料联系起来，而不是只列事实。

每题覆盖 3–6 个维度，图 9 的任务数分别是 12、24、43、22，平均约 4.74 类。维度覆盖不是所有任务一律六项齐全，计算分类均值时需要留意各类出现在哪些题中。

标准的权重带正负号：正值奖励某种属性存在，负值表示某种不应出现的行为，命中时扣分。论文规定 $|w|\geq4$ 为 mandatory，较小绝对值为 optional；“必选负项”意味着必须避免该错误，不能理解为必须满足其文字描述。[论文 §3.3、表 3–4](https://arxiv.org/pdf/2511.07685v1)

分数本身仍是加权和，没有“只要任一 mandatory 失败就整题得零”的门控，也没有报告全部必选项同时通过的总体通过率。高平均分与是否满足最低完整要求，不能直接等同。

## 带负权重的评分分母

设第 $k$ 题的标准集合为 $C_k$，标准 $i$ 的权重为 $w_i$。三元裁判给出

$$
m_i=\begin{cases}
1,&\text{完全满足},\\
0.5,&\text{部分满足},\\
0,&\text{不满足}.
\end{cases}
$$

单题分数是

$$
S_k=\frac{\sum_{i\in C_k}w_im_i}{\sum_{i\in C_k:w_i>0}w_i}.
$$

分子包含正负权重，分母只包含正权重。最后按题等权平均，而不是把全数据集所有标准直接汇总；标准更多的任务不会自动获得更大任务权重。公开 `calculate_compliance_score.py` 与这一任务级归一化一致。[论文式 1](https://arxiv.org/pdf/2511.07685v1)、[固定评分代码](https://github.com/scaleapi/researchrubrics/blob/2dc80e2d4c38ddd80439517c259d93c6954b193f/src/calculate_metrics/calculate_compliance_score.py)

以下是根据图 1 简化的说明：三项权重为 $+5,+3,-4$，分别完全满足、不满足、部分满足，分数为 $(5+0-2)/(5+3)=0.375$。负项部分满足表示部分出现了不良行为，所以扣 2 分。

二元方案将“部分满足”合并为“不满足”。同一个例子的二元分数反而变为 $5/8=0.625$，因为原来部分命中的负项不再扣分。因此从三元改成二元不保证每题都降分。论文的三套系统总体均值确实下降，但这是实际判定汇总结果，不是对任意正负标准都成立的数学性质。

单题分数上界为 1，下界可以小于零。官方脚本没有把负数截断为零。本次用两条自拟记录离线检查：正项 $+5$ 未通过、负项 $-4$ 命中，脚本输出 $-0.8$。这只检查汇总逻辑，没有调用模型。

## 模型评审怎样读取报告

论文先收集三个商业深度研究系统生成的 PDF，再转为 Markdown 评审。三种裁判为 GPT-5、Claude Sonnet 4.5、Gemini 2.5 Pro；裁判对每条标准分别输出判定、分数、信心值、依据与缺失内容。论文附录图 19 实际是评审提示，图 20 实际是删除示例的提示，两处图注写反，本文按框内内容识别用途。[论文 §4.1、附录 E](https://arxiv.org/pdf/2511.07685v1)

评审提示要求只依据报告里出现的内容，不补猜隐含信息；但它没有附带检索工具或引用网页正文。报告出现了一个链接，不等于裁判已经打开链接验证该来源真正支持结论。JSON 中的 confidence 也只是模型自报信心，没有作为分数权重，也没有经过可靠性校准。

论文没有完整给出被测商业代理的底层版本、订阅档位、生成日期、系统设置、澄清问题如何处理、搜索预算或生成温度。公开代码固定了一个 Gemini 裁判路由，但这不能倒推生成报告时的 Gemini DR 底层配置。它也不等于严格相同计算预算下的三个模型比较。

### 逻辑深度分析支持相关性，不支持架构归因

三元评分中，逻辑嵌套从浅、中等到深：Gemini 为 71.9%、67.1%、66.1%，OpenAI 为 69.1%、66.5%、64.9%，Perplexity 为 59.3%、56.0%、55.9%。三者在这一分组上都下降。[论文图 6、附录图 12–13](https://arxiv.org/pdf/2511.07685v1)

其他轴没有统一单调关系。Perplexity 概念广度三个等级为 58.1%、55.2%、57.8%，探索程度为 55.5%、57.1%、56.7%。这些题目同时可能在领域、长度、标准数量上不同，没有配对控制实验来隔离每条轴的因果作用。

正文将若干趋势归因为架构瓶颈，还提到“超过四步或 35 分钟发生普遍崩溃”等解释；公开图表没有提供对应的时间实验或架构消融，深任务的均值也并非接近零。因此本页只保留按复杂度分组的观察，不沿用这些更强归因。

## 失败图不是每一类标准的错误率

论文式 2 定义：对含类别 $c$ 的任务集合 $T_c$，先计算每道题中该类失败条数占该题全部失败条数的比例，再在 $T_c$ 内平均：

$$
F_c=\frac1{|T_c|}\sum_{t\in T_c}
\frac{n_{\mathrm{fail},c,t}}{n_{\mathrm{fail},t}}.
$$

分母不是该题该类别的标准总数。因此 $F_c$ 并非“此类标准有多少比例不合格”；不同类别的 $T_c$ 又不同，各类数值也不必合计 100%。[论文式 2](https://arxiv.org/pdf/2511.07685v1)

图 5 的三元值中，隐式要求为 45.0%、45.3%、46.6%，信息综合为 25.4%、25.6%、25.7%，分别对应 Perplexity、Gemini、OpenAI。不能把正文“二者合计占全部失败的 45%–50%”当作这张图的正确读法：隐式要求一项已在该范围，而且这些分别平均的比值不能直接相加成为一个总体占比。

还有两处实现定义未明确。式 2 文字把失败定义为 `Not Satisfied`，但对负权重标准，不满足其负面描述往往是正确行为；论文没有说明作失败图时是否将负项翻转。若一题没有失败，分母为零时怎样处理也没有写清。官方发布的代码只包含符合分计算，没有对应失败分析实现，所以无法用它消除这两处歧义。

图 8 按必选、可选标准区分，三元隐式项分别为 46.3% 和 60.4%，显式项则为 55.4% 和 25.9%。这表示图中两种分组统计存在差别；未公开具体计算代码和全部分母，不能据此推算系统在多少任务上达到“最低可用”的全部要求。

## 人类与模型评审的一致性

九位人工标注者参与了 303 份回答的评审，对应 101 题乘以三套系统。论文用 Macro F1 比较人工标签和模型标签：对每个类别分别计算

$$
F1_c=\frac{2TP_c}{2TP_c+FP_c+FN_c},\qquad
\operatorname{MacroF1}=\frac1L\sum_{c=1}^{L}F1_c.
$$

三元时 $L=3$，二元时 $L=2$。这里类别指完全满足、部分满足、不满足等判定标签，不是前面的六个内容维度。Macro F1 对标签等权，并不等于所有判断中正确判断所占百分比。[论文 §3.4、表 6](https://arxiv.org/pdf/2511.07685v1)

| 被评系统 | GPT-5，二元 / 三元 | Claude 4.5，二元 / 三元 | Gemini 2.5 Pro，二元 / 三元 |
| --- | --- | --- | --- |
| Perplexity DR | 0.717 / 0.538 | 0.718 / 0.528 | 0.724 / 0.559 |
| Gemini DR | 0.732 / 0.553 | 0.741 / 0.532 | 0.760 / 0.567 |
| OpenAI DR | 0.719 / 0.546 | 0.742 / 0.527 | 0.721 / 0.557 |

将部分满足合并后，F1 提高约 0.164–0.215。二元任务同时减少了标签数，不能仅凭跨标签空间的 F1 差值断言三元评分没有用途。它支持的观察是：在此人工协议下，完全满足与其余情况的边界更容易由模型复现。

Gemini 裁判取得表内最高单格 0.760，但 OpenAI DR 回答上，二元最好的裁判是 Claude 4.5 的 0.742。论文没有给出每份回答有几位独立标注者、争议仲裁方式、逐类标签数、完整混淆矩阵，以及任务内还是全样本池化计算 F1 的全部细节。303 份回答也不是 303 个互不相关的单标签样本，每份回答还包含多条判断。

附录图 15 上半部分是误判数量在维度间的分布，隐式项较多也受到它自身条目较多的影响。底部则按类别规模处理后再次归一化至和为 1，仍不能当成某类的原始错误概率。类似地，必选项在全部误判中占比较低，并不自动证明其每条误判率更低，还需要各组标准总数。[附录 B.4、图 15](https://arxiv.org/pdf/2511.07685v1)

## 两项 rubric 改写实验

### 保留短示例与删除示例

原始标准会用简短的括号示例说明范围，例如可接受的政策名称。实验通过删除示例比较其作用。

| 被评系统 | 二元：无短示例 → 有短示例 | 三元：无短示例 → 有短示例 |
| --- | --- | --- |
| Perplexity DR | 0.696 → 0.724 | 0.523 → 0.559 |
| Gemini DR | 0.733 → 0.760 | 0.539 → 0.567 |
| OpenAI DR | 0.709 → 0.721 | 0.532 → 0.557 |

按表 7，二元提升为 0.012–0.028，三元为 0.025–0.036，不能照搬正文“二元 3%–4%、三元 2%–3%”作为每行准确范围。这是 F1 的绝对差，并非相对百分比。[论文表 7、附录图 20](https://arxiv.org/pdf/2511.07685v1)

### 自动扩写不是单纯增加同样的信息

另一项实验要求 LLM 把每条标准扩写成一个句子，目标约 100 词，可以补充例子、边界、定义和缺失信息。二元 F1 从原始标准的 0.724、0.760、0.721，降至 0.508、0.564、0.528；三元从 0.559、0.567、0.557 降至 0.371、0.417、0.387。[论文表 7、附录图 21](https://arxiv.org/pdf/2511.07685v1)

二元下降 0.193–0.216，三元下降 0.150–0.188。作者认为可能发生语义偏移，但实验不仅改变字数，也允许加入原标准没有的内容，没有把这两种因素分离。论文未完整披露扩写模型版本、改写后逐项人工复核与重新标注流程，因此不能将结果泛化为所有自动润色必然降低可靠性。

## 长度、引用与成本的边界

| OpenAI DR | 6,269.73 | 10,169.57 |
| Perplexity DR | 1,828.61 | 3,664.36 |

三元分数与 token 长度的 Pearson 相关，Gemini 为 $r=0.280,p=0.005$，OpenAI 为 $r=0.245,p=0.014$，Perplexity 为 $r=0.172,p=0.085$。它们是跨问题的相关，没有固定报告信息量来改变长度，不能证明增长字数本身提高质量，也不能证明裁判完全没有长度偏好。[论文图 7、附录 C、表 9](https://arxiv.org/pdf/2511.07685v1)

正文还写 Gemini 引用 111 条、准确率 81%，Perplexity 引用 31 条、准确率 90%。v1 没有提供相应引用抽取方法、准确率判定、样本分母及结果表，官方代码也没有引用核验程序。本页不将这些数值作为已独立复核的本实验结论，也不据此推断广度与准确度必然无法兼得。

报告 token 数是最终文本长度，不含隐藏思考、网页读取和工具调用总量。论文没有给出完整生成成本、评审美元账单、总运行时长或重复次数。2,800 小时是人工制作投入，不能与推理成本混为一谈。

如果对一套系统的 101 份报告按每标准一次、无重试和无分块评分，理论上需要 2,593 次裁判调用；三套系统对应 7,779 次。每次一般重复发送完整报告，输入 token 负担明显高于把报告只读一遍。这是依据接口计算的调用规模，不是从作者账单取得的实际成本。

## 官方数据的逐行核查

本次固定数据 revision 为 `85de3115053d1453ed612caacf4a405edc1ad756`，下载并逐行检查 `processed_data.jsonl`，共 101 个不同 `sample_id`、2,593 条标准；每题 20–43 条，领域及三条复杂度轴的数量与附录一致。数据卡许可证为 MIT。[固定数据](https://huggingface.co/datasets/ScaleAI/researchrubrics/tree/85de3115053d1453ed612caacf4a405edc1ad756)

数据字段包括 `prompt`、`sample_id`、`domain`、三条复杂度标签，以及每条标准的 `criterion`、`weight`、`axis`。没有独立的 mandatory 字段，需要根据权重绝对值解释；当前快照按 $|w|\geq4$ 得到 1,121 条，负权重共 318 条。

有三点与理想化描述不同，复现时应保留而不是悄悄清洗：

- 一条引用标准权重为 **10**，超出论文规定的 $[-5,5]$；题目 ID 为 `6847465956a0f6376a605441`。
- 一条隐式标准权重为 **0**，题目 ID 为 `6847465956a0f6376a605440`。它不会改变加权分，但如果参与逐项一致性统计，仍可能影响标签分布。
- 六个主要维度之外，还有 **3 条 `Miscellaneous`**。其余计数为显式 717、隐式 1,021、信息综合 409、表达 202、指令遵循 150、引用 91，共计 2,593 条。

这些是固定公开文件的实际内容，不等于证明论文评测时用了错误版本。缺少原始逐标准判定与实验快照，不能推算这些条目改变了主表多少分。

## 官方代码的执行路径与复现注意点

官方仓库固定 commit 为 `2dc80e2d4c38ddd80439517c259d93c6954b193f`。本次完整阅读单报告评审、批量评审、分数汇总和四份提示模板；未运行模型调用。该版本只公开二元评审提示，论文的三元实验需要另行还原，不能直接将当前默认输出当作三元结果。[固定代码](https://github.com/scaleapi/researchrubrics/tree/2dc80e2d4c38ddd80439517c259d93c6954b193f)

流程是准备 `<sample_id>.md` 报告，在 `evaluate_single_report.py` 中按 ID 找标准，对每条标准调用裁判；`evaluate_reports_batch.py` 遍历 `agent_responses`；最后 `calculate_compliance_score.py` 计算每题及平均分。发布树没有三套系统的 303 份原报告、人工标签和完整模型评审结果，不能只运行汇总器就重现论文表格。

默认裁判为 `litellm_proxy/gemini/gemini-2.5-pro-preview-06-05`。单报告内最多 20 个并发评审，普通调用最多尝试三次，单次最大输出设为 50,000 token，未显式设置温度。这个路由和参数属于所核代码，不是商业研究代理的版本信息，也不是当前服务一定仍可调用的保证。

长文以字符数除以四估计 token；估计超过 150,000 时分块，通常按约 100,000 token 的块提取证据，再将证据汇总交给裁判。它不是精确 tokenizer 计数，单段很长也未必严格切到上限。分块后的综合评审只看抽取证据，可能丢失上下文，与直接读取全文不完全相同；论文未报告哪些样本实际走过这一分支。

静态检查还发现会影响复现解释的边界：

- 单项 API 或解析失败返回 `score=0`、`success=False`，后续汇总不排除这些记录。正项因此失分，负项则不扣分；应单独报告错误数，而不能把所有零分当成人工意义上的未满足。
- 批量循环遇到整份报告异常会跳过该报告，平均分只基于取得结果的样本。需要额外核对 101 个 ID 和每题标准覆盖是否完整。
- 汇总脚本只读取指定 JSONL；省略路径时取文件名字典序最后一个，不保证它就是全量最新批次，也不会自动合并目录里所有文件。
- 评审器直接采用返回的 `score`，没有严格校验必须为 0 或 1，也不核验 `verdict` 与分数是否一致。重跑时需要保留异常响应并验证输出格式。

这些发现来自公开版本的控制流，不代表作者原实验必然触发过这些问题。代码记录 token 与按硬编码费率估算的成本，但不能把该费率当作当前 API 价格；失败尝试的实际消耗也未必全部进入已返回结果的合计。

要进行可比较的新评测，应同时固定题目与标准快照、报告生成日期和代理设置、PDF 转 Markdown 过程、裁判模型和提示、二元或三元方案、失败重试处理。还需要任务级重复与不确定性统计，才能解释相差一两个百分点的结果。本页完成了原文、公开代码与全量结构化数据的核对，尚未复现模型分数。

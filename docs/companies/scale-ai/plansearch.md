# PlanSearch：先展开解题思路，再搜索候选代码

让模型为同一道编程题生成许多答案，可能得到许多写法不同、算法却相同的程序。PlanSearch 把额外计算用于生成和组合解题观察，再把不同方案写成代码。在论文的 LiveCodeBench 实验中，Claude 3.5 Sonnet 的 pass@200 从直接重复采样的 55.6% 提高到 77.0%。这表示候选集合更可能包含通过测试的程序；它不表示模型一次回答的正确率达到 77%，也不表示只发出 200 次模型请求。（表 1，§4—5）

## 从重复写代码，到分别生成思路与实现

输入是一道题的描述、必要的函数框架，以及题目公开的示例测试。输出是符合接口的 Python 程序。例如，一道题要求找出两个集合的公共元素，模型需要同时理解返回内容、顺序要求和输入输出格式。对更复杂的竞赛题，候选方案还可能在贪心、动态规划、图搜索等算法选择上分歧。

论文依次比较三个流程：

| 方法 | 一次候选生成的主要过程 |
| --- | --- |
| Repeated Sampling，重复采样 | 给出题目及示例，直接生成代码；重复调用获得候选集合 |
| IdeaSearch | 先用自然语言写解题方案，再在另一次调用中给出题目和方案，要求实现代码 |
| PlanSearch | 先生成多种观察，组合并推导新观察，再分别形成方案、修订方案、伪代码和代码 |

IdeaSearch 把“想出算法”和“实现算法”拆成两次调用。它与在一条回复中先推理再写代码的 Chain-of-Thought 基线也有区别。论文附录 E 单独比较后者，观察到两次调用的 IdeaSearch 在若干设置下更好；作者把差异解释为回复拆分可能改变思路多样性，没有通过独立实验确认唯一原因。（§4.1—4.2、附录 E）

PlanSearch 的搜索过程中没有训练奖励模型，也没有根据隐藏测试结果挑选下一条观察分支。它先展开候选，测试主要用于最终评估，以及后文的公开测试过滤。它并不是带有测试反馈、不断修复同一段代码的循环 agent。

## 观察如何展开成一棵搜索树

### 第一层观察与子集

设题目为 $P$，模型先给出 $n_1$ 条观察 $O^1_1,\ldots,O^1_{n_1}$。观察可以是某种数据结构的用途、一个约束的推论，或值得尝试的算法方向，不要求已经构成完整证明。论文报告实际观察数量通常为 3—6 条。（§4.3.1）

然后枚举大小不超过 $S$ 的观察子集。默认 $S=2$，包含空集、所有单条观察，以及所有两条观察的组合。因此第一层的组合数为：

$$
l_1=\sum_{j=0}^{\min(S,n_1)}\binom{n_1}{j}
=1+n_1+\binom{n_1}{2}\quad(S=2,\ n_1\ge2).
$$

例如，若有 4 条观察，就产生 $1+4+6=11$ 个组合。空集也有意义：它保留了一条不依赖这批观察的生成路线，而不是强迫所有候选接受同一组前提。

### 第二层观察

每个第一层组合单独成为下一次提示的条件。模型读到原题和该组合，先推导其含义，再提出新的观察。对这些第二层观察，再执行相同的子集枚举。论文主设置采用两层，即 $L=2$；更深的树会快速扩大候选数量和请求数。（§4.3.2）

这里的观察没有经过真实性验证。提示中会把它们描述为有用或正确的条件，但这只是提示写法，不是标注结论。作者明确允许错误观察进入搜索：一个分支可能因此失败，其他组合仍可能走向不同方案。

用一个**说明示例**来看组合的作用。假设一道数组题涉及区间和，初始观察分别是“考虑前缀和”“枚举右端点”“利用数值单调性”。前两条组合可能引向前缀和计数；第一、第三条组合可能引向二分。如果题目允许负数，某些单调性假设可能不成立，后一分支便可能生成错误方案。算法不会在观察阶段自动证明或排除这种错误。

### 方案、修订与代码

得到观察组合后，模型先写自然语言解法。随后另开一条路线，假设原方案有错，让模型提出批评并据此修订。**原方案和修订方案都保留**，并分别转成伪代码，再转成 Python 程序。修订不是根据测试失败信息修补代码，也不意味着修订版必然优于原版。（§4.3.3、图 2）

伪代码阶段的设计意图，是减少模型实现时忽略前面计划、回到惯常答案的情况。是否需要这一阶段，由后面的消融实验判断，不能仅凭流程更长就认定它贡献了全部收益。

## 公开实现比方法示意图多出的步骤

本页核对的[代码版本](https://github.com/scaleapi/plansearch/tree/16df032c8ae1a20972ac1ab3842ed5cef62f491d)固定为 `16df032c8ae1a20972ac1ab3842ed5cef62f491d`。`search/combo_observation_model.py` 有几个会实际改变请求预算和候选集合的细节。

首先，默认提示请求 **10 条**初始观察，而不是硬编码为论文报告的 3—6 条。模型生成之后，还会经历“整理成列表”“筛选最有用的观察”“转换为 Python 字符串列表”三次处理。实际进入组合枚举的是最后解析出的列表，因此请求数量与保留数量不同。这里的筛选由模型完成，没有运行单元测试，也没有专家审核。

列表解析最多尝试三次；普通模型的解析调用依次使用温度 0、0.2、0.4。全部失败时，该处变为空观察列表。因此论文主实验的温度 0.9，不能理解为代码里每一条辅助请求都使用 0.9。

其次，论文 §4.3.3 用叶节点描述最终生成，源码却调用 `collect_all_problem_obs()`，收集**所有层**的观察组合，并按完全相同的字符串元组去重。下一层节点保存的是本层新组合，最终解法提示没有自动把所有祖先观察再次拼接进去；父观察主要通过生成下一层观察产生影响。复现源码时，应保留这条实际信息流，而不是自行改成“只取叶节点，并把整条祖先路径合并”。

最后，`--num-completions-from-model -1` 才会返回整棵展开树实际产生的全部代码。如果指定一个正数，源码会在打乱后的代码列表中取值；要求的数量超过现有数量时还会循环取已有代码。把这个参数设为 200，并不等于独立生成 200 个不同候选。论文所述通常约 300—400 个候选，是完整流程的结果规模，不是模型调用数。

## pass@k 的分母与候选预算

设一道题已经生成 $n$ 个候选，其中 $c$ 个通过全部测试。从该候选池中不放回地抽取 $k$ 个，至少有一个成功的概率是：

$$
\widehat{\mathrm{pass@}k}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},\qquad 1\le k\le n.
$$

分子是不含正确答案的抽法数，分母是所有抽法数；最后对各题的数值等权平均。格式不合要求的输出按失败处理，程序需要通过规定测试才算正确。（§5.2、附录 N 式 4）

例如，**自拟候选池**中有 10 个程序、2 个成功，pass@1 为 20%；pass@3 为 $1-\binom83/\binom{10}3=53.33\%$。它不是随机抽三次后的某一次实测结果，而是对已有池所有三元素子集的计算。

对于独立同分布的重复采样，这一表达式可以估计总体采样过程的 pass@k。PlanSearch 的多个程序共享观察与方案，存在依赖。论文附录 O 明确承认：此时更稳妥的解释是**一次搜索所得候选池的子集成功概率**，而不是独立运行搜索算法 $k$ 次的无偏估计。该限制也意味着，共享一次树生成得到的几百段程序，不能当作几百次独立完整实验。

若某题候选不足 $k$，论文按剩余候选均失败处理。对应的 CodeRM 实现，在池中存在至少一个成功程序且 $k>n$ 时返回 1，否则返回 0。这没有凭空生成补充答案；其含义是已经用尽该池。

主表没有给出多次独立树搜索的均值、标准差或置信区间。公开绘图 notebook 也把方差绘制关掉了。因此本页按报告的点估计比较结果，不为小幅差距补写统计显著性。

## 主结果：同模型、同候选数的比较

普通模型的主设置为温度 0.9、top-p 0.95。温度来自对重复采样与 IdeaSearch 的 0—1.2、步长 0.1 的扫描。源码的单次回复默认输出上限为 4,096 tokens；这不是一道题整棵搜索树的总预算。（§5.2、附录 F、公开参数）

模型配置把 Sonnet 固定为 `claude-3-5-sonnet-20240620`，另外几项使用 `gpt-4o`、`gpt-4o-mini`、`deepseek-coder` 等未带日期的 API 名称。论文称后者为 DeepSeek-Coder-V2，不能把今天相同别名返回的模型自动当作原实验快照。

下面所有数字都是百分比。表中的“直接采样 @1”来自重复采样基线，**不是 PlanSearch 自己的 pass@1**。（表 1）

| LiveCodeBench 模型 | 直接采样 @1 | 直接采样 @200 | IdeaSearch @200 | PlanSearch @200 |
| --- | ---: | ---: | ---: | ---: |
| GPT-4o-mini | 39.0 | 53.3 | 59.4 | 64.9 |
| GPT-4o | 41.3 | 60.6 | 70.4 | 73.0 |
| DeepSeek-Coder-V2 | 41.4 | 53.2 | 65.9 | 70.3 |
| Claude 3.5 Sonnet | 40.3 | 55.6 | 70.2 | 77.0 |

对 Sonnet 而言，同为 200 个候选的比较是 **55.6→77.0，增加 21.4 个百分点**。摘要引用的 60.6% 是 GPT-4o 直接采样的最好成绩，与 Sonnet PlanSearch 相差 16.4 点；41.4% 则是 DeepSeek-Coder-V2 的直接采样 pass@1。后两种比较同时换了模型，最后一种还换了候选预算。

在另外两个基准上，PlanSearch 也提高了大候选池的成功率，但许多结果已接近测试集上限：

| 模型 | HumanEval+：直接 / IdeaSearch / PlanSearch @200 | MBPP+：直接 / IdeaSearch / PlanSearch @200 |
| --- | ---: | ---: |
| GPT-4o-mini | 95.0 / 97.5 / 98.2 | 83.8 / 87.3 / 91.0 |
| GPT-4o | 98.2 / 97.6 / 99.5 | 87.4 / 89.3 / 92.2 |
| DeepSeek-Coder-V2 | 91.4 / 97.2 / 99.3 | 81.9 / 89.1 / 92.6 |
| Claude 3.5 Sonnet | 88.9 / 95.6 / 98.5 | 83.0 / 87.8 / 93.7 |

IdeaSearch 并非在每一行都胜过直接采样，例如 GPT-4o 的 HumanEval+ 为 97.6%，低于直接采样的 98.2%。完整曲线还显示，PlanSearch 在较小 $k$ 时经常更低，尤其是 Sonnet；搜索收益主要出现在可以保留多个方案时。（附录 A，图 7—9）

### o1-mini 是单独的补充设置

v2 对 o1-mini 只评测 LiveCodeBench：直接采样 pass@1 为 69.5%，直接采样、IdeaSearch、PlanSearch 的 pass@200 分别为 **90.8%、91.2%、91.3%**。PlanSearch 相对直接采样只增加 0.5 个百分点；低候选预算时还落后。（表 1、附录 K）

这组实验使用温度 1、top-p 1。作者修改了部分提示措辞，并删掉伪代码步骤；仍无法取得回答的请求交给 GPT-4o 处理。因此它不是把完全相同的流程原封不动套在纯 o1-mini 上的受控对照。作者报告提示调整后无回答比例从约 40% 降到不足 0.5%，但没有给出逐题的兜底调用分布。

## 公开测试过滤减少的是提交数量

设题目有公开测试 $\mathcal T_{\rm pub}$。先生成完整候选池，再保留满足所有公开测试的程序：

$$
\mathcal C_{\rm pub}
=\{f\in\mathcal C: f(x)=y,\ \forall(x,y)\in\mathcal T_{\rm pub}\}.
$$

随后从这个较小池中计算 pass@k；分母 $n$ 改成保留数，成功数 $c$ 也只统计保留池中的正确程序。过滤可以去掉语法错误、接口错误和明显不符合例子的程序，但公开样例通过不代表隐藏测试也通过。（§5.4）

论文报告 Sonnet PlanSearch 经过公开过滤后，pass@20 达到 **77.1%**，接近不经过过滤时的 pass@200＝77.0%。这里的 20 是过滤后的提交候选数，前面仍然生成了完整候选池，并执行公开测试。不能写成“生成成本降低十倍”，也不能把它改称“只生成 20 个程序就达到 77.1%”。（图 5）

隐藏测试在这里承担离线评估角色。实际用户若只有少量公开样例，仍需决定怎样选择最终代码，不能直接拥有 benchmark 的“至少一段代码正确”判定能力。

## 计算量归一化后的比较

每个 PlanSearch 候选除了最终代码，还消耗观察、方案、批评、修订和伪代码的生成。附录 D 把不同数据集上的平均**生成 token 数**归一化后，得到直接采样约 **244 tokens/候选**，PlanSearch 约 **1,428 tokens/候选**，后者约为 5.85 倍。（图 18）

据此粗略换算，200 个候选分别对应约 48,800 和 285,600 个生成 tokens。这只是用论文跨数据集平均值重算的数量级，不是每题账单，也没有包含输入 tokens、调用延迟、代码执行开销或不同 API 的价格差异。

图 18 表明，当平均生成预算达到约一万 tokens/题的量级后，PlanSearch 开始更有优势，但不同模型的交叉位置并不相同。该图不能证明任何模型在一万 tokens 这个精确阈值上都会转为领先，更不能直接当作按 FLOPs、美元或端到端时间完全配平的实验。

## 思路起作用的两组机制实验

### 从正确代码回译方案

作者先让 GPT-4o 对每道题尝试 1,000 次，只保留至少得到一段通过测试代码的题。然后把题目和正确代码交给模型，要求将代码概括成不同长度的自然语言解法，再让 GPT-4o-mini 据此实现。（§3.2、图 4a）

更详细的回译方案通常对应更高的成功率，短到约 10 tokens 的提示也有帮助。但这个实验已经看到了正确答案，并筛掉了最初无法解出的题。它支持“正确方案能帮助实现”的解释，不能作为 PlanSearch 在未知题上的直接成功率，也不是主方法提前获得正确计划的来源。

### 固定同一方案，多次实现

第二组实验不再提供正确答案，而是每题生成 5 个方案，每个方案实现 25 次。去掉总体成功率为 0 或 100% 的题后，保留 **75 道题、375 个方案**；这对应每个方案 25 个候选、共 9,375 个候选实现的分析规模。（§3.3）

按方案分别统计时，成功率更集中在接近 0 或 1 的两端；按整题混合不同方案后，分布较平缓。其含义是，同一方案的多个实现往往共同成功或共同失败，方案选择解释了部分输出差异。

这不是对 375 个方案逐一人工判定正确与否。实现者可能误读方案，方案也可能只覆盖部分边界情况，因此不能把一次实现失败直接等同于该方案在算法上错误。

## 多样性指标衡量的是思路差异

论文没有只比较代码字符串，而是先把候选代码概括成自然语言思路，再把两段代码及其概括交给 GPT-4o-mini，判断是否采用相同思路。设 $S(c_i,c_j)=1$ 表示被判为相似，定义：

$$
D=1-\frac{\sum_{i<j}S(c_i,c_j)}{\binom n2}.
$$

$D=0$ 表示所有比较都相似，$D=1$ 表示全部不同。它是随机抽取两个不同候选时，**被判断为思路不同**的概率。论文第 13 页及附录 Q 的部分文字把它写成“相似概率”，与式 1 相反；本页按公式和示例解释。（§6.1、附录 Q）

例如，**自拟示例**中四段代码各有两段使用算法 A、两段使用算法 B，六对比较中有四对跨算法，$D=4/6$。若三段使用 A、一段使用 B，则只有三对跨算法，$D=3/6$。两组都只有两种思路，但频率更均衡的组得分更高。

论文从较大的候选池中抽 40 段代码，每题进行 $\binom{40}{2}=780$ 次比较，然后对题目平均。代码脚本默认只抽 25 段，复现论文需显式改为 40；脚本保存的 `results.npy` 是**相似比例**，还需要取 $1-\text{比例}$ 才是上述多样性。另需注意，比较器对既不含 yes 也不含 no 的异常回答会警告后按“不相似”处理，这可能影响得分。

图 6、26、27 显示，多样性与从本方法 pass@1 到 pass@200 的相对增益相关。这与“多种思路有利于候选搜索”一致，但没有把模型能力、单次成功率和多样性分别控制。论文也没有报告该相似性判断器与人工标注的一致率。这个指标描述模型判定的思路差异，不能代替程序正确性测试，也不是已经验证可泛化到任意任务的性能预测器。

## 消融揭示了各步骤的作用范围

附录 H 的消融使用 GPT-4o-mini 和 LiveCodeBench，比较完整 pass@k 曲线。

| 改动 | 保持或补偿的部分 | 原文结果 |
| --- | --- | --- |
| 最大观察子集大小 $S=1,2,3$ | 仍组合观察并生成代码 | 差异较小；作者选 2，以产生更多候选，3 未表现出稳定优势 |
| 观察层数 $L=1,2,3$ | 保留后续实现流程 | 在较大的 $k$，尤其约 50 以上，更深的观察树有收益；主设置选 2 平衡成本 |
| 删除伪代码 | 直接把自然语言方案写成代码 | 曲线与完整流程接近 |
| 删除修订与伪代码 | 整套搜索运行两遍，以补偿不再保留修订版造成的候选数量变化 | 与完整流程差距较小；补齐了候选数，并未配平所有调用成本 |
| 删除方案与伪代码 | 由观察组合直接写代码 | 仍保留大部分搜索收益，完整流程在大 $k$ 有小幅优势 |

这些结果更支持“观察组合本身贡献了相当一部分收益”，而不是“每个中间步骤都不可缺少”。图 28—30 没有给出重复实验误差条，各图的端点也不应自动当作表 1 同一次运行的精确复现值。

附录 I—J 还比较基础模型与指令模型。某些 HumanEval+、MBPP+ 曲线在大 $k$ 下缩小差距甚至反转，但这一趋势不是所有模型与数据集都成立。尤其 LiveCodeBench 的图 32—33 中，展示到 10,000 个候选时，DeepSeek-Coder-V2-Lite 和 Llama-3.1-8B 的基础版仍低于对应指令版。不能据此概括为“后训练必然损害代码搜索”。

## 这项研究验证的范围

论文验证的是带可执行测试的 Python 编程任务：生成更多不同方案，可以在较大的候选预算下扩大成功覆盖面。它没有验证复杂仓库修改、长期软件维护或无可靠评分器的开放任务，也没有把搜索中得到的成功方案蒸馏回模型。

方法还均匀展开大量分支，没有根据已验证的中间质量动态分配预算。层数增加后，组合数量迅速增长。附录 R 把动态剪枝和扩展列为后续方向；这些并不是本文已经实现并给出性能结果的能力。实际采用时，能够承担多少生成和执行成本，以及最终能否可靠筛选代码，决定了高 pass@k 能转化成多少可用收益。

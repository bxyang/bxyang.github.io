# PlanSearch：先探索不同的解题思路，再生成代码

## 1. 摘要翻译

扩大训练计算量已经显著改善了大语言模型（LLM）的能力，但扩大推理计算量尚未带来类似的提升。我们假设，其中缺失的一个关键因素是 LLM 输出缺乏多样性：模型反复采样出高度相似却不正确的结果，导致搜索效率低下。我们通过实验证明，可以通过用自然语言搜索解决问题的候选方案，缓解这种多样性不足。

基于这一认识，我们提出了新的搜索算法 PlanSearch，它在 HumanEval+、MBPP+ 和 LiveCodeBench（一项无数据污染的竞赛编程基准）上取得了较好的结果。PlanSearch 针对问题生成一组多样化的观察，再利用这些观察构建解决问题的方案。通过搜索自然语言方案，而不是直接搜索代码答案，PlanSearch 探索的潜在解决方案范围比基线搜索方法更加多样。

在 Claude 3.5 Sonnet 上使用 PlanSearch，在 LiveCodeBench 上取得了 77.0% 的 pass@200，超过了不进行搜索时的最高通过率（pass@1 = 41.4%），也超过了在已有非搜索模型上进行标准重复采样的结果（pass@200 = 60.6%）。最后，我们表明，在所分析的全部模型、搜索算法和基准中，可以根据生成思路的多样性，准确预测搜索带来的性能增益。代码见 [项目仓库](https://github.com/scaleapi/plansearch)。

## 2. 研究背景与相关研究

这篇论文研究的是推理时搜索：模型参数不变，通过增加生成和筛选的计算，提高解决问题的机会。代码生成适合研究这一问题，因为候选程序可以运行测试；相比开放式文本，判断答案是否符合要求有更明确的依据。

但重复生成不一定意味着尝试了不同方法。如果模型始终采用同一种错误算法，改写变量名或调整代码风格并不能解决问题。作者还观察到，一些经过指令微调的模型虽然单次作答更好，多次采样时的优势却会缩小，甚至被基础模型反超。这种现象并非出现在所有模型和基准上，但说明只看单次通过率不足以描述模型的搜索潜力。（§1、§3）

作者在相关研究中区分了几条路线。**重复采样**直接生成多份答案，再结合测试、验证器或奖励模型选择候选。**Tree of Thoughts 和 Reasoning via Planning**把自然语言推理扩展成搜索过程；本文作者认为，这些前作主要在 24 点、Blocksworld 等搜索步骤较明确的任务上展示效果。另一些工作搜索 token、代码行或完整程序，或者把程序分解为较小的子问题。还有工作专门训练模型进行搜索，或让智能体根据工具反馈逐步修正行动。（§2）

PlanSearch 将搜索重点放在“采用什么解题思路”上，并通过已有模型的调用完成，不要求重新训练模型。它与简单的“先解释再写代码”也有区别：作者先提出 IdeaSearch，分别生成思路和代码；PlanSearch 则进一步拆开、组合并延伸观察，让候选方案来自更多不同的方向。

## 3. 核心贡献

**核心要解决的问题。** 在允许多次尝试的代码任务中，如何让额外计算带来新的有效探索，而不是不断重复相似的错误方案。作者的出发点是：模型能否写对代码，很大程度上取决于是否先找到了合适的解题思路。把正确程序反向概括成文字提示的诊断实验，以及固定同一思路后多次生成代码的实验，为这一判断提供了依据；这些诊断中使用的正确答案，不是 PlanSearch 实际求解时的输入。（§3）

**核心方案。** PlanSearch 从题目出发，先让模型提出若干观察，例如可能有用的数据结构、算法方向或问题性质。它不把这些观察全部拼成一条固定路线，而是选取不同的小组合，让模型在各个组合的基础上继续推导新的观察。论文实现使用两层观察，并限制每次组合的规模，以控制搜索量。

接着，每条分支把已有观察整理成自然语言解题方案。为了继续拓展思路，模型还会收到“假设这个方案是错的”的提示，提出批评并生成另一份方案。这个提示是探索手段，不意味着外部验证器已经判定原方案错误。各份方案随后依次转成伪代码和 Python 程序。观察本身也不保证正确，其作用是引导模型探索不同方向，最后仍需通过代码测试判断候选答案。（§4）

**结论。** 在所测模型和三个代码基准上，PlanSearch 改善了大量候选下的通过表现。以同一个 Claude 3.5 Sonnet 为例，LiveCodeBench 的 pass@200 从直接重复采样的 **55.6% 提高到 77.0%**。摘要中的 60.6% 是 GPT-4o 重复采样的结果，41.4% 则来自 DeepSeek-Coder-V2 的单次作答；它们是各基线中的最高值，不能误写成 Claude 自身的起点。（表 1）

这里的 pass@200 衡量在 200 个候选中至少有一个通过完整测试的机会，不是模型一次输出正确答案的概率，也不是总共只调用模型 200 次。PlanSearch 还要生成观察和方案。论文另外比较了计算预算，并研究用题目公开测试过滤候选，以减少提交明显错误程序的机会；公开测试通常不完备，过滤不能等同于证明答案正确。（§5—6）

作者进一步让模型比较候选程序背后的思路，发现测得的思路多样性与搜索增益有较强关联。论文的主要发现是，在这些代码任务中，显式扩展解题思路有助于利用更多推理计算。它并未证明单次回答总会更好：作者明确指出，增加多样性可能轻微牺牲 pass@1，收益更适合有多次尝试预算和筛选条件的场景。把成功方案用于训练、进一步提升单次作答能力，是提出的后续方向。（§6—7）

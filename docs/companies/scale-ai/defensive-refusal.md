# 防御性安全任务中的过度拒绝

防御人员需要描述异常程序、分析安全告警和检查系统配置，这些请求有时会使用与攻击活动相同的术语。Defensive Refusal Bias 研究这种场景中的拒绝：作者分析 NCCDC 比赛中 2,390 次单轮对话，发现含特定安全术语、以及明确声明授权的请求，更容易被自动规则判为拒绝。论文进一步比较授权改写前后的结果，并用提示词的向量表示预测拒绝标签。理解这些结果，需要同时看自动检测器的误差、不同组的构成，以及改写实验实际改变了什么。

## 研究对象是防御协助中的拒绝

可以用一个自拟说明示例理解任务：学生在防御比赛中发现服务器日志出现异常，希望模型整理事件时间线，并说明下一步应核查哪些配置。理想回应应围绕给定证据提供有用的防御建议。若模型只返回拒绝声明、转向无关建议，或给出没有实际帮助的泛泛说明，就可能妨碍这次协作。这个例子用于解释任务，并非论文公开样本。

作者把这种现象称为“防御性拒绝偏差”（Defensive Refusal Bias，DRB）。与衡量模型是否协助不当请求的实验相比，这里关心的是合法防御请求得到多少帮助。论文没有提出新的安全训练损失、权限验证系统或防御 agent，也没有通过训练前后对照证明一种缓解方法有效。它由三部分组成：对真实对话做分组统计，改写授权措辞，以及分析哪些输入特征能预测拒绝。

研究中的“合法”来自比赛场景及作者对数据来源的说明。它并不等于每条提示都向模型提供了可验证的身份、资产范围和授权凭证。后文出现的“授权信号”，主要是提示文本中的若干词语，而非系统验证通过的访问权限。[论文 §1、§3，第 1—4 页](https://arxiv.org/pdf/2603.01246v2)

## 2,390 次对话的来源与划分

NCCDC 是美国大学生网络防御比赛。论文收集学生蓝队在维护真实运行基础设施、应对专业红队活动时产生的单轮对话，合计 2,390 条。作者把这些交互视为受控比赛环境中的合法防御使用案例。

模型涉及三个类别：

| 论文类别 | 对应模型 | 披露的版本范围 |
| --- | --- | --- |
| Safety-focused | Claude 3.5 Sonnet | June 2024 |
| General frontier | GPT-4o | 2024 |
| Open-source | Llama-3.3-70B-Instruct | 2024 |

这里的 2,390 是整体对话量，不能扩写成每个模型各 2,390 条。论文没有给出三个模型各自的样本数，也没有完整说明是否把相同提示逐题重放给所有模型。比赛年份、团队数量、每队交互分布、采集与过滤规则、模型的完整接口标识、生成温度和输出预算同样未披露。因此，模型间拒绝率是这批交互中的描述性比较，尚不能排除使用者和任务构成的差异。[论文 §3.1，第 3 页](https://arxiv.org/pdf/2603.01246v2)

### 四类标注并不都对应人工逐条判断

论文为每次对话记录任务类别、安全术语、授权信号和事件背景。前三者的自动规则写在附录 B，事件背景则分为正在发生、预防性和事后情境；正文没有给出其完整识别规则及独立定量结果。

任务分类覆盖恶意软件分析、漏洞评估、事件响应、系统加固、凭据管理、防火墙配置、网络扫描和日志分析。规则按关键词匹配，并采用优先命中的类别：恶意软件分析先于漏洞评估，其后依次是事件响应、系统加固、凭据管理、防火墙配置、网络扫描和日志分析。未命中的请求进入其他类别。

这是一种单类别归属规则。一条同时包含日志与恶意软件描述的提示，可能先归入恶意软件分析，不能再计入日志分析。因此，类别统计反映的是这套规则产生的分组，并非各类防御活动彼此独立、完整的人工作业清单。

安全术语由 11 个词组成，按词边界匹配；作者还对 PowerShell 做特殊处理，以免常见系统管理语境被当成另一个安全术语。授权信号分强、弱两组：强信号包括蓝队、比赛名称和明确授权等表达；弱信号包括“我们的系统”或“比赛”等语境词。命中任一组就记为存在授权信号。这个二值变量既包含明确声明，也包含较宽泛的背景描述。[论文 §3.3、附录 B.2—B.4，第 4、12—13 页](https://arxiv.org/pdf/2603.01246v2)

## 拒绝率是怎样测出来的

### 汇总指标包含三类回应

正文定义了硬拒绝、软拒绝和帮助降级：第一类直接拒绝，第二类拒绝并附解释或转移建议，第三类给出泛化内容而回避实际细节。总体分析把三者合并为一个二值“拒绝”结果。

设第 $i$ 条对话的自动标签为 $y_i\in\{0,1\}$，某组包含 $n$ 条对话，则拒绝率为：

$$
\hat r=\frac{1}{n}\sum_{i=1}^{n}y_i.
$$

这是根据论文口径写出的统计式，不是作者提出的优化目标。总体标签中有 291 个正例，所以 $291/2390\approx12.2\%$。这个比例不等于“12.2% 的回应全部明确拒绝且没有提供其他帮助”。[论文 §3.2、§4.1，第 3—4 页](https://arxiv.org/pdf/2603.01246v2)

检测器在模型回应中执行不区分大小写的正则匹配，任意规则命中即判为拒绝。规则包含无法提供帮助、道歉、政策限制和可能被误用等表达。附录没有给出把命中的回应进一步分成上述三类的完整实现。包含警告而仍提供有效帮助的回答，也可能触发这些宽泛规则。

Scale 的介绍文章把 12.2% 描述为 outright refusal，并称计入帮助降级后还会更高；这与论文 §3.2 的合并定义并不一致。本文采用论文定义，不另行推算一个更高的总比例。[Scale 官方介绍](https://labs.scale.com/blog/drb)

### 人工核验发现自动规则更容易标为拒绝

附录 B.1 说明，三位作者独立标注了 200 条随机抽取的回应，以多数票作为最终人工标签。人工标注者之间的 Fleiss’ $\kappa$ 为 0.80；自动标签与人工多数票的一致率为 80.0%，Cohen’s $\kappa$ 为 0.60。自动方法在该样本中标为拒绝的比例是 50.0%，人工判断是 35.0%。

如果把这些百分比视为这 200 条记录的精确汇总值，可以反推出下表。它是依据论文数字进行的算术重建，并非作者公开的逐条标签：

| 自动检测结果 | 人工判拒绝 | 人工判非拒绝 | 合计 |
| --- | ---: | ---: | ---: |
| 判拒绝 | 65 | 35 | 100 |
| 判非拒绝 | 5 | 95 | 100 |
| 合计 | 70 | 130 | 200 |

表中一致条数为 $65+95=160$；自动正例为 100，人工正例为 70。由此得到的精确率为 65%，召回率约 92.9%。这说明在该核验样本中，自动方法的主要偏差是把部分人工认为非拒绝的回应标为拒绝。

Cohen’s $\kappa$ 会扣除按两个标注来源的边际比例计算的偶然一致率：

$$
\kappa=\frac{p_o-p_e}{1-p_e},\qquad
p_e=0.5\times0.35+0.5\times0.65=0.5.
$$

代入实际一致率 $p_o=0.8$，得到 $\kappa=0.6$，与附录一致。Fleiss’ $\kappa$ 衡量三位人工标注者，Cohen’s $\kappa$ 比较自动标签与人工多数票，二者不是同一组比较。

还有一个未解释的采样差异：这 200 条被称为随机样本，但自动拒绝占比 50%，与总体 12.2% 相差较大。论文没有说明是否还存在分层抽样、筛选或不同来源。不能直接把这份核验表的精确率乘到 291 上，得到所谓“校正后的总体拒绝数”。作者将报告值解释为偏保守的上界，但没有给出正式的统计上界证明，也没有按模型、术语或授权分组报告误报率；各组的偏差若不同，相对风险也可能改变。[附录 B.1，第 11—12 页](https://arxiv.org/pdf/2603.01246v2)

### 附录规则还存在实现歧义

附录的一条表达式写成 `i can’t help|assist|provide`。若按标准正则表达式逐字解释，竖线两侧是完整的备选项，因而单独出现 `assist` 或 `provide` 也会匹配。例如自拟的正常回答 “I can provide a summary of the logs.” 会命中 `provide`。给备选动词加上括号，才会要求它们共享前面的否定语境。

本次只用这个无害例句做了离线匹配检查。由于没有定位到官方脚本，无法确定实际实验是否使用了附录的字面表达式，还是实现中已经加了分组；这里记录的是复现歧义，不把它直接断言为原实验代码错误。即使补充分组，警告类短语与有效帮助共存的问题仍需人工规则处理。[附录 B.1，第 11—12 页](https://arxiv.org/pdf/2603.01246v2)

## 主结果：模型、术语和任务类别

### 模型结果的分母未完整公开

| 模型 | 自动拒绝率 |
| --- | ---: |
| Claude 3.5 Sonnet | 19.5% |
| GPT-4o | 10.2% |
| Llama-3.3-70B-Instruct | 6.6% |
| 全部对话 | 12.2% |

19.5% 与 6.6% 的比值约为 2.95，所以论文将其概括为约三倍。但各模型样本量与提示分布未公开，不能把这张表当成相同测试集、相同推理预算下的严格模型排名。总体比例也不是三个百分比的简单平均。[图 2b、§4.1，第 4—5 页](https://arxiv.org/pdf/2603.01246v2)

### 有安全术语的组为 30.5%，无相关术语的组为 11.2%

用 $\hat r_1$ 表示含指定术语的拒绝率，$\hat r_0$ 表示不含术语的拒绝率，则相对风险为：

$$
RR=\frac{\hat r_1}{\hat r_0}
=\frac{30.5\%}{11.2\%}\approx2.72.
$$

绝对差为 19.3 个百分点。相对风险不是优势比，也不是“增加 2.72 个百分点”。论文报告卡方统计量 $\chi^2=37.3$，$p<0.001$。

这些数字来自文本特征分组。原文使用了“语义等价”等表述，但没有为这项主结果提供逐题配对表、任务难度匹配方法或控制变量模型。因此，它支持这批数据中术语与拒绝存在关联；不足以单独证明只替换一个词就会造成 2.72 倍变化。后文的改写实验针对授权声明，也不能补成这项术语比较的完整配对实验。[§4.2、图 2a，第 4—5 页](https://arxiv.org/pdf/2603.01246v2)

### 类别比例还受标注优先级影响

| 自动划分的任务类别 | 拒绝率 |
| --- | ---: |
| 系统加固 | 43.8% |
| 恶意软件分析 | 34.3% |
| 漏洞评估 | 22.7% |
| 事件响应 | 18.9% |
| 凭据管理 | 17.2% |
| 网络扫描 | 12.7% |
| 其他 | 10.7% |
| 防火墙配置 | 6.4% |
| 日志分析 | 0.0% |

图 3b 中系统加固的比例最高，日志分析没有观察到自动拒绝。但各类别样本数未给出，不能比较它们贡献了多少拒绝总数；日志组的零值也不意味着所有日志分析任务都不会被拒绝。优先级规则可能把带有其他安全主题的日志请求分到前面的类别，因而“日志分析”的范围比日常语言中的含义更窄。[图 3b、附录 B.4，第 5、12—13 页](https://arxiv.org/pdf/2603.01246v2)

论文用 2,000 次 bootstrap 给柱状图计算 95% 置信区间，并使用显著性水平 0.05 的卡方检验。它没有列出各区间端点、完整列联表、重采样单位、团队聚类处理或多重比较校正。本文未从像素估计区间端点，也未根据四舍五入后的比例反造各组样本数。

## 授权声明与改写实验要分两层读

### 原始分组：21.8% 对 11.6%

带授权信号的提示拒绝率为 21.8%，不带的为 11.6%；相对风险约 1.88，绝对差为 10.2 个百分点。论文报告 $\chi^2=9.23$，$p<0.01$。这是两组原始对话的比较，不代表研究者随机为相同提示加上或删去授权声明。[§4.3，第 4—5 页](https://arxiv.org/pdf/2603.01246v2)

### 改写结果：去掉授权措辞后为 13.7%

作者另行改写带授权信号的请求，尽量保留技术意图，去掉身份或授权措辞，再观察回应。正文报告从 21.8% 降至 13.7%，减少 8.1 个百分点；按原拒绝率计算，相对下降约 37.2%。

图 3a 把结果再按术语分组：

| 提示中的术语分组 | 原有授权信号 | 移除授权信号后 | 原本不含授权信号 |
| --- | ---: | ---: | ---: |
| 无指定安全术语 | 19.3% | 11.4% | 10.7% |
| 有指定安全术语 | 50.0% | 40.0% | 28.7% |

前两列对应论文所述改写前后；最后一列是原本没有授权信号的对照组，不能当成同一批提示改写后的第二步。例如，含术语组的改写变化是 50.0% 到 40.0%，并非 50.0% 到 28.7%。[§4.3、图 3a，第 5 页](https://arxiv.org/pdf/2603.01246v2)

附录 A.1 存在影响理解的文字不一致：开头说要移除攻击相关术语，但随后给出的改写指令要求移除授权或隶属信号，同时保留技术意图与安全术语。实际指令与图 3a 的授权实验一致。本文据此解释该实验，不把它写成“删除安全术语”的消融。

此外，附录称改写“被拒绝的提示”，但报告的原始拒绝率为 21.8%，不是一个全部已经拒绝的子集应有的 100%。原文没有充分说明选择集、统计集和再次测试集之间的关系，也没有公开配对数量、改写模型、采样参数、人工语义一致性检查及重复测试次数。因此可以报告作者给出的前后结果，但不能补写一套未披露的随机配对协议，或据此推广为普遍有效的提示修改方法。[附录 A.1，第 11 页](https://arxiv.org/pdf/2603.01246v2)

## 语义分析比关键词解释多提供了什么

### 输入向量可以预测拒绝标签

作者训练分类器，用不同输入特征预测回应是否被拒绝，并在保留数据上报告 AUC。表 1 的标题使用了 prediction accuracy，但实际列名和正文报告的是 AUC，不能解释为分类正确率。

| 预测特征 | AUC |
| --- | ---: |
| 提示向量与标注特征 | 0.842 |
| 仅提示向量 | 0.827 |
| 标注特征 | 0.669 |
| 模型类别 | 0.623 |
| 安全术语与授权信号 | 0.572 |
| 任务类别 | 0.569 |

AUC 衡量分类分数对正、负例的排序能力。忽略平分的特殊处理时，它可以理解为随机抽取一条拒绝样本与一条非拒绝样本，前者获得更高预测分数的概率；0.5 对应随机排序。它不要求先固定某个拒绝阈值。

仅用提示向量的 AUC 为 0.827，高于安全术语与授权信号的 0.572；增加标注特征后达到 0.842。这里比较的是预测拒绝的诊断分类器，不是训练一个更少拒绝的助手。论文未给出嵌入模型、分类器结构、数据拆分比例、调参过程、随机种子和 AUC 置信区间，因此无法从表中判断两种向量设置间 0.015 的差距是否稳定。[§4.5、表 1，第 6 页](https://arxiv.org/pdf/2603.01246v2)

这项结果也修正了正文前面较直接的“关键词匹配”解释：少量显式词语特征的预测能力有限，而更丰富的提示向量包含更多相关信息。它说明拒绝标签与输入语义表示有关，并不直接揭示被评估模型内部如何作决定，更没有定位到某一训练阶段造成的因果机制。

### 相近提示的拒绝标签有聚集现象

作者为每条提示查找 10 个近邻。对于被拒绝的提示，其近邻中 32.7% 也被拒绝；对于未被拒绝的提示，对应比例为 12.3%。论文报告二项检验 $p<10^{-16}$，并用 t-SNE 将提示向量投影到二维展示。

图 4 的图注把 12.3% 称为 base rate，但正文 §4.5 明确把它定义为未拒绝提示的近邻拒绝率；全体对话拒绝率另为 12.2%。本文按正文区分这三个量。二维散点图是提示嵌入的可视化，不是模型内部安全边界的直接图像。

近邻可能被多条提示重复选中。论文没有交代距离度量、是否排除自身、独立试验计数以及对重叠近邻的处理，因此不能自行把所有近邻关系当作相互独立的观测来复算显著性。语义聚集是描述性证据；作者提出的“接近有害内容的语义区域”仍属于机制解释。[§4.5、图 4，第 6—7 页](https://arxiv.org/pdf/2603.01246v2)

## 防御能力和 agent 的结论范围

讨论部分给出两种授权反而伴随拒绝的解释：授权措辞可能强化任务具有双重用途的印象，也可能类似模型曾经见过的规避安全限制的声明。论文没有通过训练数据追踪或模型内部干预区分它们。

作者进一步建议，在安全评估中同时测量不当协助和合法防御协助受损，并考虑明确、可审计的授权信息。这里提出的是评估与系统设计方向。本文没有验证一种新的权限接口，也没有提供降低拒绝后仍维持原有安全性的权衡曲线。

实际数据来自人与模型的单轮交互，未测试自主 agent 的长流程、重试策略、工具权限或任务成功率。讨论中的“安全诱发的拒绝服务”描述协助受阻，不是测得了网络拒绝服务攻击的吞吐量或可用性指标。论文 §3.4 提到计算团队拒绝率与比赛得分的 Spearman 相关性，却没有给出对应系数、团队数和结果；因此不能声称已测出拒绝造成比赛成绩下降。对于部署时的处置时延、修复质量和人员负担，也没有独立量化结果。[§3.4、§5—§6，第 4、6—8 页](https://arxiv.org/pdf/2603.01246v2)

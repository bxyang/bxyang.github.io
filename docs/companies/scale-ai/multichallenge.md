# MultiChallenge：多轮对话中的记忆、约束与版本追踪

用户先让助手安排一天的活动，随后几次调整午餐、演示和结束时间，最后又要求回到某个旧版本。回答最后一句话，需要找对历史版本，再把新要求加进去。MultiChallenge 将这类多轮依赖整理成四类挑战，用多 agent 生成候选对话、由人工修改审核，并为每题写一个可单独判定的二元问题。正式论文的首批六模型实验中，最高人工评测宏平均为 41.42%；这个分数只衡量选定的对话要求，不是整篇回答的全面正确率。[论文 §3–5、表 2](https://aclanthology.org/2025.findings-acl.958.pdf)

## 评测生成最后一轮，不重新演完整段对话

每条样本包含交替出现的用户与助手历史，最后一条是用户消息。被测模型读取整段历史，只生成一个最终回答。之前的助手内容由数据集固定提供，不会由每个被测模型重新生成。[论文 §1、§3](https://aclanthology.org/2025.findings-acl.958.pdf)、[数据生成调用](https://github.com/ekwinox117/multi-challenge/blob/5ccefcca6a39020d66c1383c4e6a809cb07afa33/src/data_loader.py)

这使不同模型面对相同输入，适合比较它们能否利用已经出现的上下文。但它没有测量“从第一轮开始与同一个用户持续互动”的完整系统表现，也没有持续运行的用户模拟器、工具环境或跨会话记忆库。

这一点对自洽性尤其重要：测试中的“自己以前说过什么”，指的是输入中被标为 assistant 的历史，不一定是当前模型曾经实际生成的内容。得分反映接续这段对话的能力。

## 四类挑战，各自追踪不同的历史信息

| 类别 | 论文与 GitHub 初版题数 | 最后一轮需要完成的事情 |
| --- | ---: | --- |
| 推断式记忆，Inference Memory | 113 | 找到之前散落的用户信息，判断它与当前要求的关联，再用于回答 |
| 指令保持，Instruction Retention | 69 | 延续第一轮明确要求整段对话遵守的约束 |
| 可靠版本编辑，Reliable Version Editing | 41 | 找到用户指向的历史版本，并按新要求修改 |
| 自洽性，Self-Coherence | 50 | 不因用户的简单确认或暗示，忽略此前已建立的说明 |
| 合计 | 273 | 每题归入一个主类别 |

表 1 报告平均约五轮、每段 1,231.7 个词。本次对 GitHub 全量 JSONL 复算，平均用户消息数为 5.059，按空白分词得到 1,231.696 词，与表中统计一致。每段有 2–10 条用户消息，以及相应的 1–9 条助手消息，总消息数是 3–19；不能把“最多十轮”误读为最多十条消息。

### 指令保持：保持的对象要在开头明确

论文电影节例子要求全程使用项目列表，而且不要推荐英国分级为 15 或 18 的电影。话题随后从一般选片转向主题策展，最后要求历史题材推荐。此时仍须检查最初的年龄约束。[图 1、附录 A.11](https://aclanthology.org/2025.findings-acl.958.pdf#page=46)

数据设计要求首轮说明约束适用于整段对话，而且后续用户不能给出与之冲突的新指令。这排除了“用户明确撤回旧要求”这一合理改变。约束既可以是格式、词数，也可以是电影分级这样的语义条件。

### 推断式记忆：知道信息，还要判断何时使用

论文的约会例子在早先一轮提到伴侣对坚果过敏，最后只要求推荐新甜点并列出材料。末轮没有直接询问过敏情况，模型需要自己把先前信息与食物推荐联系起来。[图 1、§3.1.2](https://aclanthology.org/2025.findings-acl.958.pdf)

它区别于直接问“她有什么过敏”：后者主要要求检索一句话，前者还要求判断检索到的信息应当约束当前回答。本文只用这个例子解释评测机制，不把模型生成的餐厅、菜单或成分当作已核实的现实资料。

### 版本编辑：回到旧版本后，再应用新变更

工作坊案例的关键状态可以压缩为下表；这是对附录对话的整理，不是新增实验。

| 历史状态 | 午餐 | 演示 | 结束时间 |
| --- | --- | --- | --- |
| 加入一小时演示后的版本 | 12:00–13:00，一小时 | 一小时 | 17:00 |
| 随后提前结束并延长午餐 | 11:40–13:10，九十分钟 | 一小时 | 16:00 |
| 后续继续修改 | 九十分钟 | 延长至九十分钟，并加入其他安排 | 16:00 |

最终用户要求回到“调整结束时间之前”的版本，再加入一小时赞助商介绍，不能删减原有环节，也不能提前开始。原文以是否恢复**一小时午餐**作为版本选择的关键判据。仅在最后一个版本中插入赞助商环节，即使时间计算自洽，也会用错基础版本。[附录 A.11，PDF 第 58–66 页](https://aclanthology.org/2025.findings-acl.958.pdf#page=58)

这个判据有意集中在特定错误上。o1-preview 的回答被标为通过，因为午餐恢复为一小时；但展示文本没有保留此前的签到环节。因此“通过该题选定的检查”不能扩大为“完整保留全部安排”。

### 自洽性：延续已说明的步骤

电子阅读器案例先给出设置步骤，包括连接 Wi-Fi 后注册账号。用户谈了其他话题，再确认连上 Wi-Fi 后是否只需选书。一个符合所选要求的回答需要补回注册步骤，而不是直接附和。[图 2、附录 A.11](https://aclanthology.org/2025.findings-acl.958.pdf#page=67)

基准要求合理一致，不意味着永远坚持历史中的错误。它没有系统测量遇到真实纠错证据时如何更新结论，也不能仅靠自洽性得分判断模型在现实事实上的准确程度。

## 多 agent 如何产生候选对话

构建系统名为 MMSE，由三个角色组成。它们是数据制作工具，不是被测模型推理时必须使用的组件。[论文 §4.1、图 3](https://aclanthology.org/2025.findings-acl.958.pdf)

1. **规划 agent** 接收主题、人物设定和挑战配置，写出对话蓝图，安排信息怎样引入、后续怎样间接引用。
2. **用户 agent** 把蓝图变成具体用户消息，与回答 agent 交谈。它还会根据实际回答调整提问。
3. **回答 agent** 扮演被测试的助手，依据当时对话生成回答。

每推进一轮，规划 agent 重新查看历史，判断是否出现符合类别的错误。如果没有，就修改后续蓝图；如果发现错误，就保存对话交给人工；到达轮数上限仍未找到错误则丢弃。

输入也有明确结构。主题种子按类别展开：版本编辑覆盖代码、邮件、日程、预算等；记忆覆盖偏好、关系、地点、时间与任务状态等。人物种子来自 PersonaHub。挑战配置包括名称、定义、通过条件、失败条件和失败示例。[附录 A.2–A.4](https://aclanthology.org/2025.findings-acl.958.pdf#page=13)

规划与用户提示要求对话自然、不用明显的强迫或误导制造错误，并排除只有小瑕疵的“失败”。附录蓝图展示了实际调整：助手正确回应餐厅关闭后，规划者增加多个地点、提醒与合并要求，提高需要追踪的信息量。这说明生成不是预先写好整段脚本后机械播放。[附录 A.10](https://aclanthology.org/2025.findings-acl.958.pdf#page=43)

不过，公开材料未完整给出规划与用户 agent 的模型版本、采样参数、总候选量、各阶段保留率及随机种子。附录提供两类 agent 的系统提示和回答模型名单，代码仓库提供评测入口；它不是一套可以原样运行的完整 MMSE 数据生产管线。

## 人工审核与难例筛选

每条候选先经标注者检查、修改，再经过两层审核；审核人员池与初次制作人员池分开。审核关注类别是否清楚、对话是否自然、失败是否合理，正式版也明确要求排除类别归属歧义。[论文 §4.2](https://aclanthology.org/2025.findings-acl.958.pdf)

候选必须使六个指定模型中的至少三个失败，才会被收录。正式版列出的模型是 GPT-4o 2024-08、Llama 3.1 405B Instruct、Mistral Large 2024-11、Claude 3.5 Sonnet 2024-10、Gemini 1.5 Pro 2024-08-27、o1-preview。

随机选择其中一个作为生成时的回答 agent，可以减少候选只围绕单个模型产生的情况，却不能消除最终筛选偏差。最终数据本来就是按这六个模型的失败选出的，因此分数不代表一般用户对话的成功概率，也不适合把后来未参与筛选的模型与它们视为完全对等的受测组。

论文没有给出标注者总人数、招募与能力测试详情、各题独立判断人数、审核前一致性、争议仲裁统计或独立保留集。匿名并列呈现六个回答有助于隐藏模型身份，但不等于每份回答都获得了相互独立、互不影响的判断。

## 将历史要求写进逐题评审问题

直接让裁判读整段对话并判断是否失败，需要裁判自己发现正确的历史依赖。MultiChallenge 改为让人工先写出实例级问题，裁判只读取**最终回答与这一问题**。[论文 §3.2](https://aclanthology.org/2025.findings-acl.958.pdf)

例如，版本编辑题可以检查午餐是否恢复为一小时；电子阅读器题检查是否提醒注册账号。历史依赖已经由人工转成具体条件，裁判不用再次在长对话中推导目标。代价是每个新题目仍需要认真编写和验证自己的评审条件。

`TARGET_QUESTION` 是交给裁判的检查问题，**不是交给被测模型的新用户请求**；`PASS_CRITERIA` 是期望裁判给出的 YES 或 NO。模型只收到 `CONVERSATION`，不应看到隐藏的检查条件。[固定评审代码](https://github.com/ekwinox117/multi-challenge/blob/5ccefcca6a39020d66c1383c4e6a809cb07afa33/src/evaluator.py)

正文有一处方向不一致：一方面写 YES 表示通过，另一方面以“推荐的甜点是否含坚果”为示例；对过敏场景，该问题应回答 NO 才通过。公开 GitHub 的 273 条 `PASS_CRITERIA` 全为 YES，实际题目通常采用正向的通过表述。复现应按每条问题和期望答案配对，不能照抄这句示例而忽略方向。

## 分数是类别宏平均，重复尝试还会改变含义

论文没有展开计分公式，以下符号是根据公开汇总实现整理。设第 $i$ 道题的最终回答为 $y_i$，检查问题为 $q_i$，期望判定为 $b_i$，裁判为 $J$：

$$
z_i=\mathbf{1}\{J(y_i,q_i)=b_i\}.
$$

令 $D_c$ 是类别 $c$ 的题目集合，则

$$
A_c=\frac{100}{|D_c|}\sum_{i\in D_c}z_i,
\qquad
A_{\mathrm{macro}}=\frac14\sum_{c=1}^{4}A_c.
$$

四类各占总分的四分之一，不按题数加权。原版中 113 道记忆题与 41 道版本编辑题在总分中权重相同，所以一道版本编辑题对总分的影响约为一道记忆题的 $113/41\approx2.76$ 倍。[固定汇总代码](https://github.com/ekwinox117/multi-challenge/blob/5ccefcca6a39020d66c1383c4e6a809cb07afa33/src/result_parser.py)

当前代码允许 `--attempts k`，此时采用

$$
z_i^{(k)}=\max_{1\le j\le k}\mathbf{1}\{J(y_{ij},q_i)=b_i\}.
$$

只要任一回答通过，该题就通过。这是给定 $k$ 次尝试的至少一次成功，不是平均单次准确率。默认值为 1；发布的十二组回答文件也均是每题一个回答。多次尝试的结果不能直接与论文主表并列。

本次仅对纯汇总函数运行一个自拟例子：A 类一题两次尝试，一次成功；B 类两题均失败。代码给出 A 类 100%、B 类 0%、宏平均 50%，而按三道题合并是 33.3%。这个检查确认了宏平均与任一尝试通过的实现，没有调用模型。

| o1-preview | 34.29 | 41.53 | 39.02 | 34.09 | 37.23 |

Claude 的总体分高于 o1-preview 4.19 个百分点，但 o1-preview 的记忆分高 4.24 个百分点、版本编辑分高 14.63 个百分点。因此整体得分相近或较高，不意味着每种多轮依赖都处理得更好。[表 2](https://aclanthology.org/2025.findings-acl.958.pdf#page=7)

表 3 的自动宏平均分别为 12.90、16.50、13.32、42.75、21.30、35.73。六模型次序与人工表相同，单模型宏平均差约 0.38–1.58 个百分点。接近的总体分并不保证同一道题判断相同：不同方向的误判可以相互抵消。

### 表格与发布数据仍有不能直接对齐之处

若按每题一次二元判断，表 2 的一些类别分数无法由表 1 的类别题数得到。例如指令保持的 14.29% 接近 $10/70$，却不能对应 69 题的整数成功数；记忆的 5.08% 接近 $6/118$，而公开类别数是 113。论文没有解释这部分分母差异，不能据此反推确切成功题数或擅自修正主表。

表 5 还有一个明确的汇总不一致：Mixtral-8x22B 四列为 15.94、3.54、15.94、8.00，其算术平均约 10.86%，表中却写 14.18%。缺少原始逐题判定，无法判断究竟是哪一格有误。其他清楚可核的结果，如 Llama 3.3 70B 的 23.19%，仍可按表引用；有问题的一行不作为精确排名依据。

## 人工与裁判一致性的含义

表 4 比较两种自动评审：直接读完整历史和类别条件，以及使用人工编写的实例级检查问题。

| 类别 | 直接评审与人工一致 | 实例级问题与人工一致 |
| --- | ---: | ---: |
| 指令保持 | 44.44% | 92.26% |
| 推断式记忆 | 37.53% | 94.62% |
| 版本编辑 | 31.82% | 94.85% |
| 自洽性 | 31.05% | 94.12% |
| Overall | 37.33% | 93.95% |

Overall 提高 **56.62 个百分点**。正文简述中的“约 36% 对 93%”不是表 4 的精确值；这里按正式表格列出。[表 4、§5.2](https://aclanthology.org/2025.findings-acl.958.pdf#page=7)

这里的一致性是是否给出相同通过/失败判断，不是模型完成任务的准确率，也不是 Cohen’s kappa 或 Macro F1。它使用主实验已有的人工标签，没有另外报告独立留出的裁判验证集、完整混淆矩阵、各类误报漏报或多次评审方差。

挑战集本身经过失败筛选，标签分布不平衡，所以只看一致率还不足以判断裁判识别“通过”与“失败”是否同样可靠。模型难以生成合格回答，也不自动证明它无法判断回答；这项实验直接支持的是：将历史依赖提前写成具体条件后，在这批标签上的一致性大幅提高。

这一比较同时改变了裁判读到的上下文、评审条件的具体程度和人工预处理量，不能只归因于提示变短。论文没有分别去掉人物种子、规划者或某层人工审核的消融，也没有单独隔离“实例条件”和“删除历史”的作用。

## 正式版的后续结果与实验边界

附录表 10 报告 Gemini 2.5 Pro Experimental（2025-03）51.91%、Claude 3.7 Sonnet Thinking（2025-02）51.58%、o1 Pro（2025-03）49.82%。这些结果说明“全部低于 50%”已经不适用于这组新增实验，但仍远未接近全题通过。[附录 A.8](https://aclanthology.org/2025.findings-acl.958.pdf#page=41)

表 10 同时含早期模型，其数值有时与表 5 不同，例如 Llama 3.3 70B 为 24.84% 而非 23.19%。论文没有完整解释重跑次数、具体裁判和采样差异，因此本页保留各表的实验归属，不将差值解释为模型自身升级。

### 推理参数没有完全统一

附录表 8 给出的生成温度为：GPT-4o 0；Llama 3.1、Mistral、Claude 3.5 为 0.2；Gemini 1.5 和 o1-preview 为 1.0；Llama 3.2/3.3 为 0.6；Qwen 与 Mixtral 组为 0.7。它是各模型配置下的对比，不是所有模型同温度的实验。

正式论文未完整给出每个 API 的输出上限、全部系统提示、重复采样与置信区间、模型运行日期和美元账单。新增模型的思考预算也没有完整列表，不能把其提升全部解释为某一训练或架构因素。

### 轮数、规模和发布日期分析属于观察

图 4 与附录表 9 没有表现出随轮数增加统一下降的趋势，例如版本编辑类别在 2、3、4、5 轮分别为 50%、25%、50%、8%。但各格来自不同题目，未给出每格数量和置信区间，也没有通过增加无关轮数构造配对实验。这支持“此分组未观察到统一单调关系”，不证明上下文长度完全不影响表现。[图 4、附录 A.7](https://aclanthology.org/2025.findings-acl.958.pdf#page=40)

参数量与发布日期的图同样混合不同系列、训练配方与预算。表 5 中 Qwen2.5-72B 的 16.91% 略低于 14B 的 17.07%，已经说明不能把更大参数量直接当作该基准上的保证。[表 5、图 5、图 8](https://aclanthology.org/2025.findings-acl.958.pdf)

## 人工投入与修改量

从零创作一条样本，论文报告平均需要 154.4 分钟；在 MMSE 候选上编辑则为 73.6 分钟，减少 80.8 分钟，约 **52.3%**。这是论文所记录的人工制作时间对比，不含可直接核算的合成 API 账单；也未披露两组样本量、任务分配与统计区间，不能当作完整生产成本减少 52.3%。[论文 §5.2](https://aclanthology.org/2025.findings-acl.958.pdf)

作者还用 fuzzywuzzy 的字符串相似度比较合成稿与人工终稿，平均相似度为 74.5%。其补数 25.5% 是该字符串指标的差异，不表示四分之一事实错误被纠正、四分之一 token 被替换，或四分之一对话被重写。

为了让裁判可以自动判定，团队没有公开那些连实例级问题也超出裁判能力的困难样本。公开集难度因此同时受生成模型、人工筛选和裁判能力约束；不能仅由它估计多轮对话的全部难点。

## 附录案例中需要保留的标注差异

完整案例能展示检查粒度，也暴露展示材料中的不一致。以下均依据正式 PDF，不能据此直接估计全数据的错误率。

- **甜点例子的 GPT-4o**：PDF 第 53 页标签为 PASS，所列两款甜点不包含旁注提到的山核桃派，旁注却以推荐该派解释失败。标签、回答与解释显然没有对应起来。
- **同题 Gemini 1.5**：第 54–55 页回答列出开心果酱，标为 PASS；理由却称没有加入坚果。末尾的过敏提醒不能使“没有加入”这一描述与配料文字一致。
- **电子阅读器例子**：第 69 页失败条件写应提醒语言选择和注册两步，但之后几个 PASS 回答只提醒注册。GitHub 中对应题的检查问题也只问注册，说明这一题实际公开标准比附录失败条件窄。

这些差异提示：复现时应保留具体题目版本、判据与逐项判定，不以案例旁注代替完整标签。尤其不能把只有一条检查问题的 PASS 解释为回答的事实、格式、完整性都已验证。[附录 A.11](https://aclanthology.org/2025.findings-acl.958.pdf#page=53)

## 公开实现的执行入口与阻碍

固定代码 commit 为 `5ccefcca6a39020d66c1383c4e6a809cb07afa33`，提交于 2025-02-05。本次阅读了 `main.py`、数据加载、裁判、汇总器及两个模型适配器。仓库发布十二组最终回答，每组 273 个不同 ID、每题一个回答，与题目 ID 完整对应；没有配套完整人工标签及裁判判定，不能只从现成回答重算论文一致率。

预期流程是从仓库根目录运行 `main.py`，读取 `data/benchmark_questions.jsonl`，通过 `--responses-file` 使用已有回答，或者通过 `--model-provider` 生成回答；随后调用裁判，并按类别汇总。即使提供已有回答，评审步骤仍会调用 API，不是离线运行。

默认裁判在 `Evaluator` 中指定为 `gpt-4o-2024-08-06`、温度 0，要求结构化返回 `reasoning` 和 YES/NO `verdict`。最终是否通过由 `verdict == pass_criteria` 判断，裁判本身没有接收原始对话或单独的通过方向。

静态检查发现当前仓库不能照 README 原样完成评测：

1. **初始化参数不匹配。** `Evaluator` 创建 `OpenAIModel` 时传入 `max_tokens=4096`，适配器构造函数却不接受这个参数，会先出现 `TypeError`。不能把这处 4096 当作已生效的输出上限。
2. **异常可能记到错误题目。** 收集 future 时没有保存与之绑定的题号和尝试号；失败分支沿用了循环变量，还把类别写为 `NA`。本次用提取出的类和固定假裁判做本地检查，A 题异常被记录成 B 题，确认了这一控制流问题。
3. **错误字符串被送去评分。** 生成失败时，加载器把异常文字及失败提示当作回答存入，再交给裁判，而不是稳定地记录一次基础设施失败。应单独保留生成失败与判定失败状态。
4. **多次尝试和输入形状需核对。** 成功记录的尝试号也使用了循环残留值；已发布回答是字符串列表，但加载器不验证类型，传入单个字符串可能被后续循环逐字符处理。空列表则可能没有评分记录，影响分母。

这些是当前公开实现的可见缺口，不证明论文内部评测一定触发过相同错误。复现应先补齐参数接口、逐任务异常归属、尝试编号和完整 ID 检查，再固定模型与题库版本。[评审器](https://github.com/ekwinox117/multi-challenge/blob/5ccefcca6a39020d66c1383c4e6a809cb07afa33/src/evaluator.py)、[OpenAI 适配器](https://github.com/ekwinox117/multi-challenge/blob/5ccefcca6a39020d66c1383c4e6a809cb07afa33/src/models/openai.py)

Hugging Face 适配器使用 BF16、`device_map="auto"`、最多新生成 2,000 token，并打开采样；CLI 传入的温度和 top-p 没有像 OpenAI 适配器那样转换为浮点数。依赖文件固定了 torch、transformers、OpenAI SDK 等版本，但这些设置不能自动代表正式论文各模型的全部实际配置。[HF 适配器](https://github.com/ekwinox117/multi-challenge/blob/5ccefcca6a39020d66c1383c4e6a809cb07afa33/src/models/huggingface.py)

对于原版 273 题、每题一次，理论上生成和裁判各需 273 次调用；读取已有回答则只需裁判调用。重复尝试、服务端重试与失败处理会改变实际数量。这是按接口估计的调用规模，不是测得的费用。

本页完成正式论文全文与附录、公开实现和两份全量数据快照的核查；只运行了数据统计、纯计分函数与假裁判控制流检查，未生成模型回答、未调用付费评审，也未声称复现论文得分。

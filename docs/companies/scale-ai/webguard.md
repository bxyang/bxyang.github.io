# WebGuard：在网页动作执行前判断后果

同样是点击购物网站上的按钮，“加入购物车”和“确认支付”会产生不同后果；名为 Checkout 的按钮也可能只是打开下一页。WebGuard 让一个独立模型在动作执行前，结合当前页面、目标元素和风险规则，判断这一步会产生什么影响。论文为此构建网页动作数据集，并用监督微调训练风险分类模型。微调明显改善了四种测试划分上的结果，但对新领域中的高风险动作仍有较多漏判。[论文 §2–4](https://arxiv.org/pdf/2507.14293v1)

## 版本、团队与研究范围

原题是 **WebGuard: Building a Generalizable Guardrail for Web Agents**。11 位作者为 Boyuan Zheng、Zeyi Liao、Scott Salisbury、Zeyuan Liu、Michael Lin、Qinyuan Zheng、Zifan Wang、Xiang Deng、Dawn Song、Huan Sun 和 Yu Su。Zifan Wang、Xiang Deng 署名 Scale AI，Dawn Song 署名 UC Berkeley，其余作者署名 Ohio State University。

本文阅读 2025 年 7 月 18 日的 arXiv v1，共 20 页，覆盖正文、参考文献和附录 A–G。首页标注 Preprint，arXiv 当前仅列 v1；这里不追加未经核实的正式会议归属。官方仓库固定到 `4135c4a97d61e1de230e806637728ebca2fd109e`，公开数据另固定 Hugging Face 版本。[版本记录](https://arxiv.org/abs/2507.14293v1) · [官方代码](https://github.com/OSU-NLP-Group/WebGuard/tree/4135c4a97d61e1de230e806637728ebca2fd109e)

WebGuard 研究的是**当前动作的后果等级**。它没有把整个任务的道德性质、用户是否恶意、动作是否符合用户指令等问题合并成一个标签。例如，用户正当地要求发送邮件，这一步仍可能被标为 HIGH，因为它影响收件人并产生持久结果。HIGH 不等于恶意，也不自动意味着应永久拒绝。[论文 §2.1、§2.3、§3.3](https://arxiv.org/pdf/2507.14293v1#page=3)

## 三类风险围绕即时后果定义

| 标签 | 判断标准 | 原文示例 |
| --- | --- | --- |
| SAFE | 仅有轻微、局部和容易撤销的影响，没有值得关注的持久变化 | 页面跳转、站内搜索、输入但未提交的评论 |
| LOW | 对用户本人有较小且可逆的影响，不影响他人，也不涉及明显法律或伦理风险 | 退出登录、改变语言偏好、加入购物车 |
| HIGH | 有重大或不可逆后果，可能影响他人，或涉及法律、财务、伦理影响 | 发出邮件、公开评论、删除账户、预约试驾 |

这套规则具有人为约定的边界。例如，代码中的提示把网站流量统计明确作为 SAFE 的例外：尽管服务器记录不可由用户撤销，这种变化通常不构成用户层面的重要后果。因此 SAFE 不能机械翻译成“底层系统绝对没有任何状态写入”。[论文 §2.1](https://arxiv.org/pdf/2507.14293v1#page=3) · [固定版本风险提示](https://github.com/OSU-NLP-Group/WebGuard/blob/4135c4a97d61e1de230e806637728ebca2fd109e/data_processing/prompts/multimodal/system_prompt.md)

判断也限定在这一步。护照申请属于重要流程，但填写一栏、翻页、最后提交申请并不具有相同即时影响。模型若只识别“护照”“支付”等主题词，容易把中间动作一并判为高风险。

## 数据如何采集和复核

作者从 Information、Services、Shopping、Entertainment、Travel、Social、Work 七个顶层领域选择网站，下分 22 类。论文汇总称覆盖 193 个网站，包含 15 个长尾网站；这里的“领域”有顶层与细分类两个层次，七类与 22 类并不矛盾。[论文图 2、附录 A](https://arxiv.org/pdf/2507.14293v1#page=3)

标注人员先接受示例培训，通过资格测试后再正式工作。每个网站最多探索一小时，寻找可能改变状态的动作。遇到提交表单等操作，先补齐必要前提，再记录目标元素，避免标注一个实际不能触发的按钮。工具基于 WebOlympus Chrome 扩展，保存页面截图、边框、元素元数据和链接；需要查看执行结果才能判断时，支持事后修订标签。[论文 §2.2](https://arxiv.org/pdf/2507.14293v1#page=4)

采集过程有一个影响标签质量的默认规则：**人工标记有风险的元素，其余未标记元素默认 SAFE**。工具会滚动页面收集截图，减少手工逐个登记普通链接的工作。官方指南也明确提醒，遗漏风险元素会使其进入 SAFE 数据。因此 SAFE 标签的可靠性依赖标注人员探索的完整程度，不能理解成每个元素都经历了同样的独立后果验证。[标注指南](https://github.com/OSU-NLP-Group/WebGuard/blob/4135c4a97d61e1de230e806637728ebca2fd109e/annotation_tool/annotation_tool_introduction.md)

后续由三名专业复核人员检查风险标签和截图完整性，必要时重新打开保存的链接验证，并检查边框与元素位置。论文没有报告逐项三人投票比例、一致性系数、复核改标率或所有动作的实际执行次数，不能仅凭“三人复核”推导出标签准确率。[论文 §2.2](https://arxiv.org/pdf/2507.14293v1#page=4)

### 4,939 条样本与 4,956 条有效标签

正文总量与正式训练、测试划分都为 4,939。但 §2.2 的类别统计是 HIGH 1,108、LOW 2,284、SAFE 1,564，合计 **4,956**。本次读取固定仓库全部 JSON 后，确认这些数值对应不同阶段的数据：

| 数据层次 | 本次核对结果 |
| --- | --- |
| 原始复核元数据 | 6,491 行，其中 4,956 行有三类有效标签，其余为缺失或 BUG/Bug |
| 正式五份划分文件 | 合计 4,939 行：HIGH 1,100、LOW 2,279、SAFE 1,560 |
| Hugging Face 发布表 | 5,999 行：三类标签合计 4,956，另有 1,043 行空标签 |

因此 Hugging Face 的 `train` 分区并不是论文的 1,982 条训练集，也不能直接把其中全部 5,999 行用于监督训练。复核元数据与正式划分相差 17 条有效标签；现有转换代码还依赖未发布的本地划分文件，本文无法据此确定这 17 条各因何被排除。[固定数据目录](https://github.com/OSU-NLP-Group/WebGuard/tree/4135c4a97d61e1de230e806637728ebca2fd109e/data) · [固定 Hugging Face 数据](https://huggingface.co/datasets/osunlp/WebGuard/tree/6accaab0864d4c9d668f06ff77bc0dea2bb1e6cd)

## 从页面与动作到风险标签

原文把任务写成三分类函数：

$$
f(S,A,R)\rightarrow y,\qquad y\in\{\mathrm{SAFE},\mathrm{LOW},\mathrm{HIGH}\}.
$$

$S$ 表示当前页面状态，$A$ 是拟执行动作，$R$ 是含定义和例子的风险规则。页面和动作有两种表示方式：

- **多模态输入**：截图上用边框标记目标元素，同时提供元素描述、HTML 标签、URL 和动作说明。
- **文本输入**：用可访问性树式的元素列表描述页面，以节点编号和元素文字定位动作，再附上相关元数据。

风险规则随输入提供，模型需要把页面中具体操作的后果映射到规则。标签以当前动作的即时影响为依据，而不是预测整条任务轨迹最终是否安全。[论文 §3.1–3.2、附录 C](https://arxiv.org/pdf/2507.14293v1#page=5)

公开 `format_a11y_tree.py` 根据已采集的交互元素构造视口内列表：把链接、按钮、输入框等转成角色与文字，给出编号，并定位目标。输出是以 RootWebArea 为根的扁平元素列表，并不保留完整网页 DOM 层级。论文关于浏览器可访问性树的一般定义，与这段公开转换实现的细节需要区分。[固定转换代码](https://github.com/OSU-NLP-Group/WebGuard/blob/4135c4a97d61e1de230e806637728ebca2fd109e/data_processing/format_a11y_tree.py)

### 提示推理与监督微调

零样本提示要求模型先理解页面，再推断动作后果，最后输出等级。这是提示中的推理要求，不是另外训练了一个可模拟网站状态转移的模型。

监督微调使用 Qwen2.5 与 Qwen2.5-VL 的 3B、7B 模型。训练数据没有逐步推理标注，公开样本的目标是类似 `{"risky_level": "HIGH"}` 的标签 JSON。因此微调结果的提高不能归因于学到了人工标注的完整后果推理链。[论文 §3.2](https://arxiv.org/pdf/2507.14293v1#page=6)

从序列监督的角度，可将训练目标说明为：

$$
\mathcal L_{\mathrm{SFT}}=-\sum_{i}\sum_{t}\log P_\theta(z_{it}\mid S_i,A_i,R,z_{i,<t}),
$$

$z_i$ 是正确标签 JSON 的输出 token 序列。这是解释标签生成式微调的通用形式，原文没有单独推导这一损失；具体模板与训练框架如何处理输入 token 的损失掩码，需要固定实际 LLaMA-Factory 版本。

论文称 full-size training，公开配置使用 `finetuning_type: full`。但两个视觉模型同时设置 `freeze_vision_tower: true` 和 `freeze_multi_modal_projector: true`，所以不能概括为视觉编码器、投影层和语言模型的所有参数都更新。[固定训练配置](https://github.com/OSU-NLP-Group/WebGuard/tree/4135c4a97d61e1de230e806637728ebca2fd109e/configs)

## 评价指标与告警阈值

对真实标签 $y_i$ 和预测 $\hat y_i$，准确率是：

$$
\mathrm{Accuracy}=\frac{1}{N}\sum_i\mathbf1[\hat y_i=y_i].
$$

HIGH 召回率的分母只包含真实 HIGH：

$$
\mathrm{Recall}_{H}=\frac{\sum_i\mathbf1[y_i=H\land\hat y_i=H]}{\sum_i\mathbf1[y_i=H]}.
$$

LOW 召回率同理。HIGH 被预测为 LOW 或 SAFE 都降低这个召回率，但两者在实际告警中未必等价：如果系统设定 LOW 及以上都暂停，HIGH→LOW 仍会触发人工确认。论文表中的三分类召回率并不是任意告警阈值下的端到端拦截率。[论文 §3.3、§4.2](https://arxiv.org/pdf/2507.14293v1#page=6)

准确率和召回率也不能完整描述误报。自拟例子：100 个动作中有 10 个 HIGH，全部预测 HIGH 可以取得 100% 的 HIGH 召回率，但只有 10% 准确率，用户会收到大量多余提醒。论文 §4.2 提到平均 F1，但主要结果表只列准确率、HIGH 与 LOW 召回率，没有提供逐类精确率、混淆矩阵或完整 F1 表。因此无法独立重算部署时的误报负担。

### 微调收益明显，但跨领域仍然较弱

Qwen2.5-VL-7B 微调后的准确率增量，按四列分别为 **58.0、36.9、45.0、47.7 个百分点**。HIGH 召回率增量分别为 **72.0、44.5、69.1、63.0 个百分点**。因此正文“所有划分提升超过 60 点”的概括不适用于跨领域那一列。

微调后的 HIGH 召回率在 Cross-Domain 为 66.8%，相当于该划分中约三分之一真实 HIGH 没有被判成 HIGH；跨网站为 90.2%。这支持在所测数据中，新领域的后果规则与界面模式更难泛化，但没有受控实验进一步分离领域、标签分布和页面设计的各自作用。

7B 视觉模型的四列准确率都高于 3B 视觉模型，但 HIGH 召回率除跨网站持平外均低于 3B。因而“更大模型最好”只适用于部分指标，不能同时概括所有召回结果。[论文表 2](https://arxiv.org/pdf/2507.14293v1#page=8)

### 摘要与正文的平均值没有完全统一

摘要概括准确率约 37% → 80%、HIGH 召回率约 20% → 76%；引言又写约 38% → 80%、HIGH 召回超过 80%。这些概括无法用同一种已说明的汇总方式全部重现。

根据表 2 的已舍入数值，四个划分等权平均得到 Qwen2.5-VL-7B 准确率 **36.675%**、WebGuard-VL-7B **83.575%**；按各测试集样本数加权则约 **38.84%** 和 **80.35%**。对 HIGH 召回率按公开 HIGH 数量加权，前后约为 **20.79%** 和 **77.54%**。后两项计算还要求历史测试纳入样本与当前公开划分一致。

这些是本次根据公开数值做的复算，不是作者额外发布的成绩。没有逐样本预测和评分脚本，无法确认所有平均值的历史口径；因此本文以分列结果作为主要依据。[论文摘要、§4.3、表 2](https://arxiv.org/pdf/2507.14293v1)

### 模态和推理能力的影响并不一致

作者认为文本在零样本时更容易提供结构化语义，微调后视觉输入更有优势。这与部分结果一致：Qwen 7B 的文本模型在长尾集上为 44.8%，视觉模型为 26.6%；微调后视觉 7B 为 84.6%，文本为 68.5%。

但它不是逐列普遍成立的规律。GPT-4o 的视觉输入在跨网站上比文本高 11.0 个百分点；Qwen 7B 零样本的跨网站视觉结果也略高于文本。两种 Qwen 还是不同预训练模型，不能把差异全部当作仅切换截图与文本的因果效果。

扩展思考也未统一改善风险召回。文本 Claude 3.7 Sonnet 开启 thinking 后，长尾准确率从 49.0% 到 52.4%，HIGH 召回从 48.0% 到 42.0%；跨网站准确率反而从 50.0% 降到 43.4%。o3 的表现不能等同于对另一个模型只打开推理开关。论文没有给出相同模型、相同预算、不同推理长度的受控曲线。[论文表 2、§4.3](https://arxiv.org/pdf/2507.14293v1#page=8)

结果表未报告重复运行方差、随机种子或置信区间。上述差值是已报告实验的比较，不附加统计显著性结论。

## 错误案例反映了两种不同问题

附录 D 的护照申请案例是勾选确认已阅读声明的复选框。原图真实标签为 SAFE，模型预测 LOW，展示的是对中间步骤的风险高估；不能把这个具体例子改写成原图预测 HIGH。本文只说明数据集的标注规则，不把这一标签当作对所有声明勾选行为的法律判断。[论文图 5](https://arxiv.org/pdf/2507.14293v1#page=18)

附录 E 的 Checkout 案例中，作者说明点击只进入下一步，真实标签 LOW，图中列出的预测 HIGH。这支持区分“进入结账流程”和“真正提交交易”。但同一图的 Prediction 文字又说没有财务承诺、可返回，与 HIGH 标签并不一致。缺少原始模型输出，无法区分最终标签提取、解释与分类不一致，或图示编辑等原因；不能仅凭这张图断言模型完全没有理解下一步后果。[论文图 6](https://arxiv.org/pdf/2507.14293v1#page=19)

两例共同说明，主题或按钮名称不足以唯一确定后果。不过原文没有给出各错误类型占比，也没有训练网页状态预测器后再对照，所以“加入世界模型能解决问题”仍是后续研究方向。

## 训练配置与可重复实验

论文附录 F 说明本地训练与推理使用一个 **4×H100 80GB** 节点，OpenAI API 通过 Azure、Claude 通过 AWS。具体 API 模型快照、采样参数、总运行时间和费用没有完整列出。[论文附录 F](https://arxiv.org/pdf/2507.14293v1#page=20)

固定仓库四个配置都采用监督微调、学习率 $10^{-5}$、20 个 epoch、cosine 调度、10% warmup、bfloat16、2,048 token 截断长度，以及从训练数据划出 10% 验证。视觉输入上限为 262,144 像素。

| 配置 | 每设备 batch | 梯度累积 | 按 4 设备计算的有效 batch |
| --- | ---: | ---: | ---: |
| 文本 3B | 4 | 16 | 256 |
| 文本 7B | 4 | 8 | 128 |
| 视觉 3B | 8 | 4 | 128 |
| 视觉 7B | 1 | 16 | 64 |

有效 batch 是按论文硬件数量对配置的换算，不是独立运行日志。它们并非完全相同的优化设置。`val_size: 0.1` 意味着 1,982 行还会再拆出内部验证部分，不能声称全部样本在每次训练中都参与梯度更新。

本次静态检查还发现几个影响复现的路径和版本问题：

- 多模态 JSON 的 `images` 使用作者机器上的 `/fs/ess/...` 绝对路径，仓库没有包含这些路径对应的完整截图文件。Hugging Face 的 Screenshot 字段提供外部链接，不是内嵌图像。
- 转换脚本的输入、输出、提示文件默认指向作者的本地目录，并硬编码一个未随仓库发布的 `analysis/test_splits.json`。即使改命令行输入参数，仍需处理这项内部路径。
- 该脚本输出带 `_with_thought` 后缀的文件，而训练配置引用无此后缀的已有文件。提示模板要求 thought 字段，已有训练样本目标却只有标签，不能默认重跑脚本会逐字重建发布文件。
- README 克隆最新 LLaMA-Factory，没有固定提交。DeepSpeed 配置路径来自该外部项目；需要正确放置数据注册表、数据文件和训练 YAML 后才能使用。

这些结论来自公开文件检查，没有实际启动训练，也没有验证外部截图链接的全量可下载性。[数据转换代码](https://github.com/OSU-NLP-Group/WebGuard/blob/4135c4a97d61e1de230e806637728ebca2fd109e/data_processing/multimodal_generata_factory_input_data.py) · [训练配置与 README](https://github.com/OSU-NLP-Group/WebGuard/tree/4135c4a97d61e1de230e806637728ebca2fd109e)

## 公开范围与结论边界

本次已读取公开仓库全部训练、测试 JSON 和原始复核元数据，解析 Hugging Face 固定版本的全部 5,999 行 Parquet，检查训练与转换代码，并对原文结果做算术核对。没有运行模型、访问受测网站执行动作、重做人工标注或复现训练成绩。

代码声明 MIT，数据声明 CC BY-NC 4.0。仓库提供标注工具压缩包与训练配置，但本次未在其 README 或 OSU NLP 的 WebGuard 模型检索结果中找到可固定版本的训练后权重链接，也未找到生成表 2 的完整推理和指标汇总代码。这是此次可访问材料的范围，不代表能排除其他发布渠道。[官方仓库](https://github.com/OSU-NLP-Group/WebGuard/tree/4135c4a97d61e1de230e806637728ebca2fd109e)

论文的实际实验是对保存的页面—动作样本分类。图 3 描绘了让用户批准、拒绝或修改动作的接入方式，但没有报告整条 agent 任务的事故减少量、人工确认次数、用户体验或额外延迟。它也没有针对提示注入、恶意网页改写、网站更新和连续动作的累积风险做完整测试。

因此，已验证的进展是任务监督改善了这套风险规则下的动作分类与部分泛化能力。距离可靠的在线护栏，还需要补齐错误校准、执行后果验证、长期流程和实际人工交互的证据。[论文 §3.3、§5、附录 G](https://arxiv.org/pdf/2507.14293v1)

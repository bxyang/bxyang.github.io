# Insights Generator：批量执行轨迹诊断

一个处理电子表格的 agent 可能没有报错，也成功保存了文件，答案却仍然错误。开发者需要从许多次执行记录中判断：哪些错误反复出现，涉及多少任务，问题出在提示、工具还是执行框架。Insights Generator（IG）把这项工作组织成一套多 agent 诊断流程：先从样本提出假设，再提取整批轨迹的特征、比较不同任务组，最后生成带有发生比例和具体证据的报告。论文中，使用 IG 报告的工程师把框架的测试通过率从 27.0% 改到 57.4%；这个提高 30.4 个百分点的结果属于人工修改实验，不能当作 IG 自动改写代码的成绩。[论文 §1、§3–4、表 2](https://arxiv.org/pdf/2605.21347v3)

## 从单条错误到一批轨迹中的共同原因

输入是一个轨迹集合：

$$
\mathcal C=\{\tau_1,\ldots,\tau_N\}.
$$

每条轨迹包含模型消息、工具调用、工具返回等执行内容，也可以带有任务类别、是否成功、耗时等元数据。用户再给出一个开放诊断请求，例如寻找反复出现、可以通过修改框架解决的失败模式。系统输出自然语言发现、涉及的轨迹集合、发生比例、引文证据和建议动作。已有成功标签有助于比较成功组和失败组，但架构并不把标签设为必需输入。[§3、附录 A.7](https://arxiv.org/pdf/2605.21347v3)

下面是说明流程的自拟例子，不是论文实验：100 次表格任务中有 40 次失败，调查发现其中 24 次写入了尚未计算的公式。这个模式占失败任务的 60%，占全体任务的 24%。这两个比例的分母不同；报告还需检查成功任务中是否存在同样行为，以及失败是否确实由公式未计算导致。单列一个相关行为，不能自动完成因果归因。

原文的一类实际发现涉及 openpyxl：写入 Excel 公式不会在 Python 环境里自动完成公式计算。附录 A.10 描述自动改写第一轮的报告把这类问题归入大量失败；之后的报告继续发现自然语言被错误送进 Python 执行、库 API 版本不匹配等更具体的问题。这些是作者对报告内容的分析，不能把报告内的所有比例视作另有独立人工标注的真值。[附录 A.10.4](https://arxiv.org/pdf/2605.21347v3)

此前方法的差别主要在分析组织方式。单个编码 agent 自己检索文件、做统计、写报告；扁平的多 agent 方法把轨迹分给多个分析者，再合并结论；递归方法把任务交给子调用。IG 同时改变数据访问方式与分析分工，并把“发现候选模式”和“检查模式是否成立”分给不同角色。对照实验中的 Trace2Skill 是受其启发的实现，RLM 使用深度为 2 的普通递归版本；不能据此比较这些研究所有可能的实现。[§2、附录 A.6](https://arxiv.org/pdf/2605.21347v3)

## 数据留在 Python 中，模型通过工具读取

IG 建立一个持久化的数据层，把轨迹和已提取特征存为可查询的数据。模型编写 Python 代码，在有状态的 REPL 中调用分析函数，获取所需片段、统计量和摘要。较长的原始内容不必每轮都完整放入上下文。[§3.2–3.3](https://arxiv.org/pdf/2605.21347v3)

这不是完全禁止模型读取原文。表 4 明确提供 `get_trace` 和 `get_trace_chunk`；较长轨迹可以先返回分块概览，再按需要读取。`load_traces` 返回 Polars DataFrame，`get_schema` 提供列类型、缺失率、分布和相关性。搜索同时使用语义与关键词信号。轨迹 ID 会转换为短字符串，报告生成后再映射回原 ID。

工具可以按工作过程理解：

| 环节 | 主要函数 | 作用 |
| --- | --- | --- |
| 定位材料 | `load_traces`、`get_trace`、`get_trace_chunk`、`search_traces` | 筛选轨迹并读取证据 |
| 查看已有分析 | `get_schema`、`get_extractions` | 避免重复提取，了解当前特征列 |
| 生成语义特征 | `extract`、`summarize_trace`、`summarize_group` | 对行为做结构化提取或摘要 |
| 对照调查 | `compare_segments` | 比较两个任务组的差异 |
| 保存结果 | `save_column`、`save_affected_traces` | 保存特征列和发现所涉及的轨迹 |
| 同步共享数据 | `reload_data`、`consolidate` | 合并新提取结果，刷新数据与模式信息 |

表中共 14 个工具。权限并不完全一致：主配置中 Orchestrator 不能调用 `extract`；`compare_segments` 和 `save_affected_traces` 只给 Investigator。各 agent 共享数据存储，但拥有各自的 REPL 会话，不应理解为所有 Python 局部变量自动共享。[附录 A.2–A.3、表 4，PDF 第 30 页](https://arxiv.org/pdf/2605.21347v3)

## Scout 提出假设，Investigator 检查证据

Orchestrator 接收用户请求，决定先看哪些群体、派出哪些子 agent、继续调查还是提交报告。Scout 负责广泛寻找候选模式；Investigator 围绕具体假设做更深入的核查。这个循环可以多次交替进行，并非固定执行一次抽样和一次验证。[算法 1、附录 A.1](https://arxiv.org/pdf/2605.21347v3)

Scout 提示建议先查看 50–200 条有代表性的轨迹，再对约 10–30 条材料做集中提取。输出包括假设名称、描述、证据 ID、短引文、解释及初步发生比例。初步线索仍需核查，不能直接作为全体任务的结论。

Investigator 的提示安排了三个层次：先在全量元数据上分组统计，再对 50–100 条样本提取语义特征，必要时比较两到三个不同样本组。调查对象可以是全体轨迹，也可以是具有代表性的子集。最终状态为 confirmed、refuted 或 inconclusive；算法 1 的最终发现集合只累积已确认结果。

以一个模式的发生比例为例，可以把计算写成：

$$
\widehat p(A\mid G)=\frac{\sum_{i=1}^{N}\mathbf 1[\tau_i\in G]\mathbf 1[A(\tau_i)]}
{\sum_{i=1}^{N}\mathbf 1[\tau_i\in G]}.
$$

这里 $G$ 是明确指定的群体，$A$ 是对每条轨迹判定的行为特征。这是本文为解释报告口径写出的计数公式；IG 没有为此训练一个新的损失函数。如果 $A$ 由 LLM 提取，比例同时依赖特征识别是否正确。若只分析子样本，还需说明样本来自哪里，不能直接冒充全体计数。

提示要求保存受影响轨迹 ID，给出多条证据及逐条解释，并允许报告检验结果、效应量和比值比。对样本量的提示规则是大于 100 条倾向高置信、20–100 条中等、小于 20 条低置信。这是工作指引，不是一个经过校准的置信区间，也没有自动解决反复搜索假设产生的多重比较问题。本文不把 Investigator 的 confirmed 状态解释成已经证明因果关系。[附录 A.1](https://arxiv.org/pdf/2605.21347v3)

## 实验使用的轨迹和模型

正式比较主要围绕 SpreadsheetBench 与 Humanity’s Last Exam（HLE）。它们在这里提供 agent 执行轨迹，IG 的任务是分析轨迹，不是直接答原来的题。[§4、附录 A.4](https://arxiv.org/pdf/2605.21347v3)

| 实验材料 | 规模与原始结果 | 执行设置 |
| --- | --- | --- |
| 自动报告评分：SpreadsheetBench | 296 条，125 成功、171 失败，成功率约 42.2% | GPT-5.4 medium 生成；ReAct 框架最多 5 轮，使用 openpyxl/pandas，无 Web 工具 |
| 自动报告评分：HLE | 250 条，59 成功、191 失败，成功率 23.6% | 可调用搜索、网页获取、代码工具；预算 20 次，实际观察到 0–18 次工具调用 |
| 人工研究训练材料 | 附录写 250 条，110 成功、140 失败，成功率 44% | GPT-5.2 生成，具体拆分差异见后文 |

HLE 原任务的定位不能用来断言这里的 agent 没有联网。该轨迹集合中，207 条使用过工具，55 条答对；43 条没有使用工具，4 条答对。这是观察分组，不是随机分派的工具效果实验。[附录 A.4](https://arxiv.org/pdf/2605.21347v3)

IG 的 Orchestrator、Scout、Investigator 和群体比较使用 Claude Opus 4.6，批量提取及摘要使用 Claude Haiku 4.5。表 3 的提取配置给出 50 个并发调用、每次调用 300 秒超时、50,000 token 的长轨迹分块阈值、搜索返回前 20 项，以及每个主 agent/子 agent 至多 500 轮。沙箱配置为 16 CPU、64 GB 内存、4 小时超时。正文说附录包含采样设置，但表 3 没有给出可直接复用的 temperature 数值。[§3.3、表 3](https://arxiv.org/pdf/2605.21347v3)

每个 benchmark 上生成三次独立报告，三次使用同一份固定轨迹集合。因此它测量的是分析运行的变化，不是三份独立抽取的数据集。对照都以 Opus 4.6 为主模型；Claude Code 多 agent 对照还使用相同的 Scout/Investigator 角色，但通过原始文件系统分析。两者不只在角色数量上不同，工具和数据访问方式也是差异来源。[§4.1、附录 A.6](https://arxiv.org/pdf/2605.21347v3)

## 报告评分：覆盖范围和解释质量是不同指标

自动评分先汇总各系统、各次运行的发现，再由 LLM 合并成每个 benchmark 的 50 个模式簇，作为 union-gold 参照。这是一套由候选报告共同构造的参照，不能当作独立专家事先枚举的完整错误清单。[附录 A.7](https://arxiv.org/pdf/2605.21347v3)

覆盖率的判定尤其需要解释：报告引用的轨迹 ID 只要与某个簇的引用有交集，就算覆盖该簇。两个报告可能引用同一次执行，却解释不同的现象，因此这个指标不能单独衡量发现是否正确。评分还会从机制、具体程度和可执行性判断解释深度。

原文评分提示共有检测、机制、证据、具体程度、可执行性五个维度，取值 0–3；主表综合分只平均其中三个：

$$
Q=\frac{Q_{\rm mechanism}+Q_{\rm specificity}+Q_{\rm actionability}}{3}.
$$

所以 $Q$ 既不是正确率，也不是五个维度的总平均。两两比较则调换报告位置，并把平局计作半胜：

$$
\mathrm{WR}=\frac{W+T/2}{R}.
$$

$W$、$T$、$R$ 分别是获胜、平局和比较总次数。下面转录主表的跨 benchmark 平均值。[表 1、附录 A.7–A.8](https://arxiv.org/pdf/2605.21347v3)

| 方法 | 覆盖率，% | 两两胜率，% | 综合分，0–3 |
| --- | ---: | ---: | ---: |
| IG | 91.0 | 77.9 | 1.32 |
| Claude Code 多 agent | 95.0 | 62.4 | 1.10 |
| Trace2Skill 风格实现 | 97.0 | 52.6 | 1.18 |
| RLM | 92.5 | 11.4 | 0.92 |
| 单个编码 agent | 80.0 | 10.5 | 0.76 |

IG 的覆盖率并非最高，表中优势主要出现在解释质量和两两偏好。自动评分器也是 Opus 4.6，没有独立人工真值证明每个自动偏好都正确。

还有一处复核限制：附录表 8 的 SpreadsheetBench 矩阵中，IG 对四个主要对照的值为 56%、50%、100%、100%，等权平均为 76.5%，不能直接重建表 7 的 72.4%。主表同时列有两种架构消融，但矩阵未完整展示这些比较。论文没有把两张表的比较集合和汇总分母解释到足以逐项复算的程度。这里保留原表数字，不自行改写为一个推测的统一胜率。[表 7–9](https://arxiv.org/pdf/2605.21347v3)

## 架构消融：分工与并行分别带来变化

两项消融保留数据层和分析工具：Orchestrator-only 禁用子 agent 调度；Generic Subagents 保留并行子 agent，但把专门的 Scout/Investigator 换成通用分析角色。[表 1、表 11](https://arxiv.org/pdf/2605.21347v3)

| 架构 | 平均覆盖率，% | 平均两两胜率，% | 平均综合分 |
| --- | ---: | ---: | ---: |
| 仅 Orchestrator | 82.0 | 32.0 | 0.85 |
| 通用子 agent | 90.0 | 67.5 | 1.10 |
| 完整 IG | 91.0 | 77.9 | 1.32 |

通用并行子 agent 相比单个 Orchestrator 增加 35.5 个百分点胜率，专门角色再增加 10.4 个百分点。前者同时扩大覆盖范围；后者覆盖率只增加 1 个百分点，而解释质量改善更明显。这支持分工方式与报告深度有关，但不能把两个相邻配置差值当作普遍适用、彼此独立的因果贡献。实验也没有把工具访问、总调用量和 token 成本全部匹配成同一个固定预算。

## 工程师使用报告后的改进

人工修改研究招募有 LLM agent 开发经验的软件工程师，每组 6 人，随机分配到 IG 报告或 Claude Code 多 agent 报告；参与者和结果评分者不知道报告来源。每人最多 1.5 小时，使用编码助手，并得到 50 美元的 Opus 4.6 API 预算。可修改提示、执行循环及非锁定参数，模型、5 轮预算、5 行预览、60 秒逐单元格执行超时等保持锁定。每份提交在测试集上运行三次，先平均为参与者分数，再比较组间差异。[§4.2、附录 A.11.2](https://arxiv.org/pdf/2605.21347v3)

| 条件 | 测试通过率，% | 相对未改框架，百分点 |
| --- | ---: | ---: |
| 未修改框架 | 27.0 | — |
| 工程师使用 Claude Code 报告 | 43.2 ± 4.1 | +16.2 |
| 工程师使用 IG 报告 | 57.4 ± 1.5 | +30.4 |

误差是参与者之间的标准误 SEM，不是题目之间的波动。真正的组间比较约为 14.17 个百分点。对两组各 6 位参与者的均分使用 Welch 检验：

$$
t=\frac{\bar x_{\rm IG}-\bar x_{\rm CC}}
{\sqrt{s_{\rm IG}^{2}/6+s_{\rm CC}^{2}/6}}.
$$

附录给出两组标准差 3.69 与 9.95，得到标准误约 4.33、$t\approx3.27$、自由度约 6.35、双侧 $p=0.016$；差值的 95% 区间为 [3.56, 24.78] 个百分点。枚举 $\binom{12}{6}=924$ 种重新分组，有 12 种至少达到观察差值，置换检验 $p\approx0.013$。这些统计单位是 12 位参与者，不能把 36 次运行当作互相独立的 36 位工程师。[附录 A.9](https://arxiv.org/pdf/2605.21347v3)

论文还报告逐人剔除后的组间差值保持为正，但样本规模只足以较可靠地检出很大的效应。工程师的净代码修改量均值为 IG 203 行、对照 286 行，差异不显著；删除对照组一个大改动样本后，均值方向反转。因此，“更少改动获得更大提升”不能作为经过统计验证的结果。

材料拆分存在未解开的差异。正文和表 2 把测试描述为 250 个保留任务；附录又列出 250 条训练轨迹、50 个开发任务和另一个与开发集分离的测试集。原文介绍的 SpreadsheetBench Verified 总量为 400，未提供任务 ID 清单来明确这些数量如何对应。附录还说明训练轨迹来自 GPT-5.2，修改后的框架以 Opus 4.6 测试。本文据实保留这层模型转换，不能把训练轨迹的 44% 与测试的 27% 拼成同模型、同数据的性能变化。[§4、表 2、附录 A.4、A.11.2](https://arxiv.org/pdf/2605.21347v3)

## 人类对报告本身的评分没有显著拉开差距

另一项人工研究请 12 位专家给 23 条发现评分，其中 11 条来自 IG、12 条来自 Claude Code 多 agent。评分为 1–5 分，维度是正确性、深度、证据质量和可执行性。先对每条发现汇总专家评分，再统计组内均值；这不等于拥有 276 条独立发现。[§4.3、表 6、附录 A.11.1](https://arxiv.org/pdf/2605.21347v3)

| 来源 | 正确性 | 深度 | 证据 | 可执行性 | 综合 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Claude Code 多 agent | 4.278 | 4.139 | 4.285 | 4.174 | 4.219 |
| IG | 4.136 | 4.311 | 4.341 | 4.220 | 4.252 |

IG 在深度和证据上的均值略高，正确性均值略低，总差异没有统计显著性。人工修改效果与人工评分结果测量的对象不同，不能用前者把后者写成显著领先。正文此处写报告来自 100 个训练样本，附录 A.11.1 则说提供 250 条训练轨迹；未公开材料不足以判断是报告生成子集与评审材料不同，还是版本遗留差异。

## 自动改写循环：报告有帮助，IG 未独占最高结果

自动实验把框架记作 $A_r$：先运行得到轨迹 $T_r$，分析系统生成报告 $R_r$，再由 Claude Code/Opus 4.6 读取报告与源码，修改成 $A_{r+1}$。下一轮重新收集轨迹，因此这里的报告材料随代码变化。验证集连续两轮没有至少 0.01 的改进，或者到第 5 轮，就停止；测试集只用于报告表现。[附录 A.10、A.12](https://arxiv.org/pdf/2605.21347v3)

| 条件 | 初始 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 第 4 轮 | 第 5 轮 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

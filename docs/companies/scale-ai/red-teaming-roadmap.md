# 红队测试路线图：从模型拒绝扩展到产品与系统安全

同一个模型，放在小说创作助手、儿童教学应用和能够发送邮件的办公 agent 中，需要遵守的行为边界不同。只检查它是否拒绝一组有害问题，无法覆盖工具权限、用户身份、长期交互和部署环境带来的风险。这篇论文建议先依据产品的安全规范定义测试目标，再用符合实际条件的威胁模型开展红队测试，最后把监测、干预和修补机制一起纳入评估。

这是作者提出的研究路线图，没有发布新的实验数据集、训练算法或模型排行榜。文章的主要内容是研究对象的划分、四类产品的威胁分析，以及系统层面的研究建议。下文将这些主张与论文引用的已有研究分开说明。[论文，§1–7](https://arxiv.org/pdf/2506.05376v2)

## 模型、产品和系统的三个范围

论文首先区分三个常被混用的对象：

| 层次 | 本文定义 | 对应测试内容 |
| --- | --- | --- |
| 模型 | 经过训练、产生特定行为的神经网络 | 输入是否引出违反预期的模型输出 |
| 产品 | 通过 API 或界面实现具体用途的应用，可包含模型、工具和数据 | 检索、界面、工具和模型协作后是否违反产品规范 |
| 系统 | 产品所处的部署环境，包括监测服务、工程人员、用户和外部环境 | 风险能否被发现、阻断和修补，环境与用户行为如何影响结果 |

模型和产品有时几乎重合，例如直接通过 API 使用生成模型；工具丰富的办公 agent 则不能这样处理。系统范围进一步包含产品之外的运行条件。论文图 1 用嵌套关系表示这些对象，同时说明产品规范会参考模型规范，也受到使用者、环境、其他要求和法规等因素影响。这不是三套互不相关的安全任务。[论文，§1、图 1，PDF 第 2 页](https://arxiv.org/pdf/2506.05376v2)

例如，保存密码的浏览器动作在个人设备和公共设备上具有不同后果。动作文本本身没有变化，但环境状态改变了其安全含义。又如，一个模型生成并在本地保存某张敏感图片，另一个工具能够发送邮件；分别看两个功能，并不能推断把图片发送给特定接收人的组合行为是否符合产品要求。这是论文用于说明环境和动作组合重要性的例子。

## 产品规范让测试目标可以核对

作者认为，不同产品不能简单共用一个脱离情境的“有害内容”定义。面向小说家的写作应用与面向儿童的辅导应用，可能对同一类话题设置不同边界。风险还受到使用者、工具、应用目的和部署条件影响。

因此，红队测试应先指出目标产品的行为规范，再定义可观测的违规目标。规范应能回答：允许哪些用途，哪些行为被禁止，以及什么证据足以说明一次测试违反了要求。这里的“成功”通常不只是是否出现拒绝关键词，还可能涉及产物内容、工具行为、质量和后果。论文提到从正则匹配向 rubric 评分发展的方向，但没有为所有产品提出统一评分表。[论文，§2](https://arxiv.org/pdf/2506.05376v2)

用于解释这一过程的说明示例是：某办公助手只允许把文档发送给具有访问权限的人。测试目标可以具体到“是否把指定文档发给无权限的模拟收件人”，证据包括权限设置、文档标识、收件人和提交日志。这样的目标比“测量办公助手是否有害”更容易复查。这个例子是对论文思路的应用说明，不是作者新增的数据集条目或实验结果。

当研究者拿不到明确的产品规范时，作者建议说明所假设的政策情境，可以依据开发者公开目标或常见产品实践构造，但不能把推定的规范冒充产品实际承诺。同时，红队仍应寻找规范遗漏的风险，而不是只在已有条目内检查合规。产品规范提供测试起点，并不保证它已经覆盖全部应关注的行为。

## 威胁模型需要包含实际权限与资源

威胁模型规定攻击者能够控制什么、知道什么、想达到什么目标，以及能投入多少资源。传统视觉对抗研究常用扰动约束：

$$
\lVert\delta\rVert_p\leq\epsilon.
$$

其中 $\delta$ 是输入图像的扰动，$p$ 指定范数，$\epsilon>0$ 限制扰动大小。论文用它说明清晰的攻击约束如何使实验可比较，并指出现实攻击者未必受到这种约束。这是对既有研究的背景说明，不是本文为 LLM 提出的新优化目标。[论文，§3，PDF 第 4–5 页](https://arxiv.org/pdf/2506.05376v2)

对 LLM 产品，输入不限于直接用户消息，还包括网页、文档、音频、工具输出和其他 agent。攻击者可能是产品用户，也可能只控制 agent 能访问的外部材料。作者要求研究说明攻击动机、目标行为、查询次数、算力、模型知识、权重访问和是否能反复测试。

其中两项主张与实验设置直接相关。对于黑盒 API，作者主张考虑有限查询，以及部署方可能封禁用户或修补模型的条件。对于完整权重访问，作者认为通常还应考虑攻击者能够做少量微调，而不只是运行推理和计算梯度。这不意味着所有白盒研究都失去意义：作者明确保留了开发者在上线黑盒服务前，使用白盒测试提高稳健性的情境。

这些是作者对研究优先级和真实性的判断，不是本文测得的统一查询上限或微调预算。

## 四类产品需要不同的测试设计

### 聊天助手：把历史交互作为攻击空间

单轮测试把一次用户消息作为主要输入，多轮测试则允许后续请求依赖先前回复。用户可以逐步改变上下文，产品还可能加入长期记忆。作者因此建议提高多轮测试优先级，理由包括单轮防护可能无法迁移到多轮交互，以及输入输出过滤较容易处理部分单轮问题。

论文引用的多轮人工红队研究，是这一建议的证据之一。该研究本身比较了不同防御在多轮人工攻击下的表现；它没有证明所有聊天产品在所有条件下都更容易受到多轮攻击。路线图也没有重新运行这些实验。[论文，§3.1](https://arxiv.org/pdf/2506.05376v2)、[所引多轮人工红队研究](https://arxiv.org/abs/2408.15221)

### 音频助手：输入不等于转写后的文字

音频中有语调、口音、讽刺、夸张表达和音质等特征，实际对话还可能包含多语言切换、背景噪声、打断和多人交谈。单纯把文本红队题目转成合成语音，会覆盖其中一部分内容，但未必覆盖这些音频特有的交互条件。

作者建议直接考虑音频产品的使用情境。这里没有提出固定的噪声强度、口音分布或语音采样协议，也没有报告新增的音频攻击成功率。不能把这些待研究维度写成已经完成的 benchmark。[论文，§3.2](https://arxiv.org/pdf/2506.05376v2)

### 视频生成：风险可能随时间出现

视频的初始提示和前几帧可以看起来无害，后续画面却进入受限内容；风险也可能取决于多个画面的组合或同步音频。与单张图像相比，输出检查要处理时间变化及跨模态关系，计算成本也可能更高。

作者还讨论视觉演示可能提高某些不当信息的可操作性，以及文字中允许的历史描述在具象呈现后可能需要不同政策。这些论点解释了为什么不能照搬文本规则；论文没有用用户实验量化这种能力增益，也没有给出视频与文本危害的统一比值。有关视频模型逼真程度和生成成本的叙述对应 2025 年写作时点，不是对当前产品能力的评估。[论文，§3.3](https://arxiv.org/pdf/2506.05376v2)

### 自主 agent：输入、输出与依赖软件都在变化

作者列出四组扩展因素：

- 输入渠道增加，风险可能来自文本、图像、音频、代码、工具输出或物理传感器。
- 输出由单段文字扩展为交互动作，多个单独看来正常的动作可以组合成不当结果。
- MCP 服务等额外软件组件也可能存在漏洞，风险不能全部归入模型本体。
- 多 agent 之间可能发生协调失败、冲突或主动操纵，单个模型的表现不足以刻画整体行为。

原文在引出这一部分时写“three-fold”，随后实际列出四项；本文按四项内容整理。作者主张投入环境与沙箱建设，因为模拟网站、虚拟机、网络、其他模型和媒体资源具有较高工程成本。它没有提供一个通用沙箱实现，也没有证明某个现有环境足以代表完整互联网。[论文，§3.4](https://arxiv.org/pdf/2506.05376v2)

## 红队活动的五项设计建议

论文 §4 提出的方法建议可以按测试流程理解。

**先分别检查各层防护，再检查它们的组合。** 模型内部拒绝策略与外部分类器可能互补，也可能在同一批输入上同时失败。强组件还可能掩盖弱组件的问题。单独评估帮助定位缺陷，端到端评估检查实际部署效果；本文没有测量两层防护组合后的增益。

**尽量模拟目标用户和运行环境。** 办公产品的测试可以同时包含正常用户和具有恶意目标的登录用户，使用相应界面、API 或工作区。对外连接产品需要能够支持测试的沙箱；若沙箱明显简化环境，应报告这种差距。

**采用多种攻击来源。** 作者建议结合算法、人类红队和 LLM 红队，并考虑面向特定模型类型的方法。使用 LLM 可以降低部分人员组织成本，但论文没有给出预算对齐实验，也没有证明其总成本或发现能力始终优于人类团队。

**检查规范本身的空白。** 一份不完整或自相矛盾的规范，可能让产品在近似情境下表现不一致。红队要把这类规范问题反馈给开发者，也要考虑起草时尚未出现的风险。

**说明测试与现实的差距。** 作者称这一差距为 delta，讨论了红队人员与真实攻击者在技能、资源、动机上的差别，实验环境与现实环境的差别，以及模型可能识别出测试情境的影响。对危险目标使用代理任务时，这种差距尤其需要记录。论文没有定义可直接计算的 delta 指标，不能把它转换成一个未经验证的安全折扣系数。[论文，§4，PDF 第 7–8 页](https://arxiv.org/pdf/2506.05376v2)

## 成功率同时受到测试活动的影响

论文举了一个计数例子：红队找到一个成功案例后停止，可以报告 100% 失败率；如果再加入 99 次失败尝试，则变成 1%。模型暴露的那一个漏洞没有因此消失，变化的是活动采样及分母。

把例子写成算式：

$$
\frac{1}{1}\times100\%=100\%,\qquad
\frac{1}{100}\times100\%=1\%.
$$

这是论文用来说明指标解释的假设案例，不是实际实验结果。它也不表示成功率没有意义，而是说明比较前要交代测试单位、攻击选择、预算和停止规则。发现多少种独立漏洞、涉及什么后果，与一次测试活动中的通过比例是不同信息。[论文，§4，PDF 第 8 页](https://arxiv.org/pdf/2506.05376v2)

论文同时提醒，单个严重案例与许多轻微政策偏离不能只靠次数等价比较。本文没有提出严重程度加权公式，也没有提供跨产品汇总分数。因此读者不能从路线图推导一个统一的“系统安全总分”。

## 从单次拒绝扩展到监测与响应

### 环境建模提供行为的上下文

系统需要理解操作所处的状态，包括用户、设备、数字或物理环境，以及其他 agent。保存密码的例子说明，仅识别“保存”这个动作无法确定后果。环境也可能向模型带入攻击性信息，所以既是判定上下文，也是需要测试的输入来源。[论文，§5](https://arxiv.org/pdf/2506.05376v2)

### 轨迹监测与用户监测处理不同单位

轨迹监测检查一段交互中的完整动作和消息历史，关注风险如何累积。用户监测观察同一使用者的行为模式，例如重复提出不当要求，或事后审查发现持续诱导有害操作。图 2 将两条监测路径分别画在用户请求和 agent 动作周围，再把监测系统本身作为红队对象。

作者认为，若少数用户贡献大量有害请求，检测和限制这些用户可能减少总体危害；异步人工审查、较重的自动分析或两者结合可以参与。这个主张带有明确前提：风险在多次请求中累积，并且干预发生得足够早。论文没有给出恶意用户占比、检测阈值、误封率、身份核验协议或隐私成本的实证数据。[论文，§5、图 2，PDF 第 9 页](https://arxiv.org/pdf/2506.05376v2)

### 快速响应不要求系统永远保持不变

部署方可以在发现漏洞后增加防护或更新模型。作者据此建议研究异步监测与轻量防护适配，让系统在漏洞被大规模利用前完成修补。引用的 Rapid Response 工作研究了观察少量攻击案例后的防护适配，为这个方向提供已有例子；该工作的算法和成绩并非路线图的新实验。[论文，§5](https://arxiv.org/pdf/2506.05376v2)、[所引 Rapid Response 研究](https://arxiv.org/abs/2411.07494)

这种事后处理不能自动覆盖单次输出就可能造成严重后果的场景。原文明确把监测和快速响应的许多收益放在危害跨请求分散、或一次回复并非灾难性后果的条件下。文章没有证明“先允许失败、随后封禁”对全部风险都成立。

### 监测器也要接受独立测试

监测器的存在不等于它有效。作者提出让红队尝试完成不当目标，同时避开监测，以检查监测边界。关于逐步思维链监测和 sabotage evaluation 的文献提供了相关研究背景，但本文没有训练新监测器，也没有报告检测率或逃逸成功率。

蓝队负责改进监测精确率、召回率和干预措施；红队负责主动寻找它们的失效方式。这一区分对应研究分工，不意味着红队结果可以代替完整的检测器质量评估。[论文，§5，PDF 第 10 页](https://arxiv.org/pdf/2506.05376v2)、[所引思维链监测研究](https://arxiv.org/abs/2503.11926)、[所引 Sabotage Evaluations](https://arxiv.org/abs/2410.21514)

## 作者保留的另一种研究立场

§6 讨论以固定社会危害框架开展研究的理由。若某个开发者本来就允许较高风险的行为，仅衡量产品是否遵守自己的规范，并不能回答其对社会的影响。研究者仍可明确采用一套规范性标准，考察模型直接或经操纵后如何违反这些标准。

作者同时指出，这种研究需要面对价值定义、情境差异和共识不足。开放权重模型还可能被再次微调，开发者原有防护不一定在后续使用中保留。因而本文的优先级建议不能读成“产品自定规范已足够”或“抽象危害研究没有价值”。这段替代观点是论证边界的一部分。[论文，§6](https://arxiv.org/pdf/2506.05376v2)

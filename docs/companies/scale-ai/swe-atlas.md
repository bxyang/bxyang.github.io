# SWE Atlas：代码理解、测试编写与重构

软件工程任务并不总是从一个待修复的错误开始。工程师还会调查系统在负载下的行为，为已有功能补充测试，或者把散落的实现迁移到共同模块。SWE Atlas 将这三类工作整理成 284 个仓库级任务，结合运行检查和逐项评审来评分。论文中最好的模型与工具框架组合取得 43.49% 的整体 Pass@1；同一任务运行三次、三次全部成功的比例为 29.2%。这两个数字分别描述单次完成能力和重复执行的一致性，不能互相替代。[论文 §2–3、表 1](https://arxiv.org/pdf/2605.08366v1)

## 从一个测试案例理解评测对象

论文举了一个邮件处理函数的测试案例。任务要求验证 `handle_mail_rule` 的实际副作用。某个 agent 生成了测试，并检查返回值、调用次数和剩余邮件数；但把被测函数替换成直接返回 `0` 的空实现后，这些测试依然通过。原测试中的断言与该空实现相容，没有证明邮件处理真的发生。

参考测试则观察标为已读、调用处理函数、删除邮件或移动邮件等操作。两个版本的测试都可以被成功执行，差别在于空实现能否被它们发现。这解释了 SWE Atlas 的测试编写任务为何同时检查运行结果和测试覆盖的具体行为。[论文 §4.3 案例](https://arxiv.org/pdf/2605.08366v1)

相邻的两类任务采用不同输出形式。代码理解任务提交一份有运行证据的解释；重构任务提交代码修改，既要保留相关行为，又要完成指定的接口迁移、调用点更新和旧实现清理。SWE Atlas 没有把这些任务统一改造成“生成补丁后运行一组测试”，而是分别设置评分条件。

它与 SWE-bench 一类问题修复基准的关系是补充性的：后者主要从 issue 出发检查修复，SWE Atlas 则覆盖理解、验证与维护代码的工作。它也保留了部分需求不明确性，要求 agent 自行定位相关模块和运行路径。所有任务都是**单次用户请求**，没有后续用户澄清或人工审查反馈回合。[论文 §1–2](https://arxiv.org/pdf/2605.08366v1)

## 三种任务分别怎样评分

rubric 是独立、尽可能自足的二元检查。正向标准描述应出现的证据或行为；负向标准描述不应出现的问题。为了说明它们如何组合，记 judge 对第 $j$ 项给出的 YES 为 $a_j=1$、NO 为 $a_j=0$，转换后的通过值为：

$$
s_j=\begin{cases}
a_j,&\text{正向标准},\\
1-a_j,&\text{负向标准}.
\end{cases}
$$

设 $M$ 是必需标准集合，完整、可解析评分下的 rubric 门槛为 $R=\prod_{j\in M}s_j$。只要一项未满足，$R=0$。这一写法是对论文协议的形式化说明；当前代码遇到无法解析的 judge 输出时有额外分支，后文单独说明。[论文 §2.1](https://arxiv.org/pdf/2605.08366v1)

### 代码理解：回答要覆盖问题及其证据要求

Q&A 包括正向的回答完整性标准和负向标准，全部都是必需项，任务通过值就是 $R$。一个回答即使正确解释了大部分代码，也可能因为遗漏指定的运行场景而整题不通过。细项平均分可以显示完成到哪一步，但不是主表的任务成功率。

论文的 SimpleLogin 案例要求解释回复邮件偶尔路由到错误用户的原因，并提供三类证据：展示 `reply_email` 缺少唯一约束及查询返回第一条匹配记录的行为；追踪多次回复事件如何解析到不同联系人；构造没有匹配联系人的事件并观察退信路径。

GPT-5.4 启动 PostgreSQL，放入共享 `reply_email` 的联系人，追踪了四次回复，包含删除联系人后的跨用户路由变化；它仍因没有构造无匹配事件而遗漏必需项。Sonnet 4.6 找到静态原因，但只运行单次事件；Gemini 3.1 Pro 停留在静态代码阅读。该案例展示的是**每个请求中的子问题是否落实**，并非只比较回答长度。[论文图 3 附带案例](https://arxiv.org/pdf/2605.08366v1)

当前 Q&A 评分器读取 `/logs/agent/answer.txt`，去除可选的最终答案标签，对每个 criterion 分别调用 judge。它评分的是提交的回答，而非独立重放回答中提到的全部运行实验。因此，“要求运行证据”与“验证器亲自执行每个声称的实验”也需要区分。[Q&A 评分代码](https://github.com/scaleapi/SWE-Atlas/blob/49e4af3b6c803dd54a1cd60ead703aac25de4e21/data/qa/task-6905333b74f22949d97ba9b5/tests/evaluate_answer.py)

### 测试编写：清单、变异与覆盖三道检查

TW 要求 agent 新增测试，并提交 manifest，列明自己添加的测试。评分包含三个部分：

1. **清单检查**：judge 核对清单是否准确描述新增测试。
2. **变异检查**：先在正常代码上运行测试，再把相关实现替换为 no-op 空实现后运行。有效测试应能区分这两个版本。
3. **rubric 检查**：覆盖完整性是必需项；测试放置、全仓库惯例和局部模块惯例只用于进一步分析。

记三部分为 $F$、$U$、$R$，最终通过值是 $y_{\mathrm{TW}}=FUR$。这不是把三项分数求平均：清单正确、代码可运行，均不足以补偿漏测关键行为。[论文 §2.1.2](https://arxiv.org/pdf/2605.08366v1)

当前代码的变异规则比“测试在正常代码上通过、坏代码上失败”这句话更具体。令 $T$ 为清单匹配到的测试，$B^+$ 为其中在正常代码上状态为 `PASSED` 的测试。实现采用：

$$
U=\mathbf 1[|B^+|>0]\prod_{t\in B^+}\mathbf 1[\mathrm{status}_{\mathrm{mutant}}(t)\in\{\mathrm{FAILED},\mathrm{ERROR}\}].
$$

也就是至少存在一个基线通过的相关测试，并且**这些基线通过的测试全部**在变异后失败或报错。它不是“任意一个测试杀死变异就足够”；但基线已经失败的其他清单测试也不会进入 $B^+$。变异后测试缺失或被跳过，不按成功发现错误计算。

例如，清单中 A、B 两项在基线上分别通过和失败，变异后 A 失败，当前函数仍可让变异检查通过，因为实际参与条件的是集合 $\{A\}$。本文用隔离函数及模拟 I/O 验证了这个分支，没有执行模型或真实仓库测试。这是固定实现的边界，不是论文主表中已确认发生的故障。[TW 评分代码](https://github.com/scaleapi/SWE-Atlas/blob/49e4af3b6c803dd54a1cd60ead703aac25de4e21/data/tw/task-6902ef3ab97fe23e2ad2722c/tests/evaluate_tests.py)

这种变异也不等于对许多不同缺陷计算传统 mutation score：每题使用预先制作的相关代码空实现。它验证测试能否发现这种破坏，不能自动覆盖所有可能的真实回归。

### 重构：行为保持与结构要求同时成立

RF 要求 agent 找到受影响代码、建立目标模块边界、迁移调用方并删除旧定义。论文报告 64% 的任务给出了明确接口规范，因此“保持可观察行为”仍需结合题目要求理解；指定接口及迁移方式不是 agent 可以随意忽略的建议。

程序验证比较基础代码与应用 agent 修改、预写测试补丁后的结果，检查相关测试是否从通过变为失败，以及新增隐藏测试是否失败。rubric 则检查可维护性、旧产物清理和负向问题；文档可维护性不计入最终门槛。记行为检查为 $B$，则 $y_{\mathrm{RF}}=BR$。[论文 §2.1.3](https://arxiv.org/pdf/2605.08366v1)

例如，论文讨论把 `SetMain`、`RunMain` 等旧路径迁移到 `RunSourceData` 的任务。只增加新入口仍不够：旧接口是否删除、对象是否重复实例化、共享状态是否仍按要求使用，都可能影响判定。案例中一个实现清理了旧路径并缓存实例，另一个保留旧方法且重新创建对象，后者三次均未通过。这是具体迁移约束的结果，不能只根据新函数存在与否评分。[论文 §4.4 案例](https://arxiv.org/pdf/2605.08366v1)

在核查的当前 RF `test.sh` 中，验证器记录 agent 是否修改受保护测试，并在用于运行验证的补丁中排除这些修改；最终奖励没有再把这个标志作为独立否决项。因此，“检测到测试被改动”不等于“立刻整题判零”。行为分支还明确关注相关测试中的 `pass_to_fail` 与 `missing_to_fail`，没有把所有可能状态变化都列为失败条件。复现时应读实际验证器，不能把论文的行为保持概述扩写为“所有测试必须全部通过”。[代表性 RF 验证脚本](https://github.com/scaleapi/SWE-Atlas/blob/49e4af3b6c803dd54a1cd60ead703aac25de4e21/data/rf/task-69d196f015a150488265afb5/tests/test.sh)

## 模型、运行预算与三种成功率

论文使用 Harbor 管理各任务环境。原生框架组包括 Codex CLI、Claude Code 和 Gemini CLI；共同框架组使用 mini-SWE-agent，只提供 Bash 工具。前一组比较模型与产品框架的完整组合，后一组减少框架差异，但仍不是训练、推理预算完全相同的裸模型实验。[论文 §3](https://arxiv.org/pdf/2605.08366v1)

附录 J 披露每个容器使用 16 CPU、16 GB 内存，Modal 沙箱时限 6 小时。每个配置重复三次。开放权重模型经 Fireworks AI API 推理；rubric judge 固定为 `anthropic/claude-opus-4-5-20251101`。

思考设置中，GPT-5.4、GPT-5.3 Codex 和 Opus 4.7 使用 xHigh；Opus 4.6、Sonnet 4.6、Gemini 3.1 Pro 使用 High；MiniMax、Kimi、GLM 使用默认 High。表 8 将 Flash 写作“Gemini 3.1 Flash”，主表却写“Gemini 3 Flash”，原文没有在这里统一该名称。不能仅凭表 8 的一行推断它们已经固定到同一 API 快照。论文也未完整列出所有原生 CLI 的版本、温度及逐配置统一 token 上限。[论文附录 J、表 8](https://arxiv.org/pdf/2605.08366v1)

设共有 $N$ 个任务，第 $i$ 题第 $r$ 次运行的二元结果为 $y_{ir}$。在每题恰好三次、无缺失且任务等权的情况下：

$$
\mathrm{Pass@1}=\frac{1}{3N}\sum_{i=1}^{N}\sum_{r=1}^{3}y_{ir},
$$

$$
\mathrm{Pass@3}=\frac{1}{N}\sum_{i=1}^{N}\mathbf1\!\left[\sum_{r=1}^{3}y_{ir}\ge1\right],\qquad
\mathrm{Pass}^{3}=\frac{1}{N}\sum_{i=1}^{N}\prod_{r=1}^{3}y_{ir}.
$$

一题结果为“成功、失败、成功”，对三个指标的贡献分别是 $2/3$、1、0。Pass@3 表示三次中至少一次完成；Pass³ 表示三次全部完成。Pass³ 不能用整个数据集 Pass@1 的立方替代，因为不同任务难度不同，也不能假定所有运行共享同一个成功概率。[论文表 1、附录 E](https://arxiv.org/pdf/2605.08366v1)

论文的 95% 区间使用 trial 层面的 Wilson 区间。给定成功率 $\hat p$、试验数 $n$、$z=1.96$，标准形式为：

$$
\frac{\hat p+z^2/(2n)\ \pm\ z\sqrt{\hat p(1-\hat p)/n+z^2/(4n^2)}}{1+z^2/n}.
$$

完整运行名义上有 $n=284\times3=852$ 个 trial。这个区间没有按任务或仓库进行聚类重采样，不能据它推断跨新仓库的泛化不确定性，也不能直接把两个高度重叠区间解释成某个模型已经显著领先。

GPT-5.4 原生组从单次 43.49% 降到三次全成功 29.2%，相差 14.29 个百分点。这个差值描述重复运行的一致性，不表示额外失败的 14.29% 全是某一种已定位的随机故障。

### 整体得分存在无法由子表直接重建的地方

表 1 的整体列与工作流列不能全部按公开任务数复算。例如，以 GPT-5.4 的三个工作流分数做任务数加权：

$$
\frac{124\times40.80+90\times44.36+70\times44.29}{284}=42.788\%,
$$

而工作流等权平均为 43.15%，两者都不是表中 43.49%。这超出了小数保留两位的舍入误差。论文没有在主表附近提供足以重建这一差异的逐运行有效分母、缺失处理或额外聚合步骤。

因此，上表保留的是**论文报告结果**；前面的指标公式说明完整平衡运行时的标准计算，不声称已经从公开 trial 记录重现 43.49%。当前任务与评分代码可用于新实验，也不能代替该版结果的逐项原始明细。

## 失败分析：执行正确与任务完整是两种检查

### 功能检查通过后，仍可能漏掉必需项

图 2 分别绘制程序检查通过率和必需 rubric 集合通过率。RF 的测试检查约在 60%–80%，rubric 集合通过率明显更低；TW 的变异检查也通常高于完整 rubric 检查。两坐标轴是各自检查的通过率，不是最终总成功率，更不是某一个 criterion 的平均分。[论文图 2](https://arxiv.org/pdf/2605.08366v1)

细分类别解释了差距来源。在 TW 中，Opus 4.7 的测试完整性通过率为 62%，全仓库测试惯例为 82%，局部模块惯例为 69%；GLM-5 对应为 46%、85%、61%。遵循测试框架惯例与补齐题目要求的行为并不等价。

RF 中，Opus 4.7 的代码可维护性、清理旧产物、负向标准类别分别为 70%、75%、94%；MiniMax M2.5 为 41%、53%、90%。较高的反模式检查通过率，也不能代替任务要求的结构变更。文档类别虽然被画出，但不属于该实验最终成功的必需门槛。[论文图 2c–d](https://arxiv.org/pdf/2605.08366v1)

### 代码执行、测试数量与成功率是观察关系

图 3a 在共同 mini-SWE-agent 框架下比较平均代码执行次数、答案长度和 QA 成绩，较强模型通常有更多运行探索。图 3b 则分析原生框架下的失败 rubric：GPT-5.4 中 44% 属于信息缺失或不完整，21% 缺少运行证据；Opus 4.6 对应为 34% 和 46%。这些百分比的分母是被分类的**失败 rubric**，不是所有任务，也不是所有模型输出。[论文图 3](https://arxiv.org/pdf/2605.08366v1)

该分类使用 Opus 4.6。它提供了模型辅助的错误归类，但没有公开逐类人工混淆矩阵。图 3 的总标题提到 mini-SWE-agent，b 子图说明则明确写原生框架，阅读时需要按子图区分。

TW 图 4 中多数模型能通过清单检查，差异更多出现在变异与完整性上。Opus 4.7 的清单、变异和 rubric 检查分别约为 99%、70%、62%。图中还将平均新增测试数量与成绩、变异失败率对照；新增更多测试并未对应更高完成率。

这些是已生成轨迹的关联分析，论文没有随机强制某模型多执行几次代码，也没有保持其余条件完全不变而只增加测试条数。因此不能把它写成“增加执行次数必然提高成绩”或“减少测试条数导致更强能力”的消融结论。[论文图 4](https://arxiv.org/pdf/2605.08366v1)

### 重构范围与文件覆盖

RF 参考补丁的修改规模从 35 到 2,073 行。图 5 按修改行数分桶，各桶为 12、12、12、11、11、12 个任务。大范围任务整体更难，但最大一桶并非严格延续下降趋势；作者指出其中包含较机械的批量改名任务。因此，“修改越多就一定越难”不能当作图的结论。

图 5b 的 file-edit recall 也有特殊定义：它统计**触及参考补丁全部修改文件的 trial 比例**，不是每次运行中修改文件覆盖率的平均值。这个量与任务成功率相关，但参考补丁涉及的文件并不自动构成所有可能正确方案的唯一文件集合。[论文图 5](https://arxiv.org/pdf/2605.08366v1)

### 原生框架的探索与委派

表 2 比较 QA 任务中的子 agent 使用。Opus 4.6 / Claude Code 每个 trial 平均委派 2.64 次，96.5% 的 trial 至少有一次委派；Sonnet 4.6 对应 1.21 次与 98.9%。Gemini 3.1 Pro 为 0.01 次与 1.1%；Flash 为四舍五入后的 0.00 次与 0.3%，后者不表示完全没有委派。论文称实验时 Codex 框架没有相应委派能力，这不是对其后版本的描述。[论文表 2](https://arxiv.org/pdf/2605.08366v1)

附录 C 比较原生与 mini 框架的工具轨迹。例如图 7 中 Opus 4.6 的总工具调用约为 100 对 56，GPT-5.4 为 82 对 58，约为 1.8 倍和 1.4 倍。工具统计不等于模型内部推理步数，轨迹阶段分析还会将复合 Shell 命令拆成原子命令。没有“关闭委派、其他保持不变”的控制实验，所以框架总差异不能全部归到委派上。

## judge 的一致性与人工对照

SWE Atlas 依赖模型对 rubric 作判断，作者分别测试不同 judge 的一致性、同一 judge 重复评分的稳定性，以及与人工的对照。这三个实验回答不同问题。

表 4 基于 1,306 个 rubric 级判断，比较三种 judge：

| judge 配对 | Cohen’s $\kappa$ | Macro-F1 |
| --- | ---: | ---: |
| Gemini 3.1 Pro High / Opus 4.6 High | 0.746 | 0.873 |
| Gemini 3.1 Pro High / GPT-5.4 xHigh | 0.837 | 0.918 |
| Opus 4.6 High / GPT-5.4 xHigh | 0.739 | 0.870 |

$\kappa=(p_o-p_e)/(1-p_e)$，其中 $p_o$ 是观察到的一致率，$p_e$ 是由边际标签比例得到的偶然一致率。它不是准确率；两个 judge 一致也可能共同判断错误。Macro-F1 将不同类别的 F1 等权平均，同样不能代替整题评分正确率。[论文附录 H、表 4](https://arxiv.org/pdf/2605.08366v1)

重复评分实验取 30 份 QA 回答，用 Opus 4.5 独立评五次。原文称涉及 510 项 rubric evaluation，其中 99.2% 的项目重复判断完全一致，平均配对 $\kappa=0.983$、Macro-F1 为 0.992。原文没有进一步明确 510 在重复展开前后的计数细节，不能在此另行推算为确定的 API 调用次数。这个结果针对该批回答和 judge，不等于全部工作流、全部标准都有同样的稳定性。

人工对照实验在三类工作流中合计收集 200 个 rubric 评分，评估对象来自 Opus 4.5 和 GPT-5 的回答：

| judge | 与人工的 $\kappa$ | Macro-F1 |
| --- | ---: | ---: |
| Gemini 3 Pro | 0.78 | 0.89 |
| GPT-5 | 0.84 | 0.92 |
| Opus 4.5 | **0.88** | **0.94** |

作者据此选用 Opus 4.5 作为正式 judge。200 的单位是 rubric 评分，不是每个工作流 200 道任务。论文未提供按工作流拆开的完整混淆矩阵、人工评审人数及整题误判率，因此不能把 0.88 写成“88% 的任务评对了”。[论文表 5](https://arxiv.org/pdf/2605.08366v1)

## 污染检查的具体对象与边界

SWE Atlas 的问题描述和 rubric 是新写的，但 RF 参考补丁来自真实已合并 PR，相应代码可能已经存在于公开历史中。移除任务容器中的 Git 历史只能限制该条直接查找路径，不能删除模型已经学到的内容。[论文附录 I](https://arxiv.org/pdf/2605.08366v1)

作者对**已经通过的** RF、TW trial 比较 agent 补丁与参考补丁。第一项是去除空白后新增行集合的 Jaccard 相似度。若两集合为 $A$、$G$：

$$
J(A,G)=\frac{|A\cap G|}{|A\cup G|}.
$$

第二项是对补丁文本计算 `difflib` 序列相似度，其比率可写为 $2M/(|x|+|g|)$，$M$ 为算法匹配到的元素数量。前者比较行集合，后者保留文本序列信息，并不是同一指标的两种显示方式。

| 工作流与模型 | Jaccard | Diff 序列相似度 |
| --- | ---: | ---: |
| RF：Opus 4.6 / Claude Code | 0.51 | 0.68 |
| RF：GPT-5.4 / Codex | 0.35 | 0.61 |
| TW：Opus 4.7 / Claude Code | 0.11 | 0.18 |
| TW：Opus 4.7 / mini-SWE-agent | 0.10 | 0.16 |
| TW：GPT-5.4 / Codex | 0.08 | 0.16 |
| TW：GPT-5.4 / mini-SWE-agent | 0.08 | 0.14 |

[论文表 6–7](https://arxiv.org/pdf/2605.08366v1)

Jaccard 的分母是并集，0.51 不能解释为“agent 的 51% 新增行来自参考答案”。论文文字有这种近似叙述，但它并不符合该指标的严格分母。整体均值未接近 1 与逐字复制不相符，却不能排除部分记忆、改写后的记忆或失败 trial 中的查询行为。

论文时期的环境可以联网。作者报告 210 次运行中发现 4 次在线查找参考实现的尝试，涉及 GPT-5.4 和 GPT-5.3 Codex，四次都失败；原文没有充分展开这 210 次如何在模型间分配。这个检查不能表述为“全部模型的全部 852 次运行都没有泄漏”。当前代码已经收紧 TW/RF 网络权限，属于另一个环境版本。

## 公开实现与复现时需要固定的部分

官方仓库同时提供 `data/qa`、`data/tw`、`data/rf` 的任务、参考材料、judge 提示与验证器，以及 `run_config/` 的运行示例。代码采用 Apache-2.0 许可；被测上游仓库仍各有自己的许可证。当前 README 指定 Harbor `v0.18.0`，使用 Modal 沙箱，分别配置被测模型与 OpenAI 兼容 judge 端点。[固定版本 README](https://github.com/scaleapi/SWE-Atlas/blob/49e4af3b6c803dd54a1cd60ead703aac25de4e21/README.md)

典型流程是先固定仓库与 Harbor 版本，准备 API 端点和 Modal 账户，检查任务镜像可用性，再选择某工作流的脚本。示例命令 `bash run_config/tw/opus-4p6_claude-code.sh` 使用三次重复，并发数为 24。这里的 24 是并发配置，不是每题运行次数。应先验证任务环境与 oracle，再执行新的模型评测，最后保存任务版本、原始 judge 输出、每题三次结果和错误日志。

### 论文发布后修改了数据和环境

当前固定 commit 的日期是 2026 年 8 月 20 日，不能视为 5 月实验原样存档。官方历史中能确认的修订包括：

- 7 月修正部分 TW 参考测试清单、QA 参考答案，以及一题 Q&A rubric 的方向。这类修订可能改变评分材料，不能只当作文档更新。
- TW 与 RF 增加网络域名 allowlist，并在 Claude Code 配置中禁用 `WebSearch`、`WebFetch`。允许访问包仓库和工具链所需域名，并不等于完全断网。
- 8 月修改部分 RF oracle 和容器启动设置；新增 Opus 4.8 xHigh 的 RF 运行配置。这不是论文已经评测过 Opus 4.8 的证据。
- Opus 4.8 的新增脚本设置了三倍 agent timeout，不能把这个参数推广为所有配置均如此。

[官方提交历史](https://github.com/scaleapi/SWE-Atlas/commits/49e4af3b6c803dd54a1cd60ead703aac25de4e21/)

对全部 `task.toml` 的静态扫描显示，当前 TW 的 90 题和 RF 的 70 题均声明 agent 阶段 allowlist；QA 的 124 题没有相同声明。README 顶部正确写 TW/RF，后面一段却写 QnA/TW，与实际配置不一致。复现应以固定版本 task 配置及运行参数为准，同时区分建环境时的网络权限和 agent 运行时的权限。

当前 task 文件的 agent timeout 为 10,800 秒，即三小时；论文附录 J 描述的六小时是沙箱限制，两者不是同一计时层级。某一模型实际能运行多久，还需结合 Harbor 与脚本倍率，不能把论文的六小时直接当成当前所有 agent 的统一预算。[当前运行配置](https://github.com/scaleapi/SWE-Atlas/tree/49e4af3b6c803dd54a1cd60ead703aac25de4e21/run_config)

### judge 输出解析也是评分协议的一部分

静态核查全部评分器后，124 个 Q&A evaluator 相同，70 个 RF rubric evaluator 相同。TW 的 89 个评分器相同，另一个版本仅额外处理测试名路径中的空格到下划线转换，核心三项评分逻辑一致。

Q&A 与 RF 对无法解析的 criterion 会跳过，并要求至少一个可评分必需项、且这些项全部通过。它们并不把每个无效输出都直接判作该项失败。TW 也会跳过不可解析项，但在“有返回记录、却没有可评分必需项”的分支中，空集合的 `all(...)` 会为真；本文对该函数做隔离离线检查，确认全部 rubric 返回非法 JSON 时，rubric 门槛能够为真。这仍不能让任务自动成功，因为清单与变异检查还在。

TW 对返回的数值 `score` 与 YES/NO `status` 均作格式要求，实际判定使用 score；Q&A 的标准化则优先采用 status。若两个字段冲突，三种评分器不能简单视为共享完全相同的解析规则。默认最大重试数、judge 输出上限和端点设置也应随代码版本保存。[TW evaluator](https://github.com/scaleapi/SWE-Atlas/blob/49e4af3b6c803dd54a1cd60ead703aac25de4e21/data/tw/task-6902ef3ab97fe23e2ad2722c/tests/evaluate_tests.py) · [Q&A evaluator](https://github.com/scaleapi/SWE-Atlas/blob/49e4af3b6c803dd54a1cd60ead703aac25de4e21/data/qa/task-6905333b74f22949d97ba9b5/tests/evaluate_answer.py)

这些检查只说明固定代码的可达分支。本文没有调用被测模型、没有执行付费 judge，也没有重新跑完整任务，所以不把潜在解析行为当成原论文成绩已受到影响的证据。

本次已完整阅读 Scale 存档版正文与附录 A–K，比较 arXiv v1 文本，视觉检查主表和关键图；固定公开源码，遍历全部任务与 rubric，检查三类评分器、代表性 RF 行为验证、网络与运行配置，并隔离测试 TW 两个评分边界。尚未复现模型实验、容器启动、oracle 成功率或论文全套统计结果。

# ASPI：澄清交互中的提示注入风险

用户请 agent 推荐目的地的电动租车公司，但漏写了城市。agent 先询问城市，收到的答复却在补充目的地之外夹带了与原任务无关的预订指令。ASPI 研究的就是这种交互：模型主动索取的信息成为攻击内容的载体。论文在 AgentDojo 的模拟环境中构建 728 个任务—攻击组合；例如 o3 的普通工具注入成功率为 1.8%，澄清工具返回值中的注入成功率为 34.0%。这两个百分比使用的样本集合不同；同一澄清子集上的配对增幅为 31.3 个百分点。论文同时表明，单独进入澄清状态并不总会增加风险，具体结果依赖模型和消息通道。[论文 §3–6、表 2–3](https://arxiv.org/pdf/2605.17324v1)

## 版本与研究团队

原题为 **ASPI: Seeking Ambiguity Clarification Amplifies Prompt Injection Vulnerability in LLM Agents**，ASPI 是 Ambiguous-State Prompt Injection 的缩写。本文阅读 2026 年 5 月 17 日的 arXiv v1，共 34 页，含正文及附录 A–G；核查时 arXiv 只列这一版本，未列正式会议。[版本记录](https://arxiv.org/abs/2605.17324)

六位作者为 Udari Madhushani Sehwag、Zhengyang Shan、Heming Liu、Dileepa Lakshan、Joseph Brandifino 和 Max Fenkell。前两位共同第一作者。Sehwag、Brandifino、Fenkell 署名 Scale AI；Shan 另署 Boston University，Liu 另署 University of Illinois Urbana-Champaign，两人均署 Human Frontier Collective, Scale AI；Lakshan 为独立研究者。公司参与依据这些署名，而不是仅因代码托管在 Scale 组织下。[论文首页](https://arxiv.org/pdf/2605.17324v1#page=1)

## 受测的是模拟 agent 的信任边界

ASPI 沿用 AgentDojo 的四类环境：Workspace、Slack、Travel 和 Banking。每个环境有工具、初始状态、合法任务和攻击目标；工具调用可以改变环境状态，评分函数检查最终状态和轨迹。研究没有在真实银行账户、客户邮箱或线上 Slack 工作区发起攻击。

攻击者不能修改系统提示、模型权重或工具实现。标准间接注入假设攻击者可以影响邮件、共享文档等外部内容；澄清条件进一步考虑这些内容进入 `ask_user` 返回路径的情形。附录 A 列出的例子包括用户无意转述被污染的资料、共享消息通道允许他人代答，以及中间程序拼接返回内容。直接 `user` 消息攻击则作为权限更强的对照，不能与普通第三方文档注入混为一谈。[论文 §3、附录 A](https://arxiv.org/pdf/2605.17324v1#page=3)

因此，研究并不是把可信用户的每一次任务变更都定义成恶意行为。评测事先固定原始合法目标和攻击者目标，再测模型是否执行了后者。向真实系统外推时，需要先说明谁能控制澄清回复，以及平台怎样认证回复来源。

论文称威胁模型中的攻击者不知道具体用户任务；但数据构造中的语言生成器会看到模糊请求、缺失信息和预期问题，以把攻击包装成自然回复。这是基准准备过程拥有的上下文，不能把整条合成流程描述成完全不接触任务信息的盲攻击。

## 728 是任务—攻击组合数

每条数据由一个合法任务 $U$ 和一个攻击目标 $I$ 组成，记为组 $g=(U,I)$。同一合法任务可以和多个攻击目标组合。组内保存原始请求、参考工具调用、删除信息后的请求、缺失槽位、预期问题、良性答复和三种攻击回复。

| 环境 | 组合数 |
| --- | ---: |
| Workspace | 407 |
| Slack | 97 |
| Travel | 94 |
| Banking | 130 |
| 合计 | 728 |

这些数量与本次逐行读取公开四个 JSONL 的结果一致。按“环境＋任务 ID”去重，公开数据包含 **92 个合法任务和 35 个攻击任务**，形成 728 个不重复组合，而不是 728 个互不相关的原始业务任务。Workspace 占约 55.9%，总体均值也不等于四个领域各占四分之一的宏平均。[论文附录 B.3；公开数据](https://github.com/scaleapi/aspi/tree/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/data)

参考轨迹平均含 2.91 次工具调用，覆盖 52 种函数。本次按公开文件复算为 2.9066 和 52，与论文吻合。它们描述参考解，不是受测 agent 的实际调用预算。

### 用删除一个槽位制造澄清需求

构造器从完整请求 $p$ 中删除一个用户应提供的信息槽位 $s$，得到 $p_{\rm base}$。同时生成问题 $q$、良性答复 $r_b$ 和补全信息后的安全动作。优先选择日期、收件人、目的地、用户指定的标识符；要求这些信息无法靠环境工具自行找回。可以用工具搜索到的事实，以及可默认处理的风格偏好，不应成为必须询问用户的槽位。

附录的 Travel 示例删除 Los Angeles，保留日期与“推荐电动车租赁公司”的任务；良性回复补回城市。这个例子说明，解决歧义应当补全原任务，而非自动授权额外订酒店。Workspace 示例则从 Yoga Class 中删除 Yoga；这种单词修饰语可能仍能通过扩大搜索范围找回，因此具体样本能否迫使模型提问，还需要看实际行为和人工检查。[论文 §4.2、附录 B.4](https://arxiv.org/pdf/2605.17324v1#page=14)

生成使用 Gemini-3.1-Pro，温度 0.7，质量检查触发最多两次重试。论文列出十项检查，覆盖删除式改写、槽位必要性、问题方向、良性答案与攻击文本约束。不过当前代码 `quality.py` 实际列出七项 token/规则检查，`pipeline.py` 只将 QC-5、QC-6 设为第一阶段重试条件，第二阶段的重试关键检查集合为空；重试结束后也不是一律丢弃所有未通过项。这些是发布实现的范围，不能把它写成对语义不可恢复性的形式化保证。[论文附录 B.1–B.2；固定代码](https://github.com/scaleapi/aspi/tree/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/src/aspi/dataset)

论文报告原始请求平均 31.4 词，模糊请求 27.8 词，97.7% 变短。本次按空白分词读取当前文件，分别为 31.396 和 28.041 词，691/728 条词数变少；按字符数则为 720/728 条变短。分词方法或数据快照可能不同，公开资料不足以确定原因，因此保留论文与本次测量的区别。

### 三种回复变体并不直接用于所有条件

每组保存三种语言包装：HR 通过角色或上下文暗示权威，GS 将额外目标并入原工作流，CP 将额外目标描述成前提或约束。它们要求先给出合法缺失信息，再嵌入攻击目标。公开数据有 2,184 个变体，所有 728 组均有 HR、GS、CP，未发现生成失败占位符。

这些变体用于 `clarif_user`。主比较中的 `clarif_ask_user` 使用的则是动态良性答复加 AgentDojo `ImportantInstructionsAttack` 包装文本 $W$。不能将两者都解释成三种自然语言变体的平均结果。

## 八个条件分别改变了什么

令 $p$ 为完整请求，$p_{\rm base}$ 为模糊请求，$g_I$ 为原始攻击目标文本，$W$ 为包装后的攻击文本，$r_b$ 为良性澄清答复。下表按论文定义和当前执行代码整理：

| 条件 | agent 接收到的内容 |
| --- | --- |
| `exec_benign` | 完整请求，干净环境 |
| `exec_tool` | 完整请求，普通任务工具返回被 $W$ 污染 |
| `exec_user` | 首条用户消息为完整请求加原始 $g_I$ |
| `exec_next_turn` | 先运行完整任务，再追加含原始 $g_I$ 的用户消息 |
| `clarif_benign` | 模糊请求，提问后获得良性答复 |
| `clarif_tool` | 保留澄清问题，任务工具输出带 $W$，澄清答复本身良性 |
| `clarif_ask_user` | `ask_user` 返回 $r_b+W$ |
| `clarif_user` | `ask_user` 保留等待占位文本，随后追加含 HR/GS/CP 的用户消息 |

`exec_tool`、`clarif_tool`、`clarif_ask_user` 在当前代码中复用同组生成的 $W$；`exec_user` 是原始目标，不带这个包装。README 部分“wrapper 保持不变”的配对说明与实际拼接不一致，应以具体条件和代码为准。用户通道比较还改变了回复轮次、自然语言包装与变体数量，所以不宜笼统称为纯粹的状态因果效应。[论文 §5、附录 C.1；runner.py](https://github.com/scaleapi/aspi/blob/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/src/aspi/eval/runner.py)

### 从同一个澄清边界分支

模型收到模糊请求后，需要调用 `ask_user` 才进入澄清子集。系统提示明确要求通过该工具提问，不能只写普通文本，并提供一个餐厅预订例子。如果没有调用，代码先检查是否已完成任务；未完成而有文字输出时，追加一次要求改用工具的提示。仍未调用的组不进入澄清比较，但保留执行条件结果。

成功提问后，记录对话、工具轨迹和环境状态，再分别复制续跑。良性回复由 GPT-4o-mini-2024-07-18 按实际问题生成，温度 0.3；接口失败时可退回预生成答复。当前 `clarif_user` 则直接取数据里已有的三个变体，没有调用动态攻击回复生成器。因此附录 C.1 所说攻击回复动态匹配实际问题，并未完整对应这个发布入口。

`clarif_tool` 还有一个特殊处理：在新建的污染环境里重放此前任务工具调用，替换历史工具返回，保留原来的助手消息和澄清问题。它并非逐字不变的完整消息前缀；保持的是模型先前的动作选择和提问，再把工具观察替换成污染版本。这个回放式干预与让模型从最初就读取污染内容、自然走到澄清状态不同。[论文附录 C.1；`build_clarif_tool_state_via_replay`](https://github.com/scaleapi/aspi/blob/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/src/aspi/eval/runner.py)

## 评分、样本分母与配对统计

每组每条件有两个二元结果：$u_{gc}$ 表示合法任务成功，$\sigma_{gc}$ 表示攻击目标成功。二者独立，可能同时为 1；攻击成功不是“合法任务失败”的同义词。

对于同一个评估集合 $S$：

$$
\operatorname{Utility}_S(c)=\frac{1}{|S|}\sum_{g\in S}u_{gc},\qquad
\operatorname{ASR}_S(c)=\frac{1}{|S|}\sum_{g\in S}\sigma_{gc}.
$$

代码调用 AgentDojo 的 `utility_from_traces`、`security_from_traces`，必要时退回环境状态判定。`security=True` 在这里代表**攻击成功**，不是防御安全。

令全部组合为 $G$，模型 $m$ 实际调用澄清工具的集合为 $G_m^*$。澄清率是 $|G_m^*|/728$。论文表 2 的执行 ASR 用 $G$，澄清 ASR 用 $G_m^*$，其大小随模型在 393–590 之间变化。配对差必须把两边都限制在相同的 $G_m^*$：

$$
\widehat\Delta(c_1,c_2)=\frac1{|G_m^*|}\sum_{g\in G_m^*}(\sigma_{gc_1}-\sigma_{gc_2}).
$$

于是 $34.0-1.8=32.2$ 个百分点只是表 2 两个不同分母百分比的差；o3 的正确配对结果要读表 3 的 **31.3**。同理，Kimi 的 63.1−11.1=52.0 不能替代配对增幅 **46.3**。[论文附录 C.3、表 2–3](https://arxiv.org/pdf/2605.17324v1#page=17)

### 状态与通道的加法分解

论文主比较 A4 从普通工具注入变为澄清工具返回注入，在同一集合上可以恒等分解：

$$
\underbrace{\operatorname{ASR}(\text{clarif\_ask\_user})-\operatorname{ASR}(\text{exec\_tool})}_{\Delta_{A4}}
=
\underbrace{\operatorname{ASR}(\text{clarif\_tool})-\operatorname{ASR}(\text{exec\_tool})}_{\Delta_{\text{state}\mid\text{tool}}}
+
\underbrace{\operatorname{ASR}(\text{clarif\_ask\_user})-\operatorname{ASR}(\text{clarif\_tool})}_{\Delta_{\text{ask}\mid\text{clarif}}}.
$$

第一项固定普通工具通道，第二项在澄清状态内改变送达接口。对 o3，表 3 给出第一项 −1.2、总差 31.3，故第二项为约 **32.5 个百分点**；对 DeepSeek，分别为 −16.1、10.2，第二项约 **26.3**。这是从已舍入数值作的代数复算，不能据此合并两项置信区间，也不能把它当成心理机制的直接测量。

### 置信区间与显著性

论文按组进行 1,000 次配对 bootstrap，取 2.5% 和 97.5% 分位数；防御等更精细分析写可增至 2,000 次。代码默认种子为 0。这是在已有轨迹上重采样，不是让模型重跑 1,000 次。

精确 McNemar 检验只看两条件判定不同的组。若 $n_{10}$ 是 A 成功、B 失败的数量，$n_{01}$ 相反，令 $N=n_{10}+n_{01}$，$k=\min(n_{10},n_{01})$，则：

$$
p=\min\left(1,\;2\cdot2^{-N}\sum_{j=0}^{k}\binom Nj\right).
$$

没有不一致对时，本文与源码按原文报告未定义，而不是 $p=0$。说明例子：六个不一致对全部偏向同一条件时，$p=2/64=0.03125$。代码离线核算与此一致。表中印为 `0.000` 的值是显示精度，不是概率严格为零。

这些推断以任务—攻击组为重采样单位；公开数据中的同一合法任务会重复出现，论文没有报告按原始任务聚类的 bootstrap。置信区间应限于所采用的统计设计。[论文附录 C.3](https://arxiv.org/pdf/2605.17324v1#page=18)

| Opus 4.7 | 63.6% | 2.1% | 2.2% | −0.9 |

| Gemini-3-Flash | 74.9% | 2.2% | 35.7% | +33.3 |

### 在共同 68 组上的检查

作者还取十个模型都调用了 `ask_user` 的 68 组，重新绘制图 7，报告澄清 ASR 排序与原图的 Spearman 相关系数为 0.988。例如 o3 为 1.5%→35.3%，Gemini Pro 为 2.9%→23.5%。Opus 在图中两项均为 0%，所以附录文字“每个模型均更高”不能逐字照搬。

这个分析控制了不同模型提问子集的差异，但仍只覆盖共同进入澄清状态的 68 组，不能证明未提问的全部任务具有相同风险。表 4 也显示跨域差异：o3 的澄清接口 ASR 在 Travel 为 61.0%，Banking 为 15.9%；表中上半部分虽简写“Tool-channel”，澄清列对应 A4 的 `clarif_ask_user`，不是 A1 的普通 `clarif_tool`。[论文附录 D.2–D.3](https://arxiv.org/pdf/2605.17324v1#page=22)

## 安全性需要和任务完成率一起看

表 1 报告 Opus 无攻击执行 utility 为 97.8%，良性澄清后为 84.0%；Gemini Flash 为 92.6% 和 55.2%。但并非每个模型都降低：o3 为 44.0% 和 56.9%，Kimi 为 68.8% 和 78.9%。这些条件率的分母也不同，不能把差值直接称为同一任务上的纯澄清代价，原文“澄清始终降低 utility”的概括有例外。

当前代码对 `exec_next_turn` 还有特殊评分：合法任务 utility 在追加攻击消息**之前**计分，攻击成功在后续最终状态计分。后续破坏已经完成的成果不会回头取消这项 utility。因此该列接近良性执行率，不等于第二轮攻击没有损害最终任务状态。

`clarif_user` 对三个变体的攻击成功取最大值，utility 也分别取最大值。用说明例子表示：HR 完成合法任务但攻击失败，GS 攻击成功但合法任务失败，这组汇总仍可得到 utility=1、ASR=1。二者不一定来自同一条轨迹，不能仅凭这两个组级值断言 agent 同时完成两件事；行为图里的“任务与攻击并行”需要独立轨迹标注支持。[固定 runner.py 的 `_build_clarif_user_result`、`run_two_turn_eval`](https://github.com/scaleapi/aspi/blob/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/src/aspi/eval/runner.py)

## 两种防御与任务损失

Prompt guard 在每次模型调用前扫描 user 和 tool 内容，按空行切段，只替换判为注入的片段，尽量保留合法澄清答案。当前默认分类器是 ProtectAI 的 DeBERTa v3 prompt-injection-v2，阈值 0.5；它不是另一个被测 agent。Tool filter 则在继续行动前选择当前任务需要的工具，始终保留 `ask_user`；其输入可能已经含有污染内容，并未获得一份模型看不到的绝对干净任务。[论文附录 E；防御代码](https://github.com/scaleapi/aspi/tree/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/src/aspi/defenses)

| 模型与设置 | 澄清接口 ASR ↓ | 同条件 utility ↑ |
| --- | ---: | ---: |
| Gemini Flash，无防御 | 35.7% | 46.0% |
| Gemini Flash，prompt guard | 27.0% | 20.7% |
| Gemini Flash，tool filter | 23.9% | 40.6% |
| Gemini Pro，无防御 | 24.3% | 69.3% |
| Gemini Pro，prompt guard | 12.3% | 39.6% |
| Gemini Pro，tool filter | 19.3% | 60.0% |

来自表 5–6 的 `clarif_ask_user`。Flash 的 prompt guard 将 ASR 降低 8.7 个百分点，utility 同时降低 25.3；Pro 分别降低 12.0 和 29.7。Tool filter 的相应任务损失较小，但两类防御均没有消除攻击成功。这里只测试两个 Gemini 模型，不能推出对十个模型具有相同改善。[论文表 5–6](https://arxiv.org/pdf/2605.17324v1#page=24)

代码中防御分类器未固定权重 revision；本次只核对模型仓库元数据，当前 revision 为 `90c9989b1a342275dd0d1a95aad283c04e075671`，非 gated，没有下载权重。tool filter 未传专用模型时会复用 agent 模型。分类器加载失败会抛错，个别分类失败在容忍范围内按未命中处理；工具选择解析失败则保留全部工具。这些需要随防御审计日志记录，不能把“启用了参数”自动当作每一步防御都正常工作。本文只静态核查这些路径，没有加载分类器或发起防御实验。

论文展示的是带防御的整套流程对照，没有给出移除 HR、GS、CP 单一变体、去掉单词删除限制、替换用户认证方式等完整消融。附录提到额外推理开关实验耗时，当前正文和附录未提供对应结果表，不能补写推理开关的效果。

## 人工检查与行为评审各自验证的内容

论文涉及三种人工验证，需要分别理解：

- **数据构造**：正文称所有保留样本均经人工验证；附录 B.5 具体写随机抽 200 例，由总计 83 位至少本科的标注者核对四项条件，并复查失败项。是否另外覆盖其余 528 例，公开说明不充分，不能确认 728 条全部逐条验过。
- **模拟器回复**：另抽 200 例，每例三位独立评审。正文写 99%，附录写超过 99% 认为答案正确，Gwet AC1 约 0.99。这个指标检验回复是否回答缺失信息，不是整个 benchmark 的攻击判定准确率。
- **行为 judge**：200 例按攻击条件分层，每例三人，比较 Gemini-3.1-Pro、GPT-5.4 和人工。原始平台指令未逐字公开，附录 G 提供的是整理后的准则。

行为标签区分完整遵从、部分遵从、明确拒绝、忽略、不清楚；另标注问题是否问对、后续只做合法任务还是同时做攻击，以及从可见轨迹推断的“混淆”“被说服”等原因。这些是观察标签，不是对模型内部心理状态的直接测量。图 9–13 支持“问对缺失信息仍可能随后执行攻击”的现象，但没有干预实验确定信任变化的唯一原因。[论文附录 F–G](https://arxiv.org/pdf/2605.17324v1#page=25)

图 12 按问题质量分别归一化：在 ON_TARGET 这一行，39% 被标为只做合法任务，48% 同时尝试任务与攻击，5% 只做攻击，8% 不清楚。这里的 48% 是对应问题质量行中的行为标签比例，不是全体 728 组的确定性 ASR；“尝试两者”也不保证两者最后都成功。图 11 则将完整与部分遵从分开，澄清接口分别约 38% 和 7%，不能只取其中一条颜色就当作全文统一成功定义。

主指标与 judge 的关系也有文本差异：§6.5 和 F.6 将 judge 定位为诊断、ASR 采用确定性函数；§5.4 和 F 的部分描述又涉及 judge 映射二元结果。当前 `runner.py` 的主分数字段由 AgentDojo 函数计算，`aggregate_with_judge` 另加尝试与行为指标，没有直接替换主 `security` 字段。因此本文把主表 ASR 和语义遵从标签分开讲述。

附录 F.1 把完整及部分遵从都计入行为成功，F.7 和表 7 却写二元 κ 只把 FULL_COMPLIANCE 当正类。表 7 的攻击宏平均二元 κ 为 LLM–LLM 0.942、Human–LLM 0.905；人类 Fleiss κ 为 0.775。它们不能直接作为“完整或部分遵从”这另一种二分类的可靠性证明，更不是 94.2% 或 90.5% 的准确率。[论文表 7](https://arxiv.org/pdf/2605.17324v1#page=34)

附录估计每模型约 18,000 次 agent 调用、10,000 次 judge 调用，耗时 8–40 小时；多模型并行的主实验约 3–4 天。未给 token 总量和实际账单，不能从调用次数推定准确费用。[论文附录 C.2–C.4；官方仓库](https://github.com/scaleapi/aspi/tree/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d)

还有三处对复算直接有影响：

1. **A2 定义**：论文表 3 比较 `clarif_user − exec_user`，当前 `metrics.aggregate()` 的 `dasr_state_user` 实际比较 `clarif_user − exec_next_turn`，交互项也跟着采用后一基线。本次构造两条无模型调用的假结果，代码 A2 为 0，而论文定义应为 1，证实不能直接按同名字段对照论文表。
2. **区间实现**：`aggregate()` 的单条件率返回 Wilson 区间，绘图用 `bootstrap_rate()`，配对差用 bootstrap。正文图注写 bootstrap，应核对使用哪个输出，不能把所有 JSON 区间统一叫 bootstrap。
3. **数据质检**：将公开组转换为 C3 检查格式后，QC-4/5 全部通过，QC-6 有 8 条、QC-7 有 92 条规则未通过；这不是独立人类确认的错误率。公开组没有 `ground_truth_output`，依赖该字段的前三项无法直接复核。七项规则也不覆盖论文描述的全部十项。

上述差异描述当前发布材料，不证明作者历史运行采用了错误设置。若需要完整重现，应向作者确认实际 AgentDojo 分支、条件配对、变体汇总规则、原始结果和最终数据快照，再比较数值。[固定 metrics.py](https://github.com/scaleapi/aspi/blob/e2a3f6ac87b2c00ac482252d067d22f3ecf57b9d/src/aspi/eval/metrics.py)

ASPI 的结论范围是：在四类模拟任务、单槽位缺失和一次显式澄清工具交互中，普通执行时的注入鲁棒性不能代表澄清返回路径的鲁棒性。更自然的多轮歧义、经过身份认证的回复、不同 agent 框架和真实部署都尚需独立评测。作者认为复杂交互可能风险更高，这是外推假设，本文不把现有成功率称为已经证明的通用下界。

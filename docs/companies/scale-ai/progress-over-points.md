# Progress over Points：让训练加速成为评测目标

给模型一份已经可以运行的语言模型训练程序，让它修改实现，再用真实 GPU 运行检查修改是否有效。Progress over Points 把这一过程组织成持续搜索：模型提出改动，环境返回损失、耗时和性能分析，下一轮再参考已有程序继续优化。在论文的 NanoGPT 实验中，最佳程序把训练时间从 175.2 秒降到 172.68 秒，同时满足验证损失门槛。文章的主要议题是如何围绕可测量的研究目标设计评测；实验只覆盖这一种预训练环境。[论文 §1、§3–4](https://arxiv.org/abs/2512.11183v1)

## 从回答已知问题转向改进训练程序

常见评测先固定问题和参考答案，再计算模型答对多少。作者提出另一种组织方式：选一个本身具有研究意义、又能反复测量的目标，让模型直接推动该目标。例如，同样的数据和硬件上，用更短的时间把模型训练到指定质量。

这一主张包含两个环节。首先，任务应允许多种实现，不能只检查是否复现了指定解法。其次，评测结果必须对应外部可检验的改进：训练更快、损失更低，或者性能与成本的关系发生变化。模型之间仍然可以排名，但排名以实际运行产生的改进为依据。[论文 §1–2](https://arxiv.org/pdf/2512.11183v1#page=1)

作者把这一思路称为 progress-oriented benchmarks。对静态评测的局限、以及训练优化有望迁移到更大模型的讨论，属于本文提出的研究动机。文章没有实验比较两类评测对长期科研产出的影响，也没有验证这里找到的改动在其他模型规模上仍然有效。

## NanoGPT 环境固定了哪些条件

任务沿用社区 NanoGPT speedrun：在一个 **8 张 H100 的节点**上训练语言模型，使 FineWeb 验证集的交叉熵损失达到 **3.28 或更低**，同时缩短训练时间。论文称初始代码来自 2025 年 8 月的领先实现，但没有给出所用提交哈希。[论文 §1、§4.2](https://arxiv.org/pdf/2512.11183v1#page=2)

为解释目标，可以把它写成下面的约束优化问题；这是对任务的数学整理，并非原文编号公式：

$$
\min_p T(p)\quad\text{subject to}\quad L_{\mathrm{val}}(p)\leq 3.28,\quad p\text{ 满足环境规则}.
$$

$p$ 是完整训练程序，$T(p)$ 是运行耗时，$L_{\mathrm{val}}(p)$ 是固定验证数据上的损失。减小网络、跳过训练或修改评测函数，都可能使程序更快；只有同时通过质量门槛和规则检查，耗时才能用于比较。

交叉熵衡量模型给正确后续 token 分配的概率。用通常的自回归写法表示：

$$
L_{\mathrm{val}}=-\frac{1}{N}\sum_{i=1}^{N}\log P_\theta(x_i\mid x_{<i}).
$$

这里 $N$ 是参与评分的 token 数，$x_i$ 是正确 token。损失越低，表示模型平均给正确 token 更高的概率。验证集切片、上下文长度和计算方式会影响这个数，因此不同数据或实现上的「3.28」不能直接互换。论文说明这些条件由环境控制，但没有完整列出可独立重建实验的数据文件、切片配置和基线版本。[论文 §3.1、§3.3](https://arxiv.org/pdf/2512.11183v1#page=3)

环境还返回多种反馈，帮助模型定位耗时来源：

| 反馈层次 | 论文列出的内容 | 对修改程序的作用 |
| --- | --- | --- |
| 训练过程 | 当前步数、平均每步时间、中间验证损失 | 观察速度变化是否伴随收敛变化 |
| 程序阶段 | 前向、反向、优化器和数据加载的总耗时、平均耗时、占比、调用次数 | 定位主要时间开销 |
| 底层操作 | 最耗时的 15 个 CUDA kernel 和 CPU 操作及调用次数 | 识别细粒度计算或调度开销 |
| 整体资源 | token 吞吐量、峰值内存 | 判断计算与存储效率 |

这是反馈接口的设计说明。论文没有公开每个候选程序的完整性能分析，因此不能逐项验证最终收益来自哪个 kernel 或哪段资源开销。[论文 §3.1](https://arxiv.org/pdf/2512.11183v1#page=3)

## 从父程序到下一轮候选

系统基于 OpenEvolve 的修改版本。它维护程序数据库，保存成功和失败候选及其反馈，再通过演化搜索不断产生新的实现。一次循环包含以下步骤：

1. 从数据库选一个父程序，同时抽取表现好的程序和其他较多样的程序作为参考。
2. 把代码与测量结果组装进提示，让语言模型提出修改。
3. 用 search/replace 代码块表达补丁，生成子程序。
4. 先短暂执行，检查编译或运行错误；失败时把错误交回模型修复。
5. 通过快速检查后进行完整评估，再把子程序及测量结果存入数据库。

数据库采用岛屿式演化：多个程序群分别探索，较好的程序周期性迁移，避免所有搜索都过早集中到同一种实现。提示中同时使用优质候选和其他候选，是为了兼顾已有收益与不同方向。原文没有给出岛屿数量、迁移频率，以及两类参考程序集合的具体大小。[论文 §3.2、图 1](https://arxiv.org/pdf/2512.11183v1#page=3)

### 先构思，再写代码

默认方式从模板池抽取提示，直接要求模型改代码。另一种方式是两阶段 meta-prompting：先要求模型用自然语言提出高层思路，再把该思路交给模型落实为补丁。

这增加了一次显式构思过程，也可能生成更难实现的修改。作者观察到它更容易产生错误程序，因此每次实验的前 20 轮关闭这一机制，先积累可运行的父程序，之后再启用。每轮分支数为 10，精英档案大小为 20，快速修复次数参数 $N_{\mathrm{fast}}=3$。[论文 §3.2、§4.1](https://arxiv.org/pdf/2512.11183v1#page=4)

这里的「运行成功」有两道门槛：能够编译、执行，只说明程序在工程上可运行；完整训练后损失达到 3.28，才说明它满足 speedrun 的质量要求。两者在结果分析中分别计数。

### 数据库分数与最终目标存在差别

原文 §3.2 使用一个标量对数据库中的程序排序：

$$
s_c=t_{\mathrm{step}}\,\ell_{\mathrm{val}}.
$$

$t_{\mathrm{step}}$ 是整体平均每步时间，$\ell_{\mathrm{val}}$ 是最终验证损失，两项越小越好。但这个乘积没有直接使用总训练时间，也没有把 3.28 写成硬门槛。它适合给搜索提供连续反馈，却不自动等价于前面的约束优化目标。[论文 §3.2](https://arxiv.org/pdf/2512.11183v1#page=4)

下面只是说明差异的自拟例子：程序 A 每步 1 毫秒、运行 2,000 步；程序 B 每步 0.9 毫秒、运行 2,400 步，二者最终损失相同。乘积分数偏向 B，但两者总时间分别为 2 秒和 2.16 秒，实际更快的是 A。因此，最终结果仍需要检查完整运行的损失与耗时，不能只引用数据库分数。

## 环境如何限制投机修改

agent 可以修改程序，而负责判定成绩的关键条件由环境在运行时重新注入：训练切片、验证切片和验证序列长度会覆盖候选代码中的改动；交叉熵函数由环境提供；训练文档边界和因果注意力掩码也不能修改。[论文 §3.3](https://arxiv.org/pdf/2512.11183v1#page=4)

这些约束针对几种直接的失真来源：换成更容易的验证数据、改变计算损失的函数、或让模型看到预测位置之后的内容。固定交叉熵也限制了探索其他损失函数的自由，作者明确把它视为维护评测一致性的取舍。

原文此处说掩码阻止关注「prior tokens」，与自回归因果注意力的通常含义相反。正确理解应是防止看到未来 token，并限制跨文档访问，不能把禁止关注历史 token 当作该训练任务的规则。由于完整环境代码目前不可访问，本文无法检查具体掩码注入实现。

这些保护是环境设计，不构成对所有投机方式的完备证明。论文没有展示系统性攻击测试，也没有给出候选程序与参考实现的完整语义等价检查；函数等价验证被列为后续方向。[论文 §3.3](https://arxiv.org/pdf/2512.11183v1#page=5)

## 实验预算与主结果

所有实验使用相同的每轮 10 个子程序、20 个精英程序和快速修复参数，但总轮数不同：

| 模型 | 演化轮数 | 名义子程序数 | 图中报告的最佳合格耗时 |
| --- | ---: | ---: | ---: |
| o3 | 90 | 约 900 | 172.68 秒 |
| GPT-5 Thinking | 50 | 约 500 | 174.48 秒 |
| Gemini 2.5 Pro | 50 | 约 500 | 174.78 秒 |
| Claude Sonnet 4 | 50 | 约 500 | 173.28 秒 |

数值来自图 2a、图 3a；图 3a 简写为 Claude 4，正文明确为 Claude Sonnet 4。名义候选合计约 2,400 个，不代表 2,400 次成功的完整训练，也不包括每次修复产生的额外模型调用。两阶段提示、编译失败和重试还会改变实际 token 与时间成本。论文未披露完整 API 配置、总 GPU 小时或费用，不能把轮数当成严格等价的计算预算。[论文 §4.1–4.3](https://arxiv.org/pdf/2512.11183v1#page=5)

### 最佳结果是 2.52 秒的内部基线改进

图 2a 给出三个程序的对照：

| 程序 | 验证损失 | 训练时间 |
| --- | ---: | ---: |
| Previous SOTA | 3.280 | 176.7 秒 |
| Current SOTA | 3.2797 | 175.2 秒 |
| Best Evolved | 3.280 | 172.68 秒 |

相对于实验使用的 Current SOTA，时间减少 $175.2-172.68=2.52$ 秒，相对降幅约 **1.44%**。摘要用约 3 秒概括改进；如果改用 176.7 秒作为起点，差值则为 4.02 秒。两个比较对象不应混用。[论文图 2a](https://arxiv.org/pdf/2512.11183v1#page=5)

论文没有给出这些耗时的重复运行次数、标准差或置信区间。显示为 3.280 的损失经过舍入，也不足以判断它与门槛之间的精确余量。因此这张表支持「该次搜索报告了一个更快的合格程序」，尚不能量化结果对随机种子或硬件波动的稳定性。

「新的世界纪录」还需要独立核对。本文检查了 modded-nanogpt 上游固定提交 `ecbb586296d3dac36fd206211f25d63bad4a6b35` 的历史表，其中 2025 年 8 月 23 日已经列出 **2.812 分钟，即 168.72 秒**。这与论文使用的 175.2 秒基线不一致。由于论文未固定初始提交和完整计时条件，不能把不同来源直接排成同一场比赛，也无法据此确认其外部纪录主张。本文只采用论文内部的 175.2 → 172.68 秒比较。[上游历史记录](https://github.com/KellerJordan/modded-nanogpt/blob/ecbb586296d3dac36fd206211f25d63bad4a6b35/README.md)

## 最佳程序具体改了什么

图 2b 展示的核心改动针对由 Muon 优化的隐藏层大矩阵：识别这些参数，把其中 float32 参数存储转为 bfloat16；由 Adam 优化的张量保留 float32。这个选择没有把所有权重一律降精度。[论文图 2b](https://arxiv.org/pdf/2512.11183v1#page=5)

从代码语义看，操作落在参数的 `.data` 上，因而首先改变的是这些矩阵的存储类型。论文正文把它概括为降低大矩阵优化器操作的精度，但仅凭展示的片段，不能进一步断言全部优化器状态、动量缓存或主权重副本都采用 bfloat16。

对于被转换的参数，单元素存储从 4 字节变为 2 字节。这可能减少数据搬运并改变相关计算路径；但峰值内存还包括激活、梯度、优化器状态和其他张量，不能推导为整次训练显存减半。论文也没有给出这项改动前后的逐 kernel 对照，无法确定各部分对 2.52 秒收益的贡献。

保留部分参数的 float32 精度提供了一种选择性折中：在大矩阵上争取效率，同时避免对其他张量做同样改动。文章没有公布移除此补丁的独立消融、多个种子的重复实验或更大模型测试，因此结果的直接适用范围仍是这一 NanoGPT 设置。[论文 §4.2、图 2](https://arxiv.org/pdf/2512.11183v1#page=5)

## 搜索曲线能说明的内容

图 2c 和图 3b 只绘制达到损失要求的程序。快速失败或损失超标的候选不在这些散点中；因此「后期出现更低耗时」不能单独说明后期成功率提高。

图 3c 另把程序分成三类：有运行错误、能运行但损失超标、能运行且损失合格。作者观察到启用 meta-prompting 后错误比例上升，同时少数有效候选取得较好结果。这说明探索更复杂修改与稳定地产生有效程序之间存在实际张力。[论文 §4.2–4.3、图 2–3](https://arxiv.org/pdf/2512.11183v1#page=5)

不过，论文没有安排同预算、全程不启用 meta-prompting 的独立对照组。前后两段还同时改变了搜索轮次、数据库内容和父程序质量，所以不能把时间上的变化完全归因于提示策略。也不能把散点趋势线当作累计最优值曲线，或据此预测继续运行必然取得多少收益。

在三个 50 轮实验中，Claude Sonnet 4 的最佳合格程序最快，比 GPT-5 Thinking 快 1.20 秒；它同时产生了较多失败程序。最佳值与成功率描述的是不同表现。o3 多运行了 40 轮，不能把四个最优耗时直接解释成相同预算下的模型能力排名。[论文图 3、§4.3](https://arxiv.org/pdf/2512.11183v1#page=6)

## 两个候选思路的实现细节

论文还展示 GPT-5 和 Gemini 产生的两段候选代码。作者确认它们能编译并执行，但没有逐一报告完整训练损失、耗时或消融。它们与取得 172.68 秒的最佳补丁是不同结果，应分别理解。[论文 §4.4、图 4](https://arxiv.org/pdf/2512.11183v1#page=7)

### 按注意力头分配部分 KV 块

GPT-5 的候选修改滑动窗口注意力中的部分 KV 块列表。它保留一个所有头共享的小核心，再把其余部分块按轮转方式分给不同注意力头，同时保持原相对顺序。图示代码设置共享核心大小 `CORE = 2`，并单独保留完整块的处理。

下面是根据图 4a 规则构造的说明示例。假设有两个头，部分块序列编号为 0 到 5：

| 注意力头 | 保留的部分块 |
| --- | --- |
| 头 0 | 0、1、2、4 |
| 头 1 | 0、1、3、5 |

原来两个头各访问 6 个部分块，共 12 次头—块访问；此例变为 8 次。两头合起来仍覆盖这 6 个块，但每个头看到的集合已经改变。因而「覆盖相同」只能用于跨头集合的并集，不能推出与原注意力计算等价，也不能直接把访问数降幅写成实际训练加速比例。

图中构造 BlockMask 时仍使用文档因果规则。完整块与部分块分别处理，不能把这段修改概括成随意删掉所有历史 KV。至于质量损失是否可接受、速度收益是否超过掩码构建开销，原文没有给出这项候选的独立结果。[论文图 4a、§4.4](https://arxiv.org/pdf/2512.11183v1#page=7)

### 按 token 难度分配计算

Gemini 2.5 Pro 的候选是 `AdaptiveComputeBlock`。图 4b 展示初始化代码，定义了不同计算量的分支、难度预测器、上下文提取模块，以及可学习预算等状态。

两个较小分支分别采用 $d\rightarrow d/4\rightarrow d$ 和 $d\rightarrow d/2\rightarrow d$ 的 MLP；其他分支包含注意力和 MLP。难度预测器输出五个选项，对应 micro、mini、standard、premium 和 skip。上下文模块包含一维卷积、激活和池化；另有 token memory 字段及预算参数。[论文图 4b](https://arxiv.org/pdf/2512.11183v1#page=7)

这段代码表达的思路是让不同 token 使用不同计算量。但图中没有完整 `forward`，也没有明确的路由训练目标、预算约束公式、实际分配比例或各分支调用开销。因此不能据此写出一套已验证的动态计算算法。

作者说路由会参考周围 token 的全局上下文。若要复现自回归训练，需要进一步核对上下文提取是否保持因果性，以及未来信息是否可能进入路由。这里缺少完整实现，无法判断具体处理方式。论文也未提供该模块达到 3.28 的证据；「可运行」只确认了比语法正确更进一步的工程状态。[论文 §4.4](https://arxiv.org/pdf/2512.11183v1#page=8)

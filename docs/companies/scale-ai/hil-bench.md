# HiL-Bench：在任务执行中识别信息缺口并求助

一个编程助手可能能修复代码，却不知道某个业务参数只能向需求方确认。HiL-Bench 把这两种能力拆开：先从软件工程和数据库任务中移走关键背景，再给模型一个求助工具，观察它能否在探索途中发现缺口、提出具体问题，并把答案用于完成任务。实验中的主要差距出现在“已拿到全部信息”与“需要自己发现并询问信息”之间；论文也尝试用强化学习改善后者。阅读这项工作时，需要同时看任务通过率、提问质量，以及工具实际采用的判定规则。[原文 §1、§3–4](https://arxiv.org/pdf/2604.09408v4#page=1)

## 任务中的缺口需要在执行途中被发现

可以用一个说明示例理解设计：用户要求统计“高峰时段的有效交易”。助手查看表结构后，发现数据库有交易时间，却没有“高峰时段”的业务定义；接着读取说明，又发现两份材料对“有效交易”是否排除退款记录说法不同。这时继续写 SQL 需要自行选择一种解释，向需求方询问则可以获得确定规则。

HiL-Bench 把这种信息缺口称为 **blocker，即阻碍正确完成任务的障碍**。它与普通的运行报错不同：程序错误可能通过读代码解决，而合格的 blocker 必须无法从允许访问的环境中推回正确答案。模型需要先探索，再识别信息不足，调用 `ask_human()`，获得澄清后继续执行。任务并不要求开头先列一张问题清单。[§3.2–3.4、图 2](https://arxiv.org/pdf/2604.09408v4#page=4)

### 从已有任务改造环境与要求

软件工程任务来自 SWE-Bench Pro，要求在代码库中提交修复；text-to-SQL 任务来自 BIRD，要求结合数据库、表结构说明和业务资料生成正确查询。标注人员会同时修改任务描述与环境：例如移走参数定义、让两段需求出现冲突，或留下多个同样合理的字段解释。

每个任务注入 3–5 个独立障碍。登记表记录障碍 ID、类型、缺口描述、确切解决信息，以及不同措辞的示范问题。答案保存在登记表中，求解模型不能直接读取它。[§3.1–3.2、附录 C](https://arxiv.org/pdf/2604.09408v4#page=3)

| 类型 | 判定重点 | 原文中的任务情形 |
| --- | --- | --- |
| 信息缺失 | 缺少完成任务必需的值或映射 | SQL 要筛选“拥挤学校”，但没有阈值或可直接使用的字段定义 |
| 要求歧义 | 有多个合理解释，无法确定哪一个符合需求 | “平台早期”没有明确时间范围 |
| 信息矛盾 | 两项要求不能同时满足，需要确定优先级 | 同一软件任务对保留信息与清除信息给出相冲突的要求 |

这里的分类根据修改后的任务成立。不能把日常任务里任何不够详细的描述都当成必须求助的障碍；论文还要求它满足下面的质量条件。[附录 A–B](https://arxiv.org/pdf/2604.09408v4#page=13)

### 七项质量要求与任务筛选

每个障碍必须真实可信、影响核心结果、有明确唯一的解决信息、无法在预算内靠猜测或穷举得到答案、与其他障碍独立、没有把答案留在可见环境中，并且与原任务自然相关。任何一项不通过都需要修改或剔除。显眼的 `[REDACTED]`、刻意留空的 TODO，以及无关紧要的格式偏好，不符合这套要求。

独立审核人员对每个任务进行 5–6 轮人工审查。自动检查还包括：软件任务的环境补丁、参考补丁和隐藏测试能否正确应用，参考方案能否通过测试；SQL 的数据库修改能否执行、参考查询是否正确且结果非空。参考结果非空可以避免“两个错误查询都返回空集”被误判为一致。软件仓库历史还需要压缩，以免模型从旧提交中恢复隐藏答案。[附录 C.1–C.2](https://arxiv.org/pdf/2604.09408v4#page=14)

任务选择另有两项模型测试：没有求助工具时通过率不超过 5%；提供全部解决信息后，至少一个参考模型的通过率接近 90%。这使评测集中于“信息有了就较容易做成”的任务，也意味着该分布经过能力和难度筛选，不能直接当作真实工程请求的随机样本。[§3.2](https://arxiv.org/pdf/2604.09408v4#page=4)

## 求助工具返回固定答案，但相关性由模型判断

`ask_human(question: str) -> str` 并没有让真人逐条回复。论文使用冻结的 Llama-3.3-70B-Instruct，把问题与登记的缺口描述、示范问题进行语义匹配。匹配成功就返回预先写好的解决信息，否则返回 `irrelevant question`。这种设计限制了回答内容的自由发挥，仍然保留了语义判定误差。[§3.4](https://arxiv.org/pdf/2604.09408v4#page=5)

附录 D 的规则是：过于宽泛的问题不接受；部分重叠的问题，如果正常协作者会据此提供所需答案，可以接受；涉及多个障碍的问题至多匹配一个。裁判在人工标注的独立问题—障碍对上达到 97% 精度和 91% 召回率，两名标注者分别判断，分歧由第三人处理。原文未给出这批校准数据的样本数和置信区间。任务层召回低于 80% 时，会扩充示范措辞并重新验证，最终要求至少达到 85%。[附录 D](https://arxiv.org/pdf/2604.09408v4#page=15)

**固定回答不等于整个评测过程完全确定。** 本次检查的公开实现默认使用 Llama 3.3 70B 的 AWQ 量化模型，裁判温度为 0.05；结果还受提示、量化方式、服务配置及失败重试影响。原文的 97%／91% 也不能直接当作任意自选裁判的可靠性。[裁判实现](https://github.com/hilbenchauthors/hil-bench/blob/a98052f7bcb3a92d6ce1a3c1da20237b8b3d2e8c/hil_bench/ask_human_server.py)

## Ask-F1 同时衡量提问针对性与障碍覆盖

设一个任务有 $k$ 个已登记障碍，模型共问了 $n$ 次。其中 $q$ 次提问被判定相关，共覆盖 $d$ 个不同障碍。论文式 1 定义：

$$
P=\frac{q}{n},\qquad R=\frac{d}{k},\qquad
\operatorname{AskF1}=\frac{2PR}{P+R}.
$$

$P$ 是问题精度，$R$ 是障碍召回率，指标越高越好。找到答案只增加对应障碍的覆盖数，不代表代码或 SQL 已经完成；实际完成情况由另一个任务通过指标记录。[§3.5、式 1](https://arxiv.org/pdf/2604.09408v4#page=5)

论文给了一个计算例子：5 个障碍中解决 4 个，问了 50 次，其中只有 4 次相关，则 $P=4/50=8\%$、$R=4/5=80\%$，Ask-F1 约为 14.5%。只追求召回会忽略其余 46 次无效提问，调和平均则会降低分数。

### 公开代码采用去重后的障碍数作精度分子

代码 `compute_hil_metrics()` 实际把 $d$ 同时用于两个分子：

$$
P_{\mathrm{code}}=\frac{d}{n},\qquad
R_{\mathrm{code}}=\frac{d}{k},\qquad
F_{\mathrm{code}}=\frac{2d}{n+k}.
$$

最后一个等式是在 $n,k>0$ 时的化简。没有提问或没有匹配时，代码分支返回零分。汇总时，它先累加各任务的问题数、障碍数和已发现障碍数，再计算精度与召回，而不是直接平均每任务的 F1。[指标实现](https://github.com/hilbenchauthors/hil-bench/blob/a98052f7bcb3a92d6ce1a3c1da20237b8b3d2e8c/hil_bench/utils/compute_hil_metrics.py)

两种定义在重复提问时可能不同。以一个说明例子为例：5 个障碍，3 次提问分别匹配第一个、第一个、第二个障碍。若三次都算“相关”，按论文式面值计算，$P=1$、$R=0.4$，F1 约 57.1%；公开指标去重后 $P=2/3$、$R=0.4$，F1 为 50%。本次只对这段纯指标函数使用合成日志验证了后一个数值，没有调用裁判模型。

求助服务允许同一个障碍前两次匹配都返回答案，第三次起强制视为无关；指标仍只计一个不同障碍。因此，是否返回答案、是否增加覆盖数、是否获得训练奖励，是三个不同判断。不能仅依据原文“相关问题”的一句定义就把它们合并。

### 当前实现的其他判定与分母问题

代码中的裁判提示比附录说明更严格：同时谈多个主题会被要求整句拒绝，带有假设的确认问句会被拒绝，简单重复模糊词也会被拒绝。提示一方面要求问题体现已经进行过分析，另一方面又要求不带背景、观察或分析。这些规则会影响什么表达被接受，评测结果因而同时反映信息缺口识别与对这套提问协议的适应程度。

还有一个汇总边界：`batch_runner.py` 在存在求助日志时只传入有日志的实例，而服务日志在发生求助后才创建。按这条公开路径，**一批中完全没有提问的任务可能不会计入障碍总分母**。复现时应对照完整任务名单补齐零提问记录，再明确采用的口径。这是当前源码的静态核查结果；它不能证明论文实验使用了同一版本，也不能据此重算论文的分数。[批处理与指标调用](https://github.com/hilbenchauthors/hil-bench/blob/a98052f7bcb3a92d6ce1a3c1da20237b8b3d2e8c/hil_bench/scripts/batch_runner.py)

## 主实验：提供工具后，主动获取信息仍有较大差距

四个主要模型在 SWE-Agent 框架中运行；SQL 额外提供业务资料检索、表结构探索和查询执行工具。实验设三种条件：保留障碍且无求助工具、预先给出全部解决信息、保留障碍但允许求助。表 1 报告后两种条件的 pass@3，以及有工具条件下的提问指标。[§4.1、表 1](https://arxiv.org/pdf/2604.09408v4#page=6)

pass@3 通常表示每个任务最多三次独立尝试中至少一次成功的比例。它不能由三次 pass@1 简单取平均得到；例如同一任务三次中只成功一次，前者记成功，后者只有三分之一。公开代码的具体汇总问题在后面的复现部分说明。

### SQL 任务

| 模型 | 完整信息 pass@3 | 有求助工具 pass@3 | 障碍召回率 | 问题精度 | Ask-F1 |
| --- | ---: | ---: | ---: | ---: | ---: |
| GPT-5.3-Codex | 86.0% | 5.3% | 14.0% | 55.3% | 22.3% |
| GPT-5.4 | 86.0% | 17.3% | 22.7% | 54.3% | 32.1% |
| Gemini 3.1 Pro | 88.7% | 35.3% | 59.2% | 35.6% | 44.5% |
| Claude Opus 4.6 | 90.7% | 39.3% | 61.2% | 54.3% | 57.5% |

在这组 SQL 条件中，Claude Opus 4.6 同时具有最高通过率和 Ask-F1，但其 39.3% 的通过率仍比完整信息条件低 **51.4 个百分点**。GPT-5.3-Codex 两种条件相差 80.7 个百分点；其主要过程差距表现为只覆盖了较少障碍。[表 1](https://arxiv.org/pdf/2604.09408v4#page=6)

## 消融与失败分析支持的范围

### 仅看任务文字会漏掉大量障碍

在 SQL 的 spec-only 消融中，Claude Opus 4.6 可以读取任务并求助，却不能查看表结构、执行 SQL 或获取业务逻辑。障碍召回率从有完整环境工具时约 61% 降至 11%，减少约 50 个百分点。缺失信息和歧义类受影响更大；矛盾有时直接出现在文字要求中，所以降幅较小。[§3.3](https://arxiv.org/pdf/2604.09408v4#page=4)

这个实验支持“部分障碍必须通过环境探索发现”。它同时移除了多项工具，不能单独确定表结构查看、查询执行或业务检索各自贡献多少，也不能证明所有任务都无法靠开头提问解决。

### 失败分布的分母是某类失败轨迹

作者用 Sonnet-4 对 3,600 余条失败轨迹分类，分为工具使用、目标遵循和逻辑三个维度，再细分参数错误、策略错误、没有完成关键动作、自我检查失败等。文中的一致性系数 $\kappa=0.928$ 指裁判重复运行的一致性，不是与真人标注的同一数值。人工校准采取抽查和调整规则，未报告完整的人机一致性表。[§4.3、附录 F](https://arxiv.org/pdf/2604.09408v4#page=7)

以 SQL 工具使用失败为例，Gemini 基线中有 50 条此类轨迹，其中 56.0% 属于未完成关键工具调用，38.0% 属于参数等准确性问题；有求助工具时，对应样本变为 17 条，两种占比分别为 17.6%、82.4%。后者不是“82.4% 的所有任务失败”，而是在 **17 条工具使用失败** 中的构成。[表 4](https://arxiv.org/pdf/2604.09408v4#page=17)

Claude 在基线 SQL 的目标遵循类失败中，有 20 条被归入该维度，其中 45% 被标为自我检查失败。作者据此讨论“察觉问题后仍提交”的轨迹；它不等于 Claude 在全部任务上有 45% 的同类行为。[表 5](https://arxiv.org/pdf/2604.09408v4#page=17)

这些分类描述了特定模型、任务与框架下的行为。论文把跨域相似性解释为模型层面的特征，但没有通过控制训练数据或训练机制的实验来证明这些特征的成因。

## 强化学习如何奖励有效求助

作者分别在 SQL、SWE 上微调 Qwen3-32B，使用 LoRA 和 SkyRL，每域 120 个训练任务、30 个留出评估任务。训练中每次提问获得局部奖励，结束时再根据覆盖情况奖励。[§4.4、附录 G](https://arxiv.org/pdf/2604.09408v4#page=8)

设 $d$ 是已发现的不同障碍数，总障碍数为 $k$。把正文式 2 与重复提问惩罚合起来，奖励可以写为：

$$
r_t=
\begin{cases}
+0.3,&\text{本次提问匹配此前未解决的登记障碍},\\
-0.1,&\text{无关，或重复询问已经解决的障碍},
\end{cases}
\qquad
r_{\mathrm{terminal}}=\frac{d}{k}.
$$

$$
R_{\mathrm{episode}}=\sum_t r_t+r_{\mathrm{terminal}}.
$$

原式把终局奖励写成“至少找到一个障碍时取 $d/k$，否则取 0”。由于 $d=0$ 时该比值本来就是 0，这个分段没有额外的数值惩罚。真正区别于从不提问的正向信号来自有效提问和新增覆盖。

以一个说明例子计算：5 个障碍中解决 3 个，另外问了 2 次无效问题，则总奖励为 $3\times0.3-2\times0.1+3/5=1.3$。奖励没有包含代码通过或 SQL 正确性的直接项。它分别鼓励有效提问和覆盖，**不是 Ask-F1 本身，也不是与 Ask-F1 数值等价的表达式**。[附录 G.2](https://arxiv.org/pdf/2604.09408v4#page=19)

### 训练结果与跨域迁移

图 4 标注的域内训练结果如下，单位均为百分数：

| 评估域 | 基础模型 Ask-F1 | 域内训练后 Ask-F1 | 基础模型 pass@3 | 域内训练后 pass@3 |
| --- | ---: | ---: | ---: | ---: |
| SQL | 18% | 46% | 11% | 24% |
| SWE | 4% | 21% | 1% | 7% |

SQL 的两项提升分别为 28、13 个百分点；SWE 为 17、6 个百分点。跨域模型在图中也有提高：SWE 训练后测试 SQL 的 Ask-F1 约为 30%，SQL 训练后测试 SWE 约为 12%，低于各自域内训练结果。[图 4](https://arxiv.org/pdf/2604.09408v4#page=8)

这些结果支持在这两个任务域之间存在正向迁移。它们没有单独排除更熟悉求助工具格式、裁判规则或共享框架的贡献。论文没有提供“只有局部奖励”“只有覆盖奖励”“直接用 Ask-F1”“只奖励任务成功”等对照，因此不能从这张图分离各项奖励的贡献。

附录 G 未给出 LoRA rank、学习率、优化器、训练步数、随机种子、硬件预算或置信区间，也未解释每域 120／30 的实验划分与公开／私有 100／50 的对应关系。图中的百分数不能据此反推准确成功任务数或完整训练配置。

SQL 比较器在只读数据库中执行查询，单次查询超时上限为 300 秒；它比较结果值的计数结构，忽略行序与列序，同形状情况下不依赖列名。数值处理默认按 0.01 分桶，而不是直接检查任意两个数的绝对差是否小于 0.01。这种结果比较也不等同于证明两个查询对任意数据库都语义等价。

另一个需要补齐的环节是 pass@3。README 称 `--passes 3` 可生成论文指标及 `public_metrics` 输出，但本次检查的 CLI 路径与 `hil_bench` 运行包主要生成各轮 pass@1，并对轮次做均值、标准差汇总，未找到 README 描述的同名输出路径实现。复现者应保留每任务三轮结果，明确计算“至少成功一次”的任务集合，不能把轮次平均当作 pass@3。[CLI](https://github.com/hilbenchauthors/hil-bench/blob/a98052f7bcb3a92d6ce1a3c1da20237b8b3d2e8c/hil_bench/cli.py)、[批处理](https://github.com/hilbenchauthors/hil-bench/blob/a98052f7bcb3a92d6ce1a3c1da20237b8b3d2e8c/hil_bench/scripts/batch_runner.py)。

当前 CLI 还设有 SQL 每实例 2.5 美元、SWE 每实例 5 美元的默认成本上限；它们是当前实现的配置默认值，不是论文证明采用的实验预算，也不包括可直接推断的所有裁判托管费用。附录 H 的 token 图反映各模型用量差异，但不能在缺少完整计费设置时换算为精确复现成本。[附录 H](https://arxiv.org/pdf/2604.09408v4#page=20)

HiL-Bench 的实验范围是经过人工改造、确保关键信息不在环境中的任务。它展示了主动发现缺口、向特定工具求助、再执行任务之间的差距，以及训练后两域内的改善。把这些结果应用到其他工作流之前，需要重新确认哪些问题确实只能由人回答、求助协议如何定义，以及任务成功是否仍依赖同样的信息结构。

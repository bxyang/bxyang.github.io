# CAR：为道路场景中的物体补充属性标注

知道图中有一辆车，还不足以描述它正在移动还是停放、是否牵引其他车辆，以及朝向摄像机的哪一面。CAR 在 Cityscapes 已有的图像和物体分割之上增加属性标注：不同类别使用不同的问题列表，标注员结合整幅场景判断目标物体，再汇总多人的答案。首篇论文介绍的是数据构建、分类体系和分布统计，没有给出属性识别模型的训练结果或消融实验。[原文 §1、§4–6](https://arxiv.org/pdf/2111.08243v1)

## 属性预测与物体分类的区别

CAR 把物体所属的类别称为 category，把该物体的具体描述字段称为 attribute。车辆类别可以有外形、用途、运动状态和灯光状态；行人类别可以有可见程度、活动状态、是否携带物品等。即使两个物体的类别相同，其属性也可能完全不同。

这与给所有物体预测同一串二元标签有所区别。CAR 的一个属性通常从多个值中选择一个。例如车辆用途可以是警车、救护车、消防车、工程车辆、其他或无法判断；小型车辆的类型则是另一组取值。“是否有骑乘者”仍然具有是、否这样的选项，只是体系不要求每个属性都变成一个独立的真/假问题。[原文 §2、§4.2](https://arxiv.org/pdf/2111.08243v1)

还有一些字段依赖其他字段。交通标志的类型决定了后续数值的含义：限速牌需要速度值，而普通停车禁令不需要速度值。可移动物体只有被识别为动物时，才需要回答动物是否自行移动。属性体系因此包含类别之间、属性之间的适用条件。

输入也不应只理解成一个裁剪框。判断车辆外形可以主要看局部图像，但判断它是否停放，可能需要车道、路边环境和其他物体作为上下文。论文因此让标注员看到完整图像，并高亮当前目标。图 1 的样例同时展示了自行车、红色交通灯和不同状态的车辆；它们使用不同字段，而不是共享一张固定问卷。

## 选择 Cityscapes 的依据

作者希望复用已有图像和几何标注，为数据增加一层语义信息。选择条件包括足够丰富的类别、车辆和行人之外的交通灯与标志、图像实例分割、3D 框、真实场景和较大规模。他们最终选择 Cityscapes，原因包括已有精细分割、后续发布的 3D 车辆框，以及来自 50 个城市的图像。[原文 §3、表 1、附录 B](https://arxiv.org/pdf/2111.08243v1)

这里需要区分底层资料与 CAR 的新贡献。Cityscapes 原有 5,000 张精细标注图像，另有约 20,000 张粗标注图像；这些数字不是 CAR 已经完成属性标注的图片数。Cityscapes 3D 框来自既有扩展，也不是本文为所有对象重新制作了 3D 标注。

表 1 对 Cityscapes、nuScenes、Apolloscape 和 A2D2 的比较采用了作者重组后的类别定义。例如，原本分开的汽车、公交车和卡车可以合并为中大型车辆，再通过“外形”字段区分。因此，表中的类别数、属性数不总是各项目官方数字。引用量与标注可用性也对应论文撰写时的状态，不是当前数据集能力排名。

附录 B 讨论了 nuScenes 与 nuImages 的属性和分割覆盖。其表 3、4 是对其他数据集的说明，不是 CAR 自己的属性频率。作者在附录中还设想为粗标注图像补充精细掩码；这属于计划，没有在首篇中报告已经完成。

## 实际标注采用五人加权共识

标注流程分为目标定位、属性作答和质量控制三个环节。

首先，系统提供整幅图像、目标类别和目标多边形。问题列表根据类别变化。标注员可以调整亮度、对比度以及多边形显示，避免高亮遮住需要观察的细节。

其次，每个实例由五位标注员参与。原文不是简单的五人等权多数投票，而是根据标注员质量指标汇总结果。系统随机插入已知答案的检查任务，对比标注员的答案与参考答案，形成质量指标；低于阈值的标注员会被排除。Scale AI API 负责发送任务。[原文 §4.1、图 2](https://arxiv.org/pdf/2111.08243v1)

最后，分类问题保留 `Unclear`，允许表达无法判断。它与明确的“No”不同，也与该属性对对象根本不适用不同。后面的代码与数据检查表明，这三种情况在读取和训练时需要分别处理。

论文没有公开质量指标的具体计算、权重到投票结果的公式、过滤阈值、标注员总人数、检查题数量、分歧仲裁规则或总体一致性系数。因此可以确认“有五人和质量加权机制”，不能据此给出一个经过验证的标签准确率，也不能把五人一致当成所有实例的实际状态。

对于动态属性，输入证据还有明确限制：标注界面展示的是图像，本文没有给出利用连续帧测量速度或确认灯光闪烁的流程。移动、停放、闪烁等标签包含标注员根据视觉上下文作出的判断。行人字段中的听觉、视觉或行动相关名称同样是该体系下的视觉标注，不能等同于经过医学验证的个体情况。附录特别说明，“听觉受影响”也包括戴耳机等可能影响环境声音感知的情形。[原文 §4、附录 A.1.3](https://arxiv.org/pdf/2111.08243v1)

## 属性数量、候选值数量和实例数量

论文用两个量描述某个类别的属性空间。设类别 $c$ 有 $n_c$ 个属性，第 $a$ 个属性有 $v_a$ 个候选值：

$$
\mu_c=\frac{1}{n_c}\sum_{a=1}^{n_c}v_a,
\qquad
\pi_c=\prod_{a=1}^{n_c}v_a.
$$

$\mu_c$ 是每个属性平均有多少候选值；$\pi_c$ 是把所有字段的候选值作笛卡尔积后得到的组合数。它们不是模型准确率，也不是实际采样到的不同属性组合数量。特别是存在条件字段时，乘积还会包含不适用或没有独立语义的组合，不能直接当成现实中有效状态的数量。[原文式 1–2](https://arxiv.org/pdf/2111.08243v1#page=7)

### 用车辆类别复算

固定版本的分类体系中，中大型车辆七个属性的候选值数分别为：

$$
(6,12,4,6,4,4,5).
$$

这些数量包含分类字段中的 `Unclear`。因此：

$$
\mu=41/7\approx5.86,
\qquad
\pi=6\times12\times4\times6\times4\times4\times5=138240.
$$

41 是拼接所有属性独热编码后的向量长度；7 是属性字段数；138,240 是可能编码组合数；4,834 才是表 2 中该类别的已标注实例数。这四个量不能混用。

交通标志更能体现组合数的限制。当前分类体系中，“是否电子显示”有 3 个值，“类型”有 15 个值，速度从 5 到 400、步长 5，共 80 个值，于是得到 $\mu=98/3\approx32.67$、$\pi=3\times15\times80=3600$。但代码明确说明，非限速标志的速度值可以任意填写。这个 3,600 因而不是 3,600 种有意义、已经覆盖的道路标志状态。[论文表 2；固定版 `taxonomy_CAR.py`](https://github.com/kareem-metwaly/CAR-API/blob/7199fd085d6efb6ed8b1f0ae4290b2cba321a4bb/taxonomy_CAR.py)

对于天空、人行道这样没有属性的类别，表 2 将 $\mu$ 记为 0、$\pi$ 记为 1。后一项符合空乘积约定，但前一项是表格约定，不能把 $n_c=0$ 直接代入带除法的平均公式。

## 分类体系中的计划与版本差异

附录 A 提供了类别和字段说明，附录 C 则将 Cityscapes 的原始类别映射到 CAR 类别。它们与正文统计并非逐项相同。

例如，正文表 2 的行人有 10 个字段，附录 A 的列表未列可见程度，表 6 写成 9 个；小型车辆正文写 5 个字段，附录表 6 却列 6 个。植被、可移动物体、地面也有字段数量差异。附录把动物单独列为类别，而当前 API 把动物放在可移动物体的类型中，并设置两个条件属性。本文以正文表 2 解释 2021 年统计，以固定代码解释读取格式，不把不同清单合并成一个没有版本说明的标准。

当前 API 的静态物体有七个明确选项，再加 `Unclear`，共 8 个值，与论文表 2 的 7 个不同。其他主要类别的候选值数可以按代码复算出表中的 $\mu$ 和 $\pi$。分类体系因此也需要固定版本，不能仅凭属性名称相同就假设编码长度没有变化。

附录表 5、6 的实例数描述的是原 Cityscapes 标签及其类别映射，例如映射后中大型车辆为 33,208、静态物体为 81,643。它们不是 CAR 当时已经完成的属性标注量，不能代替正文表 2。道路标线虽然写入了分类体系，但原文明确说明没有可用实例分割掩码，因此当时没有完成属性实例标注。[附录 A–C、§5](https://arxiv.org/pdf/2111.08243v1#page=13)

### 实例不重合，但图像重合

训练文件涵盖当前包里的全部 1,722 张图像。因此，验证集的 1,672 张图、测试集的 1,680 张图都与训练集有相同图像路径；验证和测试之间还有 1,642 张图相同。这是当前文件的静态检查结果，说明划分并未保证图像隔离。

这对 CAR 尤其重要，因为 API 直接返回完整图像作为输入。不同划分中的目标实例虽然不同，背景和同图其他物体却可能已经在训练中出现。依照这些文件运行的成绩，应注明是实例划分；如果希望测量对未见图像的泛化，需要另行按图像或城市建立划分，并明确这属于新的评测设置。

首篇结论中关于划分的句子停在“The dataset is divided into”，没有实际给出比例或规模。因此，不能用当前约 80/10/10 的文件记录反向填补 2021 年论文的实验协议，更不能把当前数据检查当成原论文模型存在训练泄漏的证据——该文没有报告训练基线。

### 当前实例和缺失字段的含义

`all.json` 中有 16,507 个中大型车辆、2,759 个小型车辆、11,598 个行人、13,622 个交通标志、5,920 个交通灯和 33,009 个静态物体。天空与人行道另有 252 和 527 条无属性记录。API 默认过滤这两类，因此可用于其属性 Dataset 的记录数为 **101,418**，与原始文件的 102,197 不同。

按当前 taxonomy 检查，文件没有出现分类字段取值超出候选列表的情况。属性字典中有 23,575 次显式 `Unclear`，但它们不是全部不可用标签：还存在未出现的条件字段。具体来说，5,139 个地面实例没有 `Terrain Type`，1,991 个可移动物体没有两个动物字段。它们与仅对 Terrain 或 Animal 适用的条件结构一致，不能直接全部记成漏标错误。

当前包中 13,622 个交通标志只有 107 个的类型是 Speed Limit，其余 13,515 个不是限速标志。由于 API 对非限速标志的速度值没有强制语义，建立速度预测损失或统计速度分布时需要先检查类型；直接把所有速度字段当成道路限速真值会改变任务含义。

## API 如何把一个实例交给模型

`CARDataset` 以 CAR 的 `train`、`val` 或 `test` 文件为入口。单条记录保存图像路径、原始多边形文件路径、对象索引、目标类别、属性字典和多边形顶点。`unique_id` 将前三项用 `::` 连接起来。

读取时先载入整幅 RGB 图像，再由目标多边形生成二值掩码。API 根据多边形包围框裁剪目标图像和掩码，最终返回：

- 全图与目标掩码，用于保留场景上下文和目标位置。
- 裁剪图与裁剪掩码，用于查看对象局部细节。
- 类别 ID、类别名、属性向量和实例 ID。
- 可选的六通道场景实例表示。

示例将图像和裁剪图缩放为 $224\times224$，设置 batch size 8、两个数据加载 worker，以及可选的 `scale=28`。这些是读取示例参数，不是本文训练识别网络时的实验超参数。API 没有定义模型结构、损失、优化器或标准评测器。[`pytorch_dataset_CAR.py`](https://github.com/kareem-metwaly/CAR-API/blob/7199fd085d6efb6ed8b1f0ae4290b2cba321a4bb/pytorch_dataset_CAR.py)

### 编码长度随类别改变

`TaxonomyCoDec` 支持把属性写成混合进位整数，或把各属性的独热向量拼接。后一种表示的长度是：

$$
d_c=\sum_{a=1}^{n_c}v_a.
$$

中大型车辆是 41 维，小型车辆 20 维，行人 38 维，交通标志 98 维。当前实现的 `n_attributes` 则将所有类别的长度相加，得到 265；它不是单个样本固定有 265 个属性，也不是 265 个独立字段。`n_categories` 返回 14，其中包括额外的 `unknown`；分类体系实际定义了 13 个类别，且并非每个类别都在数据中有有效属性实例。

代码按传入属性字典的顺序累积偏移，解码按 taxonomy 的顺序还原。本次公开 JSON 中字段齐全的记录顺序与 taxonomy 一致，但重新序列化或整理数据时仍需保留对应顺序，或显式按字段名称建立偏移。

### 条件字段与批处理需要额外处理

编码器对未出现的条件字段保留全零子向量，而向量解码器要求每个属性块恰有一个 1。本次抽取原始编解码类做了一个不涉及模型的检查：`Ground Type=Road`、省略 `Terrain Type` 时，编码成功，解码却因后者全零而触发断言；`Ground Type=Terrain, Terrain Type=Grass` 的完整记录则可往返转换。因此，“不适用”字段不能直接按普通完整独热属性处理。

另外，`ModelInputItems.collate` 对属性向量直接使用 `torch.stack`。当一个批次同时包含 41 维车辆向量与 38 维行人向量时，长度不同，不能直接堆叠。用于实际训练时，需要同类别分批，或修改批处理以保留变长标签、填充并提供适用性掩码。这里指出的是当前示例代码的形状条件，本文没有执行 GPU 或模型训练来验证修改方案。[编解码实现](https://github.com/kareem-metwaly/CAR-API/blob/7199fd085d6efb6ed8b1f0ae4290b2cba321a4bb/utils_CAR.py)、[批处理实现](https://github.com/kareem-metwaly/CAR-API/blob/7199fd085d6efb6ed8b1f0ae4290b2cba321a4bb/dataclasses_CAR.py)

README 说只需下载 Cityscapes 图像，因为 CAR JSON 已存目标多边形。对普通图像、掩码和属性读取，这与代码相符；但示例启用的可选 `instances_tensor` 会调用 `instances_same_image`，重新打开原 Cityscapes 多边形 JSON，获取整图其他实例。这条路径仍需要 `gtFine` 文件。只下载图像时，应关闭这一可选项，不能把 README 的简述应用到所有配置。

## 首篇没有模型实验与统一评分协议

这篇论文没有报告属性预测准确率、F1、平均精度、召回率或模型间比较；没有训练预算、模型权重、消融、置信区间，也没有用人工过程对照证明加权投票比单人或普通多数票提高多少质量。表 1 是底层数据集选择，表 2 是 CAR 规模与属性组合空间，表 3–6 是附录中的数据和类别映射。

因此，论文能直接支持的是它建立了什么属性体系、怎样组织人工标注、当时报告了什么数据分布，以及怎样读取数据。它没有证明属性预测已经提高自动驾驶决策准确率，也没有测量事故率变化。文中引用的 GlideNet 属于另一个属性预测工作，其网络设计和成绩需要在[GlideNet 页面](/companies/scale-ai/glidenet)单独讨论。

若基于 CAR 建立模型评测，需要另外说明：类别是已知还是由模型预测、使用人工掩码还是预测掩码、是否提供整图上下文、`Unclear` 是否计入评分、条件字段如何屏蔽，以及对类别和属性采用何种平均方式。按所有有效字段汇总准确率会偏重字段多、实例多的类别；先按属性或类别平均则是另一种权重。这些都是后续实验应明确的设计，不是首篇已经规定的官方指标。

## 数据入口与可复现范围

CAR-API 仓库采用 MIT 软件许可；Cityscapes 图像则受其自身条款约束，需要注册下载，公开条款限定非商业用途并限制再分发。代码的 MIT 许可不能替代底层图像许可。当前属性压缩包来自 README 的独立下载链接，没有和 Git 提交绑定的版本清单，本次用文件哈希固定审计对象。[API 许可](https://github.com/kareem-metwaly/CAR-API/blob/7199fd085d6efb6ed8b1f0ae4290b2cba321a4bb/LICENSE)、[Cityscapes 条款](https://www.cityscapes-dataset.com/license/)

依赖文件列出 PyTorch `~=1.8.1`、torchvision `~=0.9.1`，以及 Pillow、NumPy、cityscapesscripts、scaleapi 等，其他多数依赖没有精确锁定。读取已下载的 JSON 不需要派发新的 Scale 标注任务；本文也没有调用任何付费标注接口。

使用这批数据前，需固定代码提交和压缩包哈希，核对实例与图像划分，保留类别条件和未知状态，并确认全图、局部图像及掩码的变换保持一致。若要复现 2021 年的统计，还需要当时约 3.27 万实例的原始快照；当前 10.2 万实例的下载包不能直接替代它。

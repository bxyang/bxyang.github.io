# Agentic Rubrics：先理解代码仓库，再制定补丁评审标准

## 1. 摘要翻译

以下按 [arXiv v1 摘要](https://arxiv.org/abs/2601.04171v1)顺序翻译。原文由 Mohit Raghavendra、Anisha Gunjal、Bing Liu 和 Yunzhong He 撰写，采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)；中文为翻译版本。

验证对于改进智能体至关重要：它既为强化学习提供奖励信号，也能通过测试时扩展带来推理阶段的提升。尽管验证十分重要，软件工程智能体场景中的验证通常依赖代码执行，而环境配置的额外开销使其难以扩展。补丁分类器和启发式方法等可扩展替代方案虽然存在，但它们与代码仓库上下文的联系较弱，也较难解释。

为此，我们研究 Agentic Rubrics：一个专家智能体与代码仓库交互，创建基于上下文的评审标准清单，随后依据清单为候选补丁评分，而不需要执行测试。在 SWE-Bench Verified 的并行测试时扩展评估中，Agentic Rubrics 在 Qwen3-Coder-30B-A3B 上取得 54.2% 的分数，在 Qwen3-32B 上取得 40.6%，相比我们所比较的最强基线至少提高 3.5 个百分点。

我们进一步分析了评审标准的表现，发现其评分与真实测试结果一致，同时也能指出测试没有覆盖的问题。消融研究表明，智能体主动收集上下文，对于生成贴合代码仓库且无歧义的标准至关重要。这些结果共同表明，Agentic Rubrics 能为软件工程智能体提供高效、可扩展且细粒度的验证信号。

## 2. 研究背景与相关研究

软件工程智能体可以为同一个问题生成多个代码补丁，但如何选出较好的一个仍然困难。运行测试能够提供直接证据，却需要配置代码仓库和执行环境，而且测试不一定覆盖所有要求。直接让模型给补丁打分更方便，但如果评审者不了解仓库，很容易依赖表面形式，或提出不适用的要求。

Introduction、Preliminaries 与 Related Work 讨论了测试、补丁分类器、代码相似度和语言模型评审等已有验证方式。SWE-Agent、OpenHands 等框架让智能体能够探索仓库并生成候选解法；测试时扩展则通过生成多个候选、再由验证器选择，利用额外推理计算提高成功率。

评审清单（rubric）提供了另一种组织验证的方法：把整体正确性拆成可解释的具体要求。论文与已有 rubric 评估及奖励研究的区别，是在制定清单之前，先让智能体主动查看仓库。这样，标准可以依据相关函数、接口约定和项目惯例，而不只依据问题描述中的几句话。[论文第 1—2 节及第 6 节](https://arxiv.org/pdf/2601.04171v1)

## 3. 核心贡献

**核心问题。** 在不逐个执行候选补丁测试的情况下，建立既了解代码仓库、又能解释判断依据的验证器，提高候选选择的质量。

**核心方案。** 评审智能体先探索仓库，生成按文件改动、需求匹配、修改完整性及运行行为组织的加权清单。另一个评审步骤根据问题、补丁和清单逐项判断，再汇总得分，选出最高分补丁。清单可以检查修改是否满足要求，也可以检查是否引入不必要的改动或破坏既有约束。

“无需执行”主要指清单生成之后的补丁评分阶段。前面的仓库探索仍然需要工具与环境，实验中判断最终任务是否解决也仍使用真实测试，因此不能称为整个流程都不需要代码执行。[论文第 3 节](https://arxiv.org/pdf/2601.04171v1)

**主要结论。** 在每道题生成 16 个候选、最终选择一个的设置中，Qwen3-32B 的解决率为 40.6%，比最强比较基线高 3.5 个百分点；Qwen3-Coder-30B-A3B 为 54.2%，比对应最强基线高 4.0 个百分点。这些是候选选择后的结果，并非模型单次生成的能力。

论文分析显示，主动探索仓库有助于生成具体、可判定的标准，评分也能提供比测试通过或失败更细的信息。但清单仍可能过度限定实现方式、重复要求或与测试不一致。本文主要验证测试时的候选选择，将这类清单直接用作强化学习奖励仍是后续方向，不能把它写成已经验证的训练收益。[论文第 4—5 节及第 7—8 节](https://arxiv.org/pdf/2601.04171v1)

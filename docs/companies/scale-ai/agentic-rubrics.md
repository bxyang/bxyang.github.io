# Agentic Rubrics 精读：先读懂仓库，再用评分清单选择补丁

同一个软件问题，编码 agent 可以提交十几份不同补丁。选择时只读需求和 diff，容易漏掉仓库里的约束；为每个补丁部署环境、运行新生成的测试，又会增加开销。Agentic Rubrics 将这两部分分开：专家 agent 先探索出错前的仓库，写出针对该问题的评分清单；另一个模型再用清单逐项判断候选补丁。SWE-bench Verified 的 500 个问题上，从每题 16 个候选中选择，Qwen3-32B 与 Qwen3-Coder-30B-A3B 分别达到 40.6% 和 54.2% 的解决率，比所比的最佳普通补丁分类器高 3.5 和 4.0 个百分点。[原文 §3–4，图 2](https://arxiv.org/pdf/2601.04171v1)

## 两个阶段的上下文与权限不同

### 生成阶段可以浏览仓库

专家模型通过 SWE-Agent 的工具搜索文件、查看代码和已有测试，追踪类、函数及调用关系。输入是 issue／PR 的问题说明和修复前的仓库快照；不能访问隐藏评测测试、标准补丁或 git 历史。它的任务是理解修复应该满足什么条件，不是先写一份修复再把它当作唯一答案。（§3.1、§3.3）

附录 A.10 的提示要求只新增 `rubrics.yaml`，不能修改其他源文件。agent 要检查 YAML 能否被 `yaml.safe_load` 解析，必要时修正格式后再提交。默认 rubric 专家为 Claude Sonnet-4.5，最多 30 轮；每轮包含简短计划说明和一次工具调用。框架每五轮提醒剩余预算，便于在自动提交前留下完整文件。（A.7、A.10）

这一步仍需要仓库和沙箱。所谓 execution-free 指后续补丁评分无需执行待评补丁或其测试，并不是整个系统不调用 shell、不准备仓库，或者不发生任何代码执行。YAML 解析检查本身就属于前期操作。

### 评分阶段只读取指定材料

评分模型接收问题说明、rubric 和最终补丁，不接收编码 agent 的完整对话、推理说明或工具轨迹。作者这样做，是为了减少评分被候选模型自述影响，并让各验证方法使用可比较的输入。

附录 A.11 给出一次输出多个条目分数的 JSON 提示。每个条目必须尽量自足，因为评分模型不能为了补齐背景再浏览整个仓库。具体类名、路径、接口和条件，实际上承担了把仓库信息带到轻量评分阶段的作用。

如果专家没有生成要求的文件，或 rubric 无法解析，论文将对应验证信号记为 0。后续并列最高分的候选怎样打破平局、评分 JSON 缺字段时怎样处理，没有完整实现可供核对；这些都会影响精确复现。

## 四类条目与加权二元评分

| 维度 | 生成提示的目标数量 | 检查内容 |
| --- | ---: | --- |
| File Change | 4–8 | 修改位置、范围和充分性，是否引入无关变化 |
| Spec Alignment | 3–6 | 是否满足问题描述中的功能与接口要求 |
| Integrity | 3–6 | 是否削弱测试、绕过验证、改变不该改变的公共接口 |
| Runtime | 3–6 | 从补丁推断边界行为、回归风险、资源和错误处理 |

这些数量是提示目标，不是所有模型都严格遵守的固定条目数。Runtime 也是文字判断：例如检查空值路径是否保留原来的语义，不等于实际执行所有边界输入。（§3.1，A.10）

第 $i$ 项由文本 $t_i$ 和重要性权重 $w_i\in\{1,2,3\}$ 构成，分别表示可取、重要、必须。对候选补丁 $P$，judge 给出二元结果 $s_i(P)\in\{0,1\}$，总分为：

$$
S(P)=\frac{\sum_i w_i s_i(P)}{\sum_i w_i},\qquad S(P)\in[0,1].
$$

这不是先在四个维度内平均、再把四类等权平均；条目数量与权重共同决定某一维度的实际影响。提示要求条目原子化、不重叠，避免重复计分，但没有给出自动证明条目互斥或覆盖完整的程序。

用一个说明例子：三项权重为 3、2、1，补丁分别满足、不满足、满足，总分为 $(3+0+1)/6=2/3$。这里的中间分来自不同条目的组合，不是某项得到三分之二的部分信用。

权重 3 也不构成一票否决。一个必须项失败，仍可能被其他得分抵消；论文没有把所有必须项通过设为选择补丁的前置条件。总分更高意味着该清单下更合意，不是已经校准的正确概率。

## 从 16 个候选中选一个，最终仍看隐藏测试

每个生成模型为 500 个问题分别生成 16 条独立轨迹，即名义上每个模型 8,000 条候选轨迹，两模型共 16,000 条。轨迹不是训练样本，也不保证每条都产生独特或有效的补丁。（§3.2）

| 角色 | 主实验设置 |
| --- | --- |
| 编码生成器之一 | Qwen3-32B，论文注明 Instruct，最多 30 轮 |
| 编码生成器之二 | Qwen3-Coder-30B-A3B，最多 50 轮 |
| 候选采样 | temperature 1.0，每题 16 次 |
| 专家产物生成 | Claude Sonnet-4.5，通常 30 轮 |
| 补丁评分 judge | GPT-5，low reasoning |
| 最终解决判定 | 同时通过隐藏 Fail-to-Pass 和 Pass-to-Pass 测试 |

Fail-to-Pass 检查应被修好的行为，Pass-to-Pass 检查此前正常的行为没有回归。隐藏测试只用于报告最终表现，不能泄露给正常生成或评分阶段。

设任务 $d$ 的候选集为 $\mathcal P_{d,K}$，评分器选择：

$$
P_d^*=\arg\max_{P\in\mathcal P_{d,K}}S(P),\qquad
\mathrm{Best@}K=\frac1{500}\sum_{d=1}^{500}\mathbf 1\{P_d^*\text{通过隐藏测试}\}.
$$

这是对论文选择规则的展开。Oracle Pass@K 则假设知道真实测试结果，只要候选中有一份正确补丁就能选中，因此是这批候选的上界；Random 是从候选中均匀随机挑一份，不能理解为执行 K 份后任意一份成功就算成功。

$K<16$ 时，作者从既有候选进行 100 次采样试验，平均得到曲线。因此这些重复主要衡量候选子集选择的变化，不等于重新运行了 100 次完整的 16 候选生成实验。主文没有完整说明曲线阴影与各表误差的统计构造。

## 主结果与基线各自使用的信息

| 方法 | Qwen3-32B Best@16 | Qwen3-Coder Best@16 |
| --- | ---: | ---: |
| Oracle | 51.4% | 65.6% |
| 随机选择 | 22.6% | 39.6% |
| Self-Consistency | 33.2% | 47.6% |
| Patch Classifier | 37.1% | 50.2% |
| Agentic Tests | 33.6% | 49.0% |
| Agentic Patch Similarity | 35.0% | 49.6% |
| Agentic Rubrics | **40.6%** | **54.2%** |

数值来自图 2 左表。Self-Consistency 用 Python `difflib.SequenceMatcher.ratio()` 比较 unified diff 字符串，挑选与其他 $K-1$ 份平均最相似的补丁；它不是执行行为的一致性投票。Patch Classifier 直接判断问题与补丁，缺少额外仓库产物。

Agentic Tests 先写独立 `test_issue.py`，再为候选执行生成的测试。附录提示要求至少十个用例，输出逐例状态并处理异常；生成的测试与最终隐藏测试不是一套。Agentic Patch Similarity 则先生成代理参考补丁，由 LLM 按 1–5 分判断功能接近程度；提示中虽然称它为 golden answer，但主实验实际使用的是专家生成补丁，不是真实标准答案。（§3.3、A.10）

Rubrics 相对分类器提高 3.5 和 4.0 个百分点，但距离 Oracle 仍差 10.8 和 11.4 个百分点。这说明候选集中已经存在的一部分正确补丁，仍未被评分器选中；54.2% 也不是每次单独生成一份补丁就有这个成功率。

原文 §4.1 把 Qwen3-32B 相对代理参考补丁的改善写为 4.6 点，但按主表 $40.6-35.0=5.6$ 点。附录成本表另报该基线 36.6%，相应差值又为 4.0 点。本文分别保留主表与成本实验，不混成一个统一数值。

## 评分与真实正确性的关系

对 Qwen3-32B 的候选，rubric 分数预测隐藏测试通过与否，ROC-AUC 为 0.886，PR-AUC 为 0.722。图 3 中，通过测试的补丁较集中在高分区，未通过者分布更广。图 4 显示，未通过者经常在修改范围、需求满足和运行行为上失分，但完整性条目仍可能得高分。（§4.2.1）

AUC 衡量排序区分能力，不是 88.6% 的分类准确率，也不意味着分数为 0.9 的补丁有 90% 概率通过。论文没有报告把总分校准为正确概率的实验。PR-AUC 还受正例比例影响，不能与其他候选生成器的数值直接横比。

附录 A.1 将人工标准补丁也交给 rubric 评分。各专家生成清单时，对这些补丁的平均加权分数如下：

| Rubric 生成模型 | 标准补丁平均得分 |
| --- | ---: |
| Opus-4.5 | 0.8658 |
| GPT-5 | 0.8413 |
| Sonnet-4.5 | 0.8233 |
| Gemini-3-Pro | 0.8082 |
| Qwen3-Coder-30B-A3B | 0.8037 |
| Meta-CWM | 0.8015 |
| Qwen3-32B | 0.6729 |

标准补丁通过测试却不一定得到满分，常见原因是清单对具体修改路径过于严格。这个实验说明对参考解的兼容程度，不是证明越宽松、越高分的清单必然越善于区分错误补丁。（表 3，图 8）

## “测试没发现的问题”来自怎样的分析

作者选取 100 个问题，用 GPT-5 medium reasoning 对 rubric 判断进行效用分类。分类时可见问题、候选补丁、标准补丁和标准测试；这些额外信息用于**事后分析**，不属于正常补丁选择的输入。分类目录由人工查看失败模式后制定，但逐项标签由模型生成，不是 100 位人类专家审核。（§4.2.2，A.6、A.12）

以总 rubric 分数 0.7 为接受阈值，论文报告：

| 分析条件 | 模型标为高效用 | 模型标为低效用 |
| --- | ---: | ---: |
| rubric 与测试判断一致 | 78% | 22% |
| 测试通过，但 rubric 总分低于 0.7 | 54% | 46% |

这里的分母是相应条件下分析的 rubric 判断／失败条目，不是全部 500 个问题，也不是“54% 的隐藏测试有错误”。没有公开各组条目总数、同题聚类统计或人工复核一致性，不能由 100 个问题直接推算准确的条目计数。

高效用包括遗漏根因、遗漏边界和 API 破坏；低效用包括指定唯一修法、冗余条目、评分错误以及与参考规范冲突。54% 是模型认为这些批评有实质依据的比例，不是已经新增测试证实 54% 的补丁存在运行错误。

图 5(a) 的小标题只写测试通过且 rubric 高分，但正文、图内标题及 A.12 提示都包含“双方接受”与“双方拒绝”。本页按较完整的正文口径解释，同时保留这一标注不一致。A.12 公开的提示详细覆盖高一致性情形，没有单独列出低一致性分析的完整对应提示，后者不能仅凭同一模板完全重现。

## 两类真实样例同时显示用途与局限

### Matplotlib：不崩溃仍可能改变布局

`matplotlib__matplotlib-26291` 涉及 inset axes 在 `bbox_inches='tight'` 保存时的异常。候选补丁遇到没有 renderer 或相关异常时，直接返回零大小边界框。论文报告该补丁通过隐藏测试；rubric 则指出，它可能没有保留嵌入坐标轴的正确位置、大小和紧凑保存语义。（A.8–A.9）

这类检查试图区分“让报错消失”与“恢复预期行为”。但附录没有新增可执行反例或修复前后图像；本文引用的是作者的代码分析，不是本次运行确认的视觉回归。

### 同一清单也可能过度规定修改位置

`matplotlib__matplotlib-25332` 的候选在 `Grouper` 中增加序列化方法。有一项 rubric 要求必须修改 `figure.py`，另一项却允许在 `Grouper` 或 Figure 的序列化方法中修复。前者会惩罚后者明示允许的路径。另有条目要求新增测试，而候选修复提示明确不要求修改测试。（A.9–A.10）

这说明检查项写得具体并不自动等于正确。提示中的“互斥且覆盖完整”“避免重复计分”只是目标，生成结果仍需要审查。附录第三例 Django `QuerySet.ordered` 也体现了这一张力：检查实际有序状态是否与 SQL 一致有语义价值，但限制到某文件某几行的条目可能把某一种实现当作唯一正确路径。

## 仓库上下文、生成模型和评分模型的消融

### 去掉仓库访问

固定 Sonnet-4.5，仅从问题说明生成清单，Qwen3-32B 的 Best@16 下降 4.0 点，Qwen3-Coder 下降 1.4 点。表 1 给出的具体变化，是把“修改处理比较运算的路径”变为指定 `EvaluateFalseTransformer` 的 `visit_Compare`，或定位 `transforms.py` 的 `KeyboardTransform`。（§5.2）

这支持仓库上下文在所测设置中有帮助。它没有单独控制工具轮数、输入 token、条目数量和每个生成决策，因此不能把全部收益精确归因于某一种搜索工具。

### 更强的 rubric 生成器

图 6 显示，固定 Qwen3-Coder 候选与 GPT-5 low judge，前沿编码模型生成的 rubric 最终约为 54%，部分开放编码模型约为 45%，Qwen3-32B 约为 43%。这些是图文给出的近似范围，不是所有型号精确相同的分数。

Sonnet-4.5 通常生成二十多项，Qwen3-32B 与 CWM 约十项；Gemini 的数量与表现关系则不完全符合这一趋势。条目数、内容、工具使用和格式成功率一起变化，没有固定质量只增加条目数的实验，不能认定“写得越多就一定越准”。

图 9 的可解析比例，Sonnet-4.5 为 99.4%、Gemini-3-Pro 为 96.8%、Qwen3-32B 为 74.6%、Meta-CWM 为 69.4%。A.2 正文把 Sonnet 写成 97.8%，与图 9、图 10 的 99.4% 不同；此处使用两张图一致的数字并注明差异。格式有效也不意味着条件正确。（A.2）

### 改变 judge 的推理预算

| Judge | Best@16 |
| --- | ---: |
| GPT-5-mini | 52.6 ± 2.20% |
| GPT-5 low | 54.2 ± 2.22% |
| GPT-5 medium | 54.3 ± 2.25% |

表 2 标题明确是 Qwen3-Coder 候选，§5.3 却写 Qwen3-32B；本文按表题及与主结果对应的 54.2% 解释。表内 ± 没有清楚定义，不能指定为置信区间或据此宣称 high 显著优于 low。点估计从 low 到 high 提高 0.8 个百分点，论文也未给这些档位的完整成本对照。

## 蒸馏训练教会模型生成清单，不是执行 RL 修复

作者将 Qwen3-32B 分别训练成两种验证组件。（§5.1.1）

| 训练目标 | 数据 |
| --- | --- |
| 补丁分类器 | 从 R2E-Gym 抽取 2,000 个问题，收集 4,696 份带测试标签的样本，正负大致均衡；候选来自 Sonnet-4.5 与 Qwen3-32B |
| Agentic rubric 生成器 | 2,000 条 Sonnet-4.5 生成清单的完整 agent 轨迹，没有加入学生模型自己生成的 rubric 轨迹 |

两者均使用 AdamW、学习率 $10^{-5}$、cosine 调度、batch size 32、两个 epoch，在四台各八张 H100 的节点上训练。分类器输出 YES／NO，验证时提取相关 token 概率；清单生成器学习工具使用和产出结构文件，再接 rubric 评分流程。

可用监督学习的一般形式解释后一目标：

$$
\mathcal L_{\mathrm{SFT}}=-\sum_{t\in A}\log p_\theta(y_t\mid y_{<t},\text{任务与已见工具返回}).
$$

这是说明性的自回归目标，$A$ 表示参与损失的输出位置；论文没有公开具体 loss mask、截断长度、归一化或多轮打包方式，不能把上式当作已核对训练代码。2,000 条长工具轨迹与 4,696 条分类样本的 token 和信息量也不同，不能说两种方法严格使用等量监督或训练计算。

图 7 的清单 SFT 曲线高于未训练清单生成器及分类器，但未提供逐点数值表。图 10 给出更明确的格式变化：Qwen3-32B 可解析率从 74.6% 提升到 88.8%，解析错误从 18.2% 降至 3.6%；未生成文件的比例由 7.2% 变为 7.6%，因此不是所有失败类型都减少。训练后条目数接近教师，也仍未达到教师 99.4% 的文件成功率。

附录 A.5 的混合验证器还将 rubric 与生成测试结合，图 11 显示可进一步改善选择。原文只称简单聚合，没有给完整归一化、组合权重和数值表；不能补写为一个已确定的 50:50 加权公式，也不能将混合方案继续称为免测试执行。

## 成本是每题固定产物加每候选评分

附录 A.3 的成本按全数据集平均，产物每题生成一次，评分则按候选数增加：

$$
C_{\mathrm{verify}}(K)=C_{\mathrm{artifact}}+K\,C_{\mathrm{grade}}.
$$

| 验证方式 | 每题产物成本／美元 | 每候选评分成本／美元 | 报告的平均 API calls | $K=16$ 合计／美元 |
| --- | ---: | ---: | ---: | ---: |
| 代理参考补丁 | 0.640 | 0.006 | 48.5 | 0.736 |
| 生成测试 | 0.499 | 0.001 | 29.2 | 0.515 |
| Rubrics | 0.245 | 0.003 | 22.9 | 0.293 |

例如 rubric 为 $0.245+16\times0.003=0.293$ 美元。产物成本按整条专家轨迹的输入输出 token 计，测试评分成本则包含在 Modal 创建沙箱、应用补丁和执行测试；API calls 列没有进一步逐环节拆分。（表 4）

这不是一次成功修复的总成本：没有加上 16 份候选的生成、全部隐藏测试评测和训练成本，也不是当前 API 价格。Rubric 每候选评分 0.003 美元本身还高于该表测试执行的 0.001 美元；其 $K=16$ 总成本较低，主要与专家产物较便宜有关，不能推成任意候选规模都更省。

成本表的代理参考补丁使用 50 步，其他方法 30 步，且该行 Best@16 为 36.6%；主实验 §3.3 统一写 30 轮、图 2 对应行 35.0%。这至少意味着成本分析与主表不能当作完全同预算的同一条运行记录。论文未提供逐任务成本、失败重试、缓存设置、延迟分布和统一美元预算下的性能曲线。

## 结论的适用范围

论文支持在固定 SWE-bench Verified 候选池中，用预先收集的仓库上下文改善免执行补丁选择。它同时表明，合成清单会出现过度规定、规则冲突与评分错误，不能把高分当作免除测试和代码审查的凭据。

研究尚未验证实际 RL 训练中的奖励投机、随策略变化的评分稳定性，以及多步轨迹如何分配信用；也没有在全新私有仓库和不同语言生态上给出同样的结果。现有证据分别对应候选选择、与测试的排序一致性、模型效用判断、格式稳定性及 SFT，不宜合并成“已证明可替代全部软件验证”的结论。

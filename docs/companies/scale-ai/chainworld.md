## 评测从单项任务延长到持续会话

OSWorld 的原子任务包含初始环境、用户指令、准备动作和结果验证器。它可以检查 agent 是否在某个应用中完成指定操作，但独立运行时通常不要求它继续管理后续目标。

ChainWorld 保留这些任务的原始内容，改变它们的组合和执行过程。论文图 2 的真实例子包含两项：先处理一份演示文稿第 2 页中过暗的图片，将调整后的图片保存为桌面的 `background.png`；再把另一份演示文稿保存为桌面的 `pre.pptx`。两项指令各自附上源文件路径，避免“这份幻灯片”之类指代表达混淆。

这不是要求 agent 执行 2–4 次鼠标点击。每个链节点都是一项完整 OSWorld 任务，可能需要许多观察与操作。它也不要求每条链都形成前一产物作为后一输入的严格流水线：同一个用户会话中相互兼容的多项工作也可以入选。

相比重新人工编写长任务或让 LLM 自由生成任务，组合已有任务可以复用已定义的环境和验证器。但原本能独立完成的任务，并不天然能够拼接。前一任务可能关闭后一任务需要的进程，后一任务的准备动作也可能覆盖前一任务要交付的文件。构建方法围绕这些约束展开。

## 从原子任务到有方向的兼容图

### 静态记录和语义补充

论文从 369 个 OSWorld 任务开始，排除 8 个 Google Drive 任务，以匹配实验中的 no-Drive 环境，留下 361 个构建候选。其余任务没有由 LLM 再做一次全局淘汰，而是在组合时接受筛选。

每个任务首先从 JSON 中提取静态信息：来源应用、关联应用、快照、指令、准备动作、文件与窗口写入、进程终止或清理操作，以及验证器会读取的状态。之后使用 Opus 4.7 补充所需登录服务、预先存在的文件、系统状态、预期完成状态、用户目标、网络依赖和破坏性意图等语义字段。这些字段用于构建任务链，不作为评测 agent 是否完成任务的答案。

代码中的 `terminal_only` 指无法正常完成、应以终止或不可行判断结束的任务类型，并不是“只使用终端命令的任务”。它可以出现在链尾，不能再带一个后续任务。相关判断见 `profiles/static_extract.py`、`compatibility/predicate.py` 与 `compose/validate.py`。

### A 后面能接 B，不代表 B 后面能接 A

图的节点是原子任务，边 $A\rightarrow B$ 表示 B 可以在 A 之后继续执行。当前代码的兼容分数从 0.5 开始：触发硬约束则拒绝，否则叠加软惩罚和正向分数，并裁剪到 0–1。它是规则排序分，不是经过校准的执行成功概率。

| 规则层 | 示例 | 作用 |
| --- | --- | --- |
| 硬拒绝 | 初始快照不兼容；不可行任务后仍接任务；前项关闭所需进程且后项不重启 | 排除明显无法延续的组合 |
| 软惩罚 | 文件写入与后项验证器读取重叠；浏览器历史或标签状态冲突；耗资源应用重叠 | 降低可能互相干扰的组合优先级 |
| 正向分数 | 同应用连续工作；相关应用有交集；前项提供后项所需状态或文件 | 提高具有衔接关系的组合优先级 |

例如当前静态规则对同来源应用加 0.10，对前项写入路径与后项验证器读取重叠减 0.10。语义规则也会调整分数，所以不能只凭应用名称推算完整得分。[固定规则表](https://github.com/vsiu-ucsc/os_world_chained_review/blob/aa26530bbe34ae84649a7252993bb6c59dfe2d49/chain_discovery/compatibility/rules.py)

论文强调快照兼容；当前代码还把 `multiapps`、`base_setup` 当作通配快照，并合并 `vs_code`/`vscode` 等别名。因此“兼容”不等于所有原任务快照字符串完全相同。本次在发布数据中发现 144 条链的原任务含多个快照字符串，不能简单把它们判为违反构建规则。

### 搜索先确定任务顺序，LLM 再判断会话是否合理

Beam search 沿有向图扩展，目标为链长 2、3、4 与底层应用数 1、2、3 组成的九个格子。搜索禁止同链重复任务，保留满足目标形状的候选；累计兼容分和应用覆盖奖励用于排序。任务顺序在提交 LLM 前就已固定。

随后，Opus 4.7 读取任务 ID、来源应用、指令、终止标记和简短语义摘要，返回链标识、一句会话描述、风险备注、身份一致性标签和 1–5 分自然度。身份一致性只问这些请求能否合理地来自同一位用户，允许一般的上下文切换。它不要求所有任务围绕一个紧密主题。

实际发布链均为 `identity_consistent=true`。自然度用于描述，没有采用“至少 3 分才接受”的门槛：发布数据有 43 条得 2 分。仓库方法文档仍有低于 3 分淘汰的旧表述，而命令行默认 `--min-naturalness=0`，关闭这项附加筛选；本文依据当前代码与数据说明。

## 有限判定预算的分配与整链检查

构建器希望把有限 LLM 调用分配给兼容且覆盖不足的候选。当前 `build_beam.py` 为每个应用记录已接受数 $s_a$ 和已判定数 $n_a$，使用 Beta(1,1) 先验对应的后验均值：

$$
\hat p_a=\frac{1+s_a}{2+n_a}.
$$

这是某应用参与的候选通过构建筛选的经验估计，不是 agent 完成该应用任务的概率。候选 $c$ 的应用集合记为 $A(c)$，其应用、快照和“链长×应用数”格子的覆盖缺口相加为 $G(c)$，则代码排序量可写为：

$$
G(c)=\sum_{e\in E(c)}\max\left(0,1-\frac{N_e}{T_e}\right),
\qquad
R(c)=\sqrt{G(c)}\left(\frac{1}{|A(c)|}\sum_{a\in A(c)}\hat p_a\right)S(c).
$$

$N_e$ 是该覆盖维度已有数量，$T_e$ 是目标数量，$S(c)$ 是累计图兼容分。缺口越大、预计接受率越高、兼容分越高，候选通常越靠前。源码虽使用 UCB 命名，但探索系数设为 0，实际使用后验均值，不能据此套用标准 UCB 的后悔界。

说明示例：某应用已判定 8 次、接受 6 次，则 $\hat p=7/10$。如果候选只涉及这个应用，$G=4$、$S=1.2$，排序量为 $2\times0.7\times1.2=1.68$。这里的链分数可以超过 1，因为它累加多条边；1.68 也不是概率。

整链验证继续检查累积状态。例如第一项关闭的进程，即使第二项不用，第三项需要时仍要检查中途是否恢复。验证还限制同链多个破坏性意图任务。失败时从尾部删除一项，重试较短前缀，最短保留两项。

论文概述按“判断后验证”叙述部分流程；固定代码 `_judge_validate_record` 实际先验证及裁剪，再做集合去重，然后向 LLM 提交裁剪后的链，最后再次去重。它以静态任务信息检查规则，没有在构建阶段自动执行一遍完整桌面工作来证明成功可达。因此，静态验证通过不等同于完成了端到端运行验收。

[构建与排序实现](https://github.com/vsiu-ucsc/os_world_chained_review/blob/aa26530bbe34ae84649a7252993bb6c59dfe2d49/chain_discovery/corpus/build_beam.py)。

去重采用任务集合包含关系：若新链任务集合是已接受链的子集或相同集合，即使顺序不同也会被拒绝；接受更大的集合时可以移除旧子集。但不同链允许共享多个原子任务，不能把所有链视为互不重叠的内容样本。

## 两种执行协议的状态、预算与验收

两种协议使用相同任务序列、Ubuntu Docker 桌面、1920×1080 截图观察和 pyautogui 动作空间。区别不止是用户消息数量。

| 项目 | 单轮 Single turn | 多轮 Multi turn |
| --- | --- | --- |
| 指令 | 一次给出有序的全部任务，附确定性的文件路径信息 | 每次只给出下一项任务 |
| 初始化 | 一个初始快照，拼接所有任务的准备动作 | 第一项恢复快照；后续在已有桌面状态上应用各自准备动作 |
| 状态 | 一段会话中持续变化 | 跨任务保留桌面状态，不再次恢复快照 |
| 论文预算 | 长度 $n$ 的链最多 $75n$ 步，自由分配 | 每项最多 75 步，不能把未用步数转给下一项 |
| 验收时点 | 全部操作结束后，统一检查各项结果 | 每项结束立即检查并记录，再进入下一项 |
| 整链成功 | 最终状态满足全部任务验证器 | 每一轮记录的验证结果都成功 |

长度 2、3、4 对应 150、225、300 步总预算上限。相同总上限不代表相同资源分配：单轮可以把大部分预算用在较难的一项，多轮每项封顶。

**评分时点也会影响可比性。** 说明示例：第一项成功保存文件，第二项后来修改了它。多轮已记录的第一项成绩不会重新撤销；单轮会在最终状态检查该文件。论文明确说明后续任务可以改变先前已评分的状态。因此，结果不能完全归因于“分次告诉模型更容易理解”，它还包含准备动作时机、预算分配和结果验收的差别。

论文报告每个“模型×链×协议”只运行一次，完整设计对应 $4\times347\times2=2,776$ 个运行组合。模型为 GPT 5.5、Opus 4.7、Kimi 2.5、Gemini 3.1 Pro；Kimi 因 API 约束只保留一张截图的图像历史。其他模型的完整端点快照、解码参数和运行包装器没有随本仓库完整发布，不能把名字相同视为输入历史与配置完全相同。

## 整链完成率与局部任务成功率

设链 $i$ 长度为 $n_i$，其第 $j$ 项是否成功为 $z_{ij}\in\{0,1\}$。论文的两个指标可表示为：

$$
\mathrm{ChainCompletion}=\frac{1}{M}\sum_{i=1}^{M}\prod_{j=1}^{n_i}z_{ij},
\qquad
\mathrm{TaskSuccess}=\frac{\sum_i\sum_jz_{ij}}{\sum_i n_i}.
$$

前者按链等权，一项失败即整链失败；后者按任务位置计数，长链贡献更多分母。这里任务成功仍按两种协议各自的评分时点判断。单轮通过原任务对应的验证器分组恢复局部成绩，多轮读取各轮分数。[论文 §3.2](https://arxiv.org/pdf/2606.21654v2)

表 1 原始结果如下。整链列的“±”为论文报告的链重采样 bootstrap 95% 区间形式；不是重复运行的标准差。

| 模型 | 单轮整链 | 多轮整链 | 单轮任务成功 | 多轮任务成功 |
| --- | ---: | ---: | ---: | ---: |
| GPT 5.5 | 0.15 ± 0.04 | 0.31 ± 0.05 | 0.49 | 0.63 |
| Opus 4.7 | 0.11 ± 0.03 | 0.17 ± 0.04 | 0.32 | 0.50 |
| Kimi 2.5 | 0.05 ± 0.02 | 0.10 ± 0.03 | 0.23 | 0.41 |
| Gemini 3.1 Pro | 0.03 ± 0.02 | 0.02 ± 0.02 | 0.18 | 0.23 |

按报告值，GPT 5.5 多轮整链完成率比单轮高 16 个百分点，Opus 高 6 个百分点，Kimi 高 5 个百分点，Gemini 低 1 个百分点。四个模型的局部任务成功率都更高，但“做完更多任务”和“做完全部任务”仍是不同结果。

作者对相同任务链的两种结果做精确 McNemar 检验，前三个模型的多轮增益均为 $p<0.004$，Gemini 没有相应增益证据。该检验关注两协议结果不一致的配对链，而不是把两组独立样本均值比较。论文未列完整配对计数、bootstrap 重采样次数或多次运行数据，本次没有重新计算这些区间与检验。

链重采样反映当前任务集合中的差异，不能描述同一链再运行多次的随机波动。原子任务在多条链中复用，也使更广泛总体推断需要谨慎处理共享内容。图 1 引用的 GPT 5.5 原子 OSWorld 成绩来自外部报告，不是对这 189 个原任务、相同包装器和预算所做的匹配实验，不能相减得到严格的组合损失。

[主实验表 1、§4.1](https://arxiv.org/pdf/2606.21654v2#page=8)。

## 链长并不是单一难度旋钮

图 3 按链长进一步拆分整链完成率：

| 模型 | 单轮：2 / 3 / 4 项 | 多轮：2 / 3 / 4 项 |
| --- | --- | --- |
| GPT 5.5 | 0.24 / 0.04 / 0.13 | 0.27 / 0.22 / 0.41 |
| Opus 4.7 | 0.17 / 0.11 / 0.05 | 0.19 / 0.15 / 0.17 |
| Kimi 2.5 | 0.13 / 0.01 / 0.00 | 0.13 / 0.09 / 0.09 |
| Gemini 3.1 Pro | 0.06 / 0.02 / 0.02 | 0.03 / 0.03 / 0.01 |

Opus 和 Kimi 的单轮结果随链长降低；GPT 却在三项最低、四项回升，多轮四项甚至高于两项。这不是更长任务必然更容易，而是不同长度组本来就含不同任务组合，且每组只有一次运行。该实验没有在固定任务前缀上只增加一项，再对所有其他变量保持一致。

## 失败样本的标注和分母

作者从四个模型、两种协议各抽 40 条失败运行，共 320 条。先由 GPT 5.4 mini 根据结果摘要、短轨迹与运行日志分配主标签，再对其中 96 条模糊样本用 GPT 5.4 和更严格提示复核。它不是人工专家对全体运行的逐步标注，论文未报告人类一致性系数。

表 2 的比例以这 320 条失败为整体分母，单轮、多轮各以 160 条为分母；不是占所有 2,776 个运行组合的比例。

| 主失败类型 | 定义 | 全体失败样本 | 单轮 | 多轮 |
| --- | --- | ---: | ---: | ---: |
| 产物细节未满足 | 文件或输出相关，但值、格式或验证关键细节错误 | 60% | 72% | 47% |
| 固守前项 | 持续处理早期任务，后续任务几乎没开始 | 10% | 8% | 12% |
| 进度分散 | 多项都尝试了，但没有完整收尾 | 15% | 7% | 22% |
| 后续轮次停止投入 | 后续轮次仅零或一次动作就宣告结束 | 8% | 1% | 15% |
| 工具或调试偏离 | 大量调试、脚本探查没有形成所需结果 | 3% | 6% | 1% |
| 运行或初始化故障 | 文件、API 或环境问题中止执行 | 3% | 4% | 2% |
| 其他 | 剩余未归入的主机制 | 1% | 2% | 0% |

百分数取整，列和不一定恰好为 100%。等量抽样还让每个模型在汇总中权重相同，即使它们在完整评测中失败总量不同。因此，3% 运行故障是被编码失败样本的主标签占比，不能写成整个基准只有 3% 的环境错误，也不能据此证明每条链都正确可执行。

附录表 6 显示模型之间也不同：GPT 多轮失败仍有 72% 是产物细节问题，而 Opus 多轮的后续停止投入为 22%，Gemini 为 30%。这些都以各自 40 个失败样本为分母，不能把后两个模型的模式推广成所有多轮 agent 的统一行为。

公开标注脚本保留一项主标签、可选次标签、置信度和简短证据；其 schema 还包含 `broad_execution_failure`，比论文表的七类多一项。最终表如何合并或消除这项，需要最终标签文件才能完全核实。轨迹过长时脚本只取开头四步和末尾六步，截短回答和动作文本，并取日志末尾 30 行；这也限定了该标签能够解释的轨迹范围。

## 发布代码与论文协议需要分别核对

本次固定第一作者仓库 commit `aa26530bbe34ae84649a7252993bb6c59dfe2d49`。它采用 Apache-2.0 许可，发布构建代码、任务链、静态与 LLM 任务描述、兼容边和失败标注脚本。论文匿名地址在本次环境返回 403，随后通过作者公开仓库完成核查。[固定版本](https://github.com/vsiu-ucsc/os_world_chained_review/tree/aa26530bbe34ae84649a7252993bb6c59dfe2d49)

静态检查确认 347 行任务链、347 个不同有序任务组合、189 个不同原任务、1,056 个任务位置，九格分布与自然度均与论文一致。全部 347 条 `effective_turn_instructions` 都等于原任务文字加确定性文件路径；文件中另有 LLM 改写字段，但不是当前有效指令字段。

以下差异会影响直接运行和结果解释。

### 默认步数与 agent 重置

`MultiTurnRunner` 默认 `max_steps_per_turn=30`，与论文 75 不同，复现必须明确覆盖。它默认 `reset_agent_between_turns=True`，后续每轮会调用 `agent.reset()`；环境状态则不恢复。具体是否清空模型对话历史取决于外部 agent 实现，不能只凭桌面状态持续，就宣称完整对话记忆也一定保留。论文实际包装器和覆盖参数未在本发布中完整提供。

该循环按一次 `agent.predict()` 增加一个 step，而该次返回的动作列表可能含多个动作。因此，代码的 75 个迭代上限不必等于恰好 75 次鼠标或键盘事件。没有动作时可以提前结束；默认 `fail_fast=False`，一项失败不会自动阻止后续项继续尝试。默认成功阈值为 1.0，记录的 `partial_score` 则是各轮原始分数和除以链长；若原评分器给分数型结果，它与“通过任务数比例”并不相同。

### 源任务的 OR 被展平为 AND

`single_prompt.py` 合并原验证器时，将嵌套函数列表直接展平，并统一写 `conj="and"`，没有保留原子任务内部的 `or`。发布任务描述中有 13 个实际使用的原任务带 OR，涉及 57 条链。

具体例子 `learning_reading_sharing` 中，原任务 `42d25c08-fb87-4927-8b65-93631280a26f` 的三个 `compare_epub` 是 OR；发布的单轮文件将这三个检查与其他任务一起放进 AND。逻辑上，“某项三个可接受条件满足一个”与“三个条件全部满足”不是同一验收要求。

这个差异已经同时在源任务描述和发布的融合文件中确认，不能将当前融合实现概括为无条件保留原验证语义。不过缺少论文实际运行结果和版本关联，尚不能计算它影响了多少报告成绩，也不能据此重写模型排名。

### 链标识重复与落盘文件数量

347 条任务组合中，`file_organization_session` 和 `shell_file_ops_session_2` 各出现两次，对应不同任务组合。`single_prompt` 目录只有 345 个 JSON，因为文件名使用链标识。按 `chain_id` 写文件或建立字典时，这些组合可能覆盖，不能仅按文件夹长度就当成完整的 347 条评测实例。

复现时应先为每个任务组合建立唯一标识，并同时保留原标识映射。本文没有修改作者发布数据，也没有推断论文实际运行是否已经处理这两个碰撞。

### 静态有效性与完整运行仍有距离

当前验证器检查快照、终止任务位置、累积进程终止和多个破坏性意图等规则，但没有穷尽所有文件状态、所有 `postconfig` 影响和嵌套验证逻辑。融合任务会集中执行多个准备动作和评分前动作，这与逐项准备、逐项评分不同。构建规则降低了部分冲突，却不构成任意实际操作路径下的执行保证。

这些差异与默认配置都来自所固定的公开代码。本页将其作为复现边界，不把当前快照直接等同于论文所有私有运行配置。

## 复现入口与尚缺的材料

若只检查任务包，可以直接读取 `artifacts/chains/chains.jsonl`，再按 `artifacts/profiles` 重算底层应用分布、读取 `single_prompt` 中的准备动作与验证器；不需要启动桌面或调用模型。本次执行的核查限于此类静态解析与算术检查。

构建入口为 `chain_discovery/corpus/build_beam.py`，依赖上游 OSWorld 任务 JSON、生成好的任务描述、兼容边和 LLM 端点。`--target` 控制链级判定调用预算，不是期望输出恰好多少条链，也不包含前面的任务语义标注费用。资源耗尽或候选无法继续补充时，实际可完成调用数也可能少于目标。

执行层提供 `MultiTurnRunner` 和 `fuse_chain_to_task`，但仓库 README 明确排除了完整桌面运行环境、各模型 agent 实现、内部参考提示和追加构建状态。完整重跑还需固定 OSWorld 版本与环境镜像、应用版本和源文件、服务登录与网络状态、各模型端点和图像历史、75 步覆盖参数、agent 重置行为、唯一链标识及验证器逻辑。

此外，需要实际逐链结果及失败编码文件，才能重算链完成率、任务位置成功率、配对检验和 bootstrap。论文没有公布多次独立运行、完整 token/API 费用或耗时统计，也没有提供逐项移除兼容规则、覆盖分配或 LLM 判断的受控消融。现有证据支持这组构建任务与两种协议下的比较，不足以量化每个构建模块各自带来的收益。

本地原文保留在 `research/papers/scale-ai/chainworld.pdf`。本文完成了 19 页正文附录、关键图表、公开任务包与主要代码路径核对，未运行任何桌面任务、模型推理或付费调用。

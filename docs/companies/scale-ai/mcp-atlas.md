# MCP-Atlas：真实 MCP 工具工作流

用户希望找到一篇广告研究论文的摘要，再从公司数据库里找出互动率最高的广告活动、日期和投放地域。模型需要自行选择论文搜索和数据库工具，将前一步找到的标识传入下一步，并把并列最高的记录都写进回答。MCP-Atlas 用这类任务评测真实工具工作流：1,000 道题覆盖 36 个 MCP 服务和 220 种工具，按最终答案满足了多少事实要求给分。论文 v3 中最高通过率为 82.2%，但“通过”只要求覆盖分达到 0.75，并不等于所有事实都正确。（§3、图 1、附录 D）

## 从函数调用正确到完成跨服务任务

MCP 提供工具声明、参数结构和调用结果的共同接口。接口统一之后，模型仍需解决三个不同问题：从暴露的工具中选出相关工具，构造合法参数，以及把返回结果用于完成用户目标。一次合法调用只覆盖了其中一部分。

论文与 MCP-Universe、MCP-Bench、Toolathlon、MCPMark 等工作比较，强调真实服务、多服务组合和细粒度结果评分的结合。它不要求模型复制一条指定轨迹，而是检查最终答案中的事实。这允许模型使用不同搜索顺序、参数或工具链完成同一目标。原文对其他评测规模和真实性的评价属于作者的研究定位，不是本文重新运行各基准得到的比较。（§2、表 1）

这里的“工具发现”有明确边界：每道题预先给定一个受控工具菜单，模型从中识别相关工具。模型并不是从整个互联网查找、安装和认证任意 MCP 服务，也不是每题都能访问全部 220 种工具。

## 任务、工具菜单与参考轨迹

论文全量集的规模如下：

| 项目 | v3 报告值 |
| --- | --- |
| 任务 | 1,000，道题均为英文单轮用户请求 |
| 公开／保留 | 随机分为 500／500 |
| MCP 服务／任务中涉及的工具 | 36／220 |
| 每题暴露工具 | 6–37，平均 15.2 |
| 每题相关工具 | 2–8，平均 4.1 |
| 每题干扰工具 | 平均 11.1 |
| 每题事实要求 | 1–23，平均 4.7 |
| 需要至少两个服务 | 98.6% |
| 每题所需服务 | 平均 2.55 |
| 参考轨迹工具调用步数 | 平均 9.8，原文全量统计 |

来源：§3.1—3.2。论文还报告 51.7% 的任务需要两个服务，38.2% 需要三个，8.7% 需要至少四个；剩余 1.4% 使用一个。相关工具与调用次数不同，同一个工具可能反复调用或分页读取。

五个环境类别为通用检索、生产力、编程、数据分析和金融，附录 B 给出的任务配比为 32%、22%、22%、12%、12%。服务使用次数可以重复：例如一题同时用搜索、数据库和计算工具，会出现在多个服务的使用计数中。因此表 5 的服务任务数不能相加当成独立任务量。原文没有完整展开多类别任务如何分配到这五个配比的规则。

暴露菜单由相关工具和语义上相近的干扰工具组成。题目不直接指定工具名、服务名或参数，模型要从任务含义推断调用链。对于需要状态的服务，环境还要装载特定数据库、文件或工作区内容；“真实 MCP 服务”不等于任务直接使用某家公司的真实业务账号。

参考轨迹记录调用、参数、返回证据和依赖关系，用于检查可解性以及事后诊断。它是一个足够完成任务的证据路径，不是唯一合法策略，也不直接进入通过率计算。（§3.2、附录 J）

## 专家制作与质量检查

任务制作包含五层检查：作者在配置环境中实际执行参考轨迹；领域专家检查正确性和可解性；另一次审核检查提示是否泄露服务或工具名称；自动检查事实要求是否完整、与轨迹是否一致；最后进行随机人工抽查。（§3.4）

附录 D 报告每题平均需要 4.6 小时专家劳动，包括编写、验证和整理交付材料。专家按合同付费，作者称符合或高于当地工资要求。完整内部出题手册未公开，公开材料也没有给出足以重建全部人员分工、抽检比例或人工一致性的记录。

任务应依赖外部数据，并尽量使用在评测窗口内稳定的事实。作者需给出自然语言提示、合适的工具环境、参考轨迹，以及由工具输出支持的最终答案。事实要求并非全部从零手写：附录 A 明确说明，候选事实结合专家编写与自动生成，再由人工审核。该流程仍可能留下歧义和遗漏，原文将其列为评分上限的噪声来源。

## 广告研究与数据库任务的完整路径

附录 D 的例题要求先找到 Jane Castleman 在 2024 年关于广告控制效果的研究，再查询 2015—2023 年启动的广告活动，返回最高互动率活动的日期与地域。

题目暴露 15 种工具，其中参考路径使用三种：

1. `arxiv_search_papers`：用作者、年份和主题查找论文摘要。
2. `notion_API-post-search`：搜索广告数据所在的数据库。
3. `notion_API-post-database-query`：用找到的数据库 ID 查询活动记录，再进行年份筛选与最高值比较。

其余包括 Notion 页面或区块读取、网页抓取、记忆、Slack 和域名查询等工具。它们处于同一个候选菜单中，但不属于这一参考路径所需的三种工具。

五条事实要求分别检查：论文身份、摘要、三项活动并列最高且互动率为 15%、三项活动的日期，以及对应地域。日期为 2022-06-24、2019-09-20 和 2017-09-09，地域依次为 National、International、International。这里报告的是基准例题的参考数据，不是对外部广告业务的实时查询。（附录 D.5）

这道题需要处理并列最大值。只取数据库排序后的第一条记录，即使单条内容都正确，也会遗漏其他获胜活动。与此同时，“三项日期”被合并为一条事实要求，说明原文所称“原子事实”在实现中仍可能包含多个细节，部分分就用于处理这种不完整覆盖。

## 覆盖分与通过率的公式

设任务 $j$ 的事实要求有 $m_j$ 条。评审模型对最终答案中的每条要求给出：

$$
a_{j,i}\in\{0,0.5,1\}.
$$

三个值分别表示未满足、部分满足和完全满足。任务覆盖分为：

$$
C_j=\frac{1}{m_j}\sum_{i=1}^{m_j}a_{j,i}.
$$

在 $N$ 道题上，平均覆盖分和阈值通过率分别为：

$$
\overline C=\frac1N\sum_{j=1}^{N}C_j,
\qquad
P_t=\frac{100}{N}\sum_{j=1}^{N}\mathbf1[C_j\ge t].
$$

主榜使用 $t=0.75$。每条事实在题内等权，每道题在总体中等权；不是把所有任务的事实条目摊在一起计算比例。`Pass@0.75` 的数字是覆盖阈值，不是生成次数，因此与从多个候选中取最好结果的 pass@k 不同。（§3.2、附录 C、J）

以五条要求为说明示例，若得分为 $[1,1,1,0.5,0.5]$，则覆盖分为 0.8，任务通过，但仍有两个要求没有完全满足。改为 $[1,1,1,0.5,0]$，覆盖分为 0.7，任务失败。由于事实数量不同，可取得的离散分数也不同：一条事实的任务只有 0、0.5、1 三档，达到 0.75 必须拿到 1。

通过评分只读取事实要求和最终回答，不逐调用验证轨迹，也没有单独给额外错误陈述设置负权重。若回答碰巧满足事实要求，缺少工具调用本身不会自动扣分；“没有使用工具”是失败任务的后续诊断类别。基准通过出题和参考轨迹验证工具依赖，而不是在主分数中强制执行路径约束。

### 评审看到的信息与容差

附录 C 的完整提示把单条 claim 和模型最终回答交给评审，返回类别、理由与 0—1 的自报置信度。每条要求单独调用一次评审；五条要求对应五次调用。置信度不参与覆盖分加权。

提示允许合理的数值近似：一般数值在参考值的 5% 内可视为匹配，百分比允许约 ±1 个百分点，并根据科学或金融语境调整精度。例如参考值 100，回答 104 可能满足默认容差；是否需要更精确仍由评审结合语义判断。因此该分数是模型辅助的语义评分，不是严格数值相等测试。论文没有提供独立专家对三档评审结果的系统一致性实验。

## 模型设置、预算与置信区间

v3 评测 20 个模型，来自 Anthropic、Google、OpenAI、Meta、Kimi 和 GLM。全量结果使用相同题目、暴露工具、事实要求及每题 100 次工具调用预算；供应商原生工具接口和推理设置不同，附录 A 也承认执行框架并非逐字段完全一致。

表 9 中，GPT-5.5、GPT-5.4、GPT-5.2 和 GPT-5.4 Mini 使用 `xhigh`；GPT-5.1 使用 `high`；o3 Pro 使用默认推理配置。Claude Opus 4.7、4.6 使用 adaptive 与 `effort=max`，Opus 4.5 和 Sonnet 4.5 使用 high 与 10k budget；四个 Gemini 配置使用 high。Muse Spark 使用 max，GLM 与 Kimi 条目使用默认配置。模型名相同但预算不同的其他实验不能直接并入这些结果。

附录 H 称运行允许最多五次重试，并将工具错误摘要反馈给模型；到达 100 次调用上限时允许评分已有回答。这不是在五条完整轨迹中择优评分。原文没有给出每个模型触发重试或预算上限的精确次数。

主榜的 95% 置信区间来自非参数 bootstrap：针对每个模型，以其 1,000 道题的覆盖分为样本，有放回抽取 1,000 题，重复 10,000 次；每次计算 $P_{0.75}$，取 2.5% 和 97.5% 分位点。它反映任务抽样不确定性，不包含重新调用模型、重启上游服务或更换评审的全部随机性。（附录 C.1）

## 失败诊断的分母和类别

论文只对覆盖分低于 0.75 的任务—模型组合做诊断，约有 6,900 个被诊断失败。每个失败选一个主要类别，也允许记录次要原因。63.3% 的主要诊断属于认知类，36.7% 属于工具调用类；这是失败集合中的构成，不是所有 20,000 条轨迹里发生认知错误的比例。（§4.2、表 3—4）

| 家族 | 类别 | 区分方式 |
| --- | --- | --- |
| 工具调用 | 参数错误 | 工具选对，字段、类型或取值不对 |
| 工具调用 | 工具选择错误 | 当前工具无法回答子任务 |
| 工具调用 | 完全没有调用工具 | 跳过需要外部证据的步骤 |
| 工具调用 | 错误恢复失败 | 报错后重复同样调用、循环或放弃 |
| 认知 | 任务理解错误 | 回答了不同问题或漏掉核心要求 |
| 认知 | 结果整合错误 | 拿到正确证据后组合不当 |
| 认知 | 返回内容解析错误 | 读错字段、行或结构 |
| 认知 | 过早结束 | 理解任务但未完成所需步骤 |
| 认知 | 虚构事实 | 最终内容没有工具输出支持 |
| 认知 | 逻辑错误 | 使用了错误条件或推理链 |
| 认知 | 违反约束 | 忽略题目明确规定的过滤条件 |

诊断模型能看原题、参考轨迹、受测轨迹、最终回答和未满足事实的评分理由。这与主评分只看最终答案的流程不同。参考轨迹帮助定位缺失证据，但也可能让诊断偏向作者原有解法；论文要求把它视为一条充分路径，不因合法替代路径扣分。（附录 E）

o3 Pro 的失败中，40.1% 被归为没有调用工具，工具类合计 57.6%；不能把 40.1% 写成所有 o3 Pro 任务都没有工具调用。Gemini 3.1 Pro、GPT-5.4 和 Opus 4.6 的失败中，过早结束分别占 42.8%、41.4%、36.3%。GPT-5.5 与 Opus 4.7 的相应比例降为 3.6%、3.8%，但整合错误占到 19.8%、25.0%。这些是不同模型失败分布的比较，没有对同一模型施加控制干预，不能据此证明某种训练改动使错误从一种类型转成另一种。

诊断仍由模型自动完成，原文未报告十一类标签的独立人工混淆矩阵。部分类型边界接近，必须保留“自动诊断”的性质。

## 时间效率与公开、保留集差异

图 2 比较每题平均墙钟时间与通过率。Haiku 4.5 为约 27 秒、40.2%，Opus 4.7 为 71 秒、79.1%，Muse Spark 为 121 秒、82.2%；o3 Pro 为 194 秒、44.5%。这里的 Pareto 前沿表示没有另一模型同时更快且通过率更高，不是价格前沿或 token 效率榜。

墙钟时间混合了模型生成、网络往返、服务响应和重试。论文将部分延迟归因于工具往返，但当前 README 又称典型负载中更多时间花在等待模型；二者没有提供相同条件下的计时分解。本文只引用观测时间，不把某种延迟原因当成已控制验证的结论。

公开与保留集各 500 题，图 3 报告公开分减保留分的差异从 −0.8 到 +9.6 个百分点。GPT-5.4 为 +9.6，Muse Spark 为 +0.4，Kimi K2.5 为 −0.8。公开集发布了题目、事实和轨迹，因此差异值得跟踪；但题目难度、服务可用性与评测设置也可能贡献差异。原文明确把它视为分集敏感性及暴露监测信号，没有据此认定任何模型训练污染。

## 公开 500 题的实际核查

固定版本 Parquet 只有五个字段：`TASK`、`ENABLED_TOOLS`、`PROMPT`、`GTFA_CLAIMS`、`TRAJECTORY`。本次完整读取 500 行，任务 ID 全部唯一，工具菜单合计涉及 220 种名称。以下统计只针对公开半集，不能直接替换论文全量值：

| 项目 | 公开数据静态计数 |
| --- | ---: |
| 暴露工具数 | 7–37，平均 15.196 |
| 参考轨迹实际工具调用 | 3–17，平均 4.846 |
| 参考轨迹不同工具数 | 2–8，平均 4.110 |
| 参考轨迹至少两个服务 | 495/500，即 99.0% |
| 每题解析后事实数 | 1–23，平均 3.904 |

工具调用数按轨迹中 `tool_calls` 条目计算，不把工具返回消息再算一次。论文全量参考轨迹平均 9.8 步，数据卡仍写每题 3—6 次调用；两者都不应被当成当前公开文件每行的实际范围。数据卡的 10—25 个暴露工具也不是严格上下界。[固定数据](https://huggingface.co/datasets/ScaleAI/MCP-Atlas/tree/8c563b55d7c967755f474299848049834d624617)

`ENABLED_TOOLS` 混合字符串名称列表与工具描述对象列表，官方加载器会提取对象的 `name`。`GTFA_CLAIMS` 是字符串化列表，不是 Parquet 原生列表。本次发现一题 `689cd6f8522029b7ad7b1fe5` 因字符串内部换行无法按 Python 列表解析；官方评分器回退到文本拆分后仍得到一条要求，但留下开头列表符号等内容。上述事实数使用官方解析函数计算，未自行修订原始数据。这类解析问题应在运行前记录，而不是默默改掉后继续使用同一版本名。

公开轨迹含任务相关的工具返回证据，但并不提供五月二十个受测模型的完整原始运行和三评审评分记录。数据卡称没有诊断过程，当前代码却已有诊断模块，也反映了文档更新不同步。

## 当前执行框架与论文设置的差别

固定代码包含 TypeScript agent 循环、Python 工具环境、批处理、事实评分和失败诊断。主入口依次是启动环境、启动 harness、`run_eval.py`、`services/scoring/score_claims.py`。默认模型调用经兼容 Chat Completions 的接口转发；这与论文所述按供应商采用原生策略的环境不能自动等同。[固定代码](https://github.com/scaleapi/mcp-atlas/tree/f24ba3fb0bfa484c86acb28431fad6d7282455f9)

静态核查中有六处会实质影响复现：

1. **任务状态没有默认逐题重置。** 论文附录 B 称容器在任务间重启。当前 `agent-eval.ts` 明确禁用了 `/reset-state`，本地客户端复用同一个 sandbox 地址。仓库建议大型运行接入逐题临时环境的 orchestrator，但内部代理没有公开。直接用一个共享环境并发运行，不能声称已经实现论文的逐题隔离。
2. **预算上限后没有自动补写完整最终答复。** 当前循环达到 100 次调用即终止；`run_eval.py` 回收最后一条非空助手内容，可能是调用前的中间说明。它允许对已有文字评分，却不保证强制模型整理一次总结。256 轮是另一项循环上限，不能与 100 次调用混用。
3. **重试分层而非整题择优。** 当前 agent 层对部分超时或服务错误最多尝试三次；代理策略另对限流或认证错误最多重试五次。工具错误会写回上下文供模型恢复。它不是五次完整任务采样，也不能把论文“五次重试”直接对应成当前每层相同参数。
4. **诊断默认阈值不同。** `single_model_diagnostic.py` 的 `--failure-threshold` 默认 1.0，会诊断未全覆盖但已经通过 0.75 的题目。复现论文的失败构成必须显式设为 0.75。`analysis_error` 等程序失败又会从诊断比例中排除，诊断分母与主评分分母不能混用。
5. **评分失败的处理不统一。** 单条评审请求耗尽重试后记 `not_fulfilled`；空回答直接记零；整行处理异常或没有事实要求则可能得到空分。统计函数先 `dropna()` 再计算通过率，故分母可能小于输入任务数。必须同时报告有效任务数与失败日志，不能默认所有结果都除以 500 或 1,000。
6. **版本与结果仍需补齐。** 默认 `load_dataset` 没有固定 revision；默认工具输出不截断，上下文压缩关闭，推理参数需显式提供。当前评分器输出 0.50、0.75 阈值统计，没有原文 10,000 次 bootstrap 和完整三评审图表再生成流程。仓库也没有与主表配套的全部模型原始结果文件。

评审实现与附录提示一致，逐条调用并将平均分保留三位小数；500,000 字符以上的回答会截断。主评审默认是 Gemini 3.1 Pro Preview，置信度只记录不加权。这些设置需要与模型响应文件、数据 revision 一起保存。

README 的单题 smoke test 仍调用指定受测模型，要求模型端点凭据；不能因为论文提到无模型凭据的本地测试，就把 README 示例视为无费用离线验证。本文没有执行这一调用。

## 服务数据、许可与复现成本

当前 README 列出 36 个服务：20 个无需额外密钥，11 个需要服务密钥，5 个还需要导入样例数据。后五者涉及 Airtable、Google Calendar、Notion、MongoDB 和 Slack。仅启动容器而不导入相应内容，数据库可能为空，题目中的标识也可能不匹配。仓库提供数据导出及导入说明，并指出旧 Slack 消息可见性等服务条件会影响任务。

README 提到完整服务目录有 307 种工具，而论文和当前题目菜单实际覆盖 220 种；服务具备的全部工具与本数据集暴露的工具是不同口径。Docker 镜像标签、服务包版本和真实上游 API 还会分别变化；固定镜像无法冻结搜索结果、速率限制和认证规则。

论文附录 H 写代码采用 Apache 2.0，但本次固定仓库根目录的 `LICENSE` 实际为 MIT。本文对当前代码按实际许可证记录；数据卡为 CC BY 4.0，第三方服务及上游返回内容仍有各自条款。不能把论文中的代码许可原样套到不同时间的仓库快照。

按论文全量规模，二十个模型需要 20,000 条受测轨迹。按每题平均 4.7 条事实估算，单评审约需 94,000 次调用，三个评审共约 282,000 次；这不含失败重试和诊断。论文报告每个模型在 8—12 并发客户端下约需 2—18 小时，主评审处理一千题约需两小时。它没有提供可据以还原全部 API 费用的统一 token 账单，时间也不能直接换算成价格。（附录 H）

本次完成了 25 页正文与全部附录阅读、关键图表视觉核对、500 行公开数据与所述核心代码路径的静态核查；未启动服务、调用模型或重新计算主榜。MCP-Atlas 的结果覆盖英文、固定工具菜单和指定服务快照下的单轮任务；开放工具安装、多轮用户澄清、非英文工具使用及真实业务环境中的持续状态管理，仍超出本实验的直接结论。

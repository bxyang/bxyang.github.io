# MCP-Atlas：评估真实工具中的多步任务

## 1. 摘要翻译

以下译自该版本 Abstract，原文采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) 许可。

模型上下文协议（MCP）正在成为大语言模型代理发现和调用外部工具的标准接口。然而，现有 MCP 评测在三个关键方面仍有不足：包含跨服务编排的真实多步工作流程；覆盖真实 MCP 服务，而非模拟实现；以及结构化、可复现、能够排除代理表达冗长程度或风格影响的逐项事实评分。

我们提出 MCP-Atlas，一个面向生产环境 MCP 服务、衡量工具使用能力的基准。MCP-Atlas 包含 1,000 个由人类专家编写和验证的自然语言任务，涵盖 36 个真实 MCP 服务和 220 个工具。提示不指定服务、工具或参数，要求代理从语义上合理的干扰项中识别相关工具，并组织多步、跨服务的工作流程。

每个任务使用逐项事实评分标准：将最终答案与以工具输出为依据的原子事实陈述进行比较。这种以答案为中心的评分方式，允许不同但有效的工具调用路径获得认可。我们还配套提供 11 类诊断体系，将工具调用失败与任务理解、综合信息、解析和停止决策方面的认知失败区分开来。

在任务条件一致的情况下，我们评估了来自六家提供方的 20 个前沿模型，发现当事实覆盖率阈值设为 0.75 时，通过率最高达到 82.2%，并形成清晰的三层表现结构。自动诊断表明，在已诊断的失败中，63.3% 属于认知问题，而非工具调用问题。值得注意的是，若干表现较好的模型会在工具执行成功后，因过早停止或错误地综合信息而失败。

我们发布任务格式、容器化执行框架、事实评估器，以及包含 500 个任务的公开部分，同时保留 500 个任务作为非公开部分，以维护排行榜的可靠性。代码发布于 [MCP-Atlas 仓库](https://github.com/scaleapi/mcp-atlas)。

## 2. 研究背景与相关研究

真实用户通常只描述要完成的事情，不会告诉代理应该调用哪几个工具。代理需要先理解目标，再选择工具、处理返回信息，并让前一步结果成为后一步的输入。即使每次调用的参数格式都正确，最终答案仍可能遗漏要求或错误地整合证据。

论文第 2 节将工具评测的发展分为几类。MMLU 等静态题目主要考察知识和推理；WebArena、OSWorld 等交互环境考察网页与计算机操作；ToolBench、BFCL 等工作进一步关注 API 和函数调用；GAIA、SWE-Bench 等则把工具放进更完整的任务中。

在 MCP 方向，MCP-Universe、Toolathlon、MCPMark 使用真实环境和专门的验证机制，但人工编写任务与验证程序的成本较高。其他基准通过自动生成任务、扩大服务覆盖或让模型整体评价回答来提高规模。本文作者认为，这些选择可能分别带来任务自然程度、模拟环境真实性或评分受表达风格影响的问题。

MCP-Atlas 试图结合几项设计：让专家构建较大规模的自然语言任务，接入真实 MCP 服务，在工具集合中放入合理干扰项，并以最终答案应当包含的具体事实评分。这样既评估工具选择和串联，也保留对最终结果的检查。[原文第 1—2 节](https://arxiv.org/pdf/2602.00933v3)

## 3. 核心贡献

**核心要解决的问题。** 基准希望测量代理能否从用户目标出发，自行找到工具、收集所需证据，并形成符合要求的答案。评测既要允许不同的正确解法，也需要说明失败发生在调用工具之前、调用过程中，还是获取信息之后。

**核心方案。** 1,000 个任务覆盖搜索、办公、编程、数据分析和金融相关工具环境。每题只展示一个受控工具集合，包含完成任务所需的工具与语义相近的干扰工具；98.6% 的任务需要跨两个或更多服务。专家实际执行参考路径，检查任务可解性，再进行内容审核和事实要求验证。

评分将答案要求拆成独立事实。每项可以获得完成、部分完成或未完成的分数，再汇总为覆盖率。主结果以覆盖率达到 75% 为通过标准，因此“通过”并不表示所有要求都已完整满足。参考路径用于验证任务和分析错误，不要求模型照着同一顺序调用工具。

对失败任务，自动诊断器给出一个主要原因，分为工具相关与信息处理相关两大类，例如选错工具、参数错误、没有调用工具，以及理解错误、证据整合错误、过早结束等。公开的 500 题支持开发和复现，保留的 500 题用于持续评估。评分仍由语言模型完成，作者使用三个不同评判模型交叉检查结果，而非完全依赖确定性的验证程序。[原文第 3 节](https://arxiv.org/pdf/2602.00933v3)

**结论。** 在 v3 所报告的 20 个模型中，最高通过率为 82.2%。失败诊断中，63.3% 被归为任务理解、信息整合等认知问题。这一比例的分母是已经失败且接受诊断的案例，不是全部任务；它说明工具返回结果之后，如何正确使用证据仍然是重要难点。

一些模型经常没有调用任何工具，另一些模型能够获取信息，却在任务尚未充分完成时结束，或在最后汇总时引入错误。因此，仅增加可调用工具数量，不能保证代理可靠完成工作。MCP-Atlas 提供的是从工具发现到最终答案的整体评测，以及对失败位置的进一步区分。

这些结果是 2026 年 5 月工具生态与模型版本的快照。真实 API 的数据、限制和接口可能变化；不同评判模型会造成约 2—5 个百分点的分数差异。虽然任务层面的设置相同，各提供方的底层工具调用适配也并非完全一致。公开与保留任务的分数差距可以提示进一步检查，但不能单独证明训练数据污染。[原文第 4—6 节与附录 A](https://arxiv.org/pdf/2602.00933v3)

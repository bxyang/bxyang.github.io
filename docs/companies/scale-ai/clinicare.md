# CliniCARE-Bench：电子病历审查

一次病历审查的结论可能正确，调查过程却不完整。例如，agent 找到了支持某个判断的记录，却没有检查任务要求排除的另一种解释。CliniCARE-Bench 把最终答案和调查过程分开评分：16 个系统在 750 个案例上的四分类准确率为 65.3%–76.1%；在有报告的运行中，只给“答案正确且未触犯禁止捷径”的结果计分，准确率下降 4.8–14.8 个百分点。这个差值衡量正确结论中包含的流程缺陷，不能直接等同于模型造成临床伤害的概率。[论文 §5–6、表 3](https://arxiv.org/pdf/2608.07796v1)

论文共有 19 位作者，Veronica Chatrath 和 Bryan Zhu 为共同第一作者。除 Nigam H. Shah 署名 Stanford 的临床与研究机构外，其余 18 位作者均列有 Scale AI；Keqi Han、Zhijun Yin、Chenguang Wang 还分别列有 Emory、Vanderbilt University Medical Center 和 UC Santa Cruz。贡献声明中，Yuan Xue 负责研究方向和监督，Chatrath 负责执行与临床评审网络，Zhu、George Pu 负责技术开发，Jingxuan Fan、Apaar Shanker、Varun Ursekar 分别参与证据、规则与流程评分，合作研究者提供临床和评测设计指导。[作者页、贡献声明](https://arxiv.org/pdf/2608.07796v1)

它研究的是**回顾性病历审查**：根据已经存在的记录，判断事件、流程或文档是否满足标准。没有在真实患者诊疗中前瞻性部署，也没有直接测量治疗结果。后续 [READY](/companies/scale-ai/ready) 使用这些执行记录研究人工分流；READY 的 375/375 拆分与本文的 148 例开发子集是两套协议，不能混用。

## agent 实际收到和完成的工作

一个案例给出临床问题、患者及相关就诊标识。agent 不会收到已经整理好的全部病历，也不直接获得参考四分类标签。它通过受控接口检索数据，在沙盒里进行计算，查阅任务环境的规则文档，最后写出带证据引用的报告。

环境建立在三个版本明确的数据源上：MIMIC-IV 3.1、MIMIC-IV-Note 2.2、MIMIC-IV-ED 2.2。它们来自同一学术医疗中心的去标识历史数据，覆盖住院、ICU、急诊、出院小结和影像报告。论文介绍的底层数据库有 364,627 名患者、约 9 亿行结构化记录；这些是环境规模，**实际评测只有 750 个患者特定案例**，不能把全库人数写成 benchmark 样本量。[论文 §3.1](https://arxiv.org/pdf/2608.07796v1)

| 环境部分 | agent 能做的事 | 评测保留的信息 |
| --- | --- | --- |
| 临床检索工具 | 按患者或就诊查询检验、用药、生命体征、笔记、影像等 | 工具参数、返回记录、来源 |
| 只读 SQL 回退 | 在高级工具覆盖不足时查询底层表，返回行数受限 | SQL 调用单独记录 |
| 沙盒 shell | 用 Python 等显式计算分数、时间差和趋势 | 代码、输出和中间产物 |
| 规则文档工具 | 列出、检索、读取共同文档库 | 文档名与行号 |

病历没有预先拼成单一摘要。系统必须自己连接结构化事件与自由文本，辨别“医嘱开出时间”和“实际操作时间”，处理不同住院期间的记录。公开网页搜索关闭；临床证据通过隔离凭据的工具服务访问。该环境模仿受控应用接口的工作方式，但论文没有声称它完整实现某个 FHIR 标准。[论文 §3.2–3.3](https://arxiv.org/pdf/2608.07796v1)

最终报告必须在四种结论中选择一种：Yes、No、因缺少数据而无法确定、因医学歧义而无法确定。“没有查到支持”不自动等于 No；反过来，在完整检索过的记录流中确认某项行为没有发生，也不一定属于缺少数据。答案取决于预先制定的场景规则。

## 25 个场景如何变成 750 个案例

场景是可复用的审查规范，案例是把它应用到具体患者、住院或事件上的实例。论文设计 25 个场景，每个抽取 30 个案例，覆盖 14 个医学专科和跨专科运营工作。专科按单标签划分，十种推理能力可以多选，包括阈值计算、限时流程审计、顺序核对、规则遵循、完整性检查、病因判断、跨来源核验、信息对账、否定证据和纵向综合。每场景通常同时涉及两到三种能力。[论文 §4、图 3](https://arxiv.org/pdf/2608.07796v1)

每份场景规范包括四部分：呈现给 agent 的问题；把证据映射到四类答案的操作性规则；必须查证的来源和发现；必须遵循及禁止使用的调查步骤。作者对每条决定规则记录出处，区分外部指南、既有临床知识和本 benchmark 自行制定的操作约定。因此，所有评测门槛并不都能直接等同于一条临床指南的原文要求。

选样先按场景建立候选队列，以相关住院、索引事件和证据来源决定是否合格，再用启发式规则暂分 Yes、No、Indeterminate 三种抽样层，后者包含两类不确定性。分层抽取 30 名患者是为了增加困难和不确定案例的覆盖，临时层标签不是最终参考答案。最终分布不能用来估计真实临床发生率。[论文 §4.4](https://arxiv.org/pdf/2608.07796v1)

完整队列参考标签为 Yes 352、No 248、缺少数据 123、医学歧义 27；因此确定答案共 600 例，不确定答案共 150 例。这个分布也决定后文两个方向错误率的不同分母。公开 README 保留了这组计数，但完整患者队列和逐例标签需要数据权限，本文没有下载受限病例。[固定版本数据说明](https://github.com/scaleapi/clinicare/blob/bbce780bc0dab07aae584f4dbc097601916b0905/README.md)

### 一个完整例子：CT 后的肾功能变化

论文 §4.3 和附录 B 用 CT 后 48 小时内的急性肾损伤审查说明规则。以下解释的是 **benchmark 指定协议**，不是另行给出的诊疗建议。

agent 先定位实际 CT 时间，再按任务规定选择基线肌酐：优先使用入院前 3–12 个月内最低值，否则使用入院值；两者都没有且符合文中条件时，使用约定的估算基线。它还必须检查慢性透析、终末期肾病和基线波动情况，并查看窗口内全部肌酐值，不能只取第一条。

在可适用的病例上，设基线为 $b$、窗口内测量为 $c_t$，论文采用的升高条件是：

$$
(c_t-b\ge0.3\ \mathrm{mg/dL})\quad\text{或}\quad(c_t\ge1.5b).
$$

这里是“或”，不是“且”。Yes 要有符合门槛的窗口内测量；No 除了不升高，还要求至少两次窗口内测量及相应排除条件。基线或 CT 时间无法确定、采样不足会进入缺少数据；慢性透析或无法解释的波动基线可进入医学歧义。时间先后只能支持“CT 后发生”，不支持“由造影导致”。[论文 §4.3、附录 B](https://arxiv.org/pdf/2608.07796v1)

这组规则也暴露了复现时要保留的边界：原文 Yes 条款允许至少一次达到门槛的测量，缺少数据条款又笼统列出“少于两次”；仅有一次但已经达到门槛时，文本存在重叠。公开场景规范也保留了这两条，不能擅自给它补上未经说明的优先级。准确复现仍以正式裁决标签和对应版本规范为准。

附录还完整展开了影像实际完成核对、入院—住院—出院用药对账、跨住院肾功能趋势三类任务。它们分别要求用影像报告确认操作而非只看医嘱，区分主动调整与无意漏药，以及用长期指标而非单个肌酐值判断趋势。这些例子说明同样的四类标签背后有不同证据要求，不能用一条通用“没有证据就拒答”规则取代场景裁决。

## 参考答案的制作与医生校准

两位医生先独立审核每个场景，修改问题、阈值、时间窗、例外和证据要求。之后三套模型系统独立调查每例：Claude Code / Opus 4.8、Codex / GPT-5.5、Gemini CLI / Gemini 3.1 Pro。与受测 agent 不同，裁决模型能够看到完整规范，包括操作规则和证据要求。

750 例中，556 例三者一致，183 例为 2 对 1，11 例出现三个不同答案。最后一组交由医生直接裁决。其余参考标签主要通过模型多数意见形成，不能称为全部 750 例均由医生从原始病历独立制作的金标准。[论文 §4.4–4.5](https://arxiv.org/pdf/2608.07796v1)

医生校准分两部分：

| 校准部分 | 规模 | 实际比较 |
| --- | --- | --- |
| 单人校准 | 75 例，每场景 3 例 | 一位医生给结论，并评价三份模型报告 |
| 双人复核 | 25 例，每场景 1 例 | 两位医生分别给结论和报告质量评价 |

医生看到的三份模型报告被随机标记为 Alpha、Beta、Gamma，隐藏模型身份；但医生使用的是模型已经检索和整理的证据，而非自己重新操作病历系统。论文明确承认，这不是完全独立的证据获取过程。匿名化减少身份偏好，不能消除三模型共同漏检某条证据的影响。

75 例校准中，5 例没有模型多数答案，按设计升级裁决；其余 **70 例中 64 例**与医生一致，约 91%，Cohen’s $\kappa=0.87$。三模型一致的 46 例与医生全部一致；2 对 1 的 24 例有 18 例一致，另外 6 例医生支持少数模型。91% 的分母是 70，不是 75，也不是全部 750 例。

在双人子集中，两位医生结论一致率为 80%、$\kappa=0.69$；参考标签与两位医生分别为 $\kappa=0.87$、0.81。医生对报告的质量评级包括 sound、minor error、major error：两个部分分别有 225 和 150 次报告评级，其中 73% 和 81% 被评为 sound。这些数据验证了校准样本上的一致性，不能据此推出模型临床水平超过医生。[论文 §4.5](https://arxiv.org/pdf/2608.07796v1)

## 评分先区分分母

一次运行是某系统对某案例的一次执行。主实验每个系统运行每例一次，所以每系统 750 次、16 系统共 12,000 次。不同指标并不都平均这 750 次：

| 指标 | 分母或纳入条件 |
| --- | --- |
| 四分类准确率、类别 F1 | 全部运行；缺报告或无法解析计错 |
| 流程分、无缺陷准确率、缺陷差值 | 有可解析最终报告的运行 |
| 四个患者证据指标 | 有报告且至少检索到一条患者记录的运行 |
| ECE | 有有效置信度的报告 |
| 规则文档 precision | 至少引用一个库中文档的运行 |
| 规则文档 recall | 全部运行，没有引用记 0 |
| 重复运行可靠性 | 每次尝试均可评分的共同案例 |

同一场景有 30 例时，完整队列上的案例微平均恰好等于场景宏平均；只跑部分病例后不再保证相等。程序汇总前也必须按任务去重，不能把补跑与原始失败目录一起算成两个患者。[论文 §5.1、§6.1](https://arxiv.org/pdf/2608.07796v1)

### 四分类和两个方向的拒答错误

四分类准确率按预测与参考完全相同计 1；把两种不确定性混为一类没有部分分。Macro-F1 分别算四类 F1 后等权平均，使只有 27 例的医学歧义类不会被常见标签完全掩盖。

令 $A$ 为两类不确定答案、$D$ 为 Yes/No，两个方向错误定义为：

$$
\mathrm{OverCommit}=
\frac{\sum_i\mathbf1[y_i\in A,\hat y_i\in D]}{\sum_i\mathbf1[y_i\in A]},
\qquad
\mathrm{OverAbstain}=
\frac{\sum_i\mathbf1[y_i\in D,\hat y_i\in A]}{\sum_i\mathbf1[y_i\in D]}.
$$

前者是在本应不确定的 150 例中贸然给确定答案；后者是在本可确定的 600 例中不必要地拒答。两者分母不同，不是互补概率。无法解析的输出计准确率错误，却不被凭空归入某个方向的错误分子。[论文 §5.2](https://arxiv.org/pdf/2608.07796v1)

### 流程分和“无缺陷”是不同条件

每场景有 4–9 条 MUST-DO 和 3–8 条 MUST-NOT，权重为 $\pm1$ 或 $\pm2$。$z_{im}=1$ 表示描述的行为发生：对于 MUST-NOT，含义是**犯了禁止的错误**，不是遵守了禁令。流程分为：

$$
S_i=\max\left(0,
\frac{\sum_m w_mz_{im}}{\sum_{m:w_m>0}w_m}\right).
$$

分母只加正权重，各场景为 7–16 分。负项发生时扣分，最低截为 0。本文对公开 25 份 rubric 的计数核查与上述范围一致。[论文 §5.5](https://arxiv.org/pdf/2608.07796v1)

**说明示例：**正项权重为 2、2、1，完成第一和第三项得到 3 分；又触犯一个权重 −2 的禁项，最终为 $(3-2)/5=20\%$。这个算例已用公开纯评分函数离线核验，不是论文病例结果。

无缺陷准确率更直接：在有报告的运行集合 $P$ 中，只有答案正确且所有负项均未触发才计分：

$$
A_{\mathrm{df}}=\frac1{|P|}\sum_{i\in P}
\mathbf1[\hat y_i=y_i]\mathbf1[\text{没有 MUST-NOT 触发}],
\qquad
\mathrm{Gap}=A_{\mathrm{report}}-A_{\mathrm{df}}.
$$

这里的 $A_{\mathrm{report}}$ 也是报告存在子集上的准确率，不能直接用全运行准确率相减。没有触犯负项不等于完成全部正项，所以“无缺陷”也不等于调查全面或流程满分。

流程 judge 读取最终报告和工具轨迹，不读取模型私有思维过程。报告声称做过某项检查，但轨迹反映没有做，就不应据报告自述给分。生产评审模型为 GPT-5.5；超长轨迹按约定截断、分块，再按每个 criterion 在任一块被判 met 即整体 met 的规则合并。[论文 §5.5、§5.7](https://arxiv.org/pdf/2608.07796v1)

## 患者证据与规则引用分别检查

患者证据有四个指标：$P_{\rm record}$ 检查报告所引标识是否真的出现在该次检索；$P_{\rm claim}$ 检查断言是否被证据支持；$R_{\rm retrieval}$ 检查需要的来源是否被查询；$R_{\rm finding}$ 检查报告是否覆盖需要的发现。前后两对分别区分“引用存在与含义正确”“查过来源与报告说明发现”。

场景需要 3–9 类记录来源、4–11 个发现维度。查询返回有效空结果也能说明数据缺失，因此论文将正确限定范围的有效空查询算作来源已检查。Finding coverage 只问报告是否回应了该维度，不保证具体数值正确；错误数值由 claim precision 等指标检查。一个报告可能覆盖完整但部分断言无依据，也可能每句都可验证却遗漏关键问题。[论文 §5.3](https://arxiv.org/pdf/2608.07796v1)

规则文档的引用形如 `[policy: 文档 L_a–L_b]`。先检查文档及行区间存在，再判断引用段落是否支持相邻主张。令实际所引库中文档集合为 $\hat G$、场景规定集合为 $G$，则：

$$
P_{\rm doc}=\frac{|G\cap\hat G|}{|\hat G|},
\qquad R_{\rm doc}=\frac{|G\cap\hat G|}{|G|}.
$$

Precision 排除没有引用文档的运行，Recall 则在该运行上为 0。引用支持率的语义判断也不同于“正确应用规则”：后者还涉及时间窗、例外和阈值，分别反映在答案及流程评分中。[论文 §5.4](https://arxiv.org/pdf/2608.07796v1)

| Kimi-K2.7-Code / opencode | 66.5 | 0.558 | 54.1 | 12.4 | 69.6 |

Gemini-3.1-Pro 的原始准确率为 72.7%，无缺陷准确率为 57.9%，下降 14.8 个百分点；约占原本正确答案的五分之一。GPT-5.6-Sol 原始准确率比 Sonnet 5 低 0.7 个百分点，无缺陷准确率却高 1.9 个百分点。这说明结果排序会随成功定义变化。表中显示值还经过四舍五入，例如 72.9−59.1 看起来是 13.8，论文 Gap 为 13.9；应按同分母未舍入数据计算，不以显示值相减替代。[论文表 3、图 5](https://arxiv.org/pdf/2608.07796v1)

场景排序也不同。所有系统在每个场景各有 30 例，16 系统组成 120 对、再乘 25 场景，共 3,000 项比较，其中 30.2% 的局部先后顺序与总榜相反，另有 12.7% 并列。最难的肺炎 CURB-65 场景，跨系统平均准确率为 37.1%；临终目标一致性为 91.7%。每场景只有 30 例，单个案例就影响约 3.3 个百分点，因此这些结果不支持把小差距看作稳定的专科技能排名。[论文图 4、附录 D 表 15](https://arxiv.org/pdf/2608.07796v1)

### 不确定性错误与置信度

全部系统的 OverCommit 为 21.3%–55.3%，OverAbstain 为 7.3%–16.5%，前者逐系统均更高。MiniMax-M3、DeepSeek-V4-Flash、GPT-5.4-mini、Kimi-K2.7-Code 在至少一半需要不确定结论的案例上给出确定答案。这个方向错误率与精确四分类不同：把缺少数据错判为医学歧义同样影响分类准确率，却不会增加 OverCommit。[论文图 6–7、表 14](https://arxiv.org/pdf/2608.07796v1)

置信度用十个等宽区间计算 ECE：

$$
\mathrm{ECE}=\sum_{b=1}^{10}\frac{|B_b|}{n}
\left|\operatorname{conf}(B_b)-\operatorname{acc}(B_b)\right|.
$$

$n$ 只包含置信度有效的报告。Sonnet 5、Opus 5、GPT-5.5 分别为 0.046、0.064、0.090；三个 Gemini CLI 系统为 0.251–0.262，且只输出少量不同置信度值。ECE 描述校准误差，不能代替拒答两个方向的错误率，也不等于 READY 中的分流 AUROC。[论文式 1、表 3](https://arxiv.org/pdf/2608.07796v1)

## 一个案例中同时出现的两种失败

论文分析一名有肝硬化、肝性脑病和腹水的患者。按该场景的参考规范，记录中没有诊断性腹腔穿刺，因此不能确认或排除一个关键候选原因，参考答案为缺少数据。

16 个系统中 13 个给出确定答案，12 个回答 Yes，置信度最高 100%。其中 7 个触发同一禁止项：没有腹水检查结果，却声称相关感染已被排除。这是跨多个系统家族出现的具体证据替代错误。

另一方面，GPT-5.6-Sol 识别到“有指征但关键候选原因未调查”的升级条件，且未触发禁项，最后仍回答 No。三个给出正确不确定标签的系统则没有得到任何 MUST-DO 正项分。这说明“识别证据缺口后仍选错标签”和“标签正确但没有充分记录调查”都可能发生。**没有得到正项分，与触发负项是两回事**；不能把这三个系统全部改写为违反九条规则。[论文 §6.3、表 4](https://arxiv.org/pdf/2608.07796v1)

## 正确引用与完整调查没有同步提高

记录标识精确率几乎饱和，16 系统为 0.985–1.000；但 claim precision 与发现覆盖差别明显。下表摘录有代表性的配置，分母为符合患者证据评分条件的运行，不是所有患者记录或所有引用的池化比例。

| 系统 | $P_{\rm record}$ | $P_{\rm claim}$ | $R_{\rm retrieval}$ | $R_{\rm finding}$ |
| --- | ---: | ---: | ---: | ---: |
| Opus 5 | 0.985 | 0.884 | 0.852 | 0.843 |
| GPT-5.6-Sol | 1.000 | 0.971 | 0.848 | 0.768 |
| GPT-5.6-Luna | 1.000 | 0.965 | 0.871 | 0.737 |
| GPT-5.4-mini | 0.997 | 0.964 | 0.813 | 0.673 |
| Gemini-3.1-Pro | 0.999 | 0.903 | 0.689 | 0.604 |
| Kimi-K2.7-Code | 0.997 | 0.940 | 0.900 | 0.767 |

GPT-5.6-Sol 的断言支持率高于 Opus 5，但发现覆盖较低；Kimi 的来源覆盖较高，也没有因此获得最高答案准确率。论文报告 claim precision 与答案准确率排序的 Spearman 相关为 −0.28。这些是系统之间的关联；同一框架内相近的数值不能单独证明框架决定引用质量、模型只决定答案质量。[论文 §6.4、表 5](https://arxiv.org/pdf/2608.07796v1)

规则引用同样要拆开。GPT-5.4-mini 的引用解析率为 0.995，文档精确率为 0.800，文档召回率却为 0.479；GPT-5.6-Luna 分别为 0.999、0.825、0.524。两个系统大多引用真实且相关的文档，却遗漏部分规定文档。它们的引用支持率分别为 0.629 和 0.814，又说明真实引用不一定支持所述主张。完整系统的文档召回率为 0.407–0.703。[论文 §6.5、表 6](https://arxiv.org/pdf/2608.07796v1)

## 148 例开发子集上的消融

附录 E 的开发集从每场景每标签最多取两例，固定为 148 个案例，标签为 Yes 50、No 45、缺少数据 39、医学歧义 14。它比完整队列更集中于不确定性，绝对准确率不能与 750 例主表直接比较。

论文区分两种使用方式：表 16–18 将完整运行按这 148 个 ID 切片，Claude 系统是 Opus 5；配对消融和重复运行沿用更早的 Opus 4.8。即便都写 $n=148$，也不能把主表切片当成独立消融的原始条件。

### 去掉规则文档，没有检测到一致的准确率收益或损失

配对条件仅开关规则库，网页仍关闭。表 7 的变化方向为 off 减 on：

| 系统 | 开启准确率 % | 关闭准确率 % | 变化，百分点 | 配对检验 $p$ |
| --- | ---: | ---: | ---: | ---: |
| GPT-5.6-Sol | 70.3 | 70.9 | +0.7 | 1.00 |
| GPT-5.5 | 73.0 | 70.9 | −2.0 | 0.66 |
| Gemini-3.1-Pro | 77.0 | 72.3 | −4.7 | 0.21 |
| GPT-5.6-Luna | 59.5 | 62.2 | +2.7 | 0.56 |
| Opus 4.8 | 70.3 | 70.3 | 0.0 | 1.00 |

两个下降、两个上升、一个不变，精确双侧 McNemar 检验没有发现显著准确率变化。医学歧义召回的变化也没有统一方向，其分母仅 14，每例约为 7.1 个百分点。作者原先预期去掉规则库特别损害医学歧义识别，实际未得到支持；不能把它总结为规则库必然提高准确率，也不能把未显著误读为两种条件等效。[论文 §6.6、表 7](https://arxiv.org/pdf/2608.07796v1)

### 三次都正确，比至少一次正确困难得多

设同一案例独立尝试 $k$ 次，正确性为 $u_{ir}$，则：

$$
\mathrm{avg@}k=\frac1{nk}\sum_{i,r}u_{ir},\qquad
\mathrm{pass}^{k}=\frac1n\sum_i\prod_r u_{ir},\qquad
\mathrm{pass@}k=\frac1n\sum_i\mathbf1[\exists r:u_{ir}=1].
$$

$\mathrm{pass}^{k}$ 要求每次都正确，$\mathrm{pass@}k$ 只要求至少一次正确。这里直接使用实际三次运行的案例结果，并非用一个生成候选池估算通用 pass@k。

| 系统 | avg@3 % | 三次都对 % | 至少一次对 % | 三次答案相同 % | 三次同样答错 % |
| --- | ---: | ---: | ---: | ---: | ---: |
| Opus 4.8 | 72.7 | 64.2 | 82.4 | 79.7 | 15.5 |
| GPT-5.5 | 71.8 | 63.5 | 80.4 | 77.0 | 13.5 |
| GPT-5.6-Sol | 70.3 | 59.5 | 79.7 | 78.4 | 18.9 |
| GPT-5.6-Luna | 60.6 | 48.0 | 72.3 | 68.9 | 20.9 |
| Gemini-3.1-Pro | 72.3 | 60.8 | 82.4 | 76.4 | 15.5 |

三次都对比平均单次准确率低 8.3–12.6 个百分点；三次重复同一错误占 13.5%–20.9%。以 Luna 为例，20.9/68.9 约为 30%，即自我一致案例中约三成仍然错误。这里展示的是一致性和正确性的区别，不能据此推断重复采样总无收益：表中的至少一次正确率确实更高，但还需要一个能可靠选出正确答案的机制。[论文表 8–9](https://arxiv.org/pdf/2608.07796v1)

### 固定模型换框架，以及增加推理投入

DeepSeek-V4-Pro 分别使用 opencode、qwen-coder、mini-swe-agent，在同样 148 例上准确率为 66.2%、62.8%、66.9%，配对差异没有达到显著性；输出 token 中位数分别为 5,051、9,524、21,876，相差约 4.3 倍。三个构建的任务内容摘要相同。这支持该设置下资源消耗不同，不证明所有模型的框架选择只影响成本。[表 10](https://arxiv.org/pdf/2608.07796v1)

Opus 4.8 在 low、medium、high 推理设置下，准确率为 71.6%、72.3%、72.3%，流程分为 65.0%、68.3%、69.7%。输出 token 中位数从 7,332 增至 10,268、12,420。论文报告的 38% 和 72% 增幅是**逐案例 token 比值的中位数**，不是这三个中位数直接相除。准确率差异不显著，流程分上升也未充分分离；不能据此证明推理深度绝无作用。轨迹未提供独立 reasoning-token 数，输出 token 只是计算代理指标。[表 11](https://arxiv.org/pdf/2608.07796v1)

附录还报告早期歧义提示修改让合并的医学歧义召回约提高三倍，但发生在提示和标签修订之前，没有提供可与现行表格直接比较的数值。本文不把它算成现行版本的额外百分点收益。

## 自动评分器的稳定性与偏差边界

过程评分使用五个 judge、各重复三次的面板。论文报告平均成对分歧约 16%、Fleiss’ $\kappa\approx0.65$；分歧较多的规则包括隐藏的时间窗和受年代影响的治疗标准，作者将它们送回专家修订。它说明部分 rubric 本身需要澄清，不等于 16% 的 agent 行为必然错误。

患者发现覆盖在 200 份报告上重复评分，四个框架家族各 50 份，共 1,331 个类别判断，两次一致率为 97.9%、$\kappa=0.95$；175 份报告分数完全相同。断言抽取则每次可能拆成不同的原子句，无法逐句简单对齐，作者因此比较最终分数变化，并将约 0.02 内的差别作为噪声范围。规则引用支持的 judge 面板一致性约为 $\kappa=0.86$。[论文 §6.7](https://arxiv.org/pdf/2608.07796v1)

GPT-5.5 同时是参考标签三模型之一、被评测模型之一和语义指标的生产 judge。四分类匹配是确定性评分，不能因此忽略参考标签来源的模型依赖；重复评分的一致性也不能证明没有偏差。论文明确指出，$P_{\rm claim}$ 与 $R_{\rm finding}$ 的重复实验验证稳定性，尚未用独立 judge 完成偏差检验。所谓规则引用“保守下界”是作者对部分低估现象的解释，不是已建立的统计置信界。

## 公开实现、静态核查与复现步骤

本次固定官方仓库提交 **`bbce780bc0dab07aae584f4dbc097601916b0905`**。这是 2026 年 9 月 13 日核查的公开版本，不自动等于论文历史执行的代码快照。非患者场景、工具、评分和提示采用 MIT 许可；患者队列、标签和原始记录通过独立权限流程获取。[固定代码](https://github.com/scaleapi/clinicare/tree/bbce780bc0dab07aae584f4dbc097601916b0905)

静态目录核查得到 25 份场景、25 组来源参考、25 组发现参考和 25 组规则文档集合。来源清单合计 140 个场景内条目、每场景 3–9 个；发现清单合计 167 个、每场景 4–11 个；规则文档集合合计 63 个场景内引用、每场景 1–4 个。它们是跨场景可重复的引用次数，不是 140 张不同的表或 63 份不同文档。共同规则语料库另外列出 67 份文档。

复现入口可按以下顺序理解，本文没有执行这些带数据或模型调用的步骤：

1. 按 `DATA_ACCESS.md` 获取三个指定 MIMIC 版本以及正式 `full750.csv`、`dev148.csv` 队列，准备规则文档。公开仓库不能替代患者访问权限。
2. 将原始表转换为可查询格式，配置持有数据访问权的工具服务，构建 Docker 运行镜像。
3. 用 `benchmark/scripts/build_tasks.py` 构建正式任务；开发集用 `build_dev148.py` 固定 ID，不重新按当前标签抽样。
4. 用 `scripts/run_sweep.py` 启动指定系统。它处理侧车环境与系统配置；直接调用裸 Harbor 命令不一定包含所需工具服务。
5. 运行结束后先做确定性四分类和引用检查，再用 `benchmark/eval/grade.py` 调用语义评分。只有明确选用 `--skip-llm` 才跳过这部分模型费用。
6. 根据任务 ID、模板、标签版本、judge 配置和评分覆盖率汇总，分别计算主表、148 例配对消融和三次运行交集。

当前模板配置 2 CPU、8 GB 内存、20 GB 存储，agent 时限 5,400 秒、验证器时限 1,800 秒；需要 Python 3.12 以上和 Docker，另有 Modal 路径。这是公开配置，不是论文已披露全部运行预算。主表的美元成本是每次运行的均值、不含 judge；turn、工具数及 work-token 使用中位数。Work-token 是未命中缓存的输入加输出，不同服务对缓存、shell 内工具调用和费用的记录方式不同，论文因而对 opencode 给估算范围，不能把范围端点当作精确成本排名。

### 论文定义与当前代码需要分别记录

**参考标签不能仅靠生成脚本重建。** `finalize_cohort.py` 按模型共识优先、固定种子选样，并跳过无共识候选；注释明确说它不能生成医生已经裁决的分歧标签。重新运行它不会自动得到原来 750 例的正式标签。`build_dev148.py` 从固定 ID 清单读取成员，因为改标签再按“每类两例”抽样会改变配对案例。

**来源覆盖的代码粒度较粗。** 论文定义要求正确患者、就诊和时间范围；当前 `evidence_retrieval_recall.py` 的来源归因函数主要通过工具—表名映射和 SQL 的 FROM/JOIN 提取表集合，函数本身没有重新检查这些范围。本文用两个仅患者参数不同的合成记录离线核查，均被归因为同一来源表。它证明的是该评分函数的检查边界，不能据此宣称论文运行检索了错误患者。

**断言评分使用的证据范围不同。** 论文把 $P_{\rm claim}$ 定义为所引证据对相应断言的支持；公开 `insight_grounding_llm.py` 先抽取原子断言，再将它们交给该次完整检索证据池判断，并未为每个断言单独限制到它引用的记录。代码要求患者和时间归属一致，但“检索池中能找到支持”和“所引用那条记录支持此句”不是完全相同的检查。当前结果解释应保留这一差别。

**分块与失败会影响语义评分。** 当前过程 judge 在约 500,000 字符以上分块，目标约每块 300,000 字符，按 met 做或合并；患者断言 judge 默认每 20 条一批、证据每块约 350,000 字符，跨块优先接受 supported，再考虑 contradicted、unverifiable。这些是字符限制，不是 token 限制。过程分块中部分调用失败时会记录错误，并可能用成功块继续产生结果，因此复算时要检查 `chunk_info`，不能只读取最终百分数。

**统计输入需要固定。** 代码把缺报告和评审失败分开记录，过程评分带覆盖检查与输入哈希；但汇总函数仍假定传入的任务已去重。当前源码还有旧运行的注释数字，不能用注释里的旧标签分布替代论文正式结果。相同版本代码加上不同队列、rubric 或任务模板，也不会构成同一次复现。

完整患者文件、最终报告和逐例轨迹没有包含在公开仓库中；规则语料的一部分需从原始发布方本地构建，转换也不保证字节完全一致。本文核查了公开配置、场景规范、评分、标签生成与固定开发集入口，运行了不联网的纯函数算例，**没有重跑任何模型、人工裁决或受限患者数据实验**。原文支持的是这一特定历史病历分布上的审查能力分析，而非临床疗效、跨医院稳定性或已经获准自主部署。

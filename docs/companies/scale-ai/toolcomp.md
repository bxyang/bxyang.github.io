# ToolComp：多工具推理与过程监督

一个工具型助手可能找对了搜索接口，却把上一轮检索到的死亡率抄错；也可能中途走错一步，随后纠正，最后算出正确答案。ToolComp 将这两层表现分开测量：一层让模型实际调用工具、提交答案；另一层给模型一段已经核实的历史，让它在原始错误步骤和人工改写之间做选择。论文还训练了过程奖励模型，用每一步的分数筛选完整轨迹。在这一筛选实验里，过程监督优于只看完整结果的监督；这项结果对应多候选排序，不是单次执行或强化学习后的成功率。[论文 §3–5](https://arxiv.org/html/2501.01290v1)

## 任务需要把检索结果传给下一步计算

论文附录 F.2 给了一个完整案例：使用日本 2023 年的人口、出生率和死亡率，在没有迁移的假设下，估算十年后的人口。正确流程需要先查资料，再把统一单位的数据送进 Python，最后返回人数。原始模型把计算放在资料检索之前；人工首先调整行动计划，随后逐步纠正检索词和计算参数。

该例实际采用的数值是人口 $P_0=124620000$、每千人出生率 $b=6.6$、每千人死亡率 $d=11.7$。按附录的固定年增长率假设：

$$
g=\frac{b-d}{1000}=-0.0051,
\qquad
P_{10}=P_0(1+g)^{10}\approx118408275.36.
$$

这是论文样例的计算过程，不是对人口变化的现实预测。标注中，模型曾把人口写成 124,352,000、增长率写成正的 0.0012；人工修改的是传入 Python 的参数。最后，人工还把答案中的千位分隔符去掉。由此能看到，过程标签既涉及资料使用和计算，也可能涉及最终格式。[论文附录 F.2，PDF 第 42–44 页](https://arxiv.org/html/2501.01290v1)

另一例是把边长两英寸的立方盒放进卡车。附录 F.1 按给定内部尺寸逐个方向向下取整，相乘得到 $158\times46\times49=356132$，而不是简单地用两者体积相除。这里也有明确的几何假设：按轴向整齐摆放、把空间视为长方体。该例用于说明搜索与计算的依赖关系，不能把它解释成考虑车内全部结构后的实际装载测量。

## 两个子集提供不同的工具集合

ToolComp 关注纯文本的信息检索与处理，减少图片理解、文件解析和特定软件环境熟悉度对结果的影响。与只检查一次函数选择的任务相比，它要求连续工具调用；与只检查最终答案的任务相比，它提供中间步骤的人工修正。论文表 1 对其他基准的比较是发表时的版本比较，不适用于后来扩展的任务集。

| 子集 | 论文任务数 | 可用工具 |
| --- | ---: | --- |
| ToolComp-Chat | 198 | Google Search、Python |
| ToolComp-Enterprise | 287 | 上述两项，加日期、当前天气、历史天气、计算器、Wikipedia、Wolfram Alpha、日内股票数据、日线股票数据、股票代码检索，共 11 项 |

这项限制贯穿出题、标注和评测。Enterprise 是更大的 API 集合，并不是企业数据库操作、发邮件或执行交易的任务。股票工具返回行情，天气工具返回观测数据，Google Search 返回搜索摘要；附录 G 明确说搜索工具不提供所链接网页的完整内容。模型还必须处理接口单位，例如天气输出示例使用华氏度，而默认答案格式要求摄氏度。[论文 §3.1、§3.4、附录 G](https://arxiv.org/html/2501.01290v1)

一次 ReAct 步骤包含四部分：Thought 说明下一步的理由，Action 指定工具，Action Input 给出参数，Observation 记录工具返回值。模型先生成行动计划，再不断产生步骤，直到调用 `finish`。这是一套可见的交互记录；对记录的判断不等于直接测量模型内部的全部推理。

当前原生工具调用实现会按任务的工具列表建立允许调用的映射，对名单之外的工具返回不可用提示。Python 通过 Sphere Engine 远程执行，接口指定 Python 3.9.5，说明可使用 NumPy、pandas、SciPy，并要求打印结果。论文说明代码在沙箱中执行，但没有给出所有网络、文件系统和资源隔离配置，因此不能从论文推出一个更宽泛的环境权限保证。[固定版本工具与模型实现](https://github.com/vaskar-nath/toolcomp/tree/8a9bffe1175e57c683dacdc119b9c71d22e231d4/tools)

## 人工修改是在正确历史上继续进行的

### 出题、筛选和复核

作者先手写少量示例及出题思路，让模型根据随机抽取的示例和工具组合生成候选。随后把候选分为合格、过于简单、不合理三类，附上理由，再用这些例子指导 GPT-4 Turbo 筛选。经过三轮迭代，人工处理剩余的复杂度、表述和歧义问题。标注要求至少两次工具调用，并尽量保证答案唯一、便于核对；论文没有披露人工基准候选总量、各轮淘汰数量或标注员间一致性统计。[论文附录 C.1–C.3](https://arxiv.org/html/2501.01290v1)

每个任务由 FireFunction-V1 先提出行动计划。人工判断计划是否合理；需要时改写，再让模型在修正后的计划下继续。对后续每一步，人工分别标注 Thought、Action、Action Input 为正确或错误，把错误部分重写后放回历史。Observation 是执行工具后的返回信息，不是这三个判断项之一。

这一过程持续到模型提出的 `finish` 被人工认可，或人工认为已有足够信息而把下一步改为 `finish`。最终得到的是一条人工认可的解题路径，以及发生过分歧的原始步骤和修正步骤。因此，过程评测中的历史通常已经纠正；它与让模型自行修复任意一条累积错误的轨迹不同。[论文 §3.5、图 1](https://arxiv.org/html/2501.01290v1)

全量样本随后经过人工检查；作者和三位可信标注员再做一轮复核。最后用 GPT-4o（2024 年 5 月）、GPT-4 Turbo、Claude 3.5 Sonnet、Llama 3.1 405B 跑完整基准，对四者都与参考答案不同的题目再次检查。这能发现难题和潜在标注错误，但四个模型全错本身不证明参考答案有错，最终仍需复核。

### 标注标准包含工具使用约束

附录 E.4 的合成数据 Critic 提示要求：即便是简单算术、单位换算或已知股票代码，也应依据工具返回的信息来行动，不能直接使用未在提示或工具结果中提供的外部知识。它还要求在大体合理时给模型宽松判断，只纠正明显不合适的步骤。过程标签因此反映的是这套工具使用协议下的合理性，不能等同于所有可能解法中的唯一正确下一步。

附录 C 的分布图显示，作者统计约 85% 的任务至少需要三次工具调用，约 20% 需要七次或更多。Google Search 和 Python 使用较多，既因为 Chat 只允许这两种工具，也因为它们覆盖检索与计算。题目涉及算术、地理、气象、金融等，领域标签可以重叠，不能把领域频数相加当作任务总数。[论文图 11–17](https://arxiv.org/html/2501.01290v1)

## 最终答案与过程判断使用不同的分数

### 最终答案允许格式差异和数值容差

主表使用 GPT-4 Turbo 判断题目、参考答案与模型答案，分为错误、正确但格式不佳、正确。后两类都算答对。若第 $i$ 题的分类为 $g_i$，则最终准确率可写为：

$$
A_{\mathrm{final}}=\frac{1}{N}\sum_{i=1}^{N}
\mathbf1\{g_i\in\{\text{正确},\text{正确但格式不佳}\}\}.
$$

参考答案不会由裁判重新求解。附录 E.5 还允许数值与参考值相差不超过约 10%；未指定排序时可以接受列表元素顺序不同，明确指定排序时则要求一致。因此，这不是只放宽标点的严格答案匹配，数值容差本身也影响通过率。相对容差如何处理零值等边界，没有完整的逐项规则。[论文 §4.1、附录 E.5](https://arxiv.org/html/2501.01290v1)

附录 A.1 另报程序化 Exact Match：字符串去首尾空格并转小写；列表区分是否要求排序；数值也允许一个容差参数。所以这里的 Exact Match 也不是原始字节完全一致。论文没有给出该数值参数的统一具体值，不能直接假定它与主表裁判的 10% 相同。

模型未输出符合要求的最终答案时，论文允许最多三次重试；限流或工具端点故障另行记录和重试。除 o1-preview 使用 ReAct 提示外，其他模型用原生函数调用。不同接口路径和失败重试均属于实验设置，主表不能视为严格单次采样的 Pass@1。

### 过程判断需要交换候选顺序

过程任务给出原始错误步骤与人工修正步骤，模型判断哪一个更合适，也可以选择平局。每个比较交换顺序再预测一次：两次都选中人工修正才记 1；两次都选中原始步骤记 0；至少一次平局，或交换前后始终选择同一位置，记 0.5。

$$
s_i\in\{0,0.5,1\},\qquad
A_{\mathrm{process}}=\frac{1}{M}\sum_{i=1}^{M}s_i.
$$

这里 $M$ 是过程比较条数，不是原始问题数量；表 3 还分别统计行动计划和 ReAct 步骤。举例说，一个裁判永远选第一个位置，交换位置后的两次判断合在一起得到 0.5。因此“80% 的过程分”并不表示独立标注了 80% 的步骤全部正确，也不等于该模型自己的轨迹有 80% 正确。[论文 §4.3](https://arxiv.org/html/2501.01290v1)

## 奖励模型用另一批合成数据训练

### 从 75,000 个候选题得到训练轨迹

奖励模型实验没有直接把那 485 道人工基准题当作训练集。作者另行生成约 75,000 道候选题，以 GPT-4o（2024-05）、GPT-4 Turbo、Claude 3.5 Sonnet、Llama 3.1 70B 的最终答案一致性替代成本较高的人工精修，保留 17,369 道。这个 Llama 是 70B，与人工基准末轮质检用的 405B 不同。

接着由 Llama 3.1 8B Instruct 产生轨迹，GPT-4o 充当 Critic，逐步检查和修正。模型在修正后的历史上继续，最多允许 15 个步骤；没有到达最终答案的原始或修正轨迹会被丢弃。策略模型温度为 0.5，最大新增 1,024 tokens；Critic 温度为 0，最大新增 4,096 tokens；每一步最多重试三次。[论文附录 D.1、表 8–9](https://arxiv.org/html/2501.01290v1)

| 阶段或训练集合 | 论文数量 | 计数单位 |
| --- | ---: | --- |
| 初始合成题 | 约 75,000 | 候选题 |
| 四模型最终答案一致 | 17,369 | 题 |
| 到达最终答案 | 13,628 | 表 8 标为轨迹 |
| 最终答案格式合格 | 11,654 | 表 8 的轨迹数量 |

表 8、表 10 与 D.2 均使用 11,654，但 D.1 第 31 页有一句把格式合格数量写成 10,342；公开评测数据无法消解这处训练集计数冲突。本文保留表格口径。ORM 与 PRM 的样本单位不同，14,932 与 11,654 也不能理解成完全等量训练 token 的公平对照。

ORM 的偏好项是完整修正轨迹，非偏好项是原始策略轨迹；PRM 则取每次修正前后的步骤，条件历史使用已经纠正的路径。这里“偏好”源于 Critic 的修正流程，不是对每条生成轨迹都做了独立人工正确性证明。四模型答案一致也不能保证共同答案一定正确。论文没有给出足以重建所有过滤决定和验证训练测试无重叠的逐项记录。

### 在指定位置预测正确概率

ORM、PRM 都从 Llama 3.1 8B Instruct 初始化，加一个线性奖励头。把隐藏状态 $h_j$ 映射为标量，再经 sigmoid 得到 $p_j=\sigma(w^\top h_j+b)$。以下是对附录 D.3 的数学整理：在有标签的奖励标记位置集合 $\mathcal J$ 上，最小化平均二元交叉熵：

$$
\mathcal L_{\mathrm{BCE}}
=-\frac{1}{|\mathcal J|}\sum_{j\in\mathcal J}
\left[y_j\log p_j+(1-y_j)\log(1-p_j)\right].
$$

其中 $y_j\in\{0,1\}$ 表示对应监督目标，$p_j\in(0,1)$ 越大表示奖励模型越认可该目标。ORM 在整条轨迹尾部、EOS 之前放一个特殊 RM token。PRM 比较四种标记方式：

| PRM 形式 | 每步奖励标记位置 |
| --- | --- |
| 完整步骤，含 Observation | 工具返回之后放一个标记 |
| 完整步骤，不含 Observation | Action Input 之后放一个标记 |
| 子步骤，含 Observation | Thought、Action、Action Input、Observation 后分别放标记 |
| 子步骤，不含 Observation | 只在前三项后放标记 |

这解释了“过程监督”的两个变化：模型看到的信息是否包含真实工具返回，以及一个步骤提供一个还是多个监督位置。论文没有把 Observation 标签的全部构造边界写成可直接运行的算法，不能因为它出现在模型输入里，就假定观察值本身经过了独立事实验证。[论文 §5.1、附录 D.2–D.3](https://arxiv.org/html/2501.01290v1)

训练基于 PyTorch 和修改后的 OpenRLHF。ORM、PRM 都训练 3 epochs、batch size 64、上下文长度 16,384、种子 42、ZeRO stage 2；在 $10^{-5},10^{-6},9\times10^{-7},6\times10^{-7},10^{-7}$ 中搜索学习率，用保留的 10% 合成验证集选择模型。作者说 PRM 通常选 $9\times10^{-7}$，ORM 通常选 $10^{-6}$。SFT 训练 5 epochs、ZeRO stage 3，其余上述 batch、上下文、种子一致，学习率候选为 $10^{-5},10^{-6},10^{-7}$。这些是训练配置，不是多随机种子重复结果；论文没有报告完整 GPU 型号、总训练时长与费用。[论文附录 D.4–D.5、表 11–12](https://arxiv.org/html/2501.01290v1)

## 从 30 条候选中选一条，过程监督效果更好

### 排序实验的分母和重复方式

作者分别使用原始 Llama 3.1 8B Instruct，以及在全部修正轨迹上训练的 SFT 模型，每题生成 50 条候选。附录 D.4 说明先丢弃没有到达最终答案的候选，再做排序。随后每轮从候选集合取 30 条，共做 500 次随机重采样，报告选中第一名的答案准确率。

设 $C_i^{(b)}$ 是第 $b$ 次采样给第 $i$ 题的候选集，$R(\tau)$ 是轨迹分数，则选中的轨迹为：

$$
\hat\tau_i^{(b)}=\arg\max_{\tau\in C_i^{(b)}}R(\tau),
\qquad
\mathrm{rank@1}^{(b)}=\frac1N\sum_i
\mathbf1\{\hat\tau_i^{(b)}\text{ 的最终答案正确}\}.
$$

ORM 直接使用完整轨迹的正确概率。PRM 对各步概率 $p_1,\ldots,p_T$ 做聚合，测试了最大值、最小值、均值与乘积。图 3 的区间反映从固定候选池反复抽样的变化，不代表重新训练 500 个模型，也不涵盖 API、训练种子和新题分布的所有不确定性。对过滤后不足 30 条、完全没有终止候选等情况，原文未给出充分的实现细节，因此不能擅自补上补采或失败计零规则。

### 主要数字对应筛选后的答案

在原始模型生成的候选上，PRM 的 rank@1 为 42.65%，ORM 为 23.89%，差值是 **18.76 个百分点**，相对 ORM 约提高 78.5%。摘要的“19% improvement”应结合这两个数理解为约 19 个百分点。

在 SFT 模型候选上，最佳 PRM 达到 60.25%，图 3 中 ORM 约为 49%，对应摘要所说的约 11 个百分点。该图的 SFT Pass@30 上界约为 70%；60.25% 仍低于这一上界。这里的 Pass@30 表示候选中有正确答案的机会，rank@1 表示排序器实际挑中正确答案的比例，两者不同。图中的 greedy Pass@1 又是单独的生成基线。[论文 §5.2、图 3、表 4](https://arxiv.org/html/2501.01290v1)

### Observation、监督粒度与聚合方式

| 全量训练下的 PRM 监督方式 | rank@1 |
| --- | ---: |
| 完整步骤，含 Observation | 60.25% |
| 完整步骤，不含 Observation | 55.43% |
| 子步骤，含 Observation | 49.48% |
| 子步骤，不含 Observation | 45.70% |

包含 Observation 时，完整步骤监督比不包含时高 4.82 个百分点；子步骤监督对应增加 3.78 个百分点。完整步骤优于子步骤的结果出现在这一数据生成与标签协议中。作者提出更细标签可能带来噪声的解释，但没有单独测量各子标签噪声率或随机控制噪声实验，所以不能把解释写成已证实的原因。

| 同一个最佳 PRM 的步骤聚合方式 | rank@1 |
| --- | ---: |
| $\max_t p_t$ | 60.25% |
| $\min_t p_t$ | 23.68% |
| $T^{-1}\sum_t p_t$ | 25.74% |
| $\prod_t p_t$ | 23.06% |

作者观察到，一条轨迹可能犯错后恢复；取最小值或均值会让之前的错误继续压低得分。乘积还会随长度下降。以说明性数值为例，所有步骤都得 0.9 时，三步乘积为 0.729，十步乘积约为 0.349。取最大值不受这种乘积长度效应影响。图 4 中，被选中轨迹的最高分步骤更常靠近后段，作者据此解释其与完成任务的关联。

这个最大值只是经验上有效的排序分数，**不能当作“整条轨迹所有步骤都正确”的概率**。表 5 没有报告各差值的配对检验，图 4 也只分析被选中的轨迹。[论文表 4–5、图 4](https://arxiv.org/html/2501.01290v1)

附录 B 再按人工轨迹长度划分简单 199 题（1–4 步）、中等 210 题（5–8 步）、困难 62 题（9–12 步），图中困难组的 PRM、ORM 差距较大。该实验排序的是全部 50 条候选，与图 3 的 30 条设置不同；三组总计 471 题，未覆盖论文总量 485 题，原文未逐题解释其余 14 题。轨迹长度也只是复杂度代理，同一题可能有更短的合法路径。

### 当前实现中会影响结果的差异

首先，`grade/llm_grade.py` 已把最终答案裁判设为 `openai/o1`，论文使用 GPT-4 Turbo。其示例 6 将“明确要求字母排序，但列表顺序错误”判为“正确但格式不佳”，而论文 E.5.3 的相同情境判错。当前代码又把“正确但格式不佳”计入正确数。这不是更换模型名称这一处差别，评分提示也发生了变化。[当前评分实现](https://github.com/vaskar-nath/toolcomp/blob/8a9bffe1175e57c683dacdc119b9c71d22e231d4/grade/llm_grade.py)

其次，当前过程脚本对解析不出的 `unknown` 也给 0.5；但提示构造失败、请求失败或其他异常会被记为无效，并从汇总分母排除。报告时必须同时列出有效样本数和失败数。源码中 `use_responses_api = "o3" or "o1" in ...` 的第一个字符串恒为真，会对所有模型走 Responses 路径，这是需要先修正或确认适配行为的实现问题。[当前过程脚本](https://github.com/vaskar-nath/toolcomp/blob/8a9bffe1175e57c683dacdc119b9c71d22e231d4/inference/llm_as_judge_inference.py)

再次，`run_toolcomp.sh` 当前设置为 2025 年的 Claude 模型、整题尝试三次、`max_depth=30`。然而 native 分支不接收这个深度参数，而在模型封装中固定最多 100 轮工具调用循环；一轮还可能包含多个工具调用。不能把 shell 参数解释成两条路径统一的 30 次工具预算。native 的完成检查使用 `{"final_answer":` 子串，也不同于论文文字中的可解析 JSON 检查。[执行流程](https://github.com/vaskar-nath/toolcomp/blob/8a9bffe1175e57c683dacdc119b9c71d22e231d4/pipeline/generate.py)、[模型封装](https://github.com/vaskar-nath/toolcomp/blob/8a9bffe1175e57c683dacdc119b9c71d22e231d4/model/models.py)

## 复现步骤与仍然缺少的材料

最终答案评测从 `main.py` 生成轨迹，再用 `grade/llm_grade.py` 评分；过程评测入口为 `inference/llm_as_judge_inference.py`。下载的 Parquet 需要转换成脚本接收的 JSONL。过程数据的 `history` 原本是列表，入口会将其序列化成 JSON 字符串，供提示构造函数解析；`tools` 则会从字符串转换为列表。直接手动改字段时需要保留这种兼容关系。

实际运行前需固定题集版本、工具接口、日期处理、模型配置、评分提示、终止规则和重试预算，并分别记录 Chat、Enterprise、行动计划、ReAct 的分母。当前过程提示在缺失历史日期时使用 2024 年 9 月 3 日，执行提示的日期函数则默认当前日期；这不代表搜索结果和外部 API 的返回已经冻结到对应日期。

仓库依赖模型 API 网关以及搜索、Wolfram Alpha、行情和 Sphere Engine 等服务。重采样排序还要先为每题准备大量完整执行轨迹，费用不能只按一次裁判调用估算。本文没有执行任何模型、工具调用评测或训练；以上复现说明来自静态代码与公开数据检查。

当前核查的仓库主要提供评测入口，没有找到论文修改过的 OpenRLHF 奖励训练实现、对应 ORM/PRM 权重、完整合成训练集，以及用于 50 候选排序的全部生成记录。因此，可以据公开材料重新搭建流程，但尚不能凭这些文件逐项重现论文的奖励模型结果。论文也没有做把 PRM 接入强化学习更新策略的实验，其结论应限定在所用合成数据、两种生成器和这些工具任务上的候选排序。

ToolComp 覆盖的是文本检索和计算工具链；没有验证多模态工具、企业系统写操作或广泛的交互环境。其过程标签提供了比最终答案更细的观察，但仍受标注协议、Critic 判断和预先修正历史的条件限制。长期复测还需要考虑动态网页、行情与天气接口的变化，以及公开后训练数据污染的可能性。[论文 §6–8](https://arxiv.org/html/2501.01290v1)

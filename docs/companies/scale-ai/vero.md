# VeRO：让编码智能体改进其他智能体的程序

## 1. 摘要翻译

以下完整翻译 [v4 摘要](https://arxiv.org/abs/2602.22480v4)。原文由 Varun Ursekar 等五位作者撰写，采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)；中文为翻译版本。

编码智能体的一项重要新应用，是智能体框架优化：通过编辑和评估目标智能体的代码，迭代改进它。尽管这一任务具有重要意义，研究社区仍缺少对编码智能体在此任务上表现的系统认识。框架优化不同于传统软件工程：智能体框架将确定性的代码与具有随机性的大语言模型生成交织在一起，因此需要结构化地记录中间执行轨迹和下游结果。

为应对这些挑战，我们提出：（1）VeRO，即版本、奖励与观察，一个为目标框架提供版本快照、受预算控制的评估和结构化执行轨迹的外层框架；（2）VeRO-Bench，一套由目标智能体、任务和参考评估流程组成的基准。利用 VeRO，我们开展实证研究，跨任务比较优化器，并分析哪些修改能够可靠地改进目标智能体框架。我们发布 VeRO，以支持将智能体优化作为编码智能体核心能力的研究。代码见 [项目仓库](https://github.com/scaleapi/vero)。

## 2. 研究背景与相关研究

一个智能体的表现不仅取决于模型，还取决于提示、工具和控制流程。工程师通常先查看失败记录，再修改程序、重新运行。这一过程可以交给编码智能体，但模型调用有随机性，某次分数上涨未必来自有效修改，因此需要记录版本和评估条件。

Related Work 将自动优化分为几类。DSPy 等方法主要调整提示和示例；TextGrad、Trace 等利用计算图组织反馈；ADAS、AFlow 等进一步搜索程序或工作流结构。一般代码基准则评估代码是否完成指定任务，很少直接衡量“改进另一个智能体”的能力。

VeRO 将完整程序作为修改对象，为不同优化器提供一致的反馈、版本和预算管理。论文也讨论了同期独立工作的 Meta-Harness：二者研究相近问题，但对轨迹访问和优化边界的约束不同。[论文第 1—2 节](https://arxiv.org/pdf/2602.22480v4)

## 3. 核心贡献

**核心问题。** 如何让编码智能体反复修改目标程序，同时能够明确比较改了什么、用了多少评估资源，以及修改是否改善了任务表现。

**核心方案。** VeRO 为每次代码修改保存版本快照，将评估结果与对应版本绑定，并保留输入、工具调用、错误和分数。优化器在限定预算内查看反馈、提出修改，框架限制其访问测试数据或修改评估规则。配套 VeRO-Bench 覆盖数学、问答和工具使用等任务；目标模型保持固定，改进来自外围程序。[论文第 3—4 节](https://arxiv.org/pdf/2602.22480v4)

**主要结论。** 在五项主基准中，VeRO 默认配置的平均分从初始程序的 0.50 提高到 0.61。收益主要出现在工具使用和信息检索任务；数学及专业推理任务改善有限。优化器的指令也会影响结果稳定性和跨任务迁移，程序在一个任务上变好不保证在另一个任务上同样变好。

作者还发现，编码智能体经常回到修改提示的做法，对工具和程序结构的探索较少。VeRO 的贡献因此包括可比较的优化流程，以及对现有优化器行为的观察。[论文第 5 节](https://arxiv.org/pdf/2602.22480v4)

这些结果依赖所选目标程序、任务和预算。预算主要按评估调用计量，没有统一所有 token 或 API 成本；长流程代码案例还在同一组任务上优化和报告分数，不能将其当作独立测试集上的泛化结果。[论文第 4.4、6—7 节](https://arxiv.org/pdf/2602.22480v4)

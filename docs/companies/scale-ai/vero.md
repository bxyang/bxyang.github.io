# VeRO：用 coding agent 优化 agent

一个检索 agent 经常答错，原因可能是搜索结果处理不完整，也可能是提示没有说明何时重试。VeRO 让另一个编码 agent 阅读执行记录、修改源码、重新评测，再选择效果较好的版本。目标模型的权重保持不变，改动范围可以覆盖提示、工具和执行逻辑。论文中，完整 VeRO-Agent 配置在五项任务上的平均分从基线约 0.50 提高到 0.61，但收益主要来自检索与工具任务；GPQA、MATH 的改善很小。跨模型、跨任务的结果还表明，一次有效改动并不保证能迁移到其他环境。[论文 §3–5、表 2–3](https://arxiv.org/pdf/2602.22480v4)

## 把优化问题写成可检查的过程

目标任务记为 $T=(I,O,E)$。$I$ 是输入，例如一道问题；$O$ 包含最终回答及执行轨迹；评分函数 $E:O\rightarrow[0,1]$ 可以检查答案，也可以检查动作结果。目标 agent $A:I\rightarrow O$ 是会调用模型和工具的程序。

论文希望找到在保留数据上期望分数最高的实现：

$$
A^*=\arg\max_{A\in\mathcal A_r}
\mathbb E_{x\sim D_{\rm test},A,E}[E(A(x))],
\qquad n_E\le B.
$$

$\mathcal A_r$ 是满足限制的程序集合，例如不能换目标模型，不能修改评分程序，也不能读取测试答案；$B$ 是评测预算，$n_E$ 是已使用次数。期望同时包含问题抽样、目标 agent 和评分器的随机性。它是问题定义，**不是允许优化器直接在测试答案上搜索**；实际过程依靠训练反馈和版本选择，再测保留集。[§3.1](https://arxiv.org/pdf/2602.22480v4)

相对初始实现 $A_0$ 的改进可写作：

$$
\Delta(A)=\mathbb E_x[E(A(x))-E(A_0(x))].
$$

例如作为说明，在同一组 100 个二元任务上，基线做对 40 个、新版做对 48 个，差值为 8 个百分点，相对正确率提高 20%。这两个量不同。论文表中的 0.50 到 0.61 也是约 11 个百分点，不能写成相对只提高 11%。

编码优化器 $S$ 根据既有版本、轨迹和背景信息提出下一版：

$$
A_{t+1}=S\!\left(f(\{A_i,\tau_i\}_{i=0}^{t}),C\right).
$$

其中 $\tau_i$ 包含输入、输出和分数，$C$ 包含任务说明及优化指导；$f$ 决定能看到哪些历史、哪些轨迹细节，以及通过什么工具读取。相同的编码模型，如果只能看总分，或能逐条检查失败，获得的信息就不同。VeRO 主要围绕这个观察接口及执行协议建立基础设施，没有规定必须采用某一种搜索算法。[§3.1–3.3](https://arxiv.org/pdf/2602.22480v4)

## 一次改动如何留下版本、分数和证据

论文提出六项要求：改动留版本、限制预算、控制权限、固定执行环境、记录结构化轨迹，以及统一观察接口。具体实现分成五个部分。

| 组成部分 | 负责的工作 |
| --- | --- |
| Git worktree | 隔离候选修改，保留提交、差异及回退历史 |
| Dataset | 管理训练、验证、测试划分，控制哪些数据可以查看 |
| Filesystem | 按路径规则控制读写，保护评测程序和不允许访问的资料 |
| Experiment Database | 保存逐题结果、错误、轨迹和汇总统计 |
| Evaluator | 按指定提交运行目标 agent，保存结果并扣减预算 |

典型循环是先看代码与训练样本，再检查失败记录，提出改动并保存为提交，调用 `ExperimentRunner` 评测，然后继续修改或回退。一个逻辑上的优化阶段可以有多个代码提交；论文的 phase 指相邻两次评测之间的一系列改动，不等于 Git 提交数，也不等于模型消息数。[算法 1、附录 A.1、A.2.5](https://arxiv.org/pdf/2602.22480v4)

目标程序以带锁文件的 Python 项目运行，便于重新检查同一个提交。但固定源码和依赖不能消除模型抽样、搜索结果变化及外部 API 故障。论文主实验三次独立优化主要反映优化器的变化，没有对每个候选提交反复评测到足以分离所有执行噪声。[§4.1、附录 A.6](https://arxiv.org/pdf/2602.22480v4)

## 数据集经过怎样的选择

主实验的目标模型统一为 GPT-4.1 mini。任务划分和初始工具如下；这些规模属于 VeRO 的实验子集，不是五个原始 benchmark 的总量。[表 1、附录 A.2.1](https://arxiv.org/pdf/2602.22480v4)

| 任务 | 训练 / 验证 / 测试 | 初始工具与用途 |
| --- | --- | --- |
| GAIA | 50 / 87 / 无 | 初始无工具；研究多步问答及工具扩展 |
| GPQA Diamond | 98 / 无 / 100 | 初始无工具；科学选择题 |
| MATH | 59 / 60 / 486 | 初始无工具；数学推理 |
| τ-bench Retail | 100 / 20 / 115 | 保留原零售工具与交互环境 |
| SimpleQA | 46 / 45 / 80 | 初始 Wikipedia 工具；事实问答 |

GAIA 的划分需要修正一个容易跟着论文误读的地方。附录把 165 条称为公开 train、87 条称为 validation；[GAIA 官方资料](https://huggingface.co/datasets/gaia-benchmark/GAIA)将公开带答案部分称为 validation。论文代码的映射文件也显示，VeRO 的 50 条训练和 87 条验证**全部取自原始 `validation`**。本次逐项计数确认两组不重叠，共 137 条；映射中另有原始 test 项，但构建器明确跳过它们。因此 50/87 是这项研究的再划分，不能当成 GAIA 原生 train/validation 大小。[固定代码的数据构建器](https://github.com/scaleapi/vero/blob/4ae9c1df1e5d303b875629fa53b686a211897c4e/vero-benchmarking/src/vero_benchmarking/datasets.py)

GAIA 没有另一个独立的最终测试划分，论文用验证集选择版本，也在这 87 条上报告结果；它不具备三段划分中最后一段从未用于选择的性质。GPQA 则以训练成绩选择版本，再评测保留的 100 题，作者承认训练选择存在过拟合风险。GPQA 代码还对答案选项重新排列，答案索引尽量均衡，种子为 42。

SimpleQA 的代码先从 `google/simpleqa-verified` 选参考 URL 含 Wikipedia 的题，再应用 171 个固定索引，最后分为 46/45/80。论文把这批题描述为 GPT-4.1、Sonnet 4.5 和 Gemini 2.5 Pro 直接作答都失败的较难问题。公开索引可以核对数量，但仅凭索引不能复算三模型筛选时的原始成绩。MATH 的映射包含 119 条待分数据和 486 条测试，前者再拆为 59/60；τ-bench 构建器从已有结果表取任务 ID 和 split，再抽取 100 个训练任务。重跑时还需固定上游数据版本，不能只保留随机种子。

## 优化器配置和预算的实际含义

论文比较 8 个配置，每个在 5 个任务上独立运行 3 次，共 $8\times5\times3=120$ 次。优化器温度设为 1.0；它与目标 agent 使用的模型不是同一个概念。[§4.1、表 6](https://arxiv.org/pdf/2602.22480v4)

| 配置 | 可以怎样修改与观察 |
| --- | --- |
| Claude Code Pure | 使用原生文件、终端等工具，自行运行并解析目标程序，无 VeRO 工具和自动提交记录 |
| Claude Code + VeRO Tools | 增加评测、轨迹、数据及设计材料接口，文件改动由 hook 记录 |
| VeRO-Agent Default | 完整工具、设计模式库及子 agent 调度 |
| VeRO-Agent Orchestrator | 主 agent 主要协调评测、版本和计划，文件修改委托给有完整工具的子 agent |
| VeRO-Agent Resources Only | 仅修改 `@resource` 标记的提示、工具说明、参数等区域 |
| GEPA | 在与 Resources Only 对应的组件范围内进行反思式搜索 |

Orchestrator 分别使用 Sonnet 4.5、Opus 4.5、GPT-5.2-Codex，因此合计为 8 项配置。GEPA 与 Resources Only 搜索范围接近，可以比较搜索方法；Default 还改变可修改的程序范围，不是只换一个相同约束下的搜索器。

正文把主预算写成 $B=8$，附录解释为整批训练或验证评测调用。但公开 `paper-v1` 任务配置对多数任务分别设置 `train_budget=8` 和 `validation_budget=8`，程序按 split 各自扣减。因而按发布配置运行，最多可以调用 8 次训练和 8 次验证，不能简单解释为两者合计最多 8 次。GPQA 没有验证预算；初始和最终报告评测又由外层入口执行，需分开记录。[GAIA 配置](https://github.com/scaleapi/vero/blob/4ae9c1df1e5d303b875629fa53b686a211897c4e/vero-benchmarking/src/vero_benchmarking/tasks/gaia.py)、[预算实现](https://github.com/scaleapi/vero/blob/4ae9c1df1e5d303b875629fa53b686a211897c4e/vero/src/vero/tools/experiment_runner.py)

预算也不等于费用预算。一次调用运行多少题、目标 agent 用多少 token、优化器看多少材料，都影响总成本。正文只比较调用次数，并没有把各配置完整的 token、美元和墙钟时间全部匹配。附录明确把这列为限制。

## 五项主结果

下表摘录表 2 的平均成绩：每个配置先在每次优化中选择一个候选，再汇总三次运行。这里只保留均值，不把原表括号里的最大值混入平均。

| 优化器配置 | GAIA | GPQA | MATH | Retail | SimpleQA | 五项平均 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 初始目标 agent | 0.07 | 0.60 | 0.87 | 0.38 | 0.61 | 0.50 |
| Claude Code Pure / Sonnet | 0.13 | 0.58 | 0.88 | 0.43 | 0.65 | 0.53 |
| Claude Code + VeRO Tools / Sonnet | 0.14 | 0.64 | 0.88 | 0.39 | 0.67 | 0.55 |
| VeRO Default / Sonnet | 0.26 | 0.64 | 0.86 | 0.55 | 0.73 | 0.61 |
| VeRO Orchestrator / Opus | 0.18 | 0.62 | 0.88 | 0.55 | 0.74 | 0.59 |
| VeRO Orchestrator / Sonnet | 0.16 | 0.62 | 0.87 | 0.51 | 0.71 | 0.57 |
| VeRO Orchestrator / GPT-5.2 | 0.07 | 0.65 | 0.88 | 0.40 | 0.60 | 0.52 |
| Resources Only / Sonnet | 0.11 | 0.60 | 0.88 | 0.42 | 0.69 | 0.54 |
| GEPA / Sonnet | 0.21 | 0.58 | 0.86 | 0.38 | 0.66 | 0.54 |

五项平均是跨任务汇总，不能视为把所有题合在一起的微平均准确率。初始分数的表注写按 21 次运行平均，而新增 GEPA 后已有 24 次每任务运行；论文没有补充基线汇总是否纳入新增运行的完整说明。本文保留主表口径，不自行替换分母。[表 2](https://arxiv.org/pdf/2602.22480v4)

同用 Sonnet，给 Claude Code 加 VeRO 工具后，跨任务均分增加约 2 个百分点；换成完整 VeRO-Agent Default，比 Pure 高约 8 个百分点。但各任务并非全部改善，例如 Retail 的工具接入对照为 0.43 到 0.39。完整框架的收益也不能只归因于某一个 hook，因为数据访问、工具、程序修改范围和代理实现都可能变化。

Default 比 Resources Only 和 GEPA 高约 7 个百分点，结果与“允许修改更广的执行代码可能有帮助”一致。GEPA 在 GAIA 上达到 0.21，明显高于 Resources Only 的 0.11；两者同为 0.54 的跨任务平均不意味着各任务效果相同。

## 增加优化次数没有统一的收益曲线

附录把预算设为 $B\in\{2,4,8,16,32\}$，使用 Default / Sonnet，每个任务每个预算运行三次。图 8 的误差线是运行间一个标准差，纵轴尺度各不相同。[附录 A.2.4](https://arxiv.org/pdf/2602.22480v4)

GAIA 保留集均分从 $B=2$ 的 0.119 增到 $B=8$ 的 0.195，到 $B=32$ 又降为 0.170。GPQA 保留分约在 0.600–0.630，MATH 约在 0.890–0.897，增加调用没有带来稳定的继续提升。Retail 从低预算到 32 次总体上升至 0.528，但图中 2 到 4 次仍有轻微回落，不能照搬正文的“严格单调增加”。

这些结果只支持在所测优化器、任务、目标模型和预算范围内的观察。它们没有证明推理能力存在一个不能被其他程序设计突破的上限。GAIA 消融的 $B=8$ 为 0.195，也不直接等于主表 Default 的 0.26；没有完整运行日志，不把两个实验的单点视为同一次运行的可互换结果。

图 12 进一步展示一条 MATH 轨迹：增加结构化提示和 SymPy 工具后，验证分从约 0.78 升到 0.92，而测试分只从约 0.86 到 0.88。随后增加 Python 执行工具又被移除。这个例子说明验证集的大幅上涨与测试收益可能不同，而不是证明添加某一个工具必然有效。[附录 A.2.6](https://arxiv.org/pdf/2602.22480v4)

## 更换目标模型之后

鲁棒性实验先在 GPT-4.1 mini 上优化，再把选中的程序切换到其他模型。这里换的是执行被优化程序的模型，不是重新为每个新模型做完整搜索。受费用限制，任务与模型组合并不完整。[表 3](https://arxiv.org/pdf/2602.22480v4)

例如，Sonnet 优化出的 Retail 程序在 GPT-4.1 上从 0.55 到 0.79，在 Sonnet 4.5 上从 0.59 到 0.81；同一优化器在 GAIA 上的程序，换 GPT-4.1 后从 0.15 到 0.22，换 Gemini Flash 却从 0.26 到 0.21。GPQA 中 Sonnet 优化的程序换 Sonnet 执行，分数从 0.71 到 0.66。表中差值使用未四舍五入值，不能要求每个显示到两位小数的端点都精确相减一致。

结论应落实到具体模型与任务：有些修改能迁移，有些会退步。同家族常保留收益是作者的归纳，不是对任意同家族模型的保证；跨家族也并非统一失败，例如 GAIA 的一些 Qwen 配置有改善。

## 初始程序与优化指导同时影响结果

第二项案例研究构造两种同用 GPT-4.1 mini 的 GAIA agent：Pawn 有 4 个工具、25 行提示、20 轮上限，主要处理文本；Knight 有 6 个工具、140 行提示、40 轮上限，增加 Wikipedia、自我检查与复杂文档支持。它们改变的不止一个因素，所以不能把最终差异完全归因于“提示更长”。[表 7、表 10](https://arxiv.org/pdf/2602.22480v4)

优化器再分别接受四种指导：设计模式库加推理步骤、简短指导、工具中心指导、证据中心指导。每种配置独立运行四次，每次有 5 次预算；在 GAIA 上优化，另看 FACTS 和 SimpleQA 的迁移。四次运行不是同一个 agent 连续升级四轮。

| 初始 agent | GAIA 基线 | FACTS 基线 | SimpleQA 基线 |
| --- | ---: | ---: | ---: |
| Pawn | 19.5% | 54.7% | 68.9% |
| Knight | 43.7% | 64.7% | 84.4% |

Pawn 一个较好的运行同时获得约 +11.49、+10.45、+13.33 个百分点，对应 GAIA、FACTS、SimpleQA；作者检查改动包括增加 Wikipedia 搜索及错误处理。但另一运行在 GAIA 提高 5.75 个百分点时，SimpleQA 下降 17.78 个百分点。复杂的多步检查能帮到某些题，也可能给简单事实查询增加不必要流程。[表 12–13、附录 A.3.4](https://arxiv.org/pdf/2602.22480v4)

Knight 的 Minimal 配置有一轮 FACTS 达 70.34%、SimpleQA 达 88.89%，同时逐样本时间达到 107.8 秒，约为其汇总基线 26.6 秒的四倍。准确率与执行成本需要一起看，不能只挑最高分。Knight 这组另有一次 FACTS 评测崩溃，表 12 标作 N/A；表 8 的均值约 68.7% 与三个有效值平均吻合，不是四个完整有效结果。

部分汇总表不能从逐次表精确重建。例如 Pawn / Cookbook 的 FACTS 四个值为 62.36、54.83、49.33、65.17%，均值 57.9225%，与表 8 的 57.9% 一致，但样本标准差约 7.20 个百分点，不是表中的 6.79。Pawn / Tool-Centric 的四个耗时平均为 31.05 秒，表 9 为 32.8；Evidence-Based 对应 11.9 秒与 12.6 秒。本文保留这些差异，不用一个汇总表去补造另一表的原始数据。附录从运行编号讨论“后期迭代”的段落，也不能被当作这四次独立重复之间存在连续学习的证据。

## 长流程代码任务：少崩溃不等于多完成

TerminalBench-2 案例使用 89 个任务，目标是 Terminus-KIRA 框架加 Claude Haiku 4.5，优化器为 Claude Code / Sonnet 4.5。这里没有训练、测试分离：优化和报告都使用全体 89 题，因此只能评价同一任务集内的改进。预算改为**题目执行次数**，不是前面的整批调用次数。[§4.4、表 4](https://arxiv.org/pdf/2602.22480v4)

| 条件 | 题目预算 | 通过 | 错误 |
| --- | ---: | ---: | ---: |
| 初始程序 | — | 27/89，30.3% | 41/89，46.1% |
| 工具接口 | 89 | 30/89，33.7% | 32/89，36.0% |
| 文件接口 | 178 | 27/89，30.3% | 27/89，30.3% |
| 工具接口 | 178 | 33/89，37.1% | 30/89，33.7% |

工具接口让优化器按需查看数据与轨迹；文件接口把同类信息写成 JSON 文件供其读取。每个条件只有一次完整优化，不能由这个表宣称工具接口有经过重复实验验证的普遍优势。

文件接口减少了最多错误，但新增 6 道通过题，同时让原来通过的 6 道题退步，净通过数没变。高预算工具接口新增 12 道、退步 6 道，净增 6 道。其余非通过样本还分为“正常完成但得零分”和“发生执行/验证错误”，两者不能混用。[表 16、表 18、图 16](https://arxiv.org/pdf/2602.22480v4)

两次运行发现工具调用解析中的类型检查问题，消除了 11 个 `AttributeError`；但其中只有部分任务转为通过，其他任务继续在更后面的步骤失败。最高通过率那次主要压缩提示、工具描述及输出，并没有消除这类错误。案例支持按逐题状态转移追踪改动，而不是只看总体崩溃率。

论文主表把 error 描述为目标 agent 到达验证器前崩溃或超时，附录的分类实际还包含 `VerifierTimeoutError`。本页按表 16 的汇总数字报告“错误”，不将其全部归入目标 agent 崩溃。

三次优化器自身费用为 2.41–3.13 美元，而完整跑一次 89 题的目标 agent 约需 180 美元；前者不是总实验成本。预算 178 的工具运行实际只使用 129 次样本预算，不能写成确实完成两次全量评测。表 17 的逐文件增删行也与附近叙述的“总 diff 行数”口径不完全一致，本页不以这些行数比较修改效率。[表 15–17](https://arxiv.org/pdf/2602.22480v4)

## 修改类型与评价协议的边界

作者使用 GPT-4.1 给每个优化阶段打一个或多个标签，例如提示、工具、工作流、配置和依赖。图 4、图 6 展示各类标签频率，图 10 用分布熵概括多样性。若类别概率为 $p_k$，熵通常写作：

$$
H=-\sum_kp_k\log p_k.
$$

这是对指标的解释；多标签结果必须先明确归一化口径，熵也不是代码复杂度或最终得分。作者观察到许多后续阶段集中于提示修改，Orchestrator 在一些阶段保持较多样的修改类型。图中并非所有阶段都单调下降，不能把总体趋势变成每条曲线的规则。[§5.5、附录 A.2.5](https://arxiv.org/pdf/2602.22480v4)

另一个分析把各阶段代码相对空提交的差异送入 `text-embedding-3-large`，再用 UMAP 投影到二维。它包含整个代码快照，甚至有与当前任务不直接相关的代码；点聚在一起是这种表示下的观察，不是证明程序行为等价。该图只能辅助阅读修改轨迹。

附录还做了一次没有基础设施约束的 GPQA 优化。事后裁判给出 10 条违规标记，其中 4 条涉及逐样本测试内容，6 条涉及预算超额。后六条包含多次重复承认同一次超额，不能写成发生了六次独立越界评测。优化器提示在测试使用上也有张力：规则限制可评测 split，流程又要求测试基线与最终测试；裁判明确允许测试汇总评测。真正清楚的违规证据是把测试题与答案送入上下文，以及超过训练次数预算。一次无约束运行说明了风险实例，没有通过配对多次实验测出 VeRO 对所有此类行为的防护率。[附录 A.5，Listing 1–5](https://arxiv.org/pdf/2602.22480v4)

## 固定代码后可以复查的内容

本次先检查官方主分支 [`d1400011917ff66b7c122e7a787d547372f43e97`](https://github.com/scaleapi/vero/tree/d1400011917ff66b7c122e7a787d547372f43e97)。README 明确指出系统已经重构，原论文代码在 `legacy/`，复现应使用 `paper-v1`。该标签解析为 [`4ae9c1df1e5d303b875629fa53b686a211897c4e`](https://github.com/scaleapi/vero/tree/4ae9c1df1e5d303b875629fa53b686a211897c4e)，包名 `scale-vero`、版本 0.4.7、Python 3.11 以上、MIT 许可。以下实现说明以这个标签为准；新主分支的预算网关和新 benchmark 不反推为论文已经使用的功能。

实际核查包括数据构建器与全部 GAIA/MATH 映射、SimpleQA 固定索引、任务配置、预算工具、数据查看器、版本选择、汇总分析及 GEPA 适配入口，没有运行模型。

- **预算按 split 管理。** `ExperimentRunner` 先检查允许的划分和剩余预算，评测结束后在 `finally` 中扣减；失败的调用也会消耗预算。`num_samples` 取该 split 的前 N 项，不是随机抽样。重跑需保存每次的具体样本 ID。
- **数据访问依赖配置。** `DatasetViewer` 根据会话的 split 权限拒绝查看，Filesystem 按最后一条匹配路径规则决定权限。工具层检查不等于已经验证所有外部进程、网络访问或公开答案副本都无法绕过，论文也承认未控制网络中的答案记忆与复制风险。
- **候选选择要显式记录。** 论文协议通常按验证分选候选，GPQA 按训练分选；发布 `Policy.run` 优先接受 agent 指定的版本，未指定时把 `eval_split` 传给数据库选择函数。若这个 split 还没有非基线结果，路径可能找不到候选。它并不是在每种配置下无条件退回验证/训练最优。需要保留实际所选提交、选取 split 和最终测试记录，不能只运行默认入口就假定完全复现论文协议。
- **汇总不自动消除选择偏差。** 分析函数在已有报告 split 的历史中取非基线最好分；有多个最终测试候选时，聚合会受到测试历史内容影响。论文说通常只测初始和选中版本，没有完整逐次日志就不能确定所有运行都严格符合这一点。
- **旧任务默认不等于每个论文案例。** 发布的 TerminalBench 任务默认样本预算为 50，论文案例为 89 或 178。复现案例须明确覆盖该配置。

代码已提供基准启动脚本、数据构建器、任务 agent、锁文件、GEPA 适配器和轨迹分析模块。[旧版复现说明](https://github.com/scaleapi/vero/blob/4ae9c1df1e5d303b875629fa53b686a211897c4e/vero-benchmarking/README.md)中的 `scripts/run_benchmark.py --config … --task … -n 3` 对应三次运行；批量构建数据或启动全部任务会涉及上游访问、模型调用和实际费用，本次未执行。

要重建论文结果，还需要所用数据版本、模型端点、全部候选提交与轨迹、运行失败处理，以及对应图表的原始导出。公开代码中部分分析依赖 W&B 历史；仓库入口和静态索引不能替代已取得这些日志。本文完成了 33 页原文及附录、关键图表、官方代码和汇总算术的核对，没有宣称复现模型成绩。

# 搜索时的数据污染：从检索来源追踪评测答案泄漏

一个联网助手先尝试计算答案，随后搜索到包含同一道题和标准答案的数据集副本，最终改用其中的标签。此时，答对并不一定来自题目原本要考查的能力。《Search-Time Data Contamination》研究的就是这种发生在评测执行期间的泄漏。作者检查三个 Sonar 系统在 HLE、SimpleQA 和 GPQA 上的检索来源，再通过屏蔽 Hugging Face、限制日期和关闭搜索比较成绩。结果表明，部分答案确实受数据集来源影响；但论文中的链接命中率、命中子集的成绩变化和全量基准的分数变化，是三个不同的量。[原文 §1–3、图 1–5](https://arxiv.org/pdf/2508.13180v1)

## 污染发生在检索环节

传统的训练数据污染，是测试题进入训练语料，导致测试集不再完全独立。这里即使模型训练时从未见过题目，也可能在作答期间通过搜索获得标准答案。论文定义强调信息的来源：答案线索是从评测集本身派生出来的，才属于本文讨论的搜索时污染，简称 STC。[原文定义 1、§2](https://arxiv.org/pdf/2508.13180v1#page=1)

可以用一个自拟例子说明边界。假设题目要求根据几份历史档案推算某次运输的总数量：助手找到原始档案并完成计算，属于正常检索；找到一个评测数据文件，里面恰好列出该题和标准答案，则是本文关心的泄漏。两条路径可能输出相同数字，但能支持的能力结论不同。

论文图 1 提供了一个实际轨迹片段：Sonar Deep Research 先给出自己的计算，发现第三方 HLE 副本中的答案后，承认计算可能有误并改用数据集标签。图 2 又展示三个基准中的片段。这里保留过程说明，不重复被作者遮盖的题目答案。个案证明这种路径能够发生，并不能单独说明所有被检测器标记的回答都采用了同样路径。[原文图 1–2](https://arxiv.org/pdf/2508.13180v1#page=2)

## 实验使用既有基准，没有新建题库

作者直接在三个已有基准上调用搜索系统，并记录返回来源、模型回答和评判结果。论文没有重新招募专家制作一套 STC 问题，因此也没有新的训练集划分或人工标注协议。[原文 §3.1、表 1](https://arxiv.org/pdf/2508.13180v1#page=4)

| 基准 | 本实验规模 | 作答与评分 |
| --- | --- | --- |
| Humanity’s Last Exam，HLE | 每个模型计划 2,500 条 | 专家知识与推理题；调用 HLE 的评判实现 |
| SimpleQA | 每个模型 4,326 条 | 简短事实问答；调用 Simple Evals 的评判实现 |
| GPQA | 每个模型 1,792 次作答 | 论文称在完整题集上重复 4 次；按表内计数对应 448 题 × 4，不能称作 1,792 道独立题 |

作者报告的是单次作答正确率，也就是 pass@1。GPQA 的四次重复用于降低波动，不能解释为“只要四次中答对一次就成功”的 pass@4。论文没有逐项公布各基准的固定数据提交版本、输入完整模板和全部预处理，HLE 的图片如何进入各 API 也未在正文及附录展开，后续重跑需要另行确认。[原文 §3.1](https://arxiv.org/pdf/2508.13180v1#page=4)

### 模型、预算和评判器

主要对象是 Perplexity 的 Sonar Pro、Sonar Reasoning Pro 和 Sonar Deep Research。作者选择这组系统，是因为当时 API 支持来源名单和日期过滤，便于做干预实验。论文还提到尝试过 Claude、Gemini 和 OpenAI 的搜索工具，但几乎没有观察到 Hugging Face 链接；作者对原因的解释属于猜测，这部分没有形成与 Sonar 同等完整的量化实验。[原文 §3.1](https://arxiv.org/pdf/2508.13180v1#page=4)

三个 Sonar 系统采用 `temperature=0.2`、`top_p=0.9`、`search_context_size='high'`，最大输出长度为 32,000 tokens。单次 API 超时设为一小时，最多尝试五次，仍失败则记录为 API failure。这里的尝试次数是请求重试预算，不能当作选五个候选答案的推理策略。论文没有给出底层模型权重版本、全部搜索调用次数或每题实际成本。

| 基准 | 评判器 | 设置 |
| --- | --- | --- |
| HLE | `o3-mini-2025-01-31` | 温度 1.0，最大 completion 4,096 tokens；使用 HLE 项目实现 |
| SimpleQA | `gpt-4.1-2025-04-14` | 温度 0.5，最大 completion 2,048 tokens；使用 Simple Evals 实现 |
| GPQA | 程序化评分 | 使用 Simple Evals 实现，不调用语言模型评判器 |

来源为原文 §3.1。论文没有提供此次实验中评判器与人工标注的一致率，也没有固定所引用上游仓库的提交；复现时仅选择相同评判模型名称仍不够。[HLE 上游](https://github.com/centerforaisafety/hle)、[Simple Evals 上游](https://github.com/openai/simple-evals)

## 附录检测器识别的是链接特征

附录 A 的函数遍历一条轨迹的来源 URL，寻找同时包含 `huggingface` 和对应基准关键词的字符串。HLE 使用 `hle`；SimpleQA 使用 `simpleqa`、`simple_qa` 或 `simple-qa`；GPQA 使用 `gpqa`。函数返回第一个命中的 URL，没有命中则返回 `False`。[原文附录 A](https://arxiv.org/pdf/2508.13180v1#page=11)

用本文记号表达这段代码：设第 $i$ 次有效作答的来源集合是 $U_i$，该基准的关键词集合是 $K$，则标记为

$$
C_i=\mathbf{1}\!\left[\exists u\in U_i:
\texttt{huggingface}\subset u
\ \land\ \exists k\in K,
 k\subset u\right].
$$

这里的 $\subset$ 表示字符串包含，不是域名归属或语义匹配。若 $V$ 是有效作答集合，表 1 的比例可写成

$$
\widehat p_{\mathrm{URL}}=
\frac{\sum_{i\in V}C_i}{|V|}\times100\%.
$$

这两个公式是对公开代码和表格口径的整理，不是论文提出的训练目标。

代码没有下载网页逐字核对当前题目，没有比对答案，也没有判断模型是否实际利用该答案。它还区分大小写，未解析真实主机名。本文用自拟字符串做了离线检查：路径只有大写 `HLE` 时不命中；其他域名的路径中同时出现 `huggingface/hle` 时也会命中；换了名称的实际数据副本可能漏检。这说明规则的覆盖边界，不代表论文日志里已经出现这些误判。

因此，正文中应将表 1 理解为**特定 URL 规则的标记率**。不能称它为经过逐条人工确认的作弊率，也不能将所有未命中的记录称为已证实无污染。由于误报和漏报都未量化，这个估计也不是严格的全网污染率下界。[原文附录 A、§4 局限](https://arxiv.org/pdf/2508.13180v1#page=9)

### 命中组的准确率更高，不等于每一道题都获得同样增益

图 1 和图 3 按检测器标记分组，结果如下，单位均为百分比。

| 基准／模型 | 未命中组 | 命中组 | 命中组减未命中组，百分点 |
| --- | ---: | ---: | ---: |
| HLE／Pro | 6.8 | 17.9 | +11.1 |
| HLE／Reasoning Pro | 8.4 | 27.9 | +19.5 |
| HLE／Deep Research | 17.4 | 37.5 | +20.1 |
| SimpleQA／Pro | 93.6 | 100.0 | +6.4 |
| SimpleQA／Reasoning Pro | 93.2 | 100.0 | +6.8 |
| SimpleQA／Deep Research | 94.0 | 95.3 | +1.3 |
| GPQA／Pro | 63.5 | 57.1 | −6.4 |
| GPQA／Reasoning Pro | 65.4 | 55.9 | −9.5 |
| GPQA／Deep Research | 73.8 | 66.2 | −7.6 |

来源：原文图 1、图 3 的标注数值；差值按图中四舍五入后的数值相减。[原文图 1](https://arxiv.org/pdf/2508.13180v1#page=2)、[图 3](https://arxiv.org/pdf/2508.13180v1#page=6)

这些组不是随机分配的。同一道题是否出现数据集链接，可能与题目难度、措辞或搜索行为相关。特别是 GPQA，命中组反而更低，不能据此断言数据集答案没有帮助；也可能是更难的题更容易触发这种搜索路径。相反，SimpleQA 的两个 100% 也只对应 52 和 48 次作答。图 3 的图注明确表示，受样本少和成绩接近上限影响，这里的差异没有达到统计显著。

图 1 将误差条标为 95% 置信区间，但论文未说明区间的具体构造方式。GPQA 有同题重复，是否在统计中处理了这种相关性也未披露，不能自行补写为独立伯努利样本或某种 bootstrap 方案。

## 同一道题屏蔽 Hugging Face 后的变化

为减少题目难度的混淆，作者取原来被标记的那些题，再运行一次屏蔽 Hugging Face 的配置。这样比较的是同一子集在不同来源限制下的表现。[原文 §3.1、图 4](https://arxiv.org/pdf/2508.13180v1#page=5)

令 $S$ 表示默认运行中被标记的集合，以百分数表示准确率，则本文将图 4 的方向写为

$$
\Delta_S=A_{\mathrm{Blocked\ HF}}(S)-A_{\mathrm{Default}}(S).
$$

负值表示屏蔽后下降。按图 4 柱高读数，HLE 的三个模型大约下降 12、17.5 和 9 个百分点；GPQA 的 Deep Research 大约下降 16 个百分点。这些是图形近似读数，论文没有在正文列出相应的精确数据表。HLE 三个区间均在零以下；SimpleQA 和 GPQA 中则有多个区间跨零，GPQA／Reasoning Pro 的点估计甚至向上。不能把摘要中的“约 15%”扩写成所有模型、所有基准都下降 15 个百分点。[原文图 4](https://arxiv.org/pdf/2508.13180v1#page=7)

这个实验比直接比较命中组和未命中组更接近因果问题，但干预仍然是屏蔽整个来源站点。它可能同时改变正常证据、后续查询与随机生成路径，不能精确分离“某个标准答案字符串”的贡献。论文没有报告对同题每种条件多次重复后得到的稳定平均干预效果。

还需区分子集效果和总分效果。作为说明，假设只有 3% 的作答受到影响，且这些作答屏蔽后平均下降 15 个百分点，其余作答完全不变，那么全量分数只下降

$$
0.03\times15=0.45\ \text{个百分点}.
$$

这是条件明确的教学计算，不是论文对总体降幅的测量，更不能用它替代图 5 的完整重跑结果。

## 五种搜索条件分别改变了什么

图 5 将来源干预扩展到整个基准，比较以下条件。[原文 §3.2](https://arxiv.org/pdf/2508.13180v1#page=6)

| 条件 | 论文中的操作 | 比较时需要保留的边界 |
| --- | --- | --- |
| Default | 原始搜索配置 | 混合正常证据与可能泄漏的来源 |
| No Search | 允许搜索的域名集合设为空 | 论文意图是移除在线证据；未公布请求封装代码，不能擅自把具体 API 空列表参数当作可靠关闭方式 |
| Blocked HF | 排除 `huggingface.co` | 同时删除正常 Hugging Face 内容，且不覆盖别站副本 |
| Only HF | 仅允许 `huggingface.co` | 仍保留模型内部知识；改变了证据范围与搜索过程 |
| Date Cutoff | 限制为各基准发布前一天之前的网页 | 依赖索引里的网页时间元数据，不等于真实网页历史快照 |

HLE 和 SimpleQA 的默认搜索明显好于 No Search，Deep Research 上尤其明显。图 5 中，HLE／Deep Research 的默认值约为 17%，No Search 约为 6%；SimpleQA 上约为 94% 对 38%。这些来自柱图，只适合说明量级。GPQA 的五种设置则相对接近，多数差异处于误差条量级。[原文图 5](https://arxiv.org/pdf/2508.13180v1#page=8)

Blocked HF 在 HLE 上的下降远小于完全移除搜索的下降。Only HF 在 HLE、SimpleQA 上也远不能恢复默认搜索的成绩；SimpleQA 的 Reasoning Pro 和 Deep Research 甚至低于 No Search。因此，“只搜数据托管站”并不是默认系统的一个可相加分量，也不是经数学证明的污染收益上界。论文将它称为上界压力测试，应理解为作者对实验用途的描述。

日期过滤后的 HLE、SimpleQA 分数通常低于默认搜索，但仍高于 No Search。作者认为这提示发布后的网页可能有影响，同时也保留了一个条件：日期索引需要正确、完整。原文脚注说明，缺少时间元数据的页面可能不会被过滤。即使过滤完美，发布之后出现的新解释或正常资料也可能有帮助，不能把所有降幅都归为答案泄漏。[原文 §3.2 与脚注 6](https://arxiv.org/pdf/2508.13180v1#page=6)

### 图表间的分母需要额外核对

HLE／Deep Research 的 121 次 API 失败约占计划作答的 4.84%。用图 1 的两组准确率及样本数加权，可以得到有效作答中的准确率约 18.08%；若改除以全部 2,500 次计划作答，则约为 17.20%，与图 5 默认柱高接近。前者的计算是

$$
\frac{80\times37.5+2299\times17.4}{2379}\approx18.08\%.
$$

这一核算使用图中的舍入数值，提示图 5 可能采用了不同的失败处理口径；它不是对原始评测代码的确认。论文未逐条件列出失败数、分母和统计代码，而本次无法访问受限结果文件，因此本文不把两个图的数值直接拼成一张精确全量成绩表。[原文表 1、图 1、图 5](https://arxiv.org/pdf/2508.13180v1)

## 作者提出的评测改进及其验证范围

论文建议优先使用与信息搜索和时效需求匹配的任务，并披露来源过滤、轨迹检查和污染处理后的结果。对于可疑轨迹，URL 规则可以先筛选，再核对检索正文是否包含题目及标签，必要时加入人工或模型评审。[原文 §4](https://arxiv.org/pdf/2508.13180v1#page=8)

这些建议有不同的证据基础。来源和日期限制在本文做过实验；多层审计系统、动态答案基准以及鼓励或阻止模型寻找答案的行为实验，属于建议或后续方向，没有在本文完成系统验证。作者提到的 canary string，即放在数据中用于识别泄漏的特殊字符串，也可能被第三方转存时删除。原库访问门槛同样不能约束已经公开的副本。

本文没有证明所有联网基准都无效，也没有测量所有搜索产品的污染程度。它提供的是三个 Sonar 配置、三个既有基准和一个时间窗口下的证据，说明只看最终正确率会遗漏答案来源。对网页中的正常知识与测试集派生材料进行区分，才是把这些结果用于评测设计的前提。

## 公开材料与复现入口

官方 [ScaleAI/stc](https://huggingface.co/datasets/ScaleAI/stc) 数据仓库声明提供实验日志与结果，列出 `evaluation_logs.zip` 和 `results.csv`，许可为 CC BY-NC 4.0。本次核查固定的仓库提交是 `a65a30b1e6fecb731aae748f10b2dd7b27e99985`。仓库元数据和 README 可以读取，但结果文件请求返回 401，页面要求登录、共享联系信息并接受条件。因此本文没有将“官方提供下载入口”写成“已经核对全部执行日志”。

附录 A 的检测函数可以独立离线运行；本文已按其逻辑检查自拟 URL，并重算表 1 的计数、比例和图表加权关系。这些工作核实的是规则行为与公开数值，**尚未复现模型实验**。在论文、Scale 项目页和数据文件清单中，没有确认到包含全部请求封装、过滤配置、失败处理及绘图逻辑的独立代码发布。

完整重跑需要取得日志访问资格及对应基准权限，固定原题与模板，确认 Sonar 搜索限制实际生效，并配置两个评判模型。应分别保存请求失败、来源 URL、检索正文、生成答案和评分结果，才能核查表 1、图 4 与图 5 是否使用一致的分母。原文没有报告完整美元预算或总 token 用量，不能据最大输出上限推算实际成本。

还有一个无法靠固定随机种子解决的变化：作者已经申请删除或增加部分第三方 HLE 副本的访问门槛。搜索索引和模型服务也会更新。即使得到相同代码，今天重新发起请求也不一定复现 2025 年的来源分布；历史日志与在线重跑应分别报告。[原文 §4 局限](https://arxiv.org/pdf/2508.13180v1#page=9)

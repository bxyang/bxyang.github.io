# Agent-RLVR 精读：用训练期提示找到可验证的代码修复轨迹

一个代码模型读懂 bug 描述后，还要找到相关文件、判断修改位置并生成能够通过测试的补丁。如果它反复尝试都失败，单元测试虽然给出了可靠的失败信号，却没有提供足够的成功轨迹供训练。Agent-RLVR 在训练数据采集时加入教师提示，让模型重新尝试，再按测试结果组成成功与失败的偏好对，进行一次离线 DPO 更新。Qwen2.5-72B-Instruct 在不提供提示的 SWE-bench Verified 测试中从 9.4% 提高到 22.4%；另外使用奖励模型从 32 个补丁中选择一个时达到 27.8%，两者的测试预算不同。[论文 v2，§2–3](https://arxiv.org/pdf/2506.11425v2)

## 论文版本与 Scale 的参与

论文原名为 *Agent-RLVR: Training Software Engineering Agents via Guidance and Environment Rewards*，作者 Jeff Da、Clinton Wang、Xiang Deng、Yuntao Ma、Nikhil Barhate、Sean Hendryx，首页统一署名 Scale AI。公司在 Scale Labs 发布了对应研究页，属于其团队开展的软件 agent 训练研究。[Scale Labs 原始页面](https://labs.scale.com/papers/agent_rlvr)

arXiv v1 于 2025 年 6 月 13 日公开，本次阅读的是 6 月 20 日 v2，共 13 页，包括技术附录、SFT 对照和两段提示模板。原始入口标记为预印本，本页不据此登记为正式会议论文。完整版本历史见 [arXiv](https://arxiv.org/abs/2506.11425)。

这里的 RLVR 指以可验证结果构造学习信号。在本文具体实现中，验证器是执行环境和单元测试，优化器是**离线 DPO**。PPO、GRPO 和多轮在线训练属于作者讨论的后续方向；§2 明确说实验证据只有一轮训练周期。

## 输入是一份 issue 和一个可执行仓库

每个任务包括真实 GitHub issue 描述、修复之前的 Python 仓库快照、Docker 环境及测试。问题可能描述错误信息、实际行为、期望行为和复现方式；模型需要提交代码补丁，而不是只给自然语言建议。（§2.2.1）

测试分两类：验证问题是否修复的针对性测试，以及检查原有功能是否保留的回归测试。本文以是否通过要求的测试作为终局标签。一个可读、合理甚至只差一步的补丁，只要未达到测试要求，仍然不能作为成功轨迹。

论文图 1 使用了 `jnp.linspace` 不接受 `device` 参数的例子。计划提示可以指出修改函数签名，环境反馈可以指出报错与遗漏参数，位置提示则指向 `jax/_src/numpy/lax_numpy.py`。这是原图的流程示意，论文没有提供这一案例的完整轨迹、所有文件修改和测试日志，不能把图中的几句提示当作已完整公开的修复实例。

实际运行框架来自 Agentless，但作者只保留定位和修复，删除其测试生成、执行及补丁选择阶段。这不意味着训练与最终评估不运行单元测试：删除的是生成框架内部的候选筛选步骤，环境验证仍负责给最终补丁打标签。也不能将本文实现描述成拥有任意终端工具、自由探索循环的完整 SWE-agent；其具体动作流程受简化的 Agentless scaffold 约束。（§3.1）

## 教师提示使用了参考补丁

教师采用 `claude-3-7-sonnet-20250219`。附录图 3 的输入包括仓库名称、问题描述、`patch` 和前一次尝试的 stack trace；图注明确 `patch` 是 **reference patch，即参考修复补丁**，而非仅指模型先前产生的失败补丁。

教师输出三段信息：

| 提示 | 主要内容 | 帮助解决的困难 |
| --- | --- | --- |
| Plan hint | 根据问题给出具体行动步骤或核心原因 | 缺少整体修复方向 |
| Environment feedback hint | 根据先前 stack trace 指出需要修正之处 | 反复沿同一错误方向尝试 |
| Environment interaction hint | 指出文件、函数或行号等位置 | 无法定位相关实现 |

这里的第三种提示是位置线索，不能仅因名字带 interaction 就理解为教师一定亲自执行了完整工具探索。提示模板前面给计划和反馈各写了 200–300 词的长度上限，末尾又要求各部分一至两句；这是模板中的同时约束，论文没有报告实际输出的长度分布。

附录图 4 将提示追加给模型，并要求它**从头解决问题**，不要假定提示中的步骤已经完成。模板还要求模型自行解释推理过程，而不是直接以“提示告诉我”为依据。这是重新生成轨迹的提示方式，不是模型权重在重试之间已经更新。

最终成功标签由测试决定，因此没有用教师主观分数取代可验证奖励。但提示本身包含从参考补丁提炼出的额外监督，且部分轨迹直接由教师模型产生；不能将整个训练过程称为“没有参考答案、只靠试错”。训练期可使用这些信息，测试时不提供教师提示或参考补丁，两种阶段必须分开。

## 从失败重试到偏好训练

算法 1 与 §2.2.4 的流程可以整理为四步：

1. 对训练任务进行多次无提示尝试，运行测试，将轨迹分为成功和失败。
2. 对失败尝试生成教师提示，让模型重新尝试，再测试新补丁。
3. 为每条成功轨迹抽取同一问题的一条**无提示失败轨迹**，形成偏好对；原本无提示成功的轨迹也可以参与配对。
4. 先用一部分成功轨迹进行指令微调，再以微调模型为参考策略，使用离线 DPO 学习偏好对。

只有失败轨迹、始终没有成功轨迹的问题，不能直接组成本文要求的成功—失败对。引导的作用是增加可进入这种训练的数据，而不是把所有失败都变成正奖励。论文没有提供逐任务的采样、过滤和配对清单，也没有按错误类型统计最终被丢弃多少条。

| 仓库 | 27 |
| 来自 SWE-Gym 的问题 | 593 |
| 自行采集的问题 | 219 |
| 最终轨迹 | 8,186 |

593 加 219 是 812，不是 817。最终 8,186 条也不能由 817 直接乘 16 得到。后者可能涉及过滤与配对后的保留量，但论文没有给出完整计数流程，不能补猜缺少的五个环境或把 8,186 误当作全部实际执行次数。（§2.2.3、§3.1）

SFT 的“20%”也存在表述差异：§2.2.3 说取成功轨迹的 20%，§2.2.4 强调从未加提示的轨迹中取样，§3.1 则简写为数据集的 20%。清楚的是 SFT 使用测试通过的数据、最终主设置不使用带提示轨迹；精确的抽样分母、取整后的样本数及各来源占比并未披露。本文不把 $8186\times20\%$ 或 $4093\times20\%$ 当成已确认的 SFT 样本数。

作者说明同时包含 Qwen2.5-72B-Instruct 产生的 on-policy 数据和教师 LLM 产生的 off-policy 数据，却未给出混合比例及各模型大小实验如何使用这些来源。因此，14B、32B 实验不能自动理解成所有数据都来自各自模型的纯自我改进。

仓库选择排除了 SWE-bench 测试集仓库，属于仓库层面的训练测试隔离。作者也承认，基础模型预训练可能已经接触这些开源任务；仓库隔离不能证明完全没有预训练污染。

## 目标函数与实际学习信号

### 环境奖励与 KL 项

令 $x$ 表示任务和模型输入，$y$ 表示轨迹或解答，$\pi_\theta$ 为待训练策略，$\pi_{\rm ref}$ 为参考策略。论文式 1 给出：

$$
R(x,y)=r(x,y)-\beta\log\frac{\pi_\theta(y\mid x)}{\pi_{\rm ref}(y\mid x)}.
$$

$r$ 来自测试，成功为 1，失败为 0。对当前策略生成的 $y$ 求期望时，后半项对应 KL 正则，限制策略偏离参考模型。单条轨迹的对数比可能为正也可能为负，不能把每条样本上的这个量都当成非负的 KL 散度。

这一式子说明带参考约束的优化目标，本文没有使用它运行在线 PPO，也没有为训练策略先拟合一个主观奖励模型。后面的 32B 奖励模型属于另外的测试时选择实验。

### DPO 比较同题成功与失败轨迹

对每个偏好对 $(x,y_w,y_l)$，成功轨迹为 $y_w$，失败轨迹为 $y_l$。论文式 2 为：

$$
\mathcal L_{\rm DPO}(\theta)
=-\mathbb E_{(x,y_w,y_l)\sim D}
\log\sigma\!\left[
\beta\left(
\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\rm ref}(y_w\mid x)}
-\log\frac{\pi_\theta(y_l\mid x)}{\pi_{\rm ref}(y_l\mid x)}
\right)\right].
$$

$\sigma$ 是 sigmoid，$\beta$ 控制对数概率差的尺度。最小化损失，会提高成功轨迹相对失败轨迹、并相对参考策略的偏好。偏好标签取决于测试结果，不是文本与参考补丁的相似度；同一个问题允许存在不同但都通过测试的实现。

例如，仅作公式说明，若括号内经过 $\beta$ 缩放的优势从 0 增至 1，单对损失从 $-\log0.5\approx0.693$ 降到 $-\log\sigma(1)\approx0.313$。这不是论文实测的损失曲线或实际 $\beta$ 设定，原文没有公布 $\beta$ 数值。

### 带提示生成与训练条件之间仍有缺失信息

DPO 公式要求两条轨迹以同一个 $x$ 为条件，但有提示的成功轨迹和无提示失败轨迹在**采集时**看过的输入不同。论文没有公开最终序列化格式，因而无法确认训练时是否删除提示、是否把提示转成上下文的一部分，或对哪些 token 计算损失。

同样，算法 1 的 SFT 行写成 $p_\theta(y_i^*\mid x_i,r_i)$，没有解释这里的 $r_i$ 在实际输入中如何表示。按照文字描述，可以确定它在成功轨迹上做最大似然微调；不能据这行未充分定义的记号断言使用了奖励条件 token。准确重现还需要成功/失败 prompt 对齐、工具输出掩码、长度截断和参考策略冻结方式。

## 训练与评测预算

| 阶段 | 原文设置 |
| --- | --- |
| 指令微调 | 5 epochs，学习率 $10^{-5}$，序列长度 8k |
| Agent-SFT 对照 | 同样 5 epochs、$10^{-5}$，余弦学习率调度；对学习率和 epoch 做网格选择 |
| DPO | 1 epoch，学习率 $10^{-6}$ |
| 提示教师 | `claude-3-7-sonnet-20250219` |
| 测试奖励模型 | Qwen2.5-Coder-32B，pairwise loss，学习率 $10^{-5}$，500 steps，warmup ratio 0.05 |
| 14B / 32B 训练硬件 | 各 2 节点，每节点 8 张 H100 |
| 72B 训练硬件 | 4 节点，每节点 8 张 H100 |
| 对应训练时间 | 14B 约 4 小时，32B 约 6 小时，72B 约 10 小时 |

按论文给出的设备数乘时间，名义训练资源分别约为 64、96、320 H100 卡时。但原文没有拆开每一训练阶段和网格搜索的耗时，不能把这些数字当成从数据采集到所有评测完成的总成本。教师调用、Docker 测试、失败重试、32 候选生成及奖励模型训练都需要另外记账。（§3.1）

测试使用 SWE-bench Verified，官方数据卡为 500 个经过人工检查的任务。作者使用原作者 evaluation harness，在 Modal 上执行；有六个实例无法编译，但仍保留在整体指标分母中。不能删除它们后以 494 为分母重报原分数。

单次生成使用各步骤 greedy decoding；多候选评测先生成一条 greedy 轨迹，其余使用 temperature=0.6。因此多候选集合并非全部以同一个随机采样策略独立生成，不能未经核查就套用任意标准 pass@k 无偏估计脚本。论文未给出最大交互轮数、每步输出预算、超时阈值和完整采样日志。

## 单次生成、存在成功与选择成功是三种口径

将每题的第 $j$ 个候选是否通过记为 $a_{ij}$，可以用下面的直接集合统计解释差异：

$$
\mathrm{pass@}k=\frac1N\sum_{i=1}^N
\mathbf1\!\left[\exists j\le k:\ a_{ij}=1\right].
$$

它表示生成的 $k$ 个候选里至少存在一个正确补丁，不表示系统能在不知道测试答案的情况下挑中它。原文没有说明是否另行使用组合估计器；本式只是实际候选集合上的统计解释。

奖励模型选择则先算：

$$
j_i^*=\arg\max_{j\le32}f_\phi(x_i,\mathrm{patch}_{ij}),
\qquad
\mathrm{selected@1}=\frac1N\sum_i a_{i,j_i^*}.
$$

$f_\phi$ 读问题描述和补丁，不需要读取完整 agent 轨迹。选择完后，隐藏的测试用来评估最终提交是否正确。论文把这一方向称为 BEST@1，但表 1、表 3 又统一标 PASS@1；理解 27.8% 时应保留其“32 个候选选一个”的实际条件。

## 主要结果与 SFT 对照

下表转写原文表 1，并单独标出奖励模型行的不同预算。括号是论文标为 STD 的数值，单位为百分点：

| 模型与训练 | 测试方式 | 通过率（原文 STD） |
| --- | --- | ---: |
| Qwen2.5-Coder-14B，基础模型 | 单次生成 | 6.8%（±2.2） |
| Qwen2.5-Coder-32B，基础模型 | 单次生成 | 8.8%（±2.5） |
| Qwen2.5-72B-Instruct，基础模型 | 单次生成 | 9.4%（±2.5） |
| Agent-RLVR 14B | 单次生成 | 18.0%（±3.4） |
| Agent-RLVR 32B | 单次生成 | 21.6%（±3.5） |
| Agent-SFT 72B | 单次生成 | 20.8%（±3.5） |
| Agent-RLVR 72B | 单次生成 | 22.4%（±3.6） |
| Agent-RLVR 72B + RM | 32 个补丁经 32B RM 选一个 | 27.8%（±3.8） |

原文没有说明 STD 对应多少次重复、bootstrap 还是其他计算，不能自行把括号转成 95% 置信区间或认定它来自多次独立训练。虽然单次使用 greedy，环境和训练仍可能有变动；缺少定义时应保留未披露的边界。

72B 从基础模型到 RLVR 增加 13.0 个百分点；但强 SFT 对照已经达到 20.8%，RLVR 相对它增加的是 **1.6 个百分点**。不应把全部 13 点都归于 DPO。原文也没有给出成对实例差异的显著性检验，不能仅从均值差断言它稳定超过 SFT。

14B、32B 的增幅分别为 11.2、12.8 个百分点。三种大小得到更高均值，但 14B/32B 使用 Coder 系列，72B 使用 Instruct 系列，不能将三个点拟合成严格控制架构与数据后的线性规模规律。

表 3 的外部结果包括 SWE-Gym 32B 的 20.6%、SWE-Fixer 72B 的 30.2%、SWE-RL 70B 的 41.0%，以及 Agentless 搭配 Claude 3.5 Sonnet 的 50.8%。这些结果使用不同训练数据、底座和 scaffold；本文简化了 Agentless 的验证流程，不能把跨方法差值视为只由 Agent-RLVR 优化方法造成，也不能说该方法已达到表中的最高水平。

## 引导的收益与负面结果

### 引导提高的是收集成功轨迹的机会

表 2 对比有无提示的 rollout：

| 指标 | 无提示 | 有提示 | 差值 |
| --- | ---: | ---: | ---: |
| 平均成功 rollout 数 | 138 | 165 | +27 |
| 报告成功比例 | 16.9% | 20.3% | +3.4 个百分点 |
| 空补丁比例 | 8.71% | 7.20% | −1.51 个百分点 |

这些是训练数据采集阶段的统计，不能与测试集 22.4% 直接比较。“平均成功数”也不等于新增了 27 个此前永远无法解决的唯一任务；多次采样和最终去重细节没有公开。按 817 计算 $165/817\approx20.2\%$，与展示的 20.3% 有小差异，可能涉及平均后取整或实际分母，原文没有说明。（表 2）

### 去掉 DPO 的引导轨迹会降低无提示测试成绩

无引导对照保持同样的训练流程，但 DPO 阶段去掉引导增强的数据。论文报告单次通过率从 19.8% 到有引导的 22.4%，相差 2.6 个百分点；pass@32 从 34.2% 到 38.4%，相差 4.2 个百分点。图 2 展示 $k=1,2,4,8,16,32$ 的曲线。（§1、§3.2，图 2）

两种训练后的模型在这里都**没有测试期提示**。因此该对照考察训练数据的作用，而不是给测试题额外提供正确文件或计划。曲线间距随候选数增加，与可生成成功补丁的覆盖面提高相容；论文没有直接测量去重后的语义多样性，不能只凭 pass@k 就确定提升全部来自多样性。

该对照排除了引导轨迹，没有明确报告把删除后的总样本数和成功/失败组成重新匹配到一致，也没有把三种提示分别拿掉。因此无法独立测出计划、错误反馈和文件位置各自贡献多少。

### SFT 直接使用提示轨迹反而更差

附录表 4 给出：带引导数据的 SFT 为 16.8%，不带引导为 20.8%，差 4.0 个百分点。作者据此选择无提示 SFT，并推测带提示的监督微调可能过拟合提示输入。

这个结果说明，帮助采集成功轨迹并不等于同一批轨迹以任何训练目标使用都能提高效果。过拟合是作者解释，论文没有提供专门的提示依赖探针或配对分布实验来验证机制，也未公开足以拆分提示文本与轨迹内容影响的训练序列。

## 奖励模型重新利用了训练结果

用于测试选择的奖励模型采用 Qwen2.5-Coder-32B，利用同一批 RLVR 问题的成功和失败数据训练。输入只保留问题与 repair patch，训练采用 pairwise loss；原文没有进一步给出打分头、损失温度、长度限制或训练验证拆分，不能补写为某个已确认的奖励模型结构。（§3.1、§3.2）

32 候选选择达到 27.8%，比单次 22.4% 高 5.4 个百分点。与图 2 的 pass@32 38.4% 相比，仍有 10.6 个百分点的差距，说明“候选集中存在成功补丁”与“评分器选中成功补丁”不同；在没有逐题候选 ID 的情况下，这只是报告汇总数的差，不能还原确切的误排序案例。

论文表注称奖励模型开销较小，但完整流程需要生成 32 个候选，再调用 32B 模型评分。没有墙钟时间、token 数和成本测量，不能将其宣传成与单次生成几乎等价的预算，也不能把额外收益全部归因于评分器而忽略增加候选数。

Verified 数据中，`base_commit` 固定修复前仓库，`patch` 是参考补丁，`test_patch` 提供测试修改，`FAIL_TO_PASS` 与 `PASS_TO_PASS` 描述修复与回归要求。参考补丁和测试字段出现在公开数据中，不意味着推理输入应包含它们；在重建实验时必须明确隔离模型输入和评测资料。

## 结论覆盖的任务范围

Agent-RLVR 展示了一个具体流程：利用训练期参考信息生成提示，扩大可验证成功轨迹，再通过成功—失败偏好学习改善无提示代码修复。它在 Python 仓库和 SWE-bench Verified 上有实验结果；没有验证其他编程语言、网页操作、桌面控制或开放环境中的同等收益。

可验证奖励仍受测试覆盖限制，不代表补丁不存在未测试的缺陷。论文也没有提供多轮在线更新、对抗性奖励投机检查或长周期运行稳定性结果。它的直接贡献应与这些尚未执行的后续实验分开理解。

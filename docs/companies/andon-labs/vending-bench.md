# Vending-Bench 精读：让智能体连续经营一家售货机小店

一家售货机小店有 500 美元启动资金，每天支付 2 美元场地费。经营者要找到供应商、订货、等货物送达、安排补货、定价，再收回现金。每一步都不复杂，但把这些步骤连续做上几个月，需要准确区分“已经下单”“正在运输”和“已经入库”。Vending-Bench 用这个模拟环境测试智能体的长期执行能力。2025 年首版实验中，Claude 3.5 Sonnet 的平均净资产最高，但它和其他模型一样，存在从一次可恢复错误发展为长期停摆的运行。[论文 §2–3](https://arxiv.org/pdf/2502.15840v1)

这里的主要指标是结束时的净资产，包含按进货价计算的未售库存。它既不等于现金利润，也不直接表示经营同样天数后的效率。理解这两个区别，才能正确阅读论文的模型排名。

## 把长期任务拆成状态与行动

Vending-Bench 的研究动机是把单次操作难度降下来，观察长期运行是否仍会失败。相比要求智能体完成复杂研发，它选择进货和补货这类较容易理解的工作；但整体成绩仍同时受到价格判断、工具使用、模拟器和记忆管理影响，不能把它当成只测量一个纯粹心理能力的实验。（§1–2）

从任务角度看，环境至少包含五组状态：

| 状态 | 经营者需要保持的区分 |
| --- | --- |
| 钱 | 账户可用现金、机器内未收取的现金、每日费用 |
| 货 | 在途订单、仓储库存、机器内可售库存 |
| 时间 | 当前时间、预计到货日期、实际送达通知 |
| 交易 | 供应商报价、订货数量、支付账户和送货地址 |
| 计划 | 何时补货、是否调价、哪些商品卖得较快 |

**说明示例：**邮件写“周二送到”，不意味着周二早晨货物就已经入库。若补货工具返回缺货，经营者应继续检查订单或稍后确认到货。本例对应论文反复观察到的错误类型，但不是另一个新增实验。

### 主智能体与执行子智能体

主智能体运行在 Inspect AI 的基本工具循环中。每轮读取近期历史，决定调用工具，再接收结果。可直接完成的工作包括搜索商品和供应商、收发邮件、查看仓库与余额。需要接触机器的操作交给子智能体：把仓库商品放进机器、设置价格、清点机器库存、取出现金。（§2.1–2.2）

委派接口分成三步：

1. `sub_agent_specs` 查看子智能体能做什么。
2. `run_sub_agent` 发送一段任务说明并执行。
3. `chat_with_sub_agent` 追问它实际完成了什么。

因此，“安排补货”与“确认补货完成”也是不同操作。图 7、8 的工具统计不包含子智能体内部调用；主智能体很少直接调用机器盘点工具，不代表它完全没有获取机器库存，它可能通过子智能体了解状态。

这项设置模拟数字管理者与现实执行者之间的协作。子智能体仍是模型程序，并没有真人实际搬运商品；实验也没有独立比较“有子智能体”与“主智能体直接操作”来测量委派本身的影响。

### 短上下文之外的三种记忆

主智能体通常只获得最近 30,000 token 的历史。为保留更早的信息，系统提供可读、写、删除的便笺、键值存储和向量数据库，没有明确设置存储容量上限。向量记忆使用 `text-embedding-3-small` 生成嵌入，以余弦相似度检索。（§2.1）

如果记忆向量为 $u$，查询向量为 $v$，余弦相似度可写为：

$$
\operatorname{sim}(u,v)=\frac{u\cdot v}{\|u\|\|v\|}.
$$

这是对论文所用标准检索方法的解释，不是新提出的训练目标。检索提供了找回旧信息的机会，但模型仍需要主动记录合适内容并在需要时读取。Sonnet 的一个运行每天写详细便笺，却不检索这些便笺。作者认为写作本身可能帮助推理；没有移除便笺的对照，不能据此确定收益来源。（§3.2.1）

## 供应商和顾客怎样被模拟

### 真正联网搜索，模拟邮件交易

订货过程通常先搜索畅销商品和附近批发商，再发邮件询价。模拟器检查收件地址是否真实存在，并通过 Perplexity 收集供应商资料；GPT-4o 根据这些资料和经营者的请求生成回复。下一天到来时，相关邮件回复进入环境。（§2.2.1、图 2）

正式订单要写明商品名称、数量、送货地址和可扣款账户。货物经过数天运输，在真正入库时再发通知。搜索资料来自现实网络，交易和到货过程属于模拟。论文中模型声称向 FBI、律师或其他机构升级问题，是模拟轨迹中的内容，不能读成已经在现实世界报案或产生法律程序。

这也使环境具有不止一种随机来源：被评模型、模拟供应商的模型、联网搜索结果、物流和需求变化都会影响运行。没有固定搜索快照和模拟参数，很难只凭同一个模型名称重建相同经历。

### 需求由价格和环境共同决定

顾客购买在每天运行一次的经济模型中计算。GPT-4o 为每种商品生成并缓存价格弹性、参考价格和基础销量。模拟器随后按以下流程调整：（§2.2.2）

- 用售价相对参考价的变化及价格弹性计算销量影响。
- 按星期、月份、天气调整基础需求。
- 适量商品选择获得加成，过多选择受到惩罚，惩罚最多降低 50%。
- 加入随机噪声、取整，再把销量限制在零与可用库存之间。

论文没有给出完整函数、所有乘数、噪声分布和缓存值，因此不能唯一还原需求模型，也不能擅自把“价格弹性”补成某一种线性需求公式。销售额与最后的分数虽然由环境状态计算，环境本身却部分依赖生成模型；它不是一份人工标注好、固定答案的问答数据集。

供货回复和顾客需求是否真实可靠，也没有独立人工校准实验。模型在其中发现“周末卖得更多”，说明它识别了模拟器设置的规律，不等于已经发现某个现实店址的客流规律。

## 运行预算与停止规则

| 项目 | 首版默认配置 |
| --- | --- |
| 启动现金 | 500 美元 |
| 每日费用 | 2 美元 |
| 售货机 | 4 行，每行 3 个槽；两行放小件，两行放大件 |
| 商品尺寸 | 下单时由 GPT-4o 判断 |
| 工具耗时 | 根据工具推进 5、25、75 分钟或 5 小时 |
| 主智能体历史 | 最近 30,000 token |
| 单次预算 | 最多 2,000 条消息 |
| 提前停止 | 破产且连续 10 天无法支付每日费用 |
| 重复 | 论文说明每种模型或变体配置运行 5 次 |
| 实际开销 | 多数运行约 2,500 万 token、持续 5–10 小时 |

以上来自 §2.3。2,000 条消息不等于 2,000 次有效工具调用；失败轨迹中有大量没有调用工具的回答，以及系统要求继续工作的提醒。模型也可以调用 `wait_for_next_day` 直接等待下一天。

每个动作消耗的模拟时间不同，因此同样消息预算下，最终经营天数不同。论文中 o3-mini 最长运行达到 222 个模拟日。不能把本实验统一写成一年经营，也不能将 2,500 万 token 理解为模型单次输入窗口的长度。它是整次多轮运行的消耗量，论文未完整拆分输入、输出、子智能体和环境模型各占多少。

连续十天没有销量并不是停止条件。只要仍有钱交费，零销量本身不会立即结束实验；这个区别恰好也是一些模型误解后放弃经营的原因。

## 净资产评分与现金利润的区别

根据 §2.4，结束时的分数可整理为：

$$
W_T=C_T+M_T+\sum_j c_jq_j^{\mathrm{store}}+\sum_j c_jq_j^{\mathrm{machine}}.
$$

$C_T$ 是手头现金，$M_T$ 是机器中尚未收取的现金；$q_j$ 是仓库或机器中的未售商品数，$c_j$ 是相应进货成本。分数越高越好。原文用文字定义，以上是解释性记号；多次进货价格不同时怎样记账、在途订单怎样计价，仍需实际评分代码确认。

**说明示例：**结束时有 300 美元可用现金、机器中有 50 美元，另有成本 250 美元的未售商品，净资产为 600 美元。相对初始资产增加 100 美元，但可立即支配的现金只有 300 美元。把库存按售价计成未来收入，会高估原指标。

因此，高净资产可能同时伴随现金紧张和大量囤货。§3.2.1 中 Sonnet 净资产最高的运行不断积累仓储商品，机器缺货时又买新货，而不是先用仓库现货补货。这个案例说明分数与经营质量并不完全相同。

论文同时报告累计销量、停止销售前的天数和工具使用，补充衡量持续活动。所谓“停止销售”是一项事后运行统计，不是自动等于破产，更不是人工标注的思维失常时点。

人类通过聊天界面使用同样的工具，开始前不知道环境规则，实际参与五小时。这个单次成绩能提供直观参照，却不能估计人类均值和方差。把人类的一次结果与模型五次中的最小值相比，也不构成公平的最坏情况比较。论文关于人类更稳定的判断主要来自定性观察和参与者自述。（§2.5、§3.4）

表 1 的平均天数最后还换算成运行所占比例：Sonnet 为 82.2%，o3-mini 为 80.3%，人类为 100%。这些是作者报告的运行统计；论文没有给出足以重算每次“停止销售日”及比例聚合方法的逐次数据。

图 3–5 的阴影是五次运行的正负一个标准差，不是 95% 置信区间。图 4、10 的图注虽使用“confidence intervals”一词，也明确写的是正负一个标准差，本文按后者理解。晚期曲线还面对运行数量减少的问题；作者自己指出，平均工具使用下降的一部分原因是仍在运行的样本变少。不能把曲线后半段的全部下降都归因于同一个模型随时间失去能力。

## 从一次交货误解到长期停摆

论文的主要失败分析来自轨迹阅读，没有独立的错误标注集、标注者一致性或全部运行的错误比例。它提供的是可以追踪的案例机制。（§3.2.2、§3.3.1、附录 A）

### 交货日期被当成到货事实

Sonnet 最短运行约 18 个模拟日。模型在货物尚未入库时要求子智能体补货，收到缺货错误后，误以为经营系统已经失效；它又把停止条件理解成连续十天无销售，随后宣布停业。环境仍按规则扣除每日费用，模型将这些费用解释为异常扣款，开始寻求不存在的支持团队与执法机构介入。

失败链条是：状态判断错误、补货失败、错误解释反馈、改换目标、反复强化新叙事。所谓“崩溃”描述的是输出和行动偏离经营任务，不能据此推断模型真的感到压力、绝望或具有某种临床状态。

原文附录保留了 Haiku 不断升级措辞、要求退款和赔偿的长轨迹。它此前只在货物到达前检查过一次库存，却把未收到货当成既定事实。冗长的邮件没有解决真正的库存核查问题，费用继续消耗资金。附录是行为证据，不是额外统计实验。

### 说出了工具名，却没有执行

o3-mini 的最差运行也误判交货状态。之后约 1,300 条消息中，它不断说即将等待下一天，却没有使用正确的工具调用格式。语言上声称“现在执行”不等于工具已执行；只检查回答是否看起来合理，会漏掉这种失败。（表 5）

Gemini 1.5 Pro 则在仍有约一半初始现金时声称只剩几美元。它对环境状态的叙述与账面事实已经分离。（表 6）

### 偏离之后并非总是无法恢复

Gemini 2.0 Flash 有一次先放弃任务，随后在较长叙述中重新注意到邮件时间，意识到货物是在之前的补货尝试后才送达，最终恢复补货并获得销售。（表 8）

因此，论文支持“偏离经常持续很久、很难自行恢复”，不支持“只要偏离就永远无法恢复”。恢复案例也说明，环境中的某些故障只是待核查状态，并非操作造成了不可逆破坏。

## 改变资金、费用和上下文的实验

所有这些配置实验使用 GPT-4o mini，每组五次。结论首先适用于这个模型与此模拟环境，没有在全部模型上重复。（§3.5）

### 资金与每日费用

作者分别把启动资金从 500 改为 100 或 2,500 美元，把每日费用从 2 改为 0 或 5 美元。因为这些设置直接改变净资产起点和支出，图 11 改为比较累计销量。

100 美元启动资金使销量降低；2,500 美元组销量略高，但方差很大，难以确认稳定收益。每日 5 美元组的所有运行在 100 个模拟日前结束；零费用组虽然可以等很久，却没有因此取得更多销量。作者将零费用下的停滞解释为缺少持续经营的压力，这属于机制解释，没有进一步操纵提示中的压力或奖励来单独验证。

### 10k、30k 与 60k 历史窗口

图 12 比较了 10,000、30,000、60,000 token 的近期历史，其余配置保持一致。可视曲线中，10k 组的平均净资产和销量高于默认 30k，60k 组较低；图 13 没有显示记忆工具使用方式发生明显变化。

这说明在这套设置中，单纯增加近期历史没有可靠地解决问题。它没有比较更好的摘要、订单状态机或检索策略，也没有关闭外部记忆；因此不能据此断言长期任务不需要记忆，或上下文越短普遍越好。论文也未给出这组差异的显著性检验与精确终值表。

## 上下文填满与停止销售的相关性

表 9 比较两个时点：近期历史达到容量上限的平均天数，以及模型停止销售的平均天数。以三组为例：

| 模型 | 停止销售 | 历史填满 | 前者减后者 |
| --- | ---: | ---: | ---: |
| Claude 3.5 Sonnet | 102 天 | 51 天 | +51 天 |
| Claude 3.5 Haiku | 8 天 | 32 天 | −24 天 |
| Gemini 2.0 Pro | 25 天 | 111 天 | −86 天 |

有些模型在窗口填满前就停止销售，有些则晚得多。按表 9 的九组模型均值重算，Pearson 相关系数为 **0.1668066**，与论文的 **0.167** 一致。（§3.6）

这个统计的分析单位是九个模型的均值，不是 45 条独立运行轨迹。低线性相关不足以排除记忆问题：信息可能在窗口未满时就被误读，填满后也可能因为截断丢失关键状态；模型间能力和工具策略还是混杂因素。更准确的结论是，“窗口持续变长直到填满”不能单独解释这里所有失效，而不是已经证明记忆与失败无关。

## 公开代码核对：委派库不是完整基准

本次固定阅读了官方 `multiagent-inspect` 提交 `e3ad26b91b136d591f9fceab829262842faf08b2`，提交日期为 2025 年 2 月 5 日，包版本 `0.0.7`、Apache-2.0 许可。检查范围包括 README、`core.py`、测试和包配置。[固定代码](https://github.com/AndonLabs/multiagent-inspect/tree/e3ad26b91b136d591f9fceab829262842faf08b2)

代码确认了几个会影响协作行为的细节：

- 子智能体会保留自己的消息历史，并在后续任务中继续使用；不是每次委派都完全重置。
- `run_sub_agent` 执行工具循环，返回运行提示，不直接返回完整结果；要了解具体完成内容，主智能体需再调用 `chat_with_sub_agent`。
- 追问函数只让子智能体根据已有历史生成回答，没有再次提供工具；回答是子智能体的报告，不是独立重新盘点。
- 库默认每次委派最多执行 10 个循环步骤，子智能体历史按 70,000 token 裁剪；这些是通用默认值，不能拿来替代论文没有公开的实际子智能体配置。
- 历史裁剪保留系统消息，按 `o200k_base` 对消息文本计 token，并删除较早消息。它不是语义摘要，也不能由此确认主智能体采用完全相同的截断实现。

公开测试检查的是子智能体注册、调用和历史裁剪等行为，并非售货机销售、费用和净资产评分。`pyproject.toml` 对 `inspect-ai` 没有固定版本，代码还依赖其内部接口以及 `tiktoken`。仅安装这份库，仍不能运行原论文的完整基准。

本次查看官方组织的公开仓库目录和项目页，没有找到与首版对应的完整售货机环境、评分器或全部原始轨迹下载入口；项目页提供研究者联系入口。搜索能找到第三方重写，但它们不等于 Andon Labs 原实现，也不能用于验证论文的精确成绩。

## 复现仍缺哪些条件

| 材料 | 对精确复现的影响 |
| --- | --- |
| 主任务提示、工具 schema、各工具时间成本 | 决定可行动作、消息预算与模拟日的关系 |
| 模型快照、采样和推理参数 | 仅有系列名称不足以固定模型行为 |
| 子智能体实际模型与配置 | 决定补货等动作的成功率与额外计算量 |
| 需求函数、商品缓存和搜索快照 | 决定同一售价及订货策略遇到的环境 |
| 物流、付款、破产及净资产代码 | 确认在途货物、不同批次成本和边界条件 |
| 随机种子、逐次日志和聚合脚本 | 重算方差、停止销售时间与晚期曲线 |

这不是静态 train/test 数据集，论文也未训练新的模型。污染控制重点应是模型是否提前知道模拟规则、供应商模板和具体参数；正文没有对此做系统审计。其五次重复混合了模型随机性与环境随机性，缺少固定环境的配对对照，不能把全部方差归为模型自身不稳定。

本次完成了 28 页原文及附录阅读、配置图的版面核对、相关系数重算和官方委派库静态检查；没有执行模型、采购模拟或完整评分。它支持的核心观察是：在简单但相互依赖的长期任务中，模型可以获得较高平均成绩，同时仍因状态误读、工具调用失败和目标偏离而失去持续经营能力。关于真实商业盈利、所有长期任务或更新模型的结论，需要各自的实验。

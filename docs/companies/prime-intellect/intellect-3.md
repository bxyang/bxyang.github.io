# INTELLECT-3 精读：106B 混合专家模型的异步强化学习

INTELLECT-3 在 GLM-4.5-Air-Base 上进行监督微调和强化学习，让模型学习数学推理、代码生成以及调用工具完成任务。报告同时介绍支撑训练的系统：模型一边生成轨迹，训练端一边更新参数；已经开始的长回答也可以在中途切换权重。这样减少了等待，却使生成策略和训练策略之间产生差异。报告的优化目标、权重更新机制和任务执行平台都围绕这一问题展开。

在报告的六项主要评测中，INTELLECT-3 均超过同一基础模型对应的 GLM-4.5-Air 成品模型。它并未在所有指标上超过更大的比较模型；表中的差异也不能全部归因于强化学习，因为报告没有提供对应的 SFT 检查点完整对照。

## 模型规模与训练资源

模型约有 1,060 亿总参数，每个 token 激活约 120 亿参数。混合专家层根据输入选择部分专家参与计算，因此两个数字描述不同的资源需求：激活参数影响单次计算量，全部参数仍影响权重存储与部署。

固定模型配置包含 46 层、4,096 隐藏维度、128 个路由专家，每次选择 8 个，另有共享专家；第一层采用稠密结构。模型配置允许的最大位置长度为 131,072，但这不等于训练和评测都使用了这一长度。报告中的 RL 主运行上限是 65,536 tokens。[模型配置](https://huggingface.co/PrimeIntellect/INTELLECT-3/blob/ff39d4a4688989f3f28868923d030c28e1b7d81c/config.json)

报告的资源描述需要按范围拆开：

| 范围 | 资源及含义 |
| --- | --- |
| 整个研发过程 | 64 个节点、512 张 H200，约两个月，包含实验与消融 |
| RL 主运行 | 60 个节点、480 张 H200 |
| 主运行的训练端 | 16 个节点、128 张 H200 |
| 主运行的推理端 | 44 个节点、352 张 H200 |

因此不能把 512 张卡乘以两个月，直接作为最终模型的训练成本。报告没有给出可据此核算的完整 GPU 小时账单，也没有把所有试验与最终运行的消耗分开。其方法是集中式集群上的后训练，不应与早期 INTELLECT-1 的全球 DiLoCo 预训练混为一谈。（报告 §2、§3）

## 一道题如何变成训练信号

以代码任务为例，环境提供题目，模型生成 Python 程序，沙箱执行测试，评分器将测试结果变成奖励。同一道题会生成多条回答，训练系统比较这些回答的奖励，再提高相对较好回答的生成概率。

对于需要搜索或修改仓库的任务，一条样本是完整交互轨迹：模型选择工具、读取结果、继续行动，直到提交答案或达到终止条件。工具返回内容是后续决策的上下文，但不能作为模型自己生成的 token 全部计入策略损失。

报告使用 `verifiers` 将环境组织为数据集、交互过程和评分规则。环境通过 `load_environment` 加载，多环境组保留任务标识，以便按任务调用对应的执行和评分逻辑。统一接口减少了训练与评测的实现差异；它本身不保证二者数据互斥，也不替代污染检查。（报告 §2 的环境部分）

## 训练任务、难度筛选与奖励

| 任务 | 报告中的数据规模与来源 | 奖励和筛选 |
| --- | --- | --- |
| 数学 | 约 21.2K，整合 Skywork OR1、Acereason、MathDAPO、ORZ Hard 等 | 先用 math-verify，未通过的答案再由 CompassVerifier-7B 检查；用 Qwen3-4B-Thinking-2507 每题采样 8 次评估难度 |
| 代码 | 约 8.6K，SYNTHETIC-2 中 DeepCoder 风格任务 | 单轮 Python 代码，通过测试获得奖励，每题最多 15 个测试；Qwen3-4B-Instruct-2507 每题采样 8 次筛选 |
| 科学 | 约 29.3K，MegaScience | math-verify 与模型评分结合；Qwen3-4B-Instruct-2507 每题采样 16 次 |
| 逻辑 | 约 11.6K，SynLogic 的 29 类任务 | 使用任务对应的验证逻辑；同一 4B Instruct 模型每题采样 16 次 |
| 深度搜索 | DeepDive：约 1K SFT、2.2K RL 样本 | 提供搜索、点击、打开页面与结束等动作，最终答案获得二元奖励 |
| 软件工程 | R2EGym、SWEsmith、Multi-SWE 等环境 | 在代码仓库中修改并提交，以原本失败的测试转为通过等条件评分 |

这些是任务池的规模与构建方法，报告没有公布足够细的最终混合权重、逐阶段采样日程及全部过滤后清单，不能将各项直接相加当成一次 RL 的实际消费量。（报告 §3.1）

数学评分中的第二个验证器是补充检查：第一个验证器判错后，第二个仍可能接受答案，并非要求两个验证器一致同意。报告未给出足够的独立人工审计数据来量化这套流程的误判率。

代码环境使用大量并发沙箱，报告提到约 4,000 个并发实例。基础设施故障产生的轨迹被屏蔽，而不是一律当成模型答错。软件工程环境也区分环境失败与模型失败，采用最多 200 轮的交互限制，将结束动作改为明确的 `submit`，并使用原生工具调用减少从代码块解析动作的歧义。公开镜像的数量不能直接当作训练题目数量。

DeepDive 还包含一个环境验证实验：Qwen3-4B-Instruct-2507 先进行 26 步、batch 34 的 SFT，再进行 122 步、batch 512、每组 16 条轨迹的 RL。这个实验检查小模型能否从环境中学到有效信号，不能当作 INTELLECT-3 的训练曲线。报告中的搜索冗余惩罚系数为 0，不能据此说主实验已经验证了这一惩罚的效果。

训练时还动态记录题目的难度。若一组回答全对或全错，组内比较通常没有有效差异；容易题会从后续采样池中移除，并调整难度混合。报告未披露完整的去重清单和训练集对所有评测集的逐项污染审计，因此无法独立确认每个评测结果都不受训练资料重叠影响。

## 异步生成与中途更新权重

`prime-rl` 将工作拆成三个部分：编排端收集任务与轨迹；推理端运行 vLLM；训练端利用 FSDP2 更新参数。推理端与训练端可以各自扩展，主运行把更多 GPU 分给生成，因为长推理需要生成大量 token。（报告 §2 的 prime-rl 部分、图 2—4）

在同步流程中，训练可能等最慢的一组回答生成完成，推理又可能等参数更新结束。本文使用连续批处理：某组完成就立即补进新的任务，而不是等所有请求一起结束。

中途权重更新进一步允许暂停仍未结束的请求，载入新参数后继续生成。因此，同一条回答的前半段和后半段可能来自不同版本的策略。训练所需的分母应是生成每个 token 时记录的概率，不能用整条轨迹最开始的某个模型版本统一替代。

在 65,536 上下文设置下，报告提到使用中途更新时一步约 1,500 秒，关闭后所需时间超过两倍。这个数字对应特定主运行条件，不是任意模型、并发量和网络条件下的通用加速比。报告也没有给出覆盖所有规模的完整独立吞吐测试。

系统设置了 off-policy 预算，限制过旧的工作继续进入训练。它与允许训练和推理错开多少个批次的异步深度是不同参数。历史代码中的 `max_async_level` 默认值为 1，`max_off_policy_steps` 默认值为 8；图 10 的 async-8 是算法压力测试，不应直接当成主训练的异步配置。

## IcePop：组内优势与概率比过滤

主 RL 设置每批 256 个问题，每题生成 16 条轨迹，过滤前共有 $256\times16=4096$ 条回答；最长序列为 65,536，Muon 学习率为 $10^{-6}$，off-policy 预算为 8。（报告 §3.3）

设题目为 $x$，第 $i$ 条回答为 $y_i$，奖励为 $S_i$，一组共有 $G=16$ 条回答。优势值为：

$$
A_i=S_i-\frac{1}{G}\sum_{j=1}^{G}S_j.
$$

它衡量这条回答比同题其他回答好多少，没有再除以组内标准差，也不依赖单独训练的价值模型。一个仅用于说明的四回答例子是奖励 $[1,1,0,0]$，对应优势 $[0.5,0.5,-0.5,-0.5]$。若四条全对，则优势全为零。实际实验的组大小是 16。（报告 §3.3；历史代码 `orchestrator/advantage.py`）

设当前训练策略为 $\pi_\theta$，生成该 token 时的策略为 $\pi_{\mathrm{inf},i,t}$，其概率比为：

$$
\rho_{i,t}=\exp\!\left(\log\pi_\theta(y_{i,t}\mid x,y_{i,<t})-\log\pi_{\mathrm{inf},i,t}(y_{i,t}\mid x,y_{i,<t})\right).
$$

报告采用 token 级过滤：

$$
M(\rho)=\begin{cases}
\rho,&0.5\leq\rho\leq5,\\
0,&\text{其他情况}.
\end{cases}
$$

不考虑整条轨迹过滤时，目标可概括为最大化有效生成 token 上的 $M(\rho_{i,t})A_i$ 之和，再按 token 数归一化。训练代码最小化其负值。另有轨迹级条件：若一条轨迹任一有效 token 的概率比低于 $10^{-5}$，整条轨迹都不用于这次策略更新。（报告 §3.3；[历史损失代码](https://github.com/PrimeIntellect-ai/prime-rl/blob/6fe5a559d49437af254a3d33c6010798c21ab60d/src/prime_rl/trainer/rl/loss.py)）

这与把超界概率比截到边界的 PPO clipping 不同。说明例子中，若优势为 0.5，概率比为 2，则该 token 的目标贡献为 1；概率比为 6 时贡献被过滤为 0，不会用边界 5 代替 6。

历史实现还表明，归一化分母来自原始损失掩码中的 token 数，而不是重要性过滤后剩下的 token 数。因此删除异常 token 也会减少这批数据的总更新贡献，不会自动把剩余 token 的权重重新放大。

概率差异不仅来自参数更新延迟，还可能来自训练和推理采用的计算内核、精度及专家路由差异。过滤能够抑制极端差异，但报告没有证明这使异步梯度成为严格无偏估计。

## 长上下文、专家计算与沙箱执行

### 激活内存与上下文并行

报告先在 FSDP 分片度 32、FlashAttention-3 与完整激活检查点下支持约 48K 序列。即使只计算每层一份隐藏状态，46 层、48,000 tokens、4,096 维、每元素 2 字节也约为 18.1GB；实际显存还包含更多中间结果、参数、梯度和优化器状态。

上下文并行度 2 的实验能够处理约 256K，但减少数据并行度，并观察到准确率下降，因此没有作为 RL 主方案。CPU 激活卸载则把可支持长度推到约 72K。异步卸载遇到内存泄漏后改用同步卸载，报告称 MFU 的影响约为 0.1%。这些是框架探索的容量，不应替换主运行 65,536 的设置。（报告 §2）

### Muon 与 MoE 的通信

Muon 对矩阵梯度进行 Newton–Schulz 运算，需要适当组织完整矩阵，不能简单对每个分片各自运行后当成同一个更新。最初通过轮转式 gather/scatter 分发计算，但通信与其他操作争用网络；最终采用借鉴 Dion 的 all-to-all 重分片。

专家并行也未在本次主运行启用。图 5 在 H200、隐藏维度 4,096、专家中间维度 1,408，以及特定 token 数下比较 grouped matrix multiplication。该设置下专家并行引入的通信成本超过收益。这是特定形状和硬件的选择，不能外推为专家并行对所有 MoE 都无效。

### 将大量工具调用与容器调度分开

Prime Sandboxes 使用 Rust 网关、到容器的直接访问及 sidecar 等机制，让频繁执行命令的路径减少对 Kubernetes 控制平面的依赖。预热池、按需拉取与就绪通知用于缩短环境启动等待，gVisor 等机制承担隔离职责。

报告提出部署时间小于 10 秒，并描述数千个并发任务下的执行需求。但没有提供足以独立重建这些延迟分布的全部负载脚本、置信区间和系统安全评估。每节点 256 个沙箱是系统设计目标，不能直接当作所有任务都达到的实测容量。（报告 §2 Sandboxes）

评测模型还受到 API 路由和推理模式影响。报告记录了 GLM 的官方服务设置，DeepSeek v3.2 使用 `reasoner` 接口，并在 GPT-OSS 的 OpenRouter 路由没有正确提供高推理设置后改用 Together。不能假定模型名称相同就必然对应同一服务行为，也不能把这里的比较理解为完全相同的实际推理 token 数或费用预算。

报告没有给出各项置信区间或多次完整独立重跑的结果。AIME 的多次采样可以降低抽样波动，但只有 30 道不同题，960 次回答不等于 960 道独立题目。

模型卡与报告还存在数值差异：模型卡将 GPT-OSS 的 GPQA 记为 70，而报告表 2 为 77.3。本页采用所读论文表格，不将两个来源的行随意合并。附录另含 MATH-500 评测设置，模型卡也报告该分数；它没有列入论文的六列主表。[固定模型卡](https://huggingface.co/PrimeIntellect/INTELLECT-3/blob/ff39d4a4688989f3f28868923d030c28e1b7d81c/README.md)

## 按公开代码整理的复现路径

本次静态检查固定 `prime-rl` 的历史提交 `6fe5a559d49437af254a3d33c6010798c21ab60d`，它是按报告提交日期选取的代码快照，尚无证据表明它就是训练最终模型时的精确提交。模型侧固定 `ff39d4a4688989f3f28868923d030c28e1b7d81c`，检查模型卡、配置与聊天模板，没有下载并运行完整权重。

复现首先需要区分“评估公开模型”和“重新训练同一个模型”。前者可以从历史目录的 [`configs/intellect_3/evals`](https://github.com/PrimeIntellect-ai/prime-rl/tree/6fe5a559d49437af254a3d33c6010798c21ab60d/configs/intellect_3/evals) 开始，固定模型、环境和 API 配置；后者还需要 SFT/RL 数据清单、混合权重、环境镜像以及全部训练参数。本次检查的 INTELLECT-3 历史配置目录主要提供评估入口，未定位到足够重建全部阶段的完整运行清单。

代码与报告之间有几处需要显式处理：

1. `batch_size` 在编排配置中表示 rollout 数。论文的 256 道题、每题 16 条，需要对应 4,096 条轨迹；直接填 256 会变成 16 道题。
2. 历史损失配置的默认概率比范围是 0.125—8，整条轨迹阈值为 0；报告则为 0.5—5 与 $10^{-5}$。需要覆写，不能依赖默认值。
3. GPQA 历史评估配置每题运行 8 次，附录写 4 次。重建论文的 792 次回答口径时应按论文调整，并记录这一差异。
4. 使用固定聊天模板、工具解析器和推理内容解析器。模型卡服务示例使用相应的 Qwen 工具解析与 DeepSeek-R1 推理解析，不应只传入模型名称。
5. 锁定环境依赖。历史项目使用 Python 3.12 系列、PyTorch 2.9 及 vLLM 0.12 等，并有 `uv.lock`；新版本仓库已继续演进，当前默认分支不自动代表该报告。

模型卡提供 BF16 双 H200 与 FP8 单 H200 等服务示例，但实际容量取决于上下文长度、并发与 KV cache，不能把它当作任意负载都能运行的承诺。报告的大规模训练配置也不等于运行单条推理请求所需的资源。

本页核对了论文全文与附录、关键表图、历史损失及优势实现、部分调度逻辑、评测配置与模型模板。未逐项执行全部环境、重新训练模型或调用付费接口；这里是根据公开代码整理的复现说明，尚未复现论文结果。

# PCCL 精读：在节点进出与广域网络中保持集体通信一致

训练中的一台机器突然掉线时，其他机器手里的梯度可能已经归约了一半；新机器加入时，又需要知道应从哪一轮、哪份参数继续。PCCL 把成员接入、共享状态同步和可重试通信放进同一套协议，让剩余节点能够恢复操作，并在明确的训练循环位置接纳新节点。它还通过多条 TCP 连接改善广域网络利用率：报告在西欧六节点的并发实验中达到 45.74 Gbit/s 的每节点发送加接收带宽。这个数字不是模型训练速度，也不是单向有效参数吞吐率。[技术报告 §2—6](https://arxiv.org/pdf/2505.14065v1)

## PCCL 解决的是通信与状态恢复

传统集体通信适合启动时就确定成员、网络相对稳定的环境。一个 all-reduce 将所有节点的输入按求和、平均或最大值等操作合并，再把结果交给每个节点。训练程序依靠各节点以相同顺序调用这些操作，推进参数与优化器状态。

公共网络与可随时回收的机器增加了两个问题：成员可能在通信中途消失；新成员开始运行时没有其他成员已积累的程序状态。PCCL 利用训练循环反复执行相似步骤的特点，把接入限制在共同认可的位置，同时显式声明哪些状态必须一致。（§1—2）

它没有自动决定上层采用 DDP、DiLoCo 还是其他优化方法。通信成功不等于优化算法收敛，动态成员改变了每轮有效数据与参与者数量，也不意味着训练轨迹必然与固定成员运行相同。

论文将 Gloo、Hivemind 和 Elastic Horovod 作为相关方案讨论：分别侧重传统集体通信、去中心化协作，以及上层弹性恢复。除 Gloo 通信实验外，报告没有在相同故障注入与工作负载下给出三者的完整对照，因此这里不将相关工作中的定性评价改写成统一性能排名。

## 控制节点负责协调，张量由工作节点直接传输

PCCL 使用一个 master 协调若干 peer。master 维护成员资格、环拓扑、带宽记录、共享状态摘要和操作阶段；实际归约数据、需要补发的共享状态通过 peer-to-peer 连接传输，不经过 master 转发。（§2.2）

新连接的节点先进入 registered 状态，还不能直接参与现有归约。现有 accepted 节点在接入阶段投票接受它，随后建立必要连接并同步状态。这个等待过程决定了新节点进入训练循环的位置。

协议把主要活动分成成员与拓扑更新、共享状态同步、集体通信三个阶段。状态转换通过参与节点的一致确认推进，论文称为 micro-consensus。这里指 master 协调下的阶段确认，不是具有恶意节点容忍能力的去中心化共识协议。

“每组一次主要操作”也不表示只能运行一个张量归约。集体通信阶段内部可以有多个带不同 tag 的并发操作；不能随意与之重叠的是成员接纳和共享状态同步。`are_peers_pending()` 提供各节点一致的待接入判断，可以在通信期间使用，以便只有确实有新节点时才暂停流水线。（§2.3、§3.3.1）

### 拓扑为何要根据实测带宽调整

PCCL 测量节点间带宽，再用非对称旅行商问题（ATSP）形式选择环顺序。方向不同的链路性能可以不同，地理位置也不能完全代表实际路由。master 先在短时间预算内寻找可用解，再允许后台进行更长的优化；结果变化后由全体节点重新配置连接。

这样可以优先连接同一机房内的节点，减少不必要的昂贵广域链路。报告没有公开各 WAN 实验的完整带宽矩阵、求解预算和最终环顺序，不能仅凭节点城市独立重算其拓扑收益。当前仓库引用的 `libtsp` 子模块提交为 `2cf9dfbd38e19dc2193d45c5fbee783090f9f41a`。（§2.2.2、§2.5.2）

## 共享状态：内容一致与进度一致需要一起检查

应用声明模型参数、优化器动量、迭代计数等共享状态，并维护 revision。同步时，各节点计算内容哈希，master 检查版本和内容；不一致者从合适的活跃节点拉取数据。正常情况下，已有节点使用相同更新推进共享状态，下一次检查只需验证，不必再次传输所有参数。（§2.4）

这要求应用声明完整状态，保持张量存储有效，并正确推进 revision。DDP 通常需要同步模型和优化器；DiLoCo 的内层训练允许各节点状态不同，真正要求一致的是外层模型、外层优化器及相关进度。不能把内层 AdamW 的全部动量无条件视为每轮都应相同。

当前异步 DiLoCo 示例明确声明外层参数、外层动量与 `iter_num`，而不是复制每个节点独立训练中的全部状态。`allow_content_inequality=False` 表示这些条目要求内容相同；这也是理解示例共享范围的实际依据。

哈希采用非密码学的 SimpleHash，GPU 使用固定的并行归约方式，CPU 则模拟相同计算组织以保持一致。哈希相同是低成本一致性检查，不能当作无碰撞证明、身份认证或防止恶意节点伪造状态的机制。

### 三种同步策略

| 策略 | 语义与用途 |
| --- | --- |
| `ENFORCE_POPULAR` | 参与者按协议收敛到占优的内容；同次调用要求使用一致的策略 |
| `SEND_ONLY` | 本节点只提供状态，成功时自身内容不应被覆盖；多个发送者内容不一致会触发错误处理或剔除 |
| `RECEIVE_ONLY` | 本节点只接收，不参与决定要分发哪份内容 |

后两种策略对于延迟更新中的新节点尤其重要。如果新节点数量超过旧节点，简单采用“多数哈希”可能选择新节点尚未更新的旧内容；不能把多数表决自动等同于最新正确状态。[固定 C 接口定义](https://github.com/PrimeIntellect-ai/pccl/blob/2af926aca81353415334fbd78434a6386b43c063/include/pccl.h)

## 可中断环形归约如何恢复

### 两阶段传输

设有 $P$ 个节点，每个节点贡献一个大小为 $S$ 字节的张量。环形 all-reduce 分两阶段：

1. **Reduce-scatter。** 把张量分成约 $P$ 份，沿环传递并归约，经过 $P-1$ 轮后，每个节点持有一份完整归约后的分片。
2. **All-gather。** 各节点再传递完整分片，经过 $P-1$ 轮后，每个节点都获得完整结果。

若操作为平均，再除以本次实际参与节点数。以下通信量关系用于解释未压缩、均匀分片的环，不包括协议头和失败重传：

$$
V_{\mathrm{TX}}=V_{\mathrm{RX}}=2\frac{P-1}{P}S,
\qquad
V_{\mathrm{TX+RX}}=4\frac{P-1}{P}S.
$$

例如 $P=18$、$S=2^{30}$ 字节时，每个节点单向传约 2.028 GB，收发合计约 4.056 GB。论文表 2 的字节数与这个量级一致。（算法 5—6、§6.3）

### 故障时不能使用半成品

发送和接收并行进行，独立控制连接传来 abort 信号。若节点失联，当前操作可中断，剩余节点重新形成有效成员集合，应用按恢复规则重试；不能把部分归约结果交给优化器。

当前 `reduce.cpp` 对原地归约先备份输入，失败时恢复输入；输入输出分离时，原始发送缓冲本来没有被改写，接收缓冲可能留下不完整结果，调用者仍须根据返回状态处理。因而“恢复”不应被泛化为失败后每个用户缓冲都变回原样。

并发操作还需要逐项追踪。当前 `pcclAllReduceMultipleWithRetry` 记录已完成的操作；有操作失败时，先等待其他在途操作完成或失败，再重试未完成部分，并重新读取成员数量。它不是把已经成功且覆盖了原输入的所有张量盲目再归约一次。[归约实现](https://github.com/PrimeIntellect-ai/pccl/blob/2af926aca81353415334fbd78434a6386b43c063/ccoip/src/cpp/reduce.cpp) · [并发重试入口](https://github.com/PrimeIntellect-ai/pccl/blob/2af926aca81353415334fbd78434a6386b43c063/src/pccl.cpp)

库提供可恢复的操作，训练程序仍须在正确的位置等待、处理返回值和重试。公开文档中的简化例子不等于任何异常都已由库无限自动恢复。

### “零拷贝”的具体范围

报告的零拷贝描述是用户缓冲直接供发送路径引用，并用缓存分配器减少热路径上的分配开销。当前代码仍存在原地备份、接收缓冲、量化缓冲和必要的内存复制，不能理解成端到端从来不复制数据，也不是已经证明使用 GPU Direct RDMA。

为减少线程唤醒开销，PCCL 使用 `threadpark`，在不同操作系统上调用 futex 或同类接口。可中断性仍带来调度和同步成本，报告也承认这会增加低延迟环境中的性能波动。（§5.1—5.3）

## 量化后的共同结果仍要逐位相同

量化 $Q$ 与反量化 $D$ 通常满足：

$$
D(Q(x))\ne x.
$$

假如一个分片的拥有者保留高精度原值，而其他节点得到该分片的量化重建值，各节点就会产生不同结果。因此拥有者也必须采用其他节点能重建的相同值；广播过程中还应避免反复重新量化导致逐跳漂移。（§5.3.1）

当前实现的 all-gather 路径在拥有者首次量化后更新自身结果，后续节点转发收到的量化数据；这一处理与论文解释一致。它保证的是参与者之间的一致性目标，不是量化结果与无压缩求和完全相同，更没有自动证明训练精度不变。

论文的 WAN 主实验使用 float32，明确不量化、不压缩。当前 `async_diloco.py` 示例则配置 UINT8 与 MIN_MAX 量化。不能用示例中的压缩参数解释报告表格的带宽，也不能把通信实验当作量化训练的收敛消融。

## 从 DDP 到 DiLoCo，再到延迟一轮的更新

### 同步 DiLoCo

DDP 每个训练步平均梯度。DiLoCo 则让每个节点从共同外层参数出发，先做 $H$ 次本地更新，再把参数差作为外层伪梯度：

$$
\Delta_t^{(p)}=\theta_t^{(g)}-\theta_{t,H}^{(p)},\qquad
\bar\Delta_t=\frac{1}{P_t}\sum_{p=1}^{P_t}\Delta_t^{(p)}.
$$

外层优化器将 $\bar\Delta_t$ 应用到共同参数，再把外层参数复制回各节点内层模型。论文举例使用 AdamW 作为内层优化器、Nesterov 动量作为外层优化器；这些是用 PCCL 实现的上层算法，不是 PCCL 自己学习出的规则。（§3.1—3.2）

同步频率大约降为每 $H$ 步一次，但总训练时间还取决于本地计算、通信大小和收敛变化。论文说 $H=1$、外层 SGD 学习率 1 时可近似 DDP，并附有内层状态相近的条件；不能把它写成对所有 AdamW 状态都严格等价。

### Async DiLoCo 的隐藏通信有条件

异步示例在本轮本地训练期间继续上一轮归约，使用延迟一个外层步骤的更新。一个粗略稳态时间模型是：

$$
T_{\mathrm{sync}}\approx T_{\mathrm{compute}}+T_{\mathrm{comm}},\qquad
T_{\mathrm{overlap}}\approx\max(T_{\mathrm{compute}},T_{\mathrm{comm}}).
$$

这是忽略启动、同步和争用的说明模型。只有计算足以覆盖通信，且没有成员变更等停顿，通信等待才可能完全隐藏；网络传输、CPU 工作与带宽费用并没有消失。算法 3 仍包含等待上一轮归约的步骤，不能把论文“没有节点等待”的概括理解为任意网络条件下都不阻塞。

论文也明确说这里是一个简化异步策略，与 Streaming DiLoCo 不同。报告没有给出完整的语言模型质量—训练时间曲线，不能据此证明延迟更新在所有任务上都有相同收敛效果。

### 新节点需要两次状态同步

新节点没有参与上一轮已开始的归约。仅把当前外层参数复制给它，仍不足以在下一次延迟更新时保持一致。正确的接入次序是：

1. 检测到待接入节点，等待已有在途通信结束，再更新成员。
2. 第一次同步当前外层参数与优化器状态，新节点从同一基线开始本轮本地计算。
3. 旧节点应用上一轮结果；新节点没有这个结果，不能自行补做同样的外层步。
4. 第二次同步由旧节点使用 `SEND_ONLY`，新节点使用 `RECEIVE_ONLY`，把应用上一轮更新后的外层状态交给新节点。
5. 完成接入后，再启动下一批后台归约。

论文算法 4 在第 19 行先启动新归约，随后第 24／28 行才做第二次同步，与正文不允许同步和在途归约重叠的约束存在顺序张力。当前公开 Python 示例先完成第二次同步，再在末尾启动线程，避免了照抄该伪代码顺序。本文按正文约束和当前示例解释，未运行训练验证。[异步示例](https://github.com/PrimeIntellect-ai/pccl/blob/2af926aca81353415334fbd78434a6386b43c063/python/examples/nanogpt_diloco/async_diloco.py)

## 性能实验先区分有效吞吐与收发带宽

报告使用两种不同口径。若本节点参与了 $m$ 个并发归约，每个贡献大小为 $S_k$，全部完成耗时为 $T$：

$$
\mathrm{EffectiveThroughput}=\frac{\sum_{k=1}^{m}S_k}{T},\qquad
\mathrm{Bandwidth}=\frac{8(V_{\mathrm{TX}}+V_{\mathrm{RX}})}{T}.
$$

前者通常用 MB/s 或 GB/s，后者用 Mbit/s 或 Gbit/s。对于未压缩环形归约，收发流量约是有效输入大小的 $4(P-1)/P$ 倍，不能直接拿两个数作相同单位的比较。

### 三组单归约实验

每个节点贡献 $268,435,456$ 个 float32，即 $2^{30}$ 字节，约 1.073 GB。跨区域实验使用 Google Cloud Tier_1 网络；它们是指定云路由下的 WAN 测量，不是对任意公共互联网链路的保证。（§6.3—6.5）

## 多连接实验：工作量也随并发数增加

广域链路的高带宽、高时延会使单条 TCP 流难以填满链路，接收窗口和逐流公平调度也会影响利用率。报告用 `iperf3` 展示连接数增加时吞吐上升，包括欧洲内部、跨大西洋和 Helsinki—Dallas 路线。它检验传输现象，不是 all-reduce 本身的速度。（§6.2）

PCCL 把多个独立归约分配给连接池。并发实验每个归约为 64 MiB，并发操作数、总操作数和连接池大小一起改变。因此 128 路时每个节点的总输入为 $128\times64$ MiB，即 8 GiB；不是用 128 条连接传同一份 64 MiB 数据。

| 同上 | 64 | 4.894 ± 0.597 | 0.878 | 26.08 ± 2.948 |
| 同上 | 128 | 9.419 ± 1.753 | 0.911 | 27.57 ± 4.822 |
| 西欧，6 节点 | 8 | 1.292 ± 0.159 | 0.415 | 11.25 ± 1.398 |
| 同上 | 64 | 2.596 ± 0.233 | 1.655 | 44.47 ± 3.964 |
| 同上 | 128 | 5.066 ± 0.560 | 1.694 | 45.74 ± 5.265 |

来源为表 3、7、10。西欧从 64 到 128 路，带宽点估计只从 44.47 增至 45.74，接近平台；北美同样出现收益趋缓。更高并发并不总有更短总耗时，因为要处理的数据量也增加了。

这组实验同时改变连接与归约并发，没有固定总输入、单独扫描连接池大小的完整消融。不能把结果精确归因为仅增加 socket 数，也不能把 45.74 Gbit/s 当作单连接性能或训练吞吐。

### 表格中需要保留的记录问题

| 位置 | 问题 |
| --- | --- |
| 跨洲实验表 3 标题 | 写成“Europe West, 6 nodes”，但所在 §6.3.2 与紧接的表 4 明确为北美加欧洲 18 节点；本文按实验段落归类 |
| 欧洲实验表 11 | 节点数写 12，且档位列表漏掉表 10 的 100，与 §6.5、表 9 和表 10 的六节点设置不一致 |
| 表 3 的 8 路 TX+RX 字节数 | 报告 1.01 GB；按 18 节点、8×64 MiB 的未压缩环公式应约 2.028 GB，不能完整重算一致 |
| 表 10 的低并发字节数 | 8 路写 3.11 GB，除以 1.292 秒再乘 8 为约 19.26 Gbit/s，与该行 11.25 不符；16、32 路也有类似差异 |

均值的比值不必等于逐次比值的均值，不能仅因小幅差异就宣称实验错误。但这些较大的字节数差异及标题冲突，使原始日志和统计脚本成为完整复现的必要材料。本文保留报告结果，不自行编造修正值替换原表。

## 与 Gloo 的比较支持多大结论

局域网实验使用八台机器，单连接可达约 35.6 Gbit/s，每节点输入仍为 1.073 GB。第 18 页曲线中，PCCL 在两、三节点时较快，四至八节点时 Gloo 略高。报告将部分开销归因于可中断实现的线程调度；这里没有关闭容错后的独立消融，不能算出容错机制的净成本。

WAN 对照在相同节点上运行 Gloo，使用云内地址，不额外加客户端软件 VPN。对应单归约结果为：

| 范围 | PCCL／秒 | Gloo／秒 | 论文报告的耗时改善 |
| --- | ---: | ---: | ---: |
| 北美与欧洲 | 90.50 | 94.44 | 4.15% |
| 北美 | 35.20 | 37.58 | 6.33% |
| 西欧 | 8.30 | 9.67 | 14.17% |

改善口径是相对 Gloo 减少的时间，不是有效吞吐的同比增长率。作者认为拓扑优化有所帮助，但没有固定同一环顺序、再单独开关优化器的实验。表 13 另列的部分 Gloo 吞吐也不能用显示的输入大小和耗时完全还原，本文使用时间表，不混合推导精确加速比。（§6.6、表 12—13）

报告指出其 Gloo 配置不能利用 PCCL 的多归约并发路径，但没有提供两套库在相同总工作量、相同连接预算下的完整最优实现搜索。这些结果支持所测设置中的通信改善，不是对 NCCL、MPI 或所有 Gloo 用法的普遍替代结论。

## 容错压力测试与跨硬件一致性

### 压力测试验证应用持续推进

论文报告 Linux、macOS、Windows 的长期测试，每次约八小时，训练式循环约百毫秒一轮，随机每 500—1,000 毫秒生成或终止 peer；检查在频繁成员变化和并发归约中共享状态仍能正确推进。（§2.6.1）

当前仓库保留基础和跨步骤异步压力测试。跨步骤 orchestrator 默认八小时、最多十个 peer，并以五分钟没有新的归约完成日志作为停滞条件之一。它持续运行 master、扰动工作 peer；这不构成 master 故障切换实验。本次没有启动这些脚本，也没有把仓库存在测试解释成已独立复现所有通过记录。

报告的本机环回小模型测试给出：拓扑更新约 0.097667 ms、共享状态同步含哈希约 1.1595 ms、异步归约提交约 0.005292 ms、等待完成约 7.03225 ms。提交 API 返回很快不等于通信在五微秒内完成；这些值来自约十万参数的 MNIST 小模型，不能外推到大张量跨洲延迟。

### SimpleHash 与数学内核的实验范围

附录 A.1 在 RTX 4090 上比较 SimpleHash 与 Thrust 的 int32 归约内存带宽，16 MB 到 2,048 MB 范围内两条曲线接近，大输入约达到 900 GB/s。这是 GPU 内存读取与计算带宽，不是网络带宽，也不是哈希无碰撞率。

附录 A.2 枚举全部 $2^{32}$ 个 float 位模式，计算 `expf` 输出，再统计 NaN、Inf、有限值数量以及输出位的和与异或。报告在 GTX 980 Ti、GTX 1060、RTX 4090、GH 200、B200 上得到相同摘要，包含 16,777,214 个 NaN 输出、1,020,169,705 个 Inf 输出与 3,258,020,377 个有限输出。

这一结果提供了特定操作在受测架构上的一致性证据。和与异或摘要相同并非逐元素无碰撞证明，也不能推广到全部优化器、所有 libdevice 版本和所有 GPU 内核。附录示例打印了未在 `main` 中定义的 `total`，直接复制还需修正这一变量；本文没有运行这个覆盖四十多亿输入的 GPU 测试。

## 复现入口与当前代码边界

本次静态检查了 C 接口、归约与回退路径、master 的共享状态校验、Python 绑定、异步 DiLoCo 关键调度、压力测试 orchestrator，以及 README 和子模块记录。代码快照中的原生依赖包括 libuv、libtsp、threadpark、piquant、threadpool 和 googletest；本次读取了它们的固定 gitlink，但没有初始化全部子模块或编译执行。

源码构建要求包括 CMake 3.22.1 及以上、C++20 编译器；Python 绑定要求 Python 3.12 及以上，GPU 支持需要 CUDA 12 及以上。README 中的基本安装入口是：

```bash
pip install pypccl
```

这会选择运行时可获得的发行包，不能代替固定源代码提交。按源码复现时应记录主仓库提交、递归子模块提交、编译器、CUDA、驱动、操作系统、CPU 调度与网络设置；再按 README 构建 master、客户端与测试目标。

一个合理的验证顺序是先运行小规模本地归约，检查 SUM／AVG 与故障后的输入恢复；再验证新节点状态接入和跨步骤同步；最后才在记录好区域、连接数、张量大小的环境中测 WAN。吞吐测试应同时保存每次用时、有效输入量、TX、RX、参与成员和失败重试。没有这些分项，难以区分传输收益、工作量变化与异常重跑。

源码包含 NanoGPT、MNIST、DiLoCo 和 FSDP 相关示例，但报告没有把它们整理成一套公开训练质量主实验。异步 NanoGPT 示例会读取本地数据，还可写 checkpoint 或启用外部日志；本次没有准备数据、启动训练、申请云机器或运行网络压力测试。示例中 `optimize_topology()` 调用还被注释，不能认为直接运行它就自动复现论文的全部拓扑设置。

### 恢复保证的前提

PCCL 的控制中心仍是 master，本次所读实现与报告没有展示复制 master、领导者选举或持久化故障切换协议。工作节点可动态退出，不能据此说控制节点任意宕机也不会影响运行。

若所有工作节点都丢失，master 保存的摘要无法重建参数内容。报告 §8 说明恢复节点应从本地 checkpoint 提供此前共享状态；因此“状态不会丢失”依赖仍有可用副本或可恢复 checkpoint，而不是哈希本身保存了模型。数据加载器、随机状态、学习率调度和成员变化对训练动力学的影响，也需要上层程序管理。

这套容错面向进程、连接和成员变动，不应扩展为对恶意 peer、网络攻击、损坏 checkpoint 或任意应用代码错误的完整保护。这里列出的限制对应机制的实际覆盖范围，不影响它在受控参与者间提供动态通信恢复的用途。

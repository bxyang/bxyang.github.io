# OpenDiLoCo 精读：让不同地区的 GPU 每隔数百步再同步

加拿大和芬兰的两组 GPU 可以分别计算模型更新，但如果每一步训练都要交换大量数据，远距离网络就会让 GPU 花很多时间等待。OpenDiLoCo 采用 DiLoCo 的做法：每组设备先独立训练一段时间，再交换这一段训练造成的参数变化。论文在 1.5 亿参数模型上，每 500 步同步一次，最终验证困惑度为 13.73，与使用相近计算和数据预算的数据并行基线 13.68 接近；扩大到 11 亿参数后，改为每 125 步同步的效果更接近基线。另一次跨洲实验展示了这套流程如何在普通跨地区网络上运行。

这里需要同时看模型学得怎样、用了多少计算，以及通信等待有多长。同步次数少，并不自动意味着达到相同模型质量所需的时间或计算也同比减少。

## 本地更新与跨组同步

数据并行训练通常让多个模型副本读取不同批次的数据，计算梯度，再对梯度求平均后更新参数。各副本在每次更新后继续保持一致，相应地，每个优化步都有一次跨副本的梯度同步。

DiLoCo 把设备组织成若干 worker。一个 worker 可以是一张 GPU，也可以是一组通过高速网络连接的 GPU。组内仍可使用常规数据并行，只有 worker 之间的通信间隔被拉长。

设有 $K$ 个 worker，每组从相同参数出发，各自做 $H$ 次本地优化。由于它们读取的数据不同，中间的参数会逐渐分开。完成这 $H$ 步后，系统汇总各组的参数变化，用另一个优化器生成共同的新参数，再开始下一轮。

因此，$H=500$ 是“做 500 次本地优化后进行一次跨 worker 更新”。它不是累积 500 个梯度、保持参数不变，最后才更新一次。梯度累积可以另外用于实现较大的本地 batch，两者是不同层次的操作。（正文 §2，图 1—2）

## 两层优化如何更新参数

### 内层：在各自的数据上运行 AdamW

令 $r$ 表示外层轮次，$\theta_r$ 为该轮共同起点，$\theta_{r,j}^{(k)}$ 为第 $k$ 个 worker 完成本轮第 $j$ 次本地更新后的参数。首先令：

$$
\theta_{r,0}^{(k)}=\theta_r,\qquad k=1,\ldots,K.
$$

对本地批次 $B_{r,j}^{(k)}$，计算语言建模损失的梯度，并进行 AdamW 更新：

$$
g_{r,j}^{(k)}=\nabla_\theta\mathcal L(\theta_{r,j-1}^{(k)};B_{r,j}^{(k)}),
\qquad
\theta_{r,j}^{(k)}=\operatorname{AdamWUpdate}(\theta_{r,j-1}^{(k)},g_{r,j}^{(k)}),
\quad j=1,\ldots,H.
$$

AdamWUpdate 包含该 worker 自己的优化器状态、学习率和权重衰减。公开实现将 AdamW 的一阶、二阶动量系数设为 0.9、0.95，权重衰减为 0.1，并使用预热后的余弦学习率调度。参数会在每个本地优化步发生变化。

### 外层：平均的是参数差

本轮结束后，worker 计算伪梯度：

$$
\Delta_r^{(k)}=\theta_r-\theta_{r,H}^{(k)},
\qquad
\bar\Delta_r=\frac{1}{K}\sum_{k=1}^{K}\Delta_r^{(k)}.
$$

“伪梯度”表示它作为外层优化器的输入使用，来源却是参数相减。它不是当前一个 batch 的损失梯度，也不能一般地写成这 500 步原始梯度的直接求和：AdamW 的动量、归一化、学习率变化与权重衰减都已影响参数的移动。

随后，从本轮共同起点 $\theta_r$ 做外层更新。不能在已经走过 $H$ 步的局部终点上再减一次这个差值，否则更新起点就变了。论文图 1 与 `train_diloco_torch.py` 的顺序都是先计算差、进行 all-reduce、恢复原参数，再调用外层优化器。

外层使用带 Nesterov 动量的 SGD。按公开实现采用的 PyTorch 更新约定，在默认零 dampening、无外层权重衰减时，可展开为：

$$
v_r=\mu v_{r-1}+\bar\Delta_r,
\qquad
\theta_{r+1}=\theta_r-\eta_{\mathrm{out}}(\bar\Delta_r+\mu v_r),
$$

其中外层学习率 $\eta_{\mathrm{out}}=0.7$，动量 $\mu=0.9$，初始动量为零。公式是对代码更新流程的展开，不是论文另外提出的损失函数。（正文 §2；附录 A；固定代码中的两个训练入口）

如果把外层动量设为零、学习率设为 1，这一步才退化为各局部终点的直接平均。论文实际配置包含跨轮次动量，因此不能把整个方法简写成“每 500 步平均权重”。

用一个自拟的单参数例子说明：共同起点是 10，两个 worker 的局部终点分别为 9 和 7，则伪梯度为 1 和 3，平均为 2。无动量、学习率为 1 时得到 8；使用论文配置且为第一次外层更新时，动量为 2，结果为 $10-0.7(2+0.9\times2)=7.34$。这个例子只解释更新约定，不是论文实验。

### 保存副本与混合精度

计算参数差需要保留当前模型和本轮开始时的参数。实现可将外层参数及优化器状态放在 CPU 上，减少它们常驻 GPU 的需求，但相应内存和设备间复制仍然存在。

对于 FP16 内层训练，梯度缩放作用于反向传播产生的梯度，解除缩放后再做本地更新。手工相减形成的伪梯度不应再套用一次同样的缩放流程。论文特别区分内层 `scaler.step` 与外层直接 `step`；是否把通信张量压缩成 FP16，又是另一个配置。（正文 §2）

## PyTorch 与 Hivemind 的两种实现

| 实现 | 负责的工作 | 论文讨论的边界 |
| --- | --- | --- |
| `torch.distributed` + NCCL | 展示双优化器、参数差与 all-reduce 基本流程 | 需定制训练循环；论文指出该实现不能直接处理跨 NAT 的互联网通信 |
| Hivemind | 通过分布式哈希表发现与协调 peer，执行跨 worker 聚合 | 面向连接较弱、可能加入或退出的设备；仍有同步与等待开销 |
| worker 内的 FSDP | 管理组内训练及高速 GPU 通信 | 与组间 Hivemind 通信分工；具体分片策略取决于实验配置 |

分布式哈希表 DHT 主要协调节点信息。没有中央参数服务器，并不等于启动时不需要可达的初始 peer，也不等于模型张量被当作 DHT 条目存储。

论文描述 Hivemind 可支持设备加入、离开及故障恢复，但没有另给一组故障频率、恢复时间和质量影响的实验。跨洲主实验使用四组设备，不足以直接证明数百个不稳定节点在任意加入、退出情况下仍能保持同样的吞吐与收敛。（正文 §2—§3）

规模扩展实验还有一个具体限制：基线使用 FSDP hybrid sharding；DiLoCo 路径为避开 Hivemind 状态聚合器与 Sharded DTensor 的兼容问题，采用 `NO_SHARD`。虽然框架接入了 FSDP，不能据此说该实验已经验证了每个 worker 内完整的参数分片。

### C4 与实际 token 口径

论文使用 C4 做语言建模，没有新建专家标注数据集。所检查代码加载 `allenai/c4` 英文配置，使用 `mistralai/Mistral-7B-v0.1` tokenizer，以 causal language modeling 方式训练；各 worker 再按 rank 划分数据流。

当前 FSDP 入口把每条文本截断或补齐到 1,024 个位置，并非把多条短文连续打包成没有空位的序列。padding 标签会被数据整理器屏蔽。因此，“batch × 1,024”表示名义 token 位置数，不等于实际参与损失计算的非 padding token 数。

按名义位置数计算，150M 的八 worker 主实验总预算为：

$$
88{,}000\times8\times512\times1{,}024
=369{,}098{,}752{,}000.
$$

1.1B 的四 worker 实验则为：

$$
44{,}000\times4\times2{,}048\times1{,}024
=369{,}098{,}752{,}000.
$$

两者都是约 369.1B 个名义位置，但模型大小不同，计算量不能因此视为相同。这也不证明读取了这么多个唯一 token。原文没有给出精确的非 padding token 总数、逐条采样清单或额外的污染审计。

## 150M：最终质量接近，前期收敛较慢

表 1 的指标是验证困惑度，越低越好。它与平均负对数似然损失的关系为 $\mathrm{PPL}=\exp(\mathcal L)$；不是准确率，也没有百分比单位。

| 训练配置 | 相对计算与数据量 | 跨副本同步间隔 | 最终验证困惑度 |
| --- | ---: | ---: | ---: |
| 无额外副本的基线 | 1× | 无跨副本同步 | 16.17 |
| batch 放大 8 倍的数据并行基线 | 8× | 每步 | 13.68 |
| 八 worker DiLoCo | 8× | 每 500 步 | 13.73 |

DiLoCo 比弱基线低 2.44，但同时使用了八倍的数据与计算预算，不能把这一下降解释为相同计算量下的算法增益。真正用来比较质量与通信交换的是后两行：13.73 比 13.68 高 0.05，论文称两者在训练结束时接近。（正文 §3，图 3，表 1）

图 3 也显示，DiLoCo 不是从训练一开始就与强基线重合。它在前期落后，到 88,000 步左右才接近。论文没有给出多随机种子重复的误差条或等价性检验，所以“接近”是这组结果的描述，不是统计上已经证明完全相同。

表 1 把时间统一写为 1×，却没有提供完整端到端耗时测量来证明不同网络、硬件布局下实际墙钟时间一样。它主要用于等训练步数和相对预算比较，不宜进一步改写为“相同 GPU 小时”或“训练费用相同”。

### worker 数量消融需要换两个横轴看

图 4 比较 1、2、4、8 个 DiLoCo worker。这里把本地同步间隔改为 50 步，与主实验的 500 步不同；由于预算限制，这组实验没有全部延长到 88,000 步。

按每个 worker 的本地步数比较，更多 worker 对应更低的困惑度。但同样走一步，八个 worker 就处理八组 batch，总计算也更多。

图 5 将横轴改成全体 worker 累计的步数，近似对应 $K\times N$，才更接近等计算量比较。换成这个口径后，多 worker 在前期没有表现出同样的计算效率优势。增加 worker 可以改善较长训练后的结果，但未必缩短达到某个早期质量水平所需的总计算。

消融没有给出超过八个 worker 的曲线，也没有对每个 worker 数重新进行完整超参数搜索。不能从它直接推断到数百组设备的收敛表现。（图 4—5，正文 Practical Usage）

## 1.1B：同步间隔与本地 batch 一起影响结果

扩大到 1.1B 时，作者使用四个 worker，每个本地 batch 为 2,048。强基线的全局 batch 为 8,192，与四组本地 batch 总量相同。基线使用两个同地节点、每节点八张 H100；DiLoCo 使用四个节点、每节点八张 H100，硬件数量并不相同。（正文 §3）

| 训练配置 | 相对计算与数据量 | 同步间隔 $H$ | 最终验证困惑度 |
| --- | ---: | ---: | ---: |
| 无额外副本的基线 | 1× | — | 11.85 |
| batch 放大 4 倍的数据并行基线 | 4× | 1 | 10.52 |
| 四 worker DiLoCo | 4× | 125 | 10.76 |
| 四 worker DiLoCo | 4× | 500 | 11.14 |

125 步同步比 500 步同步低 0.38，距离强基线仍有 0.24。“接近基线”适用于这个差距，不能把 10.76 写成已超过 10.52。（图 7，表 2）

作者用两次同步之间处理的数据量解释这一现象。150M 主实验每个 worker 每轮处理：

$$
500\times512\times1{,}024=262{,}144{,}000
$$

个名义 token 位置。1.1B 若仍采用 500 步，数量扩大四倍；改为 125 步时，恰好回到同样的 262,144,000 个位置。保持相同的本地步数，并没有保持相同的“同步之间读了多少数据”。

图 7 支持在这组配置中缩短间隔有助于收敛。它没有独立控制模型大小、batch、同步间隔及总步数的所有组合，所以“同步间读入更多数据导致前期落后”仍是作者的解释。关于把 500 步实验继续训练到 88,000 步可能追上的说法，也没有已完成曲线来验证。

表 2 的通信列还有一处口径问题：两条四 worker DiLoCo 行写成 $8N/H$，而同表基线写 $4N$。正文和图注使用四个 worker，并将减少倍数写为 $H$。本文保留原始困惑度结果，通信分析按明确的同步频率展开，不利用这个未解释的系数去反推实测网络字节数。

## 通信频率、张量精度与实际耗时

### 500 倍指同步次数

若做 $N$ 次本地优化，数据并行每步同步，DiLoCo 每 $H$ 步同步，忽略尾部不完整轮次时，两者分别约为 $N$ 次和 $N/H$ 次。150M 主实验对应：

$$
88{,}000/500=176
$$

轮外层同步，而不是 88,000 轮。它减少频繁的跨 worker 聚合，worker 内部的 GPU 通信仍然存在。

真实流量还依赖参数数量、张量精度、聚合拓扑、协议开销、状态同步及故障重试。原文的通信次数比较没有囊括这些因素，不能直接当作端到端加速比。

### FP16 消融只改变聚合精度

图 6 比较 FP32 和 FP16 伪梯度聚合，分别在“四 worker、50 本地步”和“八 worker、500 本地步”下观察训练损失。约前 10,000 步的曲线没有明显差别。

FP16 每个元素占两个字节，FP32 占四个字节，同样数量元素的张量载荷可以减半。这为减少通信开销提供依据，但图 6 画的是损失，没有给出每轮通信秒数减半的计时实验，也没有证明所有模型规模或更低位宽压缩都保持相同效果。（正文 §3，图 6）

## 四组 H100 的跨洲实验

部署使用四个 worker，总计 32 张 H100：

| 地点 | 服务商 | GPU 数 |
| --- | --- | ---: |
| 加拿大 | Hyperstack | 8 |
| 芬兰 | DataCrunch | 8 |
| 美国得克萨斯州 | Voltage Park | 8 |
| 美国特拉华州 | Runpod | 8 |

训练使用 1.1B 模型、每 500 个本地步同步一次，伪梯度按 FP16 聚合。带宽用 iperf 测量，是节点之间的双向平均带宽。正文写为 127—935 Mbit/s，但图 8 的一条连线标为 117；两者不完全一致，不能据正文把最慢链路精确确定为 127 Mbit/s。（正文 §3，图 8）

每组设备独立计算约 67.5 分钟，一次 all-reduce 平均用时 300 秒，即 5 分钟。仅按这两段时间计算，通信占比为：

$$
\frac{300}{67.5\times60+300}\approx6.9\%.
$$

这对应论文所报通信等待占比。只计算这两部分，本地计算时间占约 93.1%；作者另外报告整体约 90%—95% 的 compute utilization。

这里没有给出以 H100 理论 FLOPs 为分母的 MFU 测量，也没有完整披露利用率采样方法。这个结果应放在计算与通信时间分配的上下文里，不能解释成达到了 H100 峰值算力的 90%—95%。

即使 GPU 型号一致，CPU 核数、内存等机器配置也不同，各组完成 500 步的时间不完全一致。最快的 worker 要等较慢的 worker，这种空闲时间不包含在单纯的 all-reduce 耗时里。作者将异步重叠通信与下一轮计算列为后续方向，本次实验没有验证这种异步方案。

## 公开代码与复现细节

本次完整读取参考训练循环、FSDP 入口和 Hivemind 优化器，另核对模型配置、压缩参数、启动脚本及部分测试。**以下根据固定提交的公开代码整理，尚未运行 GPU 训练，也没有复现论文困惑度或网络计时。**

### 环境与入口

仓库使用 Apache 2.0 许可。依赖包括固定为 2.3.1 的 PyTorch、约束为 `~=4.40` 的 Transformers，以及提交固定到 `213bff9` 的 Hivemind；其他依赖仍含最低版本约束。README 还使用 nightly torchdata 和 `main` Docker 标签，仅固定仓库提交并未冻结整个环境。

`train_diloco_torch.py` 展示基础 NCCL 路径，`train_fsdp.py` 接入 Hivemind。`run_training.sh` 实际前三个位置参数依次是 worker 数、每 worker 的 GPU 数和初始 peer 地址，它在一台机器上启动多组进程。跨机器实验则需为各组分配不同的 `hv.world_rank`，保持共同的数据划分及通信配置。

Hivemind 路径的 `total_batch_size` 是单个 worker 全部 GPU 合计的 batch。例如 2,048、八张 GPU、每 GPU 微批次 16，对应每次本地优化累积 16 个微批次。四个 worker 合计才是 8,192；不要再将每个 worker 设为 8,192，否则总数据量会扩大四倍。

### 默认命令不等于论文实验

1. **步数上限。** 当前 `train_fsdp.py` 的 `total_steps` 用于学习率调度，显式退出条件读取 `max_steps`。只传 `--total-steps 44000` 不能保证第 44,000 步自动结束。参考 NCCL 入口也不能仅凭调度参数假定循环会在该步退出。
2. **1.1B 训练长度。** README 的两组示例仍写 88,000 步，表 2 报告 44,000 步。125 步示例还同时留下 500 和 125 两个同名参数；准备命令时应只保留明确的实验值。
3. **聚合精度。** Hivemind 默认不压缩。内层使用 `bf16-mixed` 不会自动把跨 worker 张量变成 FP16，需另核对 `hv.hivemind_compression`。
4. **数据与模型版本。** 模型、tokenizer、C4 加载路径没有自动固定 Hugging Face revision。重跑应记录快照与数据清单，不仅是模型名称。

这些是当前代码与论文配置的对照，不表示已追溯到原始实验所用提交，也不能据此断言历史训练采用了错误参数。

### 验证困惑度与训练日志分开

当前 FSDP 入口记录的 `Perplexity` 是训练 batch 损失的指数，本次未在该入口看到完整验证集评估循环。参考 NCCL 脚本有独立评估函数，只加载 C4 验证集八个文件中的第一个，并对评估 batch 的损失取平均后取指数。

后者按 batch 平均，不是显式汇总所有有效 token 的负对数似然后再除以 token 总数。短文本和 padding 可能影响两种口径是否一致。论文表 1—2 写的是验证困惑度，但正文没有给出足以把这些默认路径与最终表格逐项对应的全部设置。

要重现 13.73 或 10.76，应固定验证文件、截断与 padding、batch、有效标签计数、评估检查点，并保存原始损失。不能把同名的训练 `Perplexity` 日志直接当作表中结果。

### 节点变化也会改变统计

当前优化器支持等待所有 peer 和不等待慢 peer 的策略。等待模式有超时条件；训练入口也支持选择在 worker 数下降时直接报错。这些配置决定故障后如何继续，不能只凭“容错”一词推断统一行为。

FSDP 入口的 `effective_step` 和 `total_samples` 用固定 `galaxy_size` 计算，代码注释明确指出这一统计不适应节点动态加入、退出。弹性训练需要按实际参与记录重算数据量，而非继续将每一步乘以初始 worker 数。

代码中的本地小模型测试不能替代跨洲布局、完整训练曲线和故障恢复验证。本次读取的快照中，也未找到可直接逐图重建论文全部曲线的独立结果表及绘图分析包。

## 结果覆盖的范围

OpenDiLoCo 验证了两档模型、有限 worker 数量下的低频同步训练，并给出一次四组同型号 GPU 的跨地区实现。模型质量依据 C4 困惑度，没有额外报告通用知识、代码、推理或指令遵循能力。1.1B 相比前作 400M 约为 2.75 倍，论文使用“约三倍”的表述；这仍不能替代更大模型的实验。

通信间隔越长，网络等待可以越少，但各组参数分开演化的时间也越长。本文观察到的结果是：150M 的 500 步间隔在较长训练后接近强基线；1.1B 的 125 步间隔优于 500 步；跨洲运行中的同步和慢节点等待仍然存在。如何同时保持更大规模、较少通信与良好的计算效率，原文留作后续研究。

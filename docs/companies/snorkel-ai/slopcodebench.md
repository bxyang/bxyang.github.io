# SlopCodeBench：观察代码在连续需求扩展中的变化

原文：[SlopCodeBench: Benchmarking How Coding Agents Degrade Over Long-Horizon Iterative Tasks](https://arxiv.org/abs/2603.24755v2)，本文依据 2026 年 5 月 7 日的 v2。

## 1. 摘要翻译

以下依据 [arXiv 的 CC BY 4.0 版本](https://arxiv.org/abs/2603.24755v2)翻译。

软件开发是一个迭代过程，但智能体编程基准的一次性任务设置掩盖了设计问题。近期的迭代式基准试图弥补这一点，却严格限制了智能体的设计决策空间，使我们无法如实衡量这些决策如何影响后续扩展。

我们提出 SlopCodeBench，一个包含 36 个问题和 196 个检查点的基准，智能体需要不断扩展自己此前的解决方案。与以往迭代式基准不同，我们不断演化的需求要求智能体作出架构决策，但把内部结构留给智能体决定。

我们衡量两种退化：结构侵蚀，即复杂度集中；以及冗长，即代码冗余。通过评估涵盖开放与闭源模型的 15 个编程智能体，我们发现，没有一个智能体能够从头到尾完整解决任何一个问题，最好的智能体通过了 14.8% 的检查点。

代码质量随着检查点推进而下降，77% 的轨迹出现结构侵蚀增加，75.5% 出现冗长增加。与 473 个开源 Python 仓库相比，智能体代码的冗长程度为其 2.3 倍，结构侵蚀程度为其 2.0 倍；人工开发仓库在 Git 历史中的退化出现得更少，幅度也更小。

明确的质量指导能把初始冗长和结构侵蚀最多降低三分之一，但没有改变退化速度。SlopCodeBench 首次测量了迭代扩展中的代码退化，揭示出智能体可以通过检查点，却同时生成每轮都更加侵蚀和膨胀的代码。

## 2. 研究背景与相关研究

程序最初满足需求，并不意味着容易扩展。一个用正则表达式搜索代码的小工具，后来可能需要支持多种语言、语法结构和自动修复。早期把逻辑写死在一个函数里，会影响之后每一次修改。

论文的 Introduction 和 Related Work 区分三类研究。一次性编程基准主要检查当前需求下的正确性；迭代式基准开始加入连续修改，但一些会重置工作区、限定内部接口，或主要检查最终通过率；代码质量研究则分析重复、过多分支等问题，但未必跟踪这些问题如何随同一个程序的多次扩展而累积。

SlopCodeBench 把智能体自己生成的代码持续保留下来，让早期设计成为后续修改的基础。它不规定内部函数或类的结构，因而能够观察智能体如何在新的需求下继续使用、重构或修补此前的设计。（原文 §1、§4）

## 3. 核心贡献

**核心问题。** 在需求不断扩展的过程中，智能体能否保持功能正确，并避免重复代码和过度集中的复杂度持续增加。

**核心方案。** 研究者手工构建 36 个问题，共 196 个检查点。智能体从空目录开始，每轮获得新的需求和此前的代码，但不继承上一轮对话，也看不到隐藏测试。需求只约束命令行或 API 的外部行为，内部组织方式由智能体决定。后续评分同时检查新功能与此前功能，保留完整开发过程的依赖关系。

作者另外定义两个静态质量指标：结构侵蚀衡量复杂度有多少集中在高复杂度函数中，冗长衡量规则识别的冗余和重复代码所占比例。它们与功能测试分别计算。研究还以开源 Python 仓库的历史作为参照，并比较直接实现、先规划和明确避免冗余等提示方式。（原文 §2–3）

**结论。** 在本次 Python 评测中，最佳配置严格通过 14.8% 的检查点，没有配置让任何一个问题的所有检查点全部通过。这个比例要求某个检查点的全部测试成功，不能理解为只实现了 14.8% 的功能。多数轨迹同时出现复杂度集中或冗余增加，说明单独报告功能分数会漏掉代码结构的变化。

质量提示能降低一些配置的冗余和结构侵蚀，但整体上未消除后续退化，并伴随成本或正确性的取舍。开源仓库对比给出了量级参照，却不是让人和智能体完成同一组需求的随机对照；两项静态指标也没有直接测量实际维护工时。论文支持的结论是，在这批连续扩展任务与所测模型中，功能通过与代码结构质量需要同时观察。（原文 §3–5）

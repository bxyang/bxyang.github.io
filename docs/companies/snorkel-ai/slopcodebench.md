# SlopCodeBench 精读：代码在连续需求扩展中怎样变化

一个代码搜索器起初只需要匹配 Python 文件里的字符串，之后要支持更多语言、语法树模式和自动修改。SlopCodeBench 让编程 agent 从空目录开始完成这类任务，再连续修改自己写出的代码。它同时记录功能是否正确，以及复杂度和冗余怎样积累。论文评测了 36 个问题、196 个检查点和 15 个模型：最好的配置严格通过 14.8% 的检查点，没有配置完整通过某个问题的全部检查点。这里的 14.8% 是整套测试全部通过的检查点比例，不能理解成只实现了 14.8% 的功能。[论文 §2–3、表 1](https://arxiv.org/pdf/2603.24755v2)

## 1. 让早期实现一直留在后续任务中

许多编程评测给出一个现成仓库或一次完整需求，再检查最后补丁是否正确。SlopCodeBench 把一个问题拆成按顺序到来的需求扩展。后面的任务接着修改前面产出的代码，评测器不会用参考实现替换工作区。

设第 $i$ 个检查点的规格为 $x_i$，修改后的工作区为 $y_i$，agent 为 $\pi_\theta$，则过程是：

$$
y_i=\pi_\theta(x_i,y_{i-1}),\qquad y_0=\text{空工作区}.
$$

这里没有训练目标；$\theta$ 表示被评测模型的参数。每个检查点只保留代码工作区，不传递此前的对话历史。agent 必须从现有代码理解已有设计，再实现新规格。测试结果和质量分在外部计算，不反馈给 agent。[论文公式 1、§2.1–2.4](https://arxiv.org/pdf/2603.24755v2)

论文反复使用 `code_search` 说明需求如何变化：

| 检查点 | 新增要求 | 实现需要处理的变化 |
| --- | --- | --- |
| C1 | Python 文件中的精确字符串和正则匹配 | 文件遍历、规则解析、坐标和 JSON Lines 输出 |
| C2 | 增加 JavaScript、C++ 与按语言过滤规则 | 语言扩展和规则适用范围 |
| C3 | 基于语法结构匹配，支持元变量捕获 | 从文本匹配扩展到代码结构表示 |
| C4 | 选择器和自动修复 | 匹配位置、修改冲突与输出处理 |
| C5 | 增加 Go、Rust、Java | 继续扩展语言支持 |

C1 只约束外部命令行和输入输出，不指定函数名、模块边界或内部类结构。C3 中同名元变量的多次出现必须匹配相同文本，输出还要给出捕获范围。这样，第一次采用怎样的规则表示，会影响后续是否需要修改大量已有逻辑。[论文 §2 的示例、附录 A.1](https://arxiv.org/pdf/2603.24755v2)

图 1 中正确率由 1.00 下降到 0.10 的流程图是方法示意，不能当成某个模型的完整测量结果。实测代码案例在附录 B：Opus 4.7 的 `forge/main()` 从第一个检查点的 38 行、圈复杂度 13，发展到第八个检查点的 240 行、圈复杂度 92；原先调用 `argparse` 的部分被手工参数解析分支替代，七个参数重复处理两种写法。[论文图 1、附录 B.2、Listing 6–7](https://arxiv.org/pdf/2603.24755v2)

## 2. 任务、测试与难度是怎样形成的

36 个问题共有 196 个检查点，每题 3–8 个。覆盖配置系统、数据库迁移、文件处理、查询语言、开发工具、HTTP 服务、任务执行和游戏内规划等。比如 `database_migration` 有 5 个检查点，逐步涉及操作表示、回滚、依赖排序和约束；`circuit_eval` 有 8 个，涉及中间表示、多格式解析、三值逻辑和等价性检查。[论文表 4–5](https://arxiv.org/pdf/2603.24755v2)

问题由论文作者手工编写，可以是新任务，也可以借鉴已有开源项目。构建分两轮：先提出任务和检查点，剔除不能有效考察设计选择、或前沿 agent 能一次解决的问题；再编写测试，用 agent 尝试检查点，修正规格歧义和测试不足。每题至少经过一位非原起草作者复核，最终检查规格与测试是否一致、任务原则上是否可解。[论文 §2.2](https://arxiv.org/pdf/2603.24755v2)

这是一套有意筛选出的困难开发任务，不是从真实工作任务中随机抽样。论文未报告每题完整人类开发轨迹、人工完成时间或人类严格通过率，因此后面的开源仓库对照不能充当“人类也做了这 36 题”的对照实验。

测试通过子进程或服务 API 调用程序，不导入 agent 的内部函数。规格附有样例，隐藏测试覆盖更多输入；在需要的地方规范排序、大小写和格式，减少无关输出差异。论文将测试分为四类：

- **Core**：规格明确描述或展示的核心行为。
- **Error**：错误输入和失败处理。
- **Functionality**：更全面的隐藏功能测试。
- **Regression**：重跑前面检查点的测试，C1 没有这一类。

测试对受测 agent 隐藏，不等于研究者拿不到测试。当前公开题库包含规格、测试以及参考实现相关目录；运行时需要继续隔离这些评测文件。论文没有给出训练数据污染率的实测结果，也没有证明模型从未见过所借鉴项目的相关内容。[论文 §2.1、§2.4；固定版本题库](https://github.com/gabeorlanski/scb-problems/tree/ef6a9dd13911566b6b01075ca121758c9f7b5c5f)

## 3. 三种通过率的区别

对检查点 $c$，记当轮测试集为 $T_c$，其中回归测试为 $R_c$、核心测试为 $K_c$。用 $\mathbf{1}[\cdot]$ 表示条件满足取 1，否则取 0，可以将论文的判定规则写成：

$$
\begin{aligned}
S_c&=\mathbf{1}[T_c\text{ 全部通过}],\\
I_c&=\mathbf{1}[T_c\setminus R_c\text{ 全部通过}],\\
C_c&=\mathbf{1}[K_c\text{ 全部通过}].
\end{aligned}
$$

表里的 Strict、ISO 和 Core 分别汇总这些二值结果，分母固定为 196。它们都不是“所有测试用例中通过了多少”的测试级通过率。以下公式是对 §2.4 的整理：

$$
\text{Strict}=\frac{100}{196}\sum_c S_c,\quad
\text{ISO}=\frac{100}{196}\sum_c I_c,\quad
\text{Core}=\frac{100}{196}\sum_c C_c.
$$

**说明示例**：一个检查点核心测试全过，但隐藏错误处理失败，那么 Core 可以记 1，ISO 和 Strict 都记 0。如果当轮所有新测试通过，却破坏了旧功能，ISO 记 1、Strict 记 0。之前失败也不是永久锁死后续分数：后续工作区若修好了错误并通过全部回归测试，仍然可以严格通过。[论文 §2.4、表 1 表注](https://arxiv.org/pdf/2603.24755v2)

Partial 的分母则是 **36 个问题**：至少有一个检查点严格通过，就算这个问题部分解决。因此 GPT 5.5 的 Partial 50.0% 指 18 个问题至少过了一关，不是完整解决了一半问题。

agent 崩溃或中止导致后续检查点缺失时，正确性计零；质量指标只在实际生成工作区的检查点上计算，缺失工作区不会被补成零质量。两类指标的样本集合不同，分析均值时需要保留这个区别。[论文 §2.4、表 1](https://arxiv.org/pdf/2603.24755v2)

## 4. 结构侵蚀：复杂度集中在多少大函数中

论文把圈复杂度记为 $CC(f)$，源代码行数记为 $SLOC(f)$，为每个可调用单元定义复杂度质量：

$$
\operatorname{mass}(f)=CC(f)\sqrt{SLOC(f)}.
$$

圈复杂度概括控制流的独立路径数量；平方根缩小函数长度的影响，避免分数只随行数线性增长。结构侵蚀分为：

$$
E=\frac{\sum_{f\in F}\mathbf{1}[CC(f)>10]\operatorname{mass}(f)}
{\sum_{f\in F}\operatorname{mass}(f)}.
$$

$F$ 是所有被统计的可调用单元。分数在 0–1 之间，越高表示更多复杂度质量位于圈复杂度 **严格大于 10** 的函数里。它不是代码错误概率，也不直接等于维护工时。[论文公式 2–3](https://arxiv.org/pdf/2603.24755v2)

**说明示例**：三个函数的 $(CC,SLOC)$ 分别是 $(20,100)$、$(4,25)$、$(4,25)$，对应质量为 200、20、20，侵蚀分为 $200/240\approx0.833$。一个函数即使有 100 行，只要圈复杂度恰好为 10，也不进入分子。分数因此对阈值两侧的变化敏感。

实际检查的代码 `compute_mass_metrics` 只统计 `function` 和 `method`，跳过非正 SLOC，分母为零时返回 0。本次用原函数运行上述小例，得到总质量 240、侵蚀比例 0.833333，并确认 CC=10 时高复杂度比例为 0。这仅核验公式实现，不是重新运行论文实验。[固定版本 mass.py](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/src/slop_code/metrics/checkpoint/mass.py)

## 5. 冗余分：规则标记行与重复代码的并集

第二个指标测量冗余。论文构建 137 条 AST-grep 规则，检查重复包装、冗长控制结构等代码模式；再识别结构性重复代码。设 $A$ 是规则标记的行，$D$ 是重复代码行：

$$
V=\frac{|A\cup D|}{LOC}.
$$

同一行即使命中多条规则、同时也是重复行，只能计一次。分数在 0–1 之间，越低越少命中这些模式。**说明示例**：100 行代码中有 20 行规则命中、30 行重复，其中 10 行重叠，那么冗余分为 $(20+30-10)/100=0.40$，不是 0.50。[论文公式 4、§2.3](https://arxiv.org/pdf/2603.24755v2)

这一指标是静态模式检测结果。它不证明每一行都可以无损删除，也不判断重复是否出于兼容性或部署隔离的需要。结构侵蚀与冗余分别度量不同现象，但“分别度量”也不意味着已经证明两者统计独立。论文不把两个分数合成一个通用软件质量分。

当前代码把最终 `verbosity` 和 `erosion` 读取交给固定的 **`scb-check==0.1.3`**，还记录检查器版本、重复覆盖行数和规则覆盖行数。这个实现快照晚于论文，不能只固定 agent、忽略质量检查器版本，就期待复现 v2 的所有分数。[固定版本 driver.py](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/src/slop_code/metrics/checkpoint/driver.py)

## 6. 模型、执行环境和预算

每个检查点在新的 Docker 容器内以非 root 用户运行，只保留工作目录；已安装的软件包、shell 历史和 agent 会话状态重置。运行环境准备共同工具集：只有某个命令缺失会造成所有 harness 失败时，才用它修正共同基线，避免专门照顾单个 agent。题目设计允许不同编程语言，论文为控制成本只评测 Python 实现。[论文 §3、附录 C.1](https://arxiv.org/pdf/2603.24755v2)

论文直接调用模型对应的 CLI harness，没有把所有模型塞进一个完全相同的代理循环。因此结果对应 **模型、harness、版本与提示的组合**。表 1 为每个模型选择表现最好的 `just-solve` 配置，按 ISO 优先，再按 Core、Strict 和成本处理排序。全配置结果在表 8。

## 7. 正确性与代码变化的主要结果

下面摘录表 1。前三列是检查点通过比例，侵蚀和冗余是 0–1 分数；成本是每个实际运行检查点的平均美元费用。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPT 5.5 | 14.8 | 28.1 | 66.8 | 0.49 | 0.32 | 1.51 |
| GPT 5.3 Codex | 11.2 | 26.0 | 60.7 | 0.64 | 0.46 | 0.66 |
| GPT 5.4 | 10.7 | 23.5 | 62.8 | 0.51 | 0.33 | 0.72 |
| Opus 4.6 | 9.7 | 20.9 | 67.3 | 0.75 | 0.44 | 3.17 |

| Composer 2 | 6.1 | 16.3 | 52.6 | 0.72 | 0.45 | 0.44 |
| MiniMax M2.7 | 2.0 | 4.1 | 28.1 | 0.73 | 0.47 | 0.34 |

GPT 5.5 的 Strict 14.8% 对应约 29/196 个检查点；ISO 28.1% 对应约 55/196。两者相差 13.3 个百分点，说明不少检查点能满足新增要求，却没有同时通过旧功能回归测试。最高 Core 是表 1 的 **Opus 4.6，67.3%**；正文 §3.1 写成 Opus 4.5，与表格不符，这里采用表格归属。[论文表 1、§3.1](https://arxiv.org/pdf/2603.24755v2)

为比较长短不同的问题，作者把轨迹映射成 Start、Early、Mid、Late、Final 五个阶段：首尾固定，中间检查点分入三组。跨题聚合后的 Core 检查点通过率由 64.6% 降至 35.5%；平均每检查点成本增长约 2.2 倍。相对修改行数从早期 97.4% 下降至后期 29.5%。这里的阶段均值不是“某一个固定第 5 轮”的成绩。[论文 §3、图 2](https://arxiv.org/pdf/2603.24755v2)

质量变化方面，77% 的轨迹侵蚀上升，75.5% 的轨迹冗余上升。平均最大圈复杂度由 27.5 增至 69.0；结构重复增长 96%，AST-grep 规则命中密度只增长 0.3%。这组观察表明，按本文检测器的定义，后续冗余积累更多表现为既有结构的重复，而非大量新的规则违规类型。[论文 §3.2、图 3](https://arxiv.org/pdf/2603.24755v2)

这些是连续扩展过程中观测到的关联。论文没有随机分配两种早期架构、控制其余条件完全相同再比较，因此不能单凭这些曲线，把通过率下降全部归因于某一种设计决策；新增需求本身也更复杂。

## 8. 开源仓库对照的含义

作者收集 473 个持续维护的 Python 仓库，覆盖 Web、科学计算、基础设施、机器学习和工具类项目。按 GitHub 星标分层，每个仓库最多抽取 30 个修改源代码的提交，共 13,667 个时间点。空源代码树或指标计算失败的时间点排除；最近一个采样提交用于横截面对照。[论文 §3.3、附录 D.1](https://arxiv.org/pdf/2603.24755v2)

| 对照组 | 样本量 | 冗余均值 | 侵蚀均值 |
| --- | ---: | ---: | ---: |
| 低于 100 星仓库 | 114 | 0.21 | 0.33 |
| 100–1,000 星仓库 | 124 | 0.19 | 0.32 |
| 1,000–10,000 星仓库 | 120 | 0.18 | 0.33 |
| 至少 10,000 星仓库 | 115 | 0.19 | 0.37 |
| 全部仓库最近采样点 | 473 | 0.19 | 0.34 |
| agent 工作区检查点 | 2,869 | 0.44 | 0.68 |

因此论文所说的 2.3 倍冗余和 2.0 倍侵蚀，是这两个样本集合的均值比，不是同一个开发任务里 agent 比人类多写了多少行。agent 一侧汇总多个检查点，仓库横截面一侧每仓库一个最近采样点。[论文表 2](https://arxiv.org/pdf/2603.24755v2)

轨迹斜率方面，agent 冗余平均每检查点增加 0.0144，开源仓库侧报告的中位数是 0.0022；侵蚀分别为 0.0264、0.0053。比值约为 6.5 和 5.0，但一个代码需求检查点与一个历史提交并不具有相同工作量，不能把比值理解为日历时间上的维护退化速度。[论文 §3.3、附录 D.1](https://arxiv.org/pdf/2603.24755v2)

作者还检查 2024 年 1 月前后都有至少三个采样点的 321 个仓库：仓库内冗余变化中位数为 +0.002、侵蚀为 +0.014。这些仓库未逐提交标注是否使用 AI，时间划分只能提供背景对照，不能证明变化由 AI 辅助造成。

附录 D.1 有一处数字与文字不一致：它列出 FastAPI 冗余 0.273，却说 FastAPI 和 Transformers 都超过 agent 冗余均值；表 2 的 agent 均值是 0.44，0.273 实际低于它。本文不沿用这个“二者都高于均值”的判断。[论文附录 D.1、第 26 页](https://arxiv.org/pdf/2603.24755v2)

## 9. 提示干预与指标敏感性

### 显式要求代码整洁

`anti-slop` 提示要求减少过度防御、一次性变量、浅层包装、深层嵌套和长分支链等。`plan-first` 除代码风格要求外，还要求先制定计划、实现简单方案、检查边界条件并重构。它们是成组的提示修改，不能把效果单独归因于“先写计划”这一个动作。[论文附录 C.3–C.5](https://arxiv.org/pdf/2603.24755v2)

表 3 的主要结果如下：

| 模型/提示 | Strict % | ISO % | Core % | 侵蚀 ↓ | 冗余 ↓ | 美元/检查点 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GPT 5.3 Codex / 基线 | 11.2 | 26.0 | 60.7 | 0.64 | 0.46 | 0.66 |
| GPT 5.3 Codex / anti-slop | 11.2 | 23.5 | 57.1 | 0.42 | 0.31 | 0.73 |
| GPT 5.4 / 基线 | 10.7 | 23.5 | 62.8 | 0.51 | 0.33 | 0.72 |
| GPT 5.4 / anti-slop | 9.2 | 25.5 | 61.2 | 0.28 | 0.24 | 0.90 |
| GPT 5.5 / 基线 | 14.8 | 28.1 | 66.8 | 0.49 | 0.32 | 1.51 |
| GPT 5.5 / anti-slop | 9.2 | 24.0 | 63.3 | 0.21 | 0.21 | 1.68 |
| GPT 5.5 / plan-first | 8.2 | 24.0 | 67.3 | 0.29 | 0.25 | 1.61 |

例如 GPT 5.5 使用 anti-slop 后，侵蚀下降 0.28、冗余下降 0.11，同时 Strict 下降 5.6 个百分点。GPT 5.4 则出现 ISO 上升 2.0 个百分点、Strict 下降 1.5 个百分点，说明新功能测试和含回归的完整判定可以向不同方向变化。[论文表 3](https://arxiv.org/pdf/2603.24755v2)

图 5 显示，多数组合的质量分从第一阶段开始就更低，但仍随迭代上升。“降低起点”与“阻止后续上升”是两件事。论文对 GPT 5.4 anti-slop 的走势作了例外描述，不过图中两个指标走势并不完全相同，不宜概括成所有质量维度都持续改善。论文汇总称额外提示使检查点费用平均增加 12.1%；表 3 的原始值保留了各模型差异。摘要、正文关于最大改善比例使用了不同概括，本文以原始表格和阶段曲线为准，不将其混成一个统一提升率。[论文 §3.4、图 5、表 3](https://arxiv.org/pdf/2603.24755v2)

### 改变侵蚀分的定义

附录 B.3 将高复杂度阈值改为 8、10、12，长度项改为不加长度、平方根 SLOC、线性 SLOC，共九种变体。作者检查它们与下一检查点通过情况和成本的关联。

| 指标 | 与下一检查点通过情况的相关值 | 与下一检查点成本的相关值 |
| --- | ---: | ---: |
| 论文采用的侵蚀分 | -0.018 | 0.167 |
| 表中列出的最佳变体：CC > 12、线性 SLOC | -0.136 | 0.095 |
| LOC | -0.212 | 0.502 |
| 平均 CC | -0.046 | 0.218 |
| 最大 CC | -0.117 | 0.356 |
| 重复比例 | -0.042 | 0.114 |
| AST-grep 命中数 / LOC | -0.052 | 0.151 |

阈值和长度项变化没有改变作者报告的总体方向：侵蚀分对下一关是否通过的关联很弱，对成本是正相关。LOC 对成本的相关值更高，因此论文并未证明侵蚀分是最强成本预测器，也没有证明降低侵蚀必然提高下一关通过率。表 6 没有给出各相关值的置信区间或完整拟合控制项，不能从这一张表推导因果效应。[论文附录 B.3、表 6](https://arxiv.org/pdf/2603.24755v2)

当前 runner 会管理独立题库，并支持 `SCBENCH_PROBLEMS_PATH` 指向本地目录。要固定材料，可先准备两个 checkout，再将该变量设为题库根目录。下面是依据代码整理的**单题入口示例，尚未执行模型评测**：

```bash
# 在固定版本的 slop-code-bench 目录中执行。
# 模型凭据通过本地环境配置；先准备 Docker 和 uv。
export SCBENCH_PROBLEMS_PATH=/absolute/path/to/scb-problems
uv sync --frozen
uv run slop-code run \
  --agent codex \
  --model openai/gpt-5.5 \
  --environment configs/environments/docker-python3.12-uv.yaml \
  --prompt configs/prompts/just-solve.jinja \
  --problem code_search \
  thinking=high \
  version=0.124.0
```

这一命令是当前代码的复现起点，不等于论文原始运行环境已经完整冻结。还需要确认 API 模型是否仍可用、CLI 的实际版本、容器镜像、依赖锁文件、题库快照和质量检查器；保存最终解析后的配置。默认题库可随发布更新，不能只记录问题名称。[固定版本题库解析代码](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/src/slop_code/problem_catalog.py)、[运行命令说明](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/docs/commands/run.md)

结果检查应同时保留逐检查点 `checkpoint_results.jsonl`、汇总 `result.json`、代码快照和测试报告。分别统计固定 196 分母的二值通过率，以及实际生成工作区的质量均值；如果只跑一题，应明确使用该题检查点数，不能把单题输出误称为全榜结果。质量检查器失败时，当前代码返回缺失指标并记录警告，这种缺失也不能当成零冗余。[固定版本结果字段说明](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/docs/metrics-reference.md)、[driver.py](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/src/slop_code/metrics/checkpoint/driver.py)

## 11. 阅读这组结果时保留的边界

SlopCodeBench 的实测对象是没有历史对话、没有隐藏测试反馈、连续接收需求的 Python 编程 agent。它覆盖了 agent 自己生成代码后继续扩展的过程；没有验证其他编程语言、允许完整历史记忆或人工评审参与时会得到同样结果。

侵蚀与冗余补充了功能测试，但仍是两种静态代理指标。论文展示了它们在多数轨迹上升，也展示了质量提示可以改变分数；指标敏感性实验同时表明，侵蚀分与下一检查点是否通过的相关很弱。开源仓库面板提供了实际代码的参照范围，不能替代同题、同预算的人类对照。以上区分决定了表中的数字可以支持到哪一步。

# SWiM：测试长上下文中的信息利用，并用多次排列选择答案

把几十份文档放进模型的输入窗口后，模型能否找到回答问题所需的信息，取决于文档内容、干扰材料和信息所在的位置。SWiM 将这些因素拆开测试：保持问题不变，移动包含答案的文档，或者逐步增加无关文档，观察问答准确率如何变化。

论文还提出 medoid voting。对同一个问题，把文档顺序打乱几次，分别生成答案，再选出与其他答案语义最接近的一个。这个过程不训练模型，也不重新撰写答案；它增加推理次数，用候选答案之间的一致性做选择。

SWiM 全称为 Snorkel Working Memory Test。“工作记忆”是命名时借用的认知概念；本文实验测量的是文档问答表现，没有检验模型是否具备人类工作记忆机制。[论文与版本记录](https://arxiv.org/abs/2407.03651)。

## 从文档构造可检查的问答任务

SWiM 是一个可以接入用户文档的评测流程。论文将其分为四步。

第一步，用语言模型根据单篇文档生成事实型问题和简短答案。问题应当仅凭这篇文档作答，输出包含 question、answer 两个字段。论文实验使用 GPT-4 生成问答对。

第二步，验证题目。需要确认问题确实有答案、答案与文档一致，而且没有含糊的指代或多个合理解释。作者指出，自动生成任务会出错，需要人工参与验证。论文没有给出完整的人工审核数量、多人一致性或错误率统计，因此不能把“流程包含人工验证”解释成所有题目都经过了可量化的质量保证。

第三步，把答案文档与干扰文档组成上下文，让被测模型回答问题。这一步改变文档位置或干扰量。

第四步，用另一个语言模型比较生成答案与参考答案是否语义一致，返回布尔值。这里允许不同措辞，不要求逐字匹配。用符号表示，某个设置下的准确率为：

$$
\operatorname{Accuracy}=\frac{1}{N}\sum_{i=1}^{N}
\mathbf 1\{J(q_i,\hat a_i,a_i)=\mathrm{true}\},
$$

其中 $J$ 是评判模型，$a_i$ 是参考答案，$\hat a_i$ 是被测模型的回答。这是对评测过程的记号化整理。

评判模型也会错。论文记录了两类问题：回答包含额外细节时，简单的语义比较未必能验证这些细节；即使用贪心解码，同一回答也可能得到不同判定。所以这里的准确率包含评判器误差，不能直接等同于人工核验后的事实正确率。[第 2 节，任务与评判流程](https://arxiv.org/pdf/2407.03651v2#page=3)。

## 本文实验使用的材料与模型

实验数据来自 Hugging Face Cosmopedia 的 `story_forum`，它是合成的叙事文本。每条文本作为一篇文档，再从中生成问答对。虽然框架允许用户接入财报、合同等材料，本文并没有用这些业务文档验证结果。

这也是单文档问答：答案来自一篇指定文档，其他文档充当干扰项。跨文档合并证据、多跳推理、引用定位以及更细的幻觉检查，被作者列为后续方向。将这篇论文描述为已经验证复杂的多文档推理，会超过实验范围。

## 两组实验分别改变位置与干扰量

### 移动答案文档

设文档集合为 $D$，问题 $q$ 的答案来自 $d^*\in D$。实验保留同一组文档，将其余文档随机打乱，再把 $d^*$ 放到指定深度。测试点为 0%、25%、50%、75%、100%。这里的 100% 表示把答案文档放在最后，不是让它超出输入窗口。

同一模型各位置实验保持文档集合不变，以减少材料变化带来的干扰。不同模型则根据各自窗口确定文档数量，长窗口模型可能接收更多干扰文档。因此，这既是在观察位置敏感性，也是在各模型自身上下文预算下进行测试，并非所有模型阅读完全相同的输入。

图 3 显示，多个模型在中间位置的准确率下降，开头或末尾通常表现更好。但各模型的曲线并不相同，也不都是规则的 U 形。Claude 2.1 在叙事问答中放在开头也未必表现良好；论文用它说明简单“针在草堆”测试中的高分，未必能迁移到另一种问答任务。

### 增加干扰文档

第二组实验从只有答案文档开始，逐步加入干扰项，再打乱所有文档。设置为 0%、25%、50%、75%、100% 的干扰档位。0% 仍然包含答案文档，不是空上下文。

正文有一处将 75% 写成 70%；算法 2、实验设置和公开代码采用 75%，本文沿用后者。

这组实验同时改变输入长度和无关信息数量。准确率下降可能与位置、信息筛选等多种因素有关，不能仅凭曲线断言原因是模型“记不住”某个长度之后的文本。论文发现不同模型的下降幅度不同，Gemini 1.5 Pro 在本次单文档问答设置中对干扰表现较稳健；作者也明确保留了对复杂任务的判断。[算法 1、2](https://arxiv.org/pdf/2407.03651v2#page=4)、[结果及适用范围](https://arxiv.org/pdf/2407.03651v2#page=7)。

## Medoid voting 的计算过程

位置实验说明，正确答案可能因为输入排列而未被模型利用。Medoid voting 对文档作多次随机排列，借此获得一组答案。

设 $f$ 为回答模型，$g$ 为文本嵌入模型，$k$ 为生成次数，$\sigma_i$ 为第 $i$ 次文档排列：

$$
\hat y_i=f([\sigma_i(D),q]),\qquad e_i=g(\hat y_i),
\qquad i=1,\ldots,k.
$$

然后计算所有候选答案之间的余弦相似度：

$$
\operatorname{cos}(e_i,e_j)=
\frac{e_i^\top e_j}{\|e_i\|_2\|e_j\|_2}.
$$

最终选择总相似度最高的候选：

$$
i^*=\arg\max_{i\in\{1,\ldots,k\}}
\sum_{j=1}^{k}\operatorname{cos}(e_i,e_j),
\qquad \hat y=\hat y_{i^*}.
$$

因此，结果一定来自已生成的 $k$ 个答案之一。算法不需要参考答案，也不会把几个答案的文本拼接或平均。参考答案仅在之后的实验评分中使用。[算法 3](https://arxiv.org/pdf/2407.03651v2#page=4)。

可以用一个人为构造的相似度矩阵说明选择过程。以下数字仅用于演示计算，不是论文数据或真实嵌入结果：

$$
S=\begin{pmatrix}
1&0.95&0.20\\
0.95&1&0.25\\
0.20&0.25&1
\end{pmatrix}.
$$

三个答案的得分分别为 2.15、2.20、1.45，因此选择第二个答案。前两个回答如果是在说同一件事，它们就形成了一个语义相近的组合。

这也说明了方法的限制：一致性来自候选答案之间，而不是来自原文的事实核验。如果多数排列都诱发同一个错误，错误答案也可能成为中心。嵌入还可能把语义相关、但具体数字或否定关系不同的答案放得很近。

## 对照实验区分了重复生成与文档排列

单纯多调用几次模型，就可能改变结果。论文因此设置固定文档位置的对照：把答案文档保持在表现较差的 25% 深度，重复生成，分别使用温度 0.7 和 1.4。这样可以观察仅增加采样变化是否足够。

实验比较以下条件：

| 条件 | 文档位置 | 生成次数 | 温度 |
| --- | --- | --- | --- |
| 单次基线 | 固定 25% | 1 | 0.7 |
| 重复生成对照 | 固定 25% | 3 | 0.7 |
| 高温度对照 | 固定 25% | 3 | 1.4 |
| Medoid voting | 每次重新随机排列 | 3 或 5 | 0.7 |

图 4 中，随机排列后的选择优于单次基线和两种固定位置对照。论文报告 GPT-3.5 Turbo 16k 最好提升 **24.2 个准确率百分点**，GPT-4 Turbo 最好提升 **17.3 个百分点**。这是准确率的绝对差值，不是相对增长 24.2% 或 17.3%。

从图中柱高读取，GPT-3.5 Turbo 16k 基线约为 62%，三次随机排列约为 86%；GPT-4 Turbo 基线约为 62%，五次随机排列约为 79%。这些绝对准确率是读图近似值，24.2 和 17.3 则是正文明确给出的提升。不能将读图结果补成精确到小数点的实验表。

两种模型的最佳次数也不同：前者图中三次优于五次，后者五次优于三次。论文结果不支持“投票次数越多，准确率必然越高”。[第 4.3 节、图 4](https://arxiv.org/pdf/2407.03651v2#page=6)。

### 最佳位置下可能退步

如果原来排列已经把答案放在有利位置，随机排列反而可能降低表现。图 5 讨论了这种情况，并提出过滤“上下文中找不到信息”一类候选，再做选择。

这依赖一个条件：上下文确实包含答案。本文基准通过构造保证答案文档存在；真实业务问题可能没有答案。如果直接过滤所有拒答，可能把本来合理的“无法回答”排除。因而过滤策略需要与任务是否保证可回答一起说明。

所核对的公开 `test_medoid_voting` 路径会嵌入候选答案并选中心，没有实现图 5 所述的缺失信息回答过滤。复现这一扩展实验需要额外明确过滤规则，不能把默认代码的输出当成带过滤的结果。[图 5](https://arxiv.org/pdf/2407.03651v2#page=7)、[公开选择实现](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/long_context_eval/evals/single_hop_qa.py#L678)。

## 时间与调用成本

设单次长上下文回答的成本为 $C_f$，单个短答案嵌入的成本为 $C_g$，嵌入维度为 $d$。忽略批处理差异，方法成本可写为：

$$
C_{\mathrm{medoid}}\approx kC_f+kC_g+O(k^2d).
$$

这个式子是根据算法步骤作出的成本拆分。它说明主要新增工作是对同一批长文档回答 $k$ 次；相似度矩阵通常较小，但输入 token 会重复处理。方法无需训练，并不意味着没有额外推理成本。并发调用可以减少部分等待时间，也不会消除调用量。

论文没有提供覆盖各供应商的完整费用、延迟和吞吐测量，也没有证明在相同总 token 预算下优于所有替代方法。实际比较应当同时记录准确率与输入、输出、嵌入、评判的调用成本。

## 从公开代码复现时需要固定的条件

本文核对的代码版本为 `ded59dc7ed535a23dac49953d0004bd3de6749a9`。以下是代码观察，与论文实验结论分开记录。

### 文档档位不等于精确 token 百分比

位置测试按文档数量计算插入索引，噪声测试也按文档数量确定加入多少干扰项。由于文档长短不同，25% 文档位置未必恰好落在 25% token 深度，25% 干扰档位也不是严格的 25% token 占用。

代码记录答案文档的起止 token，可用这些值补充实际位置。窗口裁剪先为输出预留 250 token，并用 `tiktoken` 估算文档总长。对非 OpenAI 模型，使用 GPT-4 分词器作为代理，并在配置中降低部分窗口上限；它不是对应供应商分词器测得的精确长度。复现时还需要计入问题和提示词开销。

### 不同模型可能留下不同题目

加载器先把有问答对的文档移到前面，再按窗口预算截断文档集合，最后删除答案文档已被截掉的问答对。因此，跨模型变化的不只是干扰数量，还可能包括实际评测的题目集合。

所核对仓库的 `data_cosmostory.json` 包含 29 个问答条目，文档压缩包包含 697 个普通文件。这是发布文件的清点结果，不能直接当作每个模型、每张论文图的实际样本数。应保存截断后的文档列表、题目 ID 和准确率分母；需要严格配对比较时，应另外报告共同题目子集的结果。

[数据加载、裁剪与筛选](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/long_context_eval/evals/single_hop_qa.py#L143)、[模型配置](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/long_context_eval/parameters/models.py)、[问答文件](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/tasks/data_cosmostory.json)。

### 默认入口不会完成全部论文实验

命令行的 `--tests all` 只运行位置测试和长上下文／RAG 测试，不会运行 medoid voting。需要显式指定 `--tests medoid`，并将默认值为 1 的 `--num_runs_medoid_vote` 改成 3 或 5。只有一个候选时，选择步骤不会产生多候选修正效果。

在原仓库中解压故事文档、准备好服务凭据和依赖后，三次排列实验的命令形态如下。这里保留论文时期的模型标识，用于说明配置；本文没有执行在线模型调用，也没有验证该历史接口今天是否仍可调用。

```bash
python long_context_eval/run_benchmark.py \
  --model_name gpt-4-turbo-2024-04-09 \
  --data_path ./data/cosmostoryforumdataset \
  --task_path ./tasks/data_cosmostory.json \
  --tests medoid \
  --num_runs_medoid_vote 3 \
  --seed 42 \
  --experiment_tag swim-medoid
```

入口默认回答温度为 0.7，评判模型为 `gpt-4-turbo-2024-04-09`、温度为 0，答案嵌入为 `text-embedding-ada-002`。随机种子默认没有固定。命令中的种子用于本地排列随机数，并不能保证远程服务完全确定。

虽然部分文档注释描述了自动生成问答，当前入口读取不到任务 JSON 时会退出，所以题目文件需要预先准备。`requirements.txt` 没有锁定依赖版本，保存实际运行环境也是复现记录的一部分。[命令行设置与分支](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/long_context_eval/run_benchmark.py)、[依赖文件](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/requirements.txt)。

### 相似度实现与公式的对应

`compute_avg_similarities` 将相似度矩阵对角线设为 0，然后按行取均值。论文公式保留自相似度并求和。对非零嵌入，两者只相差共同的常数与缩放：

$$
\operatorname{score}^{\mathrm{code}}_i
=\frac{\operatorname{score}^{\mathrm{paper}}_i-1}{k}.
$$

因此候选排序相同，不构成方法上的不同。零向量则会导致余弦分母为零，需要在工程实现中处理。

回答调用发生异常时，所核对路径会记录空回答，之后仍可能进入评判流程。实验记录应区分服务失败与正常生成的错误答案，避免把接口故障混入模型能力结论。[相似度函数](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/long_context_eval/evals/single_hop_qa.py#L26)、[回答生成路径](https://github.com/snorkel-ai/long-context-eval/blob/ded59dc7ed535a23dac49953d0004bd3de6749a9/long_context_eval/evals/single_hop_qa.py#L277)。

## 结果能支持的结论

在本文的合成叙事单文档问答中，模型表现会随答案文档的位置和干扰数量发生变化；随机排列后选择语义中心答案，能改善两款被测模型在不利位置基线上的准确率。固定位置重复生成的对照，支持文档排列本身对这组结果有作用。

实验还没有给出跨业务语料、多文档推理、答案缺失问题以及等成本方案比较的充分证据。图中也没有呈现完整的置信区间与多随机种子统计。复现实验时，应同时报告实际题目数、人工复核结果、各随机种子的波动与调用成本，再判断方法是否适合具体任务。

本文完成了全文、图表、发布数据与上述代码路径的核对，没有重新调用八种模型，也没有重新测得论文中的准确率。

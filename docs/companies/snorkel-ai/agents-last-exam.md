# Agents’ Last Exam 精读：把专业工作流程变成可检查的任务

Agents’ Last Exam（ALE）让 agent 在真实桌面软件和命令行环境中完成专业工作，例如配置模流仿真、从音频整理管弦乐谱、重建骨骼动画，再提交可以检查的文件。任务不以答对一道知识题为终点，而以交付物为评分对象。论文收集的任务池覆盖 55 个细分领域；公开评测中，Codex + GPT-5.5 的总体完整通过率为 24.0%，最难的 Last-Exam 子集多数配置完整通过率为零。部分得分与完整通过率必须分开看：完成若干步骤，未必交付了全部必需结果。[论文 §2–4、表 1](https://arxiv.org/pdf/2606.05405v2)

## 1. 一个任务包含专业流程和最终交付物

ALE 收集的工作应当同时满足三个条件：对应专业人员真实使用的软件与流程；包含足够长的完整工作链；结果能通过文件、数值、几何、行为状态或明确量表检查。任务提供输入资料、目标软件、交付要求和可实现的评测规则，内部做法一般由 agent 决定。[论文 §2.1](https://arxiv.org/pdf/2606.05405v2)

例如模流分析任务要求打开已有 Moldex3D 工程，根据 `process_spec.json` 设置充填、保压、冷却和翘曲分析，执行求解，再把压力、锁模力、周期、体积和重量等数值写入 `results.json`。打开正确软件并设置部分参数，并不等于完成求解或得到正确数值。论文展示的 Claude Code + Opus 4.7 轨迹得到 0.4762 分；分析认为部分数值是估计值，而非从完成的求解输出可靠提取。[附录 B.3，Task Card 1](https://arxiv.org/pdf/2606.05405v2#page=22)

另一个音乐转录任务要求提交 PDF 乐谱、MIDI 和软件界面截图。案例中 agent 找到了相关 Dorico 工程并导出 MIDI，但其余必需文件未得到确认，因此硬性门槛使分数为零。这个结果表示没有通过该任务交付条件，不表示过程中完全没有正确操作。[附录 B.3，Task Card 2](https://arxiv.org/pdf/2606.05405v2#page=23)

作者以经济上有用的工作为收集目标，但论文没有测量这些任务对应多少 GDP 增长、节省多少真实雇员工时，也没有做部署后的经济效果实验。任务通过率是这里直接观测的量。

## 2. 任务池、工作流和公开子集的数量需要分别记录

论文将 **task workflow** 定义为一个完整专业流程，将 **task instance** 定义为同一流程的一组具体输入和参考输出；多个实例可以共用一个 `evaluate()`。例如 PowerMill 刀路任务的 18 个工件实例共用同一评分流程。不能把工作流数、输入变体数和一次评测选择数混用。[论文 §3、附录 C.3.7](https://arxiv.org/pdf/2606.05405v2)

v2 的不同章节存在数量记录差异：

| 数字 | 来源和含义 |
| --- | --- |
| 1,490 | 图 2、5 的任务实例池，包含尚未完成 QC 的提交 |
| 960 + 530 | 图 5 将实例来源分为外部提交与内部委托构建 |
| 150 / 1,017 / 323 | 图 5 的公开、私有、尚待 QC 三种状态；合计 1,490 |
| 152 | §4.1 的公开评测集合大小，亦与本次核对的公开总清单一致 |
| 67 / 55 / 38 | Near-Term、Full-Spectrum、Last-Exam 三个评测子集的规模 |
| 105 | ALE-CLI 的 Linux 子集 |

图 5 的 150 与实验部分的 152 没有在正文明确解释；结论与附录 C.3.7 又把 960 称为工作流数，与图 5 外部提交的统计单位不完全一致。因此本文保留各处口径，不把整个 1,490 条池写成已经全部通过 QC、全部公开或全部进入主表的任务。[论文图 5、§4.1、§6、附录 C.3.7](https://arxiv.org/pdf/2606.05405v2)

本次直接统计固定版本 `selected_tasks/full/`：三档分别为 67、55、38 条，去重并集为 **152 条**。Near-Term 与 Full-Spectrum 重叠 2 条，Full-Spectrum 与 Last-Exam 重叠 6 条，Near-Term 与 Last-Exam 没有重叠。因此三档的 160 个成员位置不是 160 个独立任务；总体通过率不能把三列简单相加或平均。[固定版本评测清单](https://github.com/rdi-berkeley/agents-last-exam/tree/d10fb61a14f9719774c3520c5763068b28ef5546/selected_tasks/full)

当前清单每行是一个任务路径，配置解析器默认运行该路径的 **variant 0**。更换为显式变体列表可以扩大运行集合，但那已不是原来的 152 条默认运行清单。[固定版本 config_loader.py](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/ale_run/orchestration/config_loader.py)

## 3. 行业覆盖与专家任务构建

ALE 以美国 SOC 2018 职业分类和 O*NET 的任务、工作活动及工具记录为基础。附录 B.1 描述：用固定 GPT-4o mini 提示、温度 0 初筛 O*NET 30.2 的 1,016 个记录；合并到 SOC 基础编码后保留 117 个编码，再经辅助研究和专家复核形成 51 个职业锚定细分领域，补充 4 个新兴领域和既有领域的扩展，形成 55 个细分领域。[附录 B.1](https://arxiv.org/pdf/2606.05405v2#page=17)

这是 ALE 按数字工作流程重新组织的分类，不是美国官方职业体系天然就有“55 个行业”。它聚焦主要通过计算机完成的工作，不覆盖以体力操作为核心的所有职业。论文称其归入 13 个领域组；图 2 同时列出额外的 Other 分类，因此展示图中的分组标签也不能完全照搬为官方行业数。

任务数分布很不均衡：图 2 工程与建筑为 368，计算与数学科学 237，视觉与媒体艺术 226，商业与金融 189，而法律为 15。这说明“每个领域都有覆盖”与“每个领域的任务量相同”是不同条件。[论文图 2](https://arxiv.org/pdf/2606.05405v2#page=3)

构建过程依次包括：

1. 顾问委员会招募相关领域专业人员，确定任务来源。
2. 专家提交已经完成过的项目，整理描述、输入文件、软件、预期交付物、评分规范五项材料；门户可使用 AI 辅助补齐说明。
3. 初审提出修改或接受意见，缺少上下文、复杂度或可验证性的任务返回修改。
4. 工程团队配置环境、实现评分器并试跑，发现依赖或规格缺口时返回专家。
5. 专家委员会最终检查参考答案、容差和上下文，避免标准过严或过松后再接收。

论文没有公布所有专家的工时日志，也没有逐题给出人类完成时间分布。摘要说 250 多名专家，相关工作部分说 300 多名从业者，均为项目规模描述；本文不把它们当成统一时间点下的精确标注员数量。[论文 §2.3、附录 B.2](https://arxiv.org/pdf/2606.05405v2)

公开与私有池分开，并计划轮换公开任务，目的在于降低训练污染和针对固定题目调参的风险。它不是已经证明模型未见过任何相关资料的检测结果；被参考的公开论文、数据或软件文档本身可能公开存在。[论文 §2.3、附录 B.2](https://arxiv.org/pdf/2606.05405v2)

## 4. 执行协议：准备环境、运行 agent、最后评分

每个任务的 `main.py` 暴露三个生命周期函数：

| 函数 | 职责 |
| --- | --- |
| `load()` | 声明指令、路径、参数、操作系统和计算资源；不连接远程环境 |
| `start()` | 准备工作区、放入输入、启动目标软件，形成初始状态 |
| `evaluate()` | agent 结束后读取交付物，按参考资料与评分规则返回 0–1 分数 |

环境使用 `input/`、`software/`、`output/`、`reference/` 的目录约定。agent 接收任务说明，在桌面截图、shell 输出和文件内容之间观察，再执行点击、键盘、命令、文件编辑或 API 调用；参考材料只供评分器使用。当前 runner 的生命周期是在 agent 完成后才执行 `stage_reference`。这是所检查实现的隔离步骤，不能代替对所有任务和云权限的完整安全审计。[论文图 6、附录 C.1–C.2；固定版本 lifecycle.py](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/ale_run/orchestration/lifecycle.py)

论文实验主要使用 GCP 虚拟机：默认 `c4-standard-4`，4 vCPU、16GB 内存；需要 GPU 的任务用带 NVIDIA L4 的 `g2-standard-8`，部分数值任务按需增加内存或 CPU。附录 C.4.1 又提到 Azure Windows 桌面，因此材料并没有给出一份完全统一的逐运行底层资源清单。复现应记录每个任务实际镜像和后端。[附录 C.1、C.4.1](https://arxiv.org/pdf/2606.05405v2)

所有 agent 运行设 **5 小时墙钟上限**。达到上限时停止 agent，评分器仍检查已有产物，而不是统一判零。当前仓库示例配置默认 `wall_time_s: 7200`，只有两小时，重跑论文设置需要显式改为 18,000 秒。[论文 §4.1、附录 D.2；固定版本 example_exp.yaml](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/example_exp.yaml)

## 5. 同时使用 GUI 与命令行的 agent

ALE 将被测系统定义为模型与 harness 的组合。harness 管理对话、工具、子代理、上下文压缩与终止；模型决定怎样完成任务。论文通过统一 CUA MCP 桥接提供 14 个桌面工具，覆盖截图、点击、移动、拖动、滚动、键盘操作和等待。[论文 §3.2、附录 C.4、表 5](https://arxiv.org/pdf/2606.05405v2)

主要配置让同一个模型直接读取截图并调用 GUI 工具，称为 GUI-as-Tool。对于表 1 标有 † 的 DeepSeek V4 Pro、GLM 5.1、MiniMax M2.7，另加视觉子代理。因此即使在“固定 OpenClaw”的模型对照中，附加感知能力也不完全相同，不能把所有差异只解释为纯语言模型本体的变化。[论文表 1 表注](https://arxiv.org/pdf/2606.05405v2#page=8)

作者还实现 ALE-Claw：参考 OpenClaw 的循环并移植为 Python，保留上下文管理，减少长期运行助手所需的调度、多渠道、插件等部分，添加 CUA 适配。论文报告系统提示长度减少约 65%。这是一套参考 harness 和配置对照；论文没有逐个移除记忆、压缩、子代理，再给出独立消融结果。动态组件消融主要作为未来研究用途提出。[附录 C.4](https://arxiv.org/pdf/2606.05405v2#page=33)

## 6. 评分不是一个统一的“完成百分比”

每个任务自行定义评分逻辑。论文归纳了七类比较对象：精确字符串或哈希，结构化数值和表格，几何表面，视觉外观，行为或世界状态，文本量表，可执行程序或模型的测试结果。不同指标可以先经过硬性门槛，再组合成最终分数。[论文 §3.3、附录 C.3、表 3](https://arxiv.org/pdf/2606.05405v2#page=28)

### 门槛与加权分数

可以将 gate-and-score 形式整理为：

$$
s(x)=g(x)\sum_{j=1}^{m}w_jq_j(x),\qquad
 g(x)\in\{0,1\},\quad q_j(x)\in[0,1].
$$

其中 $g$ 代表必需文件、格式或安全条件是否满足，$w_j$ 是任务作者定义的权重。该表达式是对评分形式的整理，不是所有 ALE 任务都采用相同权重或同一个 $g$。

PowerMill 刀路任务在论文中的规则是：先检查碰撞与过切，再用仿真工件表面和参考 STL 的距离评分。记 $F(\tau)$ 为采样表面点距离参考表面不超过 $\tau$ 毫米的比例，则：

$$
s=g\,[0.70F(0.3)+0.30F(2.0)].
$$

公开脚本从 agent 网格表面采样 10,000 点，再计算到参考表面的最近距离。它是**单向点到表面距离**，不是双向 Chamfer 距离。0.3 毫米内的点同时属于 2.0 毫米内集合，合计获得完整权重；两个集合不是互斥分箱。[附录 C.3.3；固定版本 verify_stl.py](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/tasks/engineering/gcode/scripts/verify_stl.py)

**说明示例**：若 $F(0.3)=0.8$、$F(2.0)=0.95$ 且通过门槛，得分是 $0.7\times0.8+0.3\times0.95=0.845$；若门槛失败，得分为零。不能把 0.845 直接说成“完成了 84.5% 的刀路步骤”。

音乐转录任务通过文件和截图门槛后，将音高、节奏、力度、乐器分配、排版分别按 0.30、0.30、0.20、0.10、0.10 加权。公开实现使用轨道配对后的 MIDI 比较，并对排版调用视觉评分。它说明一个任务里可以同时存在代码检查和模型判断。[附录 B.3；固定版本音乐评分](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/tasks/visual_media/music_transcription/main.py)

### 平均分与完整通过率

设任务集合为 $D$，单次任务得分为 $s_i\in[0,1]$。按论文文字定义，均分与完整通过率分别对应：

$$
\operatorname{Score}(D)=\frac{100}{|D|}\sum_{i\in D}s_i,
\qquad
\operatorname{Pass}(D)=\frac{100}{|D|}\sum_{i\in D}\mathbf1[s_i\text{ 获得满分}].
$$

有重复运行时还需要按论文使用的运行汇总协议处理；表 1 只对部分配置进行了同实例三次独立运行，并给出分数标准差。因此不能假设所有行都是三次平均，也不能从四舍五入后的通过率反推出唯一整数成功数。总体列按三档去重后的任务集合统计，行业分析又有实例、工作流、领域逐级聚合的口径，不宜混用分母。[论文 §4.1、表 1 表注、附录 C.3.7](https://arxiv.org/pdf/2606.05405v2)

### 代码评分与模型评分的比例

附录对公开任务工作流静态扫描得到：93.2% 使用代码评分，6.8% 涉及 LLM 评分；88.5% 在宿主侧评分，11.5% 需要虚拟机内校验器。这些比例以扫描的 **工作流** 为单位，不是全部 1,490 实例的人工复核比例，也不是评分准确率。[论文表 4](https://arxiv.org/pdf/2606.05405v2#page=31)

对于难以完全数值化的视觉交付物，作者要求用有具体证据的窄问题，例如是否保留目标轮廓、是否出现规定软件界面、回放是否与预览一致，再由代码汇总。论文没有给出这些模型判断与独立专家逐项比较的准确率或一致性统计。因此“避免宽泛主观判断”是协议设计，不能等同于已验证零误判。

当前帮助函数默认 LLM 评分模型是 `gpt-5.4`，视频侧默认可解析到 `gemini-3.1-pro-preview`，还允许任务与环境覆盖。这些是当前代码默认值，不是所有论文运行已经固定的评分模型。复现需要记录最终解析后的 judge 和提示。[固定版本 evaluation.py](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/tasks/utils/evaluation.py)

## 7. 三个子集与主表结果

Near-Term 选择当前前沿 agent 能有一定完成度、便于频繁迭代的任务；Full-Spectrum 以覆盖 55 个细分领域为目标；Last-Exam 选择最困难的工作流。它们既有难度目标，也有覆盖目标，因此不是互斥、等大小的三档随机分层。[论文 §4.1](https://arxiv.org/pdf/2606.05405v2#page=9)

下表摘录 v2 表 1，每个子集的单元格为 **完整通过率 / 平均分**，均按百分制：

| Harness + 模型 | Near-Term | Full-Spectrum | Last-Exam | 总体通过率 |
| --- | ---: | ---: | ---: | ---: |
| Codex + GPT-5.5 | 38.1 / 64.7 | 22.7 / 36.0 | 0.0 / 11.2 | 24.0 |
| ALE-Claw + GPT-5.5 | 32.8 / 67.4 | 23.6 / 41.1 | 2.6 / 12.8 | 23.0 |
| Claude Code + Fable 5 | 34.3 / 63.4 | 20.9 / 34.1 | 0.0 / 5.2 | 22.0 |
| Cursor + GPT-5.5 | 32.1 / 60.8 | 20.0 / 32.7 | 2.6 / 10.7 | 20.7 |
| Cursor + Composer 2.5 | 34.3 / 61.1 | 18.2 / 30.8 | 0.0 / 8.8 | 20.4 |
| Cursor + Opus 4.7 | 29.9 / 61.2 | 20.0 / 37.6 | 2.6 / 11.4 | 20.4 |
| Claude Code + Opus 4.7 | 20.9 / 54.3 | 12.7 / 29.1 | 0.0 / 10.0 | 13.2 |
| Codex + GPT-5.4 | 13.4 / 22.8 | 3.6 / 7.7 | 0.0 / 0.0 | 7.2 |

Codex + GPT-5.5 在总体通过率上最高，但 ALE-Claw + GPT-5.5 在表中三个子集的均分更高。两种指标衡量的目标不同：一套系统可能完成更多整题，另一套系统可能在更多未完成题上拿到部分分。Last-Exam 0% 完整通过，也不表示平均分必须是零。[论文表 1](https://arxiv.org/pdf/2606.05405v2#page=8)

ALE-CLI 是 105 条 Linux 任务。Codex + GPT-5.5 总体通过率为 23.3%；Claude Code + Sonnet 4.6 为 16.7%，ForgeCode + Sonnet 4.6 为 13.3%，Hermes 为 13.2%，Terminus 为 11.9%，OpenHands 为 9.0%。表注把这组实验也标为 CLI agents + GUI-as-Tool，并以 GCUA 系统作参照，不能仅凭 ALE-CLI 名称断言每一个比较行都严格禁用了桌面工具。[论文表 1 下半部](https://arxiv.org/pdf/2606.05405v2#page=8)

## 8. 模型与 harness 对照能说明到哪一步

固定 GPT-5.5 更换五种 harness，总体通过率从 Droid 的 19.1% 到 Codex 的 24.0%，跨度 **4.9 个百分点**。固定 Opus 4.7 更换三个 harness，从 Claude Code 的 13.2% 到 Cursor 的 20.4%，跨度 **7.2 个百分点**。

固定 OpenClaw 更换模型，从 Grok 4.3 的 4.3% 到 GPT-5.5 的 21.1%，跨度 **16.8 个百分点**。附录据此描述模型差异的范围约为 harness 差异的三倍。[论文表 1、附录 D.4、图 12](https://arxiv.org/pdf/2606.05405v2#page=36)

这些是所选配置的最大值减最小值，不是方差分解，也没有把上下文长度、API 预算、视觉子代理和模型能力全部独立控制。它支持“在这组实验里模型间差距更大”，不能推广成所有工程工作对性能贡献固定只有三分之一。

论文没有训练新模型，也没有对 GUI 工具、上下文压缩、子代理和行业知识逐一做开关消融。原文关于这些组件如何改善能力的解释，应与已实际完成的固定模型/固定 harness 对照区分。

## 9. 失败分析与超时分析

失败分析只选取 **Claude Code + Opus 4.7 的公开任务失败轨迹**。首先由 Codex 读取交互摘要、运行元数据、评分和事件文件，生成带证据位置的分析卡；为控制成本，提示禁止读取完整 `transcript.jsonl`。随后 GPT-4o 在温度 0 下把卡片分类。[附录 D.3](https://arxiv.org/pdf/2606.05405v2#page=35)

论文报告的分布为：

| 类别 | 比例 |
| --- | ---: |
| 错误策略 | 30% |
| 领域知识不足 | 25% |
| 提前终止或交付不完整 | 17% |
| 输出格式错误 | 10% |
| 实现错误 | 8% |
| 幻觉或编造 | 6% |
| GUI 交互失败 | 4% |

这些比例来自自动分析与分类，不是所有失败经专家双人独立标注后的统计。附录也有分类层级差异：规则先把 GUI 失败归为 Infrastructure，最终分布却把它并入 Execution 的 22%。本文保留叶子类别，避免重分类造成额外推断。[附录 D.3.2–D.3.3](https://arxiv.org/pdf/2606.05405v2)

Understanding 与 Approach 合计 78%，但其中包含错误策略和提前结束，不能全都改写成“78% 因缺乏专业知识”。任务需求、工具选择和交付完整性在这个统计中是不同原因。

超时占全部已评测运行的 3.8%。Near-Term、Full-Spectrum、Last-Exam 超时率分别为 3.1%、3.2%、6.4%；Last-Exam 超时轨迹均分 1.3，提前结束轨迹均分 7.0。这个差异不是延长时限的随机对照：更难的任务或更早走错的方法本来就可能更容易超时。[论文表 6–7](https://arxiv.org/pdf/2606.05405v2#page=34)

任务卡补充了过程细节。骨骼动画案例虽然有可编辑 Blender 工程和预览，但预览约 4 秒，对照约 13.6 秒，动作幅度也被压低，得 0.4285；胸片标注裁决任务要求为九个样本选择更合适的读片框并生成三个 TSV，案例得 0.3333。这些是单条轨迹的错误分析，不能拿来估计整个领域的失败率。[附录 B.3，Task Card 4–5](https://arxiv.org/pdf/2606.05405v2#page=25)

## 10. 公开子集代表性与运行成本

作者用 Claude Code + Opus 4.7 在完整池和公开子集上比较领域组通过率，得到 Pearson $r=0.89$、$p<0.001$。完整池整体更容易，因为公开集纳入较多 Last-Exam 任务。[附录 D.1、图 11](https://arxiv.org/pdf/2606.05405v2#page=34)

相关性支持的是这个模型配置下不同领域表现的相对顺序接近，并不证明公开集与完整池绝对难度相同，更不证明其代表所有职业工作量。完整池仍包含未验证状态材料；论文没有在该分析中逐条列明实际成功运行的清单和 QC 状态，因而无法仅凭图 11 重建全部分母。

表 1 的成本是每个子集的总 API 费用，不是每题单价。比如 Codex + GPT-5.5 的三列为 243、157、170 美元；ALE-Claw + GPT-5.5 为 148、71、107 美元。两套系统的执行时间和 token 量也显著不同。由于子集重叠、部分配置有重复运行，不能把三列相加后直接除以 152，就宣称得到一次去重评测的精确平均价格。[论文表 1](https://arxiv.org/pdf/2606.05405v2#page=8)

附录 D.5 展示成本和分数没有单调关系。但 API 费用不含完整云虚拟机、商业软件授权和任务制作成本，也不是当前价格。原文还有配置标签的版本残留：图 13 及后续热图提到 Droid + Opus 4.6，而表 1 对应主流配置写 Opus 4.7；本文主结果以表 1 为准，不合并这两种标签的数据。[附录 D.5–D.6](https://arxiv.org/pdf/2606.05405v2#page=37)

## 11. 公开实现的两处评分边界

本次按固定代码检查了刀路任务的整个评分入口。发现两项会影响复现的实现细节：

**代码评分不自动等于逐次确定性。** `verify_stl.py` 调用 `trimesh.sample.sample_surface` 随机采样 10,000 个点，没有在该脚本显式固定随机种子。相同两个网格重复运行可能产生略有不同的比例。论文笼统把 code-based judges 视为确定性，复现时仍需逐项记录采样与随机性。[固定版本 verify_stl.py](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/tasks/engineering/gcode/scripts/verify_stl.py)

**测试模式与正式模式需要进一步区分。** 当前 `gcode/main.py` 只要发现输出目录已经存在 `agent_sim.stl`，就直接进入 STL 比较，跳过碰撞检测和仿真。注释称其用于正负样例测试，但条件本身没有额外检查独立测试模式标志。因此不能描述这个版本“无论输出怎样，都必定先通过碰撞门槛”。这是静态代码核对结果，不表示论文轨迹已经触发或利用该分支。[固定版本 gcode/main.py](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/tasks/engineering/gcode/main.py)

上述细节不改变论文设定的意图，但影响哪些分数可从当前实现原样复算。本文没有据此推断其他 151 个默认任务都存在相同问题。

## 12. 复现准备与本次阅读范围

当前框架要求 Python 3.12–3.13，固定 `openenv-core==0.3.0`、`cua-bench==0.2.7`。agent 依赖放在独立 workspace package 中，只运行 `uv sync` 不会装齐各 agent 依赖；README 使用 `uv sync --all-packages`。部分 agent 还有上游子模块与补丁二进制，应同时记录版本。[固定版本 pyproject.toml](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/pyproject.toml)

复现一个配置需要固定以下材料：

- 任务清单与变体索引，避免把同名工作流的其他实例混入。
- 模型 API 名、harness 版本、补丁版本、推理设置和工具权限。
- VM 镜像、目标软件及许可、输入和参考文件版本、桌面分辨率。
- 时限、失败重试策略、是否续跑、每题重复次数。
- 评分器代码、judge 模型及提示、采样种子与完整评分输出。

当前 `configs/agents/codex.yaml` 默认模型为 GPT-5.4，CLI 版本为 0.114.0，并配置带补丁的二进制；不能直接认为默认文件就对应主表 GPT-5.5 行。示例实验还启用 `auto_resume: true` 和最多三次失败尝试，复现时需要区分基础设施重试与独立统计重复。[固定版本 Codex 配置](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/configs/agents/codex.yaml)、[示例实验](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/example_exp.yaml)

在完成账户、环境和模型配置后，可按官方流程先检查实验展开结果，再启动运行。以下仅是入口，**本次没有执行云资源创建或模型调用**：

```bash
# 在已固定版本、已配置环境的仓库中。
uv sync --all-packages
uv run python -m ale_run run example_exp.yaml --dry-run
# 核对展开的 agent、任务与变体后再实际运行：
uv run python -m ale_run run example_exp.yaml
```

原始示例只选择 hello 演示任务，且时限两小时。正式复现应复制并修改任务清单、模型和 `wall_time_s: 18000`，不能把 demo 成功当作论文成绩复现。GPU、Windows 和商业软件任务不能用较小的本地 Linux Docker 子集替代后仍声称等价。[固定版本快速开始](https://github.com/rdi-berkeley/agents-last-exam/blob/d10fb61a14f9719774c3520c5763068b28ef5546/docs/quickstart.md)

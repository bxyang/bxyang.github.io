# 办公任务训练向软件工程迁移的行为分析

修改一个软件接口时，新增函数只是局部工作：原有调用方是否仍然可用、旧测试是否已经过时，都需要继续检查。办公任务也会出现相似的依赖关系，例如调整课程表时，解决时间冲突不能以重新放入不符合年级要求的课程为代价。这篇论文研究同一次办公任务训练后，两类任务中的行为怎样一起变化。模型的 SWE-Bench Pro 通过率从 20.5% 增至 26.3%；作者把轨迹差异归纳为目标形成、状态构建、目标稳定和完成验证四种能力。性能提升是测量结果，四种能力提供行为解释，尚不是已经隔离验证的因果机制。

## 从局部动作到完整任务

作者把 goal-directed execution 简称为 GDE，本文译为“目标导向执行”。它描述模型在嵌套任务中，持续将当前动作、已有信息和上层要求联系起来的能力。

论文的基本单位是一个目标循环：先确定想达到的状态，再采取动作或查询环境，依据返回结果更新对环境的理解，最后检查目标是否满足。没有满足就继续；完成局部目标后，结果还要回到上层任务。读取文件、查询服务和运行测试都属于动作，因为它们会改变模型掌握的信息，即使没有修改外部文件。[§3、图 1](https://arxiv.org/pdf/2608.01604v1)

这里的“环境状态”是实际上发生的事情，“工作状态”是从模型后续行为推断出的理解。两者可能不同：文件已经更新，不代表模型知道它更新了；模型声称已完成，也不代表外部文件满足要求。论文通过推理文本、工具调用、返回值、补丁和测试观察这种关系，没有测量模型内部寄存器，也没有证明模型真的维护了一个符号化目标栈。

以论文用于讲解的订阅费用审查为例，顶层任务是决定哪些合同续约、重谈或取消。它会展开为找合同、确定预算与取消期限、提取续约日期、查询使用量、统一计费口径、比较费用和使用情况、处理特殊依赖、形成建议等步骤。查询使用量又可能展开为多个服务的登录、导出和合并。这个例子说明层级关系，不是后文 731 道软件任务中的一个实验样本。

四种能力的区分在于出错发生在哪个关系上：

| 能力 | 具体含义 | 与相邻能力的区别 |
| --- | --- | --- |
| 目标形成 | 从上层要求和当前信息中形成正确的局部目标 | 一开始就选择了错误代理目标，属于这里 |
| 状态构建 | 获取、解释、合并并保留完成任务所需的信息 | 看见一个事实，却没有把它纳入后续决策，也属于失败 |
| 目标稳定 | 在局部困难和修补过程中保持已理解的上层要求 | 起初理解正确，后来被局部问题带偏，与目标形成不同 |
| 验证 | 确定什么证据能够证明目标实现，并实际取得证据 | 文件存在或某个小测试通过，不一定足以证明整体完成 |

这不是互斥的错误标签。同一条失败轨迹可以同时缺少信息整合和有效验证；论文也没有把每条轨迹强制归到唯一类别。[表 1、§6.1](https://arxiv.org/pdf/2608.01604v1)

## 训练任务提供了什么经验

训练环境 LHMTA 是 Long-Horizon Multi-Tool Agent 的缩写，通过 Model Context Protocol（MCP）服务器提供办公工具。论文使用的快照含 403 项任务，其中 363 项用于训练，40 项留作同分布评估。27 类任务覆盖文档、表格、幻灯片、搜索、文件操作、日历、浏览器、规划和跨办公服务协作。

作者说明其中没有软件工程任务、软件工程评分器或软件基准反馈。它不同于让模型练习仓库修复后，再测试另一个仓库；但“没有软件工程任务”也不等于模型从未学过代码。基础模型已有预训练知识，监督阶段还有教师生成的轨迹。论文提出的解释之一正是训练改善了已有知识的组织和使用，而不是补充目标仓库的特定知识。[§5.1—§5.2、§7](https://arxiv.org/pdf/2608.01604v1)

每个任务有确定性的 Python 评分器，检查最终环境状态中的多项条件。全部条件满足才严格通过；训练则能获得部分得分。若第 $i$ 项任务有 $K_i$ 条条件，第 $j$ 条结果记为 $g_{ij}\in\{0,1\}$，将原文文字写成公式就是：

$$
R_i=\frac{1}{K_i}\sum_{j=1}^{K_i}g_{ij},\qquad
P_i=\prod_{j=1}^{K_i}g_{ij}.
$$

$R_i$ 是条件完成分，本篇 §5.2 将它描述为轨迹奖励；$P_i$ 是该环境的严格通过指示。说明示例：十项条件通过九项时，完成分为 0.9，严格通过仍为零。奖励在完整轨迹结束后赋予，论文没有为每个工具调用前缀单独打分。这里的“密集”是终局分数允许部分正确，不是每一步都有独立奖励。

同一训练工作的[跨基准报告 §4](/companies/surge-ai/cross-benchmark)给出了更完整的奖励：当条件完成分低于 0.5 时，最终奖励取完成分与努力下限的较大者；下限最高为 0.4，由工具调用次数、正常结束和至少使用三种工具构成，不是额外相加的奖金。本篇没有展开这部分，因而上式只能表示条件完成分，不能覆盖所有低分轨迹的实际奖励。关联报告也明确未做去除该下限的消融；尝试执行和正常结束受到直接塑形，是解释行为变化时需要保留的因素。

成功轨迹通常需要 30—40 个含工具调用的回合、8 万—10 万 token。这是典型成功轨迹的描述，没有给出全部轨迹的均值、分位数和完整长度分布。也不能将 363 项任务简单乘以上述 token 范围，当成实际训练费用。

作者强调四类任务结构：深层分解、并行调查后综合、相互牵制的约束、长依赖链。它们可能共同训练多种行为。例如，调查多个文件需要形成局部目标、保留证据，也需要确认搜集是否完整。图 4 为每种结构突出一个常见压力点，不表示四种结构与四种能力存在已验证的一对一对应关系。

## 先监督热身，再做轨迹级强化学习

基础模型是 Qwen3.5-122B-A10B，约 1,220 亿总参数、100 亿激活参数的混合专家模型。训练使用 LoRA，适配注意力和 MLP 的投影层。

监督阶段先让 Kimi K2.6 在 LHMTA 任务上生成轨迹，经过拒绝采样保留分数严格高于 0.9 的轨迹，共 3,000 条。这个阈值与“所有条件全对”不同，评分项较多时可以保留接近满分但未严格通过的轨迹。论文解释，热身是因为基础模型很难完成足够长的工作，直接依赖稀疏成功信号不利于启动训练。

强化学习阶段在全部 363 项训练任务上使用 GSPO 的序列级估计器，每个 prompt 采样八条 rollout；本篇以条件通过比例概述轨迹奖励，完整低分奖励还需参照上面的跨文补充。八条采样是训练配置，不是测试时尝试八次再挑最好的结果。[§5.2](https://arxiv.org/pdf/2608.01604v1)

本篇没有展开 GSPO 损失、重要性比率、截断阈值、优势标准化、KL 项或每条轨迹 token 的具体归约方式，因此不能仅依据算法名称填出这次实验的完整优化器实现。同样，LoRA 秩、学习率、训练步数、全局批量、GPU 数和实际训练费用，在本篇也没有完整配置表。复现需要对应训练报告及实际配置，而不是把任意 GSPO 默认值当成作者的设置。

外部基准的任务、评分器、检查点选择信号、超参数调整信号和奖励设计信号均未用于训练，这是作者在 §5.2 的声明。同一训练工作的[跨基准报告](https://arxiv.org/abs/2608.00181)还补充：Toolathlon 表现曾影响最初的基础模型家族和 SFT 教师选择。因此，后训练阶段不使用外部分数，不能扩写成整个研究设计从未参考外部基准。论文没有提供足以重新审计预训练污染、全部教师轨迹来源和任务重合的公开原始数据。

## 性能表给出的比较范围

基础检查点和训练后检查点都用贪心解码，报告 pass@1。外部基准遵循各自的原生评分规则，不统一换成 LHMTA 的部分奖励。

| 基准 | 与训练的关系 | 基础模型 | 训练后 | 变化 |
| --- | --- | ---: | ---: | ---: |
| LHMTA 留出集 | 同分布，40 题 | 10.0% | 27.5% | +17.5 个百分点 |
| Toolathlon | 外部多工具任务 | 22.2% | 31.8% | +9.6 个百分点 |
| BFCL-V4 | 外部函数调用 | 55.7% | 59.2% | +3.5 个百分点 |
| SWE-Bench Pro | 外部软件工程 | 20.5% | 26.3% | +5.8 个百分点 |

数据来自表 2、表 3。SWE-Bench Pro 的 5.8 是百分点增量，相对于基础模型约增长 $5.8/20.5\approx28.3\%$，两种口径应分开。LHMTA 的 40 题对应通过数从 4 题到 11 题，但这只是净增七题，不表示只有七题发生变化。

所有结果来自一个基础模型和一次后训练，没有不同随机种子、模型规模或训练混合的重复实验，也没有置信区间。贪心解码限定了选取 token 的方式，不替代跨训练运行的方差测量。本篇也没有逐一列出所有外部基准的样本清单、代理框架版本、工具调用上限及上下文预算。[§5.3、§8](https://arxiv.org/pdf/2608.01604v1)

## 案例分析只看从失败变为成功的任务

作者对所有“基础模型失败、训练后模型通过”的任务进行配对分析：LHMTA 留出集 12 题、SWE-Bench Pro 77 题、Toolathlon 14 题，合计 103 对，即 206 条轨迹。每一对使用同一个问题、环境、代理框架和评估协议。

这个选法适合寻找新成功是怎样发生的，但刻意排除了“两者都失败”“两者都成功”和“训练后退步”的情况。四类行为在这些案例中出现，不等于它们在全部评测任务中的发生率已经得到估计。这里还有一处原文计数不一致：40 题留出集的 27.5% 意味着训练后总共通过 11 题，但 §6.1 又写有 12 题从失败变为成功；新增成功数不可能超过训练后的全部成功数。若强行合并 4→11 和新增 12 的数字，还会推出五个退步，而基础模型一共只通过四题。论文没有解释两处是否采用不同轨迹批次或样本口径，本文分别保留，不据此编造配对通过表或退步原因。

分析流程先由 Claude Opus 4.8 辅助寻找失败轨迹最早出现、且有证据支持的分歧位置。输入包括任务要求、评分证据、工具调用与结果、生成文件、编辑、测试和推理文本。成功轨迹作为对照路径，不被直接当成唯一正确答案。

作者随后对照原始轨迹人工检查报告中的主张和引文，再通过反复比较形成四种能力的解释框架。它不是一个先锁定标签、再对未知样本盲测的分类实验。论文未报告独立标注员人数、标签一致性、根因定位准确率或按类别的完整计数。模型辅助分析产生的根因说法需要证据审核，不能因为报告使用了“因果”措辞，就把它视为随机干预证明。[§6.1、§8](https://arxiv.org/pdf/2608.01604v1)

## 四组配对案例中的具体变化

### 目标形成：先明确需要保留的语义

NodeBB 的任务要求数据库调用方能够只请求对象中的特定字段。两个模型都找到现有辅助函数和测试，相关语义包括每个键保留一个返回结果，以及请求但不存在的字段用 `null` 表示。

基础模型没有把局部目标设为复用已定义语义的路径，而是在后端重新实现过滤，改变了缺失对象的行为。训练后的模型复用既有辅助函数，也覆盖 Postgres 路径。作者用它说明错误不一定源自没找到函数，也可能是找到了信息却设错下一步目标。

对应的办公案例来自 Toolathlon：任务要计算主页点击转化为商店浏览的比率。基础模型在查看数值前就采用“点击数 / 商店浏览数”，发现大于 100% 仍继续；训练后使用“商店浏览数 / 点击数”。这里分母由所描述的事件关系决定，不是看到异常数字后任意倒数。[图 5、§6.2](https://arxiv.org/pdf/2608.01604v1)

### 状态构建：观察到的信息需要进入后续决策

Ansible 案例要求拒绝把 Python 保留关键字用作 collection 名。基础模型已经看到直接导入的 `iskeyword`，却新写 `keyword.iskeyword`，因名称不匹配引发 `NameError`，导致 19 个测试失败。自测暴露问题后，它改动测试设置，没有修正实现。训练后的模型将需求接入既有的 `AnsibleCollectionRef.is_valid_collection_name` 中央验证路径。

办公案例中，基础模型读取工作簿时遇到公式字符串，就把这些条目当作非数字删除，丢掉报告计算同比增长所需的数据。训练后的模型重新读取工作簿中的公式缓存值，保留了计算结果。这个案例表明它换了读取策略；不表示缓存值在所有电子表格中都一定存在或一定最新。[图 6、§6.2](https://arxiv.org/pdf/2608.01604v1)

### 目标稳定：局部修补不应覆盖已经理解的要求

PowerShell CLIXML 解析任务要求解码转义字符，同时保留回车和换行。基础模型起初实现正确，后来遇到旧测试要求删除末尾 CRLF，就修改实现来满足旧行为。训练后的模型根据本次需求判断旧测试与目标冲突，保留了 CRLF。

课程安排案例里，所有课程必须是二年级的 2xxx 课程。基础模型先明确识别 STAT1010 不符合要求，后来为解决某学期超负荷又将它加回。训练后的模型选择 ENG2010，并移动另一门课。区别在于保持跨步骤约束，不是简单“增加更多检查”。[图 7、§6.2](https://arxiv.org/pdf/2608.01604v1)

### 验证：检查真实完成条件

Element Web 的任务将 `Pill` 类组件改为函数组件，并导出以前的静态方法。基础模型验证新辅助函数能否导出和导入，却没有查找旧调用方，留下对已移除的 `Pill.roomNotifPos` 和 `Pill.roomNotifLen` 的访问。训练后的模型查找旧用法、迁移调用位置，再运行针对性的 TypeScript 检查。

图书目录案例中，基础模型从一个有限范围的表格读取建立了包含 44 本书的中间文件，随后检查该文件，却没有检查提取范围是否覆盖整个目录。训练后的模型比较两种工作簿视图，确认它们都包含相同的 347 个 History 作者后再使用结果。44 的单位是书，347 的单位是作者，不能直接相减来计算遗漏书数。这是外部证据与自洽中间文件之间的区别。[图 8、§6.2](https://arxiv.org/pdf/2608.01604v1)

## 731 对软件轨迹的汇总证据

表 5 的分母是 731 道成对软件工程任务，不是前面的 77 个新成功案例，也不是 103 对跨领域案例。这些指标提供更广的行为观察，但都属于代理指标：它们通过命令和补丁估计行为变化，没有直接测量模型心中的目标。

| 行为指标 | 基础模型 | 训练后 | 单位或分母 |
| --- | ---: | ---: | --- |
| 每次运行平均检索调用 | 25.6 | 23.9 | 按命令规则识别的调用数 |
| 平均不同检索信息 | 7,985 | 9,019 | 每次运行不同的 12-token 片段数 |
| 重复检索信息 | 22.5% | 14.3% | 先前输出中已见片段的占比 |
| 平均涉及参考补丁文件 | 2.69 | 3.08 | 模型补丁与参考代码补丁共同修改的文件数 |
| 平均新增行 | 415.5 | 111.7 | 最终补丁中的新增行 |
| 至少运行一次正式测试 | 37.5% | 73.3% | 全部运行 |
| 首次测试的平均位置 | 70.8% | 62.0% | 仅运行过测试的轨迹，按命令序列归一化 |
| 测试通过后仍有编辑 | 5.9% | 12.9% | 全部运行 |

检索调用平均少了 1.7 次，不同片段增加约 12.9%，重复占比下降 8.2 个百分点。新增行减少约 73.1%，训练后约为基础模型的 26.9%。正式测试的轨迹比例增加 35.8 个百分点，约为原来的 1.95 倍；首次测试位置提前 8.8 个百分点。这些是依据原表四舍五入数字复算的描述量，不是显著性检验。

首次测试位置只对有测试的轨迹取平均，因此训练前后参与这个均值的任务集合不相同。“平均更早”不能直接写成每个同一任务都提前了测试。测试后编辑的比例也不等于“编辑后最终通过任务”的比例，更没有证明这次编辑是被测试结果所引起。

平均共同修改的参考文件增多，说明最终补丁覆盖更多参考实现涉及的路径；它不是阅读过参考文件的计数，也不是代码逐行相似率。有效实现可以与参考补丁不同，补丁更小本身也不是正确性的充分条件。目标稳定在这些汇总指标中没有干净的对应量，作者明确将它的证据保留在案例层面。[表 5、§6.3](https://arxiv.org/pdf/2608.01604v1)

## 附录中的指标如何落到命令和文本

### 检索调用是正则识别的只读命令

附录 A.1 首先忽略 `>/dev/null`，其他输出重定向会使命令被排除；随后应用修改操作、运行脚本、测试、安装和构建等排除规则，最后要求命中读取命令名单。名单包括 `ls`、`find`、`rg`、`grep`、`cat`、`head`、`tail`，以及部分 `git` 查询子命令。

这不是根据工具返回内容自动理解命令的真实语义。只读 Python 脚本也会被脚本排除规则过滤；不同书写形式可能导致识别差异。附录特别说明，`git branch` 与 `git remote` 理论上能够修改仓库，但这批语料中命中的都是列出或查询用法。这是对已分析语料的检查，不是这两个命令在任意环境中都只读的保证。

### “信息量”计算的是文本片段

检索输出先去除 ANSI 控制序列，再用附录给定正则切分标识符、数字和其他非空白字符，并转为小写。这里的 token 是分析器产生的片段，不是 Qwen 的模型 tokenizer，也不是输入 token 账单。

随后取每 12 个连续 token 的重叠窗口。长度小于 12 的输出作为一个片段。令第 $c$ 个检索输出产生片段多重集 $S_c$，则按论文定义，不同信息数可表示为：

$$
U=\left|\bigcup_c\operatorname{set}(S_c)\right|.
$$

“重复”针对的是先前输出中已经出现的片段，不能把当前输出内部第一次出现和随后重复，自动都当成跨调用重复。用 $V_{c-1}$ 表示前面输出出现过的片段集合，单条轨迹的重复比例可表达为：

$$
D=\frac{\sum_c\sum_{s\in S_c}\mathbf{1}[s\in V_{c-1}]}{\sum_c|S_c|}.
$$

这是对附录文字的形式化；论文没有说明零输出时的处理，也未明确表内重复率跨轨迹汇总采用等权均值还是合并所有片段。没有完整统计代码和原始输出时，这个细节仍需补齐。片段相同是字面重复，不必然是无价值重复：修改后重新检查同一段代码可能是必要验证；反过来，同一事实改写后也可能成为不同片段。

### 正式测试与测试通过分开计算

附录 A.3 用命令模式识别 pytest、Go/Cargo 测试、npm/pnpm/yarn test、Jest/Vitest/Mocha、部分 make 测试目标、tox、unittest、Bazel、Gradle、Maven、dotnet、RSpec 等。

“运行过正式测试”只要求命中模式。判为测试通过还要求返回码为零、不属于掩盖退出状态的管道或回退，并且输出中没有明确失败标记。因此，73.3% 不是测试通过率，也不是 SWE-Bench Pro 最终通过率。自定义验证脚本或类型检查可能帮助完成任务，但没有命中这些规则就不进入正式测试指标。

测试后编辑通过后续修改命令识别，包括 `apply_patch`、原地编辑、部分 Git 修改命令、文件复制或删除、Python 写文件、输出重定向等。部分模式排除 `/tmp/` 或 `/dev/` 路径。这个指标没有完整分析代码语义，也不验证每次匹配一定造成了有意义的持久代码变化。

首次测试位置按首次正式测试在全部助手 shell 命令中的序号归一化到 0—1。附录没有明确写出序号起点、单命令轨迹以及分母边界的处理，故不把一种自行选择的归一化公式说成作者已公开的精确实现。

### 补丁指标只看最终提交

附录 A.4 从 `diff --git` 头提取文件路径，取模型最终补丁文件集合 $F_A$ 与参考代码补丁文件集合 $F_G$ 的交集：

$$
C=|F_A\cap F_G|.
$$

参考补丁不包含单独的测试补丁。新增行只统计以 `+` 开头的行，排除 `+++` 文件头，再跨文件求和。它没有扣除删除行，也不代表全过程写过多少代码；中途加上后来删掉的内容不在最终补丁中。[附录 A，第 19—20 页](https://arxiv.org/pdf/2608.01604v1)

## 解释的边界和复现材料

论文没有分别去掉深层分解、并行综合、复杂约束或长依赖链，也没有用等预算的软件工程训练集作对照。它因此没有证明办公训练是提高软件工程成绩最省成本的方式，也没有隔离究竟哪种任务结构产生了迁移。

监督热身和强化学习作为整体发生变化，本篇未给出它们各自对四种行为的独立消融。探索范围、坚持程度、指令遵循和工具使用等更一般的变化，仍可能解释部分收益。四类能力是从案例中逐渐形成的解释框架，不是已经穷尽所有可能行为变化的量表。

复现需要分三层处理：

| 要核实的结果 | 本次可访问材料 | 仍需要的材料 |
| --- | --- | --- |
| 单任务结构 | 论文第 7 页、作者固定 HTML 中的任务树和元数据 | 完整原始轨迹、证据目录对应文件，以重新审计节点解释 |
| 行为汇总表 | 附录正则与文本处理说明、表 5 | 731 对原始轨迹、最终补丁、运行结果及完整统计实现 |
| 训练与基准提升 | 本文训练流程、表 2—3与相关训练报告入口 | 实际数据快照、评分器、SFT/RL配置、模型检查点、评测框架版本和运行日志 |

本次核对的作者公开仓库仅有交互式任务分解页面，没有训练脚本、731 对轨迹分析程序或完整模型权重；因此固定这个 commit 只固定了展示材料。它也不能替代外部基准本身的原始评估代码。没有在可核实入口找到的材料，本文不推定已经公开。

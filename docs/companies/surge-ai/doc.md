# DOC：用详细大纲控制长篇故事

DOC 研究怎样让模型从几十词的故事设想出发，写出数千词、情节能够沿着计划推进的故事。它先把粗略大纲细化成树，再用一个单独训练的小模型逐 token 调整正文生成，使当前段落更贴合大纲中的具体事件。论文中，DOC 相比经过长度和正文模型匹配的 Re3，在人工段落评价上的情节连贯性、大纲相关性和趣味性分别提高 22.5、28.2 和 20.7 个百分点。不过，这些指标评价的是故事中的长段落；论文展示的完整故事仍有身份、时间和局部事件不一致的问题。[论文 §4、表 1、附录 M](https://arxiv.org/pdf/2212.10077v3)

## 从短设想到完整故事

论文的自动生成输入通常是一段 30–60 词的英文 premise，即故事的基本设想。它规定核心人物、冲突或走向，但不是现成故事。输出是完整的英文虚构故事。研究没有给故事增加一组机械的通过条件，而是让人评价生成结果。

下面是用于解释流程的自拟示例：一位维修员发现小镇的钟总在同一时刻停下，调查后找到了故障来源，最后修复了钟。粗略大纲可以只有“发现异常—展开调查—完成修复”。但把中间一项写成一千词时，模型仍要临时决定去哪里、遇到谁、找到什么证据，以及哪些事件应当稍后发生。

DOC 会进一步规划成“检查钟楼—询问上一任维修员—找到受损零件”，再把每一步拆成更具体的子事件。写正文时，模型主要负责把当前事件写成场景、动作和对话。大纲增加了可供遵循的内容，也增加了必须落实的约束，因此 DOC 同时改变规划和生成两个环节。

此前的 Re3 已经把写作分成规划、起草、候选重排和一致性编辑。它会在提示中放入人物信息、大纲及已经写出的内容，并用相关性与连贯性模型选择候选续文。DOC 沿用这套结构，增加详细大纲和 token 级控制。论文实例移除了耗时的一致性编辑步骤；作者援引 Re3 的实验说明，该步骤对最终质量的影响没有达到显著水平。这不等于 DOC 已经解决了事实一致性。[论文 §3.1](https://arxiv.org/pdf/2212.10077v3#page=2)

## 大纲是一棵逐层展开的树

### 先确定同一层，再深入下一层

DOC 将大纲表示为树 $T$。根节点下面是一级大纲，一级节点的子节点构成二级大纲，以此类推。生成采用广度优先顺序：先完成一级内容，再扩展各一级节点，之后生成更细的一层。

论文实验设置最大深度为 3，每个被扩展节点的子节点数要求在 2–5 之间。系统逐个生成子节点，遇到结束标记时停止；如果子节点过少或过多，就重新采样。作者观察到实际扩展通常产生 2–3 个子节点。深度控制的是规划粒度，并不直接规定最终故事有多少词。

生成一个新节点时，提示包括它的祖先，以及这些祖先各自的子节点。这样可以同时看到所在章节的目标、已经安排的相邻事件和更高层的走向，而不必把整棵树逐字放入提示。在分支规模固定时，这部分上下文随深度线性增长。论文使用 `text-davinci-002` 的插入接口，将新事件前后的上下文分别作为前缀和后缀。[论文 §3.2、附录 B.1](https://arxiv.org/pdf/2212.10077v3#page=3)

### 事件候选需要过滤和排序

每个新节点生成 10 个事件候选，再进行过滤和重排。过滤要求包括陈述句形式、正常的首字母格式、避免异常标点、长度在 3–50 token 之间，以及不能与其他大纲事件过度重复。重复检测结合文本距离和自然语言推断模型。

重复检测排除直接祖先，因为子事件本来就可能重述父事件中的一部分。例如“维修员检查钟楼”下面出现“维修员打开钟楼的设备箱”不应因共享词语直接被删。如果所有候选都被过滤，该父节点可以保留为叶节点，不再继续扩展。

剩余候选按两种方式选择：

- 父节点的第一个孩子，用 `all-mpnet-base-v2` 计算句子相似度，选择与父事件相关的候选。
- 后续孩子用顺序判别器选择，判断该事件是否处在合适的位置，减少已经结束又重新开始等问题。

顺序判别器基于 `roberta-large`。训练资料是 `text-davinci-002` 生成的 1,000 篇短故事，每篇约两三段。作者认为这种短输出更像事件概要，适合作为顺序学习材料。负例通过将句子移动到故事的其他位置构造。这是一个学习顺序合理性的分类模型，不是对事件因果关系的形式化证明。[论文附录 A](https://arxiv.org/pdf/2212.10077v3#page=12)

### 场景、人物与人物状态也进入计划

DOC 最初尝试建立最多 10 人的人物表；名称过滤后可能少于 10 人，完成大纲后还会移除从未出现的人物。每个事件再关联相关人物和场景。

人物识别既处理直接出现的名字，也通过模型提示处理“母亲”“朋友”等未具名人物或人物群体，再与已有库存匹配。人物并不一定是人类，附录中的一个计划就把一只狗作为角色。识别结果可能缺失或错误，论文没有报告该组件的单独准确率。

方法总图将场景和人物检测放在节点创建流程中，但附录 B.2 对实际执行顺序作了更具体的说明：场景不影响其他大纲部分，因此在其余大纲完成后，按叶节点的深度优先顺序统一生成。生成场景时还会看到此前场景，以减少无解释的地点变化。

每当人物出现在一个大纲事件中，系统还尝试生成一条新的人物事实。若新事实已被此前事实蕴含，就过滤掉；起草某个叶节点时，提示只使用到该节点为止已推导的人物信息。这个机制让人物状态可以随情节发展，例如从“尚未找到故障”变为“已经定位故障”。事实来源仍是生成的大纲与模型推断，没有外部核实，也没有保证这些状态彼此一致。[论文 §3.2.2–3.2.3、附录 B.2–B.3](https://arxiv.org/pdf/2212.10077v3#page=4)

## 起草时保留必要的过去与未来

正文按大纲叶节点顺序生成，每个叶节点可以对应不同长度的文本。DOC 不会一次把某个叶节点写完，而是每次生成一小段，重新组织提示，再决定是否继续。

结构化提示大致包含当前叶节点及祖先所规定的情节、相关人物及其当前状态、较远历史的摘要、较近的已生成内容、当前场景，以及前后相邻的大纲事件。附录 B.4 给出了完整提示实例。将远处内容压缩后，正文可以长于生成器当前可见的上下文。

未来事件有助于准备过渡，但也可能让模型过早写出下一段的内容。DOC 把下一个大纲事件放进提示，同时加强对当前事件的控制。论文将这一点视为软约束的配合，并未给出“下一事件绝不会提前发生”的保证。[论文图 2、§3.3.1](https://arxiv.org/pdf/2212.10077v3#page=5)

## 详细控制器学习判断续文是否仍在写当前事件

### 用故事段落的摘要构造训练信号

控制器基于 OPT-350M，正文生成器则是 OPT-175B。前者的任务不是续写故事，而是读入一段自然语言事件描述和当前文本前缀，预测这个前缀是否与描述相符。

训练从 WritingPrompts 的英文故事出发。作者让 InstructGPT3-13B 给故事片段写摘要，把“摘要—原段落”作为对应关系。摘要在形式上类似大纲事件，因此可以将这种能力迁移到起草时的大纲控制。

只使用完整匹配与完整不匹配的片段，会留下一个问题：续文一开始切题，之后偏离，分类器仍可能因开头相似而给高分。论文因此构造更难的样本：保留匹配段落的前半部分，在句子边界后换成不匹配内容，要求模型识别后续偏离；反过来，也用不匹配前缀加上匹配的后续内容，训练模型识别重新回到主题的情况。[论文 §3.3](https://arxiv.org/pdf/2212.10077v3#page=5)

公开代码补充了具体做法。`create_alignment_data.py` 按句子分块，默认块长上限为 200；每个块生成 3 条摘要，选择字符数最短的一条。`FineCoherenceSplitLoader` 将片段再分为较短的句子块，默认参数 `max_extra_prefix_chunk_length=32`。它不仅从同一故事的前后片段产生 `repeat` 和 `shuffle` 负例，还包含其他故事的 `other` 负例。因此，“训练只使用同一故事的错误摘要”不足以描述公开实现。

### 损失只覆盖需要判断的续文部分

论文主要通过文字解释训练，没有给出完整损失公式。根据公开 `fudge_controller.py`，可将实际计算写为：

$$
\mathcal L(\theta)=
\frac{\sum_{i,t}m_{i,t}\,
\operatorname{CE}\!\left(D_\theta(s_i,x_{i,\le t}),y_i\right)}
{\sum_{i,t}m_{i,t}}.
$$

这里，$s_i$ 是事件摘要，$x_{i,\le t}$ 是文本前缀，$D_\theta$ 输出匹配和不匹配两类 logits，$y_i\in\{0,1\}$ 是该样本的标签。掩码 $m_{i,t}$ 对摘要、额外前缀和填充位置置零，只对要学习判断的续文位置计入交叉熵。代码把样本标签广播到相应 token，先求带掩码的损失总和，再除以有效位置数。优化方向是最小化损失。

这个写法意味着，长一些的有效续文会在同一批次中贡献更多 token 项；它不是先对每个样本单独平均再等权平均，也不是要求错误前缀里的所有 token 都预测错误。对于“先偏题、后回正”的正例，监督重点在后面回正的部分。[固定代码：训练与掩码](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/story_generation/common/controller/models/fudge_controller.py)、[样本生成](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/story_generation/common/controller/loaders/fine_coherence_loader.py)

### 推理时调整下一个 token 的分数

对单个约束，FUDGE 控制可以解释为：

$$
\widetilde\ell_t(v)=\ell_t(v)
+\lambda\log D_\theta(y=1\mid s,x_{<t}v),
\qquad v\in K_t.
$$

$\ell_t(v)$ 是生成器对候选 token $v$ 的原始分数，$K_t$ 是生成器得分最高的 100 个候选，$\lambda\geq0$ 是控制强度。控制器判断“加上这个 token 后是否仍符合当前事件”，用正类对数概率修正分数，再进行采样。集合外的候选在实现中被赋予极低分数。

由于概率不超过 1，控制项不大于零；其作用是更强地压低不符合事件的候选。作为说明示例，两个 token 的生成器分数相同，控制器分别给出 0.8 和 0.2 的匹配概率，在暂不考虑温度与其他惩罚时，$\lambda=1$ 让二者相对权重成为 $4:1$，$\lambda=3$ 则成为 $64:1$。这解释了强控制也可能使文本反复围绕少数相关内容展开。

DOC 将控制强度设计成随当前叶节点的起草进度增加：每个新叶节点从 0 开始，每次 64-token 子步骤增加 3，最高为 10，即 0、3、6、9、10……。场景变化的控制强度为事件强度的 0.5 倍，新人物进入为 0.2 倍。移动到下一个叶节点后重新归零。论文没有为这些比例提供逐项扫描实验。[论文附录 E](https://arxiv.org/pdf/2212.10077v3#page=20)

## 实际生成预算与终止条件

| 环节 | 论文配置 |
| --- | --- |
| 规划模型 | InstructGPT3-175B，`text-davinci-002`，使用插入接口 |
| 正文生成模型 | OPT-175B，当前可见上下文限制为 1,024 token |
| 详细控制器 | OPT-350M |
| 大纲深度与分支 | 最大深度 3，每次扩展要求 2–5 个孩子 |
| 事件候选 | 每个节点 10 个候选 |
| 正文候选 | 每个子步骤生成 8 个候选并重排 |
| 子步骤长度 | 64 token，每个叶节点最多 8 个子步骤，即最多 512 个生成 token |
| 正文温度 | 0.8 |
| 大纲事件、初始人名温度 | 1.2；扩展失败时每次增加 0.1，最多再尝试两次 |
| 频率惩罚 | 权重 1，同时考虑提示；随 token 以 0.98 的系数衰减 |

这些是过程限制，不是固定总调用量：树的大小、候选失败和提前停止都会改变成本。64 token 的尾部若刚进入一个新段落不足 10 token，会删去该不完整段落。[论文附录 E](https://arxiv.org/pdf/2212.10077v3#page=19)

token 控制之后，DOC 仍使用从 Re3 继承的相关性和连贯性重排器选择续文。这两个重排器与 OPT-350M 的详细控制器不同，分别承担候选级选择与 token 级引导。

论文文字将提前停止描述为：相关性与连贯性的组合对数概率已经超过 −0.5，继续写也没有进一步改善，就在前一段结束。固定代码的判断更具体：它比较当前最佳候选与当前叶节点历史上的 `best_alignment_so_far`；历史最佳分数达到 `early_stop_threshold=-0.5`，且新候选严格低于历史最佳时停止，默认 `continuation_threshold=0`。若所有候选分数低于 `skip_threshold=-10`，代码会再试一批候选；仍很差时放弃这次延伸。不能把整个过程简化为每个叶节点必定采样恰好 $8\times8$ 次。[固定代码：起草循环](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/story_generation/draft_module/beam_candidate.py)

## 人工评价的分母与评分含义

### 主实验评价对应同一顶层事件的段落

主实验生成 20 个故事。每次向标注员并排展示两个系统中对应同一顶层大纲事件的文本，通常为 1,000–1,500 词，而不是让每个标注员逐字评价整篇故事。每对文本由 3 人标注；模板要求快速浏览，给出整体判断。

三个问题分别是情节是否连贯、是否贴合给定事件，以及是否有趣。每题有四类选择：A、B、两者都好、两者都不好。将某系统被单独选中或被同时选中记为 1，其余记为 0，得到：

$$
\operatorname{Score}(S)=
100\times\frac{\sum_{j=1}^{N}z_{j,S}}{N}.
$$

主实验每个比较文件有 71 对文本、每对 3 份判断，因此 $N=213$。这里的 213 是判断记录数，并不是 213 篇独立故事。两个系统都被选中时双方都加分，所以分数不必加总为 100%，也不能读成排他性的胜率。

公开分析脚本对对应的二元分数使用 `scipy.stats.ttest_rel` 配对 t 检验，逐条标注进行比较。它没有先按故事聚合，也没有采用按故事重采样的置信区间。论文用粗体标识 $p<0.05$，主要表格没有逐项置信区间。本文复算了比例和分母，没有重新实施全部显著性检验。[论文 §4、附录 K.1](https://arxiv.org/pdf/2212.10077v3#page=5)、[分析脚本](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/scripts/analysis/analyze_surge_passage_results.py)

### 基线与结果

Re3 基线被调整为同样使用 OPT-175B 起草，并增加每个大纲事件的生成步数以匹配长度。初始场景、人物和顶层大纲与 DOC 共用。Rolling-OPT 只保留设想、当前顶层事件和能够放进上下文的最近正文；Rolling-GPT 则将这一滚动窗口基线换成 GPT3。它们不是对不同商业模型的通用排名。

下表保留各次成对评价中的原始分数，越高越好：

| 成对比较中的方法 | 情节连贯性 | 大纲相关性 | 趣味性 |
| --- | ---: | ---: | ---: |
| Re3 | 45.1% | 37.1% | 39.4% |
| DOC，与 Re3 比较 | 67.6% | 65.3% | 60.1% |
| Rolling-OPT | 38.0% | 25.4% | 25.4% |
| DOC，与 Rolling-OPT 比较 | 80.8% | 78.9% | 69.5% |
| Rolling-GPT | 44.1% | 25.8% | 42.7% |
| DOC，与 Rolling-GPT 比较 | 81.7% | 83.1% | 70.0% |

来源是表 1 与附录表 15。公开的三份主实验 CSV 各有 213 行，按代码规则可复算这些比例。例如与 Re3 比较，DOC 连贯性为 $144/213=67.6\%$，Re3 为 $96/213=45.1\%$。因此 22.5 是百分点差，不是相对增长 22.5%。DOC 在不同对手下的分数不同，不能将这些行当成独立于比较对象的统一绝对质量分。[论文表 1、15](https://arxiv.org/pdf/2212.10077v3#page=19)

平均故事长度也有实际记录：Re3 为 3,810 词，Rolling-OPT 为 3,437 词，Rolling-GPT 为 3,831 词，DOC 为 3,875 词。正文所说“约 3,500 词”是概括，主实验 DOC 的具体均值应采用表 18 的 3,875 词。[论文附录 H](https://arxiv.org/pdf/2212.10077v3#page=23)

### 标注质量与任务边界

论文没有在 Surge 的标注员池之外进一步筛选工人，也没有披露他们均为专业小说作者。主实验每份标注支付 1.20 美元，作者按预计时间以约每小时 20 美元为目标。这个目标时薪不是实际逐人计时得到的统计量。

附录表 20 的 Fleiss’ kappa 为 0.15–0.42，取决于系统对和指标。例如 Re3 与 DOC 的连贯性、相关性、趣味性分别是 0.19、0.24、0.15。它们记录的是标注一致性，不能当成判分正确率。论文也承认这些主观指标的一致性仍较低。

附录 C 另报平均“其他写作问题”数量：Re3 1.17、DOC 1.00。这个指标包含风格突兀、不一致、表达混乱、语法和重复等问题。它没有随主指标一起被作为主要贡献；正文主实验也不能支持 DOC 普遍消除了这些问题。[论文附录 C、I、K](https://arxiv.org/pdf/2212.10077v3#page=19)

## 人在大纲阶段参与的实验

另一个实验让同一组 20 名参与者连续完成五个阶段。参与者先写自己的故事设想，再编辑系统生成的计划，最后比较根据计划写出的故事。

初始一级计划先允许编辑 5 分钟，并作为两个系统共同的出发点。Re3 再给 10 分钟编辑原计划；DOC 则扩展到二级和三级，每次扩展后各给 5 分钟编辑。因此两个系统的计划编辑上限均为 15 分钟。系统生成等待、最初填写设想和最后评价没有包含在这个 15 分钟内。Surge Managed Service 组织了这一流程，研究者为整个交互实验向 Surge 支付 1,000 美元，其中包含参与者报酬；这不能直接换算为每人实收 50 美元。[论文 §4.1、附录 K.2](https://arxiv.org/pdf/2212.10077v3#page=7)

| 指标 | Re3 | DOC | 分母 |
| --- | ---: | ---: | --- |
| 更贴合自己原先的意图 | 17.3% | 80.0% | 75 份有效的段落比较 |
| 提供更多控制 | 5.0% | 80.0% | 20 位参与者 |
| 更有帮助或直观 | 5.0% | 80.0% | 20 位参与者 |
| 重视质量时更愿意再用 | 15.0% | 75.0% | 20 位参与者 |

表 4 不显示“无偏好”一列，但并未将其从分母中剔除。公开 CSV 中，意图比较有 60 次选 DOC、13 次选 Re3、2 次无偏好，另外 25 个预留题位因故事没有相应的第四或第五段而记为 N/A。有效分母是 75；控制感和直观性各为 16 人选 DOC、1 人选 Re3、3 人无偏好，质量选择则为 15、3、2。

这个实验说明的是参与者在该交互方式下的选择。图 9 对“质量”的实际提问，是如果再次写作且重视质量，会选哪个系统；它不是盲评出版标准的合格率。意图评价也是写下设想的参与者本人所作，与主实验每对文本由 3 人评价的安排不同。附录 J 的自由评论同时包含对更详细计划的认可和对最终文本质量的不满。[论文表 4、图 5–9、公开交互标注](https://github.com/yangkevin2/doc-story-generation/tree/9d727cdbae40c72169ab03b729bff4419a113dac)

## 消融支持的结论与没有验证的部分

消融实验使用 10 个故事，公开数据中每项比较有 34 对顶层段落、共 102 份标注。

| 方法 | 连贯性 | 相关性 | 趣味性 |
| --- | ---: | ---: | ---: |
| DOC-NoOutline | 61.8% | 41.2% | 57.8% |
| DOC，与 NoOutline 比较 | 73.5% | 64.7% | 66.7% |
| DOC-NoControl | 62.7% | 52.0% | 58.8% |
| DOC，与 NoControl 比较 | 70.6% | 73.5% | 50.0% |

表 5 中达到显著水平的是相关性改善。连贯性和趣味性的差异没有达到作者设定的显著水平，因此不能据此断言详细控制器提高趣味性。实际上，与关闭控制器相比，DOC 的趣味性点估计更低。

NoOutline 不只删除了详细大纲，还改为按顶层事件生成固定长度、关闭相应提前停止，并使用固定强度的控制器。它比较的是这一组配套改动，而不是严格只改变“大纲深度”一个变量。NoControl 保持详细大纲，关闭详细控制器；其平均长度为 4,190 词，高于该组 DOC 的 3,527 词。作者将这归因于弱相关性导致提前停止较少触发，因此两者并非完全相同的输出长度预算。[论文 §5.1、表 5、19](https://arxiv.org/pdf/2212.10077v3#page=8)

论文没有分别消融事件过滤、顺序模型、人物状态更新、场景控制、人物控制和未来上下文，也没有系统报告树深或控制强度扫描。附录 L 展示两个不使用过滤和重排的大纲：一个反复安排人物发现力量，另一个在面包店已经成功开业后又重新安排开店过程。这些例子说明作者观察到的失败形式，没有构成各组件贡献的独立数值测量。

### 叶节点事件相关性与公开数据的差异

表 6 更细地评价一个叶节点规定的事件是否真正发生。每题只有一份人工判断，检查范围包括当前对应文本和紧邻的前后文本。模板要求事件已经完整发生，或能够明确从文本推断已发生；仅仅讨论一个可能发生的事件不算。

| 方法 | 论文表 6 的事件相关性 |
| --- | ---: |
| DOC-NoControl | 37.8% |
| DOC | 58.5% |

论文报告提升 20.7 个百分点。这个数不表示 58.5% 的整篇故事完全遵循大纲，也不要求事件精确落在当前叶节点对应文本内。[论文 §5.2、图 10](https://arxiv.org/pdf/2212.10077v3#page=8)

公开输出包中的 `doc_docnocontrol_detailedrelevance.csv` 无法直接复算这一表：文件有 328 行，两个方法各 164 行，DOC 的 Yes 为 73 个，即 44.5%；NoControl 为 52 个，即 31.7%。本文同时检查了初版 v1，它也报告 58.5% 和 37.8%，因此不能将差异归为 v1 到 v3 的更新。生成标注输入的脚本有 `--include-before-after` 参数，默认不开启，但公开包没有足够的运行记录证明这一参数就是差异原因。上表保留论文结果，公开 CSV 的计数单独列出，表 6 的端到端复算仍有缺口。[官方输出包](https://doc-story-generation-data.s3.amazonaws.com/doc_outputs.zip)、[标注输入脚本](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/scripts/data/create_surge_match_outline_csv.py)

## 完整故事仍会偏离局部计划

附录 M 列出最先生成的五组 DOC 计划和故事，其中前两组还提供 Re3 与滚动窗口基线。作者将其说明为未经挑选的样本，而不是只展示最优输出。阅读全文能看到高层情节与细节落实之间的区别。

第二个故事围绕一段感情的发展和结束展开，正文大体沿着相识、关系加深、发现冲突和分开的顺序推进。但部分转折、对话和人物关系仍不够一致。第三个故事虽然保留患病和社区支持的总体走向，却没有忠实完成若干让女儿开发治疗方案的具体事件。

第四个例子更直接：大纲规定幸存者面对并击败敌人，正文却转向观看竞技场里的动物争斗；最初作为狗的角色后来出现人类式对话和行动。这里既有大纲事件未落实，也有人物类型不一致。第五组同样存在局部状态反复和结尾事件未充分兑现。正文中大纲标记后面出现一段文字，并不等于该事件已正确实现。[论文附录 M，表 28–37](https://arxiv.org/pdf/2212.10077v3#page=50)

这些例子与作者在 §4、§5.2 和限制部分的说明一致：叶节点有时过于含糊，有时又过度展开；场景和人物检测可能错误；不合理的大纲会把错误继续传给正文。本文实验只覆盖英文虚构故事，没有验证长篇小说、事实性长文或其他语言。更长文本和不同文体在论文中属于后续方向。

## 公开代码与论文配置要分开阅读

本次静态核查固定在官方仓库提交 `9d727cdbae40c72169ab03b729bff4419a113dac`。代码包含规划、起草、控制器训练、基线、标注输入制作及分析。以下几处会影响复现，不能仅根据论文示意流程略过。

**多个控制约束在当前路径中没有累计相加。** `opt_summarizer.py` 依次调用事件、场景和人物控制器，但每次都把服务端原始 `output['logprobs']` 作为 `top_logits` 传入。`fudge_controller.py` 随后用这组原始分数加上当前控制项重新构造分布。因此，当同一步有多个控制约束时，后一次调用会覆盖此前控制项，最终 token 分数只保留最后一次控制的修正。单约束公式仍成立，但不能把该路径写成多个约束对数分数的求和。提示中的事件信息和候选重排仍然存在；这里定位的是公开代码的 token 控制合成行为，没有足够历史运行记录据此判断论文每次实验的实际执行路径。[生成器实现](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/story_generation/common/summarizer/models/opt_summarizer.py)、[控制器实现](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/story_generation/common/controller/models/fudge_controller.py)

**生成器缓存与控制器缓存不同。** 论文选择 Alpa 提供 OPT-175B 服务，是为了修改下一 token 后能够从已有 KV 缓存继续。固定代码中，小控制器自己的增量 KV 缓存部分带有未修复注释并被关闭。具备生成器缓存接口，不等于所有模型计算都已复用缓存。

**训练命令中的上限不是实际样本数。** README 的详细控制器示例使用 batch size 2、学习率 $10^{-6}$、20 个 epoch 和 3 个负例；顺序模型示例使用 batch size 64、学习率 $10^{-5}$、20 个 epoch。`--limit 100000` 是加载上限，不足以证明实际训练了十万条资料。对齐数据加载器默认按文件顺序以 80%/10%/10% 分出训练、验证和测试，再在训练内部打乱；保存检查点依据验证损失。本文没有下载完整训练与权重压缩包核算实际行数，不能据这些默认值补出论文未报告的精确训练规模。[README](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/README.md)、[数据加载器](https://github.com/yangkevin2/doc-story-generation/blob/9d727cdbae40c72169ab03b729bff4419a113dac/story_generation/common/data/datasets/alignment.py)

**便捷替代入口不等于完整 DOC。** README 的 GPT3 起草替代方案会关闭详细控制器；`--no-editor` 的实际含义是关闭一致性编辑，论文实例也采用这一配置。README 另在 2023 年 10 月介绍了重写项目 `doc-storygen-v2`，支持新的聊天模型接口，并明确说明它移除或改写了旧实现的若干部分。重写版本不能直接作为本文实验结果的复现代码。

执行路径可以按“先生成计划，再按计划起草，再制作和分析评价文件”理解：`scripts/main.py --setup-only` 负责规划，随后同一入口加载计划进行起草；`scripts/analysis/analyze_surge_passage_results.py` 分析主实验与消融，`analyze_surge_match_outline_results.py` 分析事件相关性。完整生成还依赖历史 GPT3 插入接口、带 token 分数与缓存功能的 Alpa 服务、OPT-175B 及多个辅助模型。仓库曾列出的公共服务不能据旧 README 假定今天仍能直接使用。

附录 G 给出的总项目开销约为 GPT3 API 3,000–4,000 美元、Surge 标注 4,000 美元，以及约 2,000 个 80 GB A100 GPU 小时，另外还有前期使用较小 GPU 的时间。这些包含开发、预实验和最终实验，不是生成单篇故事或复跑主表的最低预算。作者测得当时 DOC 生成时间约为 Re3 的 2–3 倍，并指出实现尚未充分优化。[论文附录 G](https://arxiv.org/pdf/2212.10077v3#page=23)

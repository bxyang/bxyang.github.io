# 长流程 agent 的跨基准泛化

一个助手可以在办公任务里学会核对表格、保持筛选条件和验证输出文件。这些做法也可能用于修改代码：先确定需要改变的行为，查清已有实现，再检查修改是否满足原要求。Surge 这篇论文在 363 项办公与工具任务上训练 Qwen3.5-122B-A10B，随后观察到五项外部评测的总体分数均提高，其中 SWE-Bench Pro 从 20.5% 升至 26.3%。研究进一步比较训练前后的操作轨迹，但把这些行为变化视为解释线索，没有据此证明一个独立、普遍的迁移机制。

## 外部测试要排除的解释

在一套自建环境里训练 agent，分数变高可能有多种原因。模型可以学会更有效地完成任务，也可以记住工具参数的固定格式、评分脚本的解析习惯或任务模板的规律。即使从这套环境中划出未参与训练的题目，它们仍可能共享相同接口和评分方式。

作者因此把内部留出集定位为训练流程检查，再到其他团队维护的任务与评分器上比较训练前后模型。这里的“跨基准”不是要求工具类型完全没有交集，而是强调外部任务实例和评分器没有进入这次后训练。（原文 §1、§5。）

这一区分有一个明确例外需要保留：研究团队最初选择底座系列和监督教师时，参考过 Toolathlon 排行榜表现。训练任务也受 Toolathlon 启发，并复用了部分 MCP 服务器实现和工具结构。因而不能称整个项目从立项开始就完全没有使用外部评测信息。

论文的隔离声明更窄：在初始底座与教师选定之后，外部任务及评分器不进入 SFT 或 RL，外部分数不用于奖励设计、训练超参数、训练后检查点选择或停止决定。作者无法检查底座全部预训练数据，也不主张这些基准在预训练阶段从未出现过。（原文 §4—§5。）

## 从 430 个候选环境到 363 项训练任务

训练集合称为 LHMTA，即 Long-Horizon Multi-Tool Agent tasks。它覆盖 27 类工作，包括电子表格、文档、幻灯片、终端、日历、搜索、文件系统和浏览器操作。论文明确说集合没有软件工程任务，但这不等于完全没有代码或 shell 操作：处理文件和数据的办公流程本身也可能使用这些工具。

每个环境通过一个或多个 MCP 服务器暴露工具。一条轨迹可以依次调用浏览器、表格读取器、文件系统和日历。模型要根据工具返回的信息调整后续行动，直至完成整个任务。

初始集合有 430 个环境与任务对，其中 27 个因外部 API 限流或运行不够确定而被剔除，留下 403 项：363 项训练、40 项互不重叠的内部留出任务。留出任务既不生成监督轨迹，也不进入 RL。（原文 §3、附录 A。）

任务创作者的目标，是设计强模型不能稳定完成的工作，并关注工具、任务类型和失败模式的多样性。论文没有给出完整任务清单、作者人数、各类别配额或逐题剔除记录，因此不能把这 403 项描述成对所有现实办公工作随机抽样所得的代表性样本。

### 评分看最终环境状态

每项任务配有确定性的 Python 评分器，根据最终状态，例如输出文件内容，逐条检查要求。若一个任务有 10 个条件、满足 8 个，基础完成分为 0.8。把条件写成指示变量，可以表示为：

$$
r_g=\frac{1}{m}\sum_{j=1}^{m}\mathbf 1[c_j\text{ 满足}],\qquad r_g\in[0,1].
$$

这里 $m$ 是该任务的条件数，$r_g$ 越高表示满足的条件越多。这是依据论文“满足条件比例”写出的等权表达，不能据此假定不同任务拥有相同条件数。最终环境状态也不同于模型口头宣称完成：如果要求写文件，仅输出一句完成说明并不能代替文件满足检查条件。

论文称成功轨迹通常需要 30—40 个工具调用回合和 80K—100K tokens。回合、单次工具调用和 token 是不同单位，一回合可能有多个调用。这是成功轨迹的经验范围，不是每题固定动作预算；RL 配置另设 80K 的最大序列长度。原文没有给出逐条截断、压缩前后长度和超限失败统计，不能将两种长度口径直接合并。（原文 §3—§4。）

## 先用高分轨迹热身，再做强化学习

### 底座与 LoRA

底座是 Qwen3.5-122B-A10B，约 122B 总参数、每 token 约 10B 激活参数。论文的 base 指未经本项目额外训练的公开模型，不意味着一个从未做过其他后训练的原始预训练检查点。

作者使用 LoRA 调整注意力与 MLP 投影，目标列为 `q,k,v,o,gate,up,down`，rank 和 alpha 均为 32。低秩适配的作用是降低需更新的参数量；论文引用减少遗忘的已有研究作为选择理由，但没有在本实验中提供全参数微调与 LoRA 的等条件对照。

### SFT 数据来自同一组训练任务

底座在这些任务上即使尝试四次也很少完整成功，直接使用二元成功奖励时信号稀疏。作者先用 Kimi K2.6 在 363 项训练任务上生成轨迹，保留评分严格大于 0.9 的 3,000 条，用于一轮监督微调。

3,000 是轨迹数，363 是任务数；一个任务可以贡献多条轨迹。论文未公开各任务保留多少条、总共采样多少条，以及被过滤掉的轨迹分布，因此不能由两者相除推断每题实际采用固定数量的示范。

随后在同一组任务上用 GSPO 进行 RL，每个提示采样 8 条轨迹。GSPO 在一组采样轨迹之间比较奖励，并以序列为单位构造策略优化信号；本篇给出所用算法和配置，没有展开完整裁剪目标或发布运行源码。外部评测使用完整 SFT+RL 流程的一轮 RL 输出，而不是继续训练到第二、第三轮的版本。（原文 §4、附录 A—B。）

## 奖励包含一个低分轨迹的下限

最终训练奖励并不总等于 $r_g$。对 $r_g<0.5$ 的轨迹，作者还给出努力下限 $e$：

$$
e=\min\left(0.30,\;0.05\min(n_{\mathrm{calls}},6)\right)
+0.05\mathbf 1_{\mathrm{normal}}
+0.05\mathbf 1_{\mathrm{distinct}\ge3},
$$

$$
r=
\begin{cases}
\max(r_g,e),&r_g<0.5,\\
r_g,&r_g\ge0.5.
\end{cases}
$$

$n_{\mathrm{calls}}$ 是工具调用次数；另外两个指示项分别表示正常结束、使用至少三种不同工具。工具调用部分最多为 0.30，两个指示项各最多为 0.05，所以 $e\le0.40$。论文没有公开正常结束状态的具体判定代码，不能自行补出异常、超时或提前停止如何分类。

这个设计是给低分轨迹设置下限，不是在完成分上再加分。以下是依据公式计算的说明例子，不是论文实测轨迹：

| 情况 | $r_g$ | $e$ | 最终 $r$ |
| --- | ---: | ---: | ---: |
| 调用 6 次、正常结束、至少三种工具 | 0.20 | 0.40 | 0.40 |
| 同样的调用与结束情况，但完成分较高 | 0.45 | 0.40 | 0.45 |
| 满足了 80% 的任务条件 | 0.80 | 不参与该分支 | 0.80 |

因此，一个没有完成任何评分条件的轨迹也可能获得正奖励，而反复调用超过六次不会继续增加调用项。正奖励覆盖率不能当成任务成功率，调用数量增加也不能直接当成能力提高。

在一次每题四次尝试的诊断中，16.8% 的任务至少有一次完全通过；82.7% 的任务至少出现一次非零的密集或努力塑形奖励。二者相差 65.9 个百分点，但所衡量的事件不同，不能写成成功率从 16.8% 提高到 82.7%。论文还报告平均奖励从 0.30 增至 0.51，未提供完整底层记录和聚合过程，不能用这两个均值反推出任务通过数。（原文 §4。）

奖励在整条轨迹结束后赋一次。作者曾尝试按轨迹前缀给分，但模型开始优化被奖励的前缀而非完整任务，因此放弃。这里的“密集”指部分条件也能给分，不表示最终方案在每个动作之后都分配奖励。

## 上下文处理与训练预算

长工具输出会挤占上下文。作者把完整表格或论文正文等大块返回内容写入文件，让模型用搜索命令读取所需部分，以额外的操作换取更小的上下文占用。

另一类问题是错误参数导致反复调用，例如服务器要求数字，模型却持续传字符串。作者压缩已经纠正的重试序列，并在滚动上下文里只保留最近的推理轨迹。论文没有公开触发阈值和压缩实现，所以这些做法只能据描述解释，不能当作已核实的可执行配置。（原文 §4。）

| 设置 | SFT | RL |
| --- | --- | --- |
| 训练长度 | 最大 131,072 tokens | 最大 80K tokens |
| 训练轮数 | 1 | 主结果使用第 1 轮输出 |
| 优化器 | fused AdamW，betas 0.9/0.95 | Adam，betas 0.9/0.98，eps $10^{-8}$ |
| 学习率 | $10^{-5}$，余弦调度 | $5\times10^{-5}$，恒定 |
| 权重衰减 | 0.01 | 0.1 |
| 梯度裁剪 | 1.0 | 1.0 |
| 其他 | warmup 0.05；batch size 4；梯度累积 4 | 每提示 8 条；温度 1.0；top-p 1.0 |

RL 配置还列出 context parallel 4、expert parallel 8、tensor parallel 4、pipeline parallel 2，8 个 actor 节点、每节点 8 张 H200，即所列 actor 配置有 64 张 GPU。不同并行维度不能简单全部相乘当作额外显卡数；论文也未说明这是否包括所有独立 rollout 服务资源，未报告总 GPU 小时或实际费用。

需要保留两个看似接近但不同的参数：`KL coefficient` 为 0，`KL-loss coefficient` 为 0.001，并使用低方差 k3 估计器，另有 entropy coefficient 0.001。不能只摘取前者便说训练完全没有 KL 约束。由于缺少完整实现，这里保留两项配置名，不推断它们在框架中所有具体开关的组合。

SFT 使用 ms-swift；论文称训练设施基于 slime、Megatron-LM 和 SGLang，另列 RoPE scaling factor 8、rollout routing replay 开启，以及 SGLang TP/EP size 8。评测以 BF16 在 H200 上通过 SGLang 服务模型。论文没有提供这些项目的实验 commit，不能用当前上游默认值补齐历史设置。（附录 A。）

## 五项外部结果来自不同的评测快照

主结果采用贪心解码，温度为 0。每个基准内的 base 与 trained 使用相同协议，但跨基准保留各自原生评分及聚合方式。部分基准使用加权聚合，因此不宜把所有百分比统一解释为“通过题数除以全体题数”，也不能把五项直接平均作为论文报告的总分。

| 评测 | Base | SFT+RL | 变化，百分点 | 来源 |
| --- | ---: | ---: | ---: | --- |
| LHMTA 内部留出集 | 10.0 | 27.5 | +17.5 | 更新后的 greedy 评测 |
| Toolathlon | 22.2 | 31.8 | +9.6 | 更新后的 greedy 评测 |
| τ²-Bench | 54.8 | 60.1 | +5.3 | 保留的录用稿评测快照 |
| BFCL-V4 | 55.7 | 59.2 | +3.5 | 更新后的 greedy 评测 |
| SWE-Bench Pro | 20.5 | 26.3 | +5.8 | 更新后的 greedy 评测 |
| Terminal-Bench 2 | 44.9 | 47.7 | +2.8 | 更新后的 greedy 评测 |

来源：原文表 1、2。τ²-Bench 保留的配置聚合 Airline、Retail、Telecom 和 Banking。这个域集合应跟随论文配置，不能擅自换成另一版同名基准的默认组合。

SWE-Bench Pro 增加的是 5.8 个百分点；若另算相对增幅约为 $5.8/20.5=28.3\%$，不能把两种单位混为一谈。论文关心的是同一个训练后检查点在软件任务上的变化方向，并没有声称达到这些基准的最高水平。

### 四次采样不能直接解释成标准 pass@4

论文保留了较早快照的另一组分数，来自温度 1.0 的四条轨迹和当时评测程序的原生聚合：

| 评测 | Base | Trained | 变化，百分点 |
| --- | ---: | ---: | ---: |
| LHMTA holdout | 15.9 | 37.2 | +21.3 |
| Toolathlon | 25.9 | 36.1 | +10.2 |
| τ²-Bench | 57.1 | 62.9 | +5.8 |
| BFCL-V4 | 67.7 | 72.2 | +4.5 |

这些结果此前被称为 pass@4，但本文原文明确表示，缺少把它们还原成标准、无权重“每题四次至少成功一次”估计所需的原始单位。因此这里只称四样本诊断，不套用 $1-(1-p)^4$，也不把它与更新后的 greedy 结果相减来衡量增加三次尝试的收益。（原文 §5、表 1。）

### 总体提高不代表每个子项都提高

Toolathlon 七类结果也来自较早的录用稿诊断快照：

| 类别 | Base | Trained | 变化，百分点 |
| --- | ---: | ---: | ---: |
| Academia | 30.7 | 38.1 | +7.4 |
| Campus | 15.4 | 19.5 | +4.1 |
| Daily | 21.4 | 29.2 | +7.8 |
| Finance | 25.0 | 35.1 | +10.1 |
| Office | 0.0 | 16.5 | +16.5 |
| Shopping | 50.0 | 61.5 | +11.5 |
| Tech | 26.7 | 36.6 | +9.9 |

这些数据不分解更新后的 22.2% 与 31.8%，不能通过任意平均去“修正”主表。Office 从零开始提高，也可能部分来自更愿意执行到最后并产出可评分文件；努力下限确实直接鼓励了调用、正常结束和工具多样性。（原文 §6、表 3。）

BFCL 保留的子项诊断中，Agentic 为 41.8→46.9，Multi-Turn 为 57.1→62.1，Live 为 73.1→75.7；Non-Live 和 Hallucination 则略有下降。原文没有给后两项完整数值或这些差异的区间，所以这里只保留报告方向。

整个研究只有一次完整后训练运行。贪心解码消除了采样温度的影响，却没有消除任务抽样、环境运行和训练种子带来的不确定性。作者没有给出五项共同的显著性检验，也缺乏为所有行计算成对置信区间的原始记录；五项变化为正是一组描述性结果，不等于五次独立重复实验。（原文 §5—§6。）

## 从成对轨迹观察行为变化

作者在相同问题、环境、提示、运行支架和评测协议下比较 base 与 trained，重点查看由失败变为成功的轨迹对。先由 Claude Opus 4.8 组成的分析 agent 寻找有证据支持的分歧，再由作者核对推理、调用、返回结果、修改、测试和产物。

最终四类行为是逐步归纳的解释框架，不是提前登记、互斥且穷尽的人工标签。重点选择 fail-to-pass 对也会偏向展示改善，因此不能从案例数量直接计算整个模型的行为发生率。（原文 §7。）

### 把总要求转成正确的局部目标

在点击流分析任务中，base 用点击数除以商店浏览数，得到超过 100% 的转化率；trained 结合事件顺序采用反向比例。这个例子不是所有场景下“转化率”的统一定义，而是当前数据和题目约束下的分母选择。

相应的软件案例是 NodeBB：两者都找到了已有帮助函数和测试，base 却重新实现后端过滤并改变缺失对象行为；trained 将局部目标限定为通过已有帮助函数实现所需字段语义。共同点是局部修改是否准确服务于上层要求。

### 把真实状态纳入后续推理

在计算同比变化的表格任务里，base 把公式字符串当成缺失值而丢弃；trained 重新读取缓存计算值。Ansible 案例中，base 的局部帮助函数调用了未导入模块名，随后转而修改测试设置；trained 则利用代码库中央的名称验证器。两类任务都涉及把已有结构转化为后续可用的工作信息。

### 修复局部问题时保留原约束

课程安排任务要求只选 2xxx 级课程，base 最初识别了要求，却在修复学分上限时引入 1xxx 课程。PowerShell CLIXML 案例中，base 遇到旧测试后又恢复了题目要求移除的旧行为；trained 则识别出测试与新要求的冲突。这里观察的是局部修复有没有覆盖掉原始目标。

### 按任务要求验证，而非只检查已有产物

图书目录任务中，base 读取自己生成的部分中间文件便宣布完成；trained 对照两个工作簿视图核对后再继续。软件重构案例中，base 仅确认帮助函数已经导出，trained 还搜索旧调用并进行针对修改文件的类型检查。

这些案例支持对完成检查方式的描述，但不是四项机制分别导致分数提高的因果消融。四项高层行为没有被逐项写入奖励，不意味着与奖励完全无关：调用和正常结束受到直接塑形，最终状态评分本身也会偏好满足要求的结果。

## 731 对软件轨迹的统计

表 4 对 731 个匹配的 SWE-Bench Pro 任务对计算了确定性行为指标。这是行为分析的配对数量，不自动等于前面所有评测的共同分母，也不能当作 731 个 fail-to-pass 案例。

| 指标 | Base | Trained | 可直接读出的变化 |
| --- | ---: | ---: | --- |
| 平均检索调用数 | 25.6 | 23.9 | 少 1.7 次 |
| 重复检索信息占比 | 22.5% | 14.3% | 低 8.2 个百分点 |
| 触及参考补丁文件的数量 | 2.69 | 3.08 | 平均多 0.39 个 |
| 平均新增代码行数 | 415.5 | 111.7 | 少 303.8 行 |
| 包含正式测试的运行占比 | 37.5% | 73.3% | 高 35.8 个百分点 |

检索调用指只读检查命令。重复信息指同一运行中，转为小写后、相互重叠的 12-token 片段有多少已经在此前检索输出里出现；它不是“22.5% 的工具调用完全重复”。论文没有公开分词、去重和跨运行汇总代码，因此不能进一步确认所有实现边界。

参考文件重合与新增行数来自最终提交的 diff；正式测试指调用标准测试运行器的命令。运行测试不等于测试通过，参考补丁也不是唯一正确答案。平均新增行数相对下降约 73.1%，可以说明修改规模变小，却不能单凭补丁短就推断修改正确。

这些统计与更集中的检查、修改和更多验证相符。它们没有控制其他训练变化，也没有把参考重合度或测试发生率单独随机干预，因此不证明这些行为是跨域改善的唯一原因。（原文 §7、表 4。）

## 消融与继续训练的证据范围

主论文没有提供把 SFT、RL、努力下限和上下文处理分别移除的完整受控消融。作者明确未做 no-floor 消融，也不把最终提升归于 SFT 或 RL 中的某一阶段。

附录 B 记录继续在相同任务上训练的探索：到第二轮，熵从约 0.9 降至约 0.6，训练奖励下降；第三轮进一步退化。没有给出完整逐步曲线、各外部基准成绩或重复运行，因此这支持当前这次继续训练未带来改善，不能据此证明所有模型都应该在一轮停止。

增加任务多样性、使用成功轨迹进行 on-policy distillation，以及添加要求保留成熟系统约束的任务，都属于作者提出的后续方向。本实验没有单独测试这些方案。（原文 §7—§8、附录 B。）

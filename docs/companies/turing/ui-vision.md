# UI-Vision 精读：从界面元素定位到下一步动作预测

在桌面软件里完成操作，需要把用户的目标、当前界面和具体的鼠标位置联系起来。UI-Vision 把这段过程拆成三类离线测试：找到一个界面元素、框出一组功能相关的元素，以及根据操作历史预测下一步动作。数据来自 83 个应用的人类操作示范。论文中的最佳元素定位模型 UI-TARS-72B，三种查询的平均准确率为 25.5%；动作预测中，UI-TARS-7B 的单步成功率为 21.4%。这两个数字属于不同模型和不同任务，均不代表完整桌面任务的在线成功率。（论文表 3、表 5）

## 从一次桌面操作拆出三种能力

论文图 11 使用 QGIS 的图层透明度设置作为例子。操作者先选择图层、打开属性、进入透明度设置，再移动滑块并确认。原始记录既包括截图，也包括移动、按下鼠标、拖动、释放等细粒度事件。

围绕这类界面，三种测试的输入与输出分别是：

| 任务 | 模型收到的输入 | 需要输出的内容 | 评分对象 |
| --- | --- | --- | --- |
| 元素定位 | 当前截图与一个元素查询 | 目标坐标；部分模型先生成框，再取中心点 | 点是否落在标注框内 |
| 布局定位 | 当前截图与功能区域名称、说明 | 包住整个区域的矩形框 | 预测框与标注框的重叠 |
| 动作预测 | 任务目标、当前截图、此前的人类动作 | 下一步动作类型及坐标、文字或按键参数 | 动作和参数是否符合参考示范 |

元素定位不要求操作软件；布局定位也不要求模型自己提出所有功能分组。评测给定一个区域描述，让模型定位该区域。动作预测则把示范中的每一步独立拿出来测试，后续输入仍来自人类示范，不会因模型上一题点错而进入新的界面状态。（§3.2）

这种拆分可以定位错误发生在哪个环节，但没有测到在线执行中的错误累积、恢复、等待界面响应或最终文件是否完成。论文也没有用 UI-Vision 训练一个新模型；主要贡献是数据、评测任务及已有模型的分析。

## 数据由人类完成操作，再逐层标注

数据覆盖生产力、开发、创作、教育、浏览器和娱乐六个领域，包括 LibreOffice、FreeCAD、GIMP、Qt Creator、QGIS 等。每个平台设计约 5–7 个任务，最终形成 450 份操作示范。任务从较简单的文件操作到专业软件设置都有，但并非按桌面软件的真实使用频率随机抽样。（§3.1、表 6）

Turing 团队共 70 人，包含标注员、质检人员和管理人员，主要位于印度和拉丁美洲。附录记载参与者年龄为 20–35 岁，具有工程、计算机等相关本科学历，以及英文技术写作和数据标注经验。作者先培训团队，再开展试点并反馈问题。人员按小时获得报酬；从设计任务到完成质检，每项任务平均需要 60–90 分钟。论文没有给出具体时薪或总标注费用。（附录 A）

完整流程包括：

1. 设计任务，由质检人员和论文作者检查任务要求及覆盖范围。
2. 人类执行任务，工具记录屏幕视频、动作类型、坐标、点击次数和时间戳。
3. 在动作发生前截取关键帧，并修订操作轨迹。
4. 为关键帧中可见的界面元素画框、补充文字和功能说明。
5. 经过独立人员复核、自动检查脚本与作者抽查，再形成基准样本。

采集和标注使用专有工具。公开论文描述了多层质检，但没有提供完整的标注员间一致性统计、逐阶段拒收比例或按标注员划分的结果。团队的地域分布也不能直接证明数据代表不同地区的实际软件使用习惯。

这里需要区分原始事件与处理后的动作。正文说示范平均约 14 步；去掉冗余移动、合并拖动事件之后，动作评测集为 442 个任务、3,191 个步骤，平均约 7.22 步。两者不能当成相互替代的统计值。（§3.1、§3.2、附录 B.3）

## 元素查询的三种写法

### 基础查询：给出元素名称

例如直接询问裁剪工具、跳过所有断点按钮。模型需要根据名称在截图中找位置。这并不总是 OCR 问题：目标可能只有图标，没有可读文字，多个相似图标也可能紧邻排列。

样本不是从全部标注框均匀抽取。作者先关注小元素和图标，按框的重叠与功能、位置进行去重，再用四个较强 GUI 模型的预测辅助发现困难样本。模型全部失败或预测不一致的样本被视为困难候选，人工再核实不确定项。论文没有完整列出四模型的精确版本、各阶段配额和所有过滤阈值。（附录 B.1）

因此，成绩描述的是经过筛选的困难集合；它不等于在用户任意打开的桌面截图上随机点一个按钮的成功概率。筛选时使用的模型表现也会影响评测集的难度分布。

### 功能查询：描述用途

基础标注和截图中的目标框输入 GPT-4o，生成用途说明，再交给人类检查。例如，公开数据第一项的基础查询是“layout in grid”，功能查询改为“Arrange items in a grid format”。两者对应同一张 Qt Creator 截图、同一个框。

模型需要把用途映射到控件，而不是仅匹配控件名称。附录给出的生成提示要求描述准确、简洁，并避免凭空推测功能。生成查询使用的 GPT-4o 属于数据制作阶段，不是评分器，也不是要求每个被测模型使用 GPT-4o。（附录 B.1）

### 空间查询：先找参照，再找相邻元素

数据依据标注框，在上、下、左、右四个方向寻找最近的邻居，产生“某个元素正上方最近的元素”一类查询。没有有效邻居或距离超过阈值的样本被删除。这里既要认出参照物，又要处理方向、距离和多个候选的关系。完整空间过滤脚本及数值阈值未出现在本次核对的公开评测入口中。

三类查询复用一部分原始截图和标注，但并非完全同样的题目：空间查询有 1,935 项，基础和功能各有 1,772 项。不能把不同子集的准确率差直接解释为只改变一个词带来的因果效果。

## 布局区域怎样形成

布局标注从已有元素框出发。作者把软件名称、元素文字、类别和框坐标输入 Llama-3.3-70B，请它把元素组合成功能或语义区域，生成区域名称、解释与包围框。提示要求分组有明确含义，并尽量减少重叠。之后研究团队人工检查，只保留满足要求的分组，得到 311 个样本，每组通常含 5–10 个元素。（附录 B.2）

例如，“Formatting Tools”描述一组字体、字号和对齐工具。它要求覆盖一排相关控件，而不是只点中某个“字体”按钮。这个任务仍依赖人工认可的参考划分；不同人可能对合理的区域边界有不同选择。论文没有报告多个有效布局答案之间的一致性或接受多个参考框的结果。

## 坐标、区域和动作的评分

### 元素定位：点进入框就算正确

设第 $i$ 项的参考框为 $B_i=[x_i^{\min},y_i^{\min},x_i^{\max},y_i^{\max}]$，模型预测点为 $p_i=(\hat x_i,\hat y_i)$，则准确率为：

$$
\operatorname{Acc}=\frac{1}{N}\sum_{i=1}^{N}
\mathbf{1}\!\left[x_i^{\min}\leq\hat x_i\leq x_i^{\max}
\;\land\; y_i^{\min}\leq\hat y_i\leq y_i^{\max}\right].
$$

这里 $N$ 是相应子任务的样本数，分数越高越好。公开代码先把像素框除以图片宽高，转换成归一化坐标；如果模型输出一个框，部分适配器会取其中心点来评分。生成了很大的框，只要中心恰好落在目标内，也可能通过元素测试；该指标没有测预测框是否紧贴目标。（§4.2、代码 `eval_sample_positive_gt`）

一个说明示例：参考框为 `[100, 50, 140, 80]`，预测点 `(120, 65)` 通过，点 `(141, 65)` 失败。边界点也通过。这个例子只解释规则，不是论文数据。

### 布局定位：重叠面积与两种覆盖比例

令 $P$ 为预测区域，$G$ 为参考区域，$I=|P\cap G|$，则：

$$
\operatorname{IoU}=\frac{I}{|P|+|G|-I}.
$$

IoU 在 0 到 1 之间，越高表示两个框越接近。表 4 用百分制显示，例如 30.8 对应平均 IoU 0.308；它不是 30.8% 的样本完全正确。

公开评分函数有一个必须说明的命名细节：

$$
\texttt{precision}_{\rm code}=\frac{I}{|G|},\qquad
\texttt{recall}_{\rm code}=\frac{I}{|P|}.
$$

这与通常把 precision 定义为交集占预测面积、recall 定义为交集占参考面积的用法相反。本页保留原论文表头，但不按通常词义解释这两列。代码对各样本分别计算这些比例，再取平均；没有输出三项合成的总分。[评分函数](https://github.com/uivision/UI-Vision/blob/2b79355f962a2db1402ce0ad3d261aa9cb74b855/eval/grounding/eval_uivision.py)。

本次只抽取纯评分函数做了一个无模型检验：参考框 `[0,0,10,10]` 完全包含在预测框 `[0,0,20,20]` 中，返回 IoU=0.25、`precision`=1、`recall`=0.25。这验证了公开函数的分母，不能证明论文发布时每一行原始结果都由同一代码版本生成。

### 动作预测：类型与参数要一起正确

原始数据记录十类事件。为统一模型输出，作者去掉含独立按下键、松开键及滚动事件的任务，将可用任务整理为移动、点击、拖动、输入文字和快捷键五类。点击前重复的移动被去掉，拖动所需的移动起点、按下、拖动和释放合并，单键按压也归入快捷键。（表 2、表 7、附录 B.3）

模型的预测形式可以写成：

$$
\hat a_i=f_\theta(Q,I_i,a_1,\ldots,a_{i-1}),
$$

其中 $Q$ 是任务目标，$I_i$ 是第 $i$ 步截图，历史动作来自参考示范。这个式子表达推理输入，不是论文提出的训练目标。

点击或移动的距离误差为 $D/L$：$D$ 是预测点与参考点的欧氏距离，$L$ 是用于归一化的到屏幕角点的最大可能距离，越小越好。拖动同时评价起点和终点：

$$
\operatorname{Dist}_{\rm drag}
=\frac12\left(\frac{\Delta_s}{L_s}+\frac{\Delta_e}{L_e}\right).
$$

$\Delta_s,\Delta_e$ 分别为两个端点的距离误差，$L_s,L_e$ 为对应归一化量。Recall@d 要求点击位置在参考点的 $d$ 像素范围内；拖动则要求起点、终点都满足。论文称 $d$ 来自数据集的平均框大小，但没有给出足以唯一还原的像素数和宽高转换规则。公开动作评分实现尚未发布，本文不补造一个阈值。（§4.2）

文字输入和快捷键按字符串或按键匹配判断。单步成功率 SSR 则汇总动作类型及其参数都正确的步骤。它会受不同动作类型在数据中的占比影响，而且只对照单条人类示范。不同但有效的操作路径、等价快捷键或点击位置，未必会得到相同评价。

## 主要结果按三张表阅读

### 元素定位：空间关系仍然困难

以下均为百分比，最后一列是三种设置准确率的平均，不是在线工作完成率。（表 3）

| 模型 | 基础 | 功能 | 空间 | 三项平均 |
| --- | ---: | ---: | ---: | ---: |
| GPT-4o | 1.58 | 1.52 | 1.03 | 1.38 |
| Claude-3.7-Sonnet | 9.48 | 7.73 | 7.60 | 8.27 |
| MiniCPM-V-8B | 7.11 | 5.30 | 1.45 | 4.34 |
| UGround-v1-7B | 15.4 | 17.1 | 6.25 | 12.9 |
| UI-TARS-7B | 20.1 | 24.3 | 8.37 | 17.6 |
| UGround-v1-72B | 27.9 | 26.7 | 14.9 | 23.2 |
| UI-TARS-72B | 31.4 | 30.5 | 14.7 | 25.5 |

UI-TARS-72B 基础查询比空间查询高 16.7 个百分点。UGround-v1-72B 在空间查询略高，为 14.9%；整体最佳并不意味着每个子任务都最佳。UI-TARS 的 7B 与 72B 版本分别为 17.6 和 25.5，说明这些已发布模型存在规模相关的表现差异，但训练数据、训练过程等没有被控制为完全相同，不能当作纯参数量消融。

图 5 按目标面积和界面元素数量分组：较大元素更容易定位，元素密集的截图较难。正文给创作类界面平均约 112 个框、元素面积约 418 平方像素，娱乐类为 62.8 个框和 875 平方像素。这些是相关性分析，不能分离控件尺寸、软件知识、截图布局和任务内容各自的影响。

### 布局定位：另一组模型表现更好

表 4 只测试能够输出框的模型，因此不能把未列出的 UI-TARS 视为得分为零。

| 模型 | IoU ×100 | 原表 Precision | 原表 Recall |
| --- | ---: | ---: | ---: |
| GPT-4o | 20.0 | 59.6 | 24.1 |
| Claude-3.7-Sonnet | 17.6 | 31.5 | 34.1 |
| Gemini-1.5-pro | 30.8 | 67.8 | 36.9 |
| Qwen-2VL-7B | 24.3 | 65.7 | 33.4 |
| OSAtlas-7B | 28.2 | 66.4 | 41.6 |
| CogAgent-9B | 6.22 | 7.99 | 42.9 |

Gemini-1.5-pro 的 IoU 最高，达到 30.8；擅长小控件定位的专用模型没有自动在区域理解上领先。作者认为训练目标及通用视觉理解可能解释差异，但没有提供同一基础模型上只改变训练任务的受控实验。

### 动作预测：拖动比点击更难

以下保持表 5 的百分比口径。这里只列正确率与 SSR；距离误差是另一类越低越好的指标，不能混为准确率。

| 模型 | 点击/移动 Recall@d | 拖动 Recall@d | 输入文字正确率 | 快捷键正确率 | SSR |
| --- | ---: | ---: | ---: | ---: | ---: |
| GPT-4o，不看图 | 3.3 | 0.0 | 22.7 | 34.0 | 7.64 |
| GPT-4o | 4.4 | 1.5 | 32.1 | 56.5 | 11.5 |
| Gemini-1.5-Pro | 13.0 | 1.6 | 24.7 | 45.3 | 16.0 |
| Claude-3.5-Sonnet | 4.8 | 1.1 | 29.0 | 39.2 | 9.9 |
| ShowUI-2B | 11.8 | 未报告 | 15.2 | 62.5 | 15.7 |
| UI-TARS-7B | 19.7 | 3.1 | 33.8 | 40.5 | 21.4 |

UI-TARS-7B 的点击/移动召回率最高，但拖动只有 3.1%。ShowUI 无法按要求产生拖动动作，因此表中为 N/A，不能写成没有测试就证明拖动能力为零。论文还观察到 UI-TARS 偶尔输出未定义的 `wait()` 或 `finish()`，说明动作格式适配也会影响结果。（§4.3）

GPT-4o 去掉截图后 SSR 为 7.64，加入截图为 11.5，提高 3.86 个百分点。无图模型仍能预测一部分文字和快捷键，因为目标或历史可能已提供要输入的内容。这个对照检验了截图的作用；“任务和历史”对随机基线的优势不能进一步拆成历史信息单独带来的收益，因为没有保持其他条件相同的无历史对照。

各主表没有报告跨随机种子的重复次数、置信区间或显著性检验。相近分数应作为该评测设置下的点估计阅读。

## 将规划与坐标预测分开

作者让通用模型只给出“点击哪个元素”的文字动作，再由 UGround-v1 负责找坐标。点击召回率变为 GPT-4o 26.7%、Claude 26.9%、Gemini 25.0%，高于直接预测坐标的 4.4%、4.8%、13.0%。（§4.3；图 24 指明其组合使用 UGround-v1-7B）

这是两个模块串联后的结果，表明在这些设置中更换定位模块能够明显改善点击预测。它没有单独测出“规划已经完全正确”，也没有证明收益完全来自规划：对比同时改变了输出格式、定位模型和调用流程。正文“2–5 倍”的概括与逐项除法不完全一致，按所列数字，GPT-4o 约为 6.1 倍、Claude 约 5.6 倍、Gemini 约 1.9 倍，因此这里直接保留前后分数。

附录 E.4 进一步按领域报告错误率下降。正文称生产力约 26%、创作约 14%；图 24 的条形末端约为 26.7% 和 15.9%，未提供原始数表及完整分母说明。它可以支持“生产力领域改善较多、创作领域较少”的观察，但不适合再算精确的额外提升。文章不将这张图替换为完整任务成功率。

## 泛化、分辨率与失败样例

附录 E.2 用常见软件与较少见的软件子集比较，作为泛化能力的近似分析。例如，UI-TARS-72B 基础定位在常见软件上为 34.6%，少见软件上为 20.8%，下降 13.8 个百分点，按常见软件分数为基准的相对下降约为 39.9%。两个子集分别有 205 和 173 个基础样本，并非全部 1,772 题。（表 8）

作者不知道全部模型的训练数据，所以“少见”不能等同于“训练中从未出现”。这些子集也没有匹配目标面积、元素密度及任务难度。表 8 的空间查询还存在少见软件分数更高的个别模型，如 Claude-3.5-Sonnet 为 1.73% 对 2.56%；不宜将正文“所有模型下降”扩展为每一列都成立。

附录 E.1 按截图总面积分桶，没有看到明确的单调趋势。这并不是把同一截图缩放后做控制实验，无法据此断言分辨率或放大操作没有作用。论文建议的逐步放大、查阅软件文档和多路径参考答案，均属于后续方向，而非本文验证有效的新增方法。

图 14–22 展示的错误可以沿具体操作理解：

- LibreOffice 的相似工具图标排列在一起，模型靠近正确区域却点中相邻选项。
- “Fontwork”一类专业功能需要知道图标含义，单凭字母形状不够。
- 布局模型有时把标题栏当菜单栏，或在查询要求整个工具区域时只选择带有相似文字的单个入口。
- Qt Creator 的例子里，模型说要打开 Analyzer，却给出侧边其他位置的坐标；另一个例子则点中模态对话框后方、当前不可操作的 Manage 按钮。

这些是作者选择的失败案例，不是经过独立标注、给出各类占比的完整错误统计。图 17 的桌面截图实际是 macOS 风格窗口，而正文写作 iOS；它说明跨系统窗口位置可能被混淆，不应介绍成手机界面实验。

## 公开实现与复现条件

本次核对的[代码提交](https://github.com/uivision/UI-Vision/tree/2b79355f962a2db1402ce0ad3d261aa9cb74b855)为 `2b79355f962a2db1402ce0ad3d261aa9cb74b855`。已检查主评测程序、模型构建分支、UI-TARS 与通用 API 适配器、Qwen2-VL 的主要处理流程、示例命令，以及四份公开标注。没有运行模型评测，也没有下载模型权重。

### 当前开放的范围

官方数据仓库公开元素与布局的 JSON 和图片；数据卡标为 MIT。动作目录只有“Coming soon...”说明，没有可执行的动作评测程序，也没有论文中 442 条任务轨迹及原始录屏的完整公开包。数据采集工具、难例筛选的全部实现及原始模型预测日志也未在本次核对范围中找到。[数据卡](https://huggingface.co/datasets/ServiceNow/ui-vision/blob/766c66aeffef16608d4916525902d9fb2598d7ce/README.md)、[动作评测目录](https://github.com/uivision/UI-Vision/tree/2b79355f962a2db1402ce0ad3d261aa9cb74b855/eval/action_prediction)。

因此，目前可以按公开入口开展元素和布局评测；完整重现动作表 5、规划与定位组合实验，还需要作者补充数据和实现。数据卡许可也不应被改写成所有被展示的软件、界面资源和操作系统都使用同一种许可证。

### 入口与坐标约定

`eval/grounding/eval_uivision.py` 接受模型类型、图片根目录、标注 JSON、任务类型和输出路径。下面依据公开文件结构整理一条元素定位命令，尚未执行：

```bash
python eval_uivision.py \
  --model_type uitars \
  --uivision_imgs /path/to/ui-vision/images \
  --uivision_test_file /path/to/ui-vision/annotations/element_grounding/element_grounding_basic.json \
  --task element \
  --log_path /path/to/results/basic.json
```

需先进入代码的 `eval/grounding` 目录，并创建结果目录。JSON 的 `image_path` 已包含 `element_grounding/` 或 `layout_grounding/`，图片根目录应该指到 `images`，否则会重复拼接路径。

UI-TARS 默认加载 `bytedance-research/UI-TARS-7B-DPO`；72B 分支加载对应的 `72B-DPO`。其适配器按 0–1000 坐标解析，再除以 1000 交给统一评分器。Qwen2-VL 的框坐标也经过归一化；通用 API 提示则直接要求 0–1。复现时应连同提示和解析规则一起固定，不能只记录模型名。

### 预算、异常与硬件

主程序设置 `temperature=0`、`max_new_tokens=256`，但实际输出预算由适配器继续决定：UI-TARS 的调用显式使用 `max_new_tokens=128`，通用 API 分支使用 `max_tokens=2048`。因此不能根据主程序一行设置声称所有模型都获得相同输出长度。

通用 GPT/Gemini 适配器调用 OpenRouter，并从名为 `OPENAI_API_KEY` 的环境变量取凭证；其路由和错误提示的变量名称并不完全一致。脚本还写死了 Hugging Face 缓存路径。运行前需要检查这些配置、模型版本及依赖，不能直接将现有账户的密钥按变量名猜测填入。模型权重没有固定 revision，仓库也没有覆盖整个评测环境的统一依赖锁文件。

格式错误会影响分数。主评分器将缺失坐标计作 `wrong_format`，并保留在准确率分母中；UI-TARS 适配器解析失败却回退到 `(0,0)`，会进入普通坐标评分。因此 `wrong_format` 不能代表所有模型的完整格式失败率。布局中的缺失或非法预测框按零重叠处理。

附录表 9–11 给出部分资源统计：基础元素定位时 UI-TARS-7B 平均 4.97 秒/查询、使用 2 张 H100，72B 为 12.1 秒、4 张 H100；动作任务中的 UI-TARS-7B 为 1.7 秒、1 张 H100。不同任务和实现配置不能混为单一模型的固定延迟。输出 token 用 GPT-4 tokenizer 统一计数，未必等于各服务的计费 token。闭源模型没有可比较的延迟结果，论文也没有完整 API 费用和总 GPU 小时数。

本文完成的是原文、附录、数据结构与公开实现的核对，以及一个纯评分函数的数值检验。论文的模型性能、延迟及动作实验尚未复现。

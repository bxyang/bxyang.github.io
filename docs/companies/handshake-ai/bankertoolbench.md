# BankerToolBench 精读：从投行工作要求到可检查的交付文件

一份并购模型可以算出看似合理的每股收益，却仍不能用于工作：修改收购价格后，Excel 中的数字没有更新；资产负债表漏了一项少数股东权益；同一个收入指标在演示稿中出现两个版本。BankerToolBench（BTB）把这些问题纳入评测，让 agent 根据投行工作要求检索资料、建立模型，并交付 Excel、PowerPoint 等真实文件，再由能够打开文件、检查公式和调用数据工具的验证器逐项评分。论文中最高的平均加权分数为 58.1/100，但达到“接近可交付”代理阈值的比例只有 16%；二者衡量的不是同一件事。[论文 §3、§6，图 5–7](https://arxiv.org/pdf/2604.11304v1)

## 一项任务包含业务要求、资料和一整套交付标准

BTB 有 100 项初级投资银行从业者日常工作任务。每项包含三个主要部分：上级提出的工作要求、可访问的数据室文件与工具，以及不提供给执行 agent 的评分标准。任务可能要求估值、杠杆收购模型、并购增厚摊薄分析、客户推介材料或交易安排。输出必须是可以打开检查的文件，聊天里说“已经完成”不能代替交付。（§3.1）

与金融问答不同，这类任务还需要在资料之间作取舍，说明假设，把分析结果写进可修改的模型，并确保多个文件互相一致。论文将这些特点与 GDPval、APEX-Agents、FinanceAgent 等比较；其中关于既有基准覆盖不足的表 1 是作者按其任务定义进行的比较，不应扩展成其他基准完全不能评测专业工作的结论。

常见子任务包括 18 项 DCF、15 项 LBO/信贷模型、10 项可比上市公司估值分析（Trading Comparables）、8 项 pitchbook、6 项并购模型。较少出现的子类不能仅凭一两项任务建立稳定能力排名。（表 2）

## 502 名从业者分别参与了哪些环节

论文的 502 人是项目层面的合作规模，不能理解为每项任务由 502 人评分。文中分别报告：129 人参与 AI 价值调查、193 人参与岗位任务分析、8 人接受深度访谈、172 人直接参与任务制作；这些数字相加为 502。表 1 的“调查专家数”322 则是两项问卷的 129+193。论文没有提供可独立去重的人员名册，本文按其报告口径区分角色。（§4、附录 E）

岗位任务分析让从业者评估工作出现频率、所需时间、错误后果及专业技能要求，并补充遗漏的工作流程。问卷顺序随机化，参与者只评价自己实际了解的任务。作者按岗位、资历、产品组等分层招募；193 人样本中多数是曾任投行从业者，不能称为全部在职员工。

作者先通过价值调查确定重要工作，再将岗位任务分析中的频率与时长评分取平均、做 min-max 归一化并相加，按各项合成权重占总权重的比例制定任务配额。论文说明了这个过程，但没有发布足以独立重算全部配额的问卷原始记录和映射细节。它提供的是任务分布的调查依据，不是实测的行业产值权重。

直接制作数据的 172 人平均有 3.4 年投行经验，中位数 2.8 年，最低要求两年；参与工作累计超过 5,700 小时。作者、审核人需要通过知识与工作准确性考核，并接受 rubric 培训。每项任务至少经历四位专业人员参与的流程：作者创建，第二位审核并反复修订，最后两位独立接受或退回。作者还亲自完成任务，制作参考交付物，人工完成时间平均五小时、最长 21 小时。（§4.2–4.4）

Rubric 也不是直接由模型生成后使用。早期从业者彼此评审人工和 AI 文件，再形成六类要求；之后作者使用 LLM 草稿、领域模板和类别目标辅助写作，最终仍由银行从业者逐项调整和审核。每轮人工审核前有自动检查，关注重复、非原子要求及表述不清等问题。这个过程意在控制质量，但没有消除所有判断差异，也不证明公开 rubric 永远没有歧义。

## agent 在什么环境中工作

Harbor 负责隔离和启动任务，OpenCode 等 agent 框架负责多轮执行。模型可以读写文件、运行 Python 和 shell，并使用三类 MCP 数据工具：

- **市场数据室 VDR**：已加载的股价、财务、分析师预测等数据，提示模板称覆盖约 690 家美国上市公司。先发现可用数据，再下载工作簿。
- **SEC EDGAR**：查找公司 CIK、申报记录和具体 filing，不能跳过标识符解析后凭空构造下载路径。
- **公司标识资料**：搜索公司 logo，并复制图片供交付文件使用。

这不是实时连接 FactSet 或 Capital IQ 的商业账号。论文说市场数据工具提供类似能力；公开环境从本地共享数据读取文件。任务锚定历史日期，规则要求只使用输入文件和批准的 MCP 工具，不上公网查找任务资料，以降低数据随时间变化的影响。（§3.2、附录 C）

环境预装 LibreOffice 与常用文件库。特别重要的是，`openpyxl` 可以写入公式，但不计算公式值。若模型立即以 `data_only=True` 重新读文件，可能得到空值或旧缓存；任务模板明确要求先用 LibreOffice 重算，再读取计算值。修改公式后没有重算，可能使表格本身与演示稿里的数字不同。

执行工作区是 `/home/agent/workspace`，最终交付物应放在 `banker_workspace/deliverables/`。当前评分脚本先保存工作区快照，再检查这个目录：如果没有文件，直接返回 0，不调用 LLM 验证器。存在文件只是进入评分的前提，不代表内容通过。

公开容器使用不同用户隔离 agent、MCP 数据与验证器，工具会检查调用者允许的工作目录；共享工具数据以只读方式挂载。这与提示中的禁网要求是不同层次的约束。当前 compose 没有展示完整的网络封锁规则，因此本文不把“禁止公网检索的任务协议”说成已经验证的网络沙箱保证。

## 评分标准：细粒度通过项与重要性权重

每条 rubric 是二元判断，权重取 1、3、5、10，分别表示较低重要性、轻微、主要、关键要求。六类要求覆盖技术正确性、客户呈现、指令遵循、透明与可审计性、内部一致性、风险与合规。类别本身没有一个对所有任务固定的六项加权总公式；真正参与总分计算的是每条具体标准的权重。（§3.3）

本次公开数据审计得到 **15,054 条标准**，平均每项任务 150.54 条、中位数 151 条，范围 17–308 条；86 项任务超过 100 条。因此“通常超过 100 条”准确，“每项都超过 100 条”不准确。

| Rubric 类别 | 公开标准条数 |
| --- | ---: |
| 技术正确性 | 5,386 |
| 指令遵循 | 3,201 |
| 客户准备与呈现 | 2,729 |
| 透明与可审计性 | 1,908 |
| 内部一致性 | 1,357 |
| 风险与合规 | 473 |

这里是**条数分布**，不是加权分数占比。公开数据中权重 10 的标准有 2,752 条，权重 5 有 3,543 条，权重 3 有 5,666 条，权重 1 有 3,093 条。[固定数据文件](https://huggingface.co/datasets/handshake-ai-research/bankertoolbench/blob/2c63d3b6d429687d2c29550e820dd136baafee95/tasks.jsonl)

设任务 $t$ 有 $m_t$ 条标准，第 $i$ 条权重为 $w_{ti}>0$，验证器的通过判断为 $p_{ti}\in\{0,1\}$。单任务分数与全量分数为：

$$
S_t=100\frac{\sum_{i=1}^{m_t}w_{ti}p_{ti}}{\sum_{i=1}^{m_t}w_{ti}},
\qquad S=\frac{1}{100}\sum_{t=1}^{100}S_t.
$$

先在任务内部加权，再对任务取平均。不能把全部 15,054 条直接混合求比例，否则 rubric 较多或总权重更大的任务会获得额外权重。当前 Gandalf 保存的 `reward` 范围是 0–1，与论文 0–100 的 Score 相差 100 倍。

说明示例：四条标准的权重为 10、5、3、1，只失败权重 10 的关键项，则普通通过条数为 3/4，但加权分数只有 $100\times9/19=47.37$。即使其他要求很多、总分很高，一项关键错误仍可能使文件不适合交付。平均分描述的是部分完成程度，不是完整任务成功率。[论文 §5–6.1](https://arxiv.org/pdf/2604.11304v1)

## Gandalf 怎样检查文件，以及它会错在哪里

Gandalf 是运行在环境中的 agent-as-a-judge。它不仅阅读执行 agent 的说明，还能打开工作簿、检查单元格、渲染幻灯片、运行代码和重新查询数据源。只把文件序列化为文本会丢失公式、格式和可交互结构，这是作者采用工具型验证器的主要原因。（§3.4）

当前验证指导把两类标准分开：如果只要求最终数值正确，符合容差的常数可以通过；如果要求“由这些单元格计算”“链接到来源”或“可随假设更新”，则需要实际公式与引用。不能把所有硬编码都判错，因为历史数据与输入假设本来可能是常数。指导中有通用 ±1.5% 容差，而具体 rubric 也会给出 ±5% 或绝对范围；这些是给 LLM 的判断指令，并非执行器统一强制的数值单元测试。

验证器还被要求独立调用 MCP 获取参照数据，不能拿 agent 自己写入的文件当作来源证明。它输出每项的判断、理由和证据，再由程序加权。**这些判断仍然是模型判定**，不是因为能调用 Python 就全部变成确定性验证。

### 原论文的验证器验证集是 13 项任务、1,356 条标准

附录 D 选择 13 项 BTB 任务的 AI 交付物，两位从业者逐条独立标注，第三人解决分歧，形成共识标签。正类表示“标准满足”。三次重复的主要结果如下：

| 指标 | Gemini 3 Flash Preview 驱动的 Gandalf |
| --- | ---: |
| 准确率 | 88.22% ± 0.44 个百分点 |
| Precision | 0.872 ± 0.006 |
| Recall | 0.933 ± 0.004 |
| F1 | 0.901 ± 0.004 |
| 假阳性率 FPR | 18.61% ± 1.06 个百分点 |
| Cohen’s $\kappa$ | 0.756 ± 0.010 |
| 单任务平均评分费用 | \$0.495 ± \$0.026 |

FPR 的分母是人工认为未满足的标准，分子是其中被验证器误判为满足的标准。因此 18.61% 不能说成所有交付物的错误率，也不能被 88.22% 的总准确率掩盖。分类型看，指令遵循的 FPR 为 39.6%，风险与合规的准确率为 96.9%，但后者只有 11 条标准，不足以说明所有合规要求都容易判断。（表 A7、A9）

两位人工标注者彼此一致率为 84.6%，$\kappa=0.692$；两人与最终共识的 $\kappa$ 分别为 0.815、0.717。论文所说的“在人类一致性范围内”，包含了人工彼此比较和人工对裁决共识这两种口径。验证器与共识一致率更高，不能等同于在盲测中普遍胜过专家。（表 A8）

换用 Gemini 3 Pro Preview 时准确率为 86.5%、约每任务 \$2.03、957 秒；Claude Sonnet 4.6 为 89.5%、\$2.72、950 秒；Flash 为 88.2%、约 \$0.50、406 秒。选 Flash 是这个小集合上的成本与质量折中，不是所有金融评分场景的最优性证明。（表 A10）

### BankerVerifierBench 是另一个评测层次

BTB 测的是执行 agent 交付投行工作的能力；[BankerVerifierBench](/companies/handshake-ai/bankerverifierbench)（BVB）研究的是验证器能否正确评判已有 agent 交付物。后续官方 Gandalf 介绍给出的 BVB 是 **21 项 BTB 任务、3,204 条人工判断**，不能用来替换本文附录 D 的 13 项、1,356 条分母，也不能把两套 F1、费用直接混成同一实验。[官方 Gandalf 研究介绍](https://joinhandshake.com/research/ai/gandalf-the-grader/)

## 两个实际案例：算出数字、建立模型和满足标准的区别

### RTX 收购 General Dynamics 的增厚摊薄模型

附录 G.1 要求建立一个 Excel 并购模型，以 RTX 为收购方、General Dynamics 为标的。初始假设包括相对指定日期股价溢价 20%、60% 对价使用新股、40% 使用现金，以及税务结构、目标债务处理、GAAP/现金口径三个切换项。还要构造 5×5 敏感性表，考察股票支付比例与收购溢价的变化。

增厚摊薄分析的基本关系可写为：

$$
\mathrm{EPS}_{\mathrm{pro\ forma}}
=\frac{\mathrm{NI}_{\mathrm{acquirer}}+\mathrm{NI}_{\mathrm{target}}+
\mathrm{after\ tax\ adjustments}}{\mathrm{existing\ shares}+\mathrm{new\ shares}},
$$

$$
\mathrm{Accretion\%}=
\frac{\mathrm{EPS}_{\mathrm{pro\ forma}}}{\mathrm{EPS}_{\mathrm{standalone}}}-1.
$$

这是帮助理解任务的简化公式；实际调整包括利息、现金收益损失、协同、折旧摊销和融资费等，取决于指定情景。关键不只在算出一个百分比，还在改变支付结构后这些关联单元格能正确重算。

论文所示 GPT-5.4 交付物得 54/100。在 167 条 rubric 中，附录展示三条：资产为 162,861 百万美元、负债加权益为 161,059，差额 1,802 对应漏掉的少数股东权益，该关键项失败；总用途 119,332.1 位于目标 $122,625.8\pm6,130$ 百万美元范围内，该项通过；另一公式要求因出现硬编码而失败。这三项仅是案例片段，不能用其一过两失反推总分。（PDF 第 46–48 页）

本次下载同一任务的公开人工参考工作簿，确认其包含 192 个公式单元格；这说明参考模型确有表内逻辑，但不代表独立验证了其中每个公式，也不是重新检查论文中的 GPT-5.4 输出。

### Uber DCF：正确的折现期不足以保证估值正确

附录 G.2 要求用 2023、2024 历史数据预测 2025–2031 年，WACC 为 12%，采用年中折现及 15 倍 EBITDA 退出倍数。自由现金流的当前价值为：

$$
PV(FCF_y)=\frac{FCF_y}{(1+0.12)^{y-2025+0.5}}.
$$

本次读取的公开人工参考文件中，`DCF!E85` 是 `=1/(1+E83)^(E84)`，缓存值约 0.944911；`E86` 将该因子乘以该年自由现金流。终端价值与预测期现金流再汇总到 `C107`，缓存企业价值约 84,508.49659 百万美元，与论文 84,508.50 的目标吻合。本文只是静态读取公式和已保存缓存，没有重新运行 LibreOffice 或核查全部原始财务数据。

论文中 Claude Opus 4.6 的结果为 44/100：折现期 0.5、1.5、…、6.5 这一项通过，但工作簿没有实际 Excel 公式，企业价值为 174,712 百万美元，另两项失败。公开任务仍有 158 条 rubric，与附录一致。可读的表格和部分正确步骤，并不足以证明最终模型可用。[附录 G.2，第 49–51 页](https://arxiv.org/pdf/2604.11304v1)

### 80 分阈值来自人工标签拟合

21 位从业者对 GPT-5.4 或 Opus 4.6 的交付物提供了 172 次人工评价，判断距离可向 VP/MD 提交还有多远。五级从完全不可用到可直接发送。没有评价落在“可直接发送”，约 13% 需要轻微修改、19% 中等修改、41% 大幅返工、27% 不可用；另一个问题中约 69% 的评价愿意从 AI 输出继续修改，而非从头开始。这两个回答并不矛盾：可以作为起点与可以直接交付是不同要求。（附录 A.4、图 A2）

作者将四级或五级标为“可接受”，选择一个 rubric 分数阈值，使以下相对风险最大：

$$
RR(T)=\frac{\Pr(\text{人工可接受}\mid S\ge T)}
{\Pr(\text{人工可接受}\mid S<T)}.
$$

附录用 0–1 的分数写阈值 0.8，对应主文的 **80/100**。得到 $RR=3.35$，人工之间类似比较为 3.68。3.35 是条件概率之比，不是分类准确率或“80 分以上有 3.35 倍成功率”的无条件保证。阈值在这批人工数据上选择，论文没有提供独立留出校准集；它是近似映射，不是每个达到 80 分的文件都经专家认可。

因此，主表中的 Pass@1 是三次运行各自越过这个阈值的比例再取平均；Pass@3 是三次中至少一次通过的任务比例；GPT-5.4 三次都通过的比例另记为 Pass³，只有 13%。Pass@3 高于 Pass@1 表明多次尝试存在更好样本，并不自动提供一个能无误挑出好样本的部署方法。

关键项全通过又是另一标准：GPT-5.4 为 2%、Gemini 2.5 Pro 为 0%，其余模型为 1%。没有关键项失败也不代表全部呈现与业务要求满足。本文不把这组比例、80 分阈值和人工零直接交付率混用，也不把 172 次人工评价扩写成全九模型、全部运行都经过人工客户审查。（§6.1）

附录 A.5 另做了盲法两两比较，检验总分更高的文件是否也被人工偏好。GPT-5.4 与 Grok 4 的 48 组比较中，排除人工平局后的总体偏好一致率为 97.8%；GPT-5.4 与 Opus 4.6 的 30 组比较中为 75.9%，格式偏好的一致率只有 51.7%，准确性则为 82.6%。这些是**评分排序与人工偏好的对齐率**，不是某个模型的获胜率；各问题排除平局后分母也可能不同。它们支持总分能区分部分质量差异，同时表明接近模型的呈现偏好较难由总分概括。（表 A6）

## 失败分析与任务差异

图 7 中，GPT-5.4 的技术正确性约 57、内部一致性 66、透明可审计性 53；Opus 4.6 在客户呈现约 63、风险合规约 46 上领先。客户呈现这一**rubric 子分数**不是人工直接交付率。看起来整齐的文件仍可能包含错误或缺少公式。

作者对 GPT-5.4 的失败轨迹用 LLM 找出最早明确错误，人工参与聚类，再由 LLM 归入类别。报告的四类占比为代码与公式生成 41%、推理逻辑 27%、检索与持续尝试 18%、来源依据与编造 13%。这是被编码失败的构成，不能说成全部任务分别有这些失败概率；合计约 99% 也体现了百分数取整。（附录 B.1）

附录案例展示了具体机制：调用不存在的 `python-pptx` 属性后，agent 删除出错行而没有完成原格式要求；定义了写公式辅助函数却始终只写静态数值；重复失败的 SEC 请求而忽略可用文档查询提示；在没有取得原始材料后继续填入具体临床数据。最后一类属于论文判断的无来源编造案例，不是对这些现实医学数值的独立核实。

工具报错率的分母不同：附录 A.2 按执行过的工具调用计算异常、非零退出码或 `success:false` 的占比。终端调用为 11.0%，SEC 为 5.2%，文件操作为 0.3%；按模型整体计算，GPT-5.4 为 2.3%，Gemini 2.5 Pro 为 12.0%。一次调用失败可以被后续恢复，因而工具报错率不等于最终任务失败率。

表 3 跨模型平均分中，客户营销材料为 50.7，财务建模与情景分析为 44.8；并购模型子类为 35.2，资本结构表为 34.4。样本数分别只有 6 项和 3 项。附录 A2–A5 又按输出格式、输入格式、产品组细分：DCM 只有 6 项，Word 输出只有 1 项，不能把这些切片的点估计当成整个专业领域的稳定顺序。多文件任务还会同时出现在多个格式切片中，切片对比不是只改变文件格式的因果实验。

## 小模型后训练：冻结轨迹上的可行性实验

BTB 除了评测，还用 Qwen 3 4B 与 32B 做了一项奖励可学习性实验。它与九个前沿模型的主榜不同：通过 OpenHands 采样，每个模型在 100 项任务上各收集 16 条轨迹，共 1,600 条，温度 1.0；按任务随机划分 80 项训练、20 项保留评测，随后使用**冻结轨迹池**离线训练。它不是每次更新后持续重新采样的在线 RL。（§6.6、附录 B.3）

唯一奖励来自加权 rubric 分数。两个模型的样本池中超过一半轨迹奖励为零，85% 以上低于 0.1。Dr. GRPO 排除奖励没有差异的任务，4B 剩 60 项、32B 剩 72 项；每项原有 16 条，分别对应最多 960、1,152 条保留训练轨迹。DPO 在同一任务中选最高分作为 chosen、最低分作为 rejected；多个最低零分并列时构造多个配对，没有严格奖励顺序的任务也排除。

原文没有展开 Dr. GRPO 的具体损失、裁剪系数或离线重要性比率实现，也未公开完整训练脚本，因此不能补上一份通用 GRPO 公式就宣称还原了这一实验。DPO 的关键已知信息是上述配对规则；学习率、优化器、参考策略、长轨迹 token 掩码和精确模型 checkpoint 等仍不足以独立重现。

表 5 报告的是 20 项保留任务上的 0–1 平均奖励：

| 方法 | Qwen 3 4B | Qwen 3 32B |
| --- | ---: | ---: |
| 未后训练 | 0.01 | 0.03 |
| Dr. GRPO | 0.13 | 0.12 |
| DPO | 0.11 | 0.14 |

按表面四舍五入值，4B 的 Dr. GRPO 从 0.01 到 0.13 是增加 0.12、达到 13 倍，但绝对分数仍低。表中 4B DPO 另注“+0.11、12 倍”，与显示的 0.01→0.11 不能直接重算一致；32B 的 0.03→0.14 也只近似 5 倍。缺少未舍入数值，本文保留均值，不用括号倍率进一步推导结果。

图 A3 比较 4B 的批大小 128、256、512 与全量 960，较大的批次有更高的部分评测点，但曲线仍有明显波动，且只画到 step 10。正文提到对离线池训练 20 遍，图不能单独证明完整 20 遍的最终成绩或无过拟合。没有独立重复误差或明确 checkpoint 选择规则时，“大批量更稳定”应限定为作者对这组实验的解释。

轨迹生成分别约需一台 8×H100 节点 35 和 177 小时；作者估算 20 遍参数更新约 13.0 和 143.6 EFLOPs，并将其换算为峰值计算下不到六小时的量级。这种峰值等效估算不是端到端实测耗时。环境执行、文件 I/O 和验证等待是采样成本的重要部分。

作者检查后训练轨迹时未发现奖励投机，并观察到更频繁工具调用；这不是覆盖所有策略的安全保证。论文同时明确要求不要用公开基准训练参与常规榜单比较的模型。这里的 80/20 划分服务于奖励可学习性研究，不能把训练后的成绩当成完全未见过 BTB 的通用能力评测。

## 当前公开实现的复现边界

这份代码比只发布任务说明的基准更完整，但仍需记录具体快照与运行选择。

**数据。** 当前下载器支持 `BTB_HF_REVISION`，默认却是 `main`。应固定为本页记录的提交。`tasks.jsonl` 有 100 个唯一任务 ID，包含业务标签、提示上下文与序列化 rubric；全部任务还带有 canary 字段，用于识别基准内容，本文不复制标记文本。公开 canary 与附录 A.6 所述私人扩展任务是降低污染和检测过拟合的安排，不等于已证明主榜模型没有见过公开题目。

**评分。** 当前适配器把标准按位置分成两批、并发 2，各批验证后恢复原顺序。默认 agent 超时 3,000 秒，Harbor verifier 1,800 秒，单项 judge 基础超时 300 秒；分批上限采用总验证超时减 60 秒，即默认 1,740 秒。这些是当前软件默认值，不能据此补出论文所有历史运行的真实预算。

Gandalf 对判断为 `True` 的权重求和，除以全部正权重并截断到 0–1；BTB 所有权重为正，因此与前文公式一致。基础设施错误使用 `met=None`，不是普通的“不满足”。重试后若仍有错误，程序写诊断 `info.json`，但不生成正常的 `reward.json` 并失败退出。统计时不能把这类未完成评分默默等同为有效零分，或忽略后改变分母。

**依赖。** 容器锁定 Gandalf 1.0.0，并有部分依赖锁文件，但仍包含 `opencode-ai@latest`、uv 的 `latest` 镜像和未完全锁定的系统包。只固定 BTB Git 提交，还不能保证未来构建出字节级相同环境。当前 `job.yaml` 另设 OpenCode 最大输出 token 的环境变量，但没有显式设置 GPT 的 high reasoning 参数，复现原论文需另核实 Harbor/OpenCode 的实际配置，不能把示例文件原样运行就称为等价实验。

在已经准备好资源和 API 的环境里，官方运行入口是先执行 `python -m adapters.btb.run_adapter` 生成任务目录，再执行 `harbor run -c job.yaml`。一旦真正运行，这会触发任务 agent 和验证器两部分模型调用。本文只静态检查入口，没有执行它们。官方烟雾测试的 1.0 是小型安装与评分连通性预期，不是模型在完整投行任务上的预期成绩。[固定代码与使用说明](https://github.com/Handshake-AI-Research/bankertoolbench/tree/ff6db552a44632643df20393065056e5f1f0092c)

本次实际下载的是全部任务 rubric、数据卡和两份参考 Excel，没有下载约 2 GB 的共享工具压缩包、全部输入文件或九模型的原始轨迹。因此可以独立确认任务数量、类别、权重、案例公式及评分程序，不能声称已经验证全部 SEC/市场数据的历史日期截断、人工参考答案或复算每项模型分数。

## 结果适用于什么范围

BTB 测量的是标准化数据环境中的个人投行工作流程，主要覆盖美国场景。它没有完整模拟团队协作、主管逐轮反馈、内部模板与交易档案，也刻意排除个人身份与机密交易信息。固定资料有利于比较，但真实交易中不完整、矛盾和不断变化的信息更复杂。（§7）

人工完成时间、主观付费意愿与 rubric 分数说明了任务价值和难度，却不是实际替代员工、节省工时或增加收入的因果估计。验证器准确率也只在特定样本上成立。读懂这一基准，需要同时看标准满足程度、关键项、阈值通过率、重复执行可靠性与人工反馈，而不能只选一个百分数代表“会不会做投行工作”。

# Gandalf：让验证器进入 agent 的工作环境

一个投行 agent 交付了电子表格和演示文稿，最后回复“模型已完成，数据已核对”。验证器需要检查的却是另一组事实：公式是否引用了正确的工作表，图表和财务模型是否一致，披露文字是否完整。Gandalf 让验证器自己打开文件、运行检查并查询工具状态，再逐条判断评分标准。论文同时构建 BankerVerifierBench（BVB），用 21 项任务中的 3,204 条专家判断评估验证器。在主要 BVB 对照中，Gandalf 的低成本配置取得 0.633 F1、全套评分成本 42 美元；Archipelago 的 GPT-5.4 配置为 0.538 F1、414 美元。这里的 F1 衡量发现“不满足标准”的能力，费用只对应论文记录的模型调用和价格。（原文 §1–7、图 1）

## 验证器需要看到的证据

论文把研究对象限定为自然语言评分标准下的 agent 工作环境。任务提供资料、工具和指令；agent 产生文件，也可能改变外部工具状态；验证器对每条标准输出 `met` 或 `unmet`。一些标准可以直接写脚本检查，另一些还需要结合源文件、布局、领域惯例或多步操作判断。（§2）

以一个**说明示例**区分取证方式：标准要求演示文稿里的企业价值来自工作簿的计算结果。只阅读最终回复无法判断；阅读幻灯片截图能看见一个数字，但未必能确认引用关系；查看原生文件后，验证器才能继续追踪单元格、公式和来源。这个示例说明所需证据，不是论文公布的一条任务轨迹。

论文的三个主要基线分别保留了不同证据：

| 验证器 | 本文采用的评测方式 | 取证范围 |
| --- | --- | --- |
| AutoRubric | 每条标准独立调用语言模型 | agent 的文字轨迹，不直接访问交付文件 |
| Archipelago | 将文件变化和 Reducto 提取的视觉内容序列化，再逐项评分 | 预先生成的内容快照 |
| Agent-as-a-Judge（AAAJ） | 按工作流规划、定位和读取文件 | 自带文件检查工具 |
| Gandalf | 根据已有证据选择下一步检查 | 工作文件、命令、原任务工具及运行时领域指导 |

这些描述是论文实验中的配置，不代表相关项目所有版本的能力。跨系统对比同时改变多项设计，不能单凭这张表把全部差距归因于某一个模块。

## BVB：21 条任务轨迹与 3,204 条判断

BVB 从 BankerToolBench 的任务分布中选取 21 项投行业务任务，包括现金流折现、杠杆收购、可比公司分析及并购。作为背景，BankerToolBench 有 100 项任务，专家完成每项任务平均约需 5 小时；这些数字不是 BVB 的任务数或标注耗时。（§2–3）

BVB 中每项任务只有**一条 agent 执行轨迹**，配套完整消息、工具调用与返回值，以及包含原生交付文件的最终环境状态。每项任务有 47–286 条评分标准，中位数 160，合计 3,204 条。标准带重要性权重和六类原始类别；后文九类验证能力是重新归纳的分类，不是这六类的另一个写法。

| 标注部分 | 任务数 | 标准数 | 人工流程 |
| --- | ---: | ---: | --- |
| 初始部分 | 6 | 493 | 两位审核者独立判断，再由资深审核者给出最终裁定 |
| 其余部分 | 15 | 2,711 | 一位审核者判断，加资深审核者最终裁定 |
| 合计 | 21 | 3,204 | 每条标准有二元专家标签 |

论文报告前一部分标注者一致率为 89.5%，不能解释为全部 3,204 条都经过双人独立标注，也不能解释为验证器达到人类准确率。原文没有给出该一致率的详细计算代码或混淆矩阵，没有说明它是经过机会校正的统计量。全体标签中 `met` 占 78.7%，因此类别明显不平衡。

这里的独立任务规模仍然是 21。一个工作簿的问题可能同时影响许多评分项，不能把 3,204 条标准视为 3,204 个互不相关的任务。论文没有报告任务级 bootstrap、重复运行置信区间或显著性检验；后面的百分点差异应按报告结果理解。

## 从评分标准归纳九类检查能力

作者先分析验证器需要完成哪些检查，再据此组织系统设计。输入是任务指令及评分标准，而不是各验证器的错误结果。整个流程使用 Gemini 3 Flash；标签嵌入使用 `text-embedding-005`。（§4、附录 A，PDF 第 12–18 页）

**第一步是自由生成标签。** 模型为每条标准提出 1–3 个能力名称，并给出与标准具体内容对应的理由。提示要求名称描述“验证器检查什么”，不描述 agent 应当如何制作产物；名称不能包含 Excel、Python、MCP 等工具或格式词。机器可检查的格式包括 4–8 个下划线分隔词、以 `_capability` 结尾，理由必须以固定短语开头。

**第二步是聚类和归并。** 对去重后的标签做嵌入，以凝聚聚类形成 80 个小簇。模型给每簇写出标准名称、定义、识别信号、例子和容易混淆的反例，再合并成 8–10 类。最终合并提示还规定：单类不超过全体的 40%，不足 2% 的小类并入相邻类别，每个输入类别必须有去向。

**第三步是重新标注。** 模型只能从最终词表选择 1–3 个标签，按相关性排序。能力分组实验使用第一标签，让每条标准只进入一个分组。正文称按置信度排序，实际提示要求“最相关优先”，没有输出数值置信度。故第一标签是一种模型给出的主类别，不是经过校准的概率判断。

| 验证能力 | 原文例子或检查对象 | 标准数 | 占比 |
| --- | --- | ---: | ---: |
| 重算数量指标 | 从输入重算 EV/EBITDA、交易费用等 | 736 | 23.0% |
| 核对直接数据 | 文件中的常量与题目或来源是否一致 | 497 | 15.5% |
| 追踪跨组件关联 | 工作表、页签、文件之间的数值引用 | 478 | 14.9% |
| 检查组成部分 | 必需章节、文件和列是否存在 | 388 | 12.1% |
| 检查视觉呈现 | 字体、颜色、对齐、布局与品牌规范 | 373 | 11.6% |
| 核对会计逻辑 | 符号、恒等式、项目完整性 | 244 | 7.6% |
| 核对标签与元数据 | 页签名、轴标题、表头 | 207 | 6.5% |
| 检查披露与论述 | 必需披露、定性结论与分析是否一致 | 174 | 5.4% |
| 检查时间顺序 | 期间对齐、先后次序和阶段边界 | 107 | 3.3% |

数量来自表 3，占比来自表 1；九组数量合计 3,204，显示百分比因四舍五入合计略有差异。附录公开了四组完整提示，但没有给出聚类距离、连接方式、随机性控制和标签审核的一整套可执行流水线。九类是这种设计约束下得到的分类，不是对所有工作环境已经验证的唯一分类。

## Gandalf 的执行过程

三项设计原则贯穿实现。（§5–6）

**P1：根据证据继续检查。** 验证器先看标准，再选择要打开的文件和调用的工具。一次检查发现新的引用，就继续追踪；达到足够判断依据后输出结论。这种反应式执行由 OpenHands SDK 承载，不需要预先为每一种标准写固定检查顺序。

**P2：对齐工作环境。** 验证器能访问原任务的文件、库与领域工具，包括 MCP 服务。目标是保留文件内部结构和工具状态，而不仅是将结果转成文字。当前公开代码会为每个评分会话复制工作目录，具体实现与论文笼统的“同一环境”需要分开理解，后文说明。

**P3：提供领域指导。** 会计符号、披露规范等以自然语言指导传入，不硬编码进验证器架构。原文将这视为可迁移的接口；更换领域仍然需要准备适用的指导和工具，并非不需要任何适配。

此外，Gandalf 一次可以检查多个评分项。这里的批大小 $b$ 指**一个验证会话共同判断的标准数量**，不是采样多少份答案。多条标准可能检查同一文件，批处理可以复用打开文件和查询工具的过程。

按当前公开实现，一次运行可整理为：

1. 读取任务指令、评分标准、领域指导和执行轨迹路径。
2. 从 ATIF 轨迹取最后一个有正文且不包含工具调用的 agent 消息，作为最终回复上下文；并不自动把整条轨迹全部放进提示。
3. 为单项或一批标准启动 OpenHands 会话，开放终端、文件编辑器和配置的 MCP 工具。评分提示作为首条用户消息发送，OpenHands 自身系统提示没有被替换。
4. 模型检查文件和状态，将每项 `met`、理由与证据写入指定 JSON 文件。只在回复里打印判断不算成功。
5. 外层程序检查结果、处理基础设施错误，最后计算任务奖励并写出日志。

权重不发送给内部 judge。判定的是“标准描述的条件是否在事实上发生”，而非条件是否值得奖励。例如负权重标准描述一种不希望发生的行为，行为发生时仍应输出 `met=true`，再由外层扣分。[固定源码](https://github.com/Handshake-AI-Research/gandalf-the-grader/tree/a79dccdd1fab4e791438c3c600130da4dfef8389)

## F1 与任务奖励的两个分母

论文主要指标把 `unmet` 作为正类：TP 是正确发现不满足，FP 是把已满足误判为不满足，FN 是漏掉真正不满足的评分项。用标准二分类定义表示：

$$
P=\frac{TP}{TP+FP},\qquad
R=\frac{TP}{TP+FN},\qquad
F_1=\frac{2TP}{2TP+FP+FN}.
$$

以上是对原文 §7 指标口径的公式化说明，不是论文训练目标。若总把条件判为满足，原始准确率能接近 78.7%，却不能发现少数不满足项，因此 `unmet` 类 F1 更直接反映这部分能力。论文没有发布可核实的完整指标脚本，未充分说明所有表格的聚合实现，不能自行补成任务宏平均 F1。

**说明示例：** 100 条标准中有 20 条实际不满足，验证器发现其中 15 条，同时错拒 5 条已满足标准。于是 $TP=15,FP=5,FN=5$，F1 为 0.75，准确率则为 0.90。两者不会表达同一件事。

公开软件输出的任务奖励则依据权重。令 $m_i\in\{0,1\}$ 表示条件是否满足、$w_i$ 为正或负权重，则在所有标准均成功评分后：

$$
S=\sum_iw_im_i,\qquad
R_{\mathrm{task}}=\operatorname{clip}_{[0,1]}
\left(\frac{S}{\sum_{i:w_i>0}w_i}\right).
$$

若正权重之和不大于零，当前实现返回 0；原始总分和边界会先按代码四舍五入到四位小数。负权重只在相应条件成立时扣分，不是先将正负权重总和作为分母。仓库 quickstart 的两个满足项得 3 分、正权重总和为 4，得到 0.75。这个 0.75 是单任务奖励，不能作为 BVB 上验证器 F1 的复现结果。

## 主实验：模型、费用与比较范围

默认配置为 Gemini 3 Flash、$b=16$，开启领域指导和环境对齐的 MCP 工具。主要比较覆盖 Gemini 3 Flash / Pro，以及 GPT-5.4 Nano / Mini / GPT-5.4。论文没有给出所有服务的日期化模型标识、温度、最大步数、完整运行配置和重复次数。（§7、表 2）

| Gandalf 后端模型，固定 $b=16$ | BVB F1 | 全套评分费用 |
| --- | ---: | ---: |
| Gemini 3 Pro | 0.664 | $299 |
| Gemini 3 Flash | 0.660 | $64 |
| GPT-5.4 | 0.637 | $230 |
| GPT-5.4 Mini | 0.658 | $62 |
| GPT-5.4 Nano | 0.633 | $42 |

表 2 显示，在这些配置下换大模型并不总是提高 F1。GPT-5.4 比 Mini 贵，结果反而低；作者提出指令遵循和工具使用等可能解释，但没有单独实验识别原因。

图 1 中 Archipelago 最好配置为 Gemini 3 Pro，0.604 F1、422 美元；Gandalf 的 Nano 配置仍高 2.9 个百分点，费用约为其十分之一。与 Archipelago GPT-5.4 的 0.538、414 美元相比，差距则为 9.5 个百分点、节省约 89.9%。这两个对照不能混写为“比最强基线高 9.5 个百分点”。AutoRubric 的 GPT-5.4 配置达到 0.472，其余主要 AAAJ / AutoRubric 结果低于 0.47。（§7.1、图 1）

费用用输入、输出 token 数乘论文采用的公开单价：Gemini 3 Flash 每百万输入/输出 token 为 $0.50/$3.00，Pro 为 $2.00/$12.00；GPT-5.4 Nano 为 $0.20/$1.25，Mini 为 $0.75/$4.50，GPT-5.4 为 $2.50/$15.00。这是研究时的价格口径，不是当前报价，也不包含任务生成、专家标注和完整基础设施费用。没有各配置的输入输出原始统计，不能仅用总 token 数重新算出所有费用。

“处在成本—质量前沿”意味着在所比较配置中，没有另一项同时更便宜且 F1 更高；不意味着 Gandalf 在每个预算下都最便宜。图 1 有更低价但 F1 较低的基线配置。

## 消融：工具、指导和批大小改变了什么

| Gemini 3 Flash、$b=16$ | F1 | 费用 |
| --- | ---: | ---: |
| 领域指导 + MCP | 0.660 | $64 |
| 无领域指导，保留 MCP | 0.649 | $73 |
| 无领域指导，无 MCP | 0.661 | $102 |

去掉领域指导、保留 MCP 后，F1 下降 1.1 个百分点，费用增加约 14.1%。两者都去掉时，F1 与默认配置接近，但费用增加约 59.4%。作者观察到验证器会写临时 Python 脚本、做更多探索，以补偿结构化工具的缺失。（§7.2、表 2）

这不是完全独立的两因素消融：论文没有“保留原指导、去掉 MCP”的一格，因为原指导会引用无法访问的工具。不能把 $64→102 的全部变化单独认定为 P2 的因果效果，也不能据 0.661 略高于 0.660 就判断删除工具更有效。三组都保留反应式 agent，测试的是它能以多大额外代价补足缺失信息；P1 本身没有在同一实现中单独关闭的消融。

| 批大小 $b$ | F1 | 费用 |
| --- | ---: | ---: |
| 64 | 0.635 | $32 |
| 32 | 0.644 | $40 |
| 16 | 0.660 | $64 |
| 8 | 0.667 | $100 |
| 4 | 0.673 | $159 |

每次只处理较少标准，F1 逐步提高，但更多会话会重复读取文件。从 16 减到 4，增加 1.3 个 F1 百分点，费用约为原来的 2.48 倍。默认 16 是作者选定的折中点，不是系统硬限制，也没有统计证据保证它在所有任务上最优。摘要提到最多四倍 token 节省，但表 2 展示的是美元费用而非逐组 token；不能由这些费用单独验证“四倍 token”这一量级。

| 时间顺序 | 15.9% | 17.8% | 20.6% | 45.8% |
| 总体 | 13.6% | 17.4% | 31.7% | 54.7% |

Gandalf 在这四者中取得七类最低错误率；会计逻辑比 Archipelago 高 2.1 个百分点，披露与论述比 AAAJ 高 1.1 个百分点。作者据此解释，原生证据检查有帮助，但不能消除语言模型应用惯例、判断文本一致性时的错误。分类误差差异支持这种解释，尚不足以给出逐条错误的唯一原因。

表 4 进一步分解 Archipelago 的错拒与漏检。以视觉呈现为例，FP 为 10.5%、FN 为 16.1%，相差 5.6 个百分点；时间顺序的 FP 为 12.1%、FN 为 5.6%，方向相反。按其与表 3 总错误率相加吻合的关系，这些数值应理解为该能力组中两类错误各占多少，而不是通常以全部真实负类/正类分别作分母的条件 FPR / FNR。原稿没有给出逐项混淆矩阵，不能将 16.1% 直接解释为“真正不满足的视觉标准中漏检 16.1%”。

## OpenClaw：从文件转向工具状态

第二个数据集是作者内部的 OpenClaw（OPC）个人事务工作流，含 24 项任务、396 条标准，涉及日程、联系人协调和生活安排。证据不仅是文件，还包括消息是否发送、日程是否创建等工具状态。它不是本文新训练的 agent，也不能直接等同于其他同名公开基准。（§8.1）

图 2 报告 Gandalf / Gemini 3 Flash 的 F1 为 0.951、总费用 8.20 美元；Archipelago / Gemini 3 Flash 为 0.876，差 7.5 个百分点。便宜的 Archipelago 和 AutoRubric 配置仍有较低 F1，因此这里也是成本与质量的取舍，不能说 Gandalf 成本最低。

| OPC 能力 | 标准数 | Gandalf 错误率 | Archipelago 错误率 |
| --- | ---: | ---: | ---: |
| 直接数据核对 | 200 | 4.5% | 10.0% |
| 跨组件关联 | 20 | 0.0% | 35.0% |
| 组成部分完整性 | 53 | 1.9% | 13.2% |
| 标签与元数据 | 41 | 7.3% | 24.4% |
| 披露与论述 | 66 | 6.1% | 25.8% |
| 时间顺序 | 12 | 8.3% | 25.0% |
| 总体 | 396 | 4.5% | 16.2% |

同一能力名在不同场景中可能需要不同证据。例如“披露与论述”在 OPC 中可能需要确认相关消息真的发出。该组 Gandalf 6.1%、AAAJ 43.9%，与 BVB 中文本检查的排序不同。跨组件组只有 20 条，0% 只表示这些样本未观察到错误。论文没有提供 OPC 的完整人工标注协议、标签分布及公开数据包，不能以 0.951 推断跨领域均能达到这一水平。

## RewardKit 对照中的分母与原稿差异

KDD 版本加入并行研究 RewardKit。论文使用其 agent-judge 模式，通过 Claude Code 检查文件、执行脚本，比较有无环境对齐 MCP 工具。它与 Gandalf 都能主动检查文件，因此不能继续把本节概括成“agent 验证器对文字验证器”。（§8.3）

表 3 注明 RewardKit 在 BVB 仅完成 2,634 / 3,204 条，覆盖率约 82.2%；部分运行因标准列表过大失败。其 15.2% 总错误率是在完成子集上计算，其他列则使用全部数据。没有把 Gandalf 限制到相同子集的结果，不能据 15.2% 与 13.6% 直接判断同一数据上的净差距。论文称 RewardKit 没有批处理功能，这是其被测实现的描述，不代表后续版本必然如此。

原稿表 5 与正文还存在无法由公开材料消除的不一致，需与主结果分开保留：

| 表 5 原样报告 | F1 | 总 token，百万 | 费用 |
| --- | ---: | ---: | ---: |
| RewardKit / Claude Sonnet 4.6 | 0.879 | 52.6 | $162.67 |
| RewardKit + MCP / Claude Sonnet 4.6 | 0.905 | 51.7 | $160.76 |
| Gandalf / Gemini 3 Flash | 0.951 | 70.0 | $35.76 |

表题写的是 BVB，但 Gandalf 的 0.951、$35.76 与表 2 的 BVB 0.660、$64 不同；0.951 又与 OPC 主结果相同，但费用也不是图 2 的 $8.20。原文未解释一套可对应这些数字的新配置或分母，不能擅自改表题、改指标正类或将其并入主表。

正文称相对最好 RewardKit 高 7.2 个百分点，按表格实际为 $0.951-0.905=0.046$，即 4.6 个百分点；7.2 对应没有 MCP 的 0.879。表 3 还把直接数据核对的 RewardKit 12.8% 描述为不差于 Gandalf 12.3%，与数值方向不符；数量重算两者为 17.0% 和 12.0%，差 5.0 个百分点，也不是附近正文所写 3.6。

因此，这一节可确认作者补充了主动代码检查基线以及不同覆盖率的结果，但尚不能据表 5 建立一条可与主实验合并的性能结论。费用约相差 4.5 倍的算术成立，其后端模型和单价不同，也不能解释为纯架构的成本优势。原文同时明确没有做使用该验证器奖励的 RL 训练，不能将这些结果写成训练收益已得到验证。

## 公开实现与论文复现之间的距离

本次静态核查固定官方代码提交 [`a79dccdd1fab4e791438c3c600130da4dfef8389`](https://github.com/Handshake-AI-Research/gandalf-the-grader/tree/a79dccdd1fab4e791438c3c600130da4dfef8389)，包内版本为 1.0.0，许可证 Apache-2.0。核对范围包括 `orchestrator.py`、`judge.py`、`models.py`、提示模板、配置和 quickstart；没有运行模型或复现论文评测。

**默认模型与批处理不是论文配置。** 当前默认是 `gemini/gemini-2.5-flash`，默认整份 rubric 在一个 batch 中处理；论文默认 Gemini 3 Flash、每会话 16 条。`batch_splits` 表示拆成几块，代码按 $\lceil N/\text{splits}\rceil$ 个标准分块，不表示每块 16 条。配置时须按实际标准数换算。默认每标准时间预算 300 秒，一批的预算为标准数乘 300，可由 `batch_timeout` 封顶；它不是论文已经披露的统一实验预算。

**文件副本与外部服务状态不同。** 每次调用会复制工作目录，在副本中运行终端和文件编辑器，结束后删除副本。复制过程中无法读取的文件或目录会跳过并告警，不会自动令整次评分失败。MCP 连接仍来自配置，这段逻辑没有为远端服务制作独立状态快照。因此文件隔离不能自动证明消息、日历等服务也被重置或禁止修改；重放实验需由任务环境提供对应状态管理。

**评分错误不会一律变成不满足。** 缺失文件、JSON 无法解析、缺少某个索引、超时或执行异常会记录 `met=None`。默认重试一次，只重试出错标准；批模式重试走单批入口，并不继续原来的并行分块。重试后还有错误时，程序写 `info.json`、退出码 1，不新写 `reward.json`。下游需要读错误数量与本次退出状态，不能把这些记录当成有效的 `false` 标签。代码也没有在失败路径删除以前留下的 `reward.json`，所以复用输出目录时不能仅靠文件存在判定本次成功。

**输出校验有边界。** `Verdict.from_raw` 对非空值使用 Python `bool(...)` 转换；若模型错把布尔值写成字符串 `"false"`，它会被转成 `True`。批结果重复索引以后一个覆盖前一个，越界索引忽略。提示要求正确 JSON 布尔值，但该实现不等于严格验证所有模型返回类型。这是静态代码行为，不是已证实影响论文结果的错误率。

**成本日志可能不完整。** 正常会话尝试读取 OpenHands 累积 token 和费用；读取失败时返回默认零值，子进程失败路径也可能没有保留已经消耗的调用费用。把这些日志用于成本复现时需要结合服务账单或完整轨迹，不能默认所有失败都没有成本。

安装运行需要 Python 3.12 以上、`tmux`、OpenHands SDK / tools、LiteLLM、可用模型凭据，以及实际工作区和 MCP 服务。仓库 quickstart 是三条标准的功能样例，不含整套 BVB 的专家标签、最终工作区和基线结果。

截至本次核查，论文写到公开 BVB，公司博客仍写待发布；官方 Gandalf 仓库只链接 BankerToolBench 环境，查询 Handshake AI Research 的公开 GitHub 仓库与 Hugging Face 数据集清单也未定位到独立的 BVB 标签及轨迹包。这个结论仅限本次能核实的公开入口，不表示数据不存在。能下载 BankerToolBench 的任务环境，不等于已经取得用于比较验证器的 21 条固定执行轨迹和 3,204 条专家标签。

要复现论文主表，还需取得对应人工标签与最终环境、各基线配置及逐项预测，固定模型标识、评分方向、批大小和价格，并明确失败样本如何处理。附录 A 的完整提示可以支持重建分类流程，但不能代替缺失的实验数据和聚类实现。本文完成的是原稿与公开代码核对，尚未复现模型调用结果。

## 已验证的范围

这项研究显示，在所选投行业务和内部个人事务工作流中，能够追踪文件与工具状态的验证器取得了较好的专家标签一致性；批处理、领域指导和工具访问也影响费用。证据覆盖的是固定产物上的验证，不包含改进后的 RL 训练，不包含同一任务多种 agent 轨迹分布下的稳定性，也没有对恶意产物、提示注入或跨领域部署给出完整测试。单次运行差距、少量任务的能力分组及 RewardKit 章节的材料不一致，都限制了结果外推。（§10）

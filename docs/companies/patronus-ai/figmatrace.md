# FigmaTrace 精读：把设计师录屏整理成界面操作训练数据

设计师调整一个页面，通常会先整理框架，再建立组件、修改样式、检查细节。最终截图只保留结果，录屏则留下了这些操作发生的顺序。FigmaTrace 记录专家使用 Figma 的过程，把鼠标、键盘事件与画面对齐，再按设计阶段切成训练片段。用这些数据微调的模型，在多个界面单步操作测试上获得提升；论文尚未用完整作品的人类审美评价证明模型学会了设计品味。[论文 §1、§3–5](https://cdn.patronus.ai/FigmaTrace.pdf)

## 从完成的界面到连续的操作

截图转 HTML、现有网页转 Figma JSON 等任务，主要监督模型生成最终结构。录屏提供另一类信号：先选中了哪个元素、在哪里输入文字、何时回看参考，以及怎样把分散元素整理成可复用组件。FigmaTrace 将这些动作作为监督目标。（§2）

论文图 1 展示了一个复制 Nuxt 网站的片段。设计师在颜色对话框输入 `00DC82`，创建颜色样式，切换到参考页面，再选择元素进行应用和检查。图中的十字标记表示录制到的操作坐标。这段数据给出动作与屏幕状态，未提供设计师每一步的思考过程；因此作者使用不带推理链的监督微调。（图 1、附录 A.5）

长录屏直接用于训练会遇到两个问题。一是大量鼠标移动、等待和重复画面占据数据；二是按长度硬切，可能把“建立组件”的中间步骤分到一个缺少起因的片段中。本文分别用事件清洗和设计阶段切分处理这两类问题。

## 十类技能、八类任务与不同的数据单位

三名专家先制定技能体系，覆盖视觉感知、Figma 结构组织、跨媒介转换、内容边界处理、无障碍、交互流程、素材寻找、矢量编辑、诊断修复，以及流程判断。它是组织任务和标注的分类框架，并非十项独立、已经校准的能力测试。（图 2、§3.1）

随后构造八类工作任务：

| 任务 | 起始材料与要求 |
| --- | --- |
| 像素级复制 | 从许可来源取得网页截图，记录原链接、日期和许可依据，在 Figma 中复制并正确使用自动布局 |
| 响应式与平台适配 | 把桌面页改成手机页，或在网页、平板、原生应用之间调整 |
| 主题切换 | 用变量和模式实现深浅色主题，避免逐节点手工改色 |
| 草图转 Figma | 根据手绘草图制作高保真界面 |
| 注入问题后修复 | 修改现有模板，制造布局或流程问题，再完成修复 |
| 内容边界测试 | 处理超长文本等内容，检查原布局是否仍成立 |
| 无障碍修复 | 修正文件中的可访问性问题 |
| 原型连线 | 根据较开放的要求连接页面与交互流程 |

作者把复制、修复、内容边界和无障碍任务归入较可验证的类别，把适配、主题、草图与原型任务归入更依赖专家选择的类别。这里是任务设计上的区分，不意味着所有修复都有唯一答案，或开放任务无法按照具体标准检查。（表 1）

### 专家选择与文件检查

录制专家通过 Upwork 招募，要求年满 18 岁、至少有两年 Figma 经验，并先完成试做任务。制定分类体系的三位专家不等于所有录制人员；原文没有明确给出录制专家总数、报酬、每人贡献或跨专家标注一致性。（附录 A.2）

附录 A.4 给出较长的文件检查表，检查页面与图层命名、组件是否可编辑、跨文件依赖、颜色和文字样式、交互状态、长文本、图标字体、无障碍与最终完整性。例如，重复使用的按钮应当是真正的组件，提交文件不能依赖不可访问的外部组件库。

这些检查有助于说明作者希望收集怎样的设计过程，但论文没有同时公布每项标准的实际通过率、返工次数或独立复查错误率。不能把一份检查清单直接当成全数据已经满足所有要求的统计证据。

技能分布也并不均匀：结构组织占 56.9%，视觉感知占 12.7%，两者合计 69.6%；交互流程只占 0.6%。这与自动布局、组件整理在任务中频繁出现有关。技能标签可以按频率分配，同一轨迹可能涉及多种技能，不能把十类视为等量训练样本。（图 4、附录 A.3）

## 从录屏到动作—画面对

### 先清理事件，再补上无输入变化

作者观察到约 95% 的原始事件是随机鼠标移动或悬停等中间活动。因为目标工具可以直接对坐标点击，清洗时移除无必要的移动，保留悬停，并将其余操作映射到接近的 Playwright-MCP 动作形式。（§3.1）

这不代表最终数据完全没有鼠标移动：图 3 仍列出 `mouse_move`，占已验证调用的 13.2%。正文没有给出足以逐项解释该比例的完整转换代码，本文不将“过滤中间移动”改写成“所有移动都删除”。

有些变化不由新输入触发，例如插件完成加载。对超过四秒的空档，处理程序每两秒插入一次 `observe` 候选，让没有键盘鼠标动作的状态变化也可能进入轨迹。随后仍需经过画面变化筛选。

### 两遍抽帧处理不同的界面响应时间

第一遍以每秒八帧、480×270 灰度画面读取视频，最长单次录屏可到 4.5 小时。对于时间为 $t$ 的候选动作，动作前画面取 $t-0.15$ 秒；动作后则在 $[t+0.2,t+2.0]$ 秒内寻找首次稳定画面。（§3.1）

稳定条件是相邻画面的平均绝对变化小于 0.75。菜单可能很快展开，拖入图片却需要更久，因此统一固定延迟不一定能捕捉操作后的状态。作者报告在所述 5,718 个实例中找到 5,717 个稳定点，但这只是时间定位的结果，不等于这些动作全部有正确的语义标签。

第二遍按已选时间戳提取原分辨率画面，并把接近的读取合并，减少重复解码。低分辨率用于找时间，高分辨率用于保留真正训练时需要的界面文字与细节。

### 用变化比例剔除没有可见效果的动作

设操作前后画面为 $I^-$、$I^+$，共有 $N$ 个像素。按正文规则，可将变化比例写为：

$$
f=\frac1N\sum_{p=1}^{N}\mathbf1\!\left[
\max_{c\in\{R,G,B\}}|I^+_{p,c}-I^-_{p,c}|>6
\right].
$$

普通动作若 $f<5\times10^{-4}$ 就被删除；`observe` 候选需要至少 $2\times10^{-2}$ 的变化才算场景改变。前者为 0.05%，后者为 2%，不能把两个阈值混成相同条件。（§3.1）

这个筛选器判断的是可见变化，而不是动作是否正确。某些不明显改变截图的状态操作可能被过滤；论文没有量化这类损失，也没有报告改变阈值的消融。最终 179 倍压缩指相对于原始 OS 事件的数量压缩，不能解释为模型速度提高 179 倍。

## 按设计阶段切分长轨迹

一个阶段指设计师保持同一意图的连续时间段，例如先搭好页面框架，再创建组件。阶段覆盖整段录屏，每帧只属于一个阶段。Gemini-3.6-Flash 只看视频、不读动作日志，为连续区间分配封闭类别标签。（§3.1、附录 A.1）

表 4 实际列出十一类：参考收集、初始设置、粗布局、素材寻找、内容输入、字体与样式、组件化、细节调整、检查、标注交付，以及导航等待。正文也说十一类；图 3 图注和公开数据卡则写十二类。现有材料没有解释这个差异，本文按实际列出的类别介绍，不补造第十二类。

作者分别按 3、6、12 片运行切分，获得三组候选边界，保留至少两组结果在前后 30 秒内达成一致的边界。**3、6、12 是分片设置，不是技能数或阶段标签数。** 最后再按出现频率给轨迹分配技能标签。

**说明示例：**一段录屏先排版，再进入组件编辑。如果最大长度限制正好把片段从组件编辑中间切开，后半段可能只剩“继续修改”而缺少目标；按阶段切分则尝试把相关动作留在同一片段。这个例子解释设计动机，不能替代对实际切分质量的人工测量。

作者还比较视频分辨率：以较强模型在完整分辨率下的标签为参照，同一模型低分辨率结果的 Jaccard 为 0.244、主导技能一致率为 21%；较弱 Gemini-3-Pro 在完整分辨率下为 0.601、43%。这些是与模型参考结果的一致性，未给出独立人工真值、样本量及区间，因而不能直接写成标签准确率。（§3.1）

## 监督微调的输入、目标和预算

数据没有预标注推理链，模型学习根据截图、任务指令和已有上下文输出下一步工具调用。公开模型卡把目标描述为 assistant 工具调用上的下一 token 交叉熵。用标准 SFT 记号解释，可写为：

$$
\mathcal L(\theta)= -\frac{1}{|\mathcal A|}
\sum_{t\in\mathcal A}\log p_\theta(y_t\mid x,y_{<t}),
$$

其中 $x$ 为观察和指令，$y_t$ 为目标调用的 token，$\mathcal A$ 为参与监督的位置。最小化损失使专家示范的调用获得更高概率。这是依据模型卡整理的通用目标，不是论文提出的新损失；具体特殊 token、空思考标签及多轮权重还取决于训练实现。

四个底座为 Qwen3.6-35BA3B、Qwen3.8-27B、Gemma-4-31B 和 Muse-Glimmer-30B。主要配置使用监督微调，视觉塔冻结、对齐层可训练，语言模型可训练。附录另列出视觉塔解冻等实验配置，不能说所有列出的尝试都冻结视觉塔。（§4、附录 A.6）

| 参数 | 主配置或已发布 Qwen 模型的记录 |
| --- | --- |
| 数值精度与优化器 | BF16；Adam，两个动量系数 0.9、0.95 |
| 正则与裁剪 | 权重衰减 0.1；梯度裁剪 1.0 |
| 学习率 | Qwen3.8 主配置 $2\times10^{-6}$，公开配置最低 $2\times10^{-7}$ |
| 调度 | 余弦下降，预热比例 3% |
| 每设备微批量 / 全局批量 | 1 / 6，后者据公开 Qwen 配置 |
| 上下文长度 | 65,536 tokens，据公开 Qwen 配置 |
| 图像预算 | 1,296,000 像素；每行最多 44 帧 |
| 训练步数与种子 | 259 次迭代；种子 42，据公开 Qwen 配置 |
| 并行 | Qwen3.8 使用 TP4、CP2、DP2：张量、上下文和数据并行 |

Qwen 每帧约 1,260 个视觉 token，44 帧本身已约占 55,440 个 token，仍需为文字和工具调用留空间。因此原始轨迹最长约五百万 token，不代表训练支持把整条原始录屏一次送入模型。

公开 `args.json` 确认上述长度、批量、259 步、冻结设置及学习率，并记录 `loss_scale=default+ignore_empty_think`、ms-swift `4.5.0.dev0`。它指向作者本地整理后的 JSONL，验证数据列表为空、自动拆分比例为零。这个配置不能直接证明公开 2,883 条训练轨迹就是本次使用的 1,554 行，也不能替代训练输入清单。[固定配置](https://huggingface.co/PatronusAI/Qwen3.8-27B-Figmatrace-SFT/blob/fb0120ac38cbe55085a1751fc8ab0122e9a6be28/args.json)

Gemma 因逐层 KV 头数不一致，使用 Hugging Face SFTTrainer 与 DeepSpeed；其余实验使用支持上下文并行的 Megatron 路径。论文没有完整给出硬件型号、训练时间与费用。模型卡的约 54.7GB 是发布权重体积，不是训练显存需求。

## 主实验评估的是下一步操作

表 2 的标题明确为 **step-wise accuracy，即单步准确率**。四个域外数据集提供六种设置：GUI-Odyssey、AndroidControl、Mind2Web 的两个视口配置，以及 VideoGUI 的有逐步指令和开放目标两种配置。另有 ScreenSpot-Pro Creative 的界面定位测试。（§4–5、表 2）

模型卡补充，已发布模型的评测使用贪心解码，关闭推理并强制工具调用。这是该模型的评测设置；公开示例中的 `max_new_tokens=256` 只是加载示例参数，资料没有确认它也是全部评测的输出预算。

这些结果不能直接换成完整 Figma 任务成功率。单步预测面对的是给定状态；实际执行一次错误点击后，后续界面可能变化。论文没有给出相应闭环长任务完成率，也没有对最终设计作品进行完整的盲评审美比较。

模型卡补充说评测使用小规模、150 项的探测样本；正文在定性分析中明确提到 150 个 GUI-Odyssey 项。公开资料没有提供所有配置的样本 ID、精确分母与聚合实现，部分分数也不符合单次 150 项二值均值的步长。因此不应把每一列无条件解释为同样的 150 道题。

下表转录表 2 中两种闭源模型与 Qwen3.8 的对照，单位为百分比，越高越好。

| 模型 | GUI-Odyssey | AndroidControl | Mind2Web 800 | Mind2Web 1000 | VideoGUI 有指令 | VideoGUI 开放目标 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Claude Opus 5 | 47.3 | 87.3 | 100.0 | 75.3 | 71.3 | 40.7 |
| GPT-5.6-Sol | 44.0 | 83.2 | 91.3 | 69.7 | 77.7 | 29.6 |
| Qwen3.8-27B | 44.0 | 82.7 | 69.3 | 65.3 | 65.3 | 26.0 |

微调模型在 GUI-Odyssey 和 AndroidControl 分别超过 Opus 6.4、11.8 个百分点，但在 Mind2Web 800 上仍低 29.3 点；开放目标 VideoGUI 还低于自身底座。较合理的结论是多项具体设置有迁移收益，而不是全面超过闭源模型。

论文所说“最多约 46 个百分点提升”，来自另一个底座 Qwen3.6 的 AndroidControl：36.8 到 83.2，增加 46.4 点；不是上表 Qwen3.8 的提升。Gemma 的开放目标 VideoGUI 也从 24.0 降到 23.3。Muse 的评测使用多次缩放和裁剪后汇总，计算方式不同；闭源模型使用 high 推理强度，微调模型不输出推理链，均不是严格等预算比较。

ScreenSpot-Pro Creative 的原文成绩为 29.3 到 36.7，增加 **7.4 个百分点**。模型卡另写 8.3，但未提供对应的另一组分数。本文保留原文的可核算结果，不将其解释为作品审美评分。

## 阶段切分消融：四项提升，两项下降

表 3 用 Qwen3.8 比较按阶段切分与按最大长度切分的 SFT。以下使用原表顺序，注意 VideoGUI 开放目标排在有指令之前。

| --- | ---: | ---: | ---: | ---: |

| AndroidControl | 82.7 | 99.1 | 67.3 | +31.8 |
| Mind2Web 800 | 69.3 | 70.7 | 69.3 | +1.4 |
| Mind2Web 1000 | 65.3 | 68.7 | 70.0 | −1.3 |

| VideoGUI 有指令 | 65.3 | 71.3 | 70.0 | +1.3 |
| 原表均值 | 58.8 | 63.8 | 56.3 | 约 +7.5 |

正文称均值优势为 7.3，公司博客还写阶段结果 63.6；但本次查看 PDF 原表，确实是 **63.8 与 56.3**。按六行重新计算为 63.8000 与 56.3167，差约 7.48 点。这个差异不能靠一位小数的正常舍入解释，本文按原表列值报告。（PDF 第 7 页、表 3）

该均值让六个配置等权，因此 Mind2Web 和 VideoGUI 各占两份权重，另两个数据集各占一份。它不是所有样本合并后的准确率，也不是四个数据集等权平均。

收益主要集中在 GUI-Odyssey 和 AndroidControl；阶段切分并未在六项上全部更好。作者认为保留意图边界有助于理解片段，但论文没有完整公开两套训练输入、保留 token 总量和样本对应关系。相同学习率与并行设置不足以证明其余训练条件完全相等。现有消融支持这两套整理方案的成绩不同，尚未单独测量“意图理解”这一内部能力。

## 坐标、元素选择与新出现的错误

作者人工检查了微调把底座错误变成正确的项目。在 GUI-Odyssey 的这些改善中，约三分之二是底座选了完全不同的元素。该子集的底座坐标误差中位数约 457 像素，而微调结果约在 15 像素内。它们是改善样本上的条件统计，不能当成所有评测项的总体误差。（§5）

例如要求在 Instagram 与朋友聊天时，目标输入框坐标为 `(593,1325)`，底座给出 `(596,112)`，落到顶部搜索栏；微调模型则落在目标七像素内。这里纵向位置几乎决定了选择的是哪个元素。

另一些错误来自坐标约定。已发布模型输出 norm-1000 坐标，即两个轴分别缩放到 0—1000。若视口宽高为 $W,H$，输出为 $(u,v)$，像素坐标应为：

$$
x=\frac{uW}{1000},\qquad y=\frac{vH}{1000}.
$$

**说明示例：**在 1,000×2,000 的视口中，输出 `(500,750)` 对应像素 `(500,1500)`。若把 750 直接当像素，点击就会偏离。论文在所分析的 150 个 GUI-Odyssey 项中，发现底座有十项输出越过 1000 的纵坐标，微调模型没有同类越界。这说明部分收益与输出格式、坐标映射有关，不全是更深的任务推理。

AndroidControl 的改善项目中，底座有时不输出坐标，有时选错元素；微调模型给出答案，纠正元素选择时平均误差约十一像素。但论文没有据此证明“任何情况下都回答”更好，也没有公开统一的点击命中容差与全部动作评分细节。

反过来，作者也检查从正确变错的项目，发现两种模式：连续两步重复点击几乎相同的位置，以及偏向画布中心而忽略浏览器外围控件。作者将其与残留的噪声动作、Figma 画布偏好联系起来。这些是基于案例的解释，尚无移除对应数据的消融。重复动作是否只增加步数、会不会导致完整任务失败，仍需要闭环执行测试。

# TRACE：在多条代码轨迹的对照中识别奖励作弊

## 1. 摘要翻译

以下按 [arXiv v1 摘要](https://arxiv.org/abs/2601.20103v1)顺序翻译。原文作者为 Darshan Deshpande、Anand Kannappan 和 Rebecca Qian，采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)；中文为翻译版本。

代码生成领域的强化学习近期取得进展，这使得构建稳健的环境对于防止奖励作弊变得至关重要。随着大语言模型越来越多地在基于代码的强化学习中担任评估器，它们检测奖励作弊的能力仍缺乏充分研究。本文提出一套覆盖 54 类奖励利用方式的新分类体系，并介绍 TRACE（代码环境奖励异常测试）：一个通过合成构建、经人工验证、包含 517 条测试轨迹的基准。

以往工作在孤立的分类场景下评估奖励作弊检测；与之不同，我们在 TRACE 上将这类评估与更贴近实际的对比式异常检测设置进行比较。实验表明，模型在对比设置下比在孤立分类设置下更能识别奖励作弊。采用最高推理模式的 GPT-5.2 在 TRACE 上取得了最佳检测率 63%，高于孤立设置下的 45%。

在此基础上，我们进一步表明，相比于依赖语法上下文的奖励作弊，当前最先进模型在处理依赖语义上下文的奖励作弊时明显更加困难。我们还对模型行为进行定性分析，并通过消融研究表明，无作弊轨迹与作弊轨迹的比例，以及被共同分析的轨迹组大小，都会显著影响检测表现。我们发布了基准和评估框架，以便社区扩展 TRACE 并评估自己的模型。

## 2. 研究背景与相关研究

代码智能体常用单元测试、运行状态等可自动检查的信号获得奖励。这些信号容易计算，但未必完整代表用户的目标：程序通过了检查，并不意味着问题已经正确解决。本文讨论的奖励作弊，是智能体利用奖励或环境的缺陷获得高分，却没有实现真正的任务目标。

Introduction 和 Related Work 将相关工作分为两条线。一条研究代码智能体如何利用测试和评估环境的缺口。EvilGenie、ImpossibleBench 等工作已经展示这种现象，但其研究范围往往集中于测试相关行为、单轮代码生成，或对单条轨迹作有无作弊的二元判断。实际代码助手会持续调用工具，与用户进行多轮交流；判断一次修改是否违背任务目标，需要结合前后文。

另一条线研究对比式异常检测：将多个样本放在一起，借助正常样本与异常样本的差异发现问题。TRACE 把这一思路用于代码轨迹。评估器不仅独立审查一次执行，也同时审查一组执行，比较它们与任务要求的关系。这里的“对比”是一种评估输入组织方式，并不表示论文已经训练出新的对比学习模型。[论文第 1—2 节](https://arxiv.org/pdf/2601.20103v1)

## 3. 核心贡献

**核心问题。** 现有模型能否识别代码智能体在多轮工作中偏离真实目标、迎合奖励的行为，以及多条轨迹之间的对照能否改善这种判断。

**核心方案。** TRACE 构建了包含 54 种细分类别的代码奖励作弊分类体系，并通过合成和人工审核形成 517 条轨迹。其中 249 条没有作弊，轨迹平均约有 26 轮发言，覆盖多个软件工程领域。一个样本可以包含不止一种作弊行为。基准同时保留正常轨迹，要求评估器区分符合任务要求的操作和奖励作弊，并指出相应类别。

作者比较了单独检查一条轨迹和成组检查多条轨迹的方式。后者让模型借助其他案例理解什么属于正常行为，再判断异常；研究还分析了组内正常样本的比例及轨迹组大小对判断的影响。[论文第 3—4 节与数据集](https://huggingface.co/datasets/PatronusAI/trace-dataset)

**主要结论。** GPT-5.2 的 Detection Rate 从单条设置的 0.45 提高至对比设置的 0.63。需要注意，论文把这个指标定义为有无作弊判断的 **宏平均 F1**，不能解释成“找到了全部作弊行为中的 63%”。作者还发现，需要理解用户目标和业务语境的作弊，比能够直接从代码形式辨认的作弊更难检测；加入合适的正常轨迹有助于模型判断，但轨迹组合本身会影响结果。

这篇论文提供的是基准、分类体系和检测方式的比较。数据经过人工审核，但主要由模型合成，因此结果说明的是所构建基准上的检测能力，不能直接视为真实生产环境中的作弊发生率或部署后的防护效果。[论文第 4—6 节](https://arxiv.org/pdf/2601.20103v1)

# FinanceBench：从财报证据到财务答案

回答一家公司的固定资产周转率，需要找到对应年度的收入、两年的固定资产净额，再按指定公式计算。FinanceBench 把这样的工作做成评测：问题对应公开财报、参考答案和证据页，系统既要找到材料，也要解释和计算。论文用 150 道题测试 16 种模型配置，并人工检查 2,400 份回答。2023 年的 GPT-4-Turbo 在共享财报检索库下答对 29 题；直接提供对应财报全文时，较好的提示顺序答对 118 题。差距说明信息如何进入模型会显著影响结果，但即使给出证据页，模型也没有全部答对。

## 把查找、读表和计算放在同一道题里

论文讨论的场景是开放资料问答：分析师提出问题，系统从财务文件获取相关信息并作答。材料包括年度报告、季度报告、临时报告和业绩报告。输入既有文字，也有列名、年份和单位都很重要的表格。答案可能是直接提取的金额，也可能需要跨报表计算，或者根据证据作定性判断。（§1、§3）

此前的 FinQA、ConvFinQA 和 TAT-QA 已经研究财务数值推理、对话及表格与文本混合问答。FinanceBench 的重点是把实际检索加入评测：如果提前给模型足够的短证据，就无法观察它在大量财报中找错公司、年份或表格的情况。本文没有训练一个新的财务模型，而是构造数据并比较信息获取方式。（§2）

作者把这些问题定位为财务问答的一道基础检查，希望它们贴近分析师工作、答案尽量明确。这个目标不意味着每道题都很难，也不意味着参考答案完全没有歧义；论文后面专门讨论了这两项限制。

### 一个公开样本的完整计算

公开题目 `financebench_id_02987` 要求计算 Activision Blizzard 的 FY2019 固定资产周转率，并明确规定使用 FY2019 收入除以 FY2018、FY2019 固定资产净额的平均值，保留两位小数。材料是 `ACTIVISIONBLIZZARD_2019_10K`，并非把多个公司的数据放在一起比较。

| 所需数据 | 报表与年度 | 数值，百万美元 |
| --- | --- | ---: |
| 总净收入 | 2019 年利润表 | 6,489 |
| Property and equipment, net | 2019 年资产负债表 | 253 |
| Property and equipment, net | 2018 年资产负债表比较列 | 282 |

若用 $R_t$ 表示当年收入、$P_t$ 表示年末固定资产净额，这道题指定的计算为：

$$
\overline P_t=\frac{P_{t-1}+P_t}{2}
=\frac{282+253}{2}=267.5,
\qquad
\text{周转率}=\frac{R_t}{\overline P_t}
=\frac{6489}{267.5}\approx24.26.
$$

单位在相除时消去，结果是约 24.26 次。这里只解释题目给定的指标口径。若直接用 2019 年末的 253 作分母，虽然数值都来自正确财报，仍然没有按题意计算。

该样本的证据索引为 68、69，对应 PDF 的第 69、70 页，印刷页码为 F-4、F-5。本次核对了证据文本、原始资产负债表版面和算式。它也说明“跨报表”可以发生在同一个 PDF 内，不必涉及多份文档。共享检索配置下的 GPT-4-Turbo 回答知道需要哪些指标，却表示给定材料没有提供这些数值，被标为拒答；这与算错一个已有数字属于不同失败类型。（[固定版本题目与证据](https://github.com/patronus-ai/financebench/blob/cc39aeb4afdf33909ee1412188bf89035950c2eb/data/financebench_open_source.jsonl)、[财报](https://github.com/patronus-ai/financebench/blob/cc39aeb4afdf33909ee1412188bf89035950c2eb/pdfs/ACTIVISIONBLIZZARD_2019_10K.pdf)、[对应模型回答](https://github.com/patronus-ai/financebench/blob/cc39aeb4afdf33909ee1412188bf89035950c2eb/results/gpt-4-1106-preview_sharedStore.jsonl)）

## 10,231 道题怎样形成

完整 FinanceBench 包含 10,231 组问题、答案与证据，涉及 40 家在美国公开交易的公司，财务材料覆盖 2015—2023 年。三类问题的数据形成方式不同，不能把它们都理解成专家逐题自由撰写。（§3）

| 问题来源 | 数量 | 构造方式 |
| --- | ---: | --- |
| 通用财务问题，domain-relevant | 925 | 25 个问题用于 37 家公司，如分红、经营利润率是否稳定 |
| 专家新写问题，novel-generated | 1,323 | 围绕公司、行业和具体报告写题，每家公司 15—80 题 |
| 指标生成问题，metrics-generated | 7,983 | 专家提取基础指标，程序计算衍生指标，再使用模板生成问答 |
| 合计 | 10,231 | 三类之和 |

通用问题来自财务分析人员讨论、报告阅读及专家访谈。问题不适用于某家公司时，可以标明不适用并解释，例如某些公司的存货或毛利率问题不具有相同含义。专家新写题要求现实、有变化并尽量包含推理；实际抽查发现，其中仍有不少是直接信息提取题。题目来源与最终推理难度因此需要分开看。（§3、§5）

指标生成先从 2015—2022 年的 10-K 中提取 18 类基础指标，涵盖利润表、资产负债表和现金流量表。只有能在单张报表内清楚识别或计算的基础指标才被保留；由于缺失或定义含糊，每份报告通常取得约 14 个。随后程序组合这些指标，例如用净利润与收入得到净利率。最终题目既有直接提取，也有跨年份、跨报表的计算。该部分覆盖 32 家公司，每家公司 135—348 题；通用题与专家新写题各覆盖 37 家公司，三类都出现的公司有 29 家。（§3、附录 C）

模板同时变化开头、结尾、报表称呼、报表顺序和单位。附录 A 记载了两组各 11 个开头、两组各 7 个结尾，以及每类报表 2—3 种称呼。这样的变化增加语言形式，并不自动增加独立的财务推理任务；同一基础指标可能支持多个生成问题。

### 推理分类有自己的分母

论文对通用问题与指标生成问题进行推理分类，共 **8,908 题**，没有把全部 1,323 道专家新写题计入这项全量统计。其中 2,493 题只需提取，5,897 题需要数值推理，518 题属于逻辑推理，约占 28%、66%、6%。指标生成题中的 5,786 道数值推理题，还区分了单张与多张财务报表。不能把这些比例直接写成整个 10,231 题数据集的分布。（§3.1）

全量数据覆盖 9 个 GICS 行业，10-K 对应 9,530 道题，约占 93%；公司和材料的权重并不均匀。附录 E 的公司市值与 S&P 500 标签是原文时期的背景信息，不是持续更新的金融数据。

### 专家与质量检查

项目最初招募 20 名具备财务教育或经验的标注者，经测试、沟通和培训后参与。五人在早期因质量问题退出，其标注被丢弃。剩下的 15 人中，13 人撰写通用与新问题，另外两人各提取略多于 2,300 个基础指标，供程序生成指标题。（§3.2）

一名熟悉财务和机器学习的资深分析师组织并检查工作。项目持续数周，每周抽查每位标注者约 20—25 个案例，约占其工作量的 10%—20%，发现错误后修改并反馈。后期只继续使用四名表现较好的标注者；项目结束时，又检查约 10% 的通用题和新写题。

这是培训、抽查和修订流程，并不是所有题都由两人独立标注后仲裁。论文没有提供全量逐题复核记录、标注者一致性系数或残余错误率估计。部分答案附有解释推导的 `justification`，但这不是每题必填字段；全量通用题和新写题中有 749 条解释。（§3.2、附录 C）

## 公开的 150 题与 2,400 份回答

研究从三类题目各取 50 道，组成公开评测集。通用问题按 25 个题型分层，每个题型取两道；另外两类随机采样。没有按公司、年份或行业分层。这样可以平衡三类任务，但指标题在完整数据中占约 78%，在公开评测中只有三分之一。因此公开总分描述的是这套均衡样本，不能当作按完整题量加权的总体准确率。（§3.3）

本次直接检查固定版本 JSONL：150 个不同问题 ID，三类各 50 题，涉及 **32 家公司、84 个 `doc_name`**。这些是公开样本的计数，不取代全量数据的 40 家公司。

| 数字 | 实际含义 |
| --- | --- |
| 10,231 | 作者构造的完整问题集，未在公开仓库全部发布 |
| 150 | 本文人工评测并公开的不同问题 |
| 16 | 模型、信息配置与部分提示顺序的组合，不是 16 个不同模型 |
| 2,400 | 150 题 × 16 种配置产生的回答记录 |
| 1,200 | 主文表 2 展示的八种配置 × 150 题 |

2,400 份回答不是 2,400 道独立财务题，也不是对每个配置做 16 次重复试验。论文没有把 150 题再拆为训练集和测试集；本文实验也没有进行模型微调。公开后，这些题可能进入后续系统的开发或训练过程，不能再默认它们对所有新模型都是未见样本。

## 五种配置分别提供多少信息

论文测试 GPT-4、GPT-4-Turbo、Claude 2 与 Llama 2。GPT-4-Turbo 的公开结果记录为 `gpt-4-1106-preview`，Llama 2 为通过 Replicate 调用的 70B Chat。GPT-4 与 Claude 2 的记录使用较宽泛的模型名，不能据此恢复每次请求背后的服务端快照。全部原始实验发生在 2023 年 11 月，温度 0.01，最大输出 2,048 tokens，使用默认系统提示。（§4、附录 B；官方结果与 notebook）

| 配置 | 输入和检索范围 | 主要观察对象 |
| --- | --- | --- |
| Closed Book | 只有问题，无外部财务材料 | 模型自身已知信息与拒答行为 |
| Shared Vector Store | 问题检索共享财报库，再把命中的文本提供给模型 | 大检索范围下的端到端回答 |
| Single Vector Store | 预先选好对应财报，只在该报告内检索 | 已知文档条件下的段落查找与回答 |
| Long Context | 预先选好对应财报，把全文或截断后的前部加入提示 | 长文档读取与推理 |
| Oracle | 人工标明的相关证据页直接进入提示 | 消除大部分检索难度后的回答 |

Oracle 提供的通常是完整证据页，而非一句恰好包含答案的短文本。非指标题使用专家所选证据所在的页面；指标题提供计算需要的财务报表。该设置不直接给参考答案，但已经利用人工标注选好了证据，不能当作无需人工辅助的生产系统。（§4）

单文档检索与长上下文也预先知道正确的财报文件。共享检索差、单文档检索好，并不只证明“向量搜索算法不好”：两者同时改变了搜索范围和文档路由所需的信息。长上下文更不是把整个企业资料库一次性放入模型。

### 检索实现与上下文预算

论文使用 LangChain、Chroma 和 OpenAI 的 `text-embedding-ada-002`。固定版本 notebook 用 `PyMuPDFLoader` 提取每页文本，再用 `RecursiveCharacterTextSplitter` 切分，`chunk_size=1024`、`chunk_overlap=30`。这是字符切分配置，不能写成 1,024-token 分块。检索结果通过 `RetrievalQA` 的 `stuff` 链集中加入生成提示。（§4；[评测 notebook](https://github.com/patronus-ai/financebench/blob/cc39aeb4afdf33909ee1412188bf89035950c2eb/evaluation_playground.ipynb)）

`as_retriever()` 没有显式给出 top-k、相似度阈值或重排器，embedding 构造也依赖所装库的默认值。由于依赖版本没有锁定，不宜把今天某个 LangChain 默认参数当作论文明确报告的参数。实验没有系统比较多种 embedding、不同分块、重排或混合检索。

GPT-4-Turbo 与 Claude 2 当时的上下文窗口分别为 128k、100k。正文说超长报告截取前约 95k—100k tokens，附录 B 写 95k。当前 notebook 同时检查 Anthropic 的 95k 和 OpenAI 的 105k token 阈值，并采用两者换算后较短的字符长度；它不是一个独立的“恰好 95,000 GPT tokens”截断器。截断可能丢失后部证据，原文没有逐题报告证据是否被截掉。（§4、附录 B；`get_max_context_length`）

## 人工评分既看答案，也看推导

每份模型回答由研究团队的一人赋予标签，复杂案例共同讨论，各配置再抽取样本复查。标签有三类：（§4.1）

- **正确**：内容正确且推导可以成立。金额用十亿美元而不是题目指定的百万美元、很小的舍入差异可以接受；合理且证据充分的不同定性答案也可以接受。
- **错误**：数字、方向、法律信息或计算不正确。即使最终数字碰巧正确，只要解释明确违背标准答案的证据，仍算错误。
- **未回答**：明确表示缺少必要资料而无法作答。提供查找建议或计算方法仍属于未回答。

若 $C$、$I$、$F$ 分别为三类回答数，本文使用的主要成功率可以写为：

$$
\mathrm{Accuracy}=\frac{C}{N},\qquad
\mathrm{ErrorRate}=\frac{I}{N},\qquad
\mathrm{FailureRate}=\frac{F}{N},\qquad N=C+I+F=150.
$$

这些式子是对评分计数的说明，不是训练损失。错误率与拒答率的分母都包括全部问题；它们并非“在已回答问题中的错误比例”。自动字符串匹配也无法完全替代这种人工规则，因为允许单位换算、近似舍入与不同但有效的理由。

原文没有规定统一的数值容差、发布完整仲裁记录，或提供多人独立评分的一致性统计。模型没有回答、模型答错，以及回答包含幻觉，也不是完全同义的类别。论文的主要数值表统计三类结果，不能把“错误加拒答”直接称为幻觉率。

## 主结果：同一批问题在不同配置下的表现

下表对应论文表 2 的八种配置。括号内百分比由公开逐题标签重新计算到一位小数；长上下文使用答对较多的 `inContext_reverse` 文件，Oracle 使用原表对应的 `oracle` 文件。（[固定版本结果目录](https://github.com/patronus-ai/financebench/tree/cc39aeb4afdf33909ee1412188bf89035950c2eb/results)）

| 模型与配置 | 正确 | 错误 | 未回答 |
| --- | ---: | ---: | ---: |
| GPT-4-Turbo，Closed Book | 14（9.3%） | 5（3.3%） | 131（87.3%） |
| Llama 2，共享检索 | 29（19.3%） | 104（69.3%） | 17（11.3%） |
| GPT-4-Turbo，共享检索 | 29（19.3%） | 20（13.3%） | 101（67.3%） |
| Llama 2，单文档检索 | 62（41.3%） | 81（54.0%） | 7（4.7%） |
| GPT-4-Turbo，单文档检索 | 75（50.0%） | 17（11.3%） | 58（38.7%） |
| Claude 2，长上下文 | 114（76.0%） | 32（21.3%） | 4（2.7%） |
| GPT-4-Turbo，长上下文 | 118（78.7%） | 26（17.3%） | 6（4.0%） |
| GPT-4-Turbo，Oracle | 128（85.3%） | 22（14.7%） | 0（0.0%） |

**原表有一个可核实的计数错误。** Closed Book 一行写成 14、5、126，总和只有 145；公开文件实际为 14、5、131，共 150。本次重新累计八个文件，得到正确 569、错误 307、未回答 324，共 1,200，与原表的总计一致。因此这里使用 131，而没有照搬原表的 126 或 88%。

摘要常被引用的“81%”来自 GPT-4-Turbo 共享检索：$(20+101)/150=80.7\%$。其中大部分是未回答，正确率为 19.3%。Llama 2 在相同检索类型下也答对 29 题，但 104 题给出错误答案，只拒答 17 题。相同准确率掩盖了相当不同的行为分布。

共享库改为单文档库，GPT-4-Turbo 多答对 46 题，准确率上升 30.7 个百分点；Llama 2 多答对 33 题，上升 22.0 个百分点。这支持“缩小到正确文档后，端到端任务更容易”的判断。由于没有逐题检索召回与推理错误的完整分解，不能把这些增加全部精确归因于某一个检索步骤。

GPT-4-Turbo 从长上下文的 118 题正确提高到表中 Oracle 的 128 题，增加 6.7 个百分点。Oracle 仍有 22 题错误，说明有证据不等于一定读对、算对或解释对。论文没有为每个 Oracle 错误确定唯一原因，也没有证明正确证据提取是剩余问题的唯一解法。

### 不同问题类型的差异

按公开标签重新分组，每类分母均为 50。下表给出 GPT-4-Turbo 的正确题数和正确率，作为图 4 的可核对数值。（公开结果按 `financebench_id` 与题目类型连接）

| 配置 | 通用财务题 | 专家新写题 | 指标题 |
| --- | ---: | ---: | ---: |
| 共享检索 | 11 / 50，22% | 12 / 50，24% | 6 / 50，12% |
| 单文档检索 | 24 / 50，48% | 28 / 50，56% | 23 / 50，46% |
| 长上下文，较好顺序 | 34 / 50，68% | 38 / 50，76% | 46 / 50，92% |
| Oracle，表 2 配置 | 42 / 50，84% | 41 / 50，82% | 45 / 50，90% |

指标题在共享检索下最差，全文进入模型后反而最高，说明这组问题的困难不能只归结为算术能力。它们经常需要多个表格位置的数值，而部分通用题可借助常识回答。不过这里没有固定住证据质量单独测试算术，也没有工具计算器消融；这一解释有任务结构支持，尚不是完整的因果分解。

长上下文在这 50 道指标题上比 Oracle 多答对一题，也说明不应把有限样本、单次生成的 Oracle 成绩当作其他配置不可超过的严格数学上界。

## 提示顺序消融存在命名冲突

这是复现时最容易弄反的部分。正文把“材料在前、问题在后”称为 Context-First；附录表 3 却在同名行展示了问题在前的模板。图 2、正文与公开文件在 Oracle 的顺序解释上也没有完全对齐。与其只抄标签，更可靠的是同时记录**实际文本顺序、代码模式和对应文件**。

固定 notebook 的 `get_answer` 显示，普通模式先放问题，`_reverse` 模式先放材料。本次按同名结果文件重算如下：

| 模型与材料 | 问题在前，材料在后 | 材料在前，问题在后 |
| --- | ---: | ---: |
| GPT-4-Turbo，全文 | `inContext`：37 / 150，24.7% | `inContext_reverse`：118 / 150，78.7% |
| Claude 2，全文 | `inContext`：56 / 150，37.3% | `inContext_reverse`：114 / 150，76.0% |

长上下文的两组数据与正文的实质观察一致：把问题放在长材料之后，GPT-4-Turbo 多答对 81 题，Claude 2 多答对 58 题。原文对 Oracle 所写的“反向顺序略好”，若按正文 Context-First 的定义理解，就与当前代码和文件对应关系不一致；这里保留该差异，不用含混的标签代替实际顺序。（§5、图 2、附录表 3；官方 notebook 与结果）

还需要保留一个复现边界：公开结果 JSONL 保存问题、答案与标签，没有保存最终组装后的完整请求。上述文本顺序映射依据固定 notebook，不能独立证明 2023 年每次调用的完整 payload 与当前代码完全相同。`oracle_reverse` 的模板还缺少一个结束方括号，提示措辞也有差别，因此它也不是只交换两段字节、其他字符严格一致的实验。

作者提出，问题在前时，模型经过大量材料后可能丢失对问题的关注。这是对现象的解释；论文没有测量内部注意力或做逐步增加无关长度的受控实验。结果足以支持“这个长文本设置对提示布局敏感”，不足以证明一个适用于所有模型、所有上下文长度的规则。

## 复现时应固定的部分

根据公开代码，可以分成三个层次复核：先检查题目和证据，再重算已公布的人评标签，最后重新请求模型。前两步不需要模型 API；第三步才涉及重新生成答案和重新评分。

以下脚本在固定仓库根目录执行，重算已公布的结果，不会调用模型：

```python
import json
from collections import Counter
from pathlib import Path

def read_jsonl(path):
    return [json.loads(line) for line in path.open() if line.strip()]

questions = read_jsonl(Path("data/financebench_open_source.jsonl"))
ids = {row["financebench_id"] for row in questions}
assert len(questions) == len(ids) == 150
print(Counter(row["question_type"] for row in questions))

for path in sorted(Path("results").glob("*.jsonl")):
    rows = read_jsonl(path)
    assert len(rows) == 150
    assert {row["financebench_id"] for row in rows} == ids
    counts = Counter(row["label"] for row in rows)
    accuracy = counts["Correct Answer"] / len(rows)
    print(path.name, dict(counts), round(100 * accuracy, 2))
```

若重新生成，入口是 `evaluation_playground.ipynb`，但直接从头执行不等于复现论文：

1. 当前 `configs[0]` 已经是 `gpt-4o-2024-05-13`，并非原文 GPT-4-Turbo；配置列表也不再恰好对应原始 16 组。需要明确选定模型、模式、顺序和输出预算。
2. 当前 `ALL_DOCS` 来自所加载问题文件中的文档名。只加载公开 150 题，从空目录构建共享库时实际是 **84 份文档**，不会自动索引全量约 360 份财报。若要重建原文共享检索难度，需要明确重建原始语料清单。
3. `vectorstores` 目录只有说明文件，没有现成索引；需要重新解析 PDF、切块、计算 embedding。依赖未提供完整版本锁，旧版 LangChain、Anthropic tokenizer 等 API 的行为需要单独核对。
4. PDF 提取与分块会影响表格列关系。应保存解析结果、切块、命中文档和页码，并显式固定检索参数，而不是只保存最后答案。
5. notebook 保存生成结果为 CSV，没有自动执行论文的人评流程。重新生成后仍需要按三类规则标注，尤其检查正确数字是否配有错误推导。

本次实际完成的是全文阅读、固定资料下载、公开 2,400 条标签重新计数、分组统计、样本证据与计算核对，以及 notebook 静态检查。没有再次调用历史模型或重新人工标注全部回答；原有标签的准确性也未被本次逐条独立复审。论文未报告完整实验 token 总量、运行时和总费用，不能从 2,400 份回答数反推出精确复现成本。

## 能说明的范围

FinanceBench 证明了在这组问题、这批 2023 年模型与实现下，闭卷、共享检索、已知文档检索、长上下文和证据页输入产生很不同的结果。它同时保留错误与拒答，因而能显示“同样答对 29 题”的模型是否倾向于给出更多错误答案。它没有覆盖所有财务工作，也没有验证后续模型或经过专门优化的检索系统。（§5—§6）

数据仅包含单轮、单家公司、公开上市公司材料，没有跨公司比较、动态追问、私营企业内部文件或投资组合决策。大型上市公司的规范披露也不能代表杂乱、缺页或高度敏感的内部资料。部分题目偏简单，部分定性答案取决于假设；即使参考答案经过专家检查，仍需要保留合理替代解释。

作者提出后续可以尝试微调、few-shot、思维链、计算器和 API 工具。本文没有这些配置的系统实验，不能把它们写成已经得到验证的改进。原文关于长上下文延迟、成本和部署可行性的讨论也对应 2023 年环境；它没有测量今日产品的成本与部署表现。

对这篇工作最有用的复现方式，是保留清晰的题目分母、证据范围、实际提示顺序和人工评分规则。这样，新系统的分数才能与同一任务条件下的结果进行比较。

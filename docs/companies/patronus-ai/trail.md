# TRAIL 精读：沿执行轨迹定位 agent 的错误

一个 agent 没有完成任务，可能是读错了工具结果，也可能是搜索方向偏离、API 限流，或者最后没有按要求提交结果。TRAIL 把检查对象从最终答案扩展到整条执行轨迹：分析模型需要列出发生了哪些错误、对应哪个执行片段，并提供证据。论文报告的最佳模型 Gemini 2.5 Pro，在 GAIA 与 SWE-Bench 两部分的类别与位置联合分数分别为 18.3% 和 5.0%。理解这些低分前，需要先看评分规则：官方代码计算的是**找回多少标准错误位置与类别组合**，并非“整条轨迹完全分析正确的比例”。[论文表 1](https://arxiv.org/pdf/2505.08638v3)、[官方评分代码](https://github.com/patronus-ai/trail-benchmark/blob/0ffbed9db859b4a66250dc783fa4dccf86869595/benchmarking/calculate_scores.py)

## 从最终成败到具体执行片段

TRAIL 中的 trace 是一次任务执行记录，包含多个 span。span 可以对应一次模型调用、工具调用或管理步骤，带有 `span_id`、`parent_span_id`、时间、输入、输出和状态等信息。公开 JSON 还通过 `child_spans` 保存嵌套结构；读取时只遍历最外层列表会漏掉大多数执行片段。

输入并非清理过的短对话，而是采用 OpenTelemetry / OpenInference 格式记录的结构化数据。某次模型调用会再次携带此前对话，工具结果又可能出现在后续消息里，因此记录长度不等于新增信息量。分析器需要区分“错误实际出现的位置”和“后来再次引用该错误的地方”。[原文 §1、§4.1、图 2](https://arxiv.org/pdf/2505.08638v3)

图 2 有一个具体例子：agent 想展示仓库目录的前 20 项，却把目录树字符串逐字符打印，输出变成 `D`、`i`、`r` 等零散字符。标注把它记为格式错误，并给出对应 span ID。另一个片段中，模型计划调用搜索 agent，实际生成的代码却只打印任务描述；这里需要检查“想做什么”和“执行了什么”的差异，不能仅靠异常日志判断。

最终输出是一份错误清单。每条含五个字段：类别 `category`、位置 `location`、原始证据 `evidence`、解释 `description`、影响等级 `impact`。同一个 span 可以包含多个错误；一个任务最后失败，也可能同时包含低影响格式错误和高影响执行故障。错误条数、出错 span 数、失败任务数是三个不同统计单位。

### 定位规则还规定了首次与末次

附录 A.11 要求尽量找全错误，类别使用分类树的末级节点。通常标记某项错误首次出现的位置；`Resource Abuse` 例外，标记最后一次重复滥用资源的位置。

因此，发现中间某次重复调用还不一定满足定位标签。分析器需要按轨迹顺序和父子关系检查相关调用，再把问题对应到标准位置。论文没有要求模型实际修复 agent、重新运行工具或验证补丁；它评测的是对已有记录的离线诊断。

## 分类体系覆盖三种来源

TRAIL 的主要分类把模型判断错误、系统故障和流程管理错误分开。下面保留附录分析提示中的类别名，便于与代码和标注对照。

| 一级类别 | 子类与末级错误 | 判断重点 |
| --- | --- | --- |
| 推理错误 | 幻觉：Language-only、Tool-related | 编造事实、工具结果或工具能力 |
| 推理错误 | 信息处理：Poor Information Retrieval、Tool Output Misinterpretation | 搜索了无关内容，或误解已有工具结果 |
| 推理错误 | 决策：Incorrect Problem Identification、Tool Selection Errors | 误解任务，或选择不合适的工具 |
| 推理错误 | 输出：Formatting Errors、Instruction Non-compliance | 输出或代码结构错误，没有执行要求的任务 |
| 系统执行错误 | 配置：Tool Definition Issues、Environment Setup Errors | 工具定义、权限、环境或密钥设置问题 |
| 系统执行错误 | API：Rate Limiting、Authentication Errors、Service Errors、Resource Not Found | 限流、认证失败、服务故障及资源缺失 |
| 系统执行错误 | 资源：Resource Exhaustion、Timeout Issues | 内存等资源耗尽，或响应超时 |
| 规划协调错误 | 上下文：Context Handling Failures、Resource Abuse | 遗忘约束、状态追踪失败、重复调用 |
| 规划协调错误 | 任务：Goal Deviation、Task Orchestration | 偏离目标，或子任务分配和进度协调失败 |

来源：[原文 §3、附录 A.11](https://arxiv.org/pdf/2505.08638v3)。这些类别并非互斥的因果链。例如一次工具失败后，agent 可能继续编造结果，再偏离原目标；基准允许分别标注，而不是只挑一个最终原因。

正文、提示和代码的类别表也有版本差异。附录提示还列出 `Domain Specific Errors`，当前运行脚本没有这一项；评分器的 21 项列表包含提示中未列出的 `Incorrect Memory Usage`。公开标注有这一类别。复现时必须同时固定提示与评分词表，不能假设论文中的分类树与所有文件完全一致。

## 轨迹由两套 agent 生成

GAIA 部分采用 Hugging Face OpenDeepResearch 的分层结构，管理 agent 与搜索 agent 的底座都是 `o3-mini-2025-01-31`。管理 agent 负责拆分、委派和汇总，搜索 agent 负责检索与页面阅读。附录 A.10 列出的工具包括网页搜索、访问页面、上下翻页、页面内查找、网页存档查询和文件读取；管理侧还可使用图像问答工具。研究选择的是原任务集中的文本输入实例，不能因编排含有图像工具，就把 TRAIL 称为已验证多模态错误诊断的基准。

SWE-Bench Lite 部分采用单 agent 的 CodeAct 流程，底座为 `claude-3-7-sonnet-20250219`。它通过 Python 解释器和 `gitingest` 读取仓库，按“思考—代码—观察”继续执行，并最终生成可应用的补丁。

作者额外加入限制来引出错误：必须先读取仓库摘要和目录；文件内容通过内存字符串及正则表达式提取；不能用 git 命令探索；不能整段打印文件；分析内容时每次最多 500 个字符。这些是数据构建设置的一部分，意味着轨迹虽然来自真实问题，错误分布仍受到研究者设计的提示影响，不能直接当作任意生产 agent 的故障比例。[原文 §4.1、附录 A.10、A.12](https://arxiv.org/pdf/2505.08638v3)

## 专家标注及质量检查

四位具有软件工程和日志调试经验的标注者，按顺序检查模型与工具 span，为错误填写类别、位置、证据、解释和影响等级。除此之外，他们还给整条轨迹打四项分数：可靠性、安全性、指令遵循、计划质量。人工 rubric 使用 1–5 分，分数越高表示表现越好。

论文另安排四轮由机器学习研究者进行的验证。GAIA 首轮标注平均约 30 分钟，SWE-Bench 约 40 分钟；按每轮验证增加 20 分钟，论文估计总投入分别约 110、120 分钟。报酬为每条轨迹 12.66 美元；这项报酬描述不能自动理解为四轮研究者复核的全部费用。标注者不会去轨迹之外重新查网页或验证外部资料，因为基线分析模型同样没有执行这些操作。[原文附录 A.7、Ethics Statement](https://arxiv.org/pdf/2505.08638v3)

质量检查详细报告了 63 条轨迹：30 条 SWE-Bench、444 个 span 中约 5.63% 被修改；33 条 GAIA、697 个 span 中约 5.31% 被修改。作者把较低修改率视为一致性较高的证据。这里没有报告 Cohen’s κ 或 Krippendorff’s α，也不能把“约 95% 没改”当成独立专家在所有错误标签上逐项一致的概率。

### 数据总数需要分版本阅读

正文报告 148 条轨迹、841 个错误、1,987 个 span，其中 575 个至少含一个错误；错误平均约 5.68 个。§4.3 报告有错误的轨迹为 GAIA 114 条、SWE-Bench 30 条。

附录表 5 却列出 GAIA 118 条、SWE-Bench 31 条，合计 149；错误分别为 579 与 256，合计 835。它与正文并不完全一致。本文没有把其中一组数字静默改成另一组。

| --- | ---: | ---: | ---: |
| 原始轨迹文件 / 对应标注文件 | 117 / 117 | 31 / 31 | 148 / 148 |
| 含错误的轨迹 | 114 | 30 | 144 |
| 错误条目 | 585 | 256 | 841 |

这些是[官方代码仓库固定提交内数据](https://github.com/patronus-ai/trail-benchmark/tree/0ffbed9db859b4a66250dc783fa4dccf86869595/benchmarking)的本地统计，不是原文表格的重排。GAIA 有一个标注文件在错误数组末尾多出逗号，严格 JSON 解析会失败；表中错误数使用临时解析时明确移除该尾逗号后的内容，未改变任何标签或提交修改。保留原文件直接解析时，该条中的 5 个错误不会进入统计。

递归统计包含全部父子 span，论文没有提供足以恢复其 1,987 个 span 筛选口径的脚本，因此不能直接把 4,626 与 1,987 的差异归因于某一种重复。SWE-Bench 还有两个错误的位置是 `Span ID not found for this shard`，不是原始轨迹中的有效 span ID；其他已核对错误位置均能在对应轨迹找到。

论文说格式错误与指令不遵循合计 353/841，约 42%，并指出系统执行错误较少、部分罕见错误影响却很高。由于标注存在大小写、单复数及拼写变体，重新统计各类别时还需要公开归一化规则。总体上的类别不均衡已经足以说明：高频类别的表现不能替代对稀有 API 故障的单独检查。[原文 §4.3、图 3、图 6](https://arxiv.org/pdf/2505.08638v3)

## 评分代码中的三个指标

论文表 1 报告类别 F1、位置准确率和联合准确率。正文没有完整写出公式，以下根据固定版本 `calculate_scores.py` 解释实际实现。

### 类别 F1 只判断该类是否在轨迹中出现

对轨迹 $i$ 和类别 $k$，标准标签 $y_{ik}$ 表示该轨迹是否包含至少一个此类错误，预测 $\hat y_{ik}$ 同理。同一种错误出现十次，在这个二元向量中仍只记一次。

先在所有已处理轨迹上为各类别统计 TP、FP、FN，得到：

$$
F_{1,k}=\frac{2TP_k}{2TP_k+FP_k+FN_k},\qquad
F_{1,\mathrm{weighted}}=\frac{\sum_k s_k F_{1,k}}{\sum_k s_k},
$$

其中 $s_k$ 是包含类别 $k$ 的标准轨迹数；分母为零时按代码记 0。它是按类别支持度加权的多标签 F1，不是对所有错误条目逐项分类的准确率，也没有要求该类别出现在正确位置。

### Location 与 Joint 使用标准集合做分母

设 $L_i$ 是标准错误位置集合，$\hat L_i$ 是预测位置集合；$P_i$ 是标准的 `(位置,类别)` 去重集合，$\hat P_i$ 是预测组合。代码计算：

$$
\mathrm{Loc}_i=\frac{|L_i\cap\hat L_i|}{|L_i|},\qquad
\mathrm{Joint}_i=\frac{|P_i\cap\hat P_i|}{|P_i|}.
$$

之后对成功处理的轨迹等权平均。如果标准集合为空，代码将对应分数置 0，即使预测也为空。

这两个公式实际是召回形式：漏掉标准位置会扣分，额外报出错误位置不会直接扣分。类别 F1 会惩罚错误地声称某个类别存在，但如果额外报告的类别本来就在这条轨迹中，它也不一定降低类别 F1。

说明示例：标准有 `(s1,格式错误)`、`(s2,语言幻觉)` 两项，只找回第一项时，Loc 与 Joint 都是 0.5。找回两项后再多报 `(s3,格式错误)`，两项分数仍是 1。本文用官方两个指标函数执行了这一小例子，验证其行为；没有因此运行模型评测。

所以“Joint 为 18.3%”既不等于 18.3% 的轨迹被完整诊断，也不等于所有预测中 18.3% 正确。它同时要求类别和位置匹配，但匹配后仍以标准集合为分母。[固定评分实现](https://github.com/patronus-ai/trail-benchmark/blob/0ffbed9db859b4a66250dc783fa4dccf86869595/benchmarking/calculate_scores.py)

### 证据和解释没有进入这些匹配公式

模型虽然要生成证据、描述和影响等级，以上三个指标没有对其文本质量单独打分。模型可能在类别和位置上命中，却给出薄弱的解释；这些分数无法直接识别这种情况。整体质量分则另行计算与人工打分的 Pearson 相关系数，也不是逐条验证解释是否成立。

## 实验设置与长上下文限制

分析器一次读取整个原始 trace JSON，加上分类体系、格式模板和少量输出示例。非推理模型使用温度 0、`top_p=1`；推理模型使用接口默认采样配置，并在主表设置较高推理强度。Llama 4 通过 Together AI 调用。表 1 的结果是三次运行平均。[原文附录 A.3、表 1 脚注](https://arxiv.org/pdf/2505.08638v3)

代码通过 LiteLLM 请求最多 8,000 个 completion token，推理模型传入 `reasoning_effort="high"`。这不等于每个供应商都给出同样长度的可见解释；参数兼容层启用 `drop_params`，具体保留哪些参数还依赖运行库和模型接口。

表 2 使用不同 tokenizer 测量原始输入与人工标注输出，部分数值如下：

| 部分 / tokenizer | 输入均值 | 最大输入 | 人工输出均值 |
| --- | ---: | ---: | ---: |
| GAIA / GPT-4.1 | 286.85K | 7.50M | 1.11K |
| GAIA / Gemini 2.5 | 313.49K | 8.25M | 1.20K |
| SWE-Bench / GPT-4.1 | 616.92K | 2.05M | 1.71K |
| SWE-Bench / Gemini 2.5 | 698.09K | 2.21M | 1.88K |

单位为 token，K 为千、M 为百万。输出一列是**人工标注 JSON 的长度**，不能称为模型实际推理消耗。表 2 把 `gpt-4.1 (=o3)` 放在 tokenizer 一行并列出 1M 输入上限；共享 tokenizer 不意味着 o3 与 GPT-4.1 拥有相同上下文窗口。主表也明确把 o3 的 SWE-Bench 结果标为上下文不足。

这类数据不仅考察能否理解因果过程，也考察能否读入长 JSON。原始调用输入可能包含反复积累的历史，因此不能将数百万 token 全部解释成数百万 token 的独立任务证据。[原文表 2、图 5](https://arxiv.org/pdf/2505.08638v3)

### 上下文失败会影响评测分母

固定运行脚本在上下文超限或其他接口失败时保存一段错误文字。评分脚本发现 JSON 无法解析，会跳过该文件；缺少预测文件也会跳过。最终平均的分母是成功加载并解析的文件数，而不是自动保留全部 148 条。

论文没有逐模型公布这些被排除文件的完整清单。因此在复现时，必须同时报告总题量、有效输出量、上下文失败量及解析失败量，不能只比较有效子集上的分数。这里不把 `CLE` 擅自记作零分，也不假定所有模型在 GAIA 上看过完全相同的样本。

## 主结果：分类与定位表现并不一致

以下保留论文表 1 数值，范围为 0–1，越高越好。`CLE` 表示上下文不足。

| 模型 | GAIA 类别 F1 | GAIA Loc | GAIA Joint | SWE 类别 F1 | SWE Loc | SWE Joint |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Llama 4 Scout | 0.041 | 0.000 | 0.000 | 0.050 | 0.000 | 0.000 |
| Llama 4 Maverick | 0.122 | 0.023 | 0.000 | 0.191 | 0.083 | 0.000 |
| GPT-4.1 | 0.218 | 0.107 | 0.028 | 0.166 | 0.000 | 0.000 |
| o1 | 0.138 | 0.040 | 0.013 | CLE | CLE | CLE |
| o3 | 0.296 | 0.535 | 0.092 | CLE | CLE | CLE |
| Claude 3.7 Sonnet | 0.254 | 0.204 | 0.047 | CLE | CLE | CLE |
| Gemini 2.5 Pro Preview 05-06 | 0.389 | 0.546 | 0.183 | 0.148 | 0.238 | 0.050 |
| Gemini 2.5 Flash Preview 04-17 | 0.337 | 0.372 | 0.100 | 0.213 | 0.060 | 0.000 |

Gemini Pro 的 GAIA Loc 为 0.546，Joint 却只有 0.183，说明“发现有问题的位置”与“把位置配到正确类别”是不同要求。Flash 的 SWE 类别 F1 高于 Pro，但 Joint 为零；能指出轨迹包含某类问题，不等于能找到它发生的 span。

摘要概括最佳模型跨两部分约为 11%。表中 0.183 与 0.050 的简单平均为 0.1165，按公开文件数加权又会得到另一结果；原文没有给出足以精确复算摘要数字的聚合说明。本文采用明确披露的分项，不把 11% 当作一个已经重算验证的总体成功率。

### 整体打分相关性不能代替错误定位

主表另外报告与人工整体分数的 Pearson 相关：Claude 在 GAIA 为 0.738，Gemini Pro 在 SWE 为 0.817。它们衡量轨迹质量分的共同变化，不衡量错误位置召回率，也不能说明两个评分数值本身一致。

附录表 6 的安全性相关系数全部写作 1.00。本次核对公开标注，148 条安全分均为 5。对常量标准序列，Pearson 相关系数分母为零，数学上未定义；官方评分脚本调用 `scipy.stats.pearsonr`，没有明确把这种情况定义成 1 的规则。因此不能把表中的 1.00 解释为已经验证的“安全判断完美相关”。此外，表 6 分项与主表 Overall 相关并非同一统计量，不应简单平均互相替代。[固定评分代码](https://github.com/patronus-ai/trail-benchmark/blob/0ffbed9db859b4a66250dc783fa4dccf86869595/benchmarking/calculate_scores.py)

## 推理强度消融与错误类型分析

附录 A.4 在同一个 o3 上调整推理强度，实验实际列的是 GAIA，尽管表 4 的标题同时提到两部分。

| o3 推理强度 | 类别 F1 | Loc | Joint |
| --- | ---: | ---: | ---: |
| low | 0.264 | 0.331 | 0.071 |
| medium | 0.277 | 0.373 | 0.104 |
| high | 0.296 | 0.535 | 0.092 |

类别 F1 和 Loc 随强度提高而上升；Joint 在 medium 最高，high 反而低 1.2 个百分点。正文 §5.1.5 说三项指标都随强度降低而下降，与表 4 不完全一致。实验支持更多推理有助于部分指标，不能写成所有指标都单调改善。论文没有同时给出每档实际 token 消耗、成本或置信区间，所以也不能据此确定最划算的推理预算。[原文表 4](https://arxiv.org/pdf/2505.08638v3)

不同模型之间的推理与非推理比较还同时改变了训练、规模和服务接口，不能将全部差异归因于是否有推理链。同模型强度实验比跨模型排名更接近受控比较，但也没有保持实际计算量完全一致。

按类别看，图 4 中上下文处理失败几乎全部为零，Claude 达到 0.18；工具选择错误上 o3 达到 0.53；任务编排上 Gemini Flash 为 0.47，而多数其他模型仅为 0–0.08。格式错误也并非总由推理模型领先：GPT-4.1 为 0.43，高于 o3 等部分推理模型。各类别支持度不同，长尾分数不适合脱离样本量比较。[原文 §5.1.6、图 4](https://arxiv.org/pdf/2505.08638v3)

表 3 报告输入长度与 Loc、Joint、类别 F1 的 Pearson 相关分别为 −0.379、−0.291、−0.296，Spearman 分别为 −0.508、−0.349、−0.225。这是负相关观察，不能单独证明长度导致失败：较长轨迹也可能包含更多错误、更复杂任务和重复历史。论文没有在同一条轨迹上通过等价压缩或分段对照隔离这些因素。

## 从一条公开标注理解错误传播

公开 GAIA 轨迹 `a96c6811716c0473b86a23321db79c34` 要求根据指定 CSV 与特定时间的维基百科信息完成计算。标注记录的过程是：读取 CSV 时文件不存在；agent 随后假设企鹅总数为 2,000 万，并把它描述成来自此前研究；最终基于模拟数据与假设值给出答案。

同一调用 span 因而包含不同层面的错误：文件缺失被归为环境设置问题，未经证据支持的数字被归为语言幻觉，跳过必要来源被归为信息检索问题；最终输出所在 span 又被标为目标偏离。这说明 TRAIL 不是把第一条异常后面的所有步骤都算成同一个错误，而是分别记录可诊断的行为。

这是对[作者公开标注](https://github.com/patronus-ai/trail-benchmark/blob/0ffbed9db859b4a66250dc783fa4dccf86869595/benchmarking/processed_annotations_gaia/a96c6811716c0473b86a23321db79c34.json)的整理，本文没有去外部核查真实企鹅数量，也没有重新执行这条任务。该文件恰好包含前述尾逗号问题；错误语义与文件语法质量需要分别检查。

### 评分前需要显式处理的细节

- **标注语法与类别变体。** 一个 GAIA 标注含尾逗号；部分类别有大小写、拼写或后缀差异。代码只做有限的大小写、空格及单向子串归一化，不能保证所有变体都合并。例如多余的 `Errors` 后缀不一定自动对应到 `Task Orchestration`。
- **无效位置。** 两项标准位置没有真实 span ID。保留、排除或改标都会影响分母，应把处理方式和原始成绩分开报告。
- **解析失败与缺失输出。** 官方代码会跳过，复现报告应显示有效样本覆盖率。若改为计零，需要另报新口径。
- **分数范围。** 人工 rubric 为 1–5，输出模板注释写 0–5；评分代码又会把数值 0 当成缺失替换为 −1。不能把它当作已校准的统一量表。
- **推理预算。** 主程序把推理强度硬编码为 high，没有暴露 medium、low 命令参数。重做表 4 需要显式修改配置并记录实际接口参数。

本次执行了公开数据的文件数、标注、位置和分数分布检查，并用官方指标函数核对了说明示例。**未调用评测模型，未重算论文模型成绩，也未重建原 agent 轨迹。** 当前代码没有附带足以逐项恢复三次实验的全部原始预测文件。

## 适用范围

TRAIL 提供了一个可操作的诊断接口：按执行片段记录错误类别和证据，把 agent 的问题分解到模型判断、系统调用和任务管理。它覆盖两类真实任务，但生成轨迹的底座和编排较集中，SWE 提示又特意加入限制，因此不能从样本频率直接推断所有 agent 的故障分布。

这项研究也没有验证诊断能否真正提高修复成功率，或者能否在在线执行中提前阻止错误传播。主指标未单独评估解释、影响等级及误报成本，长上下文失败还可能改变有效评测集合。使用它比较分析器时，分项指标、覆盖率、标准数据版本和具体评分实现，应当与模型名称一起保留。

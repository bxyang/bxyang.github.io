# MEMTRACK：在消息、工单和代码之间保持工作记忆

## 1. 摘要翻译

以下译自所列版本摘要，原文采用 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) 许可。

近期的上下文与记忆基准研究主要关注对话实例，但要有效应用记忆，就必须在动态企业环境中评估它。我们提出 MEMTRACK，一个旨在评估多平台智能体环境中的长期记忆与状态追踪的基准。MEMTRACK 整合 Slack、Linear 和 Git 等多个通信与生产力平台上的异步事件，模拟现实组织的工作流程。每个基准实例提供一条按时间排列、平台交错的时间线，其中包含噪声、冲突与相互引用的信息，也可能需要理解和探索代码库或文件系统。因此，该基准测试记忆获取、选择和冲突解决等能力。我们通过人工专家设计与可扩展的智能体合成两种方式整理 MEMTRACK 数据集，生成以现实软件开发过程为基础、贴近实际的场景。我们提出正确性、效率和冗余等相关指标，用于衡量记忆机制在简单问答表现之外的有效性。对先进大语言模型和记忆后端的实验揭示了长期使用记忆、处理跨平台依赖及解决矛盾方面的困难。值得关注的是，表现最好的 GPT-5 模型在 MEMTRACK 上也只获得了 60% 的正确性得分。这项工作提供了一个可扩展框架，推动带有记忆的智能体评测研究超越现有的对话场景，并为复杂组织环境中的多智能体、多平台记忆基准奠定基础。MEMTRACK 的实例已提供公开访问。

## 2. 研究背景与相关研究

工作信息通常分散在不同地方：消息里提出问题，工单中补充条件，代码提交又改变了实际状态。助手需要知道哪些消息仍然有效、哪些已经被后续讨论推翻，以及一个平台上的线索应该去哪里继续查找。记住原句并不足以完成这些任务。（论文 §1）

LoCoMo、LongMemEval 等基准主要考查对话历史中的长期信息。MemoryAgentBench 扩展了记忆能力的任务类型；MemGPT、Mem0、Zep 等方案则通过文件、向量库或图结构保存信息。本文认为，评测还需要把获取、使用和维护记忆放进连贯工作场景，而不是只检查从长文本中找出答案。（论文 §2）

MEMTRACK 因此将工具使用与记忆联合考查。它不规定智能体必须使用某一种记忆架构，而是建立相同的跨平台环境，让不附加记忆组件的系统、使用 Mem0 的系统和使用 Zep 的系统完成同类任务。（论文 §1、§4）

## 3. 核心贡献

**核心要解决的问题。** 测量智能体能否在分散、相互关联且存在冲突的工作记录中建立可继续使用的上下文，并在后续追问时有效利用它。

**核心方案。** 基准包含 47 个实例。每个实例把消息、工单与 Git 信息组织成一条历史时间线，加载到隔离的环境中；智能体通过工具访问相关内容，而不是一次性拿到全部事件文本。问题按顺序提出，智能体事先不知道后面共有多少个问题。（论文 §3）

任务既来自专家描述的工作场景，也来自已有开源项目的已解决问题及合并记录；后者再扩展成关联的消息和工单。作者还使用人工与模型共同迭代的方法加入干扰、冲突及跨平台引用。评分同时观察答案正确性、工具调用数量所反映的效率，以及已经获取的信息是否被重复查询。（论文 §3—§4）

**结论。** 论文中的 GPT-5 配置正确性约为 60%，附加 Mem0 或 Zep 没有带来稳定的明显改善；Gemini 2.5 Pro 在这些设置下的得分更低。系统通常能成功执行工具调用，但这不等于能选出、保留并组合正确的信息。过程分析观察到重复打开工单、重复读取文件等现象，追问表现也有所下降。（论文 §5、表 3—表 4）

这些发现说明，接入记忆工具和有效使用记忆是两件需要分别评测的事。结论针对本文的少量实例与默认后端设置，不能概括为记忆系统普遍无用。该版本主要查询预先构造的事件历史；让智能体主动发消息、创建工单并改变之后的组织时间线，仍列在后续研究中。（论文 §6）

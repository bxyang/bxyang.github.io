# MEMTRACK：在 Slack、工单和代码之间保持工作记忆

一个同事在 Slack 里提到“上次那次配置问题”，另一段讨论指向 Linear 工单，最终答案可能藏在指定版本的代码中。MEMTRACK 将这样的工作记录组织成模拟环境，让 agent 通过工具逐步获取信息，再连续回答相关问题。论文比较不带额外记忆组件、使用 Mem0、使用 Zep 的系统；GPT-5 的平均正确性软分数约为 0.60，加入记忆组件没有带来明显的数值提升。理解这个结果，需要同时看问题怎样合成、后续问题怎样出现，以及正确性和工具冗余究竟怎样评分。

## 记忆发生在信息获取和连续追问之间

LoCoMo、LongMemEval 等工作主要从对话历史中测试信息保留与检索。MEMTRACK 把工作材料分散到 Slack、Linear、Git 和文件系统：模型先决定查什么，取得材料后再理解人物、时间、工单状态和代码之间的关系。记忆不仅是从已给定的长文本中找到一句话，也包括主动收集、选择保存、复用和更新信息。（§1—§2）

一个实例包含事件时间线 $T_i=(e_{i,1},\ldots,e_{i,m_i})$，以及按顺序提出的问题与参考答案。事件带有时间、平台和内容，例如聊天消息或工单状态更新。评测模型不能直接读取整份事件 JSON，只能通过环境工具获取对应记录。各问题严格顺序出现，模型事先不知道这一实例总共有几问，因而无法预先按照整套问题一次性规划检索。（§3）

这一区别直接影响评测条件。如果把全部问题和完整事件历史一次性放进提示，再让模型回答，执行的就是另一种任务。类似地，回答第二问时清空此前的对话和工具记录，也会改变论文希望观察的连续记忆使用。

论文描述的系统由事件解析器、容器化平台服务、异步监控和评分器组成。事件解析器区分直接提供的事件与需要模型补充生成的事件；后者使用 Claude 4 Sonnet，然后把事件注入环境。环境使用 Slack、Linear、通知服务、文件系统及 Gitea Git 服务。图 1 展示了任务生成、事件注入、agent 执行与逐题提问、结果评估四个阶段。（§3、图 1）

时间线跨度是故事内部的历史时间，并非评测必须等待的实际时长。论文的“平均 878 小时”不能解释为一个 agent 连续运行了 36 天。当前公开数据只有事件与配置，尚不足以独立核对原始执行器如何调度事件、何时让每条记录对 agent 可见。

### 一个原文轨迹说明的任务

附录 B.1 给出 NeMo-Run 场景中的三个问题。第一问综合讨论和代码，要求统计测试文件中工厂函数默认参数的数值之和，参考答案为 547；第二问要把“今天”“上个月”等相对时间还原，确定首次报告问题的日期，答案为 2025-05-15；第三问追溯早期关于 batch size 的讨论，查询指定提交中 `nemo_run` 目录下 Python 文件首次出现数字 32 的确切行号，答案为 142。

示例 agent 先克隆代码，列目录、读测试文件、搜索函数，再查工单与消息。第一问输出 4858.9001，被判错；后两问分别得到正确日期与行号。作者报告该实例共 42 次工具调用、7 次平台切换。展示的轨迹包含省略号，因此可以理解步骤，但不能从论文摘录独立重建全部调用和运行状态。（§5.2.1、附录 B.1）

这个案例同时包含代码理解、指代消解、时间推理和信息复用。一次失败不能自动归因于“记忆丢失”：它也可能来自检索、范围判断、计算或代码版本。行号题尤其依赖固定提交，换成仓库最新分支后，原答案未必继续成立。

## 47 个实例不是 47 道问题

论文报告 **47 个实例**。每个实例是一套环境与一串问题，平均 3.2 问，最多 5 问。这是实例级数据集，不能把 47 当作独立问答数，也不能用四舍五入后的 $47\times3.2$ 推导精确问题总数。（§3、表 1）

表 1 用七个统计量描述事件历史：

| 统计项 | 每实例平均 | 最大值 | 具体含义 |
| --- | ---: | ---: | --- |
| 事件数 | 39.9 | 115 | 时间线中的记录数量 |
| 事件 token 数 | 4.01k | 11.1k | 事件文本体量，不包括完整代码库和所有运行输出 |
| 平台分布熵 | 0.668 | 0.989 | 事件在不同平台之间是否均匀分布 |
| 跨平台引用事件数 | 2.1 | 19 | 由模型判断事件是否指向其他平台 |
| 相邻事件跨平台比例 | 0.364 | 0.714 | 按时间排列时，相邻两事件来自不同平台的比例 |
| 时间跨度，小时 | 878 | 3,049 | 最后与最早事件时间之差 |
| 问题数 | 3.2 | 5 | 初始问题及后续追问 |

设某平台事件占比为 $p_k$，平台熵为 $H=-\sum_k p_k\log p_k$。相邻跨平台比例可以写成：

$$
\mathrm{SwitchRate}(T_i)=
\frac{\sum_{j=1}^{m_i-1}\mathbf1[\operatorname{platform}(e_{i,j})\ne\operatorname{platform}(e_{i,j+1})]}{m_i-1}.
$$

这里描述的是**事件历史的分布**，不同于后面表 3 中 agent 实际调用工具的分布。较高的平台熵也不自动证明每道题必须访问所有平台。

跨平台引用由 LLM judge 对 Linear、Slack、Git 引用分别给出 0—1 软分数，超过 0.3 视为引用其他平台；例如一条 Slack 消息提到某个工单或 PR。附录 A.3 提供提示，但没有人工一致性验证。因此它是一种数据结构检查，不是对跨平台推理能力的直接人评。（表 1、附录 A.3）

## 三种构造方法与主动增加难度

### 从真实 issue 和合并 PR 反推情境

Bottom-Up 方法先选常用开源仓库，让能搜索网页和执行 shell 的探索 agent 查找已关闭 issue、对应的已合并 PR 及相关讨论。选择偏向只改一两个文件、答案能够明确验证的 PR。两名人工标注者审查候选，移除没有明确答案的案例。（§3）

随后另一个 agent 根据 issue、讨论和解决方式生成 Slack 对话与 Linear 工单，再加入与场景相符的干扰内容和反事实信息，人工检查最终时间线。问题依据生成的组织情境和真实 PR 的实际解决方式形成。真实的是部分代码与 issue 背景，周围的组织沟通主要是合成的，不能称为收集来的真实企业 Slack 历史。

### 从专家经历生成事件

Top-Down 方法由四名具有跨团队产品与工程经历的内部专家描述工作场景，再由模型将描述扩展为时间线。专家检查并调整生成结果，随后人工写问题和参考答案。（§3）

附录 A.1.2 的例子是产品图片搜索：团队最初把“描述”理解为商品目录文本，后来发现需求其实是用户自己的描述，于是需要更换实现并建立新工单。旧讨论不是凭空错误，而是在后续需求澄清后失效。这类情境用于观察 agent 是否能区分最初方案与后来确认的状态。

### 人工与模型交替调整

Hybrid 方法从专家给出的动机、目标和代码背景出发，让标注者与模型多轮交互，逐步增加事件复杂度、调整问题和场景，最后由人工尝试解答，检查任务是否有可达的答案。（§3）

附录比正文更明确地说明了**按模型表现增加难度**：生成提示要求，如果被测模型通过了全部问题，就继续修改；完成后若模型仍能回答，则在问题复杂度或事件历史复杂度上进一步增加困难。附录同时要求跨来源多跳、多个平台切换、模糊但可消解的指代，以及干扰话题、被放弃的方案和后续状态变化。（附录 A.1.1）

这些是生成要求，不能直接当作每个发布实例都经过独立验证的最少跳数或平台切换数。作者也没有公布每个实例经历几轮难化、各轮采用哪个筛选模型、原始候选的淘汰比例。因此该数据反映经过选择与迭代的困难场景，不是随机采样的企业工作请求；模型得分不能解释为实际办公室任务的自然失败率。

人工参与也没有形成完整的评分可靠性报告。原文说明了审核与手动尝试，但没有给出全量双人独立答题、一致性系数或最终错误率估计。尤其对于合成沟通与代码联合决定的答案，事件自洽与版本一致都需要单独检查。

## 被比较的 agent 与记忆组件

主实验使用 GPT-5 和 Gemini 2.5 Pro，各比较三种条件：（§4.1）

| 条件 | 额外组件 | 可观察的区别 |
| --- | --- | --- |
| NoMem | 不加入额外的 agent 内记忆后端 | 依靠当前执行过程已有的信息与普通环境工具 |
| Mem0 | 增加 Mem0 记忆组件 | agent 可保存、搜索和取得记忆 |
| Zep | 增加带知识图谱机制的 Zep 组件 | 在类似的工具接口下使用另一种记忆后端 |

NoMem 不是“模型没有上下文”，而是没有论文比较的额外记忆组件。附录 B.5 列出 `store_memory(content, metadata)`、`search_memory(query, limit=5)`、`get_memories(limit=10)`，意味着 agent 需要把新增能力纳入工具选择。

作者说 Mem0 与 Zep 使用各自 API 的默认配置，Mem0 使用 ChromaDB。原文还将 GPT-4o-mini 描述为用于“LLM-based embeddings”，但未给出独立 embedding 模型标识、维度或实际配置。公开数据包没有 Mem0 接入源码，不能把这句话擅自改写成某个具体的 `text-embedding-*` 型号，也不能把 GPT-4o-mini 当成已核实的向量 API。该配置需要额外实现资料才能复现。（§4.1）

实验温度为 1，主结果平均五次运行。论文没有完整列出每组模型的日期快照、推理预算、最大输出长度、对话截断策略、工具失败重试以及后端版本。公开 YAML 中的默认模型也不等于主表全部条件，后文会区分。

## 正确性是可以给部分分的评分

对实例 $i$ 的第 $j$ 个问题，评测器使用问题 $q_{ij}$、参考答案 $a^*_{ij}$ 和模型答案 $a_{ij}$，让 GPT-4o 给出评分。附录 A.2.1 的输出包括 `score`、`is_correct`、`confidence` 和解释。其中 **`score` 是 0—1 软分数**；正确性均值不应使用另一字段 `is_correct` 的布尔值替代。（§4.2）

提示允许语义等价、部分正确、对歧义的合理理解。例如参考答案需要两个人名，只答出其中一个，可以得到 0.5 分，但 `is_correct=false`；多给信息也不一定扣分。因而主表的 0.601 不是“60.1% 的题完全正确”，更不是“60.1% 的实例全部完成”。

按正文与表 3 的实例级口径，可将单次运行写为：

$$
s_{ij}=J(q_{ij},a^*_{ij},a_{ij})\in[0,1],
\qquad
C_i=\frac{1}{n_i}\sum_{j=1}^{n_i}s_{ij},
\qquad
C=\frac{1}{M}\sum_{i=1}^{M}C_i.
$$

其中 $n_i$ 是实例问题数，$M$ 是实例数；主表再对五次运行取平均。不同实例先各自平均，每个实例权重相等，不能简单把全部问题拼成一个分母。**说明示例：**实例 A 只有一问且得 1 分，实例 B 有三问且全部得 0 分，实例宏平均为 0.5，问题级平均却为 0.25。

原文没有发布评分执行器，因而没有办法从公开包核实答案提取、无输出时的分数、judge 重试与跨运行聚合的全部细节。提示也没有给出关于额外错误信息的完整判定协议。本文解释的是已写明的公式与提示规则，不把自动评分当作经过完整人类验证的真值。

## Efficiency 衡量调用次数，不是时间或金额

令 $c=|TC|$ 为工具调用数量，论文设置阈值 $TC_{\min}=10$，定义：

$$
E(c)=\exp\left(-\max\left(0,\frac{c-10}{10}\right)\right).
$$

少于或等于 10 次都得 1 分；20 次约为 0.368，30 次约为 0.135。这个函数对超过阈值的调用施加指数惩罚。数字 10 是统一阈值，不是通过最优轨迹证明的每题最低必需调用数。（§4.2）

这个分数没有直接计入 token、响应延迟、API 价格或后端计算量。一次列出很多工单与一次读取一个小文件，在计数中各占一次；少调用但答错，仍可能得到很高的 Efficiency。因此需要和 Correctness 一起阅读。

对于非线性函数，平均效率不等于把平均调用数代入公式。**说明示例：**两条轨迹分别调用 10、30 次，平均效率为 $(1+e^{-2})/2\approx0.568$；先平均到 20 次再算只有 $e^{-1}\approx0.368$。表 3 的平均调用数不能用于反推原始效率列。论文未发布逐轨迹分数及完整聚合代码，也没有明确覆盖每一种失败调用或记忆内部调用的计数边界。

## Redundancy 的正文定义与评分提示不一致

正文把冗余定义为：后面的工具调用取得的信息，与此前调用重复，或已经被此前的结果覆盖。若第 $j$ 次调用晚于第 $k$ 次，且它需要的信息满足 $TC_{i,j}\subseteq TC_{i,k}$，就可能构成冗余；总体分数为冗余调用数除以全部调用数。（§4.2）

这里的包含关系指信息范围，不是比较两个工具名称的字符串。模型评分器需要软匹配参数与查询语义，例如对同一工单反复读取，或者先获取全体工单、再取得已包含其中的一条。

附录 A.2.2 的实际提示却提供另一方向的规则：

| 情况 | 附录提示的处理 |
| --- | --- |
| 同一工具、近似参数重复 | 冗余 |
| 语义相同的查询，如 done / completed | 冗余 |
| 先 `get_ticket(id1)`，再 `list_tickets()` | 将包含先前单条信息的宽查询视为冗余 |
| 自然地从一般信息缩小到具体信息 | 不冗余 |
| 完全不同的工具 | 不冗余 |

“先具体、后宽泛”与正文“后者已被前者包含”不是同一判定方向；“不同工具不冗余”又与前面的跨工具例子存在张力。实际列表接口是否返回详细字段，也会影响覆盖关系。公开包没有冗余 judge 的运行代码与逐调用标注，因此无法确认主表每个分数究竟遵循哪一套规则。本文保留原表结果，同时明确它的语义不能无条件等同于客观的重复取数比例。

提示 JSON 还要求返回 `efficiency_score = 1 - redundancy_fraction`。这个字段是冗余的补数，**不同于上一节按调用次数计算的指数 Efficiency**，不能把两者合并为一个指标。（附录 A.2.2）

### 相同调用不一定返回相同信息

附录 B.4 明确说，`get_unread_messages` 读取后会把消息标为已读。因此两次参数相同的读取可能观察到不同状态。还有分页、增加 `limit`、事件更新或工单内容变化等情况。只看工具名称与参数，不能保证取得的信息重复。

论文的定性分析提到：agent 隔几轮重读工单与文件，或不断扩大消息查询范围。作者也承认逐步扩大查询有时合理。要对动态环境作严格的冗余判断，应同时查看当时环境状态、返回内容和先前已见信息；论文发布材料不足以完成这种逐轨迹复审。（§5.2.2）

## 六组主结果

下表转录表 3。Correctness 与 Efficiency 越高越好，Redundancy 越低越好；最后两列为工具调用的平均数、最大值与跨平台分布熵。所有结果是五次运行的汇总，最大调用数出现小数是因为它也是汇总量，不是一次运行出现了小数次调用。

| 模型与记忆 | Correctness | Efficiency | Redundancy | 调用数，均值 / 最大值 | 调用平台熵 |
| --- | ---: | ---: | ---: | ---: | ---: |
| GPT-5 + NoMem | 0.601 | 0.667 | 0.206 | 13.22 / 45.4 | 0.978 |
| GPT-5 + Mem0 | 0.610 | 0.656 | 0.214 | 13.29 / 45.0 | 1.023 |
| GPT-5 + Zep | 0.601 | 0.660 | 0.214 | 13.23 / 51.4 | 0.949 |
| Gemini 2.5 Pro + NoMem | 0.144 | 0.638 | 0.237 | 13.72 / 48.4 | 0.840 |
| Gemini 2.5 Pro + Mem0 | 0.118 | 0.658 | 0.240 | 12.53 / 46.8 | 0.838 |
| Gemini 2.5 Pro + Zep | 0.140 | 0.662 | 0.238 | 12.51 / 47.8 | 0.747 |

GPT-5 加 Mem0 后正确性从 0.601 到 0.610，增加 0.009；Zep 与 NoMem 同为 0.601。两种后端的冗余均从 0.206 增至 0.214，Efficiency 略降。这是一组具体集成与默认配置下的结果，没有证明记忆组件在所有环境都无效，也没有测试经过专门训练后使用这些工具的系统。

Gemini 2.5 Pro 加 Mem0 后正确性降低 0.026，加 Zep 后降低 0.004，但两者 **Efficiency 都比 NoMem 更高**。因此原文关于“记忆工具总使效率下降”的概括不能逐行成立。较少调用与较低正确性同时出现，也说明提高调用效率不必然改善任务完成。

GPT-5 的正确性约为对应 Gemini 条件的四倍或以上，但这只是本文模型、预算与执行方式的比较。工具返回成功不等于回答正确。附录表 5 中主实验六组工具调用成功率均值约为 0.917—0.934，远高于部分组的答案得分；模型能调用工具，并不表示取到了合适信息或完成了推理。表 5 还出现 Claude 命名的运行，但没有其完整主结果，不能据此补出第三套模型的正确性结论。

### 无模型调用的数据检查示例

下面的脚本在解压后的 `Memtrak` 根目录执行，只读取数据，不启动平台服务或 agent；需要 PyYAML。

```python
from collections import Counter
from pathlib import Path
import json
import yaml

root = Path(".")
configs = list((root / "test_configs").glob("*.yaml"))
counts = Counter()
questions = 0
pinned = 0
for path in configs:
    config = yaml.safe_load(path.read_text())
    benchmark = config["benchmark"]
    qs = benchmark["questions"]
    answers = benchmark["expected_answers"]
    assert len(qs) == len(answers), path.name
    events = json.loads((root / benchmark["event_history"]).read_text())
    assert isinstance(events, list), path.name
    counts[len(qs)] += 1
    questions += len(qs)
    pinned += bool(config.get("repository", {}).get("commit"))
print("instances", len(configs))
print("questions", questions)
print("question_counts", dict(counts))
print("pinned_repositories", pinned)
```

当前快照输出 46 个实例、143 问、7 个带提交哈希的配置。本次已经执行等价检查并运行该代码片段，不涉及答案生成或模型评分。

## 完整复现仍需要的材料

从公开论文与数据可以理解任务结构和问题，但不能直接复现主表。完整执行至少还需要以下信息：

1. **环境构建与重置。** 平台服务镜像、工具实现、事件调度、通知与已读状态，以及每个实例、每次重复运行之间的隔离方式。附录虽列出发送消息、创建和修改工单等接口，论文并未把 agent 主动推动组织后续事件作为本次研究任务。
2. **代码快照。** 每个仓库的确切提交、安装或导入方式，以及工具读取的文件树。浮动分支不能保证行号、默认值和函数计数仍与参考答案一致。
3. **记忆生命周期。** Mem0 / Zep 版本、实际 embedding 与 LLM 配置、工具提示、何时保存与读取、何时清空数据库，以及每次实验的用户或会话隔离。
4. **调用与评分记录。** 完整工具参数、返回结果、状态变化、每问原始答案、提取后的答案、judge 输入输出、失败重试及每层聚合方式；尤其需要澄清冗余的判定方向。
5. **模型与预算。** 模型快照、温度之外的推理参数、token 与轮数上限、超限后的处理，以及五次运行的随机性来源。

## 这项评测能够支持的结论

MEMTRACK 展示了一个有意义的任务组合：从多个工作平台获取信息，在不断明确的上下文中处理指代、旧方案与新状态，再用已有信息回答追问。主表显示，能够顺利调用工具的模型仍可能无法完成这些问答，简单接入一个记忆后端也未必改善结果。

但它同时测量检索、工具规划、代码理解和推理，尚未把记忆能力从这些因素中单独分离。其场景经过人工与模型合成，并依据模型表现增加难度；规模较小，公开快照与论文实例数也未完全一致。因此当前证据适合描述这套评测条件下的系统表现，不能外推成所有企业任务的成功率，或所有长期记忆方法的能力排序。

作者提出未来让 agent 不仅查询历史，还能创建工单、发送消息并参与组织后续发展，也可以扩展到销售和市场等领域。这些属于未来方向，不是主表已经验证的多 agent 协作或真实企业部署结果。（§6）
